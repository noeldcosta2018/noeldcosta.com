最佳的 SAP 实施策略，是适合您的业务、团队也能坚持下去的那一个。归根结底是三个决定。选哪种部署模式：S/4HANA Cloud Public Edition（通常通过 GROW with SAP）、Private Edition（通常通过 RISE with SAP）还是本地部署。选哪条迁移路径：绿地、棕地还是蓝地。选哪种上线模式：大爆炸式、分阶段还是混合式。本指南面向为 S/4HANA 选择实施方式的 CIO、项目总监和发起人。先回答下面五个问题，首先确定部署模式，再用对比表和决策树敲定另外两项。

在我参与过的 21 个项目中，规律始终如一。策略选择确实重要，但它只是决定中较小的那一半。更大的那一半，是在选项对比表被归档之后，团队能否在 14 个月的执行中守住纪律。

## 我如何选择 SAP 实施策略

目标不是最快或最便宜的方案，而是适合业务的方式：它的结构、文化、节奏、监管特征和长期目标。

### 先回答五个问题

1. 您的组织结构有多复杂：单一实体、多实体还是跨国？
2. 您的团队需要时间适应，还是现在就准备好迎接变化？
3. 您是从多个遗留系统、一个 ERP 迁移，还是从零开始？
4. 您内部有 SAP 专业能力，还是要依赖合作伙伴？
5. 上线时您能容忍多大程度的业务中断？

没有放之四海而皆准的答案。您的策略应该反映您自己的现实，而不是别人的成功故事。

### 2023 年到 2026 年之间发生了什么变化

**RISE 和 GROW 成为在云端购买 S/4HANA 的标准方式。** RISE with SAP 把软件（通常是 Private Edition）、由 SAP 运营的基础设施和技术运维，以及 BTP 额度打包在一份订阅里。GROW with SAP 则为采用标准流程的中型企业打包提供 Public Edition。先买许可再实施的传统方式在本地部署中依然存在，但大多数新的讨论都从 RISE 或 GROW 开始。

**Clean Core 从建议变成了架构。** 在 Public Edition 上，您无法修改核心：扩展必须使用已发布的 API，要么通过 ABAP Cloud 在栈内实现，要么在 SAP BTP 上并行（side-by-side）实现。在 Private Edition 和本地部署上仍然可以修改，但 SAP 的指导把修改视为最后手段，因为每一处修改都会增加升级工作。没有 Clean Core 经验的合作伙伴从第一周就开始制造技术债。

**AI 进入了实施工具。** SAP Joule for Consultants（自 2025 年 5 月起正式发布）基于 SAP 自己的内容回答配置问题。SAP Cloud ALM 可以根据 Fit-to-Standard 研讨会的记录起草需求。SAP Build Code（自 2024 年 3 月起正式发布）使用 Joule 生成 Java 和 JavaScript 扩展，Joule for developers 则从 2024 年底起增加了 ABAP 代码生成和解释功能。这些都不会改变战略选择。它们改变的是无论您作何选择，其中所需的成本和时间。

### 策略成败的关键

执行比选择更重要。不管选了哪种方式，都会出现四种失败模式。

1. **高管参与半途消失。** 在一家银行的 S/4HANA 实施中，CEO 出席了每一次重要会议，提出好问题，并为团队撑腰。项目按时完成，花费低于计划。而一家连锁门店的高管在启动会后把一切都甩了出去。由于没人能做决定，项目停滞了好几个月。
2. **把数据迁移当成 IT 任务。** 一位客户坚称其产品主数据“足够干净”。上线第一天，它的仓库就收到了三年前已停产产品的订单。清理花了好几周，还让它失去了一个大客户。数据迁移需要业务方负责。
3. **培训被省略或草草了事。** 一家公司 SAP 上线两周后，我去了他们的办公室。会计团队的显示器上贴满了便利贴，写着基本操作的提示；他们只接受了一天培训。他们的经理对我说：“我们只是在努力撑下去。”那家公司第一年在支持上多花了 20 万美元。
4. **员工绕开系统干活。** 我合作过的一家工厂以为培训就够了。工人们不信任新系统，又回到了电子表格。上线后再纠正，代价很高。变革管理包括沟通、参与和业务内部的推动者，培训只是其中一部分。

## 大爆炸式、分阶段和混合式上线

<compare-split title="两种主要上线模式" left-label="大爆炸式" left-points="一次切换全部上线|通往标准化流程的最快路径|前期成本较低，首日风险较高|需要严格的演练和干净的数据" right-label="分阶段" right-points="按模块、区域或职能分批上线|批次之间有更多纠偏空间|支持成本周期更长，需要维护的集成更多|需要持续的纪律和治理"></compare-split>

### 大爆炸式

我曾参与一家制造企业的 SAP 上线，所有系统在一个周末内完成切换。财务、采购、销售和制造在周一早上全部上线。过程很紧张，但那种清晰感非常有力。所有人一起迁移，不会困惑该相信哪个系统或哪份数据。

成功的原因是：团队多次演练切换，提前几周清理数据，并用真实测试用例培训用户。好处是更快统一、更快见效。坏处是没有容错空间。上线第一天定价问题影响到销售订单时，所有区域都受到了波及。

**适用情形：** 流程已标准化，团队已做好准备，领导层会守住范围。

### 分阶段

在另一个零售连锁项目中，我们采用了分阶段方式：先上财务、人力资源和采购，再上物流和 POS。整个过程花了一年多，但给了团队喘息的空间。人力资源团队用第一个月理顺工作流程，然后再培训其他所有人。这在大爆炸式中是不可能的。

代价是支持期更长，而且在已上线和尚未上线的系统之间流转的数据需要格外小心。

**适用情形：** 组织规模大或分布广，各区域流程不同，或领导层希望保留纠偏的空间。

### 混合式

有时答案是两者兼用。

我合作过的一家英国消费电子分销商需要尽快让财务和采购上线。它的仓库因为依赖关系太多还没准备好。于是财务和采购先上，物流和仓储随后跟进。一个领域用大爆炸式，另一个领域用分阶段。

混合式会增加协调工作。如果采购在 SAP 中而销售不在，两者之间的数据同步就需要精心设计，治理也必须始终保持敏锐。

**适用情形：** 各业务单元推进速度不同，部分部门必须更快行动，或季节性高峰使某些上线日期无法采用。

三者对比如下：

| 标准 | 大爆炸式 | 分阶段 | 混合式 |
|---|---|---|---|
| 时间线 | 最短：一次全部完成 | 较长：分散到多个批次 | 中等：有的领域快，有的慢 |
| 业务中断 | 上线出问题时影响大 | 较低：变化是渐进的 | 第一批影响大，之后较低 |
| 风险 | 问题波及整个业务 | 问题限于一个阶段内 | 集中在大爆炸式部分 |
| 成本 | 前期较低，出错代价高 | 总成本较高，紧急情况较少 | 介于两者之间；协调是变数 |
| 数据迁移 | 一个窗口内必须全部完成 | 分批加载，每阶段量较少 | 已上线与未上线系统之间的接口是难点 |
| 用户采纳 | 困难：一夜之间改变 | 较容易：逐步接触 | 第一批是先行者，后续批次向其学习 |
| 最适合 | 规模较小、流程标准、准备度高的组织 | 流程多样的大型分布式企业 | 部分单元已就绪、部分未就绪的多单元组织 |

## 绿地、棕地和蓝地

<decision-tree question="哪条迁移路径适合您的情况?" options="遗留系统分散，希望重新设计流程 => 绿地|流程健全，ECC 稳定，必须保留历史数据 => 棕地|多实体，希望部分复用并选择性迁移数据 => 蓝地"></decision-tree>

### 绿地：从头开始

我在一家零售公司的项目中见过这种方式。那家公司通过收购快速扩张，系统七零八落。我们从零开始，在 S/4HANA 上设计统一的流程。习惯了各自做法的团队起初有抵触。结果是各区域更加一致，报表更清晰，系统之间也能互通了。

**适用情形：** 遗留系统过于分散或定制过多，无法干净地迁移，而业务希望重新思考工作方式，而不是把旧习惯数字化。

### 棕地：转换与升级

在我早期的一个制造企业项目中，棕地是正确的选择。客户对其 ECC 系统做了大量定制，从头开始风险太大。我们专注于向 S/4HANA 的技术转换。用户适应得更快，我们也更早上线，但也把一些本该重新设计的笨拙流程带了过去。

**适用情形：** 现有流程健全且有文档，交易历史对审计或合规很重要，预算或时间紧张，且组织没有在重组。

### 蓝地：选择性迁移

蓝地（选择性数据迁移）只迁移特定的公司代码、业务单元或时间范围，而不是全部。它适合经历过并购或剥离的企业，或者系统中堆积了多年无人需要的数据的情况。您既能获得绿地式的流程自由，又能在选择保留的部分获得棕地式的连续性。我的 [ECC 到 S/4HANA 迁移指南](/zh-CN/ecc-to-s4hana-migration/)对这三条路径及其时间线有更深入的介绍。

## 先选部署模式

在 2018 年，上线模式和迁移路径就是策略的全部。到了 2026 年，有了第三个决定，而且它限定了另外两个：您运行哪个版本的 S/4HANA，以及如何购买。

<explainer-layers title="三个决定，自下而上" caption="版本限定了其上的一切。在 Public Edition 上，绿地是唯一的迁移路径。" layers="上线模式 => 大爆炸式、分阶段或混合式，取决于您能承受多大的中断|迁移路径 => 绿地、棕地或蓝地，在版本支持的范围内选择|部署模式 => Public Edition、Private Edition 或本地部署。先决定这一项" tones="||accent"></explainer-layers>

**S/4HANA Cloud Public Edition**（通常通过 GROW with SAP 购买，SAP 以 SAP Cloud ERP 名义销售）。多租户 SaaS，采用 SAP 标准流程，每六个月升级一次，不能修改核心。只能走绿地路线。实现价值最快，灵活性最小。最适合愿意采用 SAP 标准的中型企业。如果您的流程需要大幅偏离标准，它就是错误的答案。

**S/4HANA Cloud Private Edition**（通常通过 RISE with SAP 购买）。单租户，基础设施由 SAP 运营，每两年发布一个新版本，提供七年主流维护，配置和扩展空间更大。支持棕地、绿地和选择性迁移。是大多数大型企业项目的默认选择。

**S/4HANA 本地部署。** 由您或您的超大规模云服务商运营基础设施。扩展性和控制力最强，升级节奏最慢。推荐 Clean Core，但不强制。适合有严格数据驻留要求、内部 Basis 团队实力强的组织。SAP 的新功能越来越多地优先提供给云版本。

上线模式和迁移路径随后都在您选定的版本之内确定。Public Edition 项目按定义就是绿地。转换高度定制 ECC 系统的 Private Edition 项目通常是棕地或蓝地，规模大时通常是分阶段。关于 RISE 和 GROW 的商务方面，请参阅我的 [GROW with SAP](/zh-CN/sap-implementation/grow-with-sap/) 和 [RISE with SAP](/zh-CN/sap-implementation/rise-with-sap/) 页面。

## Fit-to-Standard 与定制

那是一个周四上午，设计研讨会进行到一半。IT 负责人刚演示完 SAP 标准的订单到收款流程。销售部门有人说：“是啊，但我们不是这么做的。”会议室一下安静了。几乎每个项目都会出现这一刻。

### Fit-to-Standard

坚持使用标准 SAP 可以缩短实施时间、降低长期维护成本。不存在的定制逻辑，升级也就无从破坏。在我参与的一个零售项目中，Fit-to-Standard 帮助客户在不到六个月内上线：活动部件更少，来回折腾更少，系统也更干净，便于将来升级。

**经验法则：** 只有在法规要求或该流程能带来真正竞争优势时才定制。绝不因为“我们一直都是这么做的”而定制。

### 实践中的 Clean Core

请每家合作伙伴提供其基于已发布 API 或 SAP BTP 构建扩展的案例。如果回答含糊，就把它当作危险信号。把本地部署习惯带进云项目的合作伙伴，从第一个冲刺起就在累积技术债。

### 当代码无法避免时

一些定制开发是必要的。SAP Build Code 和 Joule for developers 等 AI 工具降低了编写代码的成本，但没有降低维护代码的成本。

没人记录的定制逻辑会变成没人愿意碰的逻辑，并拖慢之后的每一次变更。没有哪个 AI 工具能解决这个问题，靠的是文档纪律。如果必须定制，就从一开始写好文档，基于已发布 API 或 BTP 构建，并与核心隔离。干净的定制有一笔可以收回的真实成本。不干净的定制则是一笔要一直付下去的成本。

## 按企业规模划分的成本范围

以下是我在 2026 年看到的 S/4HANA 项目总成本范围。决定金额的主要是企业规模和范围，而远非策略。请把它们作为预算规划的参考锚点，而不是报价；完整明细请参阅我的 [2026 年 SAP 实施成本范围](/zh-CN/sap-implementation-cost-and-budget-breakdown/)。

| 企业规模 | 典型项目总成本 |
|---|---|
| 小型（员工不足 200 人） | 8 万至 50 万美元 |
| 中型市场（员工 200 至 1,000 人） | 50 万至 200 万美元 |
| 大型企业（员工 1,000 至 10,000 人） | 200 万至 1,000 万美元以上 |
| 全球集团（员工 10,000 人以上） | 1,000 万至 5,000 万美元以上 |

策略只会让您在一个区间内移动，而不会跨越区间。绿地的前期成本高于棕地，大爆炸式则以较低的前期成本换取较高的首日风险。在此之上预留 10% 到 20% 的应急费用，并预计实施服务会占总额的 35% 到 50%。

部署模式是最常被低估的成本变量。把多年承诺加总后，RISE 和 GROW 的订阅并不比本地部署许可便宜。它们的价值在于基础设施责任的转移、更快实现价值以及可预测的订阅成本。选择 RISE 或 GROW 的理由很少是总成本，而是运营模式。

## 常见问题

<details>
<summary>什么是 SAP 实施策略？</summary>

它是企业部署 SAP 所采用的方式：范围、方法、部署模式、迁移路径、上线模式和时间线。2026 年的主要选择是部署模式（Public Edition、Private Edition 或本地部署）、迁移路径（绿地、棕地或蓝地）和上线模式（大爆炸式、分阶段或混合式）。

关键在于这个组合是否适合组织的准备程度、流程复杂度、监管特征和对中断的容忍度。

</details>

<details>
<summary>大爆炸式实施在什么情况下可行？</summary>

当流程已经标准化、用户培训充分、迁移前数据已清理、领导层会守住范围时。缺少其中任何一项，尤其是干净的数据和用户准备，它就是一场赌博。

上线时的问题会同时冲击所有方面。有准备，问题可控；没有准备，就是危机。

</details>

<details>
<summary>SAP 实施中的绿地和棕地有什么区别？</summary>

绿地从新系统开始，不带入任何遗留配置。您围绕 SAP 标准从零设计流程。棕地则是转换现有系统，保留交易历史和配置。

绿地前期成本更高，但能得到更干净、更面向未来的系统。棕地更快、中断更少，但会把变通做法和定制代码一并带过去。蓝地是中间路线：选择性迁移您选定的实体和数据。

</details>

<details>
<summary>RISE with SAP 和 GROW with SAP 有什么区别？</summary>

RISE with SAP 是 SAP 面向大型企业的订阅产品，通常基于 S/4HANA Cloud Private Edition，把由 SAP 运营的基础设施和技术运维纳入一份合同。我通常看到，含实施在内，大型企业的项目总额为 200 万至 1,000 万美元以上，全球集团为 1,000 万至 5,000 万美元以上，周期 9 到 18 个月。

GROW with SAP 面向中型企业，运行在采用 SAP 标准流程的 S/4HANA Cloud Public Edition 上。对中型企业，我通常看到含实施在内为 50 万至 200 万美元，周期约 6 到 9 个月。

二者之间如何选择，取决于企业规模，以及您的流程需要在多大程度上偏离 SAP 标准。

</details>

<details>
<summary>SAP 中的 Fit-to-Standard 是什么？为什么现在更重要？</summary>

Fit-to-Standard 指的是让您的流程适应 SAP 的标准功能，而不是定制 SAP 去迎合您现在的工作方式。它能缩短实施周期、降低维护成本，让升级更顺畅。

它现在更重要，是因为 Clean Core。在 Public Edition 上，根本无法修改核心。在 Private Edition 和本地部署上，每一处修改都会增加升级工作。要问的是：是否存在标准 SAP 无法满足的真正业务理由；如果有，您的合作伙伴能否基于已发布 API 或 SAP BTP 构建扩展。

</details>

<details>
<summary>SAP Activate 方法论有哪些阶段？</summary>

[SAP Activate](https://learning.sap.com/courses/discovering-sap-activate-implementation-tools-and-methodology/describing-the-methodology-structure) 有六个阶段。Discover（了解 SAP 的产品和业务论证），然后是四个核心交付阶段：Prepare（规划、治理、组建团队）、Explore（Fit-to-Standard 研讨会和待办事项）、Realize（以冲刺方式配置、扩展、测试）和 Deploy（切换、上线和上线后强化支持）。Run 涵盖上线后的运营。

大多数项目在 Realize 阶段损失时间，尤其是在测试中暴露数据质量问题或定制范围扩大时。能否在 Realize 阶段守住严格的范围基线，决定了项目是按时上线还是一路漂移。

</details>

<details>
<summary>SAP 实施为什么会失败？</summary>

大多数失败可归结为四个原因：高管参与在启动后消失，数据迁移被当作 IT 任务，变革管理局限于培训手册，以及没有 Clean Core 经验的合作伙伴制造的技术债在第一次升级时暴露。

技术本身很少失败。项目失败是因为决定迟迟做不出来、脏数据进入新系统、用户找到变通办法，或者定制必须重建。策略很重要，执行纪律更重要。

</details>

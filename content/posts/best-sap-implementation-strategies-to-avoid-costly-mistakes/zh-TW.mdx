最佳的 SAP 導入策略，是符合您的事業、團隊也能堅持下去的那一個。說到底是三個決定。選哪種部署模式：S/4HANA Cloud Public Edition（通常透過 GROW with SAP）、Private Edition（通常透過 RISE with SAP）還是地端部署。選哪條移轉路徑：綠地、棕地還是藍地。選哪種上線模式：大爆炸式、分階段還是混合式。本指南寫給為 S/4HANA 選擇導入方式的 CIO、專案總監與贊助者。先回答下面五個問題，首先決定部署模式，再用比較表與決策樹敲定另外兩項。

在我參與過的 21 個專案中，模式始終一致。策略選擇確實重要，但它只是決定中較小的那一半。較大的那一半，是在選項比較試算表被歸檔之後，團隊能否在 14 個月的執行期間守住紀律。

## 我如何選擇 SAP 導入策略

目標不是最快或最便宜的方案，而是符合事業的方式：它的組織結構、文化、步調、法規特性與長期目標。

### 先回答五個問題

1. 您的組織結構有多複雜：單一法人、多法人還是跨國？
2. 您的團隊需要時間調適，還是現在就準備好迎接變化？
3. 您是從多個舊系統、一套 ERP 移轉，還是從零開始？
4. 您內部有 SAP 專業能力，還是要仰賴合作夥伴？
5. 上線時您能容忍多大程度的營運中斷？

沒有放諸四海皆準的答案。您的策略應該反映您自己的現實，而不是別人的成功故事。

### 2023 年到 2026 年之間改變了什麼

**RISE 與 GROW 成為在雲端購買 S/4HANA 的標準方式。** RISE with SAP 把軟體（通常是 Private Edition）、由 SAP 營運的基礎架構與技術維運，以及 BTP 額度包進同一份訂閱。GROW with SAP 則為採用標準流程的中型企業包裝 Public Edition。先買授權再導入的傳統方式在地端部署中仍然存在，但多數新的討論都從 RISE 或 GROW 開始。

**Clean Core 從建議變成了架構。** 在 Public Edition 上，您無法修改核心：擴充必須使用已發布的 API，可以透過 ABAP Cloud 在堆疊內實作，或在 SAP BTP 上以並行（side-by-side）方式實作。在 Private Edition 與地端部署上仍然可以修改，但 SAP 的指引把修改視為最後手段，因為每一處修改都會增加升級工作。沒有 Clean Core 經驗的合作夥伴，從第一週就開始製造技術債。

**AI 進入了導入工具。** SAP Joule for Consultants（自 2025 年 5 月正式推出）根據 SAP 自己的內容回答設定問題。SAP Cloud ALM 可以從 Fit-to-Standard 工作坊的逐字稿起草需求。SAP Build Code（自 2024 年 3 月正式推出）使用 Joule 產生 Java 與 JavaScript 擴充，Joule for developers 則自 2024 年底起加入 ABAP 程式碼產生與說明功能。這些都不會改變策略選擇。它們改變的是無論您做何選擇，其中所需的成本與時間。

### 策略成敗的關鍵

執行比選擇更重要。不論選了哪種方式，都會出現四種失敗模式。

1. **高層參與半途消失。** 在一家銀行的 S/4HANA 導入中，執行長出席每一場重要會議，提出好問題，並為團隊撐腰。專案準時完成，花費低於計畫。另一家連鎖門市的高層在啟動會議後就把一切丟給別人。由於沒有人能做決定，專案停擺了好幾個月。
2. **把資料移轉當成 IT 任務。** 一位客戶堅稱其產品主檔資料「夠乾淨了」。上線第一天，它的倉庫就收到三年前已停產產品的訂單。清理花了好幾週，還讓它失去一位大客戶。資料移轉需要業務端負責。
3. **訓練被省略或草草帶過。** 一家公司 SAP 上線兩週後，我去了他們的辦公室。會計團隊的螢幕上貼滿了便利貼，寫著基本操作的提醒；他們只受過一天訓練。他們的主管對我說：「我們只是努力撐下去而已。」那家公司第一年在支援上多花了 20 萬美元。
4. **員工繞過系統做事。** 我合作過的一家工廠以為訓練就夠了。工人們不信任新系統，又回頭使用試算表。上線後再修正，代價很高。變革管理包含溝通、參與以及業務內部的推動者，訓練只是其中一部分。

## 大爆炸式、分階段與混合式上線

<compare-split title="兩種主要上線模式" left-label="大爆炸式" left-points="一次切換全部上線|通往標準化流程的最快路徑|前期成本較低，首日風險較高|需要嚴謹的演練與乾淨的資料" right-label="分階段" right-points="依模組、區域或職能分批上線|批次之間有更多修正方向的空間|支援成本拉長，需要維護的整合更多|需要持續的紀律與治理"></compare-split>

### 大爆炸式

我曾參與一家製造企業的 SAP 上線，所有系統在一個週末內完成切換。財務、採購、銷售與製造在週一早上全部上線。過程很緊繃，但那份清晰感非常有力量。所有人一起轉移，不會困惑該相信哪個系統或哪份資料。

成功的原因是：團隊多次演練切換、提前幾週清理資料，並用真實測試案例訓練使用者。好處是更快對齊、更快見效。壞處是沒有犯錯的空間。上線第一天定價問題影響到銷售訂單時，每個區域都受到波及。

**適用情境：** 流程已標準化，團隊已準備好，經營層會守住範圍。

### 分階段

在另一個零售連鎖專案中，我們採取分階段方式：先上財務、人資與採購，再上物流與 POS。整個過程花了一年多，但給了團隊喘息空間。人資團隊用第一個月理順工作流程，然後才訓練其他所有人。這在大爆炸式中是不可能的。

代價是支援期較長，而且在已上線與尚未上線的系統之間流動的資料需要格外小心。

**適用情境：** 組織規模大或分布廣、各區域流程不同，或經營層希望保留修正方向的空間。

### 混合式

有時答案是兩者並用。

我合作過的一家英國消費性電子經銷商需要儘快讓財務與採購上線。它的倉庫因為相依關係太多還沒準備好。於是財務與採購先上，物流與倉儲隨後跟進。一個領域採大爆炸式，另一個領域採分階段。

混合式會增加協調工作。如果採購在 SAP 中而銷售不在，兩者之間的資料同步就需要審慎設計，治理也必須自始至終保持敏銳。

**適用情境：** 各事業單位推進速度不同、部分部門必須更快行動，或季節性高峰讓某些上線日期無法採用。

三者比較如下：

| 標準 | 大爆炸式 | 分階段 | 混合式 |
|---|---|---|---|
| 時程 | 最短：一次全部完成 | 較長：分散到多個批次 | 中等：有些領域快，有些慢 |
| 營運中斷 | 上線出問題時影響大 | 較低：變化是漸進的 | 第一批影響大，之後較低 |
| 風險 | 問題波及整個事業 | 問題侷限在單一階段 | 集中在大爆炸式的部分 |
| 成本 | 前期較低，出錯代價高 | 總成本較高，緊急狀況較少 | 介於兩者之間；協調是變數 |
| 資料移轉 | 一個時間窗內必須全部完成 | 分批載入，每階段量較少 | 已上線與未上線系統之間的介面是難點 |
| 使用者採用 | 困難：一夕之間改變 | 較容易：逐步接觸 | 第一批是先行者，後續批次向其學習 |
| 最適合 | 規模較小、流程標準、準備度高的組織 | 流程多樣的大型分散式企業 | 部分單位已就緒、部分未就緒的多單位組織 |

## 綠地、棕地與藍地

<decision-tree question="哪條移轉路徑適合您的情況?" options="舊系統分散，希望重新設計流程 => 綠地|流程健全，ECC 穩定，必須保留歷史資料 => 棕地|多法人，希望部分沿用並選擇性移轉資料 => 藍地"></decision-tree>

### 綠地：從頭開始

我在一家零售公司的專案中見過這種方式。那家公司透過併購快速成長，系統四分五裂。我們從零開始，在 S/4HANA 上設計統一的流程。習慣各自做法的團隊起初有所抗拒。結果是各區域更一致、報表更清楚，系統之間也能互通了。

**適用情境：** 舊系統過於分散或客製過多，無法乾淨地移轉，而事業希望重新思考工作方式，而不是把舊習慣數位化。

### 棕地：轉換與升級

在我早期的一個製造企業專案中，棕地是正確的決定。客戶對其 ECC 系統做了大量客製，從頭來過的風險太高。我們專注於轉換到 S/4HANA 的技術工作。使用者適應得更快，我們也更早上線，但也把一些本該重新設計的笨拙流程帶了過去。

**適用情境：** 現有流程健全且有文件，交易歷史對稽核或法遵很重要，預算或時程吃緊，而且組織沒有在重組。

### 藍地：選擇性移轉

藍地（選擇性資料移轉）只移轉特定的公司代碼、事業單位或時間範圍，而不是全部。它適合經歷過併購或分拆的企業，或系統中累積了多年沒人需要之資料的情況。您既能得到綠地式的流程自由，又能在選擇保留的部分得到棕地式的延續性。我的 [ECC 到 S/4HANA 移轉指南](/zh-TW/ecc-to-s4hana-migration/)對這三條路徑與其時程有更深入的說明。

## 先選部署模式

在 2018 年，上線模式與移轉路徑就是策略的全部。到了 2026 年，有了第三個決定，而且它限定了另外兩個：您執行哪個版本的 S/4HANA，以及如何購買。

<explainer-layers title="三個決定，由下而上" caption="版本限定了其上的一切。在 Public Edition 上，綠地是唯一的移轉路徑。" layers="上線模式 => 大爆炸式、分階段或混合式，取決於您能承受多大的中斷|移轉路徑 => 綠地、棕地或藍地，在版本支援的範圍內選擇|部署模式 => Public Edition、Private Edition 或地端部署。先決定這一項" tones="||accent"></explainer-layers>

**S/4HANA Cloud Public Edition**（通常透過 GROW with SAP 購買，SAP 以 SAP Cloud ERP 名義銷售）。多租戶 SaaS，採用 SAP 標準流程，每六個月升級一次，不能修改核心。只能走綠地。實現價值最快，彈性最小。最適合願意採用 SAP 標準的中型企業。如果您的流程需要大幅偏離標準，它就是錯誤的答案。

**S/4HANA Cloud Private Edition**（通常透過 RISE with SAP 購買）。單一租戶，基礎架構由 SAP 營運，每兩年推出新版本並提供七年主流維護，設定與擴充空間也更大。支援棕地、綠地與選擇性移轉。是多數大型企業專案的預設選擇。

**S/4HANA 地端部署。** 由您或您的超大規模雲端服務商營運基礎架構。擴充性與掌控度最高，升級節奏最慢。建議採用 Clean Core，但不強制。適合有嚴格資料落地要求、內部 Basis 團隊實力堅強的組織。SAP 的新功能愈來愈常優先提供給雲端版本。

上線模式與移轉路徑接著都在您選定的版本之內決定。Public Edition 專案依定義就是綠地。轉換高度客製 ECC 系統的 Private Edition 專案通常是棕地或藍地，規模大時通常是分階段。關於 RISE 與 GROW 的商務面，請參閱我的 [GROW with SAP](/zh-TW/sap-implementation/grow-with-sap/) 與 [RISE with SAP](/zh-TW/sap-implementation/rise-with-sap/) 頁面。

## Fit-to-Standard 與客製化

那是一個週四上午，設計工作坊進行到一半。IT 負責人剛示範完 SAP 標準的訂單到收款流程。業務部門有人說：「是啦，但我們不是這樣做的。」會議室頓時安靜下來。幾乎每個專案都會出現這一刻。

### Fit-to-Standard

維持標準 SAP 能縮短導入時間、降低長期維護成本。不存在的客製邏輯，升級也就無從破壞。在我參與的一個零售專案中，Fit-to-Standard 幫助客戶在不到六個月內上線：變動的環節更少、來回溝通更少，系統也更乾淨，便於日後升級。

**經驗法則：** 只有在法規要求，或該流程能帶來真正的競爭優勢時才客製。絕不因為「我們一直都是這樣做的」而客製。

### 實務上的 Clean Core

請每家合作夥伴提供其以已發布 API 或 SAP BTP 建置擴充的案例。如果回答含糊，就把它視為警訊。把地端習慣帶進雲端專案的合作夥伴，從第一個衝刺就開始累積技術債。

### 當程式碼無可避免時

部分客製開發是必要的。SAP Build Code 與 Joule for developers 等 AI 工具降低了撰寫程式碼的成本，卻沒有降低維護它的成本。

沒有人記錄的客製邏輯，會變成沒有人想碰的邏輯，並拖慢之後的每一次變更。沒有任何 AI 工具能解決這個問題，靠的是文件紀律。如果必須客製，就從一開始寫好文件，以已發布 API 或 BTP 建置，並與核心隔離。乾淨的客製有一筆可以回收的真實成本。不乾淨的客製則是一筆要一直付下去的成本。

## 依企業規模劃分的成本範圍

以下是我在 2026 年看到的 S/4HANA 專案總成本範圍。決定金額的主要是企業規模與範圍，遠勝於策略。請把它們當作預算規劃的參考基準，而不是報價；完整明細請參閱我的 [2026 年 SAP 導入成本範圍](/zh-TW/sap-implementation-cost-and-budget-breakdown/)。

| 企業規模 | 典型專案總成本 |
|---|---|
| 小型（員工不到 200 人） | 8 萬至 50 萬美元 |
| 中型市場（員工 200 至 1,000 人） | 50 萬至 200 萬美元 |
| 大型企業（員工 1,000 至 10,000 人） | 200 萬至 1,000 萬美元以上 |
| 全球集團（員工 10,000 人以上） | 1,000 萬至 5,000 萬美元以上 |

策略只會讓您在一個區間內移動，不會跨越區間。綠地的前期成本高於棕地，大爆炸式則以較低的前期成本換取較高的首日風險。在此之上另外預留 10% 到 20% 的預備金，並預期導入服務會占總額的 35% 到 50%。

部署模式是最常被低估的成本變數。把多年承諾加總後，RISE 與 GROW 的訂閱並不比地端授權便宜。它們的價值在於基礎架構責任的轉移、更快實現價值，以及可預測的訂閱成本。選擇 RISE 或 GROW 的理由很少是總成本，而是營運模式。

本指南是我的[SAP 導入指南](/sap-implementation/)的一部分，該指南彙整了從商業論證到上線的所有主題。

## 常見問題

<details>
<summary>什麼是 SAP 導入策略？</summary>

它是企業部署 SAP 所採用的方式：範圍、方法、部署模式、移轉路徑、上線模式與時程。2026 年的主要選擇是部署模式（Public Edition、Private Edition 或地端部署）、移轉路徑（綠地、棕地或藍地）以及上線模式（大爆炸式、分階段或混合式）。

重點在於這個組合是否符合組織的準備程度、流程複雜度、法規特性，以及對營運中斷的容忍度。

</details>

<details>
<summary>大爆炸式導入在什麼情況下可行？</summary>

當流程已經標準化、使用者訓練充足、移轉前資料已清理，而且經營層會守住範圍時。缺少其中任何一項，尤其是乾淨的資料與使用者準備，它就是一場賭博。

上線時的問題會同時衝擊所有層面。有準備，問題可控；沒有準備，就是危機。

</details>

<details>
<summary>SAP 導入的綠地與棕地有什麼差別？</summary>

綠地從新系統開始，不帶入任何舊系統設定。您以 SAP 標準為核心從零設計流程。棕地則是轉換現有系統，保留交易歷史與設定。

綠地前期成本較高，但能得到更乾淨、更能面向未來的系統。棕地較快、中斷較少，但會把權宜做法與客製程式碼一併帶過去。藍地是中間路線：選擇性移轉您選定的法人與資料。

</details>

<details>
<summary>RISE with SAP 與 GROW with SAP 有什麼差別？</summary>

RISE with SAP 是 SAP 為大型企業推出的訂閱方案，通常以 S/4HANA Cloud Private Edition 為基礎，把由 SAP 營運的基礎架構與技術維運納入同一份合約。我通常看到，含導入在內，大型企業的專案總額為 200 萬至 1,000 萬美元以上，全球集團為 1,000 萬至 5,000 萬美元以上，時程 9 到 18 個月。

GROW with SAP 鎖定中型企業，執行於採用 SAP 標準流程的 S/4HANA Cloud Public Edition。對中型企業，我通常看到含導入在內為 50 萬至 200 萬美元，時程約 6 到 9 個月。

兩者之間如何選擇，取決於企業規模，以及您的流程需要偏離 SAP 標準多少。

</details>

<details>
<summary>SAP 的 Fit-to-Standard 是什麼？為什麼現在更重要？</summary>

Fit-to-Standard 是讓您的流程配合 SAP 的標準功能，而不是客製 SAP 去遷就您現在的工作方式。它能縮短導入時程、降低維護成本，讓升級更順利。

它現在更重要，是因為 Clean Core。在 Public Edition 上，根本無法修改核心。在 Private Edition 與地端部署上，每一處修改都會增加升級工作。該問的是：是否存在標準 SAP 無法滿足的真正業務理由；如果有，您的合作夥伴能否以已發布 API 或 SAP BTP 建置擴充。

</details>

<details>
<summary>SAP Activate 方法論有哪些階段？</summary>

[SAP Activate](https://learning.sap.com/courses/discovering-sap-activate-implementation-tools-and-methodology/describing-the-methodology-structure) 有六個階段。Discover（了解 SAP 的方案與商業論證），接著是四個核心交付階段：Prepare（規劃、治理、組建團隊）、Explore（Fit-to-Standard 工作坊與待辦清單）、Realize（以衝刺方式設定、擴充、測試）以及 Deploy（切換、上線與上線後加強支援）。Run 涵蓋上線後的營運。

多數專案在 Realize 階段損失時間，尤其是測試中浮現資料品質問題，或客製範圍不斷擴大時。能否在 Realize 期間守住嚴謹的範圍基準，決定了專案是準時上線還是一路漂移。

</details>

<details>
<summary>SAP 導入為什麼會失敗？</summary>

多數失敗可歸結為四個原因：高層參與在啟動後消失、資料移轉被當作 IT 任務、變革管理侷限於訓練手冊，以及缺乏 Clean Core 經驗的合作夥伴所製造、在第一次升級時浮現的技術債。

技術本身很少失敗。專案失敗是因為決定遲遲做不出來、髒資料進入新系統、使用者找到權宜做法，或客製必須重建。策略很重要，執行紀律更重要。

</details>

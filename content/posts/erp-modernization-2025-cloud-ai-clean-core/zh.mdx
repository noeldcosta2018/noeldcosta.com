2026 年的 ERP 现代化，意味着按顺序做出三个决定：您的 ERP 应该不再做什么，您将如何保持其核心干净，以及您的数据是否好到足以让 AI 发挥作用。对 SAP 客户而言，这三个决定背后有一个硬性日期：[ECC 主流维护于 2027 年 12 月 31 日结束](https://news.sap.com/2020/02/sap-s4hana-maintenance-2040-clarity-choice-sap-business-suite-7/)，付费的延长维护可到 2030 年底。

本文写给已经完成分析、现在必须执行的 CIO、CFO 和企业架构师。内容涵盖推动行动的各种力量、主干加卫星的架构、Clean Core、治理缺口、AI 就绪度，以及未来 18 个月的风险表。

2024 年，大多数领导者还在争取时间：研究 ECC 的时间线，争论混合架构与完整迁移，运行沙箱测试却不做承诺。那个窗口已经关闭。ECC 和 Oracle E-Business Suite 环境中的技术债务不再是理论上的。它体现在更新后失败的回归测试里，体现在无人负责的自定义代码的审计发现里，也体现在计划系统和执行系统之间搬运数据要花 12 小时这件事上。

## 推动行动的四种力量

**截止期限。** 2027 年之后，ECC 客户可以购买延长维护，至 2030 年底，费用更高。再往后，SAP 提供一项针对 2031 至 2033 年的 ERP 私有版过渡选项，但只能通过 RISE，而且 SAP 明确表示，这是一项付费的过渡方案，而不是维护延期。与此同时，[The Register 报道的 Gartner 研究](https://www.theregister.com/software/2025/03/20/legacy-sap-erp-customers-still-foot-dragging-move-to-s/4hana/1352379)发现，到 2024 年底，SAP 约 35,000 家 ECC 客户中，只有约 39% 购买或订阅了 S/4HANA 许可证。获得许可不等于已完成迁移。合作伙伴市场将会吃紧。

**预算模式。** 云 ERP 把支出从资本性的许可证转向订阅。这听起来更干净。实际上，CFO 们发现云成本更难预测：在 RISE with SAP 和 SAP GROW 下，Full User Equivalent（FUE）的增长、附加服务和集成开销，增加了原始业务案例中没有的成本。

**财务和供应链的碎片化。** 财务团队在应付和应收上运行 AI，而审计流程仍在使用为另一个时代设计的模板。供应链只实现了部分现代化：计划用 SAP IBP，执行用较老的仓库管理系统，采购用 Ariba，收货却是手工的。瓶颈不在技术，而在系统之间的衔接处。

**ERP 是一层，而不是整个技术栈。** 在许多企业里，ServiceNow 负责流程编排，Salesforce 负责客户工作流，Workday 或 SuccessFactors 负责人力资源生命周期。ERP 已经成为财务主干，而不是 1990 年代宣传的那种一体化流程枢纽。

## 架构：主干加卫星

大多数企业架构师如今采用的模型，是由专业平台环绕的财务主干（SAP S/4HANA 或 Oracle Fusion）。

| 层 | 放在这里的内容 | 不放在这里的内容 |
|---|---|---|
| 财务主干 | 总账、管理会计、采购、库存、制造执行、法定关账 | 工作流审批、CRM、人力资源管理、分析 |
| 工作流 | 用于 IT 和运营流程、审批、变更管理的 ServiceNow | 交易记录保存 |
| 客户互动 | Salesforce 或 SAP Sales and Service Cloud | 财务处理 |
| 人力资源 | Workday 或 SAP SuccessFactors | 运营交易 |
| 分析 | SAP Business Data Cloud、SAP Analytics Cloud、Power BI、Snowflake | 记录系统 |

这种分离是有意为之的。把一切都塞回 SAP，会增加摩擦、拖慢更新，并模糊归属。把 CRM、工作流、分析和 EHS 塞进一个系统，正是让早期项目那么痛苦的原因。

要问的问题是：ERP 不应该再负责什么？跳过这个问题，您就会在更新的许可证上重建同样的庞然大物。我那篇关于 [SAP 与 ServiceNow 的 ERP 现代化](/zh-CN/erp-modernization-sap-servicenow/)的文章，演示了其中一种拆分方式。

## Clean Core：已分级，实际上不是可选项

2025 年 8 月，SAP 用[四个 Clean Core 等级](https://news.sap.com/2025/08/extend-sap-s4hana-cloud-right-way-clean-clear/)取代了它的三层扩展模型。A 级只使用已发布的稳定 API，可以在 SAP BTP 上并行（side-by-side）扩展，也可以用 ABAP Cloud 在系统内扩展。B 级使用 SAP 仍视为干净的经典 API 和技术。C 级触及内部对象，需要特殊措施。D 级则不是 Clean Core。

Public Edition（SAP Cloud ERP，以 SAP GROW 销售）只允许 A 级，因此由平台强制 Clean Core，并每年承接两次主要版本发布。Private Edition（RISE 下的 SAP Cloud ERP Private）和本地部署仍然允许经典扩展，所以那里的 Clean Core 取决于治理。无论哪种情况，高度定制的系统都会让每次升级变成一个项目，让每次回归测试变成一场危机。

Clean Core 对您的要求：

1. 把未使用的自定义代码从核心里拿出来。您保留的每个自定义程序，都是每次升级要测试的东西。
2. 尽可能在 A 级构建新的扩展：在 SAP BTP 上，用 SAP Build，或在系统内用 ABAP Cloud。
3. 凡是 SAP 提供标准流程的地方就用标准流程，只有在法规要求或确实有竞争差异时才定制。

抵触是文化上的，而不是技术上的。依赖了 15 年自定义代码的业务负责人，仍然期望它“直接被重新实现”。这种期望属于 2012 年。

一个典型的 ECC 环境带有 1,500 至 3,000 个自定义对象，这是基于我在制造业和服务业所做评估得出的，而其中只有约四分之一显示有活跃的业务使用。其余的是历史包袱，抬高迁移成本，并带来审计风险。

务实的做法：现在就运行一次使用情况扫描。淘汰不活跃的部分。在设计开始之前公布一份删减清单。从第一周就规划 Clean Core 的团队，升级体验要比把它当作需要绕开的约束的团队好得多。我的 [Clean Core 战略](/zh-CN/sap-clean-core-strategy-what-it-means-for-your-business/)一文讲了具体方法。

## 没人谈论的治理缺口

当 ERP 只是众多层中的一层，归属问题就变得至关重要。谁拥有：

1. Salesforce 与 ERP 之间的 API？
2. 横跨 SAP 和 ServiceNow 的工作流？
3. 两个系统同时需要更新时相互冲突的变更优先级？

我见过这种情况让上线延迟数月。团队直到集成测试暴露出重叠时，才意识到自己卡住了。

在一个案例中，五个系统在触碰同一条供应商主数据记录。五个。没有人有主数据归属文件，也没有人设计过谁可以在哪个系统里更改什么。这不是技术失败。这是被技术暴露出来的治理失败。

## AI 就绪度：先有干净的数据

ERP 中的 AI 价值是真实的，但它取决于数据质量和干净的架构。Joule 现在覆盖 S/4HANA、SuccessFactors、Ariba 和其他 SAP 产品，SAP 的智能体运行在 Joule 助手之下。SAP BTP 上的智能体用例正在交付，不是幻灯片。它们都依赖于干净、一致、结构化的数据。

如果您的数据有重复、编码不一致，或存放在 S/4HANA 不认识的自定义表里，AI 就没有可靠的东西可用。在应付账款上运行 AI 的财务团队，会很快发现这一点：因为供应商主数据从未清理过，发票被匹配到错误的供应商。

行之有效的顺序：先 Clean Core，其次数据治理，第三分析，第四 AI。跳过步骤不会加快任何事情。它只会把问题推到后面。

## 未来 18 个月的风险

| 风险 | 信号 | 务实的应对 |
|---|---|---|
| ECC 截止期限压力 | 主流维护于 2027 年 12 月结束；到 2024 年底，大多数 ECC 客户尚未购买 S/4HANA 许可证 | 现在就锁定合作伙伴的资源计划；美国资深顾问的日费率已达 1,800 至 3,500 美元 |
| 自定义代码债务 | 1,500 至 3,000 个自定义对象，约四分之一在活跃使用 | 运行使用情况扫描，公布删减清单，启动淘汰冲刺 |
| 版本发布干扰 | 版本发布与财务关账和供应链高峰碰撞 | 把发布窗口设在远离关账的时间；自动化回归测试 |
| 数据迁移风险 | 数据协调太晚，产生被团队误标为缺陷的问题 | 尽早评估规模；在设计冻结前核对银行、税务和合规数据 |
| 集成归属缺口 | 五个或更多系统触碰共享的主数据 | 公布一份权限矩阵；每个数据对象只有一位负责人 |
| 两套生命周期工具 | 混合环境同时运行 Solution Manager 和 SAP Cloud ALM | 云项目默认使用 Cloud ALM；Solution Manager 7.2 的主流维护于 2027 年底结束 |

关于这些风险在交付层面的版本，请看[ERP 现代化需要避免的十个错误](/zh-CN/erp-modernization-mistakes/)，关于迁移路径本身，请看 [ECC 到 S/4HANA 迁移指南](/zh-CN/ecc-to-s4hana-migration/)。

## 常见问题

<details>
<summary>SAP S/4HANA 中的 Clean Core 是什么？</summary>

尽可能让 S/4HANA 贴近标准，并把扩展放在升级不会破坏它们的地方。自 2025 年 8 月起，SAP 把扩展从 A 级（只用已发布的 API，在 SAP BTP 上，或在系统内用 ABAP Cloud）到 D 级（不干净）分级。商业上的理由是保护升级：干净的系统几天就能承接新版本，高度定制的系统则把每次发布都变成一个项目。

</details>

<details>
<summary>ERP 的主干加卫星架构是什么？</summary>

ERP（SAP S/4HANA 或 Oracle Fusion）处理它本就擅长的事：财务记录、库存、采购、制造交易和法定报告。其余交给专业平台：ServiceNow 管工作流，Salesforce 管客户互动，Workday 或 SuccessFactors 管人力资源，分析平台管洞察。把这些全部塞进 ERP，会造成更新缓慢、高度定制的庞然大物。

</details>

<details>
<summary>企业应如何应对 2027 年的 SAP ECC 截止期限？</summary>

从 SAP Readiness Check 开始。它会揭示自定义代码量、附加组件依赖和数据规模，这三个因素决定了您走 Brownfield、Greenfield 还是选择性转换。复杂的企业迁移从评估到上线通常需要 18 至 24 个月，所以如果您到现在还没有选定方案、也没有开始与合作伙伴洽谈，2027 年上线已经很紧张。延长维护到 2030 年费用更高，买到的是时间，而不是创新。

</details>

<details>
<summary>AI 在 ERP 现代化中何时有价值，何时没有？</summary>

当数据干净、一致、结构化，且流程规则明确时：应付账款自动化、需求预测和财务交易中的异常检测都是经过验证的用例。AI 不是绕过糟糕数据或治理缺口的捷径。基于糟糕输入做出的决策，比人工错误更难发现。Clean Core、数据治理和稳定的流程要先行。

</details>

<details>
<summary>企业在 ERP 现代化中犯的最大错误是什么？</summary>

把它当作技术项目，结果在业务负责人进场之前，Clean Core 的争论就已经输了。在设计之后才启动数据治理，而第一周做出的决定本可以省下几个月的测试。没有定义 ERP 应该不再做什么，导致核心范围默认膨胀，上一个庞然大物就是这样造出来的。

</details>

<details>
<summary>ERP 现代化要花多少钱？</summary>

中型市场公司从 ECC 到 S/4HANA 的 Brownfield 转换，实施成本通常为 200 万至 800 万美元，外加持续的订阅费用。涉及全球范围、大量定制和众多实体的企业级项目，可能达到 2,000 万至 1 亿美元以上。除许可证外，还要对集成、测试和运营支持建模，在 RISE 和 SAP GROW 下，要对整个合同期内的 FUE 增长建模。

</details>

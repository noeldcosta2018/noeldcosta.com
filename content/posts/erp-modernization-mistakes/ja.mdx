ERPモダナイゼーションの失敗は、リアルタイムで認識されることはめったにありません。表面化するのは後になってからです。go-live後、期待していた効率化が実現しなかったとき、あるいは業務上の回避策が再び現れたときです。多くは技術的な問題ではありません。戦略上の問題であり、計画段階や初期実行の中で少しずつ入り込みます。

私が主導し、立て直し、あるいは失速していくのを見てきた21件のSAPプログラムを通じて言えるのは、経験豊富なチームが運営し、十分な予算があり、外部アドバイザーも一式そろっていても、プロジェクトは期待を下回ることがあるということです。原因はシステムそのものではないことがほとんどです。オーナーシップの欠如、統合計画の不足、そして相互依存する意思決定を行うチーム間のコミュニケーション不全です。

以下の10のパターンは、私が最もよく目にするものです。記事の最後では、2026年のSAPの変化（RISE with SAP、GROW with SAP、clean-core、Joule、SAP Cloud ALM）によって、どの失敗がまだ許容でき、どの失敗はもはや許されないのかを整理します。

## 10の失敗

### 失敗1：go-liveをゴールだと考えること

go-liveをゴールラインのように扱う考え方は、私が見てきた中でも最も高くつくパターンの1つです。システムが稼働すると、多くのチームは大仕事は終わったと考えます。ですが、本当のプレッシャーが始まるのはまさにそこからです。日々の業務、変化する要件、実際のユーザー行動が、設計された内容にぶつかり始めるからです。

2024年の欧州の金融サービス案件では、go-live直後にステアリングコミッティが解散しました。6か月後には利用定着が頭打ちになり、バックログの責任者もいませんでした。経営陣はすでに次へ移っていました。本番稼働したシステムが必ず生み出す機能追加、修正、ガバナンス判断に対応するプロセスが存在しなかったのです。立て直しには、ガバナンス会議体の再立ち上げとhypercare延長のために、6桁ドルの追加費用がかかりました。

**対策：** go-live後6〜12か月のガバナンス期間を、専用予算付きで計画してください。ステアリングコミッティの権限をgo-live後も延長してください。監視すべきはシステム稼働率だけではなく、業務プロセスの整合性です。導入後の品質ゲートを、明確な責任者付きで設定してください。

### 失敗2：レガシープロセスを見直さずに移行すること

2023年の欧州製造業案件では、旧システムの承認チェーンがそのまま再構築されているのを見つけました。関係者の半分は、現行プロセスには実際には関与していませんでした。それでも、その手順が今も妥当なのかを誰も立ち止まって問いませんでした。その結果は、古いワークフローを動かす最新ERPです。これは進歩ではありません。単に、今あるものの高コスト版です。

S/4HANA移行で最もよくあるのはこれです。ECCからカスタムバッチジョブをそのまま移し、すでに存在しないテーブル構造の上に組み立てているケースです。移行自体は技術的にはきれいに見えます。ですが、業務ロジックは壊れています。2026年のclean-core方針では、そのカスタムABAPがJoule連携の障害にもなり、リリースのたびにアップグレードの議論を蒸し返すことになります。

**対策：** 業務プロセス再設計は、システム構築の前に行うべきです。1つの項目を設定する前に、業務、財務、デリバリーチームを一緒にワークフロー確認に参加させてください。各ステップに対して「これは今でもここで価値を生んでいるか」と問い直してください。

| レガシー移行領域 | よくある問題 | 代わりにやるべきこと |
|---|---|---|
| ECCからのカスタムコード | 使われていないZコードが妥当性確認なしでS/4HANAへ移される | Custom Code Analyzerを使ってください。未使用コードは廃止してください。clean-coreに合わせてください。 |
| 古いワークフロー | 自動化できるのに旧来の承認フローを再構築する | 業務オーナーと再確認してください。Fiori機能またはBTP上のSAP Build Workflowにマッピングしてください。 |
| 非標準のマスターデータ | 柔軟すぎるレガシー設定がS/4HANAの検証ルールを壊す | 移行前にSAP MDGを使ってクレンジングと標準化を行ってください。 |
| レガシーテーブル上のレポート | 直接テーブルアクセスがS/4HANAのCDSビューと整合しない | CDSビューで再構築してください。テーブルレベルのアクセスは避けてください。 |
| 手作業の回避策 | 移行中に見えなかった周辺プロセスがgo-live後に再発する | 移行前にプロセスマイニングのセッションを実施してください。抜けている部分をデジタル化してください。 |
| コピーされたバッチジョブ | 実行時の挙動分析なしでバックグラウンドジョブをそのまま移す | SAP Job Catalogで見直してください。HANAの性能差に合わせて調整してください。 |

### 失敗3：データ移行の開始が遅すぎること

質の悪いデータを新しいERPに持ち込むのは、何も捨てずに新居へ引っ越すようなものです。不要なものもすべて一緒についてきます。そして、構造化されたプラットフォームの中に入ってしまうと、片付けはさらに難しくなります。

2024年のGCC地域の小売案件では、go-liveが失敗しました。中核データセットに5つの異なる事業部のデータが混在し、それぞれ独自のコード体系を持っていたことを誰も見抜けなかったからです。技術的な移行は正しかったのです。使えなかったのはデータのほうでした。レポートは壊れ、ユーザーの信頼は失われ、本番環境でのクリーンアップには数か月かかりました。立て直しでは、契約者延長とcutover週末の再計画により、6桁ドルの超過費用が発生しました。

**対策：** データは、明確な責任を持つ独立したワークストリームとして扱ってください。技術コンサルタントだけでなく、業務プロセスオーナーを割り当ててください。何を持ち込み、何をアーカイブし、何を再構築するのかを、移行開始前に決めてください。

| 移行上の課題 | 典型的な失敗 | 代わりにやるべきこと |
|---|---|---|
| マスターデータの不整合 | 工場ごとに命名が異なり、ロード時の検証に失敗する | マッピング開始前にマスターデータの標準化を実施してください |
| ロード順序の依存関係 | ベンダーマスタが不完全で、品目ロードが失敗する | 依存関係マップを使ってください。各ロードの前提条件を検証してください。 |
| 1回だけのドライラン | 本番cutover中にエラーが遅れて表面化する | フィードバックループ付きで、少なくとも2回の完全モックロードを計画してください |
| 文書化されていない変換ルール | ルールがExcelにしかなく、版管理も責任者もない | すべてのルールを文書化してください。責任者を割り当ててください。可能ならSAP MDGを使ってください。 |
| マッピングの不一致 | 技術マッピングが業務側の期待と異なる | ロード前に業務ユーザーと項目レベルのマッピングレビューを実施してください |
| ロールバック計画なし | 重要なロードが失敗し、チームが戻し手順なしで混乱する | ロールバックの発動条件を定義してください。cutover計画にバックアップポイントを組み込んでください。 |

### 失敗4：チェンジマネジメントを付随作業として扱うこと

この失敗で最もよくあるのは、「チェンジマネジメントはすでに対応中です」と思い込むことです。たいていの場合、それは数枚のスライド、システムデモ、そしてgo-live前の1回の研修を意味します。それは計画とは言えません。

チームが反発するのは、変化そのものが嫌いだからではありません。信頼できないからです。なぜ変わるのか、変化がエンドユーザーにどう役立つのかを誰も説明しないからです。静かな抵抗が積み上がります。ユーザーはチェックリストを満たす程度にはシステムを使いますが、その後またスプレッドシートに戻ります。

2023年の米国ヘルスケア案件では、スケジュール回復のために研修期間が6週間から2週間に圧縮されました。go-liveを迎えたとき、ユーザーは圧倒されていました。多くがスプレッドシートに戻りました。hypercareはシニアコンサルタント単価でさらに8週間延長されました。立て直し費用は、当初の研修プログラムより高くつきました。

**対策：** チェンジマネジメントには、最初から独自の予算、タイムライン、そしてシニアレベルのオーナーが必要です。早い段階でロールマッピングを実施してください。技術マイルストーンと並べて、利用定着KPIをプロジェクトガバナンスに組み込んでください。

| 観察された問題 | よく起きること | 代わりにやるべきこと |
|---|---|---|
| ユーザー影響の過小評価 | go-live当日に新しい画面や手順にユーザーが不意を突かれる | 主要な変更点を早い段階でユーザーに説明してください。繰り返し伝えてください。 |
| 1回だけの大規模研修 | go-liveまでに内容を忘れ、実機練習もない | 実システムへのアクセスを使って少人数で実施してください。職務別のチートシートを配布してください。 |
| 現場チャンピオン不在 | ユーザーが自部門内で信頼できる相談先を持たない | 早い段階でパワーユーザーを特定してください。チーム支援ができるよう準備してください。 |
| 「なぜ」の説明不足 | ユーザーには改善ではなく作業増に見える | 変更を、ユーザーがすでに感じている痛点に結び付けて説明してください。 |
| フィードバックループなし | UATで出た懸念が記録されるだけで解決されない | 迅速なフィードバック対応を整備してください。入力内容への対応状況をユーザーに見せてください。 |
| go-live後の支援ギャップ | 立ち上げ後にチームが静かになり、問題発生時にユーザーが混乱する | 最初の30日間に向けて、見える支援窓口とヘルプチャネルを計画してください。 |

### 失敗5：ベンダーロードマップを前提に計画すること

2023年の欧州製造業プログラムでは、ロードマップ上のある項目を待つために重要な意思決定を止めました。その項目は12か月先送りされました。チームは、予定どおり出荷されないものを前提に統合戦略を組んでいたのです。結果として、一時的な回避策を作ることになり、それが恒久化しました。

ベンダーは幅広い顧客層に向けてロードマップを作ります。通常、あなたのビジネスモデルがその設計の中心にあるわけではありません。

**対策：** SAPのロードマップは、複数ある入力の1つとして扱ってください。自社のプロセス要件は独立して整理してください。ロードマップ上の約束は、計画の中核前提ではなく、実現すれば上振れする要素として扱ってください。自分で制御も検証もできない機能を前提にアーキテクチャを組んではいけません。

| 観察された問題 | よく起きること | 代わりにやるべきこと |
|---|---|---|
| ロードマップ時期への過度な依存 | 適合性確認なしでベンダーのリリースに合わせて計画する | ロードマップは参考情報として使ってください。社内戦略とタイミングに基づいて調整してください。 |
| 機能が期待どおり動く前提 | リリース時に安定しているはずのモジュールを前提に計画する | 新機能は早期にsandboxで検証してください。実績のあるバージョンを待ってください。 |
| 「ロードマップにあるから」でギャップを容認 | 重要業務プロセスがgo-live時点で未対応のままになる | 業務要件から出発してください。ロードマップが本当に役立つか検証してください。 |
| 約束ベースの予算化 | まだ出ていない機能による削減効果を見込む | 予算は今の現実に基づいて組んでください。ロードマップの便益は任意の上振れとして扱ってください。 |
| 将来リリースに結び付いたアーキテクチャ | 制御できない機能を前提に構造判断を行う | 計画中の機能よりも、安定して相互運用可能な設計を優先してください。 |

### 失敗6：レガシーシステムの廃止計画がないこと

2024年の欧州航空業界プログラムでは、年6桁ドルを払って旧システムを維持していました。年に2回レポートを引き出す6人のユーザーのためです。ERPのgo-live後も5年間動き続けていました。誰も廃止計画を作っておらず、計画がなければシステムはそのまま残り続けます。

新しいERPが稼働しても、旧システムは「念のため」に残されます。コンプライアンス、参照用、慣れ親しみ。そうして無期限に稼働し続け、保守予算を食い、監査リスクを生みます。

**対策：** 廃止計画は最初からプロジェクト憲章に入れておくべきです。関わるのはITだけではありません。法務、コンプライアンス、データガバナンスも必要です。法的に妥当なデータ保持方針は、go-live後ではなくgo-live前に定義してください。

| 観察された問題 | よく起きること | 代わりにやるべきこと |
|---|---|---|
| 念のためにレガシーシステムを維持 | 古いECCや周辺システムがgo-live後も何年も稼働する | 初日から明確な廃止タイムラインを計画してください。アーカイブ要件を早期に整合させてください。 |
| 移行後のコンプライアンスギャップ | システムを場当たり的に廃止し、監査証跡や税務データを取りこぼす | 監査部門と財務部門と連携してください。法的保持期間を定義してください。認証済みアーカイブツールを使ってください。 |
| 重複するデータ環境 | 新ERPと旧ERPが並行稼働し、レポーティングが混乱する | cutover後の単一の正本を定義してください。廃止日を明確に伝えてください。 |
| 宙ぶらりんの統合接続 | 利用者がいないのにレガシー向けインターフェースが残る | すべての入出力フローをマッピングしてください。go-live後作業の一部としてミドルウェア接続を切り離してください。 |
| 廃止の責任者不在 | 誰も担当せず、システムが無期限に稼働し続ける | PMOまたはアーキテクチャに廃止責任を割り当ててください。プロジェクト憲章に含めてください。 |

### 失敗7：統合の複雑さを甘く見ること

ERP統合は配管ではありません。全体ランドスケープの神経系です。これが壊れると、ITより先に業務が気付きます。ワークフローはテスト環境ではなく、業務の途中で止まるからです。

最もよくある失敗パターンは、ITと業務ユーザーの双方が、統合要件は相手が定義していると思い込むことです。どちらもやっていません。ギャップがテストで表面化する頃には、適切に再設計する時間はもうありません。

2023年の欧州小売プログラムでは、order-to-cashインターフェースが実際の本番データ量でテストされていなかったため、go-liveが5週間遅れました。立て直しでは、モックロードの再実施、契約者延長、cutover順序の見直しにより、6桁ドルの費用が発生しました。

**対策：** 統合設計は、設定完了後ではなくblueprintingの段階で始めるべきです。設計フェーズで、シナリオ、ミドルウェア、データマッピング、メッセージ量見積もりを定義してください。go-live前に、SLA付きでインターフェースオーナーを割り当ててください。2026年には、新規SAPプログラムの標準ミドルウェアはBTP上のSAP Integration Suiteです。PI/POはend-of-life移行段階にあり、greenfieldアーキテクチャの答えではもうありません。

| 観察された問題 | よく起きること | 代わりにやるべきこと |
|---|---|---|
| インターフェースのスコープ定義が遅い | テストで設計不一致が見つかり、適切に対処するには遅すぎる | blueprinting中に統合設計を開始してください |
| 非同期挙動の過小評価 | チームがリアルタイム更新を前提にし、バッチ遅延で期待が崩れる | インターフェースごとに同期か非同期かを明確にしてください。許容範囲を業務ユーザーと検証してください。 |
| 依存関係マップなし | 統合エラーが連鎖し、チームが個別に切り分ける | 上流・下流追跡を含む統合アーキテクチャマップを作成してください |
| 事前構築コンテンツは動く前提 | マスターデータ不一致で標準フローが本番データ上で壊れる | 事前構築コンテンツも必ず実データでテストしてください。適応作業の時間を予算化してください。 |
| 明確な責任者なし | 機能チームと技術チームの間にエラーが落ち、解決経路がない | go-live前に、SLAとエスカレーション経路付きでインターフェースオーナーを定義してください。 |

### 失敗8：ERPですべて対応できると思い込むこと

2024年のGCC地域の製造業プロジェクトでは、ServiceNowのような外部システムを使いたくないという理由で、複雑なサービスワークフロー（ITチケット、資産申請、エスカレーション振り分け）をERPに押し込みました。その結果、至る所にカスタム項目が増え、手作業の回避策が生まれ、そもそも適合していないプロセスをたどらされるユーザーの不満が高まりました。

ERPは、構造化され、トランザクション中心で、財務にひも付くプロセスには向いています。ITサービス申請、ワークフローオーケストレーション、ナレッジ管理では、専用プラットフォームのほうがうまく機能します。2026年のRISEおよびGROWにおけるclean-core方針の下では、この選択はもはや任意ではありません。デジタルコアに置くべきでないカスタムロジックは、SAP BTPのside-by-side拡張か、専用プラットフォームへ移す必要があります。

**対策：** ERPモダナイゼーションには、「ERPに作らないもの」を意図的に決める判断が必要です。例外処理にはSAP BTP上のside-by-side拡張を使ってください。トランザクションコアの外側にあるプロセスオーケストレーションには、ServiceNowなどのプラットフォームを使ってください。

| よくある思い込み | 実際によく起きること | 代わりに検討すべきこと |
|---|---|---|
| ERPがすべてのプロセスをネイティブに処理する | プロジェクト途中でギャップが見つかり、カスタム構築のためにスコープが膨らむ | 設計前に機能適合・ギャップ分析を実施してください。ERPのカバー範囲を検証してください。 |
| すべてのレポートをERP内で構築する | ユーザーがExcel出力やPower BIを求め、レポートが硬直的に感じられる | レポーティングアーキテクチャを早期に計画してください。組み込み分析や別データレイヤーを検討してください。 |
| ERPがすべてのコラボレーションとワークフローを担う | 承認やモバイルワークフローが使いにくく、制約が多い | ERPで不足する部分は、ワークフローツールやプラットフォーム連携を評価してください。 |
| カスタム拡張はリスクが高すぎる | スプレッドシートやシャドーシステムに回避策が現れる | 例外対応にはBTPのside-by-side拡張を使ってください。複雑さをコアに押し込まないでください。 |
| ERPが初日からすべてのレガシーツールを置き換えられる | 重要なニッチシステムをgo-live時点で無理なく置き換えられない | レガシーシステムは段階的に廃止してください。明確な置換タイムライン付きで共存を計画してください。 |

### 失敗9：長期的なライセンス費用を甘く見ること

2023年に私が助言した米国の製造業クライアントは、2年目にライセンス費用が倍増しました。上位ティアのモジュールの背後にある1つの機能が必要になったからです。当初のビジネスケースはgo-live時点の費用しかモデル化していませんでした。5年間のシナリオを誰も回していなかったのです。

現代のERPライセンスは、めったに単純ではありません。モジュール、トランザクション量、API利用、指名ユーザーに対して支払いが発生し、計画していたかどうかに関係なく、事業の成長に合わせて費用も増えます。SAPでは、Digital Access Modelにより、サードパーティシステムとの連携が、当初の商用モデルに入っていなかったライセンス費用を発生させることがあります。RISEとGROWのサブスクリプションにも独自の力学があります。Full User Equivalent（FUE）数は利用定着とともに増え、機能ティア（advanced operations、expert tools）には、見出し価格には出てこない上乗せがあります。

**対策：** 契約前に3〜5年のライセンスモデルを作ってください。ユーザーロールをライセンス種別にマッピングしてください。go-live後は、非アクティブなライセンスを定期的に監査してください。外部システムを接続する前に、間接アクセスのルールを理解してください。RISEとGROWでは、現実的な利用定着カーブに沿ってFUE増加をモデル化し、必要になる機能ティアの価格も見積もってください。

### 失敗10：ERPをITプロジェクトとして扱うこと

これは最も一般的で、最もダメージの大きいパターンです。計画はITで始まり、ITが主導し、最終的にはITの問題を解く形になります。そこで失われるのが、戦略との整合です。

2024年の欧州公共部門プログラムでは、設計フェーズに業務、財務、製品部門のリーダーを関与させないまま、大規模ERPプログラムを立ち上げました。ERPはgo-liveしました。ですが6か月後、事業側は「何も良くなった感じがしない」と言いました。システムは技術的には健全でしたが、作られていたのは明日の計画のためではなく、昨日のプロセスのためだったのです。

**対策：** ERPはインフラですが、その背後には事業戦略が必要です。商務、財務、業務のリーダーを最初からステアリングコミッティに入れてください。戦略整合は、技術スコープだけでなく、導入憲章の中に文書化してください。設計開始前に、ERPの目標を取締役会レベルの成果と照らして厳しく検証してください。

## RISE、GROW、clean-core、AIが2026年のERPモダナイゼーションをどう変えるか

2026年の4つの変化によって、上記の失敗のうち何がまだ回避可能で、何がすでに契約に組み込まれているのかが変わります。

**RISE with SAPとGROW with SAPは、新規SAPプログラムの標準導入モデルです。** RISEは、S/4HANA Cloud private editionに、ハイパースケーラー基盤、基本的なマネージドサービス、そしてSAPのカスタマーサクセス支援を束ねたものです。GROWは、中堅市場向けにS/4HANA Cloud public editionを束ねます。どちらも、clean-coreを好みではなく契約上の制約として持ち込みます。新規のon-premise導入は今ではまれで、通常はデータ所在地要件が理由です。

**上記のレガシープロセス移行とカスタムコードの失敗にとって、2026年で最も影響が大きい変化はclean-core準拠です。** デジタルコア内のカスタムABAPは、アップグレードを妨げ、Joule連携を壊し、SAPが自社のカスタム構築と重なるenable-now機能をリリースした際には商用再交渉まで引き起こします。カスタムロジックの正しい置き場所はSAP BTPです。イベント駆動型拡張、side-by-sideサービス、そしてあらゆるS/4HANAリリースをまたいで生き残るSAP Buildアプリです。fit-gapテンプレートには今、各ギャップを標準設定で解決するのか、BTP上で解決するのか、あるいは商用協議にエスカレーションするのかを明示する列が必要です。

**SAP Activate向けJouleは、end-to-endで導入されたプログラムでは、fit-gap、設定、テストスクリプト作成を30〜50 percent圧縮します。** SAP Build Codeは、BTP拡張向けのABAP生成を20〜40 percent高速化します。2026年のベンダー提案に対する含意は明確です。AIツール活用がレートカードにどう反映されているかを、明示的に確認してください。JouleやBuild Codeの採用を織り込んでいないパートナーは、単価が高すぎるか、削減分を自社マージンとして確保するつもりかのどちらかです。

**SAP Cloud ALMは、RISEとGROWにおけるアプリケーションライフサイクル管理の2026年標準です。** SAP Solution Managerのメインストリーム保守は2027年に終了し、延長サポートも2027年までです。新しいcloud editionプログラムでは、要件管理、導入計画、変更追跡、運用監視にCloud ALMが標準化されます。上記の統合の失敗（失敗7）は、Solution Manager内とCloud ALM内では現れ方が異なります。それに合わせて設計してください。

10の失敗そのものは変わっていません。変わったのは、間違えたときのコストです。RISEプログラムでは、clean-coreの判断、導入モデルの選択、FUE成長モデルの設計は、立ち上げ最初の6週間で決まります。影響を与えられる時間は短いです。

## よくある質問

<details>
<summary>なぜERPモダナイゼーションはgo-live後に期待外れに終わるのでしょうか？</summary>

多くのチームはgo-liveまでを計画して、そこで止まります。システムは立ち上がりますが、その後を誰も持ちません。機能追加、フィードバックループ、プロセス修正、バックログ整理です。専用予算付きのgo-live後ガバナンス計画がなければ、チームが次へ移る間に問題は静かに積み上がります。

go-live時点でステアリングコミッティが解散するのは、そのプログラムが問題に向かっている最も一貫したシグナルです。ガバナンスは立ち上げで終わってはいけません。初日から、専用予算付きで6〜12か月のgo-live後ガバナンス期間を計画してください。

</details>

<details>
<summary>レガシープロセスを新しいERPにそのまま持ち込むリスクは何ですか？</summary>

古いワークフロー、承認、レポートを、その価値を問い直さずに再現すると、新しいシステムは古いシステムと同じ非効率を引き継ぎます。S/4HANA移行での具体的なリスクは、ECCのテーブル構造向けに作られたカスタムコードやバッチジョブが、S/4HANAでは動かないことが多い点です。移行は技術的にはきれいでも、業務ロジックは壊れていることがあります。

2026年のRISEとGROWにおけるclean-core方針の下では、そのカスタムコードはJoule連携も妨げ、リリースのたびにアップグレードの議論を再燃させます。チームはERPに大きな予算を投じたのに、移行前に誰も疑問を持たなかった古いプロセスのデジタル版を手にすることになります。

</details>

<details>
<summary>データ品質の低さはERPモダナイゼーションにどうダメージを与えますか？</summary>

汚れたデータ、膨らみすぎたデータは、リスクを増幅させます。重複ベンダー、不整合なマスターデータ、レガシーコード、不完全なレコードは、誰かが先にクレンジングしない限り、新システムへそのまま移ります。

2024年のGCC地域の小売プログラムでは、中核データセットに5つの異なる事業部のデータが入り、それぞれコード体系が違っていたため、go-liveが失敗しました。技術的な移行は問題ありませんでした。使えなかったのはデータそのものでした。レポートは壊れ、ユーザーの信頼は失われ、本番環境でのクリーンアップには数か月かかりました。立て直しには、6桁ドルの超過費用が発生しました。

</details>

<details>
<summary>なぜERPプロジェクトではチェンジマネジメントがこれほど過小評価されるのでしょうか？</summary>

見えにくいからです。経営層は数回の研修で十分だと思いがちですが、チェンジマネジメントとは、go-live中ではなくgo-live前に、人々の日々の仕事で実際に何が変わるのかに備えさせることです。

その準備が行われないと、ユーザーは静かに反発します。監査証跡を満たす程度にはシステムを使いますが、その後またスプレッドシートに戻ります。設定がよくできたシステムでも脇に追いやられます。なぜ変わるのか、変化が実務担当者にどう役立つのかを誰も説明しなかったからです。

2026年には、デジタルアダプション層も重要です。SAPは2024年にWalkMeを約$1.5 billionで買収しました。SAP Enable Now（構造化された研修コンテンツ向け）とWalkMe（利用時点でのアプリ内ガイダンス向け）を適切に組み合わせることで、集合研修時間とhypercare負荷を減らせます。

</details>

<details>
<summary>コアシステムの準備ができていても、なぜERP統合は失敗するのでしょうか？</summary>

統合の失敗は、通常、技術的問題よりも思い込みから生まれます。ITは業務側が要件を定義したと思い、業務側は統合はすでに対応済みだと思います。どちらも実際にはやっていません。

ギャップがテストで表面化する頃には、再設計する時間はもうありません。APIは壊れ、データ同期は失敗し、システム同士の足並みが崩れます。最初に気付くのは業務側です。ワークフローはテスト環境ではなく、業務の途中で止まるからです。

2026年には、新規SAPプログラムの標準ミドルウェアはBTP上のSAP Integration Suiteです。PI/POはend-of-life移行段階にあり、greenfieldアーキテクチャの答えではもうありません。統合設計は、設定後ではなくblueprinting中に計画してください。

</details>

<details>
<summary>なぜERPのgo-live後も何年もレガシーシステムが動き続けるのでしょうか？</summary>

止める計画を誰も立てていないからです。誰もが新しいERPを稼働させることに集中します。レガシーシステムは、コンプライアンス、参照用、慣れ親しみのために残され、そのまま無期限に残ります。

2024年の欧州航空業界プログラムでは、年に2回レポートを引き出す6人のユーザーのために、クライアントは旧システム維持に年6桁ドルを払っていました。go-live後も5年間動き続けていました。廃止計画は当初のプロジェクト憲章に入っていなかったため、結局実行されませんでした。

廃止計画は、導入スコープの一部として初日から入れておく必要があります。立ち上げ後の判断ではありません。

</details>

<details>
<summary>RISE with SAPとclean-coreは、どの失敗がまだ回避可能かをどう変えますか？</summary>

RISE with SAPとGROW with SAPによって、上記の失敗の一部は契約上不可能になり、別の一部ははるかに高くつくようになります。

両サブスクリプションにおけるclean-core準拠は、デジタルコア内の深いカスタマイズを阻みます。これは失敗2（レガシープロセス移行）にとっては良い面もあります。議論を強制するからです。一方で、ECCで重いABAPカスタマイズに依存していた組織にとっては厳しい話です。移行パスでは、何をBTPへ移すのか、何を標準設定にするのか、何を廃止するのかを決める必要があるからです。

統合の失敗（失敗7）は、2026年の標準がPI/POではなくBTP上のSAP Integration Suiteであるため、現れ方が変わります。それに合わせて計画してください。

ライセンスの失敗（失敗9）は、FUEベース課金の下で新しい形を取ります。契約前に、現実的な利用定着カーブに沿ってFUE成長をモデル化し、必要になる機能ティアの価格を見積もってください。

廃止の失敗（失敗6）は、RISEとGROWが契約拘束型であるため、より緊急性が高まります。レガシーシステムを並行稼働し続けると、サブスクリプション費用とclean-coreリスクの両方が増えるからです。

</details>

ERPモダナイゼーションの失敗は、必ずしもシステムログに現れるとは限りません。システムを回避する人の働き方に現れることもありますし、システム自体が使われなくなる形で現れることもあります。上の10のパターンは、私が21件のプログラムで最もよく見てきたものです。2026年の変化（RISE、GROW、clean-core、Joule、Cloud ALM）は、パターン自体を変えるわけではありません。変えるのは、間違えたときのコストであり、正しい判断をまだ下せる時間をさらに短くすることです。

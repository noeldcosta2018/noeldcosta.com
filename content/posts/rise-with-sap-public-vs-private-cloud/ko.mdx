RISE with SAP 퍼블릭 클라우드는 프로세스가 표준적이고 아주 특수한 구성이 필요 없는 기업에 맞습니다. 프라이빗 클라우드는 산업 특화 프로세스나 깊은 구성이 있거나, 다시 만들기보다 전환하고 싶은 ECC 시스템을 가진 기업에 맞습니다.

퍼블릭 에디션은 SAP 베스트 프랙티스, 1년에 두 번 SAP가 관리하는 업그레이드를 제공하며 SAP 코드는 변경할 수 없습니다. 프라이빗 에디션은 전체 구성, 모든 산업, 브라운필드 경로를 유지합니다.

짧게 답하면, SAP 표준으로 운영할 수 있다면 퍼블릭으로 가십시오. 그럴 수 없거나 확신이 없다면, 서명하기 전에 프라이빗을 꼼꼼히 검토하십시오.

이 글은 제 [ECC에서 S/4HANA로의 마이그레이션 가이드](/ko/ecc-to-s4hana-migration/)의 하위 주제 중 하나입니다. RISE 계약에 무엇이 묶여 있는지는 제 [RISE with SAP 개요](/ko/sap-implementation/rise-with-sap/)를 읽어 보십시오. 여기서는 에디션 결정만 다룹니다.

## RISE, GROW, 퍼블릭과 프라이빗: 2026년의 명칭

명칭은 2025년에 바뀌었지만 검색에서는 여전히 옛 이름이 우세합니다. 2026년 10월 기준 현황은 다음과 같습니다.

1. **SAP Cloud ERP**는 SAP 클라우드 ERP의 마케팅 이름입니다. 핵심 애플리케이션은 여전히 SAP S/4HANA Cloud Public Edition이라 불리며, SAP의 자체 블로그는 이제 "SAP Cloud ERP Public Edition"이라고 씁니다.
2. **SAP Cloud ERP Private**는 프라이빗 클라우드 제품이며, 대부분의 사람은 여전히 SAP S/4HANA Cloud Private Edition으로 검색합니다.
3. **RISE with SAP**는 기존 SAP 고객을 위한 전환 오퍼링입니다.
4. **SAP GROW**는 대부분의 사람이 여전히 GROW with SAP라고 부르며, SAP를 처음 쓰는 기업을 위한 오퍼링입니다.

대부분의 글이 틀리는 지점이 있습니다. RISE는 프라이빗 클라우드의 동의어가 아닙니다. SAP는 [SAP GROW 페이지](https://www.sap.com/products/erp/grow.html)에서 RISE with SAP의 핵심에 SAP Cloud ERP 또는 SAP Cloud ERP Private가 올 수 있다고 말합니다. GROW는 퍼블릭 에디션 위에 만들어져 있습니다.

그러니 "RISE 퍼블릭이냐 프라이빗이냐"는 실제 선택입니다. 상업적 포장과 에디션은 별개의 두 결정이며, 에디션 결정을 먼저 내려야 합니다.

## 퍼블릭 대 프라이빗 클라우드 S/4HANA: 각 에디션이 허용하는 것

SAP는 SAP Help Portal에 [퍼블릭, 프라이빗, 온프레미스 에디션의 오퍼링 비교](https://help.sap.com/docs/SAP_S4HANA_CLOUD_PE/b89b8b9026e1456bb2a1df7c0d59c937/1485d139460246d2a4b936c0bb0ca272.html)를 공개합니다. 아래 표는 대부분의 경우를 결정하는 부분을 2026년 10월에 확인해 요약한 것입니다.

| 영역 | 퍼블릭 에디션(SAP Cloud ERP) | 프라이빗 에디션(SAP Cloud ERP Private) |
|---|---|---|
| 도입 경로 | 신규 구축만 가능 | 신규 구축, 시스템 전환, 선택적 데이터 전환, 리프트 앤 시프트 |
| 구성 | SAP Central Business Configuration | Customizing 전체 접근 |
| 확장성 | 키 유저(인앱), ABAP Cloud를 이용한 개발자 확장, SAP BTP 기반 사이드 바이 사이드 | 모든 확장 옵션 |
| SAP 코드 변경 | 불가 | 가능하지만 SAP는 권장하지 않음 |
| 업그레이드 | 1년에 두 번, 2월과 8월, SAP가 관리 | 2년마다 새 릴리스, 첫 2년 동안 6개월마다 기능 팩, 요청 시 SAP가 설치 |
| 유지보수 | 항상 최신 릴리스로 운영 | 릴리스당 7년, 유지보수를 계속 받으려면 업그레이드를 계획해야 함 |
| 산업 | 소비재, 개별 제조, 에너지 및 천연자원, 금융 서비스, 공공 서비스, 서비스 산업 | 모든 산업 |
| 애드온 | 퍼블릭 에디션 인증을 받은 애드온만 | S/4HANA 인증을 받은 애드온 |
| 호스팅 | SAP 데이터 센터 또는 하이퍼스케일러 | 하이퍼스케일러, SAP 데이터 센터, 프라이빗 데이터 센터 또는 소버린 클라우드 |

대부분의 경우를 결정하는 것은 세 행입니다. 구성, 산업, 도입 경로입니다.

Central Business Configuration은 SAP 베스트 프랙티스의 범위를 정한 뒤 그 안에서 설정을 조정하는 방식입니다. ECC 팀이 알고 있는 전체 Customizing 트리는 제공되지 않습니다. 재무, 가격, 물류 설계가 그 트리 깊숙한 설정에 의존한다면 퍼블릭 에디션에는 그 설정이 없습니다.

산업 행은 마케팅 목록이 아니라 범위 선언입니다. 핵심 프로세스가 퍼블릭 에디션 목록 밖의 산업에 속한다면, 다른 질문을 하기도 전에 이미 프라이빗 에디션 영역입니다.

업그레이드 행은 CFO가 과소평가하는 부분입니다. [퍼블릭 에디션의 SAP 업그레이드 일정](https://community.sap.com/t5/enterprise-resource-planning-blog-posts-by-sap/getting-ready-for-the-2608-upgrade-of-the-sap-cloud-erp-public-edition/ba-p/14421165)은 3 시스템 랜드스케이프 고객의 2608 운영 업그레이드를 2026년 8월 15일과 16일로 잡았습니다. 그 날짜를 정한 것은 고객이 아니라 SAP였습니다.

## 제 원칙: 표준 프로세스는 퍼블릭 클라우드로

제 원칙은 짧습니다. 아주 특수한 구성이 필요 없는 표준 프로세스는 퍼블릭 클라우드로 갈 수 있습니다.

나머지는 더 엄격히 살펴봐야 합니다. 누군가 퍼블릭 클라우드에 서명하기 전에 저는 다음 신호를 확인합니다.

1. **산업 적합성.** 핵심 사업이 퍼블릭 에디션이 지원하는 산업 밖에 있습니다.
2. **구성 깊이.** 가격, 매출, 원가 계산 또는 정산 로직이 Fit-to-Standard 워크숍으로는 SAP 베스트 프랙티스에 매핑할 수 없는 구성에 의존합니다.
3. **애드온.** 퍼블릭 에디션 인증을 받지 않은 SAP 또는 파트너 애드온에 의존합니다.
4. **프로세스 오너십.** 현업이 표준에 맞춰 프로세스를 바꿀 의지가 없고, 권한 있는 누구도 그렇게 하도록 결정하지 않습니다.
5. **이력.** 다시 구축하고 데이터를 로드하기보다, ECC를 이력과 구성째 전환하고 싶습니다.

신호 하나만 있으면 논의할 거리입니다. 둘 이상이면 저는 프라이빗 에디션이 답일 것으로 예상합니다.

저는 엔터테인먼트 업계의 한 기업이 퍼블릭 클라우드를 골랐다가 후회하는 것을 봤습니다. 그 회사의 요구는 표준적이지 않았고, 퍼블릭 클라우드는 맞지 않는 선택이었습니다.

교훈은 퍼블릭 클라우드가 약하다는 것이 아닙니다. 퍼블릭 클라우드는 원래 대상으로 만든 비즈니스에서는 잘 작동합니다. 교훈은 적합성 점검이 Explore 도중이 아니라 계약 전에 이뤄져야 한다는 것입니다.

반대 방향의 실수도 조심하십시오. 대체로 표준적인 프로세스를 가진 기업이 더 안전하게 느껴진다는 이유로 프라이빗 클라우드를 고르고, 그 안에서 ECC 습관을 다시 만듭니다. 필요하지 않았던 유연성에 돈을 내고, 업그레이드 때마다 변호해야 할 커스텀 코드를 끌고 갑니다.

## Clean Core와 업그레이드: 서명과 함께 받아들이는 트레이드오프

Clean Core는 커스터마이징을 최소한으로 유지하고 잘 통제한다는 뜻입니다. 누가 그것을 강제하는지는 에디션이 정합니다.

퍼블릭 에디션에서는 시스템이 강제합니다. 새 개발은 ABAP Cloud와 릴리스된 인터페이스만 쓰며, SAP 코드는 수정할 수 없습니다. 제 [SAP Clean Core 가이드](/ko/sap-clean-core-strategy-what-it-means-for-your-business/)에서 확장 수준을 자세히 설명합니다.

프라이빗 에디션에서 Clean Core는 거버넌스 결정입니다. 여전히 코어를 수정할 수 있으며, 모든 수정은 업그레이드 때마다 짊어지는 비용입니다.

그래서 저는 어떤 에디션을 고르든 현업과 IT로 구성된 설계 권한 조직이 모든 예외를 책임지게 합니다. IT 혼자서는 기술적으로 가능한 것은 무엇이든 승인합니다. 현업 혼자서는 예전 프로세스를 돌려 달라고 합니다.

제가 가장 자주 보는 Clean Core 실수는 SAP를 Oracle처럼 작동하게 만들려는 것입니다. 팀은 SAP 표준 프로세스를 채택하는 대신 다른 시스템의 로직을 커스텀 코드로 다시 만듭니다. 퍼블릭 에디션에서는 이것이 설계 단계에서 실패하는데, 그편이 발견하기에 더 싼 지점입니다.

업그레이드 트레이드오프도 같은 논리를 따릅니다.

- **퍼블릭 에디션.** 항상 최신 릴리스로 운영하며 1년에 두 번 새 기능을 받습니다. 테스트도 1년에 두 번, SAP의 일정에 맞춰 해야 하며, 귀사가 연말 결산 한가운데에 있어도 마찬가지입니다.
- **프라이빗 에디션.** 유지보수 기간 안에서 업그레이드 시점을 직접 고릅니다. 그 자유는 실제로 쓸 때만 가치가 있습니다. 한 번도 업그레이드하지 않는 프라이빗 에디션 시스템은 클라우드 청구서가 붙은 ECC 시스템일 뿐이기 때문입니다.

## 에디션 선택이 ECC 마이그레이션에 주는 의미

ECC 고객에게는 에디션이 마이그레이션 경로를 결정합니다. 퍼블릭 에디션은 언제나 신규 구축입니다. 구성과 프로세스는 SAP 베스트 프랙티스 위에서 다시 만들고, 비즈니스 데이터만 옮깁니다. 프라이빗 에디션은 제 마이그레이션 가이드에서 설명한 시스템 전환과 선택적 데이터 전환 경로를 지원합니다.

제 경험상 퍼블릭 에디션의 GROW with SAP 프로젝트는 약 6~9개월이 걸립니다. RISE with SAP 프로그램은 9~18개월이 걸리며, 주로 경로와 커스텀 코드에 따라 달라집니다. 제 [S/4HANA 마이그레이션 일정과 프로젝트 계획](/ko/s4hana-migration-timeline-project-plan/)에서 이를 단계별로 나눠 설명합니다.

2-tier 모델은 타당한 중간 경로입니다. SAP는 모회사가 프라이빗 에디션을, 자회사가 퍼블릭 에디션을 운영하며 서로 통합한 고객 사례를 공개합니다. 자회사가 정말로 표준적일 때 효과가 있으며, 귀사가 책임져야 할 통합 작업이 추가됩니다.

에디션은 상업적 협상도 바꿉니다. 구독 지표, FUE(full user equivalent) 산정, 각 패키지에 포함되는 내용이 다르며, 제가 RISE 계약에서 가장 많이 보는 함정은 갱신 조건, FUE 산정, AI 크레딧입니다. 제 [RISE with SAP 계약과 가격](/ko/rise-with-sap-contract-pricing/) 가이드에서 무엇을 협상할지 다룹니다.

서명하기 전에 저라면 SAP와 파트너에게 다음 질문을 하겠습니다.

1. 우리의 엔드투엔드 프로세스 중 퍼블릭 에디션 범위가 오늘 다루는 것은 무엇이며, 로드맵에만 있는 것은 무엇입니까?
2. 우리 애드온 중 제안하신 에디션 인증을 받은 것은 무엇입니까?
3. 현재 구성 중 Central Business Configuration에 대응하는 것이 없는 것은 무엇입니까?
4. 업그레이드 일정은 우리 연말 결산과 성수기와 비교해 어떻게 됩니까?
5. 퍼블릭 에디션으로 시작했다가 맞지 않게 되면 어떤 경로가 있으며, 그것은 새 프로젝트입니까?
6. 일반적인 에디션 비교가 아니라 우리 비즈니스에 대한 상위 수준 설계를 보여 주십시오.

마지막 질문이 가장 중요합니다. 일반적인 정보로 답하는 파트너는 이 선택에 대해 조언할 준비가 되어 있지 않습니다. 제 [S/4HANA 마이그레이션 파트너 선택](/ko/choose-s4hana-migration-partner/) 가이드에서 그 대화의 나머지를 다룹니다.

## 제가 다음에 할 일

상위 20개 비즈니스 프로세스를 골라 각각 표준, 구성이 필요한 표준, 특수 중 하나로 표시하십시오. 슬라이드를 보고 하지 말고, 프로세스 오너가 함께한 자리에서 하십시오.

거의 모든 것이 표준이라면 퍼블릭 에디션 제안서와 실제 데이터로 하는 Fit-to-Standard 워크숍을 요청하십시오. 핵심 프로세스 여러 개가 특수하거나 ECC를 전환하고 싶다면 프라이빗 에디션을 요청하고, 첫날부터 Clean Core 거버넌스를 계획하십시오. 제 무료 [그린필드 대 브라운필드 마이그레이션 평가](/ko/sap-s4hana-migration-strategy-greenfield-vs-brownfield/)가 경로 질문에 도움이 됩니다.

저는 계약이 결정을 굳히기 전에 이 판단을 내리도록 돕습니다. 독립적인 시각이 필요하다면 [연락해 주십시오](/ko/contact-noel-erp-support/).

## 자주 묻는 질문

<details>
<summary>RISE with SAP는 퍼블릭 클라우드입니까, 프라이빗 클라우드입니까?</summary>

둘 다 될 수 있습니다. SAP는 RISE with SAP의 핵심에 퍼블릭 에디션인 SAP Cloud ERP 또는 SAP Cloud ERP Private가 올 수 있다고 말합니다. 복잡한 프로세스를 가진 ECC 고객 대부분은 프라이빗을 고르지만, 에디션을 RISE 자체가 결정하지는 않습니다.

</details>

<details>
<summary>S/4HANA Cloud 퍼블릭 에디션과 프라이빗 에디션의 차이는 무엇입니까?</summary>

퍼블릭 에디션은 SAP 베스트 프랙티스, SAP Central Business Configuration, 1년에 두 번 SAP가 관리하는 업그레이드를 갖춘 SaaS이며, SAP 코드는 변경할 수 없습니다. 프라이빗 에디션은 Customizing 전체 접근, 모든 산업, 모든 확장 옵션, ECC에서의 시스템 전환을 제공합니다. 2년마다 새 릴리스가 나오며, 릴리스당 7년간 유지보수를 받습니다.

</details>

<details>
<summary>SAP Cloud ERP는 S/4HANA Cloud Public Edition과 같습니까?</summary>

실무적으로는 그렇습니다. SAP는 클라우드 ERP를 SAP Cloud ERP로 판매하며, SAP S/4HANA Cloud Public Edition이 그 핵심 애플리케이션입니다. 프라이빗 제품은 이제 SAP Cloud ERP Private라고 불리며, 대부분의 사람은 여전히 S/4HANA Cloud Private Edition으로 알고 있습니다.

</details>

<details>
<summary>SAP ECC를 S/4HANA Cloud Public Edition으로 전환할 수 있습니까?</summary>

아니요. 퍼블릭 에디션은 신규 구축만 지원하므로, SAP 베스트 프랙티스 위에서 프로세스를 다시 만들고 비즈니스 데이터를 마이그레이션합니다. ECC에서의 시스템 전환과 선택적 데이터 전환은 프라이빗 에디션과 온프레미스에서만 가능합니다.

</details>

<details>
<summary>S/4HANA Cloud Private Edition에서 SAP 코드를 수정할 수 있습니까?</summary>

예. SAP는 프라이빗 에디션에서 수정을 가능하지만 권장하지 않는 것으로 분류합니다. 모든 수정은 향후 업그레이드의 공수를 늘리므로, 저는 하나하나를 현업과 IT로 구성된 설계 권한 조직에 올리고 왜 존재하는지 기록합니다.

</details>

<details>
<summary>어떤 기업이 SAP 퍼블릭 클라우드 ERP를 선택해야 합니까?</summary>

프로세스가 표준적이고 아주 특수한 구성이 필요 없으며, 퍼블릭 에디션이 지원하는 산업에 속하고, SAP 베스트 프랙티스를 채택할 의지가 있는 기업입니다. 산업 특화 프로세스나 깊은 구성이 있거나 전환하고 싶은 ECC 시스템이 있는 기업은 보통 프라이빗 에디션이 더 잘 맞습니다.

</details>

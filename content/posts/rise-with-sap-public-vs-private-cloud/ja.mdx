RISE with SAPのパブリッククラウドは、プロセスが標準的で、特別な設定を必要としない企業に向いています。プライベートクラウドは、業種固有のプロセスや踏み込んだ設定がある企業、あるいはECCシステムを作り直すのではなく変換したい企業に向いています。

パブリックエディションでは、SAPのベストプラクティス、SAPが管理する年2回のアップグレードが提供され、SAPのコードは変更できません。プライベートエディションは、完全な設定、すべての業種、ブラウンフィールドのアプローチに対応します。

結論から言えば、SAP標準で業務を回せるならパブリックです。回せない場合、あるいは確信が持てない場合は、署名する前にプライベートを真剣に検討してください。

この記事は、私の[ECCからS/4HANAへの移行ガイド](/ja/ecc-to-s4hana-migration/)を構成する記事の一つです。RISEの契約に何がまとめられているかは、私の[RISE with SAPの概要](/ja/sap-implementation/rise-with-sap/)をお読みください。ここではエディションの判断だけを扱います。

## RISE、GROW、パブリック、プライベート：2026年時点の名称

名称は2025年に変わりましたが、検索ではいまも旧名称が主流です。2026年10月時点での位置づけは次のとおりです。

1. **SAP Cloud ERP**は、SAPのクラウドERPのマーケティング名です。中核となるアプリケーションは現在もSAP S/4HANA Cloud Public Editionと呼ばれ、SAP自身のブログでは「SAP Cloud ERP Public Edition」と書かれるようになっています。
2. **SAP Cloud ERP Private**はプライベートクラウド製品で、多くの人はいまもSAP S/4HANA Cloud Private Editionとして検索しています。
3. **RISE with SAP**は、既存のSAP顧客向けのトランスフォーメーションのオファーです。
4. **SAP GROW**は、多くの人がいまもGROW with SAPと呼んでいるもので、SAPを初めて使う企業向けのオファーです。

多くの記事が誤解している点があります。RISEはプライベートクラウドの同義語ではありません。SAPは[SAP GROWのページ](https://www.sap.com/products/erp/grow.html)で、RISE with SAPの中核にはSAP Cloud ERPとSAP Cloud ERP Privateのどちらも置けると述べています。GROWはパブリックエディションの上に構築されています。

つまり「RISEでパブリックかプライベートか」は実際の選択です。商用パッケージとエディションは別々の判断であり、エディションの判断を先に行うべきです。

## S/4HANAのパブリッククラウドとプライベートクラウド：各エディションでできること

SAPはSAP Help Portalで[パブリック、プライベート、オンプレミスの各エディションの提供内容の比較](https://help.sap.com/docs/SAP_S4HANA_CLOUD_PE/b89b8b9026e1456bb2a1df7c0d59c937/1485d139460246d2a4b936c0bb0ca272.html)を公開しています。次の表は、多くのケースで判断を分ける部分をまとめたもので、2026年10月に確認しました。

| 領域 | パブリックエディション（SAP Cloud ERP） | プライベートエディション（SAP Cloud ERP Private） |
|---|---|---|
| 移行の方法 | 新規導入のみ | 新規導入、システムコンバージョン、選択的データ移行、またはリフトアンドシフト |
| 設定 | SAP Central Business Configuration | カスタマイジングへの完全なアクセス |
| 拡張性 | キーユーザー拡張（インアプリ）、ABAP Cloudによる開発者拡張、SAP BTPでのサイドバイサイド拡張 | すべての拡張オプション |
| SAPコードの変更 | 不可 | 可能。ただしSAPは推奨していない |
| アップグレード | 年2回（2月と8月）、SAPが管理 | 新リリースは2年ごと。最初の2年間は6か月ごとにフィーチャーパック。顧客の依頼に応じてSAPが適用 |
| メンテナンス | 常に最新リリースを使用 | リリースごとに7年間。メンテナンス対象であり続けるにはアップグレードの計画が必要 |
| 業種 | 消費財、ディスクリート製造、エネルギー・天然資源、金融サービス、公共サービス、サービス業 | すべての業種 |
| アドオン | パブリックエディション認定のアドオンのみ | S/4HANA認定のアドオン |
| ホスティング | SAPのデータセンターまたはハイパースケーラー | ハイパースケーラー、SAPのデータセンター、プライベートデータセンター、ソブリンクラウド |

多くのケースを決めるのは3つの行です。設定、業種、そして移行の方法です。

Central Business Configurationは、SAPのベストプラクティスのスコープを決め、その範囲内で設定を調整する仕組みです。ECCのチームが知っている完全なカスタマイジングのツリーは使えません。財務、価格設定、ロジスティクスの設計がそのツリーの奥深くにある設定に依存しているなら、パブリックエディションにはそれがありません。

業種の行はスコープの宣言であって、マーケティング用の一覧ではありません。中核プロセスがパブリックエディションの一覧にない業種に属するなら、ほかのどんな問いよりも先に、プライベートエディションの領域に入っています。

CFOが過小評価しがちなのがアップグレードの行です。[パブリックエディションのSAPアップグレードスケジュール](https://community.sap.com/t5/enterprise-resource-planning-blog-posts-by-sap/getting-ready-for-the-2608-upgrade-of-the-sap-cloud-erp-public-edition/ba-p/14421165)では、3システム構成の顧客の本番環境における2608アップグレードは2026年8月15日と16日に設定されていました。その日付を決めたのは顧客ではなくSAPです。

## 私のルール：標準プロセスはパブリッククラウドへ

私のルールは短いものです。特別な設定を必要としない標準プロセスは、パブリッククラウドに移せます。

それ以外は、より厳しく見極める必要があります。誰かがパブリッククラウドの契約に署名する前に、私なら次の兆候を確認します。

1. **業種の適合。** 中核事業が、パブリックエディションの対応業種の外にある。
2. **設定の深さ。** 価格設定、収益、原価計算、決済のロジックが、Fit-to-StandardワークショップではSAPのベストプラクティスに対応づけられない設定に依存している。
3. **アドオン。** パブリックエディション認定を受けていないSAPまたはパートナーのアドオンに依存している。
4. **プロセスのオーナーシップ。** 業務部門に標準に合わせてプロセスを変える意思がなく、それを決められる権限者もいない。
5. **履歴。** 再導入してデータをロードするのではなく、履歴と設定ごとECCを変換したい。

兆候が1つだけなら、話し合いの材料です。2つ以上あれば、答えはプライベートエディションになると私は考えます。

エンターテインメント業界のある企業がパブリッククラウドを選び、後悔したのを私は見てきました。その企業のニーズは標準的ではなく、パブリッククラウドは合っていませんでした。

教訓は、パブリッククラウドが弱いということではありません。想定された業種の企業にはよく機能します。教訓は、適合性の確認をExploreの最中ではなく、契約の前に行わなければならないということです。

逆の誤りにも注意してください。プロセスの大半が標準的な企業が、安全そうだという理由でプライベートクラウドを選び、そこでECC時代の習慣を作り直してしまうケースです。必要のなかった柔軟性に料金を払い、アップグレードのたびに守らなければならないカスタムコードを抱えることになります。

## Clean Coreとアップグレード：契約で引き受けるトレードオフ

Clean Coreとは、カスタマイズを最小限にとどめ、きちんと管理することです。誰がそれを強制するかはエディションで決まります。

パブリックエディションでは、システムが強制します。新規開発はABAP Cloudとリリース済みインターフェースだけを使い、SAPのコードは変更できません。拡張のレベルについては、私の[SAP Clean Coreガイド](/ja/sap-clean-core-strategy-what-it-means-for-your-business/)で詳しく説明しています。

プライベートエディションでは、Clean Coreはガバナンスの判断です。コアを変更することは依然として可能で、変更の一つ一つが、アップグレードのたびに抱えるコストになります。

だからこそ、どちらのエディションを選んでも、私なら業務部門とITで構成するデザインオーソリティにすべての例外を管理させます。ITだけなら、技術的に可能なことは何でも承認してしまいます。業務部門だけなら、昔のプロセスを戻すよう求めます。

私が最もよく見るClean Coreの誤りは、SAPをOracleのように動かそうとすることです。チームはSAPの標準プロセスを採用する代わりに、別のシステムのロジックをカスタムコードで作り直します。パブリックエディションではそれが設計段階で破綻し、問題を見つける場所としてはそのほうが安く済みます。

アップグレードのトレードオフも同じ論理に従います。

- **パブリックエディション。** 常に最新リリースを使い、年2回新機能を受け取ります。テストも年2回、SAPのカレンダーに従って行います。年度末決算の最中であってもです。
- **プライベートエディション。** メンテナンス期間内でいつアップグレードするかを選べます。その自由は使ってこそ価値があります。アップグレードしないプライベートエディションのシステムは、クラウドの請求書が付いたECCシステムにすぎないからです。

## エディションの選択はECC移行にとって何を意味するか

ECCの顧客にとって、エディションが移行アプローチを決めます。パブリックエディションは常に新規導入です。設定とプロセスはSAPのベストプラクティスに基づいて作り直され、移るのは業務データだけです。プライベートエディションは、私の移行ガイドで説明したシステムコンバージョンと選択的データ移行のアプローチに対応しています。

私の経験では、パブリックエディションでのGROW with SAPプロジェクトは約6から9か月かかります。RISE with SAPのプログラムは9から18か月で、主にアプローチとカスタムコードによって変わります。私の[S/4HANA移行のスケジュールとプロジェクト計画](/ja/s4hana-migration-timeline-project-plan/)で、それをフェーズごとに分解しています。

2層モデルは有効な中間ルートです。SAPは、親会社がプライベートエディション、子会社がパブリックエディションを使い、両者を統合している顧客事例を公開しています。子会社が本当に標準的であれば機能しますが、自社で担うべき統合作業が加わります。

エディションによって商談の内容も変わります。サブスクリプションの指標、フルユーザー換算（FUE）のサイジング、各パッケージに含まれるものが異なります。RISEの契約で私が最もよく見る落とし穴は、更新条件、FUEのサイジング、AIクレジットです。交渉すべき点は、私の[RISE with SAPの契約と価格](/ja/rise-with-sap-contract-pricing/)のガイドで扱っています。

署名する前に、私ならSAPとパートナーに次の質問をします。

1. 当社のエンドツーエンドのプロセスのうち、パブリックエディションのスコープが現在カバーしているのはどれで、ロードマップ上にしかないのはどれか。
2. 当社のアドオンのうち、提案されたエディションの認定を受けているのはどれか。
3. 当社の現在の設定のうち、Central Business Configurationに相当するものがないのはどれか。
4. アップグレードのカレンダーは、当社の年度末決算と繁忙期に対してどうなっているか。
5. パブリックエディションで始めて手狭になった場合、どのような道筋があり、それは新しいプロジェクトになるのか。
6. 一般的なエディション比較ではなく、当社の業務に即したハイレベル設計を見せてほしい。

最後の質問が最も重要です。一般的な情報で答えるパートナーには、この選択について助言する準備ができていません。その話し合いの残りは、私の[S/4HANA移行パートナーの選び方](/ja/choose-s4hana-migration-partner/)のガイドで扱っています。

## 私が次にすること

主要な20の業務プロセスを取り上げ、それぞれを「標準」「設定を伴う標準」「固有」に分類してください。スライドからではなく、プロセスオーナーが同席した場で行ってください。

ほぼすべてが標準なら、パブリックエディションの提案と、実データを使ったFit-to-Standardワークショップを求めてください。中核プロセスのいくつかが固有である場合や、ECCを変換したい場合は、プライベートエディションを求め、初日からClean Coreのガバナンスを計画してください。アプローチの問いには、私の無料の[グリーンフィールドとブラウンフィールドの移行アセスメント](/ja/sap-s4hana-migration-strategy-greenfield-vs-brownfield/)が役立ちます。

私は、契約で固まってしまう前にこの判断を下せるよう組織を支援しています。独立した視点が必要でしたら、[ご連絡ください](/ja/contact-noel-erp-support/)。

## よくある質問

<details>
<summary>RISE with SAPはパブリッククラウドですか、プライベートクラウドですか？</summary>

どちらもあり得ます。SAPによれば、RISE with SAPの中核にはパブリックエディションであるSAP Cloud ERPか、SAP Cloud ERP Privateを置けます。複雑なプロセスを持つECC顧客の多くはプライベートを選びますが、RISEそのものがエディションを決めるわけではありません。

</details>

<details>
<summary>S/4HANA Cloudのパブリックエディションとプライベートエディションの違いは何ですか？</summary>

パブリックエディションはSaaSで、SAPのベストプラクティス、SAP Central Business Configuration、SAPが管理する年2回のアップグレードがあり、SAPのコードは変更できません。プライベートエディションは、カスタマイジングへの完全なアクセス、すべての業種、すべての拡張オプション、ECCからのシステムコンバージョンに対応します。新リリースは2年ごとで、リリースごとに7年間のメンテナンスがあります。

</details>

<details>
<summary>SAP Cloud ERPはS/4HANA Cloud Public Editionと同じですか？</summary>

実質的には同じです。SAPはクラウドERPをSAP Cloud ERPとして販売しており、SAP S/4HANA Cloud Public Editionがその中核アプリケーションです。プライベート製品は現在SAP Cloud ERP Privateと呼ばれ、多くの人はいまもS/4HANA Cloud Private Editionとして知っています。

</details>

<details>
<summary>SAP ECCをS/4HANA Cloud Public Editionに変換できますか？</summary>

できません。パブリックエディションは新規導入にしか対応していないため、SAPのベストプラクティスに基づいてプロセスを作り直し、業務データを移行します。ECCからのシステムコンバージョンと選択的データ移行は、プライベートエディションとオンプレミスでのみ利用できます。

</details>

<details>
<summary>S/4HANA Cloud Private EditionではSAPのコードを変更できますか？</summary>

できます。SAPはプライベートエディションでの変更を、可能だが推奨しないものとしています。変更のたびに将来のアップグレードの工数が増えるため、私なら一つ一つを業務部門とITで構成するデザインオーソリティに通し、存在理由を記録します。

</details>

<details>
<summary>SAPのパブリッククラウドERPを選ぶべきなのはどのような企業ですか？</summary>

プロセスが標準的で特別な設定を必要とせず、パブリックエディションが対応する業種に属し、SAPのベストプラクティスを採用する意思がある企業です。業種固有のプロセス、踏み込んだ設定、変換したいECCシステムを持つ企業には、通常プライベートエディションのほうが合います。

</details>

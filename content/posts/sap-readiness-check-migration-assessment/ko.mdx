S/4HANA 마이그레이션 평가는 ECC 시스템을 옮기는 데 드는 비용과 기간, 그리고 맞는 경로를 알려 줍니다. SAP Readiness Check는 그 평가의 기술적인 절반입니다. 시스템을 S/4HANA와 비교해 무엇이 깨질지 나열하지만, 결정을 대신 내려 주지는 않습니다.

짧게 답하면, Readiness Check를 먼저 운영 시스템에서 커스텀 코드 결과를 업로드한 상태로 실행하십시오. 그다음 실제 노력은 점검이 보지 못하는 것에 쓰십시오. 프로세스, 데이터, 커스텀 오브젝트, 인터페이스를 애초에 옮겨야 하는지입니다.

전체 마이그레이션 순서는 제 [ECC에서 S/4HANA로의 마이그레이션 가이드](/ko/ecc-to-s4hana-migration/)에서 시작하십시오.

## SAP Readiness Check란 무엇인가

SAP Readiness Check for SAP S/4HANA는 SAP의 클라우드 애플리케이션입니다. ECC 시스템에서 데이터 수집기를 실행하고, 결과를 업로드하면, S/4HANA가 그 시스템에 미치는 영향을 보여 주는 대화형 대시보드를 받습니다.

SAP의 [Readiness Check 주요 기능 개요](https://help.sap.com/doc/bb0e7ba5158c424ab7ce010228bf1de1/latest/en-US/Key%20Feature%20Overview%20SAP%20Readiness%20Check.pdf)(2026년 9월)에 따르면, 유효한 SAP 유지보수 계약이 있는 모든 고객이 SAP for Me에서 쓸 수 있습니다. SAP Cloud ALM 테넌트가 있는 고객은 그곳에서도 실행할 수 있고, 결과를 Cloud ALM에 프로젝트 작업으로 보낼 수 있습니다.

별도로 구매하지 않습니다. 실제 비용은 Basis 팀과 결과를 읽는 사람들의 시간입니다.

SAP는 업그레이드, BW/4HANA, 기타 제품용으로 별도 시나리오를 운영합니다. ECC 마이그레이션에 필요한 것은 SAP Readiness Check for SAP S/4HANA입니다. SAP의 [전환 준비 학습 콘텐츠](https://learning.sap.com/courses/implementing-sap-s-4hana-cloud-private-edition/performing-system-preparation-activities-for-system-conversions_c131e647-d7d1-4887-a2ff-c01b25966a52)가 설명하듯, 타깃은 S/4HANA 온프레미스 또는 RISE with SAP의 타깃인 SAP S/4HANA Cloud Private Edition이 될 수 있습니다.

## Readiness Check가 다루는 것

S/4HANA 시나리오에 대한 SAP의 현재 목록에는 점검 항목이 17개 있습니다. 아래 표는 마이그레이션 결정에 가장 중요한 항목을 묶어, 각각이 알려 주는 것과 제가 조심할 지점을 정리했습니다.

| 점검 | 알려 주는 것 | 조심할 지점 |
|---|---|---|
| 단순화 항목 | 귀사 시스템에 해당하는 S/4HANA 변경 사항, 공수 순위와 관련 작업 | 주로 테이블 내용과 사용된 트랜잭션에 근거하므로, 해결책이 아니라 관련성을 보여 줌 |
| 애드온 호환성 | 각 SAP 및 서드파티 애드온이 타깃 릴리스에 호환, 비호환, 미확인인지 | 비호환 애드온은 SUM에서 전환을 막음, "미확인"은 벤더에 문의해야 한다는 뜻 |
| 활성 비즈니스 기능 | 호환되지 않아 전환을 막을 비즈니스 기능 | 여기서 차단 요소가 나오면 일찍 SAP 지원 인시던트를 올려야 함 |
| 커스텀 코드 분석 | 영향별로 묶은 ATC 또는 Custom Code Migration 앱 결과, 빠른 수정 건수, 사용 및 미사용 범위 | 커스텀 코드 결과를 별도로 업로드해야만 나타남 |
| SAP S/4HANA 사이징 | 초기 HANA 메모리와 디스크 크기, 상위 테이블, 아카이빙 잠재량 | 사이징의 출발점일 뿐, 최종 하드웨어나 RISE 사이징이 아님 |
| 통합 | IDoc, RFC와 BAPI, 웹 서비스, OData, BW 추출기, 플랫 파일, SLT 목록과 예상 영향 | 이 시스템의 기술 인터페이스만 보여 주며, 반대편 시스템은 보여 주지 않음 |
| 고객 공급업체 통합 | 이미 비즈니스 파트너가 된 고객과 공급업체 수, 데이터 품질 문제 | 비즈니스 파트너 전환은 다른 어떤 전제 조건보다 많은 팀의 발목을 잡음 |
| 재무 데이터 품질 | 연도와 회사 코드별 총계정원장, 자산회계, 자재 원장의 불일치 | 범주 D 결과는 시스템별 수정이 필요하며 시간이 걸림 |
| 계획 다운타임 계산기 | 데이터 센터 하나에서 하는 표준 SUM 전환의 예상 업무 다운타임 | 참고용일 뿐이며, 실제 기간은 컷오버 계획이 정함 |
| 앱 가용성과 추천 Fiori 앱 | 지원 중단되거나 대체된 트랜잭션, 사용 패턴에 맞는 Fiori 앱 | UX 설계가 아니라 추천 |
| Business Process Discovery | 프로세스 자동화율, 지연된 미처리 건, 비표준 오더 유형 | 프로세스 인사이트의 미리보기이며, 아래에서 더 자세히 다룸 |

## 실행 방법

핵심 안내는 [SAP Note 2913617](https://me.sap.com/notes/2913617), SAP Readiness Check for SAP S/4HANA입니다. SAP가 전제 조건 노트를 정기적으로 업데이트하므로, 시작하기 전에 최신 버전을 읽으십시오.

<stepper title="Readiness Check 실행" steps="준비|수집|커스텀 코드|업로드|검토" bodies="분석할 시스템(보통 운영 시스템)에 SAP Note 2913617에 나열된 노트를 적용합니다.|데이터 수집 보고서 RC_COLLECT_ANALYSIS_DATA를 백그라운드 작업으로 실행하고, 타깃 릴리스를 고른 뒤 ZIP을 내려받습니다.|ATC 또는 Custom Code Migration 앱에서 S/4HANA 커스텀 코드 점검을 실행하고 결과를 내보냅니다.|SAP for Me의 SAP Readiness Check 페이지에서 새 분석을 만들고 두 파일을 모두 업로드합니다.|Basis, 재무, 프로세스 오너, 커스텀 코드 리더와 함께 모든 점검 항목을 살펴봅니다."></stepper>

단계 목록에 드러나지 않는 몇 가지가 있습니다.

1. **운영 시스템을 쓰십시오.** SAP의 안내는 운영 시스템을 분석하라는 것입니다. 그 결과로 계획을 세우게 되기 때문입니다. 여러 점검이 실제 사용 이력에 의존하는데, 샌드박스에는 그것이 없습니다.
2. **커스텀 코드 결과를 업로드하십시오.** 기본 데이터 수집은 그 자체로 커스텀 코드를 분석하지 않습니다. 아무도 ATC나 Custom Code Migration 앱 결과를 같은 분석에 업로드하지 않으면, 커스텀 코드 섹션은 비어 있고 보고서는 실제 시스템보다 깨끗해 보입니다.
3. **타깃 릴리스를 확인하십시오.** 실제로 안착할 S/4HANA 또는 Private Edition 릴리스를 고르십시오. 단순화 항목과 애드온 상태는 릴리스마다 바뀝니다.
4. **어느 정도의 시행착오를 예상하십시오.** 데이터 수집기가 실패하고, 노트가 빠져 있고, 대형 시스템에서는 작업이 오래 걸립니다. 공수만이 아니라 그에 필요한 경과 시간도 계획하십시오.

시작 페이지는 [me.sap.com/readinesscheck](https://me.sap.com/readinesscheck)입니다.

## Readiness Check가 놓치는 것

이 점검은 한 가지 질문에 강합니다. 이 시스템의 무엇이 S/4HANA와 충돌하는가입니다. 그것이 애초에 존재해야 하는지에 답하도록 만들어지지는 않았습니다.

### 커스텀 오브젝트

제 경험상 Readiness Check가 놓쳐서 나중에 문제를 일으키는 것은 커스텀 오브젝트입니다. 단순화 항목에 비춰 어떤 커스텀 코드가 깨지는지는 알려 줍니다. 하지만 어떤 Z 프로그램, 테이블, 개선, 양식, 보고서가 여전히 비즈니스 목적에 쓰이는지, 어떤 것이 S/4HANA 표준 기능과 중복되는지, 어떤 것을 몇 년째 아무도 실행하지 않았는지는 알려 주지 않습니다.

이 공백이 중요한 이유는 제가 보는 프로그램에서 커스텀 코드가 가장 자주 초과되는 단계이기 때문입니다. 예산에서 가장 자주 잊히는 숨은 비용이기도 합니다.

결과 건수와 커스텀 오브젝트 수는 다른 숫자입니다. 한 프로그램에서는 smartShift 분석으로 커스텀 오브젝트를 18,000개에서 3,200개로 줄였습니다. Readiness Check만으로는 그렇게 줄이지 못했을 것입니다. 가치가 아니라 영향을 측정하기 때문입니다.

그래서 저는 커스텀 코드 섹션을 목록 작성의 끝이 아니라 시작으로 봅니다. Custom Code Migration 앱은 사용 및 미사용 범위를, smartShift는 자동 분석과 수정을 더하며, 무엇을 폐기할지는 여전히 현업의 누군가가 동의해야 합니다.

### 분석 대상 시스템 밖의 모든 것

이 점검은 ECC 시스템 하나를 봅니다. 다음은 보지 못합니다.

1. **프로세스 설계.** 주문에서 수금까지(order-to-cash)나 기록에서 보고까지(record-to-report)를 재설계해야 하는지입니다. 이것이 그린필드, 브라운필드, 선택적 전환을 결정합니다.
2. **인터페이스의 반대편.** ECC의 인터페이스는 나열합니다. 미들웨어, 서드파티 시스템, 그 담당자는 범위 밖입니다.
3. **아직 로드하지 않은 데이터.** 비SAP 시스템의 데이터, 그리고 재무와 비즈니스 파트너 밖의 데이터 품질입니다.
4. **조직과 변화.** 누가 결정을 소유하는지, 사용자가 얼마나 준비되어 있는지, 프로그램 동안 현업이 무엇을 감당할 수 있는지입니다.
5. **상업 조건.** 라이선스 전환, RISE 범위, 파트너 비용은 어떤 SAP 대시보드에도 없습니다.

Business Process Discovery는 프로세스 성과를 처음 들여다보게 해 줍니다. 더 깊은 SAP 분석은 SAP Signavio Process Insights, discovery edition이며, SAP의 [지원의 가치 페이지](https://support.sap.com/en/release-upgrade-maintenance/value-support.html)는 이를 여섯 개 사업 영역에 걸친 프로세스 개선 권고라고 설명합니다. 유용한 입력이지만, 여전히 설계는 아닙니다.

## 전체 S/4HANA 마이그레이션 평가가 더해 주는 것

마이그레이션 평가는 Readiness Check를 하나의 입력으로 삼아, 예산을 배정할 수 있는 결정으로 바꿉니다. 둘을 비교하면 다음과 같습니다.

| 질문 | SAP Readiness Check | 전체 마이그레이션 평가 |
|---|---|---|
| ECC의 무엇이 S/4HANA와 충돌하는가? | 예, 상세히 | 점검 결과를 활용 |
| 어떤 커스텀 오브젝트를 유지, 폐기, 재구축해야 하는가? | 일부: 영향, 그리고 Custom Code Migration 앱을 쓰면 사용량 | 예: 오브젝트 목록, 사용량, 현업 담당자, 결정 |
| 그린필드, 브라운필드, 선택적 전환 중 무엇인가? | 아니요 | 예, 프로세스와 데이터 분석 결과에 근거 |
| 어떤 인터페이스와 외부 시스템이 바뀌는가? | ECC 쪽만 | 양쪽 모두, 담당자와 수정 방안 포함 |
| 재무 밖의 데이터는 얼마나 깨끗한가? | 일부 | 예, 정제 계획과 담당자 포함 |
| 얼마나 걸리고 비용은 얼마인가? | 다운타임과 사이징 추정만 | 일정, 비용 범위, 예비비 |
| 어떤 배포 및 상업 모델인가? | 아니요 | 온프레미스, Private Edition, Public Edition, 그리고 협상할 항목 |

제가 쓰는 도구는 SAP Readiness Check, 커스텀 코드에는 Custom Code Migration 앱과 smartShift, 선택적 데이터 전환이 검토 대상일 때는 SNP나 Natuvion입니다. 어느 것도 프로세스 오너와 함께하는 설계 검토를 대신하지 못합니다.

나머지는 제 경로 원칙이 정합니다. 다른 시스템에서 옮겨 오거나 새 프로세스를 정의해야 하면 그린필드, 프로세스가 정의되어 잘 작동하면 브라운필드, 일부 영역의 프로세스를 다시 정의해야 하면 선택적 전환입니다. 돈을 쓰기 전에 첫 판단이 필요하다면 제 무료 [S/4HANA 마이그레이션 평가 도구](/ko/sap-s4hana-migration-strategy-greenfield-vs-brownfield/)가 같은 트레이드오프를 차례로 짚어 줍니다.

그 결과는 곧바로 [마이그레이션 일정과 프로젝트 계획](/ko/s4hana-migration-timeline-project-plan/), 그리고 [마이그레이션 비용 추정](/ko/s4hana-migration-cost/)으로 이어져야 합니다. 파트너에게 건네는 것도 이것입니다. 파트너가 귀사 평가에 구체적인 상위 수준 설계로 답하지 못한다면, 그 자체로 알려 주는 것이 있습니다. 제 [S/4HANA 마이그레이션 파트너 선택](/ko/choose-s4hana-migration-partner/) 가이드에서 그 단계를 다룹니다.

## 제대로 된 평가에 걸리는 기간

상황에 따라 다릅니다. 회사마다 요인이 너무 달라서 숫자 하나를 제시하지는 않겠습니다.

기간을 움직이는 요인은 다음과 같습니다.

1. **시스템과 클라이언트 수.** ECC 운영 시스템 하나와, BW, CRM, SRM이 따로 있는 다섯 개는 다른 일입니다.
2. **커스텀 코드 양.** 수천 개의 커스텀 오브젝트에는 사용량 분석과 현업의 결정이 필요하며, 그것은 도구의 시간이 아니라 사람의 시간입니다.
3. **인터페이스.** 모든 외부 시스템에는 자기 쪽에서 무엇이 바뀌는지 말해 줄 담당자가 필요합니다.
4. **법인과 국가.** 회사 코드가 많을수록 현지화, 세금, 보고에 관한 질문이 늘어납니다.
5. **데이터 품질.** 큰 재무 불일치나 엉망인 비즈니스 파트너 데이터는 누군가 추정하기 전에 조사가 필요합니다.
6. **현업의 가용성.** 평가에 실제 시간을 내줄 수 있는 프로세스 오너가 어떤 도구보다 기간을 더 줄입니다.
7. **접근 권한.** 노트 승인과 운영 시스템 작업 일정을 기다리는 동안에는 분석 없이 경과 시간만 늘어납니다.

제가 하지 않을 일은 빌드를 빨리 시작하려고 평가를 줄이는 것입니다. 제가 이끌었거나 구해 낸 21개 SAP 프로그램에서 본 가장 큰 실수는 처음에 계획을 제대로 세우지 않는 것입니다. 평가는 그 계획이 시작되는 곳입니다.

## 제가 다음에 할 일

이번 달에 Basis 팀에 운영 시스템에 SAP Note 2913617을 적용하고, 커스텀 코드 결과를 포함해 Readiness Check를 실행하도록 요청하십시오. 그다음 재무 리더, 프로세스 오너 한 명, 커스텀 코드 리더와 반나절을 잡아 함께 결과를 읽고, 점검이 답하지 못하는 질문을 나열하십시오.

그 목록이 마이그레이션 평가의 범위입니다. 파트너를 찾아가기 전에 독립적인 시각이 필요하다면 [연락해 주십시오](/ko/contact-noel-erp-support/).

## 자주 묻는 질문

<details>
<summary>S/4HANA용 SAP Readiness Check란 무엇입니까?</summary>

SAP ERP 시스템을 SAP S/4HANA에 비춰 분석하는 SAP의 클라우드 애플리케이션입니다. 시스템에서 데이터 수집기를 실행하고 결과를 SAP for Me에 업로드하면, 단순화 항목, 애드온, 비즈니스 기능, 커스텀 코드, 사이징, 인터페이스, 비즈니스 파트너, 재무 데이터 품질, 추천 Fiori 앱을 다루는 대시보드를 받습니다.

</details>

<details>
<summary>SAP Readiness Check는 SAP 고객에게 무료입니까?</summary>

SAP는 유효한 SAP 유지보수 계약이 있는 모든 고객에게 SAP for Me에서, Cloud ALM 테넌트가 있는 고객에게는 SAP Cloud ALM에서 이를 제공합니다. 실제 비용은 시스템을 준비하고 결과를 해석하는 내부 인력과 파트너의 시간입니다.

</details>

<details>
<summary>SAP Readiness Check는 어떻게 실행합니까?</summary>

보통 운영 시스템에 SAP Note 2913617의 노트를 적용합니다. 데이터 수집 보고서 RC_COLLECT_ANALYSIS_DATA를 실행해 ZIP을 내려받고, 커스텀 코드 분석은 ATC나 Custom Code Migration 앱에서 따로 실행합니다. SAP for Me의 SAP Readiness Check 페이지에서 두 결과를 하나의 분석에 업로드합니다.

</details>

<details>
<summary>SAP Readiness Check가 다루지 않는 것은 무엇입니까?</summary>

커스텀 오브젝트가 여전히 필요한지, 프로세스를 재설계해야 하는지, 인터페이스 반대편에서 무슨 일이 일어나는지, 프로그램 비용이 얼마인지는 결정하지 않습니다. 시스템 하나의 기술적 호환성을 분석합니다. 나머지 질문은 전체 마이그레이션 평가의 몫입니다.

</details>

<details>
<summary>S/4HANA 마이그레이션 평가는 얼마나 걸립니까?</summary>

시스템 수, 커스텀 코드 양, 인터페이스와 법인 수, 데이터 상태, 프로세스 오너가 낼 수 있는 시간에 따라 달라집니다.

</details>

<details>
<summary>그린필드나 브라운필드를 고르기 전에 Readiness Check를 실행해야 합니까?</summary>

예. 시스템의 얼마만큼이 S/4HANA와 충돌하는지 보여 주며, 이는 경로 결정의 한 입력입니다. 결정 자체는 프로세스가 정의되어 잘 작동하는지에 달려 있으며, 점검은 그것을 측정하지 않습니다.

</details>

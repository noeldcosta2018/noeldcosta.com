Выбор между Databricks и Microsoft Fabric сводится к тому, кто потребляет данные. Если большая их часть попадает в Power BI, а ваша команда мыслит в SQL, Fabric обычно быстрее и проще. Если ваши трудные задачи лежат в инженерии, потоковой обработке, машинном обучении или работе в нескольких облаках, Databricks сильнее.

Для многих организаций на стеке Microsoft честный ответ: обе. Azure Databricks берёт на себя тяжёлую инженерию.

Fabric и Power BI обслуживают бизнес. Это работает, но только если вы сознательно проектируете стык между ними.

В программах в производстве и оборонной отрасли, где я работал, решение редко зависит от списков функций. Оно зависит от модели затрат, навыков, границ безопасности и того, где данным разрешено находиться.

## Как устроены обе платформы

Обе являются lakehouse на открытых табличных форматах. Различаются они тем, кто владеет хранилищем и как вы платите за вычисления.

**Microsoft Fabric** представляет собой SaaS-платформу. Всё попадает в OneLake, одно логическое озеро на тенант, а таблицы хранятся в формате Delta. Lakehouse, хранилище (warehouse), конвейеры, Real-Time Intelligence и Power BI используют одну общую мощность (capacity).

Shortcuts указывают на данные в других хранилищах без копирования. Mirroring подтягивает базы данных и внешние каталоги.

**Databricks** работает в вашей облачной учётной записи (в Azure как Azure Databricks, собственный сервис Microsoft первой стороны). Ваши данные лежат в вашем хранилище под управлением Unity Catalog. Вычисления представлены кластерами, SQL warehouses или бессерверными ресурсами (serverless) и учитываются по каждой нагрузке в Databricks Units (DBU).

По открытости разрыв сократился. OneLake виртуализирует метаданные, так что таблицу Delta можно читать как Iceberg, а таблицу Iceberg как Delta. Есть реальные ограничения: только Parquet, вывод в Iceberg V2, а equality deletes ломают конвертацию.

Управляемые таблицы Iceberg в Unity Catalog общедоступны, и внешние движки читают и записывают их через Iceberg REST Catalog API в Unity Catalog. Ни одна из платформ не запирает ваши данные в проприетарном формате. Обе запирают ваши конвейеры, модель безопасности и навыки, и именно там сидит реальная стоимость перехода.

Для компании на стеке Microsoft важнее всего мост между ними. Fabric может [зеркалировать Unity Catalog из Azure Databricks](https://learn.microsoft.com/en-us/fabric/mirroring/azure-databricks) как элемент каталога, эта функция общедоступна. Зеркалируются только метаданные.

Сами данные читаются на месте через shortcuts. Одна загвоздка: разрешения Unity Catalog не переносятся. Fabric применяет собственную модель разрешений.

## Цены Databricks и Fabric: мощность против потребления

**Fabric** продаёт мощность в F-SKU, от F2 до F8192, измеряемую в единицах мощности (CU). Azure выставляет счёт посекундно без обязательств, либо вы резервируете мощность на год. В регионе East US цена по прайс-листу при оплате по мере использования (pay-as-you-go) составляет $0,18 за CU-час.

Получается, что F64 стоит около $11,52 в час, или примерно $8 400 в месяц, если не выключать. Microsoft утверждает, что резервирование экономит около 41% по сравнению с pay-as-you-go.

Горячее хранилище OneLake стоит по прайс-листу $0,026 за ГБ в месяц. См. [страницу цен Microsoft Fabric](https://azure.microsoft.com/en-us/pricing/details/microsoft-fabric/).

F64 также служит порогом лицензирования. Согласно [документации по лицензированию Fabric](https://learn.microsoft.com/en-us/fabric/enterprise/licenses), ниже F64 каждому, кто просматривает контент Power BI, нужна лицензия Pro или Premium Per User.

Начиная с F64, зрители с бесплатной лицензией и ролью viewer могут читать отчёты. Если у вас несколько сотен читателей отчётов, одно это может определить выбор SKU.

**Azure Databricks** берёт плату в DBU по типу нагрузки, плюс виртуальные машины Azure под ними для классических вычислений. Тарифы serverless уже включают вычисления.

Ниже цены по прайс-листу для East US Premium. См. [страницу цен Azure Databricks](https://azure.microsoft.com/en-us/pricing/details/databricks/).

1. Jobs compute: $0,30 за DBU-час.
2. All-purpose compute (интерактивные ноутбуки): $0,55 за DBU-час.
3. SQL Pro: $0,55 за DBU-час. Serverless SQL: $0,70 за DBU-час.
4. Serverless jobs: $0,45 за DBU-час. Serverless interactive compute: $0,95 за DBU-час.

Все цифры являются ценами по прайс-листу для East US, проверены в октябре 2026 года. В других регионах они отличаются.

Корпоративные соглашения, предоплаченные обязательства Databricks и резервирования Azure меняют реальную цифру. Моё [руководство по ценам Databricks](/ru/databricks-pricing-explained/) подробнее разбирает DBU.

Что это значит на практике:

1. **Fabric предсказуем, но мощность общая.** Одно тяжёлое задание Spark может притормозить отчёты Power BI на той же мощности. Кто-то должен управлять мощностью, как общим сервером.
2. **Databricks детализирован, но склонен к утечкам.** Каждая нагрузка стоит ровно столько, сколько потребляет. Обычные утечки: кластеры, которые забыли выключить, завышенные по размеру warehouses и all-purpose compute, используемый для заданий по расписанию.
3. **Сравнивайте полную стоимость на реальных нагрузках.** Оцените свои десять главных конвейеров и самый загруженный час отчётности на обеих платформах. Таблица с ценами из прайс-листа ничего не доказывает.

## Сравнение бок о бок

В таблице собраны пункты, которые обычно решают дело для организации на стеке Microsoft.

| Критерий | Microsoft Fabric | Databricks (Azure Databricks) |
|---|---|---|
| Модель поставки | SaaS, один OneLake на весь тенант | Платформа в вашей облачной учётной записи и хранилище |
| Ценообразование | Мощность F-SKU, pay-as-you-go или резервирование | DBU по нагрузке, плюс VM для классических вычислений |
| Глубина инженерии данных | Хорошо для SQL, конвейеров, Dataflows и ноутбуков Spark | Глубже: тонкая настройка Spark, потоковая обработка, декларативные конвейеры, CI/CD |
| ML и GenAI | Copilot in Fabric, агенты данных Fabric (GA), ML-модели и эксперименты | Model serving, MLflow, Genie, Agent Bricks |
| Power BI | Нативно; Direct Lake на OneLake | Через mirroring в Fabric либо DirectQuery и Import |
| Управление данными | Разрешения Fabric, безопасность OneLake, Purview, метки конфиденциальности | Unity Catalog; Purview может его сканировать |
| Мультиоблако | Только Azure | Azure, AWS и Google Cloud |
| Соответствие навыкам | Power BI, SQL и команды данных Microsoft | Инженеры данных, Python и Spark, ML-инженеры |

**Power BI и Direct Lake.** Direct Lake позволяет семантической модели Power BI читать таблицы Delta в OneLake прямо в память, без обновления импорта. Это самая сильная причина использовать Fabric.

Для него нужна мощность Fabric, а лимиты на таблицы растут вместе с SKU. Зеркалированный каталог Azure Databricks является поддерживаемым источником для Direct Lake, поэтому таблицы gold, построенные в Databricks, могут питать отчёты Direct Lake.

**ML и GenAI.** Агенты данных Fabric, которые отвечают на вопросы на обычном языке по данным OneLake, общедоступны. Некоторые интеграции, например использование их из Microsoft 365 Copilot, всё ещё в preview. Copilot in Fabric требует платной мощности F2 или больше и расходует её.

В Databricks Genie позволяет бизнес-пользователям запрашивать управляемые таблицы на обычном языке. Agent Bricks служит платформой для создания и развёртывания собственных агентов в коде.

Теперь Databricks относит Knowledge Assistant и Supervisor Agent к устаревшим (legacy) и направляет новую low-code работу в Genie Agents. Мой [материал о Genie и Agent Bricks](/ru/databricks-genie-agent-bricks/) разбирает это подробно.

**Управление данными.** Unity Catalog является более зрелой единой плоскостью управления для таблиц, моделей, lineage и детального доступа между рабочими пространствами и облаками. Управление в Fabric быстро улучшается.

В среде Microsoft корпоративным каталогом часто уже служит Purview, и он умеет сканировать метаданные и lineage Unity Catalog. Моё [руководство по управлению данными в Unity Catalog](/ru/databricks-unity-catalog-data-governance/) разбирает сторону Databricks.

## Схема «используем обе»: честный взгляд

Большинство организаций на стеке Microsoft, которые я вижу, не выбирают что-то одно. Они используют Azure Databricks для загрузки, инженерии и ML, а затем открывают подготовленные таблицы для Fabric ради Power BI. С зеркалированием каталога и Direct Lake эта схема теперь хорошо поддерживается.

Она работает, когда выполняются три условия:

1. **Каждым слоем владеет одна платформа.** Databricks владеет слоями от bronze до gold. Fabric владеет семантическими моделями и отчётами. Никто не строит одну и ту же таблицу дважды.
2. **Безопасность проектируется дважды, но один раз.** Mirroring не копирует разрешения Unity Catalog. Решите, кто владеет правилами на уровне строк и столбцов в Fabric, и задокументируйте соответствие.
3. **Кто-то один отвечает за счёт по обеим платформам.** DBU и мощность попадают в разные статьи затрат. Без единого владельца каждая команда оптимизирует свою платформу, а общая сумма растёт.

Схема ломается, когда Fabric исподволь становится второй инженерной платформой, и у вас появляются два слоя gold, которые не сходятся. Там, где я видел, как «используем обе» идёт не так, всё сводилось к двум вещам: интеграция между платформами была выстроена неправильно, и никто не знал, какая платформа владеет данными. Я предпочитаю установить правило в первый же день, чем распутывать это потом.

Для данных ERP (SAP, Oracle или Microsoft Dynamics 365) действует та же логика. Загружайте и моделируйте их один раз, в одном месте. Мои заметки о [модернизации ERP и clean core](/ru/erp-modernization-2025-cloud-ai-clean-core/) объясняют, почему сторона ERP важна не меньше платформы.

## Оборонная отрасль и производство: что учесть

**Производство.** Данные с заводов становятся стресс-тестом. Потоки из историков и MES, высокочастотные потоки датчиков, записи о качестве и обслуживании, связанные с ERP. Real-Time Intelligence в Fabric (eventstreams и eventhouses) хорошо справляется с операционными дашбордами.

Для крупномасштабной потоковой инженерии, конвейеров признаков для предиктивного обслуживания и ML на данных датчиков я использую Databricks. Потоковая обработка и машинное обучение на данных датчиков и оборудования: именно здесь он оправдывает себя в моей работе.

**Оборонная отрасль.** На первом месте суверенитет и разделение. Секретные и несекретные среды остаются раздельными. Данные под экспортным контролем (ITAR как категория) требуют строгого контроля доступа и аудита.

Программы длятся десятилетиями. Здесь проверьте доступность до того, как что-либо проектировать, потому что государственные облака отстают от коммерческого Azure.

1. **Fabric в GCC High.** Согласно [Microsoft Learn](https://learn.microsoft.com/en-us/fabric/enterprise/us-government-community-cloud-high) (проверено в октябре 2026 года), Fabric работает в US Gov Virginia и US Gov Texas. Основные нагрузки доступны, включая lakehouse, warehouse, конвейеры и Power BI с Direct Lake. Ключи, управляемые клиентом, большинство источников mirroring, Private Link для рабочих пространств и Copilot for Power BI не поддерживаются. Авторизация FedRAMP High для GCC High всё ещё на оценке.
2. **Azure Databricks в Azure Government.** Согласно [списку функций Azure Databricks по регионам](https://learn.microsoft.com/en-us/azure/databricks/resources/feature-region-support), обновлённому 1 октября 2026 года, регионы US Gov не поддерживают Databricks SQL и Unity Catalog. В них также нет serverless и новых AI-функций. Databricks объявил о планах вывести полную платформу в Azure Government. Проверьте, что работает в вашем регионе, в тот день, когда принимаете решение.

За пределами США действует та же дисциплина. Проверьте региональные таблицы для того конкретного региона Azure, к которому вы привязаны. Ряд функций serverless и AI в Databricks в некоторых регионах требует обработки за пределами географии, что для суверенных данных может сразу исключить вариант.

## Правила выбора: Fabric, Databricks или обе

**Выбирайте Fabric, когда:**

1. Главный потребитель Power BI, и вам нужен Direct Lake.
2. Ваша команда ориентирована на SQL, Power BI и Microsoft, а глубокой экспертизы в Spark мало.
3. Вам нужен один счёт за мощность и SaaS-эксплуатация, а не платформенная инженерия.
4. У вас сотни зрителей отчётов, и лицензирование на F64 сходится по цифрам.

**Выбирайте Databricks, когда:**

1. Трудная часть в инженерии данных, потоковой обработке или ML, а не в отчётности.
2. Вы работаете больше чем в одном облаке или ожидаете этого.
3. Вам нужен Unity Catalog как единая плоскость управления для многих рабочих пространств.
4. Вам нужен жёсткий контроль затрат по каждой нагрузке, и у вас есть навыки для этого.

**Выбирайте обе, когда** вы уже хорошо эксплуатируете Azure Databricks, а бизнес живёт в Power BI. Зеркалируйте Unity Catalog в Fabric, используйте Direct Lake для отчётов и запишите, кто владеет каждым слоем.

Если у вас уже есть зрелая платформа Databricks, не переносите её в Fabric ради экономии на BI. Для более широкого взгляда посмотрите моё [сравнение Snowflake и Databricks](/ru/snowflake-vs-databricks/).

## Что делать дальше

Проведите двухнедельный сравнительный тест в равных условиях на трёх реальных нагрузках: один тяжёлый конвейер, одна модель Power BI для руководства, один сценарий ML или AI. Измерьте стоимость одного запуска, задержку обновления и трудозатраты вашей команды. Попросите поставщиков или вашего системного интегратора оценить именно этот набор по вашим согласованным ставкам.

Задайте каждому поставщику три вопроса: что в моём регионе GA, а что в preview, что происходит с затратами, когда использование удваивается, и как работает безопасность на стыке.

## Часто задаваемые вопросы

<details>
<summary>Заменяет ли Microsoft Fabric Azure Databricks?</summary>

Нет. Azure Databricks остаётся собственным сервисом Azure, и Microsoft документирует, как они работают вместе. Fabric может зеркалировать Unity Catalog из Azure Databricks (функция общедоступна), поэтому Power BI может использовать таблицы Databricks через Direct Lake без копирования данных. Многие организации используют обе платформы.

</details>

<details>
<summary>Fabric дешевле Databricks?</summary>

Зависит от набора нагрузок. Fabric представляет собой общую мощность (цена по прайс-листу в East US $0,18 за CU-час, примерно на 41% меньше при резервировании на год). Databricks берёт плату в DBU по каждой нагрузке, плюс VM для классических вычислений. Оцените свои главные нагрузки на обеих платформах.

</details>

<details>
<summary>Может ли Power BI использовать данные Databricks без Fabric?</summary>

Да. Power BI подключается к SQL warehouses в Databricks в режиме Import или DirectQuery. Для Direct Lake нужна мощность Fabric, а зеркалированный каталог Azure Databricks является поддерживаемым источником для Direct Lake.

</details>

<details>
<summary>Переносится ли безопасность Unity Catalog в Fabric?</summary>

Нет. Когда Fabric зеркалирует каталог Azure Databricks, он зеркалирует метаданные и читает данные через shortcuts. Политики и разрешения Unity Catalog не зеркалируются, поэтому применяется собственная модель разрешений Fabric. Проектируйте и документируйте правила доступа на стороне Fabric.

</details>

<details>
<summary>Доступен ли Microsoft Fabric в Azure Government?</summary>

Fabric работает в среде GCC High в US Gov Virginia и US Gov Texas с более узким набором функций, чем коммерческий Fabric. Ключи, управляемые клиентом, большинство источников mirroring и Copilot for Power BI не поддерживаются, согласно Microsoft Learn на октябрь 2026 года. FedRAMP High для GCC High всё ещё на оценке. Проверьте актуальный список перед планированием.

</details>

<details>
<summary>Что лучше для машинного обучения: Databricks или Fabric?</summary>

У Databricks более глубокие инструменты для ML и GenAI: MLflow, model serving, Genie и Agent Bricks для собственных агентов. Fabric покрывает ML-эксперименты и модели, агентов данных (GA) и Copilot, а его агентов данных можно использовать из Microsoft Foundry (в preview). Если ML является ключевой возможностью, а не дополнением, Databricks обычно оказывается более сильной основой.

</details>

私が初めてSAP BTP Cockpitで赤いエラーバナーを見たとき、自分が何か間違えたのだと思いました。リンクをクリックし間違えたのかもしれない。セッションの有効期限が切れたのかもしれない。

4回目になって、これは自分だけの問題ではないとはっきりしました。

数週間にわたって、何かが壊れるたびにメモを取り続けました。Integration Suiteを開くときのInternal Server Error、一見正しく見えるのに接続しないdestination、昨日は動いていたのに今日は理由もなく固まるアプリ。パターンが見えてきました。しかも、そのどれも役に立つ形ではどこにも文書化されていませんでした。

これはレアケースではありません。多くの開発者が実際に遭遇するものです。そして、いちばん厄介なのは問題そのものではなく、Cockpitが手がかりになるフィードバックをほとんど返してくれないことです。

## 2024-2026年にかけてBTP Cockpitで変わったこと

トラブルシューティングの一覧に入る前に、知っておく価値のある点がいくつかあります。BTP Cockpitのユーザー体験は2024-2025年を通じて変化しており、その影響で、古いスクリーンショットと比べて見え方が変わっています。Cloud Foundryが現在のデフォルトランタイムです。Neoは保守フェーズに入っており、新機能のサポートは限定的です。そのため、2026年時点で開発者が継続的に直面する問題の多くは、Cloud Foundry寄りのものです。Subaccountとdirectoryの構造は、以前のバージョンにはなかった階層を通じて、global accountレベルで管理されることが増えています。Integration Suite、Build、Datasphereは、基盤となるBTPサービスとCockpit体験をより多く共有するようになりました。その結果、destination設定や認証パターンは、以前よりもサービス間で一貫性が高くなっています。

以下の5つの問題は、Cloud Foundryと、まだ関係がある範囲でのNeoの両方で発生します。また、RISEに含まれるBTP entitlementでも、単体のBTP subscriptionでも見られます。特によく出るのは次のものです。

## 問題1: ログインと認証情報の失敗（401 unauthorized）

サービスインスタンスを作成し、service keyを生成し、JSONからclient IDとsecretをコピーします。Postmanに貼り付けます。token URLを追加します。リクエストを送ります。すると401が返ります。詳細はありません。ただunauthorizedと出るだけです。

認証情報を再確認します。secretをもう一度コピーします。それでも失敗します。壊れているのはサービスではありません。OAuthフローです。

**確認すべきこと:**

1. **Grant type。** ほとんどのBTPサービスは`client_credentials`を使います。Postmanでこれを明示的に設定してください。デフォルトを当てにしてはいけません。
2. **Token URL。** service keyのJSONから正確にコピーしてください。1文字でも違えば壊れます。別の環境から流用してはいけません。
3. **Headers。** token URLを直接呼ぶ場合は、`Content-Type`を`application/x-www-form-urlencoded`に設定し、client IDとsecretを`Authorization: Basic <base64(clientid:clientsecret)>`としてエンコードしてください。
4. **Scopes。** 一部のサービスでは、tokenリクエストにscopeフィールドが必要です（service key内の`xsappname`を確認してください）。これがなくてもtoken自体は返ることがありますが、そのtokenではAPI呼び出しを認可できません。
5. **サービスインスタンスの状態。** trialアカウントではサービスがアイドル状態になります。Cockpitで、インスタンスがまだアクティブか確認してください。
6. **Token audience。** tokenは取得できているのにAPIが失敗する場合は、jwt.ioでデコードしてください。`aud`クレームを確認します。呼び出しているAPIと一致していなければ、それが原因です。

| 確認項目 | 確認方法 |
|---|---|
| Grant type | authorization codeでもpassword flowでもなく、`client_credentials`を明示的に使います。 |
| Token URL | service keyのJSONから直接コピーします。変更はしません。 |
| HTTP headers | `Content-Type: application/x-www-form-urlencoded` + `Authorization: Basic <base64 encoded>` |
| Scopes | service keyで`xsappname`または`scope`フィールドを確認し、存在する場合はtokenリクエストに含めます |
| サービスインスタンスの稼働状況 | Cockpitでインスタンスがアクティブか確認し、trialアカウントでアイドルなら再起動します |
| Token audience | jwt.ioでデコードし、`aud`クレームが呼び出しているAPIと一致している必要があります |

## 問題2: 壊れたナビゲーションと死んだリンク

「Go to Application」や「Open in Cockpit」をクリックすると、空白画面、汎用的なランディングページ、あるいは意味不明なリダイレクトが表示されます。

これはランダムではありません。予測できるパターンがあります。

1. **boosters**内のリンクは、subaccountの設定が途中で変わると壊れます。リダイレクトによってホームページに飛ばされたり、間違ったspaceに落とされたりします。
2. **Integration Suite**のタイルリンクは、動くときもあれば、internal errorになるときもあり、タイムアウトすることもあります。
3. **Workzone and Launchpad**のリンクは、entitlementが存在していても「connection denied」と表示されます。
4. 複数のタブやブラウザープロファイルを使うとセッションの同期が崩れ、期限切れのコンテキストでリンクが開くことがあります。

**効果がある回避策:**
1. Integration Suite、Destination Management、Launchpadの直接URLをブックマークしてください。アプリ内リンクに頼ってはいけません。
2. Cockpitツリーから手動で移動します。Subaccount → Services → Instances → Subscriptions。
3. クリーンなブラウザープロファイルでCockpitセッションを1つだけ使ってください。複数タブは避けます。

より大きな問題は予測可能性です。3回に1回リンクが失敗するようになると、設計どおりにプラットフォームを使うのではなく、回避策を積み上げることになります。

## 問題3: Internal Server Errors（特にIntegration Suite）

Integration Suiteを開こうとします。期待した画面の代わりに、赤い「Internal Server Error」バナーが表示されます。それだけです。ログもありません。説明もありません。

再読み込みしても壊れたままです。別のブラウザーでも同じ結果です。

これは通常、サービスが数時間アイドル状態だった後に起きます。朝に開いたままにして、休憩後に戻ると発生します。非アクティブ状態がバックエンドの状態不整合を引き起こしているように見えますが、Cockpitは何も示してくれません。

**通常これで解消します:**
1. ブラウザーのキャッシュとCookieを削除します。これでセッションが十分にリセットされ、ページが読み込めるようになります。
2. Cockpitでentitlementとサービス状態を確認します。サービスはアラートなしでunboundまたはpausedになることがあります。
3. subaccountからサービスを再バインドまたは再起動します。Integration Suiteでは安定して効きます。
4. アクティブなCockpitタブは1つだけにします。複数タブによるセッション競合はよくあるトリガーです。

根本的な問題は可視性です。表に出てくるログがなく、何が失敗したのかの説明もありません。解決は試行錯誤になります。だからこそ、無駄に時間を取られます。

## 問題4: CAPアプリでのdestination設定失敗

CAPアプリをデプロイし、Cockpitでdestinationを設定しても、リクエストは失敗したままです。destinationは一覧にあり、アプリも動いているのに、「destination not found」や認証エラーが出ます。

見た目はすべて正しく見えます。エラーメッセージは役に立ちません。汎用的すぎるか、間違った場所を指しているかのどちらかです。

**よくある原因:**

1. destination名が`xs-app.json`または`cds.env`で正しく参照されていません。名前は完全一致である必要があります。
2. ODataバージョンの不一致です。アプリがv2を想定しているのにdestinationがv4サービスを指している場合（またはその逆）、CAPは黙って失敗します。不一致の吸収には`@sap/cds-odata-v2-adapter-proxy`を使ってください。
3. 認証方式が間違っています。ほとんどのCAPシナリオでは、`OAuth2ClientCredentials`または`BasicAuthentication`を使ってください。SAMLは、明確な要件がない限り不要な複雑さを持ち込みます。
4. destinationがアプリと同じsubaccountにありません。

**トラブルシューティングチェックリスト:**

| 問題 | 対処 |
|---|---|
| destinationは一覧にあるがアプリからアクセスできない | `xs-app.json`と`cds.env`の名前を確認します。完全一致が必要です |
| ODataバージョン不一致 | CAPアプリで`@sap/cds-odata-v2-adapter-proxy`パッケージを使います |
| 認証情報が正しいのに認証に失敗する | `OAuth2ClientCredentials`または`BasicAuthentication`に切り替えます |
| ローカルでは動くがデプロイ後に失敗する | デプロイ先環境の`cds.env`を確認し、destinationが正しいsubaccountにあることを確認します |
| destinationに到達できるか確信が持てない | デプロイ前にBTP CockpitのDestination Checkerツールを使います |

これをうまく回しているチームは、設定チェックリストを維持しています。設定が複雑だからではありません。バージョン、名前、認証方式のどれかで1つ思い込みを間違えるだけで、黙って失敗します。そして、その原因特定に本来より長い時間がかかります。

## 問題5: trial環境でのスロットリングとリソース制限

昨日まで動いていたCAPアプリが、今日は固まります。エラーは出ません。Cockpit上では稼働中に見えます。再起動してみても変わりません。

これは通常、trial環境でのスロットリングかリソース枯渇です。SAPはこれを明確には表示しません。Cockpit UIでは実際に何を消費しているのかがほとんど見えず、trialアカウントの制限もインターフェース内では十分に文書化されていません。

その結果、本当の原因は知らないうちに上限に達していたことなのに、アプリコードのデバッグを始めることになります。

**実際に役立つこと:**

1. CLIツール（`cf apps`、`cf services`）を使って、メモリとサービス消費量を確認してください。Cockpit UIではこの大半が隠れています。
2. ワークロードを複数のsubaccountに分散してください。すべてを1つにデプロイしてはいけません。
3. 長時間非アクティブだったサービスは手動で再起動してください。
4. 新しいサービスを作成する前に、未使用のサービスを削除してください。trialの制限はアプリ単位だけでなく、global quotaも含みます。

これに繰り返し当たるなら（アプリが複数ある、データベースが複数ある、あるいはデモ用に安定した稼働時間が必要なら）、安定性だけを理由にしても有償プランにする価値はあります。

## よくある質問

<details>
<summary>service keyの認証情報が正しく見えるのに、なぜ401エラーになるのですか？</summary>

ほぼ常に、認証情報の問題ではなくOAuthフローの問題です。最も多い原因は2つです。grant typeを間違えていること（BTPサービスでは`client_credentials`が必要です）、またはservice keyのJSONと完全一致しないtoken URLを使っていることです。

headersを確認してください。tokenリクエストには`Content-Type: application/x-www-form-urlencoded`が必要で、認証情報はAuthorization headerでbase64エンコードされている必要があります。scopeが必要な場合（service keyの`xsappname`フィールドを確認してください）に、それがリクエストに含まれていないと、token自体は返ってきてもAPI呼び出しは認可されません。

tokenは取得できているのにAPIが拒否する場合は、jwt.ioでtokenをデコードして`aud`クレームを確認してください。呼び出しているAPIと一致している必要があります。

</details>

<details>
<summary>BTP CockpitでIntegration Suiteを開くとInternal Server Errorになる原因は何ですか？</summary>

通常は、一定時間非アクティブだった後に起きます。サービスはバックグラウンドで縮退した状態に入りますが、Cockpitには何も表示されません。アラートもなく、ステータス変更もありません。開こうとしたときに初めてエラーが出ます。

通常これで解消します。ブラウザーのキャッシュとCookieを削除すること、Cockpitでサービスインスタンスがまだアクティブか確認すること（そうでなければ再起動または再バインドすること）、そしてアクティブなCockpitセッションを1つだけにすることです。複数タブは、サービス自体に問題がなくても、このエラーを引き起こすセッション競合を生みます。

</details>

<details>
<summary>Cockpitでは正しく見えているdestinationに、なぜCAPアプリが接続できないのですか？</summary>

最も多い原因は名前の不一致です。`xs-app.json`または`cds.env`で参照しているdestination名は、Cockpit上の名前と大文字小文字まで含めて完全一致している必要があります。

名前が正しいなら、次にODataバージョンを確認してください。アプリがv2を想定しているのにdestinationがv4サービスを指している場合、CAPは黙って失敗します。不一致の吸収には`@sap/cds-odata-v2-adapter-proxy`パッケージを使ってください。

認証方式もよくある原因です。`OAuth2ClientCredentials`または`BasicAuthentication`は、ほとんどのCAPシナリオで安定して動きます。SAMLのようなより複雑な方式は、デバッグしにくい変数を増やします。

アプリをデプロイする前に、CockpitのDestination Checkerツールで接続性を検証してください。

</details>

<details>
<summary>trialアカウントでリソース制限に達したかどうかは、どう確認すればよいですか？</summary>

Cockpit UIではこれが明確に表示されません。CLIを使ってください。`cf apps`ではアプリごとのメモリ消費量、`cf services`では使用中サービスの総数が確認できます。trialアカウントにはglobal quotaがありますが、Cockpitダッシュボードには表示されません。

アプリが起動しない、または新しいサービスインスタンスの作成が黙って失敗するなら、原因はリソース枯渇である可能性が高いです。再試行する前に、未使用のアプリとサービスを削除してください。定期的に上限に達するなら、複数のtrial subaccountにワークロードを分散するのが有効です。あるいは、安定性のために有償プランへ移行することです。

</details>

<details>
<summary>boostersやタイル内のリンクが空白ページや間違った場所に飛ぶのはなぜですか？</summary>

boosterが生成したリンクは、セットアップ後にsubaccount構造が変わると壊れます。特定の場所を指していたリダイレクトが、すでに存在しない場所や、正しく設定されていない場所へ送るようになります。

確実な回避策は、Cockpitツリーから手動で移動することです。Subaccount → Services → Instances → Subscriptions。日常的に使うツールの直接URLはブックマークしてください。Integration Suite、Destination Management、Launchpadです。重要な操作でショートカットタイルやbooster生成ナビゲーションに頼ってはいけません。

</details>

<details>
<summary>BTP trialアカウントから有償プランへ移るべきタイミングはいつですか？</summary>

リソース制限が日常的に作業へ影響し始めたときです。複数のアプリやデータベースを管理している場合、あるいはデモやテストのために安定した稼働時間が必要な場合、trial環境はいずれ価値より摩擦のほうが大きくなります。

有償プランで必ずしも機能が変わるわけではありません。主な利点は、安定性とリソース可視性が明確になることです。trialのスロットリングは予測しづらく、Cockpitでも明確に見えません。そのため、実際にはコードの問題ではないものにデバッグ時間を使うことになります。

</details>

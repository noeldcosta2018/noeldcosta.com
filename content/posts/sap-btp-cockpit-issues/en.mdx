# SAP BTP Cockpit issues: five problems developers run into and how to fix them

The first time I saw the red error banner in SAP BTP Cockpit, I thought I'd done something wrong. Maybe I clicked the wrong link. Maybe my session had expired.

After the fourth time, it became clear it wasn't just me.

Over a few weeks I kept notes on every time something broke. Internal Server Errors opening Integration Suite, destinations that refused to connect despite looking valid, apps that worked yesterday and hung today for no apparent reason. Patterns emerged. None of them were documented anywhere useful.

These are not edge cases. They're what a lot of developers run into, and the frustration usually isn't the issue itself; it's that the Cockpit gives almost no feedback to work with.

Here are the five that come up most often.

## Issue 1: Login and credential failures (401 unauthorized)

You create a service instance, generate a service key, copy the client ID and secret from the JSON. Plug them into Postman. Add the token URL. Make the request. Get a 401. No detail. Just unauthorized.

You double-check the credentials. Copy the secret again. Still fails. The service isn't broken; the OAuth flow is.

**What to check:**

- **Grant type.** Most BTP services use `client_credentials`. Set this explicitly in Postman. Don't assume the default.
- **Token URL.** Copy it exactly from the service key JSON. Even a character difference breaks it. Don't borrow it from another environment.
- **Headers.** When calling the token URL directly, set `Content-Type` to `application/x-www-form-urlencoded` and encode your client ID and secret as `Authorization: Basic <base64(clientid:clientsecret)>`.
- **Scopes.** Some services require a scope field in the token request (look for `xsappname` in the service key). Missing it may still return a token, but that token won't authorize the API call.
- **Service instance status.** On trial accounts, services go idle. Check the Cockpit to confirm the instance is still active.
- **Token audience.** If you're getting a token but the API still fails, decode it at jwt.io. Check the `aud` claim. If it doesn't match the API you're calling, that's the problem.

| What to check | How to validate |
|---|---|
| Grant type | Use `client_credentials` explicitly, not authorization code, not password flow. |
| Token URL | Copy directly from service key JSON. No modifications. |
| HTTP headers | `Content-Type: application/x-www-form-urlencoded` + `Authorization: Basic <base64 encoded>` |
| Scopes | Check service key for `xsappname` or `scope` field; include in token request if present |
| Service instance activity | Confirm instance is active in Cockpit; restart if idle on trial account |
| Token audience | Decode at jwt.io; `aud` claim must match the API you're calling |

## Issue 2: Broken navigation and dead links

You click "Go to Application" or "Open in Cockpit" and get a blank screen, a generic landing page, or a redirect that makes no sense.

This isn't random. It follows predictable patterns:

- Links inside **boosters** break when subaccount setup changes midway. The redirect sends you to the homepage or drops you in the wrong space.
- **Integration Suite** tile links sometimes work, sometimes throw an internal error, sometimes time out.
- **Workzone and Launchpad** links show "connection denied" even when entitlements are present.
- Multiple tabs or browser profiles cause sessions to desync, which makes links open in expired contexts.

**Workarounds that help:**
- Bookmark direct URLs for Integration Suite, Destination Management, and Launchpad. Don't rely on in-app links.
- Navigate manually via the Cockpit tree: Subaccount → Services → Instances → Subscriptions.
- Use one Cockpit session in a clean browser profile. Avoid multiple tabs.

The broader issue is predictability, when a link fails every third time, you start building workarounds instead of using the platform as designed.

## Issue 3: Internal Server Errors (especially Integration Suite)

You try to open Integration Suite. Instead of the expected screen, you get a red "Internal Server Error" banner. Nothing else. No log. No explanation.

You reload. Still broken. Different browser. Same result.

This usually happens after the service has been idle for a few hours: left open in the morning, returned to after a break. The inactivity seems to trigger a backend state issue, but the Cockpit shows you nothing.

**What usually resolves it:**
- Clear browser cache and cookies. This resets the session enough to let the page load.
- Check entitlements and service status in the Cockpit. Services can become unbound or paused without showing an alert.
- Rebind or restart the service from the subaccount. Works reliably for Integration Suite.
- One active Cockpit tab only. Session conflicts from multiple tabs are a common trigger.

The underlying problem is visibility. There's no logging surfaced, no explanation of what failed. The resolution is trial and error, which is why it wastes so much time.

## Issue 4: Destination configuration failures in CAP apps

You deploy a CAP app, configure a destination in the Cockpit, and the requests still fail. The destination is listed, the app is running, but you get "destination not found" or authentication errors.

Everything looks correct. The error messages don't help; they're either too generic or point to the wrong place.

**The common causes:**

- Destination name not correctly referenced in `xs-app.json` or `cds.env`. The name must match exactly.
- OData version mismatch. If your app expects v2 and the destination points to a v4 service (or vice versa), CAP fails silently. Use `@sap/cds-odata-v2-adapter-proxy` to handle the mismatch.
- Wrong authentication method. Use `OAuth2ClientCredentials` or `BasicAuthentication` for most CAP scenarios. SAML adds complexity you don't need unless there's a specific requirement.
- Destination not in the same subaccount as the app.

**Troubleshooting checklist:**

| Issue | Fix |
|---|---|
| Destination listed but app can't access it | Check name in `xs-app.json` and `cds.env`: must match exactly |
| OData version mismatch | Use `@sap/cds-odata-v2-adapter-proxy` package in the CAP app |
| Authentication failures despite valid credentials | Switch to `OAuth2ClientCredentials` or `BasicAuthentication` |
| Works locally but fails after deployment | Check `cds.env` in deployed environment; confirm destination is in the correct subaccount |
| Unsure if destination is reachable | Use the Destination Checker tool in BTP Cockpit before deploying |

Teams that handle this well maintain a configuration checklist, not because it's a complex setup; it's because one wrong assumption about version, name, or auth method causes a silent failure that takes longer to find than it should.

## Issue 5: Throttling and resource limits in trial environments

A CAP app that worked yesterday now hangs. No error. The Cockpit shows it as running. You try restarting. Still nothing.

This is usually throttling or resource exhaustion in the trial environment. SAP doesn't surface this clearly. The Cockpit UI rarely shows what you're actually consuming, and the limits for trial accounts aren't well-documented inside the interface itself.

You end up debugging your app code when the real cause is a quota you didn't know you'd hit.

**What actually helps:**

- Use CLI tools (`cf apps`, `cf services`) to check memory and service consumption. The Cockpit UI hides most of this.
- Spread workloads across multiple subaccounts. Don't deploy everything into one.
- Restart idle services manually after long periods of inactivity.
- Delete unused services before trying to create new ones. Trial limits include global quotas, not just per-app.

If you're hitting this repeatedly (more than one app, more than one database, or needing stable uptime for demos), a paid plan is worth it for the stability alone.

<details>
<summary>Why do I get a 401 error with service key credentials even when they look correct?</summary>

Almost always an OAuth flow problem rather than a credential problem. The two most common causes: using the wrong grant type (BTP services require `client_credentials`) or using a token URL that doesn't match the service key JSON exactly.

Check your headers. The token request needs `Content-Type: application/x-www-form-urlencoded` and the credentials base64-encoded in the Authorization header. If scopes are required (check the service key for an `xsappname` field) and they're missing from the request, you may still get a token back, but it won't authorize the API call.

If you're getting a token but the API still rejects it, decode the token at jwt.io and check the `aud` claim. It must match the API you're calling.

</details>

<details>
<summary>What causes Internal Server Errors when opening Integration Suite in BTP Cockpit?</summary>

Usually follows a period of inactivity. The service goes into a reduced state in the background, but the Cockpit shows nothing: no alert, no status change. The error only appears when you try to open it.

Three things that usually resolve it: clear browser cache and cookies, confirm the service instance is still active in the Cockpit (and restart or rebind if it isn't), and ensure you only have one active Cockpit session. Multiple tabs create session conflicts that trigger this error even when the service itself is fine.

</details>

<details>
<summary>Why does my CAP app fail to connect to a destination that appears correctly in the Cockpit?</summary>

The most common cause is a naming mismatch. The destination name referenced in `xs-app.json` or `cds.env` must match the name in the Cockpit exactly, including case.

If the naming is correct, check the OData version. If your app expects v2 and the destination points to a v4 service, CAP fails silently. Use the `@sap/cds-odata-v2-adapter-proxy` package to handle the mismatch.

Authentication method is another common source. `OAuth2ClientCredentials` or `BasicAuthentication` work predictably for most CAP scenarios. More complex types like SAML introduce variables that are harder to debug.

Use the Destination Checker tool in the Cockpit to validate connectivity before deploying the app.

</details>

<details>
<summary>How do I check if I've hit resource limits in a trial account?</summary>

The Cockpit UI doesn't show this clearly. Use the CLI: `cf apps` shows memory consumption per app; `cf services` shows total services in use. Trial accounts have global quotas that aren't exposed in the Cockpit dashboard.

If an app fails to start or a new service instance silently fails, resource exhaustion is likely the cause. Delete unused apps and services before trying again. If you're regularly hitting limits, spreading workloads across multiple trial subaccounts helps, or moving to a paid plan for the stability.

</details>

<details>
<summary>Why do links inside boosters and tiles lead to blank pages or incorrect locations?</summary>

Booster-generated links break when the subaccount structure changes after setup. A redirect that was pointing to a specific location sends you somewhere that no longer exists or hasn't been properly configured.

The reliable workaround: navigate manually via the Cockpit tree. Subaccount → Services → Instances → Subscriptions. Bookmark the direct URLs for tools you use regularly. Integration Suite, Destination Management, Launchpad. Don't rely on shortcut tiles or booster-generated navigation for anything critical.

</details>

<details>
<summary>When should I move from a BTP trial account to a paid plan?</summary>

When resource limits are affecting your work regularly. If you're managing more than one app or database, or need stable uptime for demos or testing, the trial environment will eventually cause more friction than value.

The paid plan doesn't necessarily give you different features; the main benefit is stability and clearer resource visibility. Trial throttling is unpredictable and the Cockpit doesn't surface it clearly, which means you spend time debugging problems that aren't actually in your code.

</details>

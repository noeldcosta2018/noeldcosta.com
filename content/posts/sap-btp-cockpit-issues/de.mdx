Als ich das erste Mal das rote Fehlerbanner im SAP BTP Cockpit sah, dachte ich, ich hätte etwas falsch gemacht. Vielleicht hatte ich auf den falschen Link geklickt. Vielleicht war meine Sitzung abgelaufen.

Beim vierten Mal war klar: Es lag nicht nur an mir.

Über ein paar Wochen hinweg habe ich mir jedes Mal Notizen gemacht, wenn etwas kaputtging. Internal Server Errors beim Öffnen der Integration Suite, Destinations, die trotz gültiger Konfiguration keine Verbindung aufbauten, Apps, die gestern noch funktionierten und heute ohne erkennbaren Grund hingen. Es zeigten sich Muster. Dokumentiert war davon nirgends etwas wirklich Brauchbares.

Das sind keine Randfälle. Damit haben viele Entwickler zu tun. Und der Frust kommt meist nicht vom eigentlichen Problem, sondern daher, dass das Cockpit fast kein brauchbares Feedback liefert.

## Was sich im BTP Cockpit von 2024 bis 2026 geändert hat

Ein paar Dinge sollten Sie wissen, bevor wir zur Troubleshooting-Liste kommen. Die Benutzererfahrung im BTP Cockpit hat sich 2024-2025 in einer Weise verändert, die beeinflusst, was Sie heute sehen im Vergleich zu älteren Screenshots. Cloud Foundry ist jetzt die Standard-Runtime; Neo befindet sich im Wartungsmodus und bekommt nur noch begrenzt neue Funktionen. Deshalb sind die hartnäckigen Probleme, auf die Entwickler 2026 stoßen, meist Cloud-Foundry-geprägt. Subaccount- und Directory-Strukturen werden zunehmend auf Global-Account-Ebene über Hierarchien gesteuert, die es in früheren Versionen so nicht gab. Integration Suite, Build und Datasphere teilen sich inzwischen mehr von der Cockpit-Erfahrung mit den zugrunde liegenden BTP-Services. Dadurch sind Destination-Konfiguration und Authentifizierungsmuster serviceübergreifend konsistenter als früher.

Die fünf Probleme unten treten sowohl in Cloud Foundry als auch – wo noch relevant – in Neo auf, sowohl bei mit RISE gebündelten BTP-Entitlements als auch bei eigenständigen BTP-Subskriptionen. Das sind die, die am häufigsten auftauchen.

## Problem 1: Login- und Credential-Fehler (401 unauthorized)

Sie erstellen eine Service-Instanz, generieren einen Service Key, kopieren Client ID und Secret aus dem JSON. Fügen beides in Postman ein. Ergänzen die Token-URL. Senden die Anfrage. Bekommen eine 401. Kein Detail. Nur unauthorized.

Sie prüfen die Credentials noch einmal. Kopieren das Secret erneut. Es schlägt weiter fehl. Der Service ist nicht kaputt; der OAuth-Flow ist es.

**Was Sie prüfen sollten:**

1. **Grant Type.** Die meisten BTP-Services verwenden `client_credentials`. Setzen Sie das in Postman explizit. Verlassen Sie sich nicht auf den Standardwert.
2. **Token-URL.** Kopieren Sie sie exakt aus dem Service-Key-JSON. Schon ein einziges abweichendes Zeichen reicht, damit es nicht funktioniert. Übernehmen Sie sie nicht aus einer anderen Umgebung.
3. **Header.** Wenn Sie die Token-URL direkt aufrufen, setzen Sie `Content-Type` auf `application/x-www-form-urlencoded` und kodieren Sie Ihre Client ID und Ihr Secret als `Authorization: Basic <base64(clientid:clientsecret)>`.
4. **Scopes.** Manche Services verlangen ein Scope-Feld in der Token-Anfrage (suchen Sie im Service Key nach `xsappname`). Fehlt es, bekommen Sie unter Umständen trotzdem ein Token zurück, aber dieses Token autorisiert den API-Aufruf nicht.
5. **Status der Service-Instanz.** In Trial-Accounts gehen Services in den Idle-Zustand. Prüfen Sie im Cockpit, ob die Instanz noch aktiv ist.
6. **Token Audience.** Wenn Sie ein Token bekommen, die API aber trotzdem fehlschlägt, dekodieren Sie es auf jwt.io. Prüfen Sie den Claim `aud`. Wenn er nicht zur API passt, die Sie aufrufen, ist das die Ursache.

| Was zu prüfen ist | So validieren Sie es |
|---|---|
| Grant Type | Verwenden Sie explizit `client_credentials`, nicht Authorization Code, nicht Password Flow. |
| Token-URL | Direkt aus dem Service-Key-JSON kopieren. Keine Änderungen. |
| HTTP-Header | `Content-Type: application/x-www-form-urlencoded` + `Authorization: Basic <base64 encoded>` |
| Scopes | Prüfen Sie im Service Key auf das Feld `xsappname` oder `scope`; falls vorhanden, in die Token-Anfrage aufnehmen |
| Aktivität der Service-Instanz | Bestätigen Sie im Cockpit, dass die Instanz aktiv ist; bei Idle im Trial-Account neu starten |
| Token Audience | Auf jwt.io dekodieren; der Claim `aud` muss zur API passen, die Sie aufrufen |

## Problem 2: Defekte Navigation und tote Links

Sie klicken auf "Go to Application" oder "Open in Cockpit" und bekommen einen leeren Bildschirm, eine generische Landingpage oder einen Redirect, der keinen Sinn ergibt.

Das ist nicht zufällig. Es folgt vorhersehbaren Mustern:

1. Links innerhalb von **Boostern** brechen, wenn sich das Subaccount-Setup zwischendurch ändert. Der Redirect schickt Sie auf die Startseite oder in den falschen Space.
2. **Integration Suite**-Tile-Links funktionieren manchmal, werfen manchmal einen internen Fehler und laufen manchmal einfach in ein Timeout.
3. **Workzone- und Launchpad**-Links zeigen "connection denied", obwohl die Entitlements vorhanden sind.
4. Mehrere Tabs oder Browser-Profile führen dazu, dass Sitzungen auseinanderlaufen. Dann öffnen Links in abgelaufenen Kontexten.

**Workarounds, die helfen:**
1. Speichern Sie direkte URLs für Integration Suite, Destination Management und Launchpad als Lesezeichen. Verlassen Sie sich nicht auf In-App-Links.
2. Navigieren Sie manuell über den Cockpit-Baum: Subaccount → Services → Instances → Subscriptions.
3. Verwenden Sie nur eine Cockpit-Sitzung in einem sauberen Browser-Profil. Vermeiden Sie mehrere Tabs.

Das größere Problem ist die fehlende Vorhersehbarkeit. Wenn ein Link jedes dritte Mal fehlschlägt, bauen Sie Workarounds, statt die Plattform so zu nutzen, wie sie gedacht ist.

## Problem 3: Internal Server Errors (vor allem Integration Suite)

Sie versuchen, die Integration Suite zu öffnen. Statt des erwarteten Bildschirms bekommen Sie ein rotes Banner mit "Internal Server Error". Sonst nichts. Kein Log. Keine Erklärung.

Sie laden neu. Weiter kaputt. Anderer Browser. Gleiches Ergebnis.

Das passiert meist, nachdem der Service ein paar Stunden inaktiv war: morgens geöffnet, nach einer Pause wieder zurückgekehrt. Die Inaktivität scheint ein Backend-Statusproblem auszulösen, aber das Cockpit zeigt Ihnen dazu nichts.

**Was es normalerweise löst:**
1. Browser-Cache und Cookies löschen. Das setzt die Sitzung oft weit genug zurück, damit die Seite wieder lädt.
2. Entitlements und Service-Status im Cockpit prüfen. Services können unbound oder pausiert sein, ohne dass ein Hinweis angezeigt wird.
3. Den Service aus dem Subaccount neu binden oder neu starten. Das funktioniert bei der Integration Suite zuverlässig.
4. Nur ein aktiver Cockpit-Tab. Sitzungskonflikte durch mehrere Tabs sind ein häufiger Auslöser.

Das eigentliche Problem ist die fehlende Transparenz. Es gibt keine sichtbaren Logs, keine Erklärung, was fehlgeschlagen ist. Die Lösung ist Trial and Error. Genau deshalb kostet es so viel Zeit.

## Problem 4: Fehler bei der Destination-Konfiguration in CAP-Apps

Sie deployen eine CAP-App, konfigurieren eine Destination im Cockpit, und die Requests schlagen trotzdem fehl. Die Destination ist gelistet, die App läuft, aber Sie bekommen "destination not found" oder Authentifizierungsfehler.

Alles sieht korrekt aus. Die Fehlermeldungen helfen nicht; sie sind entweder zu generisch oder zeigen auf die falsche Stelle.

**Die häufigsten Ursachen:**

1. Der Destination-Name wird in `xs-app.json` oder `cds.env` nicht korrekt referenziert. Der Name muss exakt übereinstimmen.
2. OData-Versionskonflikt. Wenn Ihre App v2 erwartet und die Destination auf einen v4-Service zeigt (oder umgekehrt), schlägt CAP still fehl. Verwenden Sie `@sap/cds-odata-v2-adapter-proxy`, um den Konflikt abzufangen.
3. Falsche Authentifizierungsmethode. Verwenden Sie für die meisten CAP-Szenarien `OAuth2ClientCredentials` oder `BasicAuthentication`. SAML bringt zusätzliche Komplexität, die Sie nicht brauchen, außer es gibt eine konkrete Anforderung.
4. Die Destination liegt nicht im selben Subaccount wie die App.

**Troubleshooting-Checkliste:**

| Problem | Lösung |
|---|---|
| Destination ist gelistet, aber die App kann nicht darauf zugreifen | Namen in `xs-app.json` und `cds.env` prüfen: muss exakt übereinstimmen |
| OData-Versionskonflikt | Paket `@sap/cds-odata-v2-adapter-proxy` in der CAP-App verwenden |
| Authentifizierungsfehler trotz gültiger Credentials | Auf `OAuth2ClientCredentials` oder `BasicAuthentication` wechseln |
| Funktioniert lokal, schlägt aber nach dem Deployment fehl | `cds.env` in der deployten Umgebung prüfen; bestätigen, dass die Destination im richtigen Subaccount liegt |
| Unklar, ob die Destination erreichbar ist | Vor dem Deployment das Tool Destination Checker im BTP Cockpit verwenden |

Teams, die das gut im Griff haben, pflegen eine Konfigurations-Checkliste. Nicht weil das Setup besonders komplex wäre. Sondern weil eine falsche Annahme bei Version, Name oder Auth-Methode zu einem stillen Fehler führt, dessen Suche länger dauert, als sie sollte.

## Problem 5: Throttling und Ressourcenlimits in Trial-Umgebungen

Eine CAP-App, die gestern noch lief, hängt jetzt. Kein Fehler. Das Cockpit zeigt sie als laufend an. Sie versuchen einen Neustart. Weiter nichts.

Meist ist das Throttling oder Ressourcenerschöpfung in der Trial-Umgebung. SAP macht das nicht klar sichtbar. Die Cockpit-UI zeigt selten, was Sie tatsächlich verbrauchen, und die Limits für Trial-Accounts sind in der Oberfläche selbst schlecht dokumentiert.

Am Ende debuggen Sie Ihren App-Code, obwohl die eigentliche Ursache ein Quota-Limit ist, von dem Sie nicht wussten, dass Sie es erreicht haben.

**Was tatsächlich hilft:**

1. Verwenden Sie CLI-Tools (`cf apps`, `cf services`), um Speicher- und Service-Verbrauch zu prüfen. Die Cockpit-UI blendet das meiste davon aus.
2. Verteilen Sie Workloads auf mehrere Subaccounts. Deployen Sie nicht alles in einen einzigen.
3. Starten Sie inaktive Services nach längeren Phasen ohne Nutzung manuell neu.
4. Löschen Sie ungenutzte Services, bevor Sie neue anlegen. Trial-Limits umfassen globale Quotas, nicht nur Limits pro App.

Wenn Ihnen das wiederholt passiert (mehr als eine App, mehr als eine Datenbank oder wenn Sie stabile Verfügbarkeit für Demos brauchen), lohnt sich ein kostenpflichtiger Plan allein schon wegen der Stabilität.

## Häufig gestellte Fragen

<details>
<summary>Warum bekomme ich mit Service-Key-Credentials einen 401-Fehler, obwohl sie korrekt aussehen?</summary>

Fast immer ist es ein OAuth-Flow-Problem und kein Credential-Problem. Die zwei häufigsten Ursachen: der falsche Grant Type (für BTP-Services ist `client_credentials` erforderlich) oder eine Token-URL, die nicht exakt zum Service-Key-JSON passt.

Prüfen Sie Ihre Header. Die Token-Anfrage braucht `Content-Type: application/x-www-form-urlencoded` und die Credentials base64-kodiert im Authorization-Header. Wenn Scopes erforderlich sind (prüfen Sie im Service Key auf ein Feld `xsappname`) und sie in der Anfrage fehlen, bekommen Sie möglicherweise trotzdem ein Token zurück, aber es autorisiert den API-Aufruf nicht.

Wenn Sie ein Token bekommen, die API es aber trotzdem ablehnt, dekodieren Sie das Token auf jwt.io und prüfen Sie den Claim `aud`. Er muss zur API passen, die Sie aufrufen.

</details>

<details>
<summary>Was verursacht Internal Server Errors beim Öffnen der Integration Suite im BTP Cockpit?</summary>

Meist folgt das auf eine Phase der Inaktivität. Der Service geht im Hintergrund in einen reduzierten Zustand, aber das Cockpit zeigt nichts an: keinen Hinweis, keine Statusänderung. Der Fehler erscheint erst, wenn Sie versuchen, ihn zu öffnen.

Drei Dinge lösen das meistens: Browser-Cache und Cookies löschen, prüfen, ob die Service-Instanz im Cockpit noch aktiv ist (und sie neu starten oder neu binden, wenn nicht), und sicherstellen, dass Sie nur eine aktive Cockpit-Sitzung haben. Mehrere Tabs erzeugen Sitzungskonflikte, die diesen Fehler auslösen, selbst wenn der Service selbst in Ordnung ist.

</details>

<details>
<summary>Warum kann meine CAP-App keine Verbindung zu einer Destination aufbauen, die im Cockpit korrekt angezeigt wird?</summary>

Die häufigste Ursache ist ein Namenskonflikt. Der in `xs-app.json` oder `cds.env` referenzierte Destination-Name muss exakt mit dem Namen im Cockpit übereinstimmen, einschließlich Groß- und Kleinschreibung.

Wenn der Name korrekt ist, prüfen Sie die OData-Version. Wenn Ihre App v2 erwartet und die Destination auf einen v4-Service zeigt, schlägt CAP still fehl. Verwenden Sie das Paket `@sap/cds-odata-v2-adapter-proxy`, um den Konflikt zu behandeln.

Auch die Authentifizierungsmethode ist eine häufige Ursache. `OAuth2ClientCredentials` oder `BasicAuthentication` funktionieren in den meisten CAP-Szenarien verlässlich. Komplexere Typen wie SAML bringen zusätzliche Variablen hinein, die schwerer zu debuggen sind.

Verwenden Sie vor dem Deployment der App das Tool Destination Checker im Cockpit, um die Konnektivität zu validieren.

</details>

<details>
<summary>Wie prüfe ich, ob ich in einem Trial-Account an Ressourcenlimits gestoßen bin?</summary>

Die Cockpit-UI zeigt das nicht klar an. Verwenden Sie die CLI: `cf apps` zeigt den Speicherverbrauch pro App; `cf services` zeigt die insgesamt genutzten Services. Trial-Accounts haben globale Quotas, die im Cockpit-Dashboard nicht sichtbar gemacht werden.

Wenn eine App nicht startet oder eine neue Service-Instanz still fehlschlägt, ist Ressourcenerschöpfung wahrscheinlich die Ursache. Löschen Sie ungenutzte Apps und Services, bevor Sie es erneut versuchen. Wenn Sie regelmäßig an Limits stoßen, hilft es, Workloads auf mehrere Trial-Subaccounts zu verteilen, oder auf einen kostenpflichtigen Plan zu wechseln, um mehr Stabilität zu bekommen.

</details>

<details>
<summary>Warum führen Links in Boostern und Tiles zu leeren Seiten oder an falsche Stellen?</summary>

Von Boostern erzeugte Links brechen, wenn sich die Subaccount-Struktur nach dem Setup ändert. Ein Redirect, der auf einen bestimmten Ort gezeigt hat, schickt Sie dann an einen Ort, der nicht mehr existiert oder nicht sauber konfiguriert wurde.

Der verlässliche Workaround: manuell über den Cockpit-Baum navigieren. Subaccount → Services → Instances → Subscriptions. Speichern Sie direkte URLs für die Tools, die Sie regelmäßig nutzen, als Lesezeichen. Integration Suite, Destination Management, Launchpad. Verlassen Sie sich bei nichts Kritischem auf Shortcut-Tiles oder von Boostern erzeugte Navigation.

</details>

<details>
<summary>Wann sollte ich von einem BTP-Trial-Account auf einen kostenpflichtigen Plan wechseln?</summary>

Dann, wenn Ressourcenlimits Ihre Arbeit regelmäßig beeinträchtigen. Wenn Sie mehr als eine App oder Datenbank verwalten oder stabile Verfügbarkeit für Demos oder Tests brauchen, wird die Trial-Umgebung irgendwann mehr Reibung erzeugen als Nutzen bringen.

Der kostenpflichtige Plan gibt Ihnen nicht zwingend andere Funktionen; der Hauptvorteil ist Stabilität und klarere Sicht auf Ressourcen. Trial-Throttling ist unvorhersehbar, und das Cockpit macht es nicht klar sichtbar. Das heißt: Sie verbringen Zeit damit, Probleme zu debuggen, die gar nicht in Ihrem Code liegen.

</details>

SAP S/4HANA Migration Cockpit это инструмент SAP для загрузки основных данных и открытых позиций в новую систему S/4HANA через приложение Fiori Migrate Your Data. Вы выбираете промежуточные таблицы или прямую передачу, отбираете объекты миграции, сопоставляете значения, проводите симуляцию и затем загружаете, объект за объектом, в порядке зависимостей.

Коротко для руководителя программы: используйте его при новом внедрении, планируйте его как отдельное направление работ с первой недели и заранее решите, кто отвечает за данные. Инструмент это самая простая часть.

Это руководство одна из частей моего [руководства по миграции с ECC на S/4HANA](/ru/ecc-to-s4hana-migration/). Оно написано для руководителей программ и руководителей по данным, которым нужно хорошо организовать работу с cockpit, а не просто его установить.

## Что такое Migration Cockpit и где он применяется

Cockpit переносит бизнес-данные в S/4HANA с помощью предопределённых объектов миграции. Каждый объект описывает исходную и целевую структуры для одного бизнес-объекта, например клиента, поставщика, материала или открытой позиции, а также правила маппинга между ними.

SAP чётко определяет его область применения. Cockpit [предназначен для первичной загрузки при новом внедрении](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/29193bf0ebdd4583930b2176cb993268/7a62b59726ce42e7a10770b06940f934.html), а не для синхронизации систем или непрерывного потока данных. Конвертация brownfield не использует его для основного переноса, потому что Software Update Manager конвертирует данные на месте.

Два момента с названиями избавят от путаницы. Старая транзакция Web Dynpro LTMC [устарела и больше не может использоваться для миграции данных](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/29193bf0ebdd4583930b2176cb993268/8f97f0b407024465a283809f0bbe000c.html); в ней можно только просматривать старые проекты. Её преемник это приложение Fiori Migrate Your Data, и именно его теперь имеют в виду, когда говорят «cockpit».

Он применяется во всех редакциях, с различиями в том, как его настраивать и расширять. Эта таблица сравнивает их по состоянию на октябрь 2026 года:

| Область | SAP S/4HANA on-premise и SAP Cloud ERP Private (S/4HANA Cloud Private Edition) | SAP S/4HANA Cloud Public Edition |
|---|---|---|
| Приложение | Migrate Your Data | Migrate Your Data (приложение F3473) |
| Промежуточные таблицы | Локальная схема S/4HANA или удалённая схема SAP HANA | Локальная схема или удалённая схема SAP HANA Cloud на SAP BTP; настраивается через scope item 2Q2 |
| Прямая передача | Из SAP ERP (ECC 6.0 и выше), SAP AFS 6.0, SAP EWM 5.1 и выше и SAP APO SPP (SCM 7.14 и выше) | Из SAP ECC 6.0 и выше; настраивается через scope item BH3 |
| Изменение объектов | Транзакция LTMOM, migration object modeler | Приложение Model Your Migration Objects для промежуточных таблиц; приложение Implementation Activities для прямой передачи; расширять можно только выпущенные объекты |
| Ограничение для исходной системы | Система S/4HANA не может быть источником | Системы S/4HANA, Private Edition и Public Edition не могут быть источником |

## Промежуточные таблицы или прямая передача

Каждый проект миграции использует один из двух подходов. Выбор определяет всё направление работ с данными, поэтому делайте его в Explore, а не в Realize.

**Промежуточные таблицы.** Cockpit создаёт набор таблиц базы данных для каждого объекта миграции в вашем проекте. Вы заполняете их из XML-шаблонов SAP, из CSV-файлов или своими инструментами, например SAP Data Services или другим ETL-инструментом. Источником может быть что угодно: старая система SAP, Oracle, Dynamics, самописная система или электронная таблица.

**Прямая передача.** Cockpit подключается к исходной системе SAP через RFC и сам отбирает данные, для источника ERP по балансовой единице. [Предварительные условия](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/29193bf0ebdd4583930b2176cb993268/94f7b5a36db64633a4d49623f66e04c7.html) включают дополнение DMIS в исходной системе, которое входит в лицензию S/4HANA. Исходные системы могут быть не-Unicode.

Вот как они сравниваются по решениям, которые предстоит принять руководителю по данным:

| Вопрос | Промежуточные таблицы | Прямая передача |
|---|---|---|
| Какие источники? | Любая система, через файлы или инструменты | Только поддерживаемые источники SAP |
| Где очищать данные? | В промежуточных таблицах или раньше, до загрузки | В основном в исходной системе, до отбора |
| Кто может проверить данные до загрузки? | Любой, у кого есть доступ к таблицам или файлам | В основном команда cockpit, через экраны cockpit |
| Трудозатраты на старте | Выше: вы строите извлечение и заполняете таблицы | Ниже: cockpit отбирает данные за вас |
| Лучше всего подходит | Несколько источников, грязные данные, сложные преобразования | Чистый источник SAP ERP, переходящий на новый дизайн S/4HANA |

Прямая передача также может сохранять отобранные данные в промежуточных таблицах как промежуточном хранилище, что даёт вам точку проверки между этапами. Прежде чем строить дизайн вокруг этой возможности, проверьте, поддерживает ли её ваш релиз.

### Почему команды, которыми я руковожу, используют промежуточные таблицы

Команды, которыми я руковожу, работают с cockpit; сам я его руками не запускаю. Их выбор по умолчанию, и моё предпочтение, это промежуточные таблицы, а не прямая передача.

Причина в контроле. С промежуточными таблицами данные, которые будут загружены, лежат в таблицах, к которым можно делать запросы, проверять их по бизнес-правилам и исправлять до того, как что-либо попадёт в S/4HANA. Ответственные за данные могут подписать то, что они действительно видят, а не выборку, которой им приходится доверять.

Это также отделяет очистку от загрузки. Дубликаты поставщиков, отсутствующие банковские реквизиты и неверные единицы измерения исправляются в одном месте, с журналом изменений, а сама загрузка становится повторяемой. Прямую передачу быстрее начать, но она обычно переносит привычки исходной системы прямо в новую.

У прямой передачи всё же есть своё место. Если источник это одна хорошо поддерживаемая система SAP ERP, а целевой дизайн близок к ней, она экономит реальную работу по извлечению.

## Migration Cockpit по шагам

SAP описывает [процесс миграции](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/29193bf0ebdd4583930b2176cb993268/c67e14ff693e423aae2b96d9f3b0fc91.html) как фиксированную последовательность. Вот шаги в том виде, в каком ваша команда будет выполнять их с промежуточными таблицами.

<stepper title="Процесс Migration Cockpit" steps="Создание проекта|Заполнение промежуточных таблиц|Маппинг значений|Симуляция|Миграция и исправление" bodies="Откройте Migrate Your Data, создайте проект и выберите объекты миграции в объёме.|Скачайте шаблоны и загрузите их или заполните таблицы своими инструментами.|Обработайте открытые задачи маппинга: сопоставление значений и фиксированные значения.|Проведите симуляцию загрузки и исправьте каждую ошибку, прежде чем что-либо проводить.|Загружайте в порядке зависимостей, затем исправьте неудачные записи и проведите сверку."></stepper>

1. **Создайте проект миграции.** В приложении Migrate Your Data создайте проект, выберите, где будут находиться промежуточные таблицы (локальная или удалённая схема), и отберите объекты в объёме. SAP рекомендует сначала создавать проекты в тестовой системе, которая является копией продуктивной, и новый проект для каждой тестовой передачи, переносящий исправления из предыдущей.
2. **Проверьте зависимости.** У объекта миграции могут быть предшествующие объекты, которые нужно обработать первыми, и последующие объекты, которые идут после. Приложение Explore Migration Objects (F8638) показывает обязательные и необязательные предшествующие объекты в виде графа. Бизнес-партнёры до открытых позиций, материалы до запасов: cockpit не позволит нарушить порядок.
3. **Заполните промежуточные таблицы.** XML-шаблоны это вариант SAP по умолчанию и рекомендуемый, потому что каждый файл содержит все структуры объекта плюс инструкции. CSV это вариант для экспертов, по одному файлу на структуру. [Один XML-файл может иметь размер до 100 МБ](https://help.sap.com/docs/SAP_S4HANA_ON-PREMISE/29193bf0ebdd4583930b2176cb993268/5cc41962b2624ac5b9a136e69369f5e0.html), и zip-архив из нескольких XML-файлов тоже не может превышать 100 МБ, поэтому крупные объекты нужно разбивать или использовать инструмент, который пишет в таблицы напрямую.
4. **Прочитайте сообщения проверки.** После загрузки система проверяет файл и добавляет лист Messages с каждой ошибкой и предупреждением, привязанными к ячейке. По файлам с предупреждениями кто-то должен решить, можно ли их игнорировать, прежде чем данные пойдут дальше.
5. **Обработайте задачи маппинга.** Задачи сопоставления значений переводят исходные значения в целевые, например старые коды заводов в новые. Задачи фиксированных значений задают значения по умолчанию. Для больших маппингов скачивайте шаблоны маппинга, а не вводите значения на экранах.
6. **Проведите симуляцию.** Симуляция выполняет загрузку без проводки и показывает, какие экземпляры пройдут успешно, а какие нет. Она может создавать новые задачи маппинга; обработайте их и проведите симуляцию снова. Несколько объектов симулировать нельзя, поэтому запланируйте для них дополнительные проверки.
7. **Выполните миграцию.** Загружайте объект за объектом, предшествующие первыми. У некоторых объектов больше одного шага передачи, и каждый шаг по очереди проходит симуляцию и миграцию.
8. **Исправьте и сверьте.** Исправьте неудачные экземпляры, при необходимости с помощью файлов исправлений, затем сверьте количество записей и финансовые итоги с источником. Задание, завершившееся без ошибок, не доказывает, что данные верны.

Прямая передача следует той же схеме, с одним отличием в начале. Вместо заполнения таблиц вы запускаете Select Data по исходной системе и можете дополнительно ограничить выборку в modeler.

## Когда стандартных объектов недостаточно

Рано или поздно какой-нибудь объект миграции подойдёт не совсем. Собственное поле в источнике, разделение, которое нужно сделать при загрузке, или объект, который SAP не поставляет.

On-premise и в частной редакции инструментом служит транзакция LTMOM, SAP S/4HANA migration object modeler. Она позволяет команде расширять стандартные объекты, добавлять поля, определять собственные объекты и управлять транспортом содержимого миграции между системами. Для неё нужна отдельная роль разработчика, поэтому запланируйте, кто её получит.

В публичной редакции возможности уже. Для промежуточных таблиц приложение Model Your Migration Objects может [расширять только определённые объекты миграции, выпущенные SAP](https://help.sap.com/docs/SAP_S4HANA_CLOUD/d5699934e7004d048c4801b552f3b013/947d9c3d00fc4e66851a8f5592871ad3.html), с SAP Note для каждого объекта, где перечислено, что можно расширить. Это согласуется с моделью clean core публичной редакции и хорошо проверяет, действительно ли ваши данные должны выглядеть так, как выглядели раньше.

Мой совет: относитесь к каждому изменению в modeler как к собственному коду. Регистрируйте его, назначайте ответственного и спрашивайте, действительно ли это нужно бизнесу.

## Работа с cockpit как с программой, а не как с инструментом

В программах S/4HANA, которые я вижу, миграция данных составляет 30–40% трудозатрат. Cockpit находится внутри этого направления работ, поэтому большая часть того, что с ним идёт не так, связана не с инструментом.

Пять вещей определяют, будет ли работа с cockpit успешной:

1. **Определите объём объектов в Explore.** Перечислите каждый объект миграции, его источник, объём и ответственного. [Бесплатный оценщик миграции данных](/ru/free-data-migration-estimator-sap-oracle-microsoft/) даст вам обоснованный диапазон трудозатрат, когда у вас будут реальные цифры.
2. **Назначьте владельцев данных для каждого объекта.** Финансы отвечают за финансовые данные клиентов и поставщиков, закупки за материалы. ИТ не может решить, какой из двух дубликатов поставщика правильный.
3. **Планируйте циклы загрузки с критериями выхода.** Каждый цикл это новый проект в тестовой системе, и каждый заканчивается сверкой, которую подписывает бизнес. В моём руководстве о том, [почему миграция данных SAP проваливается](/ru/why-sap-data-migration-fails-and-how-to-fix-it/), есть план пробных загрузок, который можно взять за основу.
4. **Оцените окно cutover.** Проведите один цикл на полном продуктивном объёме. Ограничения на файлы и время загрузки становятся видны только на реальном объёме.
5. **Заморозьте объекты и маппинги до cutover.** Продуктивная загрузка должна повторять финальную репетицию, с теми же проектами, шаблонами и маппингами.

Самая большая ошибка, которую я вижу в программах S/4HANA, это отсутствие нормального планирования в начале. С cockpit она проявляется как поздние списки объектов, отсутствие владельцев и первый цикл загрузки в Realize, который находит проблемы, которые должна была найти фаза Explore.

Эти циклы также формируют общий план. Моё [руководство по срокам миграции на S/4HANA](/ru/s4hana-migration-timeline-project-plan/) показывает, где находятся циклы загрузки на каждом пути, а [руководство по стоимости миграции на S/4HANA](/ru/s4hana-migration-cost/) описывает, что определяет бюджет на данные.

### Что спросить у партнёра о cockpit

До подписания попросите партнёра показать его подход к данным письменно, а не в презентации:

1. Какой подход они предлагают для каждого объекта, промежуточные таблицы или прямую передачу, и почему.
2. Сколько циклов загрузки они планируют и каков критерий выхода для каждого.
3. Какие объекты они собираются менять в modeler и кто будет сопровождать эти изменения.
4. Кто с вашей стороны подписывает каждый объект и когда.

Общие ответы здесь это тревожный признак. Партнёр, который уже делал это раньше, может назвать неудобные объекты для вашей отрасли.

## Что я бы сделал дальше

В этом месяце сделайте полную выгрузку основных данных клиентов, поставщиков и материалов, посчитайте записи и проведите профилирование качества. Затем для каждого объекта выберите промежуточные таблицы или прямую передачу и назначьте ответственных поимённо.

Если вы ещё не оценили исходную систему, начните с [SAP Readiness Check и оценки миграции](/ru/sap-readiness-check-migration-assessment/). Если вам нужен независимый взгляд на ваш план миграции данных, [свяжитесь со мной](/ru/contact-noel-erp-support/).

## Часто задаваемые вопросы

<details>
<summary>Что такое SAP S/4HANA Migration Cockpit?</summary>

Это инструмент SAP для первичной загрузки бизнес-данных в новую систему S/4HANA, работающий через приложение Fiori Migrate Your Data. Он использует предопределённые объекты миграции для основных данных и открытых позиций и поддерживает два подхода: промежуточные таблицы и прямую передачу из исходной системы SAP.

</details>

<details>
<summary>Доступна ли ещё LTMC в S/4HANA?</summary>

Нет, не для миграции данных. SAP объявила транзакцию LTMC устаревшей, и её больше нельзя использовать для миграции данных в S/4HANA. Старые проекты в ней по-прежнему можно просматривать.

Новые миграции выполняются в приложении Migrate Your Data.

</details>

<details>
<summary>Чем отличаются промежуточные таблицы и прямая передача?</summary>

С промежуточными таблицами cockpit создаёт таблицы для каждого объекта миграции, и вы заполняете их из шаблонов XML или CSV или своими инструментами, из любого источника. При прямой передаче cockpit читает данные напрямую из поддерживаемой исходной системы SAP, например SAP ERP 6.0, через RFC-подключение. Промежуточные таблицы дают больше возможностей проверить и очистить данные до загрузки.

</details>

<details>
<summary>Можно ли использовать Migration Cockpit для конвертации brownfield?</summary>

Не для основного переноса. SAP создаёт cockpit для первичной загрузки в сценарии нового внедрения. Конвертация системы brownfield конвертирует данные на месте с помощью Software Update Manager.

</details>

<details>
<summary>Что такое LTMOM в SAP?</summary>

LTMOM это транзакция для SAP S/4HANA migration object modeler, которая используется on-premise и в частной редакции. Она позволяет расширять стандартные объекты миграции, добавлять собственные поля, создавать свои объекты и транспортировать содержимое миграции. В публичной редакции ту же работу в более узком варианте выполняет приложение Model Your Migration Objects.

</details>

<details>
<summary>Какое ограничение на размер файла в S/4HANA Migration Cockpit?</summary>

Один файл XML-шаблона может иметь размер до 100 МБ, а zip-архив из нескольких XML-файлов не может превышать 100 МБ. Файлы внутри архива в несжатом виде могут быть больше, а ограничение на отдельный файл зависит от редакции и релиза.

Папки CSV тоже ограничены 100 МБ. Для очень крупных объектов заполняйте промежуточные таблицы инструментом, а не файлами.

</details>

SAP Business Technology Platform Cockpitは、SAPクラウド環境を管理するための中核となる管理インターフェースです。アプリケーション、サービス、セキュリティ設定、サブスクリプションまで、すべてここを通ります。

Cockpitを主に使うのは3つのグループです。技術管理者は設定と監視を担当します。開発者はアプリケーションをデプロイして管理します。業務ユーザーは特定のツールにアクセスし、それぞれの役割で使う画面が異なります。多くの企業はSAPクラウド製品を購入しても、Cockpitをきちんと学ぶ時間を誰も取らないため、十分な価値を引き出せていません。本来なら数分で終わる作業に何時間もかかります。使っていないサービスのコストが積み上がります。誰も監査していないエンタイトルメントにセキュリティ上の穴が生まれます。

Cockpitへのアクセス先は`https://account.hana.ondemand.com`です。トライアルアカウントの場合は`https://account.hanatrial.ondemand.com`です。SAPユーザーIDが必要です。持っていない場合は管理者に確認してください。

## SAP BTPで解決できること

BTPは、あらゆるSAPクラウド案件で出てくる3つの問題領域に対応します。

**統合。** SAP Cloud Integration（旧CPI）は、ビジュアルな統合フローを使ってS/4HANA、SuccessFactors、Ariba、さらにSalesforceのような非SAPシステムを接続します。API Managementは業務機能を他のアプリケーションに公開します。Event Meshは業務イベントに基づくシステム間通信を処理します。Open Connectorsは数百のサードパーティシステム向けに事前構築済みの統合を提供します。

**コアに手を入れないカスタム開発。** ABAP Cloud Environmentを使うと、開発者はSAPのコアコードを変更せずに拡張を構築できます（そのためアップグレードパスを明確に保てます）。Cloud Foundry runtimeはJava、Node.js、Pythonに対応します。Business Application StudioはブラウザベースのIDEを開発者に提供します。SAP Buildは、業務ユーザー向けにシンプルなアプリケーションを作るためのローコードツールを提供します。

**データ管理。** HANA Cloudはインメモリデータベース機能を提供します。Datasphere（旧Data Warehouse Cloud）は複数ソースのデータを統合し、業務レポーティングに使える形にします。Data Intelligence Cloudは、システム間でデータを移動・変換するためのパイプラインを作成します。

## 日常利用に向けたBTPの設定

次の6つのセクションでは、BTP管理で最もよく使う要素を扱います。アカウント構造、ID管理、サービス、デプロイ、統合、監視です。どれも最初に一度決め、その後プラットフォームの寿命まで付き合う設定判断です。

### サブアカウントとエンタイトルメント

ここで多くのチームが、何年も尾を引く混乱を作ります。

開発、テスト、本番用にサブアカウントを分けてください。グローバルアカウントで「Create Subaccount」をクリックし、一貫した命名規則を使います。たとえば「Finance-Dev」「Finance-Test」「Finance-Prod」のような形です。私が関わったある顧客では、50以上のサブアカウントに無秩序な名前が付いていて、誰も何も見つけられませんでした。プロジェクトの途中でその構造を作り直すのは苦痛です。

マルチ環境構成では、グローバル企業ならリージョン間でサブアカウント構造を揃えてください。開発用エンタイトルメントは最小限に抑えます。本番環境には性能に敏感なリソースを優先的に割り当て、関連するサブアカウントはラベルでまとめます。

**Entitlements**は、各サブアカウントがどのサービスにアクセスできるか、またグローバルアカウントから各サービスをどれだけ使えるかを制御します。「Entitlements」→「Configure Entitlements」に進み、サブアカウントを選んでサービスを追加します。グローバルアカウントで配分できるリソースには上限があります。最初は最小限から始め、必要に応じて追加してください。多くのサービスにはfree tierがあり、テストには便利です。

エンタイトルメントの配分は、必ずCockpitの外でどこかに記録してください。プラットフォーム自体は、何を決めたかも、その理由も追跡してくれません。

### ユーザー管理と認証

サブアカウントで「Security」→「Users」に進みます。ユーザーは個別に追加することも、CSVをアップロードして一括追加することもできます。

組織にIDプロバイダー（Azure AD、Oktaなど）があるなら、手動でユーザー管理するのではなく接続してください。「Security」→「Trust Configuration」に進み、SAPとIdPの間でメタデータファイルを交換します。これで認証まわりの面倒の大半が消え、ユーザーライフサイクル管理も一元化できます。

エンタープライズ構成では、カスタムSAML IDプロバイダーが最も柔軟です。標準のSAP ID Serviceは、テストや小規模導入には十分です。

ロールコレクションは、ユーザーに割り当てる権限の束です。私のやり方はこうです。
1. 個人ではなく職務機能ベースでロールコレクションを作る
2. 意味がある程度には具体的にするが、細かくしすぎて何百個も管理する状態にはしない
3. 緊急時用にbreak-glassの「admin」ロールコレクションを用意する
4. ロール割り当ては四半期ごとに見直す。人は異動しますが、古い権限は残りがちです

二要素認証を有効にし、可能なら信頼できるネットワークにアクセスを制限し、「Security Alerts」セクションを定期的に確認してください。SAPはここで環境内の潜在的な問題を通知します。

### サービスインスタンスとアプリケーション

サービスインスタンスを作成する手順です。
1. サブアカウントで「Services」→「Service Marketplace」に進む
2. 必要なサービスを見つけて「Create」をクリックする
3. プランを選択する。ここで機能とコストが決まります
4. 必要な設定を行い、外部に保存しておく（トラブルシュート時に必要になります）

サービスを作成したら、「Service Bindings」でアプリケーションにバインドします。接続と認証情報はBTPが処理します。

**Service keys**は、BTPユーザーではない外部ツールやチームがサービスにアクセスするための認証情報です。名前は分かりやすく付けてください。`dev-team-access`や`jenkins-deployment`のようにし、`key1`のような名前は避けます。

Service Marketplaceでは、必要なものが分かっているなら検索バーを使い、繰り返し使うものには「Recently Used」を使ってください。調査目的なら環境（Cloud Foundry、Kyma）で絞り込み、テスト中のものはfree planから始めるのが無難です。

### アプリケーションのデプロイ

BTP Cockpitは3つのランタイム環境をサポートしています。選ぶ基準は、チームのスキルとアプリケーション要件です。

| Runtime | 最適な用途 | 補足 |
|---|---|---|
| Cloud Foundry | Java、Node.js、Pythonアプリケーション、従来型のWebアプリ | 最も成熟した環境。サービスカタログも大きいです |
| Kyma | Kubernetesネイティブなワークロード、複雑なスケーリングが必要なマイクロサービス | 柔軟性は高いですが、Kubernetesの知識が必要です |
| ABAP Cloud | ABAPベースの拡張、clean core開発 | SAP開発者にはなじみやすく、S/4HANAと直接統合できます |

アーキテクチャ計画には合っていても、開発者のスキルに合っていない環境を押し付けたせいで、プロジェクトが何か月も遅れた例を私は見てきました。ランタイムはチームに合わせてください。

Cloud Foundryへのデプロイ手順です。
1. メモリ、インスタンス数、build pack、環境変数を指定したmanifest.ymlファイルを作成する
2. CF CLIでpushするか、BTP Cockpit経由で自動化する
3. BTPがbuild packを自動検出する
4. 環境変数が注入され、サービスがバインドされ、ルートが設定される

繰り返し発生するデプロイは、できるだけ早い段階でBTP CLIやAPIで自動化してください。手動デプロイのプロセスは、規模が大きくなると時間の無駄です。ある案件では、自動化によってセットアップ時間を80%削減できました。投資はすぐ回収できます。

### 統合と拡張のシナリオ

| Scenario | 実現できること | 設定方法 |
|---|---|---|
| S/4HANA integration | S/4HANAとBTPアプリケーション間でデータを共有する | Cloud Connectorを設定 → Destination Serviceを設定 → S/4HANA OData APIにアクセス |
| SuccessFactors extension | SuccessFactorsデータを使ったカスタムHRワークフローを構築する | SAP Event Mesh + API Managementを有効化 → CAPまたはNode.jsで拡張 |
| Third-party integration | Salesforce、Workday、その他の非-SAPシステムを接続する | Open Connectorsの事前構築済みコネクタを使うか、Integration Suiteでカスタム構築 |
| On-premise connectivity | BTPから社内システムへ安全にアクセスする | ネットワーク上にCloud Connectorをインストール → Cockpitの「Connectivity」で設定 |
| API exposure | BTPサービスやS/4HANA機能をAPIとして公開する | API Managementを使用 → API製品を設計・公開 → 利用状況を監視 |

Cloud Connectorは、オンプレミスネットワークとBTPをつなぐ橋です。インバウンドのファイアウォールルールを要求せずに、安全なトンネルを作ります。公開するのは本当に必要なシステムとパスだけにしてください。最小権限の原則はここでも有効です。

### 監視と分析

監視は、何か壊れてからではなく、その前に設定してください。サブアカウントで「Monitoring」に進み、重要なサービスに対するアラートを設定します。私の標準設定はこうです。重要アプリケーションにはメールアラート、停止できないサービスにはwebhook通知です。

見るべきポイントは次のとおりです。
1. **アプリケーション健全性**: アプリケーションごとの応答時間とエラー率
2. **サービス状態**: 主要サービスの可用性とクォータ消費量
3. **利用分析**: サービス、サブアカウント、期間ごとのリソース消費量。無駄がコスト問題になる前に見つけるのに役立ちます

未使用サービスは毎月削除してください。開発環境は営業時間外にスケールダウンします。契約更新前にはエンタイトルメント消費量を確認してください。使っていない割り当ては、超過支出のよくある原因です。

Cockpitが見せるのは現在の状態です。ダッシュボードを設定しない限り、トレンドは見えません。コストの高いサービスについては、初日から利用ダッシュボードを設定してください。

## 高度な機能

**カスタムドメイン**はユーザー定着を改善します。各サブアカウントで「Security」→「Custom Domain」から設定します。技術的なSAP URLしか見えない場合と比べて、プロフェッショナルな見た目はエンドユーザーに本当に効きます。

**BTP CLIとAPIによる自動化**は、繰り返し作業から手動ステップを取り除きます。よくある自動化は、環境プロビジョニング、デプロイパイプライン、新しいサブアカウントへのエンタイトルメント配分です。CLIはAPI経由でCockpitに接続し、UIでできることをすべてスクリプト化できます。

**Extension Factory**（Kyma環境内）は、イベント駆動型マイクロサービスでSAPシステムを拡張するためのランタイムを提供します。コアシステムを変更せずにSAPイベントへ反応する機能が必要な場合に有効です。

**ABAP Cloud**環境をBTP上で使うと、ABAPベースの拡張を実行するためのマネージド環境を提供しつつ、S/4HANAのコアをクリーンに保てます。ここで構築する拡張はclean core原則に従います。つまり、直接テーブルアクセスではなく、安定したAPIを通じてS/4HANAと連携します。

## 避けるべきこと

1. 命名規則を決める前にサブアカウントを作り始めること
2. ロールコレクションではなく個人にロールを割り当てること。管理負荷は時間とともに膨らみます
3. 「Security Alerts」セクションを無視すること
4. 開発用サービスを本番構成のまま動かし続けること
5. アカウント構造とその理由を文書化しないこと。Cockpitが保存するのは何をしたかであって、なぜそうしたかではありません

<details>
<summary>SAP BTPでサブアカウントはどう構成すべきですか。</summary>

最初から開発、テスト、本番を別々のサブアカウントに分けてください。名前も一貫させます（たとえば「Finance-Dev」「Finance-Test」「Finance-Prod」）。名前だけで環境と用途が分かるようにするためです。

大きな組織では、部門や事業部単位で分けることも検討してください。初期に作った構造は、後から変更しようとすると、稼働中サービスに影響を出さずに変えるのが難しいです。何か作る前に、まず紙の上で構造を整理してください。計画なしで始めたために、後で何週間も再編成に費やしたチームを私は見てきました。50以上のサブアカウントに無秩序な名前が付いていて、誰もサービスをすぐ見つけられない顧客もいました。

</details>

<details>
<summary>SAP BTPの4つの柱とは何ですか。</summary>

Database and Data Management。HANA Cloud、Datasphere、そして保存・処理・分析のためのデータパイプラインツールです。Application Development。Cloud Foundry、Kyma、ABAP Cloud、Business Application Studioで、拡張やアプリケーションを構築します。Integration。SAP Cloud Integration、API Management、Event Mesh、Open Connectorsで、システムとプロセスを接続します。Intelligent Technologies。AI、機械学習、分析機能で、SAP JouleやAI Coreも含みます。

この4つの柱が、Cockpitを通じて何を構築し、何を接続できるかを定義します。多くのBTPプロジェクトでは、まず統合とアプリケーション開発から着手し、その後ランドスケープの成熟に合わせてデータとインテリジェンスへ広げていきます。

</details>

<details>
<summary>SAP BTPでユーザー管理とロールコレクションはどう機能しますか。</summary>

ユーザーはサブアカウントごとに「Security」→「Users」で管理します。エンタープライズ構成では、BTP内で手動管理するのではなく、SAML信頼設定を使って社内のIDプロバイダー（Azure AD、Oktaなど）を接続してください。これでユーザーライフサイクル管理が一元化され、管理負荷の一部を取り除けます。

ロールコレクションは、ユーザーに割り当てる権限の束です。個人ではなく職務機能ベースで作成してください。よくある例は「Developer-Subaccount-Admin」「Business-User-Read-Only」「Integration-Administrator」です。割り当ては四半期ごとに見直します。人は役割を変えますが、権限は残りがちです。緊急時対応のために、フルアクセスを持つ「admin」ロールコレクションを維持しておく価値はあります。

</details>

<details>
<summary>BTPではどのランタイム環境を選ぶべきですか。Cloud Foundry、Kyma、それともABAP Cloudですか。</summary>

アーキテクチャ図だけでなく、チームがすでに持っているスキルに合わせて環境を選んでください。Cloud Foundryは最も成熟していて、サービスカタログも最大です。Java、Node.js、Pythonアプリケーションに向いています。KymaはKubernetesネイティブで柔軟ですが、多くのSAP中心のチームが持っていないKubernetes知識を必要とします。ABAP CloudはABAPベースの拡張向けで、SAP開発の背景を持つチームには自然な選択です。

開発者が実際に何を分かっているかを確認せず、アーキテクチャ原則だけでランタイムを選んだせいで、プロジェクトが何か月も遅れた例を私は見てきました。技術的には優れていても、チームがうまく実装できない選択は、実行できる現実的な選択より悪いです。

</details>

<details>
<summary>SAP BTPをオンプレミスのSAPシステムに接続するにはどうすればよいですか。</summary>

オンプレミスネットワーク上にCloud Connectorをインストールしてください。これにより、インバウンドのファイアウォール変更なしで、BTPへの安全なアウトバウンドトンネルを作れます。公開するのは、BTPが必要とする特定のシステムとURLパスだけにしてください。最小権限の原則です。

BTP Cockpitでは、サブアカウントの「Connectivity」セクションに進み、Cloud Connector接続を確認して状態をチェックします。その後、公開したSAPシステムを指すDestinationsを作成します。BTPアプリケーションや統合フローは、オンプレミスシステムを呼び出す必要があるときにこれらのDestinationsを参照します。本番へ移す前に、BTPからオンプレミスシステムまでの経路全体をテストしてください。

SAP BTP Cockpit 是管理 SAP Business Technology Platform 的網頁主控台：全域帳戶、子帳戶、權利、服務、使用者、執行環境與成本都在這裡管理。您以 SAP 使用者登入 `https://cockpit.btp.cloud.sap`，系統會把您導向最近的區域 Cockpit。

簡短回答：開啟 `cockpit.btp.cloud.sap`，選擇您的全域帳戶，然後依以下順序操作。規劃目錄與子帳戶、指派權利、啟用執行環境、建立服務執行個體、連接身分提供者並指派角色集合，最後開啟警示與成本追蹤。試用帳戶使用 `https://cockpit.hanatrial.ondemand.com/trial/`，最長可用 90 天。

我第一次摸索這些時花了好幾天。大部分麻煩來自先做了後面的步驟，再回頭做前面的。下面的順序，是我現在每個新全域帳戶都會用的。

關於名稱先說明一下。在 2026 年 5 月的 Sapphire 大會上，SAP 發表了 SAP Business AI Platform，它把 BTP、SAP Business Data Cloud 與 AI Foundation 整合在一起（[SAP News](https://news.sap.com/2026/05/sap-sapphire-keynote-business-ai-platform-power-autonomous-enterprise/)）。截至 2026 年 10 月，管理主控台在文件中仍稱為 SAP BTP Cockpit，所以本文沿用這個名稱。

## 如何登入 SAP BTP Cockpit

SAP 文件提供的入口只有一個：`https://cockpit.btp.cloud.sap`。它會把您導向最近的區域 Cockpit（[SAP Help, Access the Cockpit](https://help.sap.com/docs/btp/sap-business-technology-platform/4e750660b72e4fd6b2485ffb0b3cbdca)）。您也可以直接開啟區域閘道：

1. 歐洲、中東與非洲：`https://emea.cockpit.btp.cloud.sap`。
2. 美洲：`https://amer.cockpit.btp.cloud.sap`。
3. 亞太：`https://apac.cockpit.btp.cloud.sap`。
4. EU Access 帳戶：`https://eu-access.cockpit.btp.cloud.sap`。

閘道只決定您從哪條路徑進入 Cockpit，並不會限制您只能使用該區域的子帳戶。中國的使用者有專屬入口：`https://cockpit.cn40.platform.sapcloud.cn`。

如果您的公司透過自己的身分提供者讓平台使用者登入，請加上 `idp` 參數，例如 `https://cockpit.btp.cloud.sap?idp=mytenant.accounts.ondemand.com`。少了它，您會進到預設的 SAP ID service，可能一個帳戶也看不到。使用舊功能集 A 或 Neo 環境的帳戶使用另一個網址，SAP 文件中有列出。

## 全域帳戶與子帳戶：Cockpit 的組織方式

一切都在一個階層結構中。**全域帳戶**是您與 SAP 所簽合約的具體實現。它持有您購買的權利與配額，且與區域及環境無關。

**子帳戶**是實際工作的地方。每個子帳戶屬於一個區域，您在其中部署應用程式、使用服務、管理成員與授權。子帳戶彼此獨立，這對資安與資料隔離很重要。

**目錄**是位於兩者之間的選用資料夾。它們可以把子帳戶分組，例如依事業單位，也可以有自己的權利與授權。SAP 允許在全域帳戶與最底層子帳戶之間最多設置五層目錄（[SAP Help, Account Model](https://help.sap.com/docs/btp/sap-business-technology-platform/8ed4a705efa0431b910056c0acdbf377)）。

<explainer-org title="BTP 全域帳戶的組織方式" caption="每個子帳戶都從同一個有限的池中分配資源。在建立第一個子帳戶之前，先講好命名與分配方式。" chain="全域帳戶 => 您與 SAP 的合約以及購買的服務|目錄 => 將子帳戶分組，例如依事業單位" side="權利 => 每個子帳戶從中分配的有限資源池" roles="Finance-Dev => 開發，使用免費或小型方案|Finance-Test => 測試，有自己的使用者與角色集合|Finance-Prod => 正式環境，上線前就設好警示" highlight="side"></explainer-org>

子帳戶之下，每個執行環境有自己的層級。啟用 Cloud Foundry 會為每個子帳戶建立一個 org，您在其中建立 space。啟用 Kyma 會佈建一個或多個 Kubernetes 叢集，您再把它們劃分為 namespace。

## 如何設定 SAP BTP Cockpit：逐步說明

### 步驟 1：登入並開啟正確的全域帳戶

依上述方式登入，並選擇您的全域帳戶。Cockpit 一次只顯示一個全域帳戶。如果您不是任何全域帳戶的成員，Cockpit 會告訴您；請參閱下方的錯誤章節。

點選 Cockpit 工具列中的菱形圖示即可使用 Joule。它可以回答 BTP 相關問題並執行管理工作，但僅限您自己的授權所允許的範圍。

### 步驟 2：先在紙上規劃目錄與子帳戶命名

多數團隊就是在這一步製造出跟著他們好幾年的混亂。我曾合作過的一位客戶有 50 多個隨意命名的子帳戶，誰也找不到任何東西。在專案進行中途理清這些非常痛苦。

依領域把開發、測試與正式環境分開，例如 `Finance-Dev`、`Finance-Test`、`Finance-Prod`。較大的組織會依事業單位再加一層目錄。使用 `Landscape: Dev` 或成本中心之類的標籤，因為 Account Explorer 可以依標籤篩選。

### 步驟 3：建立子帳戶

您必須是全域帳戶管理員，或是自行管理權利之目錄的目錄管理員。接著依照 [SAP Help, Create a Subaccount](https://help.sap.com/docs/btp/sap-business-technology-platform/05280a123d3044ae97457a25b3013918) 操作：

1. 在全域帳戶中開啟 **Account Explorer**。
2. 選擇 **Create > Subaccount**。
3. 輸入顯示名稱，並可選填說明。
4. 輸入 **Subdomain**。它會成為已訂閱應用程式網址的一部分，且在該區域內必須唯一。
5. 選擇區域與上層（全域帳戶或某個目錄）。
6. 若用於正式環境，勾選 **Used for production**，並在 **Advanced** 下加入標籤。
7. 任何正式使用的子帳戶都不要開啟 **Enable beta features**。一旦開啟，就無法關閉。
8. 儲存，然後啟用環境並新增使用者。

### 步驟 4：指派權利

**權利**決定子帳戶能使用哪些服務與方案，以及能取得多少配額。全域帳戶有一個有限的池，由您分配給目錄與子帳戶。

在子帳戶中開啟 **Entitlements**，選擇 **Configure Entitlements > Add Service Plans**，選好服務、方案與配額，然後 **Save**。我從最少開始，依需要再擴大，這種做法為我的客戶在閒置服務上省下了數以千計的費用。

### 步驟 5：啟用執行環境：Cloud Foundry、Kyma 或 ABAP 環境

您可以在子帳戶概觀中點選 **Enable**、透過 Service Marketplace，或用 btp CLI 啟用環境。一個子帳戶可以執行多個環境。下表依據 SAP 的環境文件比較三者。

| 環境 | 是什麼 | 適合 | 注意事項 |
|---|---|---|---|
| Cloud Foundry | SAP BTP, Cloud Foundry runtime，以開源 Cloud Foundry 為基礎；由 buildpack 建置並執行您的應用程式 | Java、Node.js 與 Python 應用程式，包括 SAP Cloud Application Programming Model（CAP） | 對多數 SAP 團隊來說是成熟的預設選擇 |
| Kyma | SAP BTP, Kyma runtime：以開源 Kyma 專案為基礎的全代管 Kubernetes 執行環境 | 容器化微服務、無伺服器函式與事件驅動的擴充 | 需要 Kubernetes 技能；Kyma 免費方案每個全域帳戶只能用一次，最長 30 天 |
| ABAP 環境 | 現名為 SAP Business AI Platform, ABAP environment；以已發布物件為基礎的 ABAP Cloud | 在 S/4HANA 旁建置擴充的 ABAP 開發人員 | 是獨立系統，搭配專用的 SAP HANA Cloud 資料庫，規模與計費都另外處理 |

我看過一些專案延誤好幾個月，原因是開發人員必須學習一個符合架構規劃、卻不符合他們經驗的新環境。技術上較好、但您的團隊無法在上面開發的執行環境，才是比較差的選擇。

### 步驟 6：建立服務執行個體、繫結與金鑰

在子帳戶中開啟 **Services > Service Marketplace**，選擇服務磚，然後選擇 **Create**。請仔細挑選方案，因為 SAP 自己的教學提醒，選錯方案會產生額外成本（[SAP Developers](https://developers.sap.com/tutorials/btp-cockpit-instances.html)）。您建立的所有項目都會出現在 **Services > Instances and Subscriptions** 下。

把執行個體繫結到您的應用程式，BTP 就會注入憑證。對於不是 BTP 應用程式的工具，請建立 **service key**。依使用者為金鑰命名，例如 `jenkins-deployment`，而不是 `key1`。

### 步驟 7：連接身分提供者並指派角色集合

如果您的公司已經有 Microsoft Entra ID 或 Okta 這類身分提供者，就不要手動管理 BTP 使用者。用一個 SAP Cloud Identity Services 租用戶作為它的代理。在子帳戶中進入 **Security > Trust Configuration**，選擇 **Establish Trust**，系統會自動建立 OpenID Connect 信任。

之後在 **Security > Users > Assign Role Collection** 下為使用者指派角色集合，或透過群組指派。我對角色集合的做法是：

1. 圍繞職務來建立，而不是圍繞個人。
2. 具體到有意義，但不要細到得維護好幾百個。
3. 保留一個緊急狀況用的破窗管理員集合。
4. 每季檢視一次指派。人換了職務，往往還保留著舊的存取權限。

### 步驟 8：將 BTP 連接到 S/4HANA 與其他系統

BTP 的大部分工作是整合。以下是我最常設定的模式。

| 情境 | 如何設定 |
|---|---|
| 地端或 Private Edition 的 S/4HANA | 在您的網路中部署 Cloud Connector，在子帳戶中設定 destination，再使用 OData 或 SOAP API |
| SuccessFactors 等 SAP 雲端應用程式 | destination 加上 Integration Suite 或 Event Mesh，擴充以 CAP 開發 |
| Salesforce 或 Workday 等非 SAP 系統 | Integration Suite 轉接器，或自訂整合流程 |
| 對外提供您自己的 API | Integration Suite 中的 API Management：設計、發布、監控 |

Cloud Connector 開啟的是通往 BTP 的輸出通道，所以您不需要輸入方向的防火牆規則。只開放 BTP 真正需要的系統與網址路徑。我的 [SAP CPI 文章](/zh-TW/sap-cpi/)對整合設計有更深入的說明。

### 步驟 9：設定監控與警示

在需要之前就把監控設定好。我每天早上邊喝咖啡邊看儀表板。這已經成了一種習慣，也讓我避開了不少「系統怎麼掛了？」的時刻。

SAP Alert Notification service 會把平台與應用程式事件傳送到電子郵件、Slack 及其他管道。我通常的設定是：關鍵應用程式用電子郵件，絕不能停的用 Slack webhook。在 Cloud Foundry 或 Kyma 檢視中查看每個應用程式的回應時間與錯誤率。

### 步驟 10：追蹤用量與成本

有兩個頁面很重要。每個子帳戶中的 **Usage Analytics** 顯示實際用量（不是計費用量），每 24 小時更新一次。全域帳戶中的 **Costs and Usage** 依服務、目錄與子帳戶顯示每月成本，使用的是與您帳單相同的口徑。

在依用量計費的合約下，您也可以設定 **budgets**，在達到門檻時寄送電子郵件警示。超出預算並不會停止使用；停下來仍然是您的責任。每月刪除閒置的執行個體，每次續約前檢查權利的使用情況。

## 自動化與自訂網域

在 Cockpit 裡逐項點選無法規模化。BTP 命令列介面（btp CLI）與 SAP Cloud Management service API 可以把帳戶工作腳本化：建立子帳戶、指派權利、啟用環境。

在一個專案中，我需要為 12 位新開發人員準備環境。我沒有花一整天在 Cockpit 裡點選，而是執行了我的腳本，然後去喝咖啡。回來時，一切都已準備就緒。

在一個專案中，部署自動化讓設定時間縮短了 80%。把 service key 和 CF CLI 接進管線後，部署從幾小時縮短為幾分鐘。自訂網域透過 SAP Custom Domain service 設定；在一個客戶專案中，高階主管立刻注意到更專業的觀感。

## SAP BTP Cockpit 試用版與免費層

SAP 提供兩種免費入門方式，很容易混淆。試用版用於學習；免費層方案則在真正的企業帳戶之內。下表整理自 [SAP Help, Trial Accounts and Free Tier](https://help.sap.com/docs/btp/sap-business-technology-platform/046f127f2a614438b616ccfc575fdb16)。

| | 試用帳戶 | 免費層服務方案 |
|---|---|---|
| Cockpit 網址 | `cockpit.hanatrial.ondemand.com/trial/` | `cockpit.btp.cloud.sap` |
| 帳戶類型 | 獨立的試用全域帳戶 | Pay-As-You-Go 或 CPEA 企業帳戶 |
| 期限 | 最長 90 天，之後刪除 | 免費方案沒有期限；Kyma 免費方案最長 30 天 |
| 正式使用 | 不允許，也不允許團隊開發 | 允許；多數服務可升級為付費方案 |
| 您會得到什麼 | 一個含 `dev` space 的 Cloud Foundry 子帳戶；也可使用 Kyma 與 ABAP | SAP Discovery Center 中標示為 Free Tier 的服務 |

試用版以最長 30 天為一個週期，只要您持續登入就會自動延長。如果 30 天沒有登入，帳戶會被停用，之後刪除。試用版應用程式每晚都會停止，需要手動重新啟動。

## BTP Cockpit 常見錯誤與解決方法

以下每一項都有文件記載的原因與簡單的解決方式。

1. **「Your user does not belong to any global account.」** 需要由全域帳戶管理員把您加入為成員，並指派 Global Account Viewer 之類的角色集合。如果找不到管理員，SAP Note 2669325 說明了透過 SAP for Me 的替代做法。
2. **用企業身分登入後看不到全域帳戶。** BTP 會把兩個身分提供者中的同一個電子郵件視為兩個使用者。請用 `?idp=` 參數，指定管理員所用的身分提供者登入。
3. **Service Marketplace 中缺少某項服務。** 該子帳戶沒有對應的權利。請先在 Entitlements 下新增該方案。
4. **「Subdomain already exists.」** 子網域在每個區域內唯一。請在名稱中加上事業單位或階段。
5. **非預期的費用。** 某個執行個體是以付費方案建立的。請在 Instances and Subscriptions 以及 Costs and Usage 中檢查方案。
6. **試用版應用程式夜間停止。** 這是正常的。重新啟動它，並持續登入，以免試用帳戶被停用。

關於執行環境與部署錯誤，我的 [BTP Cockpit 問題指南](/zh-TW/sap-btp-cockpit-issues/)有更深入的說明。

## Cockpit 在 S/4HANA 專案中的定位

我主導或救回過 21 個 SAP 專案。在 Clean Core 專案中，BTP 是並行擴充（side-by-side）執行的地方，讓 S/4HANA 能維持接近 SAP 標準。我的 [Clean Core 指南](/zh-TW/sap-clean-core-strategy-what-it-means-for-your-business/)說明這些擴充放在哪裡。

Cockpit 記錄的是「做了什麼」，從不記錄「為什麼」。把帳戶結構、命名規則、權利分配以及各自的理由寫下來。對它們的任何變更，都要經由業務與 IT 組成的設計委員會（design authority）核准。

如果您的 BTP 帳戶在沒有規劃的情況下不斷膨脹，請在繼續增加之前[和我談談](/zh-TW/contact-noel-erp-support/)。

## 常見問題

<details>
<summary>SAP BTP Cockpit 的登入網址是什麼？</summary>

使用 `https://cockpit.btp.cloud.sap`，它會把您導向最近的區域 Cockpit。您也可以使用區域閘道，例如 `https://emea.cockpit.btp.cloud.sap`、`https://amer.cockpit.btp.cloud.sap` 或 `https://apac.cockpit.btp.cloud.sap`。試用帳戶使用 `https://cockpit.hanatrial.ondemand.com/trial/`。

</details>

<details>
<summary>SAP BTP 的全域帳戶與子帳戶有什麼差別？</summary>

全域帳戶是您與 SAP 的合約。它持有您購買的權利，不綁定任何區域。子帳戶位於其中，每個屬於一個區域，是您部署應用程式、使用服務與管理使用者的地方。

</details>

<details>
<summary>如何在 SAP BTP 中建立子帳戶？</summary>

以全域帳戶管理員身分開啟 Account Explorer，選擇 Create > Subaccount。輸入顯示名稱、在該區域內唯一的子網域、區域與上層。儲存後，指派權利並啟用一個環境，例如 Cloud Foundry。

</details>

<details>
<summary>SAP BTP 中的權利（Entitlements）是什麼？</summary>

權利是您使用某個服務方案的權利，配額則是您能用多少。全域帳戶依合約取得這些權利，再由您分配給目錄與子帳戶。在子帳戶中，選擇 Entitlements > Configure Entitlements > Add Service Plans。

</details>

<details>
<summary>SAP BTP 試用版免費嗎？可以用多久？</summary>

免費，最長 90 天。只要您持續登入，週期會自動延長；30 天未登入，帳戶就會被停用。它用於個人學習，不能用於正式環境或團隊開發；若要長期使用，請建立一個含免費層服務方案的企業帳戶。

</details>

<details>
<summary>Cloud Foundry 與 Kyma：該選哪個 BTP 執行環境？</summary>

Java、Node.js 或 Python 應用程式（包括 CAP）選 Cloud Foundry；buildpack 會替您處理容器。容器化微服務與事件驅動的擴充選 Kyma 這個代管 Kubernetes 執行環境，但前提是您的團隊具備 Kubernetes 技能。建置 S/4HANA 擴充的 ABAP 開發人員通常適合 ABAP 環境。

</details>

<details>
<summary>SAP BTP 現在改名為 SAP Business AI Platform 了嗎？</summary>

2026 年 5 月，SAP 發表了 SAP Business AI Platform，它把 BTP、SAP Business Data Cloud 與 AI Foundation 整合在一起。SAP 文件已在部分內容使用新名稱，例如 ABAP 環境。截至 2026 年 10 月，管理主控台在文件中仍稱為 SAP BTP Cockpit，網址也相同。

</details>

<details>
<summary>如何將我的身分提供者連接到 SAP BTP Cockpit？</summary>

設定一個 SAP Cloud Identity Services 租用戶，並把您的企業身分提供者（例如 Microsoft Entra ID 或 Okta）連接到它。在子帳戶中進入 Security > Trust Configuration，選擇 Establish Trust 建立 OpenID Connect 信任。然後為使用者或群組指派角色集合。

</details>

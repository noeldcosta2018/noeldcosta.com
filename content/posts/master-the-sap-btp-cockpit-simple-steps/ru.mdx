Cockpit SAP Business Technology Platform — это центральный административный интерфейс для управления вашей облачной средой SAP. Приложения, сервисы, настройки безопасности, подписки — всё проходит через него.

Cockpit используют три основные группы. Технические администраторы занимаются настройкой и мониторингом. Разработчики разворачивают приложения и управляют ими. Бизнес-пользователи работают с конкретными инструментами; у каждой роли свои разделы. Большинство компаний покупают облачные продукты SAP и не получают от них полной отдачи, потому что никто не потратил время на то, чтобы нормально разобраться с Cockpit. Задачи, которые должны занимать минуты, растягиваются на часы. Расходы копятся из-за неиспользуемых сервисов. Появляются пробелы в безопасности в entitlement'ах, которые никто не проверял.

Открыть Cockpit можно по адресу `https://account.hana.ondemand.com`. Для trial-аккаунтов: `https://account.hanatrial.ondemand.com`. Вам нужен идентификатор пользователя SAP: если его у вас нет, обратитесь к своему администратору.

## Какие задачи решает SAP BTP

закрывает три категории проблем, которые возникают в любом облачном проекте SAP.

**Интеграция.** SAP Cloud Integration (ранее CPI) соединяет S/4HANA, SuccessFactors, Ariba и не-SAP-системы, такие как Salesforce, с помощью визуальных integration flow. API Management открывает бизнес-функции для других приложений. Event Mesh обеспечивает межсистемное взаимодействие на основе бизнес-событий. Open Connectors даёт готовые интеграции для сотен сторонних систем.

**Кастомная разработка без вмешательства в core.** ABAP Cloud Environment позволяет разработчикам создавать расширения без модификации базового кода SAP (а значит, не ломать путь обновлений). Runtime Cloud Foundry поддерживает Java, Node.js и Python. Business Application Studio даёт разработчикам браузерную IDE. SAP Build даёт бизнес-пользователям low-code инструменты для простых приложений.

**Управление данными.** HANA Cloud предоставляет возможности in-memory базы данных. Datasphere (ранее Data Warehouse Cloud) объединяет данные из нескольких источников для бизнес-отчётности. Data Intelligence Cloud создаёт пайплайны для перемещения и преобразования данных между системами.

## Настройка BTP для ежедневной работы

Следующие шесть разделов охватывают компоненты администрирования BTP, которые вы будете использовать чаще всего: структура аккаунта, идентификация, сервисы, развёртывание, интеграция и мониторинг. В каждом из них есть решение по настройке, которое вы принимаете один раз и потом живёте с ним весь срок жизни платформы.

### Subaccount'ы и entitlements

Именно здесь большинство команд устраивают беспорядок, который потом преследует их годами.

Создайте отдельные subaccount'ы для разработки, тестирования и продуктивной среды. В вашем global account нажмите "Create Subaccount" и используйте единое соглашение по именованию: например, "Finance-Dev", "Finance-Test", "Finance-Prod". Я работал с клиентом, у которого было 50+ subaccount'ов со случайными именами, и никто ничего не мог найти. Перестраивать такую структуру посреди проекта — мучение.

Для multi-environment setup: зеркально повторяйте структуру subaccount'ов по регионам, если у вас глобальный бизнес. Держите entitlements для разработки минимальными. Для продуктивных сред отдавайте приоритет ресурсам, чувствительным к производительности, и используйте labels для группировки связанных subaccount'ов.

**Entitlements** определяют, к каким сервисам может обращаться каждый subaccount и в каком объёме. В global account перейдите в "Entitlements" → "Configure Entitlements", выберите subaccount и добавьте сервисы. У вашего global account есть конечный пул ресурсов для распределения: начинайте с минимума и добавляйте по мере необходимости. У многих сервисов есть free tier, что удобно для тестирования.

Всегда документируйте распределение entitlements где-то вне Cockpit. Платформа не отслеживает ваши решения и не хранит логику, почему вы их приняли.

### Управление пользователями и аутентификация

Перейдите в "Security" → "Users" в вашем subaccount. Пользователей можно добавлять по одному или загружать CSV для массового добавления.

Если в вашей организации есть провайдер удостоверений (Azure AD, Okta или аналогичный), подключите его вместо ручного управления пользователями. Перейдите в "Security" → "Trust Configuration" и обменяйтесь metadata-файлами между SAP и вашим IdP. Это убирает большую часть проблем с аутентификацией и централизует управление жизненным циклом пользователей.

Для корпоративных setup'ов наибольшую гибкость дают кастомные SAML identity provider. Стандартный SAP ID Service подходит для тестирования и небольших развёртываний.

Role collections — это наборы прав, назначаемые пользователям. Мой подход:
1. Создавайте role collections по рабочим функциям, а не под конкретных людей
2. Делайте их достаточно конкретными, чтобы в них был смысл, но не настолько дробными, чтобы вам пришлось поддерживать сотни
3. Держите аварийную role collection "admin" для экстренных случаев
4. Пересматривайте назначения ролей ежеквартально: люди меняют должности, но старые права у них часто остаются

Включите двухфакторную аутентификацию, по возможности ограничьте доступ доверенными сетями и регулярно проверяйте раздел "Security Alerts". SAP использует его, чтобы сигнализировать о потенциальных проблемах в вашей среде.

### Экземпляры сервисов и приложения

Создание экземпляра сервиса:
1. Перейдите в "Services" → "Service Marketplace" в вашем subaccount
2. Найдите нужный сервис и нажмите "Create"
3. Выберите план: он определяет функциональность и стоимость
4. Настройте необходимые параметры и сохраните их во внешнем месте (они понадобятся при разборе проблем)

После создания сервиса привяжите его к приложению в разделе "Service Bindings". BTP сам обработает подключение и учётные данные.

**Service keys** — это учётные данные для внешних инструментов или команд, которым нужен доступ к сервису без статуса пользователей BTP. Называйте их понятно: `dev-team-access` или `jenkins-deployment`, а не `key1`.

В Service Marketplace: используйте строку поиска, когда точно знаете, что вам нужно, и "Recently Used" для повторного доступа. Фильтруйте по среде (Cloud Foundry, Kyma), когда изучаете варианты, и начинайте с бесплатных планов для всего, что тестируете.

### Развёртывание приложений

Cockpit BTP поддерживает три runtime-среды. Выбирайте исходя из навыков команды и требований приложения.

| Runtime | Лучше всего подходит для | Примечания |
|---|---|---|
| Cloud Foundry | Приложения на Java, Node.js, Python; традиционные веб-приложения | Самая зрелая среда; большой каталог сервисов |
| Kyma | Kubernetes-native нагрузки; микросервисы со сложным масштабированием | Более гибкая, но требует знания Kubernetes |
| ABAP Cloud | Расширения на ABAP; разработка по принципу clean core | Привычна для разработчиков SAP; напрямую интегрируется с S/4HANA |

Я видел проекты, которые задерживались на месяцы, потому что разработчиков загоняли в среду, подходившую архитектурному плану, но не их навыкам. Подбирайте runtime под команду.

Развёртывание в Cloud Foundry:
1. Создайте файл manifest.yml, указав память, instances, buildpacks и переменные среды
2. Выполните push через CF CLI или автоматизируйте это через Cockpit BTP
3. BTP автоматически определит buildpack
4. Переменные среды будут подставлены, сервисы привязаны, маршруты настроены

Автоматизируйте повторяющиеся развёртывания через CLI и API BTP как можно раньше. Ручные процессы развёртывания на масштабе — это чёрная дыра для времени. На одном проекте автоматизация сократила время настройки на 80%: вложения окупаются быстро.

### Сценарии интеграции и расширения

| Сценарий | Что это даёт | Как настроить |
|---|---|---|
| Интеграция с S/4HANA | Обмен данными между S/4HANA и приложениями BTP | Настройте Cloud Connector → настройте Destination Service → получите доступ к OData API S/4HANA |
| Расширение SuccessFactors | Создание кастомных HR-процессов на данных SuccessFactors | Включите SAP Event Mesh + API Management → расширяйте через CAP или Node.js |
| Интеграция со сторонними системами | Подключение Salesforce, Workday или любой не-SAP-системы | Используйте готовые коннекторы Open Connectors или создайте кастомную интеграцию через Integration Suite |
| Подключение on-premise | Безопасный доступ из BTP к внутренним системам | Установите Cloud Connector в своей сети → настройте его в Cockpit в разделе "Connectivity" |
| Публикация API | Публикация сервисов BTP или функций S/4HANA как API | Используйте API Management → спроектируйте и опубликуйте API products → отслеживайте потребление |

Cloud Connector — это мост между вашей on-premise сетью и BTP. Он создаёт защищённый туннель без необходимости открывать входящие правила на firewall. Настраивайте его так, чтобы он открывал только те системы и пути, которые вам действительно нужны: принцип минимального доступа действует и здесь.

### Мониторинг и аналитика

Настройте мониторинг до того, как он вам понадобится, а не после того, как что-то сломается. В вашем subaccount перейдите в "Monitoring" и настройте оповещения для важных сервисов. Моя стандартная схема: email-оповещения для критичных приложений, webhook-уведомления для сервисов, которые не могут простаивать.

Что отслеживать:
1. **Состояние приложений**: время отклика и уровень ошибок по каждому приложению
2. **Статус сервисов**: доступность и потребление квот по ключевым сервисам
3. **Аналитика использования**: потребление ресурсов по сервису, subaccount'у и периоду времени — полезно, чтобы поймать потери до того, как они превратятся в проблему затрат

Удаляйте неиспользуемые сервисы ежемесячно. Уменьшайте масштаб сред разработки вне рабочих часов. Проверяйте потребление entitlements перед продлением контрактов: неиспользуемые аллокации — частый источник перерасхода.

Cockpit показывает текущее состояние. Тренды он вам не покажет, если вы не настроите dashboards. Настройте usage dashboards для самых дорогих сервисов с первого дня.

## Расширенные возможности

**Custom domains** улучшают принятие системы пользователями. Настраивайте их в "Security" → "Custom Domain" для каждого subaccount. Более профессиональный вид действительно влияет на конечных пользователей, которые иначе видели бы технические URL SAP.

**Автоматизация через CLI и API BTP** убирает ручные шаги из повторяющихся процессов. Типовые сценарии автоматизации: provisioning сред, deployment pipelines, распределение entitlements по новым subaccount'ам. CLI подключается к Cockpit через API и позволяет скриптовать всё, что делает UI.

**Extension Factory** (в среде Kyma) предоставляет runtime для расширения систем SAP с помощью event-driven микросервисов. Полезно для возможностей, которые должны реагировать на события SAP без модификации core-систем.

**Среды ABAP Cloud** в BTP дают управляемую систему для запуска расширений на ABAP при сохранении чистого core S/4HANA. Расширения, созданные здесь, следуют принципу clean core: они взаимодействуют с S/4HANA через стабильные API, а не через прямой доступ к таблицам.

## Чего избегать

1. Создания subaccount'ов без соглашения по именованию ещё до того, как вы вообще что-либо создадите
2. Назначения ролей отдельным людям вместо role collections: административная нагрузка со временем только накапливается
3. Игнорирования раздела "Security Alerts"
4. Ситуации, когда сервисы разработки работают в конфигурациях продуктивной среды
5. Отсутствия документации по структуре аккаунта и логике, стоящей за ней: Cockpit хранит что, но не почему

Это централизует управление жизненным циклом пользователей и убирает целый класс административной нагрузки.

<summary>Какую runtime-среду выбрать в BTP: Cloud Foundry, Kyma или ABAP Cloud?</summary>

Подбирайте среду под реальные навыки вашей команды, а не только под архитектурную схему. Cloud Foundry — самая зрелая среда и у неё самый большой каталог сервисов: используйте её для приложений на Java, Node.js и Python. Kyma — Kubernetes-native и гибкая, но требует знаний Kubernetes, которых у многих команд, сфокусированных на SAP, просто нет. ABAP Cloud предназначена для расширений на ABAP и является естественным выбором для команд с опытом разработки в SAP.

Я видел проекты, которые задерживались на месяцы, потому что runtime выбирали по архитектурным принципам, не проверив, что разработчики реально умеют. Технически более правильный вариант, который команда не может нормально реализовать, хуже прагматичного варианта, который она может.

<summary>Как подключить SAP BTP к on-premise системам SAP?</summary>

Установите Cloud Connector в вашей on-premise сети. Он создаёт защищённый исходящий туннель к BTP без необходимости менять входящие настройки firewall. Настройте его так, чтобы он открывал только те системы и URL-пути, которые действительно нужны BTP: принцип минимального доступа.

В Cockpit BTP перейдите в раздел "Connectivity" вашего subaccount, чтобы проверить подключение Cloud Connector и его статус. Затем создайте Destinations, указывающие на ваши опубликованные системы SAP. Ваши приложения BTP и integration flow будут ссылаться на эти Destinations, когда им понадобится вызывать on-premise системы. Протестируйте весь путь от BTP до вашей on-premise системы, прежде чем что-либо переводить в продуктив.

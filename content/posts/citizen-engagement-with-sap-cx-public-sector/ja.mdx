市民は、公共サービスにもオンラインバンキングのような使い勝手を期待し始めていました。1回ログインすれば申請状況が見えて、複数の窓口を追いかけなくても更新情報が届く、ということです。私たちが支援した政府機関でも、フィードバックでは一貫して同じ声が上がっていました。単に処理が遅いという不満ではなく、そもそも何も分からない、という不満です。

既存のレガシーシステムでは、その透明性を実現できませんでした。部門ごとに記録が分断されていました。どの窓口でも同じ質問を繰り返していました。市民は問い合わせを諦め、職員は別の場所ですでに受け取っているデータを毎日再入力していました。

SAP CXによって、私たちは市民との接点をゼロから再設計する機会を得ました。

## 4つのモジュールと、それぞれが実際に解決したこと

私たちはSAP CXポートフォリオの中から複数の製品を選びましたが、それぞれに明確な役割を持たせました。これはプラットフォーム選定ではありません。4つの現実の問題に対する、4つの的を絞った答えでした。

| Module | Problem it solved | What changed |
|---|---|---|
| モジュール | 解決した問題 | 何が変わったか |
| Service Cloud | 部門ごとにケースが散在し、共通のビューがない | 職員向けに単一のケースビュー、市民向けに追跡可能なステータス |
| Customer Data Cloud | サービスごとに複数ログインが必要で、同意内容が見えない | 単一ログイン、市民自身がデータ設定を管理 |
| Marketing Cloud (Emarsys) | 市民が自分でサービスを追いかける必要があり、行政側からは連絡しない | 更新、手数料、期限に関する事前リマインダー |
| Commerce Cloud | 対面支払いのみで、消込は手作業 | オンライン支払い、即時の領収書発行、ERPをリアルタイム更新 |

### SAP Service Cloud

Service Cloudは中核として機能しました。すべてのチャネル（Web、電話、対面窓口）が1つのケースビューに集約されました。ケース担当者は、たとえば駐車許可を申請した同じ市民が、先週は税務の問い合わせで電話していたことをようやく把握できるようになりました。以前は、そうした情報は別々のシステムに分かれていて、誰も結び付けて見ていませんでした。

私たちはシステム内にサービスレベル契約を設定しました。これによって説明責任が生まれました。市民は、対応期限が見えていて、しかも現実的であることに気づき始めました。この可視性だけでも、問い合わせの再発は減りました。

AIチャットボットも小さな役割は果たしましたが、適用範囲は意図的に絞りました。ある市民は、待たされずに営業時間のような基本的な質問にすぐ答えが返ってくるのは助かると言っていました。そのあとで、こうも言いました。「でも、異議申し立てがあるなら人に対応してほしいです」。私たちも同感でした。基本的な問い合わせはチャットボット、それ以外は人です。

### SAP Customer Data Cloud

複数ログインは、継続的に出ていた不満でした。許認可用に1つ、税務用に1つ、事業ライセンス用に1つ、という具合です。CDCはそれをすべて、1つの安全なデジタルIDに置き換えました。

市民は認証情報をいくつも管理しなくてよくなりました。そして同じくらい重要なのは、自分自身の同意設定をようやく確認できるようになったことです。あるフィードバックセッションで、地元の事業主がこう言いました。「少なくとも今は、自分のデータがどこに行くのか分かります。以前は、何も分からないまま同意している感じでした」。こうした信頼は、機能だけでは生まれません。人にコントロールを渡すことで生まれます。

### SAP Marketing Cloud (Emarsys)

これはテクノロジーの変化であると同時に、文化の変化でもありました。市民がこちらを追いかけるのを待つのではなく、こちらから先回りして連絡する形に変えました。更新リマインダー、税通知、期限アラートを直接送るようにしたのです。

重要だったのは、やり過ぎないことです。メッセージが多すぎると、人は読まなくなります。私たちは関連性に絞りました。たとえば、子育て世帯には保育料の期限、年金受給者には年金通知です。ある地元の事業主は、Emarsysが忘れる前に許可更新を知らせてくれるので、更新を心配しなくなったと言っていました。そこが変化の本質です。

### SAP Commerce Cloud

以前は、支払いのために窓口へ行く必要がありました。人々は列に並び、現金で支払い、その領収書が自分の記録と一致していることを願うしかありませんでした。Commerce Cloudによって、申請、手数料支払い、確認までを1回のセッションでオンライン完結できるようになりました。

経理担当者にとっては、週末に手作業で消込する必要がなくなったことを意味します。領収書は即時に発行されました。市民も、記録がすぐに残るので、プロセスを信頼できるようになりました。

## テスト運用の瞬間

展開初期に、私たちは事業許可申請でパイロットを実施しました。ある市民は申請を提出し、ポータル上では「処理中」と表示されましたが、職員側のダッシュボードでは「承認待ち」と表示されていました。この小さな不一致、つまり同じ申請なのに2つの異なるステータスが見えていたことで、問い合わせ件数は減るどころか増えました。

私たちは、両者がまったく同じデータを、同じService Cloudレコードから見るようにして修正しました。この修正こそが、何よりもまず最初の問い合わせ件数減少につながったポイントでした。

市民は、スピード以上に明確さを重視します。自分たちの職員と同じビューを市民にも提供すれば、信頼不足が生む問い合わせそのものを減らせます。

## ＜span translate="no">SAP</span> BTPによるバックオフィス統合

フロントエンドの作業は、全体の半分にすぎませんでした。市民が見るのはポータルです。Service CloudとERPの間の受け渡しは見えません。しかし、その受け渡しが壊れると、市民は確実にそれを感じます。

統合前は、市民が建築許可をオンラインで申請しても、職員はその依頼を手作業でERPに入力していました。支払いはデジタルで受け付けても、財務記録との消込は週末にまとめて行っていました。社会サービス部門は独自のケース管理を行っており、他部門からは見えませんでした。

SAP BTPが接着剤の役割を果たしました。Service CloudをS/4HANAおよび旧来のプラットフォームと接続すると、次のことが実現しました。

1. 許可申請がERP内のワークフローを直接起動
2. Commerce Cloud経由の支払いが財務元帳とリアルタイム同期
3. 社会サービスのケースステータスが、プライバシー保護の範囲内で部門横断的に可視化

あるケース担当者は私にこう言いました。「初めて、市民の案件全体像を4つのシステムを掘り返さずに見られるようになりました」。この、データ入力から例外対応へのシフトが、サービス品質を変えました。

## 360度の市民ビュー

「360 citizen view」という言葉は、最初は単なるバズワードのように聞こえました。職員にとって意味していたのは、ただ1つです。市民に同じ話を5回もさせないことです。

私たちはID、取引、サービスリクエスト、コミュニケーションログを1つのプロファイルに集約しました。誰かが住宅補助金を申請すると、ケース担当者は進行中の医療給付請求や、最近の税務窓口とのやり取りも確認できました。その機関は、ばらばらの部門の集まりではなく、1つの組織として動き始めました。

データクレンジングは遅く、時には退屈でもありました。しかし、そこを飛ばした移行で何が起きるかは、私たちはすでに見てきました。重複レコード、食い違う履歴、そして嘘をつく360ビューです。この投資は報われました。エラーが減ると、信頼は上がりました。

## 成果

| Area | Before | After |
|---|---|---|
| 領域 | 導入前 | 導入後 |
| 許可処理 | 6週間 | 10日 |
| 全体の処理時間 | ベースライン | 約50%削減 |
| オンライン申請 | ごくわずか | 1年目で65% |
| 職員のデータ入力 | システム横断の手作業による再入力 | 統合ワークフロー、例外対応のみ |
| 支払い消込 | 毎週の手作業スプレッドシート | ERPとリアルタイム同期 |
| 市民からの問い合わせ件数 | 高い：ステータス確認の問い合わせが中心 | ステータス共有の修正後に減少 |

効果はほぼすぐに明らかになりました。市民は「私の申請は今どこですか」と聞かなくなりました。自分で見られるようになったからです。職員はデータの再入力をやめ、実際の案件解決に集中できるようになりました。双方で信頼感が高まりました。

## このプログラムを2026年のSAP CXで実施するとどう見えるか

この導入は2023年から2024年にかけて行いました。同じプログラムを2026年に開始するなら、3つの点が変わります。

**SAP Service CloudとSAP Sales Cloud上のJouleは、今ではプラットフォームの一部です。** ケース担当者は、フィルタビューをたどる代わりに、市民プロファイルに対して自然言語で問い合わせできます（「この地区の未完了の住宅申請をすべて表示して」など）。Jouleはケース分類やルーティング推奨も支援します。標準スコープでは確かに加速効果がありますが、複数部門にまたがる複雑な案件では、依然として人によるトリアージが必要です。同等の2026年導入であれば、Jouleのレイヤーによって、標準ワークフローにおける定型的なケース照会時間は桁違いに短縮されます。

**SAP BTP統合は、今ではカスタム構築ではなくネイティブです。** 2023年にはカスタムのCPIフローが必要だったService CloudとS/4HANAの統合も、現在ではSAP Integration Suiteの事前構築済み統合コンテンツで提供されるケースが増えています。2026年に開始するプログラムでは、統合の配管部分にかける時間は減り、その分、市民向けワークフロー設計に時間を使えます。

**SAP Customer Data Cloudは、より広いCustomer Data Platformへ進化しています。** ID、同意、データガバナンスは、CDC、マーケティングプラットフォーム、ERPに分散するのではなく、今では1つの統合CDPの中に収まります。特に公共部門では、2023年に市民にとって重要だった同意の透明性を、今ではより簡単に見せられ、より簡単に市民自身が管理できます。

共有ステータスの修正、360度の市民ビューを維持する規律、市民のチャネル選好を尊重したオムニチャネル設計、単純な案件から複雑な案件へ段階的に自動化する進め方は、いずれも今でもそのまま有効です。これらは、AIレイヤーや統合レイヤーに関係なく成り立つ、公共部門特有の定着パターンです。

## 他の公共部門プログラムへの教訓

**オムニチャネルは、すべてのチャネルを同時に始めることではありません。** 高齢の住民は、モバイルよりもWebや電話を好みました。私たちは継続性を設計しました。オンラインで開始し、電話に切り替え、職員が市民の中断地点から引き継ぐ形です。全員をアプリに押し込むことより、その選択肢のほうが重要でした。

**まず単純な案件を自動化してください。** 職員は、複雑な案件でコントロールを失うことに慎重でした。私たちは更新手続きから始めました。ルールが明確で、リスクが低かったからです。この段階的な進め方によって、難しい領域に手を付ける前に、内部の自信を築けました。

**統合の前にデータガバナンスです。** 記録が重複していたり不整合だったりすると、360ビューはその問題を市民と職員の両方の前に同時にさらします。先にクリーンアップし、その後で統合してください。

**コミュニケーションでは量より関連性です。** Emarsysが最も効果を発揮したのは、メッセージを絞り込み、タイミングを合わせたときでした。あらゆる更新をあらゆるチャネルに一斉送信すると、せっかく得た信頼はすぐに逆戻りしました。節度が信頼性を作りました。

## よくある質問

<details>
<summary>公共部門の市民エンゲージメントには、どのSAP CXモジュールが最も適していますか？</summary>

このケースで最も価値を生んだ組み合わせは、ケース管理のためのService Cloud、統合IDと同意管理のためのCustomer Data Cloud、先回りした通知のためのEmarsys、支払いのためのCommerce Cloudでした。

通常はService Cloudから始めるのがよいです。職員には単一のケースビューを、市民には追跡可能なステータスを提供できるからです。市民が複数部門とやり取りし、ログインが分断されているならCDCは重要です。順番も大事です。まずケースレイヤー、その次にID、その後にプロアクティブなコミュニケーションと支払いです。

</details>

<details>
<summary>政府機関向けにSAP CXを導入するには、どれくらい時間がかかりますか？</summary>

このプログラムでは、最初のService Cloud導入は、スコープ定義から本番稼働までおよそ6か月でした。CDC、Emarsys、Commerce Cloudを追加したことで、4モジュールすべてで合計約18か月になりました。

最大の変動要因はデータ準備状況です。市民記録が部門間で分断されていたり重複していたりすると、統合を始める前にデータクレンジングで数週間追加されます。この工程を省いたプログラムは、たいてい本番稼働後にステータス不一致や消込失敗の形でその代償を払います。

</details>

<details>
<summary>公共部門で使う場合、SAP Service Cloudと標準的なCRMの違いは何ですか？</summary>

標準的なCRMは、商取引上の関係を前提に作られています。リード、パイプライン、顧客です。Service Cloudは、ケース管理とサービス解決を前提に作られています。公共部門で重要なのは、SLA追跡、チャネル統合（Web、電話、窓口）、そして部門横断のケース可視化です。

政府機関の文脈での大きな違いは、バックオフィスのERPやコンプライアンスシステムとの統合です。Service CloudはSAP BTPおよびS/4HANAと接続できるため、許可申請が手作業の受け渡しなしにERPワークフローを起動できます。汎用CRMには、その統合経路がありません。

</details>

<details>
<summary>市民エンゲージメントプログラムの成功は、どのように測定しますか？</summary>

このプログラムで最も重要だったKPIは、ケース種別ごとの解決時間、一次対応解決率、サービス別のデジタル利用率、市民アンケートによるCSATまたはNPS、取引あたりの対応コスト、そして月次のサポートチケット件数でした。

避けるべき見栄えだけの指標は、ポータル登録市民数です。登録はエンゲージメントを意味しません。完了した取引件数と、実際に問い合わせ件数が減ったかを追ってください。登録してもなおステータス確認の電話が来るなら、透明性の問題は解決していません。

</details>

<details>
<summary>市民向けサービスにおいて、SAP BTPはどのような役割を果たしますか？</summary>

SAP BTPは統合レイヤーです。市民には見えませんが、欠けていると確実に影響が出ます。BTPがないと、フロントエンドのポータルとバックオフィスのERPはサイロ化したままです。職員はデジタル申請を受け取っても、その後で財務やケース管理システムに手作業で再入力することになります。

BTPがService CloudとS/4HANAを接続すると、許可申請は自動的にERPワークフローを起動し、支払いはリアルタイムで同期され、ケースデータはプライバシールールの範囲内で部門間を流れます。誰かがデータを運ばなくても動くので、市民にも職員にもエンドツーエンドで機能する体験になります。

</details>

<details>
<summary>公共部門のSAP CX導入で、プライバシーと同意はどのように扱いますか？</summary>

Customer Data Cloudがこれを直接担います。市民自身が閲覧・変更できる同意設定を備えた、統合デジタルIDを提供します。あらゆるデータ利用は、利用規約の奥に埋もれるのではなく、明示的な同意にひも付きます。

実務上は、各部門がどの情報にアクセスしているかを市民が確認でき、設定も変更できるようになったということです。「ようやく自分のデータがどこに行くのか分かる」と言った地元の事業主は、特別な例ではありませんでした。このコントロール感は、フィードバックセッションで繰り返し出てきたテーマでした。同意を透明化することは、多くのEU法域ではコンプライアンス要件でもあります。つまりCDCは、市民体験と法的義務の両方に同時に応えます。

</details>

SAP技術変更管理ツールは、何が本番環境に移るのか、どの順序で、誰の承認を得て移るのかを制御します。評価の場には、ほぼ毎回4つのツールが上がります。SAP Cloud ALMは、新規プログラム向けのSAPの戦略的な選択肢です。Solution Manager ChaRMは、オンプレミス環境で実績のあるネイティブの選択肢です。Rev-Tracは、移送量が多い環境や並行開発に向いています。Basis TechnologiesのActiveControl（当初はTransport Expressの名称で販売）は、もう一つの主要なサードパーティ製品です。機能を比べるより、導入形態と移送量のほうが、候補を早く絞り込めます。

以前、欧州の製造グループでロールアウトを率いていたとき、厳しい教訓を得ました。ある開発者が、一切の承認を経ずに移送をそのまま本番環境に投入したのです。チェックは何も行われていませんでした。システムは停止しなかったものの、在庫数量が大きく狂い、復旧に2日かかりました。変更管理のツールに本気で取り組むようになったのは、それからです。

## 変更管理の仕組みがカバーすべきこと

SAPランドスケープの管理を始めたころ、私は移送を技術的な受け渡しだと考えていました。コードを移し、テストして、終わりです。ところが、依存関係を一つ見落としたことで、その考えは変わりました。重要なのは次の要素です。

1. **変更要求ワークフロー。** 記録のない変更も、裏口もあってはなりません。すべてに追跡の跡が必要です。
2. **移送の順序制御。** 順序を誤ると、システム間の不整合の修正に何時間も取られます。
3. **オブジェクト履歴。** 誰が、何を、いつ、なぜ変更したか。
4. **依存関係と競合のチェック。** 省かれがちですが、最も大きな問題を引き起こします。
5. **監査ログ。** SOXの要件がなくても役に立ちます。何かが壊れたとき、必ずその記録が必要になります。
6. **承認ゲート。** 本番環境に届く前に置く、適切な摩擦です。
7. **移送権限の制限。** 本番環境へのインポート権限は、全員に必要なわけではありません。

ツールの評価が始まるきっかけは、たいてい次の4つの問題です。移送が本番環境に直接投入されること。部門ごとに承認の方法が異なり、財務はチケット、物流はメールを使っていること。2人の開発者が別々の移送で同じオブジェクトを編集し、最後にインポートされたほうが他方を上書きしてしまうこと。そして、誰も書く時間がなかったドキュメント。

## 4つのツール

### SAP Cloud ALM

SAP Cloud ALMは、SAPのクラウドベースのアプリケーションライフサイクル管理サービスで、Solution Managerの後継です。SAP Enterprise Support, cloud edition付きのSAPクラウドサブスクリプションと、オンプレミスのお客様向けのSAP Enterprise Supportに含まれています。

変更・デプロイメント管理では、「フィーチャ」を使って、変更のドキュメントと、それを運ぶ移送をひとまとめにします。S/4HANA Private Editionと、リリース7.40以降のオンプレミスABAPシステム（ECCを含む）では、変更・移送システム（CTS）に接続します。Public EditionではAdaptation Transport Organizerを使い、BTPとIntegration SuiteのコンテンツにはSAP Cloud Transport Managementを使います。CTS+はサポートされていません。

押さえておくべき制約が2つあります。SAPは、ChaRMにある品質ゲート管理を、Cloud ALMでは現時点で対象外としています。また、ChaRMの変更データを移行する予定もありません。SAPが推奨するのは、Solution Managerで進行中の変更サイクルを完了させたうえで、Cloud ALMのデプロイメント管理を有効化することです（[SAP Support](https://support.sap.com/en/alm/sap-cloud-alm/transition-to-sap-cloud-alm/transition-to-calm-implementation.html)）。規制の厳しい環境や、リトロフィットやデジタル署名を使う複雑なChaRM構成については、足りない機能が提供されるのを待ってから移行するというのが、SAP自身のガイダンスです。

**向いている場合：** どのエディションであれ新規のS/4HANAプログラムを始める場合、RISEまたはGROWを運用している場合、Solution Managerを廃止する予定がある場合です。Cloud ALMが対応するまでは、自社のプロセスで承認ゲートを補う前提で考えてください。

### Solution Manager ChaRM

SAP Enterprise Supportを契約していれば、Solution Manager 7.2の変更要求管理（ChaRM）はすでに手元にあります。多くのお客様は、その機能の一部しか使っていません。変更要求と変更ドキュメント、緊急変更、コピーの移送、デュアルランドスケープのリトロフィット、品質ゲート管理といった機能です。

私が知る製造業のSAPクライアントは、外部ツールを購入するか、すでにあるChaRMを使うかで迷っていました。変更件数は1日に50〜60件ほどです。依存関係の要件を評価した結果、追加ライセンスなしでChaRMで対応できると分かりました。3か月後には、2,000件を超える移送を、デプロイメントの問題を一度も出さずに処理していました。違いを生んだのは、品質ゲートと承認ワークフローを適切に設定したことです。

落とし穴は時間です。「ライセンスに含まれる」ことは「無料」を意味しません。しっかりしたChaRMの構成には数か月かかります。Solution Manager 7.2の標準保守は2027年末で終了します。Business Suiteの延長保守を購入したお客様は、Solution Managerについても2030年まで限定的な延長保守を受けられ、そこには変更管理機能も引き続き含まれます。

**向いている場合：** Solution Managerがすでに稼働していて、監査人が完全なトレーサビリティを求め、品質ゲートやリトロフィットがいま必要な場合です。ChaRMを新規に構築し直すのではなく、S/4HANAのタイムラインに合わせてCloud ALMへの移行を計画してください。

### Rev-Trac

Rev-Tracは、SAPランドスケープ全体で、移送の順序制御、競合検出、承認を自動化し、SAPシステム内でネイティブに動作します。ベンダーは現在、導入企業全体でリリースサイクルが60%速くなり、移送エラーが99%減ったと公表しています（[Rev-Trac](https://rev-trac.com/)）。これらはベンダー側の主張として受け止め、自社に近いランドスケープでの導入事例を紹介してもらってください。

私が間近で見ていたある導入では、チームは毎月平均15件の本番障害を抱えており、その大半は順序制御の不備が原因でした。Rev-Tracを導入して3か月後、その件数は2件にまで減りました。自動チェックが、ほぼすべての競合を本番環境に届く前に検出したのです。

成果は、インストールしただけでは出ません。依存関係の計画を整えないままRev-Tracに飛びついて、数週間苦労したグローバル企業を私は知っています。Rev-Tracの費用は、システム数とユーザー数によって、年間150,000ドルから500,000ドルまで幅があります。十分に複雑な環境では、ツールそのものではなく、本番障害の減少に対して支払っていることになります。

**向いている場合：** 1日に何百件もの移送を処理している、複数の開発トラックが並行している、あるいはECCとS/4HANAが混在するランドスケープで、すでに競合が本番環境に届いている場合です。

### ActiveControl（旧Transport Express）

この記事の以前の版では、「Transport Express」を独立した軽量ツールとして紹介していました。それは誤りでした。Transport Express（Transport Expressoと書かれることもあります）は、Basis Technologiesの変更管理製品の当初の名称で、のちにActiveControlへ改称されました。現在は、SAP認定の変更・リリース・DevOps自動化ツールで、承認ワークフロー、コピーの移送、ServiceNow連携、CI/CDパイプラインのサポートを備えています（[Basis Technologies](https://www.basistechnologies.com/activecontrol/)）。位置づけはRev-Tracの下位ではなく、競合です。

高価なリリース調整ツールを正当化できなかった製薬業のクライアントは、変更ドキュメントの改善を目的にTransport Expressへ切り替えました。2か月以内に、移送エラーは65%減少しました。

**向いている場合：** SAPの変更・リリース管理を自動化し、より広いDevOpsツールチェーンとつなぎたい場合で、Rev-Tracも候補に入っているときです。

## 4つのツールの比較

判断の材料として、私ならこのように位置づけます。

| | SAP Cloud ALM | Solution Manager ChaRM | Rev-Trac | ActiveControl |
|---|---|---|---|---|
| 提供元 | SAP | SAP | Rev-Trac | Basis Technologies |
| ライセンス | SAPクラウドサブスクリプションとEnterprise Supportに含まれる | Enterprise Supportに含まれる。構成の工数が必要 | 商用サブスクリプション | 商用サブスクリプション |
| 対象システム | Public Edition（ATO）、Private EditionおよびオンプレミスのABAP 7.40以降（CTS）、BTP（Cloud Transport Management） | CTSおよびCTS+経由のABAPシステム | ECCおよびS/4HANAのランドスケープ | ECCおよびS/4HANAのランドスケープ |
| 承認と品質ゲート | フィーチャの承認。品質ゲート管理は現時点で対象外 | 完全な品質ゲート管理 | ルールベースの承認ルーティング | 設定可能な承認ワークフロー |
| 競合・順序制御のチェック | フィーチャを順序どおりにデプロイ。現在の対象範囲はSAPに確認 | システム横断のオブジェクトロックとダウングレード保護（構成した場合） | 自動。中核的な強み | 自動 |
| DevOps連携 | API、Jira連携 | 限定的。カスタムインターフェース | Jira、Git、Jenkinsのコネクタ | ServiceNowおよびCI/CD連携 |
| 将来性 | SAPの戦略的ツール | 標準保守は2027年に終了 | ベンダーのロードマップ | ベンダーのロードマップ |

## 状況に合うツールはどれか

すべてのランドスケープに同じレベルの統制が必要なわけではありません。まず、次の問いから始めてください。

1. いま利用している、または移行予定の導入形態はどれですか。Public Edition、Private Edition、オンプレミスのS/4HANA、ECCのいずれでしょうか。
2. 通常時とリリースのピーク時で、1日あたり何件の移送がありますか。
3. 並行して開発しているチームはいくつで、いくつのタイムゾーンにまたがっていますか。
4. 監査人は、SOXやGxPなどに向けた移送単位の証跡を求めていますか。
5. 承認は現在、本当の統制ポイントですか。それともメールで追いかけている状態ですか。
6. 開発者同士が、本番環境で互いの作業を上書きしたことはありますか。

| 状況 | 私ならここから始めます |
|---|---|
| RISEまたはGROWでの新規S/4HANAプログラム | Cloud ALM。移送量や並行トラックが必要とする場合にのみ、Rev-TracまたはActiveControlを追加 |
| ChaRMが問題なく稼働しているオンプレミス環境 | S/4HANA移行まではChaRMを使い続け、そのあとCloud ALMへの切り替えを計画 |
| ChaRMでリトロフィットやデジタル署名を使う規制産業 | Cloud ALMがそれらの機能に対応するまではChaRMにとどまる。2027年が決断を迫る場合は、サードパーティ製ツールを検討 |
| 1日に何百件もの移送、並行トラック | Rev-TracまたはActiveControl。ドキュメント用にCloud ALMを併用 |
| 小規模なランドスケープ、低い移送量、Solution Managerなし | Cloud ALM。CTSのルートと承認は規律を持って運用 |

複雑なランドスケープでは、答えが2つのツールになることがよくあります。変更ドキュメントとSAPとの整合にはCloud ALM、大量の移送での順序制御と競合管理にはRev-TracまたはActiveControlです。

適切なツールとは、機能が最も多いものではなく、実際の課題を解決するものです。ガバナンスが不十分なランドスケープでChaRMが失敗し、規律の取れた環境ではもっとシンプルな構成が成功する場面を、私は見てきました。変更管理は、[品質ゲート](/ja/sap-quality-gates-implementation/)や[テストツール](/ja/sap-testing-validation-tools-comparison/)とも足並みをそろえる必要があります。課題が移送ではなく人にあるなら、[チェンジマネジメント計画のガイド](/ja/change-management-plan-success/)でその側面を扱っています。

## よくある質問

<details>
<summary>SAP技術変更管理ツールとは何ですか？</summary>

SAPシステムへの変更を管理し、設定やコードの変更がすべて追跡され、承認され、正しい順序でインポートされるようにするツールです。最もよく評価される4つは、SAP Cloud ALM、Solution Manager ChaRM、Rev-Trac、ActiveControlです。これらがなければ、スプレッドシート、メール、記憶に頼ることになり、依存関係を一つ見落とすだけで本番環境の停止につながりかねません。

</details>

<details>
<summary>SAP Cloud ALMはSolution Manager ChaRMに置き換わりますか？</summary>

はい、時間をかけて置き換わっていきます。Cloud ALMはSAPの戦略的な後継であり、Solution Manager 7.2の標準保守は2027年に終了します。Cloud ALMはすでに、Public Edition、Private Edition、7.40以降のオンプレミスABAPシステムの移送を管理できます。SAPはChaRMの変更データを移行しません。また、品質ゲート管理はまだCloud ALMの対象外です。複雑なChaRM構成を持つ規制対象のお客様には、それらの機能が提供されるのを待つよう助言されています。

</details>

<details>
<summary>SAP Cloud ALMはECCの移送を管理できますか？</summary>

はい。Cloud ALMの変更・デプロイメント管理は、リリース7.40以降のSAP NetWeaver ABAPシステムの変更・移送システムに接続します。これにはECC、オンプレミスのS/4HANA、Private Editionが含まれます。CTS+はサポートされておらず、管理対象のシステムには前提となるサポートパッケージとSAPノートが必要です。

</details>

<details>
<summary>Transport Expressはどうなりましたか？</summary>

Transport Express（Transport Expressoと書かれることもあります）は、Basis TechnologiesのSAP変更管理製品の当初の名称です。移送管理から、変更・リリース・DevOps自動化へと発展するにつれて、ActiveControlに改称されました。ツールを比較する際は、Rev-Tracと並べてActiveControlを評価してください。

</details>

<details>
<summary>Rev-Tracが適しているのはどんなときですか？</summary>

移送量が多い、複数の開発トラックが並行している、あるいはすでに競合が本番環境に届いているときです。強みは、競合の自動検出と順序制御です。先に依存関係の計画を整える必要があり、費用も相応にかかるため、導入の根拠は本番障害の減少にあります。

</details>

<details>
<summary>SAPの変更管理ツールはどう選べばよいですか？</summary>

まず導入形態から始め、次に移送量、並行トラックの数、監査要件、そしてすでにSolution Managerを運用しているかどうかを確認します。実際に抱えている課題を解決するツールを選び、セットアップとトレーニングの予算を確保してください。これらはツール自体よりも重要です。

</details>

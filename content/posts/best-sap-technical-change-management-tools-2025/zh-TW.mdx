SAP 技術變更管理工具控制什麼內容、以什麼順序、經由誰核准後移入正式環境。幾乎每次評估都會遇到四種工具。SAP Cloud ALM 是 SAP 針對新專案的策略性選擇。Solution Manager ChaRM 是地端環境中成熟的原生選項。Rev-Trac 適合大量與平行開發。Basis Technologies 的 ActiveControl，最初以 Transport Express 名稱銷售，是另一個主要的第三方選項。您的部署模式與傳輸量，比任何功能比較都更快縮小選項範圍。

當年我為一家歐洲製造集團執行上線時，我們吃了一次慘痛的教訓。一位開發人員未經任何核准，就把一筆傳輸直接移入正式環境。沒有做任何檢查。系統沒有當機，但庫存數字全都亂了，我們花了兩天才清理乾淨。就是從那時候起，我們開始認真對待變更工具。

## 變更管理設定必須涵蓋什麼

我剛開始管理 SAP 環境時，以為傳輸只是技術交接：搬程式碼、測試、結束。後來因為漏掉一個相依項目，我改變了看法。以下是重要的部分：

1. **變更請求工作流程。** 不得有未記錄的變更，也不得有旁門。每件事都要留下軌跡。
2. **傳輸排序。** 順序錯了，您就得花好幾個小時修復系統之間的不一致。
3. **物件歷史。** 誰在何時、為何變更了什麼。
4. **相依性與衝突檢查。** 常被跳過。造成的痛苦最多。
5. **稽核日誌。** 即使沒有 SOX 要求也很有用。出問題時您會需要這條軌跡。
6. **核准關卡。** 在任何東西到達正式環境之前，設下恰當的摩擦。
7. **限制移入權限。** 不是每個人都需要匯入正式環境。

通常有四個問題會引發工具評估。傳輸被直接推到正式環境。各部門的核准方式不同，財務用工單、物流用電子郵件。兩位開發人員在不同的傳輸中編輯同一個物件，結果最後一次匯入覆蓋了另一個。還有沒人有時間寫的文件。

## 四種工具

### SAP Cloud ALM

SAP Cloud ALM 是 SAP 以雲端為基礎的應用程式生命週期管理服務，也是 Solution Manager 的接班者。它包含在附 Enterprise Support, cloud edition 的 SAP 雲端訂閱中，也包含在地端客戶的 SAP Enterprise Support 中。

它的變更與部署管理使用「features」把變更文件與承載它的傳輸綁在一起。針對 S/4HANA Private Edition 與 7.40 版起的地端 ABAP 系統（包括 ECC），它連接到變更與傳輸系統（Change and Transport System，CTS）。在 Public Edition 中它使用 Adaptation Transport Organizer，而 BTP 與 Integration Suite 的內容則使用 SAP Cloud Transport Management。不支援 CTS+。

有兩項限制很重要。SAP 將 ChaRM 具備的品質關卡管理，列為 Cloud ALM 目前不在範圍內。而且 SAP 不打算轉移 ChaRM 的變更資料；它建議先在 Solution Manager 中結束未結的變更週期，再啟用 Cloud ALM 的部署管理（[SAP Support](https://support.sap.com/en/alm/sap-cloud-alm/transition-to-sap-cloud-alm/transition-to-calm-implementation.html)）。對於受管制的環境，或帶有 retrofit 或數位簽章的複雜 ChaRM 設定，SAP 自己的指引是等缺少的功能補齊後再遷移。

**適用時機**：您正在任何版本上啟動新的 S/4HANA 專案、您使用 RISE 或 GROW，或您打算淘汰 Solution Manager。在 Cloud ALM 涵蓋核准關卡之前，預期要在自己的流程中補上。

### Solution Manager ChaRM

如果您支付 SAP Enterprise Support，您就已經擁有 Solution Manager 7.2 中的 Change Request Management（ChaRM）。多數客戶只使用了它提供功能的一部分：變更請求與變更文件、緊急變更、複本傳輸、雙環境 retrofit 與品質關卡管理。

我認識一家 SAP 製造業客戶，正在爭論要買外部工具，還是使用它已經擁有的 ChaRM。它的量大約是每天 50 到 60 筆變更。評估過它的相依性需求之後，我們發現 ChaRM 無須額外授權就能應付。三個月後，它已管理超過 2,000 筆傳輸，沒有出過任何一次部署問題。差別在於品質關卡與核准工作流程設定得當。

關鍵在於時間。「包含在授權內」不代表免費，而且一套好的 ChaRM 組態要花上好幾個月。Solution Manager 7.2 的主流維護將於 2027 年底結束。購買 Business Suite 延伸維護的客戶，可取得 Solution Manager 到 2030 年的有限延伸維護，其中仍包含變更控制管理。

**適用時機**：Solution Manager 已經上線、您的稽核人員預期完整的可追溯性，而且您現在就需要品質關卡或 retrofit。請把遷移到 Cloud ALM，與您的 S/4HANA 時程一起規劃，而不是啟動新的 ChaRM 建置。

### Rev-Trac

Rev-Trac 在整個 SAP 環境中將傳輸排序、衝突偵測與核准自動化，並原生運行於 SAP 系統內。該廠商目前宣稱，其客戶的發行週期加快了 60%，傳輸錯誤減少了 99%（[Rev-Trac](https://rev-trac.com/)）。請把這些視為廠商的說法，並要求提供與您環境相似的參考客戶。

在我密切追蹤的一次導入中，團隊平均每月有 15 個正式環境問題，大多追溯到排序不良。導入 Rev-Trac 三個月後，這個數字降到了兩個。自動化檢查在幾乎每一個衝突到達正式環境之前，就先標記出來。

成果不是光靠安裝就能得到的。我知道一家全球企業在沒有妥善設定相依性規劃的情況下就直接上 Rev-Trac，結果掙扎了好幾週。Rev-Trac 的費用視系統與使用者數而定，每年可能從 $150,000 到 $500,000 不等。在夠複雜的環境中，您付錢買的是更少的正式環境事件，而不是一個工具。

**適用時機**：您每天處理數百筆傳輸、多條平行開發軌道，或 ECC 與 S/4HANA 混合的環境，而且衝突已經在到達正式環境。

### ActiveControl（前身為 Transport Express）

本文的早期版本把「Transport Express」描述為一個獨立的輕量工具。那是錯的。Transport Express（有時寫成 Transport Expresso）是 Basis Technologies 變更管理產品最初的名稱，後來更名為 ActiveControl。如今它是通過 SAP 認證的變更、發行與 DevOps 自動化工具，具備核准工作流程、複本傳輸、ServiceNow 整合與 CI/CD 管線支援（[Basis Technologies](https://www.basistechnologies.com/activecontrol/)）。它與 Rev-Trac 競爭，而不是在其之下。

一家無法合理化昂貴發行協調工具的製藥客戶，為了更好的變更文件而改用 Transport Express。兩個月內，其傳輸錯誤降低了 65%。

**適用時機**：您想要自動化的 SAP 變更與發行管理，並連接到更廣的 DevOps 工具鏈，而且 Rev-Trac 也在您的短名單上。

## 哪種工具適合哪種情況

並非每個環境都需要相同層級的控制。從這些問題開始：

1. 您目前使用或即將遷移到的部署模式是什麼：Public Edition、Private Edition、地端 S/4HANA，還是 ECC？
2. 正常時期與發行高峰時，每天有多少傳輸？
3. 有多少團隊平行開發，橫跨多少個時區？
4. 稽核人員是否需要 SOX、GxP 或類似規範的傳輸層級證據？
5. 核准今天是真正的控制點，還是靠電子郵件追著跑？
6. 開發人員是否曾在正式環境中覆蓋彼此的工作？

| 您的情況 | 我會從哪裡開始 |
|---|---|
| 在 RISE 或 GROW 上的新 S/4HANA 專案 | Cloud ALM，只有在傳輸量或平行軌道需要時，才加上 Rev-Trac 或 ActiveControl |
| 地端環境，ChaRM 運作良好 | 在 S/4HANA 遷移期間保留 ChaRM，再規劃切換到 Cloud ALM |
| 受管制產業，ChaRM 中有 retrofit 或數位簽章 | 留在 ChaRM，直到 Cloud ALM 涵蓋這些功能；如果 2027 年迫使您做決定，可考慮第三方工具 |
| 每天數百筆傳輸、平行軌道 | Rev-Trac 或 ActiveControl，並搭配 Cloud ALM 處理文件 |
| 小型環境、低傳輸量、沒有 Solution Manager | Cloud ALM，搭配有紀律的 CTS 路由與核准 |

在複雜的環境中，答案往往是兩套工具：用 Cloud ALM 處理變更文件並與 SAP 保持一致，再加上 Rev-Trac 或 ActiveControl，在大量傳輸時負責排序與衝突控制。

對的工具，是能解決您實際問題的那一個，而不是功能最多的那一個。我見過 ChaRM 在治理不良的環境中失敗，較簡單的設定在有紀律的環境中成功。變更控制也需要與您的[品質關卡](/zh-TW/sap-quality-gates-implementation/)及[測試工具](/zh-TW/sap-testing-validation-tools-comparison/)對齊。如果問題出在人而不是傳輸，我的[變革管理計畫指南](/zh-TW/change-management-plan-success/)涵蓋了那一面。

## 常見問題

<details>
<summary>什麼是 SAP 技術變更管理工具？</summary>

控制 SAP 系統變更的工具，讓每一項組態或程式碼變更都被追蹤、核准，並依正確順序匯入。評估最多的四種是 SAP Cloud ALM、Solution Manager ChaRM、Rev-Trac 與 ActiveControl。沒有它們，您就得靠試算表、電子郵件與記憶，而漏掉一個相依項目就可能造成正式環境中斷。

</details>

<details>
<summary>SAP Cloud ALM 會取代 Solution Manager ChaRM 嗎？</summary>

會，但需要時間。Cloud ALM 是 SAP 的策略性接班者，Solution Manager 7.2 的主流維護將於 2027 年結束。Cloud ALM 已能為 Public Edition、Private Edition 與 7.40 版起的地端 ABAP 系統管理傳輸。SAP 不會遷移 ChaRM 的變更資料，品質關卡管理也尚未在 Cloud ALM 的範圍內。對於設定複雜 ChaRM 的受管制客戶，建議等待這些功能。

</details>

<details>
<summary>SAP Cloud ALM 能管理 ECC 的傳輸嗎？</summary>

可以。Cloud ALM 的變更與部署管理，可連接 7.40 版起的 SAP NetWeaver ABAP 系統的 Change and Transport System。這包括 ECC、地端 S/4HANA 與 Private Edition。不支援 CTS+，而且受管理的系統需要先具備必要的支援套件與 SAP Notes。

</details>

<details>
<summary>Transport Express 後來怎麼了？</summary>

Transport Express（也寫成 Transport Expresso）是 Basis Technologies 的 SAP 變更管理產品最初的名稱。隨著它從傳輸管理成長為變更、發行與 DevOps 自動化，名稱改為 ActiveControl。如果您在比較工具，請把 ActiveControl 與 Rev-Trac 一併評估。

</details>

<details>
<summary>Rev-Trac 在什麼情況下合理？</summary>

當傳輸量很高、多條開發軌道平行進行，或衝突已經在到達正式環境時。它的強項是自動化的衝突偵測與排序。它需要先設定好相依性規劃，而且要花真金白銀，所以這項投資的理由，建立在更少的正式環境事件上。

</details>

<details>
<summary>我該如何選擇 SAP 變更管理工具？</summary>

先從您的部署模式開始，再看傳輸量、平行軌道的數量、稽核要求，以及您是否已在使用 Solution Manager。選擇能解決您實際問題的工具，並為設定與訓練編列預算，這兩者比工具本身更重要。

</details>

2026 年最好的 SAP 文档工具，取决于要做的是哪类工作。流程图方面，SAP Signavio 在 S/4HANA 转型中领先。设计决策和交付物，用 Confluence 或 SharePoint。新项目上的需求、测试和变更控制，用 SAP Cloud ALM。培训材料用 SAP Enable Now，应用内引导用 WalkMe，它现在归 SAP 所有。需要审计级别记录的，用 SAP 自带的文档管理，或者 OpenText。本指南写给正在为 SAP 项目搭建或修复文档体系的 PMO 负责人和解决方案架构师。先从您最大的缺口入手，而不是看功能清单最长的那个。依我的经验，出问题的很少是工具选择本身。出问题的是工具周围的结构和纪律。

我见过团队用零散的 Excel 文件和共享盘来管理长达 12 个月的 SAP 上线。勉强能运转，但只是因为有一个人一直在追着大家更新。那个人在项目中途离开后，就没有人能追溯各项决策了。

## 文档在哪些时候派上用场

**当会议室里意见不一时。** 我在一次 UAT 计划会议上就遇到过。各团队在推诿测试场景该由谁负责。我们调出已签署的项目章程，讨论就此结束。至少又省下了一个小时的争论。每一项重要决策，只要文档可搜索，就能省掉一场争论。

**审计人员到场时。** 在质量关卡或审计中，第一个问题总是一样：把证据拿出来。除了通过或未通过的状态，也要留存实际的测试结果。记录谁在什么时候批准了什么。审计轨迹就是文档。

**切换期间。** 切换时没有人会去翻邮件链。如果您不能在十秒内调出一份配置文档，就已经耽误了时间。简单的命名规范和可搜索的存储就能避免这种情况。

**当人员离开时。** 我见过团队花上好几周，去重建某项配置当初为什么那样做。这些知识存在于五个不同的邮箱里，或者存在于一位已经不在的顾问的记忆中。

在压力之下最重要的那些东西，工具很少能记录下来：

1. 切换期间做出的例外处理
2. 在会议上做出、却从未写下来的配置决策
3. 业务负责人悄悄改变范围的评论
4. 上线后支持（hypercare）期间采取的权宜做法，从未回流到设计文档里

所以，习惯比平台更重要。

## 按文档工作选工具

下表把每一类文档工作与 SAP 原生选项和主要替代方案对应起来。

| 文档工作 | SAP 选项 | 主要替代方案 | 何时选择替代方案 |
|---|---|---|---|
| 流程建模和挖掘 | SAP Signavio | ARIS、Microsoft Visio、IBM Blueworks Live | 您已经拥有它，或者范围只是单个模块 |
| 设计决策和交付物 | SAP Cloud ALM（需求） | Confluence、SharePoint | 组织日常本来就在那里工作 |
| 变更控制和测试证据 | SAP Cloud ALM | SAP Solution Manager（现有用户）、ServiceNow、Jira | ITSM 已经在 ServiceNow 上运行，或者 Solution Manager 已配置并在使用 |
| 培训材料 | SAP Enable Now | 视频和文档工具 | 上线规模较小 |
| 应用内引导 | WalkMe（SAP） | Whatfix | 引导必须横跨许多非 SAP 应用 |
| 与 SAP 对象关联的记录 | SAP 文档管理系统 | OpenText Extended ECM for SAP | 法规要求超出 SAP DMS 能力的记录管理 |

## 流程建模

### SAP Signavio

SAP 流程工作的最强选择。SAP Signavio Process Manager 负责建模，SAP Signavio Process Intelligence 负责基于真实 SAP 交易的流程挖掘。SAP 在 [2025 年 3 月推出了 AI 辅助的流程建模器](https://news.sap.com/2025/03/sap-signavio-launches-ai-process-modeler-text-to-process/)，可以把书面的流程描述转成 BPMN 草稿，并已将 Joule 集成到整个套件中。

一位物流客户在对其真实 SAP 交易中的低效环节做了挖掘之后，把订单到收款的周期缩短了 11%。流程挖掘展示的是系统记录下来的东西，而这常常和流程图上画的不一样。

Signavio 不是入门工具。对于流程密集型行业的完整 S/4HANA 转型，它物有所值。对于单模块上线，则是多花钱。

### ARIS

在合规要求严格的项目上，仍用于正式的蓝图设计。自 2025 年 1 月起，ARIS 已作为独立业务运营，隶属于 Software AG 由 Silver Lake 持有的控股公司。学习曲线陡峭。它适合制药、金融服务和国防等受监管行业中专职的流程团队，这些行业里正式的蓝图本身就是合规文件。对没有这类要求的中型公司来说，则是大材小用。

### SAP Build Process Automation

SAP 在 SAP BTP 上的工作流和自动化服务，带有一个流程可视化组件，可用于轻量文档。在转型项目中它不能替代 Signavio，但当文档和工作流自动化处于同一个项目、且您已经在用 BTP 时，它很合适。

### Visio 和 IBM Blueworks Live

Visio 适合已经在使用 Microsoft 365、需要低成本绘图的团队。命名规范和版本控制要自己建，也没有任何机制把图与运行中的系统核对。IBM Blueworks Live 仍在积极开发，适合 SAP 技术栈之外的协作建模。两者都无法让文档化的流程与 SAP 实际执行的流程保持同步，而这在转型中很关键。

## 交付物、变更控制和记录

**Confluence** 是设计说明、SOP 以及带评论的审批最常见的选择。Atlassian 的 AI 现在品牌为 Rovo，包含在付费方案中，可以总结和起草页面。它能加快起草；不会替您搭好结构。

**SharePoint** 在大多数组织里已经部署。有了合理的文件夹结构、版本控制，并启用 Microsoft 365 Copilot，它就成了一个稳定、可追溯的交付物存储库。

**SAP Cloud ALM** 在一处涵盖需求、测试管理和变更文档，是 SAP 对 Solution Manager 的战略性继任者。对于有 Enterprise Support 或包含它的云订阅的客户，没有许可费用。对于基于 RISE、GROW 或任何 S/4HANA 版本的新项目，它是默认选择。我对[SAP 项目跟踪工具](/zh-CN/top-sap-project-tracking-tools-2025/)的比较中有更深入的介绍。

**SAP Solution Manager** 对于已经在其上运行的大型多系统项目，仍提供无可匹敌的可追溯性，把流程文档与配置、自定义代码和测试结果关联起来。它的主流维护在 2027 年底结束，部分功能的扩展维护延续到 2030 年。请规划迁移到 Cloud ALM；没有特别的理由，不要在这里启动新项目。

**ServiceNow** 适合组织已经在其中运行 IT 服务管理、并希望 SAP 变更请求纳入同一套事件和变更工作流的情形。要为真正的集成工作做预算。

**Jira 加 Excel 传输跟踪表** 在较小的项目上，只要审查严格，仍然可行。漏掉一条记录，审计轨迹就断了，所以在对合规敏感的环境中要避免。关于专门的变更工具，请看我的 [SAP 技术变更管理工具](/zh-CN/best-sap-technical-change-management-tools-2025/)指南。

**SAP 文档管理系统（DMS）** 把文档与物料、订单、供应商和其他 SAP 对象关联起来，带版本管理和审批工作流。**OpenText Extended ECM for SAP** 由 SAP 作为解决方案扩展销售，为制药、金融服务和受监管的制造业补充了记录管理的深度，这些行业里证据留存没有商量余地。

## 培训和数字化采用

**SAP Enable Now** 把一个流程录制一次，就能从同一份源生成文档、模拟演示和测试脚本。非技术用户也可以编辑输出。大规模上线值得用；小规模的可能不值得。我那篇关于 [SAP 培训策略](/zh-CN/sap-training-strategies-for-employees-to-drive-adoption/)的文章介绍了如何使用它。

**WalkMe** 在 SAP Fiori 和第三方应用内提供应用内引导：提示气泡、引导路径和分步演示。[SAP 在 2024 年 9 月完成了对 WalkMe 的收购](https://news.sap.com/2024/09/sap-completes-walkme-acquisition/)，股权价值约 15 亿美元，并把它与 Enable Now 和 Joule 放在一起定位。请把它当作 SAP 产品来评估，而不是第三方层。

**Whatfix** 是主要的独立替代方案。当引导需要横跨 SAP 和大量非 SAP 应用，或者您希望采用层独立于 SAP 时，它很合适。

## AI 为文档带来了什么

每家主要厂商现在都有 AI 起草层：Joule 和 Signavio 中的 AI 辅助建模、横跨 SharePoint 和 Teams 的 Microsoft 365 Copilot，以及 Confluence 中的 Rovo。它们能更快产出初稿、总结长篇记录，并从会议转录中提取决策。

它们不会决定哪些内容该记录、文档库该怎样组织，或者来源是否正确。在已经有合理结构的项目上，AI 能加快文档工作。在没有结构的项目上，它只会更快地产出不一致的文档。先搭结构，再上 AI。

## 我在真实 SAP 项目上如何组合工具

没有哪一款工具能覆盖一切。对于典型的 S/4HANA 棕地项目，我推荐这样的组合：

1. **SAP Signavio**，用于流程建模、挖掘和 AI 辅助的流程文档
2. **Confluence 或 SharePoint**，用于交付物和设计决策，并开启 AI 层
3. **SAP Cloud ALM**，用于需求、变更控制和测试证据
4. **SAP Enable Now**，用于终端用户培训材料
5. **WalkMe**，用于上线时的应用内引导
6. **OpenText Extended ECM**，仅在行业需要合规级别记录时使用

选择时，看您的团队在压力下如何工作，而不是看演示。如果配置决策总在会议中消失，先把交付物工具理顺。如果新加入的人要花一周时间重建上下文，先修好结构再加工具。如果审计人员六周后到场，而您找不到审批证据，那就是当务之急，配置得当的 SharePoint 或一套 ECM 就能解决。

合适的技术栈，是团队到第三个月仍愿意维护的最小组合。

## 常见问题

<details>
<summary>SAP 项目中的文档是什么？</summary>

SAP 项目文档记录系统如何运作、人们如何使用它，以及一路上做了哪些决定。它包括流程图、功能和技术规格、配置决策、测试证据、最终用户指南和合规记录。我见过这样的项目：没有人能说清一份报表是怎么做出来的，因为作者已经离开，也没有留下任何文字。这就是不把文档当作交付成果的代价。

</details>

<details>
<summary>为什么 SAP 文档很重要？</summary>

它能把两周的交接缩短为两天，加快故障排查，保持培训的一致，并让审计人员拿到他们要的证据。常见的失败是：知识只存在于一个人的脑子里，变更之后文档没有更新，以及没人读的 50 页规格书。先从最容易造成混乱的地方入手，再逐步建立。

</details>

<details>
<summary>SAP 有内置的文档管理系统吗？</summary>

有。SAP 文档管理系统（DMS）把文档与物料、订单、供应商和其他 SAP 对象关联起来，带版本控制、审批工作流和访问控制。对于受监管行业中更严格的记录管理，OpenText Extended ECM for SAP（由 SAP 作为解决方案扩展销售）补充了生命周期和保留控制。

</details>

<details>
<summary>SAP 收购 WalkMe 带来了什么变化？</summary>

SAP 于 2024 年 9 月 12 日完成收购，股权价值约 15 亿美元。WalkMe 现在位于 SAP 数字化采用产品组合中，与 SAP Enable Now 并列，SAP 正在把它与 Joule 集成。它仍然在 SAP Fiori 和第三方应用中提供应用内引导。请把它当作 SAP 产品来评估。

</details>

<details>
<summary>2026 年新的 SAP 项目应该用 Solution Manager 还是 Cloud ALM？</summary>

除非有特别的理由，否则用 Cloud ALM。Solution Manager 7.2 的主流维护在 2027 年底结束，SAP 建议在 2028 年之前完成向 Cloud ALM 的迁移。Cloud ALM 的搭建更轻量，对于有 Enterprise Support 或符合条件的云订阅的客户，没有许可费用。现有的 Solution Manager 用户现在就应该把迁移列入路线图。

</details>

<details>
<summary>财务和物流中常见的 SAP 凭证类型有哪些？</summary>

财务会计方面：SA（总账科目凭证）、KR（供应商发票）、DR（客户发票）、AB（会计凭证，常用于清账）、WE（收货过账）和 RE（发票收据）。采购申请和采购订单都使用 NB 作为标准凭证类型。销售方面：OR（标准订单）、QT（报价单）、LF（外向交货）和 F2（发票）。每种类型都有自己的号码范围和字段控制，所以要在设计阶段确定下来。

</details>

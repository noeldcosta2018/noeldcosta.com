SAP performance testing proves, before go-live, that critical transactions, background jobs and interfaces meet agreed response times under production volumes. Start it in design, run volume and load tests in Realize once configuration is stable, finish the cycle before user acceptance testing (UAT), and make the results a cutover gate. This guide is for CIOs, programme directors and test leads on S/4HANA programmes, including RISE with SAP. It covers what to test, who owns it, how to write acceptance criteria and what changes in the cloud. Start with the acceptance criteria table: if you cannot fill it in, you are not ready to test.

Performance issues in SAP programmes are almost always found after go-live. Fiori tiles time out when 300 users log in at shift change. Z-reports freeze because someone ran an open-ended fiscal-year query against a table with 50 million records. Background jobs overlap during month-end close and the posting run aborts.

Performance issues in SAP programmes rarely arrive by surprise. Most were predictable, just not planned for. The usual pattern: functional testing was thorough. Volume testing was planned, then pushed out when the timeline compressed. The consequences arrived in the first weeks of live operation.

These are not edge cases. They are predictable. The only question is whether the programme tested for them, or whether the business finds them with real orders running.

## Why S/4HANA changed performance testing

In an ECC system on a traditional database, performance testing meant load-testing the application server and database: ABAP runtime, SQL performance, job scheduling. The front end was SAP GUI, which rarely surprised anyone.

On S/4HANA, with Fiori front ends, extensions on SAP BTP and integration through SAP Cloud Integration (CPI), performance depends on several layers at once. A slow Fiori tile could be a long ABAP call, a gateway timeout, an OData service not designed for concurrent requests, or network latency in a hybrid set-up. Testing the back end alone will not find it. Testing the whole path will.

Integration flows add their own risk. Flows that worked in development and QA with single test messages can queue up or fail silently at production volumes. If message queues are not sized for the real load, delays build up. The symptoms look like something else: intermittent order failures, invoice mismatches, data present in one system and missing in another.

## The four tests that matter

1. **Load testing** checks behaviour under expected volume. The key word is expected. You need real transaction volumes, user counts and concurrent sessions. Many load tests fail because they used volume estimates everyone already knew were optimistic.
2. **Stress testing** pushes past design limits to find where the system breaks. If volumes will double in eighteen months, it tells you whether the architecture will cope, and whether sizing becomes a problem before the next infrastructure review.
3. **Soak testing** runs steady load for an extended period to expose problems that build over time: memory leaks, fragmentation and job-chain contention across repeated runs. It is the test most often skipped, and the one that would have caught the month-end failure described below.
4. **End-to-end testing** follows the full path a user takes: tile launch, OData call, ABAP processing, database read, rendering. It is the only way to find problems that are invisible when each layer is tested alone.

## High-risk scenarios

**Shift change and peak login.** When 200 users open the Fiori launchpad at 8am, authentication and launchpad rendering spike. A system that is fine off-peak can be unusable in that window if concurrent logins were never tested. Across manufacturing, retail and financial services, login storms produce the most visible day-one complaints.

**Month-end and year-end close.** The highest-risk scenario on most programmes: high-volume postings, job chains with strict sequencing and a finance team racing a fixed deadline. Run the close job chains end to end against closing-period volumes, not average daily counts.

Batch jobs are usually tested in isolation, which does not reflect reality. At month-end, background processing peaks and many programs run in parallel on the same resources. One poorly optimised job can block five others, and the close runs past its window.

**ECC to S/4HANA conversion.** Stable ECC code behaves differently on HANA. Many programs get much faster; some produce unexpected profiles on particular data patterns. Conversion-specific regression testing is not optional. My [ECC to S/4HANA migration guide](/ecc-to-s4hana-migration/) covers where this fits in the conversion plan.

**Multi-region users.** Network latency affects every transaction. A sales order that takes two seconds in the hosting country can feel broken 3,000 miles away if nobody tested from there. RISE moves hosting to SAP, but latency still depends on the region you choose and the routing to your users.

## Acceptance criteria you can test against

Agree criteria with the business in the Prepare phase, before any test runs. Each one names the transaction or job, the load and the threshold. These examples show the shape; set your own numbers from operational needs:

| Item | Load condition | Pass threshold | Owner |
|---|---|---|---|
| Sales order creation (VA01 or Fiori app) | 150 concurrent order-entry users | Under 3 seconds for 95% of transactions | Order-to-cash process owner |
| Fiori launchpad first load at shift start | Peak concurrent logins for the largest shift | Under 5 seconds for 95% of users | IT operations lead |
| Month-end close job chain | Closing-period volumes, full sequence | Completes inside the agreed close window with no aborts | Financial controller |
| Inbound order interface | Peak hourly message volume | No queue backlog older than 15 minutes | Integration lead |
| High-volume custom report | Full production data volume, typical selection | Under 60 seconds; open-ended selections blocked | Report owner |

"The system should be fast enough for business operations" cannot be tested or accepted. Changing criteria after results arrive defeats the point of having them.

## What IT leaders should expect from their teams

Ask for each of these by name:

| Expectation | What should be delivered | Why it matters |
|---|---|---|
| Performance service levels | Thresholds per transaction, interface and job, with pass and fail | Stops UAT opinion overriding evidence |
| Risk-based scope | Prioritisation by user volume, integration points and data dependency | Puts test cycles on the workloads that matter |
| Cross-team participation | Basis, infrastructure, functional, security and integration present during runs | Prevents blame-shifting when gaps appear |
| Tools and environments ready | Load generators (OpenText LoadRunner, Tricentis NeoLoad, Apache JMeter), monitoring and data refreshes in place before cycles start | Makes simulation realistic |
| Realistic test data | Production-volume master data, real interface calls, representative transaction mix | Makes results predict go-live behaviour |
| Performance reporting | Load mix, response times, CPU and memory, job runtimes, error rates | Gives cutover approval an evidence base |
| Post-go-live monitoring plan | KPIs to watch for the first 30 to 60 days | Confirms the live system stays within tested limits |

## Common mistakes

Four mistakes come up most often, even in large enterprises with mature delivery models.

**Treating functional testing as performance testing.** Functional tests prove a transaction gives the right result. They say nothing about 150 people running it at once.

**Testing with small data volumes.** A customer with 200,000 open order lines behaves differently from one with 5,000. Filters that return instantly in test time out in production. Seed volume for the high-risk areas.

**Leaving performance to Basis.** Basis owns sizing and job scheduling. It does not own report design, OData service architecture or integration flow design, and those drive application performance.

**Giving ownership to QA alone.** QA runs tests and reports results. The decisions that cause performance problems are made by functional, technical and Basis teams in design. A programme-level test lead or architect needs the authority to challenge those decisions early, and the RACI should say who can block go-live on performance grounds.

## What changes on RISE, GROW and with AI

### RISE splits the responsibility

Under RISE with SAP, SAP owns infrastructure: sizing, hyperscaler region, network and platform availability. The client and partner own the application layer. SAP's [RISE roles and responsibilities document](https://assets.cdn.sap.com/agreements/product-policy/hec/roles-responsibilities/rise-with-sap-s4hana-cloud-private-edition-and-sap-erp-pce-roles-and-responsibilities-english-v7-2024a.pdf) makes the point plainly: finding and tuning expensive SQL statements stays with the customer unless you buy SAP's additional application services.

A common failure on RISE programmes is the assumption that SAP will catch performance problems because it runs the infrastructure. It will catch infrastructure problems. It will not catch a badly designed OData service, an inefficient ABAP job or an integration flow that does not scale. Write the split into the charter and the test plan:

1. **SAP:** infrastructure availability and platform-level response
2. **Partner:** application performance under the defined load, including extensions and integration flows
3. **Client:** process-level outcomes such as close runtime and order throughput, and the acceptance decision

### Public Edition and GROW narrow the scope

On S/4HANA Cloud Public Edition, usually bought through GROW with SAP, SAP runs performance testing on its multi-tenant platform as part of its own product standard and does not expect customers to load-test the shared system. Your testing shifts to what is yours: custom integrations, extensions, high-volume reports and analytics, the close and consolidation sequence, and the network path from your sites. Performance problems on the platform itself go to SAP support.

### AI helps with scripts, not architecture

Load-testing vendors are adding AI for script maintenance and results analysis, which helps on programmes where the application changes between cycles. Test the claims on your own landscape before you pay for them. SAP Cloud ALM can help generate test cases and requirements, and AI assistants can draft scenario outlines from process descriptions.

None of it fixes architecture. AI will not tell you the OData service should have been designed differently, or that a report is too heavy for its volumes. Those calls are still made by people, in design, before any test runs.

Most programmes with performance problems in production did not skip testing entirely. They tested without agreed criteria, or tested and then accepted the gaps as known issues under schedule pressure. The discipline is in the criteria and in enforcing them, not in the tool. ## Frequently asked questions

<details>
<summary>What is SAP performance testing and why does it matter?</summary>

It checks how SAP behaves under realistic load: response times for user transactions, runtimes for background jobs, throughput for interfaces and resource use under concurrent work.

Functional correctness and performance are different properties. A transaction that is correct for one user can time out for 200. A job that runs in ten minutes on test data can run for hours on production volumes. Finding that after go-live disrupts operations, forces emergency changes and damages user trust when adoption is most fragile.

</details>

<details>
<summary>When should performance testing start in an SAP programme?</summary>

Risk identification starts in Explore, because architecture choices set performance outcomes. Active testing starts in Realize, once configuration is stable enough that results mean something. Partial configuration gives misleading numbers.

Finish the final cycle before UAT, not during it. Performance defects found in UAT squeeze the remaining schedule and create pressure to accept them as known issues.

</details>

<details>
<summary>Who should own SAP performance testing?</summary>

The programme, not QA alone. QA executes and reports, but the decisions that drive performance are made in design across functional, technical and Basis teams. A central architect or programme test lead needs the authority to challenge those decisions early.

Make it explicit in the RACI: who approves the acceptance criteria, who owns remediation when criteria fail, and who can block go-live on performance grounds.

</details>

<details>
<summary>How does RISE with SAP change performance testing responsibility?</summary>

SAP owns infrastructure: sizing, region, network and platform availability. The client and partner own application performance: configuration, extensions, OData and Fiori design, integration flows and process KPIs. SAP's RISE roles and responsibilities document leaves SQL tuning with the customer unless additional SAP services are bought.

Write the split into the acceptance criteria so each threshold has an owner.

</details>

<details>
<summary>What are the most common SAP Fiori performance issues?</summary>

Four patterns cover most of them. Login storms at shift start, when authentication and launchpad rendering spike. OData services that return large result sets or make several back-end calls per interaction. The gateway layer becoming a bottleneck in its own right, so it must be monitored during tests. And custom or heavily modified apps, where standard performance assumptions do not apply.

</details>

<details>
<summary>How do you define performance acceptance criteria for SAP?</summary>

Name the transaction, the load and the threshold. For example: "Order creation completes in under 3 seconds for 95% of transactions with 150 concurrent users in the order entry role." That is testable.

"The system should be fast enough" is not. Agree criteria with the business in the Prepare phase, based on real operational needs, and do not change them after the results arrive.

</details>

<details>
<summary>What happens if performance testing is skipped or compressed?</summary>

Problems surface in production: jobs overrunning their windows and blocking others, Fiori apps timing out at peak, month-end close taking twice as long and missing reporting deadlines, interface queues backing up.

Users who hit performance problems in their first weeks form a negative view of the system that is hard to reverse. And emergency remediation under live operation costs more than the testing would have, because what was a design decision in Realize becomes an urgent architectural change.

</details>

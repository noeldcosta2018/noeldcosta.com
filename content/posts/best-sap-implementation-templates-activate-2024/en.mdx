SAP Activate ships a template for almost every deliverable in an S/4HANA programme. You will find them in the [SAP Activate Roadmap Viewer](https://me.sap.com/roadmapviewer) and, on cloud programmes, inside SAP Cloud ALM. Finding them is easy. Knowing which ones to take seriously is the hard part.

This guide is for programme managers, PMO leads and sponsors setting up an implementation. It covers the templates I insist on in each phase, shows a working layout for each one, and flags where teams cut corners. If you have one week before kickoff, do the scoping document and the stakeholder matrix first. Everything downstream leans on those two.

The pattern across the ECC and S/4HANA programmes I have worked on in manufacturing, retail and financial services is consistent. Teams that follow the templates catch problems earlier. Teams that treat them as optional paperwork find out mid-project that every decision they never wrote down has turned into a scope dispute.

## The template set at a glance

This is the set I expect to see signed off, with the person who owns each one and the point it has to clear.

| Phase | Template | Owner | Signed off before |
|---|---|---|---|
| Prepare | Project scoping document | Programme manager (sponsor approves) | Explore starts |
| Prepare | Business case | CFO or business owner | Funding is released |
| Prepare | Stakeholder matrix | Programme manager | Explore workshops are booked |
| Explore | Requirements and fit-gap sheet | Solution architect with process owners | Realize starts |
| Realize | Configuration log | Functional leads | Each transport moves to QA |
| Realize | Custom development register | Development lead | Build starts on any object |
| Realize | Test strategy | Test manager | System integration testing starts |
| Realize | Data migration plan | Data migration lead | First mock load |
| Deploy | Cutover plan | Cutover manager | Final dress rehearsal |
| Deploy | Go-live readiness assessment | Programme director (sponsor signs) | Go/no-go meeting |
| Run | Hypercare support model | Service delivery lead | Go-live |
| Run | Performance monitoring sheet | Basis lead | Go-live |

## How Activate is put together

Activate has six phases: Discover, Prepare, Explore, Realize, Deploy and Run. It combines SAP Best Practices content, guided configuration and an agile delivery approach. For most customers Discover happens before the contract is signed, so the templates below start at Prepare.

<explainer-flow title="The templates that carry each Activate phase" caption="Each phase hands the next one a signed template. Skip one and the gap comes back later as a scope dispute." steps="Discover|Prepare|Explore|Realize|Deploy|Run" notes="Usually before the contract is signed|Scoping document, business case, stakeholder matrix|Requirements and fit-gap sheet|Config log, dev register, test strategy, migration plan|Cutover plan, go-live readiness|Hypercare model, performance monitoring" result="Every template signed off before its gate"></explainer-flow>

The phase sequence is not optional. I worked with a retailer that tried to skip parts of it and ended up redoing three months of work. Every quality gate exists for a reason.

When adapting templates, keep around 80% of the standard structure. Change only what reflects your context: industry requirements, regulatory controls, regional specifics. Rewriting everything defeats the purpose.

### What changed in the tooling for 2026

The Activate structure is the same as it was. The tooling around it has moved.

1. **SAP Cloud ALM holds the templates on cloud programmes.** It is SAP's successor to Solution Manager and is included with SAP Enterprise Support and with cloud subscriptions such as RISE with SAP. Scoping, requirements, test plans and cutover tasks can live there with traceability between them. [Solution Manager 7.2](https://support.sap.com/en/alm/faq.html) leaves mainstream maintenance at the end of 2027, with extended maintenance to 2030 for some functions, so existing on-premise landscapes have a few years, not a decade.
2. **Joule is now inside the methodology tooling.** SAP made Joule available in the Activate Roadmap Viewer in 2025 and in SAP Cloud ALM, so a team can ask for task guidance or draft content from the roadmap. It speeds up the first draft. It does not replace the person who signs the fit-gap.
3. **Clean core is now a design rule, with levels.** In August 2025 SAP replaced its three-tier extensibility model with [four clean core levels](https://news.sap.com/2025/08/extend-sap-s4hana-cloud-right-way-clean-clear/), A to D. Level A uses only released APIs, either on SAP BTP or in-system with ABAP Cloud. Level D is not clean at all. The fit-gap template needs a column for where each gap will land.
4. **The public edition narrows the fit-gap.** SAP now markets S/4HANA Cloud Public Edition as SAP Cloud ERP, sold to mid-sized companies as SAP GROW. The same six phases apply with lighter artefacts, and only released-API extensions are allowed, so the "gap" column has fewer possible answers.

## Prepare phase templates

Projects that skip this groundwork pay for it in Explore and Realize.

### Project scoping template

Defines what the project includes and what it does not. When someone tries to add scope three months in (and they will), this document is the reference point. The [SAP project charter](/how-to-create-an-sap-implementation-project-charter/) sits above it and carries the governance detail.

| Section | Details |
|---|---|
| Title, sponsor, PM | SAP S/4HANA Finance implementation; CFO; named senior PM |
| Background | Current state and the driver for change |
| Objectives | Reduce close cycle from 14 days to 5; eliminate manual reconciliations |
| In scope | FI/CO, MM/SD integration, data migration, UAT, go-live |
| Out of scope | HR modules, legacy report migration, third-party integrations beyond ERP |
| Assumptions | Executive sponsor available for monthly SteerCo; test data agreed by Week 6 |
| Constraints | Fixed go-live date; internal resources only for configuration |
| Deliverables | Configured system, test plans, cutover plan, training materials |
| Timeline | Prepare: Weeks 1-4; Explore: Weeks 5-10; Realize: Weeks 11-26 |
| Approval | Project sponsor and PMO sign-off required before Explore begins |

### Business case template

Walks through the cost-benefit analysis in a format the finance team can read. I have had clients get programme approval on the first submission using this structure, because the numbers are clear and the assumptions are written down.

One rule I hold to: the system integrator who will deliver the work should not write this document. Their incentive is to start. Yours is to finish. My [SAP business case template](/build-a-winning-sap-business-case-template-implementation-guide/) goes deeper on the benefits model.

| Section | Details |
|---|---|
| Owner and summary | CFO or programme director; why now, what changes, what stays the same |
| Problem statement | Specific operational issues (close cycle length, manual workarounds, system age) |
| Proposed approach | Greenfield / brownfield / selective, with scope summary |
| Benefits | Quantified: days off close cycle, FTE savings, error rate reduction, audit risk reduction |
| Cost and funding | Implementation, licence or subscription, internal resource time, contingency; budget source |
| Risks | Top three, with probability and impact |
| Recommendation | Proceed / conditional proceed / defer, with rationale |

### Stakeholder identification matrix

Maps everyone affected by the implementation and their level of influence. It tells you at a glance who needs weekly updates and who just needs a heads-up before go-live.

| Stakeholder | Role | Interest | Influence | Engagement |
|---|---|---|---|---|
| Group CFO | Executive sponsor | Programme ROI, finance close improvement | High | Monthly SteerCo, weekly written update |
| IT Director | Technical owner | System stability, integration, security | High | Weekly programme board, daily during Realize |
| Finance Director | Key process owner | FI/CO design, close process | High | Workshops in Explore, UAT sign-off |
| Plant Managers | Impacted users | MM/PP process changes | Medium | Monthly change comms, UAT participation |
| End users (AP/AR) | Operators | Transaction-level changes | Low | Training, hypercare support |
| Internal Audit | Governance | Traceability, controls, compliance | Medium | Artefact reviews at quality gates |

Use the same matrix to plan the Prepare workshops that capture high-level requirements by department. Number those requirements in the format you will use in Explore (REQ-001 and so on), so nothing gets renumbered later and the trace back to the original ask survives.

## Explore phase templates

Explore is where the implementation takes shape. These templates expose the gap between what SAP does out of the box and what the business needs.

### Requirements mapping and fit-gap template

Requirements mapping captures business needs by department and traces each one to a system component and a test case. I have seen companies skip it and end up with systems nobody uses, because the build was based on what consultants assumed rather than what the business said.

The fit-gap analysis then shows where standard SAP meets each need and where it does not. It is a real eye-opener for most of my clients. I like watching the moment a team realises it can use standard functionality instead of expensive custom code.

I keep both in one sheet, with a column for the resolution path. On S/4HANA every gap needs an explicit answer: standard configuration, key user extension, developer extension in the system, or a side-by-side extension on SAP BTP. Classic modifications to SAP code are the most expensive answer and should need a named approver.

| Req ID | Requirement | SAP component | Fit / Gap | Resolution path | Test ref |
|---|---|---|---|---|---|
| REQ-001 | Automated month-end close journals | FI-GL, period-end closing | Fit | Configure recurring document templates | TC-001 |
| REQ-002 | Purchase order approval via Fiori | MM purchasing, Fiori approval app | Gap (not in ECC) | Standard S/4HANA app and workflow configuration | TC-003 |
| REQ-003 | Intercompany billing automation | SD billing, FI integration | Gap | Intercompany billing configuration | TC-010 |
| REQ-004 | Batch job monitoring | Application Jobs app | Fit | Standard app | TC-015 |
| REQ-005 | Supplier self-service portal | SAP Ariba or supplier portal | Gap | Ariba integration | TC-020 |
| REQ-006 | GDPR-compliant data archiving | ILM, data archiving | Gap | ILM policy configuration | TC-025 |
| REQ-007 | Real-time cost centre reporting | CO, embedded analytics or SAC | Gap | Embedded analytics or SAC live connection | TC-030 |
| REQ-008 | Support 500 concurrent users | HANA sizing | Gap (300 tested) | Sizing review and infrastructure uplift | TC-035 |

## Realize phase templates

This is the build phase. These templates are the audit trail for every configuration decision, every development and every test result.

### Configuration tracking template

Records every system change: who made it, why, and which transport it went in. When something breaks later, you trace the issue in minutes rather than days.

1. Configuration ID and module: [e.g., MM-CONF-001, MM]
2. IMG path and configuration object: [e.g., Table T161, PO document types]
3. Purpose and business process affected
4. Configured by and date
5. Transport request number: [e.g., DEVK900123]
6. Key values: before and after
7. Linked test cases
8. Validation and approval status

### Custom development register

Every custom object gets a row before anyone writes code. One of my clients cut their custom code by 30% because the register showed where standard SAP would work just fine.

| Dev ID | Object | Description | Developer | Effort (hrs) | Status | Extension type |
|---|---|---|---|---|---|---|
| CD-001 | Fiori tile: cost centre overview | Real-time CO reporting tile for finance | Fiori developer | 12 | Complete | Developer extension |
| CD-002 | Intercompany billing report | Report for IC reconciliation | ABAP developer | 20 | In progress | Developer extension |
| CD-004 | Vendor payment status app | Fiori app for AP payment queries | BTP developer | 10 | Pending QA | Side-by-side on BTP |
| CD-005 | Goods receipt notification | Email trigger on goods receipt posting | Integration developer | 24 | Planned | Event-based, on BTP |

### Testing strategy template

Puts all testing plans in one place: who tests what, when, in which environment, and to what standard.

| Section | Details |
|---|---|
| Scope | Functional, integration, regression, performance, UAT across in-scope modules (penetration testing sits with InfoSec) |
| Environments | DEV, QA, UAT (pre-production), staging for final validation |
| Tools | Test management in SAP Cloud ALM or Jira/Xray; automation with Tricentis Tosca or similar; performance with JMeter or LoadRunner |
| Defect lifecycle | New, In progress, Resolved, Verified, Closed; severity and priority set at triage |
| Exit criteria | All critical defects closed; UAT sign-off received; regression pass rate at least 95%; performance benchmarks met |

### Data migration planning template

Data migration is the workstream most likely to hurt you. This template breaks it into steps that expose data quality issues before cutover rather than during it. The [data migration failure patterns](/why-sap-data-migration-fails-and-how-to-fix-it/) article covers what goes wrong when it is skipped.

| Section | Details |
|---|---|
| Scope | Customer master, vendor master, open items, material master, stock balances, cost centre hierarchies |
| Source systems | ECC 6.0 EHP 7 (primary); legacy HR system (employee cost centre assignments) |
| Target system | S/4HANA (current release) |
| Mapping and rules | Customers and vendors to Business Partner; cost centres to the new hierarchy; remove invalid bank details; merge duplicates |
| Migration tools | SAP S/4HANA Migration Cockpit (primary); Migration Object Modeler for custom objects; scripts for pre-processing |
| Load strategy | Mock load on QA; delta migration and reconciliation; production cutover |
| Validation approach | Record counts source to target; 10% random sampling; balance reconciliation reports |
| Rollback plan | Pre-cutover backup; legacy system on standby for 48 hours |

## Deploy phase templates

The Deploy phase is when you go live. These templates turn a chaotic weekend into a managed event.

### Cutover planning template

Maps the blackout window hour by hour. Every task, every owner, every start time. Your team should never be standing around at 2 AM wondering what to do next.

Agree four things before you write the task list: the window (for example Friday 22:00 to Saturday 06:00), the rollback trigger, how fast the legacy system can be reactivated, and the smoke tests that prove the new system works. Then the task sequence:

| Step | Description | Owner | Start time | Status |
|---|---|---|---|---|
| 1 | Freeze ECC system (no postings) | Basis | 22:00 | Pending |
| 2 | Final data extract and reconciliation | Data migration lead | 22:30 | Pending |
| 3 | Run production migration load | DBA | 23:00 | Pending |
| 4 | Import remaining transports to production | Basis | 00:30 | Pending |
| 5 | DNS and load balancer switch to S/4HANA | Network | 01:30 | Pending |
| 6 | Smoke test: FI posting, goods receipt, sales order | QA lead | 02:00 | Pending |
| 7 | Business confirmation and go/no-go decision | Programme director | 03:00 | Pending |
| 8 | Open system to business users | Basis | 06:00 | Pending |

### Go-live readiness assessment

Decides whether you are actually ready to switch. I have had clients delay go-live based on this assessment, and they thanked me later.

| Area | Checks (each answered yes or no, with evidence) |
|---|---|
| Functional | Key processes tested; cross-module scenarios complete; open P1/P2 defects listed; key users confirm readiness |
| Data | Master data loads complete; transaction data validated; reconciliation reports approved; legacy freeze confirmed |
| Technical | Cutover plan approved; transports in production; batch jobs scheduled; monitoring configured |
| People | Training coverage %; access roles validated; hypercare team staffed; support plan communicated |
| Decision | Critical risks and mitigations listed; Go / No-go / Conditional; approved by name, role and date |

## Run phase templates

After go-live the work changes shape. These templates carry the system and the team through hypercare and into steady state.

### Post-implementation support template

Organises how you handle issues after launch. Without it, every problem becomes a P1.

| Section | Details |
|---|---|
| Hypercare window | Weeks 1-4 after go-live: 24/7 coverage |
| Support channels | ServiceNow incident queue (primary); dedicated chat channel; phone bridge for P1 issues |
| Support tiers | 1: service desk (passwords, navigation, known issues); 2: functional consultants (process queries, minor config); 3: Basis and development (system errors, performance, interfaces) |
| SLAs (response / resolution) | Critical 15 min / 2 h; High 30 min / 4 h; Medium 4 h / 1 day; Low 1 day / 3 days |
| Monitoring | SAP Cloud ALM or Solution Manager; daily error log review |
| Exit criteria | No open P1/P2 issues; all incidents documented; final handover sign-off |

### Performance monitoring template

It lets you watch system health day by day and spot slowdowns before users complain. I recently helped a company catch a database issue this way that would have crashed their system during month-end.

| Metric | Target | Tool | Alert threshold | Owner |
|---|---|---|---|---|
| Dialog response time (95th percentile) | Under 1 second | ST03 / SAP Cloud ALM | 2 seconds | Basis team |
| Background job completion | 100% per schedule | SM37 / Application Jobs | Any failed job | Ops lead |
| Database query time | Under 200ms | SAP HANA cockpit | 500ms | DBA |
| System availability | Over 99.5% | SAP Cloud ALM | Under 99% | Infrastructure |
| Interface error rate | Under 1% | SAP Integration Suite monitoring | 2% | Middleware lead |
| Login success rate | Over 98% | Security audit log | Under 95% | Security lead |
| Month-end close job runtime | Within agreed window | Job scheduler | Over 30% above baseline | Finance ops |

## Quality gates

Quality gates stop a problem in one phase from becoming expensive rework in the next. My guide to [SAP quality gates](/sap-quality-gates-implementation/) covers how to set them up. Here is why they matter.

Executive sign-off before go-live should not be a rubber stamp. On one project I worked on, the CEO caught a big problem during the go-live review that would have disrupted the finance team's work.

Set pass/fail criteria at each gate. "95% of regression tests must pass." "All FI integration scenarios are green." Criteria like these give you a defensible basis to hold the line when the business wants to launch on a date regardless of quality.

On one of my projects, the quality gate stopped us when only 75% of integration tests had passed. We fixed the issues first instead of rushing ahead. That saved the client about €100,000 in emergency fixes after launch.

A gate the sponsor can overrule with one phone call is not a gate. Write down who can waive it before you need to.

## Frequently asked questions

<details>
<summary>What is the SAP Activate methodology?</summary>

SAP Activate is SAP's implementation methodology for S/4HANA and its other cloud products. It runs in six phases (Discover, Prepare, Explore, Realize, Deploy, Run) and combines SAP Best Practices content, guided configuration and agile delivery.

The task lists and deliverable templates for each deployment scenario are published in the SAP Activate Roadmap Viewer.

</details>

<details>
<summary>Which SAP Activate phase has the most important templates?</summary>

Prepare. The scoping document, business case and stakeholder matrix set the foundation for every decision that follows, and they are the ones teams skip to get to configuration faster. That shortcut is the most common cause of scope disputes in Realize.

Explore comes second. Gaps in the fit-gap and requirements mapping documents surface as UAT defects months later, when fixing them costs far more than it would have in week 3 of Explore.

</details>

<details>
<summary>Can you customise SAP Activate templates?</summary>

Yes. Keep around 80% of the standard structure and change only what is specific to your context: pharmaceutical validation, public sector procurement rules, SOX controls. Add these at the start of Prepare, not in Deploy.

Do not customise the quality gate structure, the phase sequence or the mandatory artefacts (scoping document, business case, go-live readiness assessment).

</details>

<details>
<summary>Do SAP Activate templates work for both greenfield and brownfield?</summary>

Yes. The main difference is in Explore. A brownfield conversion carries existing configuration forward, so the fit-gap focuses on what has to change, which custom code standard S/4HANA can now replace, and what data cleanup is needed before conversion. A greenfield programme starts from SAP Best Practices and confirms which standard processes fit.

The cutover plan also differs. A brownfield system conversion follows a different sequence from a greenfield go-live with full data migration.

</details>

<details>
<summary>How detailed should a cutover plan be?</summary>

Hour by hour at minimum, and tighter than that for the blackout window. Every task needs a start time, an owner and a dependency.

Agree the rollback criteria before the cutover begins: which conditions trigger a return to the legacy system, who makes that call, and by what time. Rollback decisions made at 4 AM without pre-agreed criteria are where post-go-live disasters start.

</details>

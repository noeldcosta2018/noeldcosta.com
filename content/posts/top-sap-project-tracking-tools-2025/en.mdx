On a European manufacturing programme in 2023, we lost five weeks trying to figure out why transports were stuck in the QA system. The project manager updated the tracking tool every Monday. The tool showed green for the transport workstream. It showed nothing about what was happening inside the actual system.

When we finally traced the blockage, it turned out three transports had been waiting for a manual approval that nobody had assigned. The sign-off sat in someone's inbox for four weeks. The tracking tool had no visibility into the SAP transport landscape at all. It was tracking tasks. Not the work.

Across 21 SAP programmes that I have led, rescued, or watched go sideways, that pattern repeats. The tool is not a reporting mechanism. It is a visibility mechanism. If it cannot show you what is actually happening across your system landscape, you are managing a project on assumptions.

## What makes a tracking tool useful on SAP programmes

Four properties separate tools that prevent delays from tools that document them after the fact.

**SAP landscape integration.** A tool that pulls data directly from the SAP system knows the actual state of transports, test cases, workflow approvals, and change logs. A tool that relies on manual updates knows what people reported, which is often what they thought was true a week ago.

**Cross-phase coverage.** Most tools work reasonably well during the build phase. They fall apart during testing, training, and cutover. Delays compound in the final phases. If the tool does not support cutover tracking and mock run management, it is abandoning you at the highest-risk point.

**Dependency visibility.** SAP projects have hard interdependencies. Data migration feeds UAT. Cutover sequencing depends on transport order. A tool that shows task completion but not dependency chains cannot show you what a delay in one area does to three others.

**Adoption.** The most capable tool in the project fails if half the team logs their status somewhere else. Adoption comes from ease of use, from the tool showing people information they actually need, and from project leadership enforcing it.

## The four tools

### 1. SAP Cloud ALM

Cloud ALM is SAP's native application lifecycle management tool for cloud and RISE with SAP implementations. It is included with the SAP cloud subscription and connects directly to the SAP landscape.

What it does well: it pulls real-time status from transports, test case execution, and system events. It structures the project automatically against SAP Activate phases. On a 10-month European manufacturing S/4HANA implementation in 2024, the data migration team hit issues during the Realize phase. Cloud ALM flagged the delay and showed the impact on dependent tasks before the project manager had scheduled the next status meeting.

For any new S/4HANA cloud or RISE project in 2026, Cloud ALM should be the default starting point.

Where it falls short: the setup requires proper landscape connectivity. On projects where the Basis team is stretched, that connection does not always happen at the start of Prepare. By the time it is configured, the project has already been tracked in a spreadsheet for two months and nobody wants to migrate the data.

**Pricing:** included with RISE with SAP and SAP BTP subscriptions. Implementation services for full configuration run from $50,000 to $150,000 depending on landscape complexity.

### 2. Jira with BigPicture (plus Atlassian Intelligence)

Jira is the dominant project and issue tracking tool in most enterprise IT departments. BigPicture is a portfolio and programme management add-on that adds Gantt charts, dependency views, and resource management on top of Jira's native issue tracking. Atlassian Intelligence (rolled out 2024) adds AI-driven summarisation and content drafting across the Atlassian suite.

The combination works well when the organisation already runs Jira for development and support. On a GCC manufacturing programme in 2024 that I joined mid-stream, the SI had set up Cloud ALM, but the client's internal IT team was using Jira for everything else. We ended up running parallel systems. Jira showed what IT was doing. Cloud ALM showed what SAP was doing. Nobody had a single view of the whole project.

The risk with Jira is in the integration. Without a properly configured connector to the SAP landscape, it is a general-purpose project tracker with no understanding of transports, Activate phases, or SAP-specific dependencies. You can track tasks. You cannot track the system.

**Pricing:** Jira Cloud starts at $7.75 per user per month at scale. BigPicture is an additional licence from about $3.50 per user per month. Atlassian Intelligence is included with Premium/Enterprise editions. Integration consulting to connect to SAP typically adds $30,000 to $80,000.

### 3. Microsoft Project with SAP Connector (plus Microsoft Copilot)

Microsoft Project is the default tool for project managers who grew up in organisations running on Office 365. It is familiar, widely licensed, and understood by most PMOs. Microsoft Copilot in M365 (rolled out 2024) drafts status updates, meeting summaries, and stakeholder briefs from prepared data.

The SAP Connector extends Project to pull data from the SAP landscape: transport status, workflow items, test execution. The result is a hybrid: a familiar interface that non-SAP people can navigate, with SAP-specific data feeding the schedule.

Where this works: mid-market implementations where the client's PMO already owns Project licences. The internal programme manager knows the tool. The budget does not justify the setup cost for Cloud ALM configuration. The integration is narrower than Cloud ALM, but for a single-entity S/4HANA Finance and Procurement rollout, it is often enough. The Copilot overlay accelerates the status reporting work that PMOs typically spend disproportionate time on.

Where it does not work: complex multi-entity programmes with parallel workstreams, heavy transport volumes, and cross-system dependencies. The connector is not deep enough to give you real-time visibility at that scale.

**Pricing:** Microsoft Project Plan 3 runs approximately $30 per user per month. Microsoft 365 Copilot adds approximately $30 per user per month. The SAP Connector adds variable licensing. Total cost for a mid-market team of 20 with Copilot is typically $25,000 to $60,000 per year.

### 4. SAP Solution Manager

Solution Manager is the on-premise predecessor to Cloud ALM. It has been the standard SAP project and application lifecycle management tool for ECC and on-premise S/4HANA since the mid-2000s.

For complex on-premise landscapes, nothing else comes close. Solution Manager can monitor transports, document business processes in the Business Process Repository, manage test cases natively, and integrate with change management workflows. On a European manufacturing programme in 2024, the transport monitoring alone caught a critical configuration conflict three weeks before UAT that would have caused a major business process failure.

The honest trade-off: it is heavy to configure. A proper Solution Manager setup for a complex programme takes weeks of Basis and Solution Manager consultant time. Organisations that do not invest in the setup get a fraction of the value. Some project teams end up using it for transport monitoring only, which wastes most of its capability.

For organisations on RISE or moving to cloud S/4HANA, Cloud ALM is the forward path. Solution Manager's mainstream maintenance ended in 2025 with extended support to 2027. For new cloud implementations in 2026, Cloud ALM is the right choice.

**Pricing:** included with SAP software licences. Implementation and configuration services typically run $75,000 to $250,000 depending on scope.

## How AI overlays change SAP project tracking in 2026

The 2024-2025 AI rollout reached project tracking workflows. Three capabilities are useful now across the four tools.

### Joule for SAP Cloud ALM

Generates first-draft status reports, risk register updates, and phase gate evidence summaries from Cloud ALM source data. Saves 30-50% of effort on the status reporting work that previously took the longest. The drafts still require human validation; the AI extraction from the system is what gets accelerated.

### Microsoft Copilot for M365 and Project

Drafts steering committee packs, executive briefings, and stakeholder updates from Microsoft Project schedule data plus M365 source documents. Particularly useful when the tracking is in Project but the executive audience needs narrative summaries rather than Gantt charts.

### Atlassian Intelligence for Jira and Confluence

Summarises Jira issue threads, generates Confluence page content from prepared briefs, and produces stakeholder-ready status from raw ticket data. Useful when Jira holds the operational detail but the steering committee needs the narrative version.

What AI does not change: the underlying tool's SAP landscape integration depth. AI accelerates the production of status content from whatever data the tool is collecting. If the tool is collecting status reports from spreadsheets, AI produces faster status content from spreadsheets. The integration layer still matters most.

## When the tool is not the problem

I have been on programmes where the tracking tool was excellent and the project still ran poorly. The tool showed everything. The right people were not looking at it. Issues surfaced in the system three weeks before they appeared in the steering committee pack.

Tracking tools create visibility. They do not create the culture of acting on what is visible. That requires a governance structure where escalation is fast and issues are resolved rather than reported. Project leadership has to treat a red flag as a reason to act, not a reason to add a mitigation comment and move on.

The tool is necessary. It is not sufficient. The AI overlay does not change this; it accelerates the reporting from a working tool, not the response from a passive steering committee.

With BigPicture or a similar portfolio add-on, Jira can manage programme-level schedules, resource allocation, and dependency views. With a properly configured SAP connector, it can pull transport and test data. Without the connector, it is a general-purpose project tracker that happens to be running alongside an SAP programme.

Having everything in one tool reduces the context-switching cost for leadership and reduces the risk of parallel tracking systems.

Where it does not make sense: the programme is a dedicated SAP implementation with no pre-existing Jira investment. In that case, starting with Cloud ALM or Solution Manager is more efficient than building Jira integration from scratch.

The most common Jira failure on SAP programmes: the connector is never set up properly because no one owns the integration between the Jira admin team and the Basis team. The result is a project tracked in Jira with no SAP system visibility.

Delays on SAP programmes accumulate before they are visible. A transport stuck in the approval queue for a week does not appear in a manual status report until the next steering committee. By then, dependent testing has already started late.

Tracking tools that connect to the SAP landscape show the actual state of the system in real time. Transport status is not what someone reported in the morning standup. It is what the system knows at the moment the project manager looks at the dashboard.

The delay reduction is most significant in the Realize and Deploy phases, when transport volumes are high and testing is running in parallel. These are also the phases where manual tracking breaks down fastest, because the number of moving parts exceeds what a weekly status meeting can cover.

The specific scenarios where Solution Manager leads: multi-entity ECC implementations with heavy customisation and complex transport landscapes; programmes that need to document business processes in the Business Process Repository for governance or audit purposes; organisations that have invested in Solution Manager configuration over multiple years and have a team that knows how to use it.

Cloud ALM is the forward path for organisations moving to RISE or cloud S/4HANA. SAP's investment in the product roadmap is behind Cloud ALM. Solution Manager's mainstream maintenance ended in 2025 with extended support to 2027. For any new cloud implementation in 2026, starting on Cloud ALM makes more sense than learning Solution Manager.

The transition scenario: an organisation running ECC with Solution Manager migrating to S/4HANA on RISE. During the migration programme, both tools may run in parallel, with Solution Manager covering the ECC landscape and Cloud ALM covering the new S/4HANA environment.

<details>
<summary>What should a project manager look for when evaluating SAP tracking tools?</summary>

Four criteria matter more than the feature comparison matrix.

SAP landscape integration. Does the tool connect to the actual SAP system or does it rely on manual data entry? A tool that shows real transport status caught a four-week approval blockage on one of my projects. A tool that shows what someone typed into a status field would have missed it.

Cross-phase support. Does the tool work in cutover and hypercare, or does it become irrelevant in the final phases? Most tools are built for the build phase. The highest-risk phases are Deploy and Run.

Adoption. Is the tool simple enough that the full project team will use it consistently? A powerful tool that half the team ignores creates a worse situation than a simpler tool that everyone uses, because the powerful tool creates a false picture of completeness.

Cost of connection. What is the real cost of setting up the SAP integration? The tool's licence is often the smallest number. The integration consulting and Basis time to configure the connection is where the real investment is. Get that number before committing.

</details>

<details>
<summary>Can you use multiple SAP tracking tools on the same programme?</summary>

You can. It usually creates problems.

The specific problem: two tools show different versions of the status for the same workstream. The SteerCo sees the Cloud ALM data. The business programme manager sees the Jira data. They are not the same. Nobody is sure which one is right. Escalations slow down because the first conversation is always about which system to believe.

Parallel tracking tools are most common when the client's internal team has invested in Jira or Microsoft Project and the SI brings Cloud ALM or Solution Manager. The result is two views of the project that are never fully reconciled.

The governance fix: designate one tool as the single source of truth for each category of information. SAP system state (transports, test execution) lives in Cloud ALM or Solution Manager. Programme schedule and business workstreams can live in Jira or Project if that is the client's standard. The two views are synchronised at defined intervals. Nobody treats either tool as the complete picture in isolation.

This is not elegant. But it is more manageable than expecting every internal PMO to abandon their existing tools and adopt SAP-native tooling mid-project.

</details>

The best SAP project tracking tool in 2026 is not the one with the longest feature list or the latest AI overlay. It is the one whose SAP landscape integration shows the real state of the system, whose adoption discipline is enforced from project kickoff, and whose data the steering committee actually acts on when red signals appear. AI accelerates the reporting work, which matters. The integration layer and the response discipline matter more. Build for the integration first. The AI tooling is the easy part to add later.

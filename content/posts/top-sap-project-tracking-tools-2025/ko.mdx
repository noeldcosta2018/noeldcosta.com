대부분의 신규 S/4HANA 프로그램에 맞는 추적 도구는 SAP Cloud ALM입니다. 트랜스포트, 테스트, 단계를 SAP 시스템에서 직접 읽어 오며, Enterprise Support나 클라우드 구독을 보유한 고객은 라이선스 비용을 내지 않습니다. Jira나 Microsoft의 Planner와 Project는 조직이 이미 그것으로 운영되고 있고 통합을 책임지는 사람이 있을 때만 의미가 있습니다. SAP Solution Manager는 복잡한 온프레미스 환경에는 여전히 맞지만 메인스트림 유지보수가 2027년에 끝납니다. 이 가이드는 도구를 고르거나 바로잡으려는 프로그램 매니저와 PMO 리드를 위한 것입니다. 네 가지 선택지를 비교하고 체크리스트로 마무리합니다. 중요한 시험은 이것입니다. 도구가 시스템 안에서 벌어지는 일을 보여 주는가, 아니면 사람들이 보고한 내용만 보여 주는가?

제 초기 S/4HANA 프로젝트 중 하나에서는 트랜스포트가 왜 QA에서 멈춰 있는지 알아내려고만 5주를 잃었습니다. 아무도 명확한 그림을 갖고 있지 않았습니다. 추적 도구는 작업 목록을 추적했을 뿐, 실제 일을 추적하지는 않았습니다.

수년간 알게 된 사실은, 진짜 문제는 대개 늦어진 작업보다 더 깊은 곳, 곧 시스템을 볼 수 있는 추적이 없다는 데 있다는 것입니다. 도구가 시스템 환경 전반에서 벌어지는 일을 보여 주지 못한다면 가정에 의존해 관리하고 있는 것입니다.

## SAP 프로그램에서 추적 도구가 쓸모 있으려면

지연을 막아 주는 도구와 지연을 나중에 기록만 하는 도구를 가르는 속성은 네 가지입니다.

**SAP 시스템과의 통합.** 시스템을 읽는 도구는 트랜스포트, 테스트 실행, 승인의 실제 상태를 압니다. 수동 업데이트로 채워지는 도구는 사람들이 보고한 내용을 알 뿐이고, 그것도 대개 일주일 늦습니다.

**후반 단계의 포괄성.** 대부분의 도구는 구축 단계는 감당합니다. 테스트, 컷오버, 하이퍼케어에서 무너지는데, 지연이 겹쳐 쌓이는 곳이 바로 거기입니다. 모의 전환(mock run)과 컷오버 작업을 추적하지 못하는 도구는 가장 위험한 지점에서 여러분을 버립니다.

**의존 관계의 가시성.** 데이터 마이그레이션 결과가 UAT로 이어집니다. 컷오버 순서는 트랜스포트 순서에 달려 있습니다. 작업 완료는 보여 주지만 의존 관계 체인은 보여 주지 못하는 도구는, 지연 하나가 다른 워크스트림 셋에 어떤 영향을 주는지 보여 줄 수 없습니다.

**정착.** 가장 뛰어난 도구도 팀의 절반이 다른 곳에 상태를 기록하면 실패합니다. 정착은 사용하기 쉬움, 사람들에게 필요한 정보를 보여 주는 것, 그리고 리더십이 사용을 고집하는 데서 나옵니다.

## 네 가지 도구

### 1. SAP Cloud ALM

[SAP Cloud ALM](https://support.sap.com/en/alm/sap-cloud-alm.html)은 클라우드 및 하이브리드 환경을 위한 SAP의 애플리케이션 라이프사이클 관리 도구입니다. 라이선스는 없습니다. Enterprise Support가 포함된 클라우드 구독, 클라우드 에디션(RISE와 GROW 계약이 해당됩니다), 또는 온프레미스 Enterprise Support를 보유한 고객은 고객 번호당 테넌트 하나를 프로비저닝할 수 있습니다. Standard Support 고객은 그런 클라우드 구독을 함께 보유하지 않는 한 대상이 아닙니다.

잘하는 점: SAP Activate 단계를 기준으로 프로젝트를 구조화하고, 테스트 실행과 트랜스포트를 포함해 시스템에서 상태를 읽어 옵니다. 저는 제조 기업의 S/4HANA를 구축하면서 10개월 프로젝트 전체를 Cloud ALM으로 추적했습니다. Realize 단계에서 데이터 마이그레이션에 문제가 생겼습니다. 도구가 지연을 표시했고 후속 작업에 미치는 영향을 계산해 주었습니다.

부족한 점: 시스템에 제대로 연결되어야 합니다. Basis 팀이 빠듯하면 그 연결은 Prepare 시작 시점에 이루어지지 않습니다. 설정이 끝났을 때는 프로젝트가 이미 두 달 동안 스프레드시트에서 살았고, 아무도 그 이력을 옮기고 싶어 하지 않습니다.

신규 S/4HANA 클라우드나 RISE 프로그램이라면 여기서 시작하십시오. 비용은 라이선스가 아닙니다. Basis와 구성 공수입니다.

### 2. 포트폴리오 애드온을 갖춘 Jira

Jira는 많은 기업 IT 부서의 기본 이슈 추적기입니다. BigPicture 같은 포트폴리오 애드온은 간트 차트, 의존 관계, 리소스 보기를 더해 줍니다. 현재 Rovo라는 브랜드로 불리는 Atlassian의 AI는 모든 유료 Jira 플랜에 월간 크레딧 한도와 함께 포함되며, 티켓을 요약하고 상태 업데이트 초안을 작성합니다.

조직이 이미 개발과 지원에 Jira를 쓰고 있을 때 효과가 있습니다. 시스템 통합업체가 Cloud ALM을 구성하는데 고객의 IT 팀은 나머지 모두를 Jira로 운영하면, 병렬 시스템이 생깁니다. Jira는 IT가 하는 일을 보여 줍니다. Cloud ALM은 SAP가 하는 일을 보여 줍니다. 전체를 한눈에 보는 사람은 없습니다.

위험은 통합입니다. Jira는 트랜스포트나 Activate 단계를 기본적으로 이해하지 못합니다. SAP 환경과의 통합을 구성하지 않으면 작업은 추적해도 시스템은 추적하지 못합니다.

### 3. Microsoft Planner와 Project

많은 PMO가 Microsoft Project를 쓰며 자랐고, 재무와 운영 리더들에게 여전히 익숙합니다. 2026년에 제품 라인이 바뀌었습니다. Microsoft는 [2026년 9월 30일에 Project Online을 종료](https://techcommunity.microsoft.com/blog/plannerblog/microsoft-project-online-is-retiring-what-you-need-to-know/4450558)했고 Planner and Project Plan 5의 신규 판매를 중단했습니다. 데스크톱 일정 관리가 필요한 고객은 Planner and Project Plan 3으로 안내되며, 정가는 사용자당 월 $30입니다. 추가 라이선스인 Microsoft 365 Copilot은 계획과 관련 문서에서 상태 업데이트와 운영위원회 자료 초안을 작성합니다.

Microsoft 도구에서 SAP로 이어지는 깊은 표준 연결은 없습니다. 트랜스포트나 테스트 상태를 계획에 넣으려면 서드파티 커넥터나 자체 통합이 필요합니다. 고객 PMO가 이미 라이선스를 보유한 단일 법인 S/4HANA 재무 및 구매 롤아웃이라면 그 정도로 충분할 수 있습니다. 트랜스포트 물량이 많고 시스템 간 의존 관계가 있는 다중 법인 프로그램에는 깊이가 부족합니다.

PMO가 Project Online으로 운영되고 있었다면, 프로그램 베이스라인을 확정하기 전에 후속 제품으로의 이전이 끝났는지 확인하십시오.

### 4. SAP Solution Manager

[SAP Solution Manager 7.2](https://support.sap.com/en/alm/solution-manager.html)는 Cloud ALM의 온프레미스 전신으로, 온프레미스 유지보수 계약에 포함되어 있습니다. 복잡한 온프레미스 환경에서는 여전히 가장 깊이 들어갑니다. 트랜스포트 모니터링, 프로세스 문서화, 네이티브 테스트 관리, 변경 통제입니다. 최근 한 프로젝트에서 Solution Manager는 충돌하는 트랜스포트가 품질 테스트 시스템으로 임포트되기 전에 경고해 주었습니다. 풀어내는 데 며칠이 걸렸을 구성 충돌을 막은 것입니다.

트레이드오프는 설정 공수입니다. 제대로 구성하려면 Basis와 Solution Manager 전문가의 시간이 몇 주 듭니다. 투자를 건너뛴 팀은 트랜스포트 모니터링에만 쓰다가 대부분의 기능을 낭비합니다.

메인스트림 유지보수는 2027년 말에 끝납니다. 연장 유지보수는 Business Suite 7 연장 유지보수를 선택한 고객에 한해 일부 기능에 대해 2030년까지 이어집니다. SAP의 공식 안내는 2028년 이전에 Cloud ALM으로 옮기라는 것입니다. 신규 프로그램이라면 이미 Solution Manager를 잘 운영하고 있고 프로그램이 그 기한이 닫히기 전에 끝나는 경우에만 선택하십시오.

## AI가 추적에서 바꾸는 것

이제 네 도구 모두 AI 레이어가 있습니다. SAP는 Cloud ALM에 Joule을 추가했고, 알림을 요약하고 일상 언어 프롬프트로 모니터링 대시보드를 만드는 운영용 에이전트도 포함됩니다. Microsoft 365 Copilot은 계획에서 서술형 업데이트 초안을 작성합니다. Atlassian의 Rovo는 Jira 스레드를 요약하고 Confluence 페이지 초안을 작성합니다.

AI가 바꾸지 못하는 것은 통합의 깊이입니다. AI는 도구가 가진 데이터로 상태 보고서를 쓰는 속도를 높일 뿐입니다. 도구가 스프레드시트로 채워진다면 AI는 스프레드시트 요약을 더 빨리 쓸 뿐입니다. 통합을 먼저 구축하십시오. AI 레이어는 나중에 더하기 쉬운 부분입니다.

## 선정 체크리스트

도구를 확정하기 전에 이 질문들을 던져 보십시오.

1. 도구가 SAP 시스템에서 트랜스포트, 테스트, 승인 상태를 읽어 옵니까, 아니면 사람이 입력하는 데 의존합니까?
2. 구축뿐 아니라 모의 마이그레이션, 컷오버 작업, 하이퍼케어 티켓도 추적합니까?
3. 워크스트림 전반의 의존 관계 체인을 보여 줄 수 있습니까?
4. 도구와 SAP 환경 사이의 통합은 누가 책임집니까? 이름으로 답하십시오.
5. 실제 설정 비용은 얼마입니까? 라이선스는 가장 작은 숫자인 경우가 많고, Basis와 통합에 드는 시간이 실제 투자입니다.
6. 현업 리더를 포함해 팀 전체가 쓰겠습니까?
7. 두 도구가 공존해야 한다면, 시스템 상태의 기준 정보원은 어느 쪽이고 비즈니스 일정의 기준 정보원은 어느 쪽입니까?

추적이 거버넌스에 어떻게 연결되는지는 제 [SAP 프로젝트를 정상 궤도로 되돌리기](/ko/project-planning-and-control-get-sap-projects-back-on-track/) 가이드를 참고하십시오.

## 문제가 도구가 아닐 때

프로젝트 팀이 추적 도구가 너무 복잡하다는 이유로 무시하고 별도의 스프레드시트를 쓰는 경우를 가끔 봅니다. 리더십이 알아차릴 즈음에는 시스템 구성이 일정보다 3주 늦어 있습니다.

도구는 가시성을 만들어 줍니다. 그것에 따라 행동하는 습관까지 만들어 주지는 않습니다. 그러려면 적신호를 완화 조치 코멘트를 달고 넘어갈 이유가 아니라 행동할 이유로 받아들이는 [운영위원회](/ko/creating-an-effective-sap-project-steering-committee/)가 필요합니다.

## 자주 묻는 질문

<details>
<summary>SAP Cloud ALM이란 무엇이며 무료입니까?</summary>

SAP Cloud ALM은 SAP 시스템을 구현하고 운영하기 위한 SAP의 애플리케이션 라이프사이클 관리 도구입니다. 별도의 라이선스는 없습니다. SAP Enterprise Support 또는 Product Support for Large Enterprises를 보유한 고객은 고객 번호당 테넌트 하나를 프로비저닝할 수 있습니다. Enterprise Support가 포함된 클라우드 구독, 곧 RISE와 GROW를 포함한 클라우드 에디션을 보유한 고객도 마찬가지입니다. 실제 비용은 연결하고 구성하는 공수입니다.

</details>

<details>
<summary>Jira는 SAP 프로젝트 추적에 쓸 만합니까?</summary>

작업과 이슈 추적에는 그렇습니다. 트랜스포트, SAP Activate 단계, SAP 의존 관계는 기본적으로 이해하지 못합니다. 포트폴리오 애드온과 구성된 통합이 있으면 프로그램 일정을 관리하고 일부 SAP 데이터를 가져올 수 있습니다. 조직이 나머지 모든 것에 이미 Jira를 쓰고 있을 때 사용하십시오. 기존 Jira 투자가 없는 전담 SAP 프로그램이라면 Cloud ALM이 더 효율적인 출발점입니다.

</details>

<details>
<summary>Microsoft Project Online을 대체한 것은 무엇입니까?</summary>

Microsoft는 2026년 9월 30일에 Project Online을 종료했습니다. 데스크톱 일정 관리가 필요한 고객에게 Microsoft는 Project 데스크톱 애플리케이션이 포함된 Planner and Project Plan 3을 안내합니다. Planner and Project Plan 5는 더 이상 신규 고객에게 판매되지 않습니다. PMO가 SAP 프로그램을 Project Online으로 추적했다면, 새 계획에 의존하기 전에 이전이 끝났는지와 이력이 옮겨졌는지 확인하십시오.

</details>

<details>
<summary>Cloud ALM 대신 SAP Solution Manager를 써야 하는 때는 언제입니까?</summary>

세 가지가 모두 참일 때입니다. 복잡한 온프레미스 ECC 또는 S/4HANA 환경을 운영하고 있습니다. 이미 Solution Manager가 구성되어 있고 이를 아는 팀이 있습니다. 그리고 프로그램이 2027년 메인스트림 유지보수 종료 전에 끝납니다. ECC에서 S/4HANA로 옮기는 동안에는 둘이 병행될 수 있습니다. 기존 환경은 Solution Manager로, 새 환경은 Cloud ALM으로 운영하는 것입니다. SAP는 2028년 이전에 Cloud ALM으로의 이전을 완료할 것을 권고합니다.

</details>

<details>
<summary>추적 도구는 SAP 프로그램의 지연을 어떻게 줄입니까?</summary>

주간 상태 회의보다 먼저 문제를 보여 줌으로써 줄입니다. 승인 대기열에 멈춰 있는 트랜스포트는 누군가 알아차리기 전까지 수동 보고서에 나타나지 않습니다. 시스템을 읽는 도구는 같은 날 보여 줍니다. 앞서 말한 초기 프로젝트에서도 실제 트랜스포트 상태를 읽는 도구가 있었다면 5주를 잃기 전에 정체를 보여 주었을 것입니다. 이점은 트랜스포트 물량이 많고 테스트가 병렬로 진행되는 Realize와 Deploy 단계에서 가장 큽니다.

</details>

<details>
<summary>같은 SAP 프로그램에서 추적 도구를 둘 이상 써도 됩니까?</summary>

쓸 수는 있지만 대개 문제가 생깁니다. 두 도구가 같은 워크스트림에 서로 다른 상태를 보여 주고, 모든 에스컬레이션이 어느 쪽이 맞는지에 대한 논쟁으로 시작됩니다. 둘을 써야 한다면 각각에 분명한 역할을 주십시오. 시스템 상태(트랜스포트, 테스트)는 Cloud ALM이나 Solution Manager에 둡니다. 비즈니스 일정은 고객의 표준이라면 Jira나 Planner에 둘 수 있습니다. 정해진 주기로 동기화하십시오.

</details>

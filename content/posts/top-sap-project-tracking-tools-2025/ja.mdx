新規のS/4HANAプログラムなら、追跡ツールの答えはたいていSAP Cloud ALMです。トランスポート、テスト、フェーズをSAPシステムから直接読み取り、Enterprise Supportまたはクラウドサブスクリプションをお持ちのお客様には、ライセンス料がかかりません。JiraやMicrosoftのPlannerとProjectが意味を持つのは、組織がすでにそれらで動いていて、連携に責任を持つ人がいる場合だけです。SAP Solution Managerは複雑なオンプレミス環境にはいまも合いますが、メインストリーム保守は2027年に終了します。このガイドは、ツールを選ぶ、あるいは立て直すプログラムマネージャーとPMOリードに向けたものです。4つの選択肢を比較し、最後にチェックリストを付けています。重要なテストは、ツールがシステムの中で何が起きているかを見せてくれるか、それとも人が報告したことしか見せてくれないか、です。

私の初期のS/4HANAプロジェクトのひとつで、トランスポートがなぜQAで止まっているのかを突き止めるだけで、5週間を失いました。誰にも全体像が見えていませんでした。追跡ツールが追っていたのは、タスクであって、作業ではありませんでした。

長年の間に分かったのは、本当の問題は、遅れたタスクよりも深いところにあることが多い、ということです。システムが見える追跡がないことです。システム環境全体で何が起きているかをツールが示せないなら、憶測で管理していることになります。

## SAPプログラムで追跡ツールが役立つ条件

遅延を防ぐツールと、後から記録するだけのツールを分ける性質が、4つあります。

**SAPシステムとの連携**。システムを読み取るツールは、トランスポート、テスト実行、承認の実際の状態を知っています。手入力で更新されるツールが知っているのは、人が報告したことで、しかもたいてい1週間遅れです。

**終盤のフェーズのカバー**。たいていのツールは、構築段階はこなします。テスト、カットオーバー、ハイパーケアで破綻します。遅延が積み重なるのは、そこです。モックランやカットオーバーのタスクを追跡できないツールは、最もリスクの高い場面で、あなたを見捨てます。

**依存関係の見える化**。データ移行はUATの前提になります。カットオーバーの順序は、トランスポートの順序に依存します。タスクの完了は示しても、依存関係の連鎖を示さないツールは、1つの遅れが、ほかの3つのワークストリームに何をもたらすかを示せません。

**定着**。チームの半分が別の場所にステータスを記録していれば、どれほど高機能なツールも失敗します。定着は、使いやすさ、人が必要とする情報を見せること、そして経営陣が使うことを徹底することから生まれます。

## 4つのツール

### 1. SAP Cloud ALM

[SAP Cloud ALM](https://support.sap.com/en/alm/sap-cloud-alm.html)は、クラウドとハイブリッドの環境向けにSAPが提供する、アプリケーションライフサイクル管理ツールです。ライセンスはありません。Enterprise Supportを含むクラウドサブスクリプション（クラウドエディション。RISEとGROWの契約は該当します）をお持ちのお客様、またはオンプレミスのEnterprise Supportをお持ちのお客様は、お客様番号ごとに1テナントを開設できます。Standard Supportのお客様は、そうしたクラウドサブスクリプションも併せて契約していない限り、対象外です。

得意なのは、SAP Activateのフェーズに沿ってプロジェクトを構造化し、テスト実行やトランスポートを含むステータスをシステムから読み取ることです。私は、製造業の会社のS/4HANA導入で、10か月のプロジェクト全体をCloud ALMで追跡しました。Realizeの間に、データ移行で問題が起きました。ツールは遅れを検知し、依存するタスクへの影響を計算しました。

弱点は、システムへの適切な接続が必要なことです。Basisチームが手一杯だと、その接続はPrepareの開始時には実現しません。接続が整う頃には、プロジェクトは2か月間スプレッドシートの上で動いていて、誰もその履歴を移したがりません。

新規のS/4HANAクラウドまたはRISEのプログラムなら、ここから始めてください。費用になるのはライセンスではありません。Basisと設定の工数です。

### 2. ポートフォリオアドオンを加えたJira

Jiraは、多くの企業のIT部門で標準の課題管理ツールです。BigPictureのようなポートフォリオアドオンを加えると、ガントチャート、依存関係、リソースのビューが使えます。AtlassianのAIは、現在Rovoの名称で、有料のJiraプランすべてに月間のクレジット枠付きで含まれ、チケットの要約やステータス更新の下書きを行います。

組織が、開発とサポートにすでにJiraを使っていれば、機能します。システムインテグレーターがCloud ALMを設定する一方で、クライアントのIT部門がそれ以外をすべてJiraで動かしていると、並行するシステムができあがります。JiraはITが何をしているかを示し、Cloud ALMはSAPが何をしているかを示します。誰にも、1つの全体像が見えません。

リスクは連携です。Jiraには、トランスポートやActivateのフェーズを理解する標準機能がありません。SAP環境への連携を設定しなければ、タスクは追えても、システムは追えません。

### 3. Microsoft Planner and Project

多くのPMOは、Microsoft Projectとともに育ち、財務やオペレーションのリーダーにとっても、いまなお馴染みがあります。製品ラインは2026年に変わりました。Microsoftは、[2026年9月30日にProject Onlineを終了し](https://techcommunity.microsoft.com/blog/plannerblog/microsoft-project-online-is-retiring-what-you-need-to-know/4450558)、Planner and Project Plan 5の新規販売も停止しました。デスクトップでのスケジュール管理が必要なお客様には、1ユーザーあたり月額30ドルで提供されるPlanner and Project Plan 3が案内されています。アドオンライセンスのMicrosoft 365 Copilotは、計画と関連文書から、ステータス更新やステアリング資料の下書きを作成します。

MicrosoftのツールからSAPへの、深い標準連携はありません。トランスポートやテストのステータスを計画に取り込むには、サードパーティのコネクタか、自社での連携開発が必要です。クライアントのPMOがすでにライセンスを持っている、単一法人のS/4HANA財務・調達ロールアウトなら、それで十分かもしれません。トランスポートの量が多く、システム間の依存関係がある複数法人のプログラムには、深さが足りません。

PMOがProject Onlineで動いていたなら、プログラムのベースラインを設定する前に、後継への移行が完了していることを確認してください。

### 4. SAP Solution Manager

[SAP Solution Manager 7.2](https://support.sap.com/en/alm/solution-manager.html)は、Cloud ALMのオンプレミスの前身で、オンプレミスの保守契約に含まれています。複雑なオンプレミス環境では、いまも最も深いところまで対応します。トランスポートの監視、プロセスのドキュメント化、標準のテスト管理、変更管理です。最近のあるプロジェクトでは、Solution Managerが、品質テストにインポートされる前に、競合するトランスポートを知らせてくれました。そのおかげで、解きほぐすのに何日もかかったはずの設定の競合を防げました。

トレードオフは、セットアップの工数です。適切な設定には、BasisとSolution Manager専門家の、何週間もの時間がかかります。その投資を省いたチームは、トランスポートの監視にしか使わず、機能の大半を無駄にします。

メインストリーム保守は、2027年末に終了します。延長保守は、Business Suite 7の延長保守を契約するお客様について、選ばれた機能に限り、2030年まで続きます。SAP自身のガイダンスは、2028年より前にCloud ALMへ移行することです。新規のプログラムでは、すでにSolution Managerをうまく運用していて、プログラムがその期限が閉じる前に終わる場合だけ、選んでください。

## AIが追跡で変えること

4つのツールすべてに、いまはAIの層があります。SAPはCloud ALMにJouleを追加し、アラートを要約し、普通の言葉の指示から監視ダッシュボードを作る、運用向けのエージェントも含まれます。Microsoft 365 Copilotは、計画から説明文のステータス更新を下書きします。AtlassianのRovoは、Jiraのスレッドを要約し、Confluenceのページの下書きを作ります。

AIが変えないのは、連携の深さです。AIが速めるのは、ツールが持つデータからステータスを書く作業です。ツールがスプレッドシートから情報を得ているなら、AIはスプレッドシートの要約を速く書くだけです。先に連携を作ってください。AIの層は、あとから足せる簡単な部分です。

## 選定チェックリスト

ツールにコミットする前に、次の質問を確認してください。

1. ツールは、トランスポート、テスト、承認のステータスをSAPシステムから読み取りますか。それとも、人の入力に頼っていますか。
2. 構築だけでなく、モック移行、カットオーバーのタスク、ハイパーケアのチケットも追跡しますか。
3. ワークストリームをまたぐ依存関係の連鎖を示せますか。
4. ツールとSAP環境の間の連携は、具体的に誰が責任を持ちますか。
5. セットアップの実際の費用はいくらですか。ライセンスが最も小さな数字であることは多く、Basisと連携の時間が本当の投資です。
6. 事業部門のリードを含め、チーム全員が使いますか。
7. 2つのツールが共存しなければならない場合、システムの状態の情報源はどちらで、業務スケジュールの情報源はどちらですか。

追跡がガバナンスにどうつながるかは、私の[SAPプロジェクトを軌道に戻すためのガイド](/ja/project-planning-and-control-get-sap-projects-back-on-track/)をご覧ください。

## ツールが問題ではないとき

プロジェクトチームが、追跡ツールが複雑すぎるという理由で無視し、別のスプレッドシートを使い続けているのを、私はときどき目にします。経営陣が気づく頃には、システム設定はスケジュールより3週間遅れています。

ツールが生み出すのは、可視性です。それに基づいて行動する習慣までは生み出しません。それには、赤信号を、リスク軽減のコメントを足して先に進む理由ではなく、対応する理由として扱う[ステアリングコミッティ](/ja/creating-an-effective-sap-project-steering-committee/)が必要です。

## よくある質問

<details>
<summary>SAP Cloud ALMとは何ですか。無料ですか？</summary>

SAP Cloud ALMは、SAPシステムの導入と運用のためにSAPが提供する、アプリケーションライフサイクル管理ツールです。別途ライセンスはありません。SAP Enterprise Support、またはProduct Support for Large Enterprisesをお持ちのお客様は、お客様番号ごとに1テナントを開設できます。Enterprise Supportを含むクラウドサブスクリプション（クラウドエディション。RISEとGROWが該当）をお持ちのお客様も同様です。本当の費用は、接続と設定にかかる工数です。

</details>

<details>
<summary>Jiraは、SAPプロジェクトの追跡に使えますか？</summary>

タスクと課題の管理には使えます。トランスポート、SAP Activateのフェーズ、SAPの依存関係は、標準では理解しません。ポートフォリオアドオンと、設定した連携を組み合わせれば、プログラムのスケジュールを管理し、SAPのデータの一部を取り込めます。組織がそれ以外のすべてにすでにJiraを使っているなら、使ってください。Jiraへの既存の投資がない、専任のSAPプログラムなら、Cloud ALMのほうが効率的な出発点です。

</details>

<details>
<summary>Microsoft Project Onlineの後継は何ですか？</summary>

Microsoftは、2026年9月30日にProject Onlineを終了しました。デスクトップでのスケジュール管理が必要なお客様には、Projectデスクトップアプリケーションを含むPlanner and Project Plan 3が案内されています。Planner and Project Plan 5は、新規のお客様には販売されていません。PMOがSAPプログラムをProject Onlineで追跡していたなら、新しい計画に頼る前に、移行が完了し、履歴が移っていることを確認してください。

</details>

<details>
<summary>Cloud ALMではなくSAP Solution Managerを使うべきなのは、いつですか？</summary>

3つの条件がそろうときです。複雑なオンプレミスのECCまたはS/4HANA環境を運用している。すでにSolution Managerが設定済みで、それを知っているチームがいる。そして、プログラムがメインストリーム保守の終了する2027年より前に終わる。ECCからS/4HANAへの移行の間は、両者を並行して使えます。古い環境にはSolution Manager、新しい環境にはCloud ALMです。SAPは、2028年より前にCloud ALMへの移行を完了することを推奨しています。

</details>

<details>
<summary>追跡ツールは、SAPプログラムの遅延をどう減らしますか？</summary>

週次のステータス会議より先に、問題を見せることによってです。承認キューで止まっているトランスポートは、誰かが気づくまで、手作業のレポートには現れません。システムを読み取るツールなら、その日のうちに表示されます。先ほどの初期のプロジェクトでは、実際のトランスポートの状態を読み取るツールがあれば、5週間を失う前に、滞留が見えたはずです。効果が最も大きいのは、トランスポートの量が多く、テストが並行して進むRealizeとDeployです。

</details>

<details>
<summary>同じSAPプログラムで、複数の追跡ツールを使えますか？</summary>

使えますが、たいてい面倒を招きます。2つのツールが同じワークストリームに別々のステータスを示し、どのエスカレーションも、どちらが正しいかの議論から始まります。2つ使わざるを得ないなら、それぞれに明確な役割を与えてください。システムの状態（トランスポート、テスト）は、Cloud ALMかSolution Managerに置きます。業務スケジュールは、クライアントの標準であれば、JiraかPlannerに置けます。両者は、決めた間隔で同期させます。

</details>

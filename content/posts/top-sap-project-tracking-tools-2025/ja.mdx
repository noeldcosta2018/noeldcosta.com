2023年の欧州の製造業プログラムで、トランスポートがQAシステムで止まっている理由を突き止めるのに5週間を失いました。プロジェクトマネージャーは毎週月曜にトラッキングツールを更新していました。そのツールでは、トランスポートのワークストリームはグリーン表示でした。実際のシステム内で何が起きているかは、何も見えていませんでした。

最終的にボトルネックを追跡すると、3件のトランスポートが、誰にも割り当てられていない手動承認待ちになっていたことが分かりました。承認依頼は4週間、誰かの受信箱に放置されていました。そのトラッキングツールには、SAPのトランスポートランドスケープに対する可視性がまったくありませんでした。追っていたのはタスクです。実際の作業ではありませんでした。

私が主導したり、立て直したり、あるいは失速していくのを見てきた21件のSAPプログラム全体で、このパターンは繰り返し現れます。ツールは報告の仕組みではありません。可視化の仕組みです。システムランドスケープ全体で実際に何が起きているかを示せないなら、そのプロジェクトは前提に基づいて管理していることになります。

## SAPプログラムでトラッキングツールを有用にするもの

遅延を防ぐツールと、後から遅延を記録するだけのツールを分ける特性は4つあります。

**SAPランドスケープとの統合。** SAPシステムから直接データを取得するツールは、トランスポート、テストケース、ワークフロー承認、変更ログの実際の状態を把握できます。手動更新に依存するツールが把握しているのは、人が報告した内容です。そしてそれは、多くの場合、1週間前にその人が正しいと思っていた内容です。

**フェーズ横断のカバレッジ。** ほとんどのツールは、ビルドフェーズではそれなりに機能します。問題が出るのは、テスト、トレーニング、カットオーバーです。遅延は終盤フェーズで複利的に膨らみます。ツールがカットオーバー管理やモックラン管理をサポートしていないなら、最もリスクが高い局面であなたを見放していることになります。

**依存関係の可視性。** SAPプロジェクトには、厳しい相互依存関係があります。データ移行はUATに影響します。カットオーバーの順序はトランスポートの順番に依存します。タスク完了だけを示し、依存関係の連鎖を示せないツールでは、ある領域の遅れが他の3つにどう波及するかは見えません。

**定着。** プロジェクト内で最も高機能なツールでも、チームの半分が別の場所にステータスを記録していれば失敗します。定着は、使いやすさから生まれます。人が本当に必要とする情報をツールが見せることから生まれます。そして、プロジェクトリーダーシップがそれを徹底することから生まれます。

## 4つのツール

### 1. SAP Cloud ALM

Cloud ALMは、クラウドおよびRISE with SAP導入向けの、SAPネイティブのアプリケーションライフサイクル管理ツールです。SAPのクラウドサブスクリプションに含まれており、SAPランドスケープに直接接続します。

優れている点は、トランスポート、テストケース実行、システムイベントからリアルタイムのステータスを取得できることです。プロジェクトはSAP Activateのフェーズに沿って自動的に構造化されます。2024年の10か月にわたる欧州の製造業向けS/4HANA導入では、Realizeフェーズ中にデータ移行チームが問題に直面しました。Cloud ALMはその遅延を検知し、プロジェクトマネージャーが次のステータス会議を設定する前に、依存タスクへの影響まで示しました。

2026年時点で、新規のS/4HANAクラウドまたはRISEプロジェクトであれば、Cloud ALMをデフォルトの出発点にすべきです。

弱い点は、セットアップに適切なランドスケープ接続が必要なことです。Basisチームに余力がないプロジェクトでは、その接続がPrepareの開始時に整わないことがあります。設定が完了する頃には、すでに2か月間スプレッドシートでプロジェクトを追跡しており、誰もデータを移行したがりません。

**価格:** RISE with SAPおよびSAP BTPサブスクリプションに含まれます。フル構成の導入サービスは、ランドスケープの複雑さに応じて$50,000〜$150,000です。

### 2. Jira with BigPicture (plus Atlassian Intelligence)

Jiraは、ほとんどのエンタープライズIT部門で主流のプロジェクトおよび課題管理ツールです。BigPictureは、Jira標準の課題管理の上に、ガントチャート、依存関係ビュー、リソース管理を追加するポートフォリオ／プログラム管理アドオンです。Atlassian Intelligence（2024年展開開始）は、Atlassianスイート全体にAIによる要約とコンテンツ下書き作成を追加します。

この組み合わせは、組織がすでに開発やサポートでJiraを使っている場合にうまく機能します。私が2024年に途中参加したGCC地域の製造業プログラムでは、SIがCloud ALMを設定していましたが、顧客の社内ITチームは他のすべてをJiraで管理していました。結果として、並行システムを運用することになりました。JiraはITが何をしているかを示し、Cloud ALMはSAPが何をしているかを示しました。プロジェクト全体を一つの画面で見られる人はいませんでした。

Jiraのリスクは統合にあります。SAPランドスケープへのコネクタが適切に設定されていなければ、これはトランスポート、Activateフェーズ、SAP固有の依存関係を理解しない汎用プロジェクトトラッカーです。タスクは追跡できます。システムは追跡できません。

**価格:** Jira Cloudは、大規模利用で1ユーザーあたり月額$7.75からです。BigPictureは追加ライセンスで、1ユーザーあたり月額約$3.50からです。Atlassian IntelligenceはPremium/Enterpriseエディションに含まれます。SAP接続のための統合コンサルティングには、通常$30,000〜$80,000が追加でかかります。

### 3. Microsoft Project with SAP Connector (plus Microsoft Copilot)

Microsoft Projectは、Office 365を基盤とする組織で育ったプロジェクトマネージャーにとっての標準ツールです。馴染みがあり、広くライセンスされており、多くのPMOが理解しています。M365のMicrosoft Copilot（2024年展開開始）は、準備済みデータからステータス更新、会議要約、ステークホルダー向けブリーフを作成します。

SAP Connectorは、Projectを拡張してSAPランドスケープからデータを取得できるようにします。トランスポート状況、ワークフロー項目、テスト実行などです。結果として、SAP以外の人でも扱いやすい馴染みのあるインターフェースに、SAP固有データがスケジュールへ流れ込むハイブリッドになります。

これが機能するのは、顧客のPMOがすでにProjectライセンスを保有しているミッドマーケットの導入です。社内プログラムマネージャーはそのツールを理解しています。予算的にCloud ALM構成のセットアップコストを正当化しにくいケースです。統合の深さはCloud ALMより浅いですが、単一法人のS/4HANA Finance and Procurementロールアウトであれば、多くの場合それで十分です。Copilotのレイヤーは、PMOが不釣り合いに多くの時間を費やしがちなステータス報告作業を加速します。

機能しないのは、並行ワークストリームが多く、トランスポート量が多く、システム間依存関係も重い複雑な複数法人プログラムです。その規模でリアルタイム可視性を得るには、コネクタの深さが足りません。

**価格:** Microsoft Project Plan 3は、1ユーザーあたり月額約$30です。Microsoft 365 Copilotは、1ユーザーあたり月額約$30が追加されます。SAP Connectorには変動ライセンス費用がかかります。Copilot込みで20名のミッドマーケットチームの場合、総コストは通常年間$25,000〜$60,000です。

### 4. SAP Solution Manager

Solution Managerは、Cloud ALMのオンプレミス前身です。2000年代半ば以降、ECCおよびオンプレミスS/4HANA向けの標準的なSAPプロジェクト／アプリケーションライフサイクル管理ツールでした。

複雑なオンプレミスランドスケープでは、これに匹敵するものはありません。Solution Managerは、トランスポート監視、Business Process Repositoryでの業務プロセス文書化、ネイティブなテストケース管理、そしてチェンジマネジメントワークフローとの統合が可能です。2024年の欧州製造業プログラムでは、トランスポート監視だけで、UATの3週間前に重大な設定競合を検知しました。放置していれば、主要な業務プロセス障害を引き起こしていました。

率直なトレードオフは、設定が重いことです。複雑なプログラム向けにSolution Managerを適切にセットアップするには、BasisとSolution Managerコンサルタントの工数が数週間必要です。セットアップに投資しない組織は、価値の一部しか得られません。プロジェクトチームによっては、トランスポート監視だけに使って終わることもあります。それでは機能の大半を無駄にしています。

RISEを採用している、またはクラウドS/4HANAへ移行する組織にとって、前進すべき道はCloud ALMです。Solution Managerのメインストリーム保守は2025年に終了し、延長サポートは2027年までです。2026年の新規クラウド導入では、Cloud ALMが正しい選択です。

**価格:** SAPソフトウェアライセンスに含まれます。導入および構成サービスは、通常、範囲に応じて$75,000〜$250,000です。

## AIレイヤーが2026年のSAPプロジェクトトラッキングをどう変えるか

2024年から2025年にかけてのAI展開は、プロジェクトトラッキングのワークフローにも及びました。4つのツールすべてで、今すぐ有用な機能は3つあります。

### SAP Cloud ALM向けJoule

Cloud ALMの元データから、ステータスレポート、リスク登録簿更新、フェーズゲート証跡サマリーの初稿を生成します。従来もっとも時間がかかっていたステータス報告作業の工数を30〜50%削減します。初稿には依然として人による検証が必要です。加速されるのは、システムからのAI抽出です。

### M365およびProject向けMicrosoft Copilot

Microsoft ProjectのスケジュールデータとM365の元文書から、ステアリングコミッティ資料、経営層向けブリーフィング、ステークホルダー向け更新を下書きします。トラッキングはProjectで行っているが、経営層にはガントチャートではなく文章による要約が必要な場合に特に有効です。

### JiraおよびConfluence向けAtlassian Intelligence

Jiraの課題スレッドを要約し、準備済みブリーフからConfluenceページの内容を生成し、生のチケットデータからステークホルダー向けのステータスを作成します。Jiraに運用の詳細が入っている一方で、ステアリングコミッティには文章版が必要な場合に有効です。

AIで変わらないものは、基盤となるツールのSAPランドスケープ統合の深さです。AIは、ツールが収集しているデータからステータスコンテンツを作る作業を加速します。ツールがスプレッドシートからステータス報告を集めているなら、AIはスプレッドシートからより速くステータスコンテンツを作るだけです。依然として最も重要なのは統合レイヤーです。

## 問題がツールではないとき

トラッキングツール自体は優れていたのに、プロジェクト運営がうまくいかなかったプログラムを私は見てきました。ツールはすべてを示していました。ですが、見るべき人が見ていませんでした。問題は、ステアリングコミッティ資料に載る3週間前には、すでにシステム上に現れていました。

トラッキングツールが作るのは可視性です。見えているものに対して行動する文化までは作りません。それには、エスカレーションが速く、問題が報告されるだけでなく解決されるガバナンス構造が必要です。プロジェクトリーダーシップは、レッドフラグを「緩和コメントを追加して次へ進む理由」ではなく、「行動する理由」として扱わなければなりません。

ツールは必要です。ただし、それだけでは十分ではありません。AIレイヤーもここは変えません。機能しているツールからの報告作業を加速するだけで、受け身のステアリングコミッティの反応を速くするわけではありません。

<summary>SAP Cloud ALMとは何ですか。なぜ2026年の新規導入でデフォルトなのですか。</summary>

SAP Cloud ALM（Application Lifecycle Management）は、クラウドおよびRISE with SAP導入向けの、SAPネイティブのプロジェクト／運用管理ツールです。SAPクラウドサブスクリプションに含まれているため、追加ライセンス費用はありません。

新規導入でデフォルトになる理由は、統合の深さです。Cloud ALMはSAPランドスケープに直接接続し、トランスポート状況、テストケース実行、ワークフロー承認、システムイベントに関するリアルタイムデータを取得します。また、プロジェクトをSAP Activateフェーズに沿って自動的に構造化するため、セットアップ開始時点でプロジェクトの骨格がすでに用意されています。

RISE with SAP導入では、選択はシンプルです。ツールは含まれており、SAPプロジェクトがどう構成されるかを理解していて、システムにも接続します。主なリスクはセットアップです。Prepareフェーズでランドスケープ接続が構成されないと、プロジェクトは数週間にわたりSAPデータなしで進み、その後で履歴をツールに取り込む移行課題に直面します。

2026年には、Cloud ALMはJouleレイヤーの恩恵も受けます。Cloud ALMの元データから、ステータスレポート、リスク登録簿更新、フェーズゲート証跡サマリーの初稿を生成します。これにより、基盤となるトラッキング規律を変えずに、ステータス報告作業を加速できます。

大規模なECCレガシーシステムを含むオンプレミスまたはハイブリッドランドスケープでは、より深いツールとしてSAP Solution Managerが引き続き有効です。移行シナリオでは、Cloud ALMとSolution Managerを共存させることもできます。

<details>
<summary>JiraはSAPプロジェクトのトラッキングに使えますか。</summary>

Jiraはタスクと課題の追跡には使えます。ただし、SAPランドスケープ、トランスポート、Activateフェーズ、SAP固有の依存関係をネイティブには理解しません。

BigPictureや同様のポートフォリオアドオンを使えば、Jiraでプログラムレベルのスケジュール、リソース配分、依存関係ビューを管理できます。適切に設定されたSAPコネクタがあれば、トランスポートやテストデータも取得できます。コネクタがなければ、SAPプログラムの横で動いているだけの汎用プロジェクトトラッカーです。

Atlassian Intelligence（2024年展開開始）は、Atlassianスイート全体にAIによる要約とコンテンツ下書き作成を追加します。生のJiraデータからステアリングコミッティ向けの文章を作るには有用ですが、根本のSAP統合という論点は変えません。

Jiraが理にかなうのは、組織の社内ITチームが、他のすべてのワークストリームでもすでにJiraを使っている場合です。SAPプログラムが、より大きな変革の中の複数並行ストリームの一つであるケースです。すべてを一つのツールに置くことで、リーダー層のコンテキスト切り替えコストを減らし、並行トラッキングシステムのリスクも下げられます。

理にかなわないのは、そのプログラムが専用のSAP導入であり、既存のJira投資もない場合です。そのケースでは、Jira統合をゼロから構築するより、Cloud ALMまたはSolution Managerから始める方が効率的です。

SAPプログラムで最もよくあるJiraの失敗は、Jira管理チームとBasisチームの間の統合を誰もオーナーシップを持って進めないため、コネクタが正しく設定されないことです。結果として、Jiraで追跡されてはいるが、SAPシステムの可視性がないプロジェクトになります。

</details>

<details>
<summary>トラッキングツールはSAPプログラムの遅延をどう減らしますか。</summary>

SAPプログラムの遅延は、見える前に積み上がります。承認キューで1週間止まったトランスポートは、次のステアリングコミッティまで手動ステータスレポートには現れません。その時点では、依存するテストはすでに遅れて始まっています。

SAPランドスケープに接続するトラッキングツールは、システムの実際の状態をリアルタイムで示します。トランスポート状況は、朝会で誰かが報告した内容ではありません。プロジェクトマネージャーがダッシュボードを見たその瞬間に、システムが把握している内容です。

具体的な仕組みは、項目が閾値を超えたときの自動アラート、別ワークストリームの遅れによってどのタスクがブロックされるかを示す依存関係チェーンの可視化、そしてテストマネージャーのスプレッドシート更新ではなく、Solution ManagerやCloud ALMから直接取得する統合テスト状況です。

遅延削減の効果が最も大きいのは、RealizeフェーズとDeployフェーズです。この時期はトランスポート量が多く、テストも並行して走っています。同時に、手動トラッキングが最も早く破綻するフェーズでもあります。動いている要素の数が、週次ステータス会議でカバーできる範囲を超えるからです。

2026年には、AIレイヤー（Cloud ALM向けJoule、Project向けCopilot、Jira向けAtlassian Intelligence）が、ツールが収集しているデータからステータスコンテンツを作る作業を加速します。ただし、統合レイヤーを改善したり、対応の規律を変えたりはしません。依然として最も重要なのは、基盤となるツールの能力です。

</details>

<details>
<summary>Cloud ALMではなくSAP Solution Managerを使うべきなのはどんな場合ですか。</summary>

SAP Solution Managerが適しているのは、複雑なオンプレミスのECCまたはS/4HANAランドスケープです。オンプレミスのトランスポート管理、業務プロセス文書化、テスト管理との統合の深さは、大規模なレガシー環境においてCloud ALMに同等のものがありません。

Solution Managerが優位になる具体的なシナリオは、重いカスタマイズと複雑なトランスポートランドスケープを持つ複数法人のECC導入、ガバナンスや監査のためにBusiness Process Repositoryで業務プロセスを文書化する必要があるプログラム、そして複数年にわたってSolution Manager構成に投資しており、それを使いこなせるチームがいる組織です。

Cloud ALMは、RISEまたはクラウドS/4HANAへ移行する組織にとっての前進ルートです。SAPの製品ロードマップ投資はCloud ALMに向いています。Solution Managerのメインストリーム保守は2025年に終了し、延長サポートは2027年までです。2026年の新規クラウド導入であれば、Solution Managerを新たに学ぶより、Cloud ALMから始める方が合理的です。

移行シナリオとしては、Solution ManagerでECCを運用している組織が、RISE上のS/4HANAへ移行するケースがあります。移行プログラム中は、Solution ManagerがECCランドスケープをカバーし、Cloud ALMが新しいS/4HANA環境をカバーする形で、両方のツールが並行稼働することがあります。

</details>

<details>
<summary>AIは2026年のSAPプロジェクトトラッキングをどう変えますか。</summary>

2024年から2025年にかけてのAI展開は、4つのツールすべてのプロジェクトトラッキングワークフローに及びました。

SAP Cloud ALM向けJouleは、Cloud ALMの元データから、ステータスレポート、リスク登録簿更新、フェーズゲート証跡サマリーの初稿を生成します。従来もっとも時間がかかっていたステータス報告作業の工数を30〜50%削減します。

M365およびProject向けMicrosoft Copilotは、ProjectのスケジュールデータとM365の元文書から、ステアリングコミッティ資料、経営層向けブリーフィング、ステークホルダー向け更新を下書きします。トラッキングはProjectで行っているが、経営層には文章による要約が必要な場合に特に有効です。

JiraおよびConfluence向けAtlassian Intelligenceは、Jiraの課題スレッドを要約し、準備済みブリーフからConfluenceページの内容を生成し、生のチケットデータからステークホルダー向けのステータスを作成します。

AIで変わらないものは、基盤となるツールのSAPランドスケープ統合の深さです。AIは、ツールが収集しているデータからステータスコンテンツを作る作業を加速します。ツールがスプレッドシートからステータス報告を集めているなら、AIはスプレッドシートからより速くステータスコンテンツを作るだけです。依然として最も重要なのは統合レイヤーです。

</details>

<details>
<summary>SAPトラッキングツールを評価するとき、プロジェクトマネージャーは何を見るべきですか。</summary>

機能比較マトリクスより重要な基準は4つあります。

SAPランドスケープ統合。ツールは実際のSAPシステムに接続するのか、それとも手動入力に依存するのか。実際のトランスポート状況を示すツールは、私のあるプロジェクトで4週間の承認ボトルネックを捉えました。誰かがステータス欄に入力した内容を示すだけのツールなら、見逃していたはずです。

フェーズ横断のサポート。ツールはカットオーバーやハイパーケアでも機能するのか、それとも終盤フェーズで無関係になるのか。多くのツールはビルドフェーズ向けに作られています。最もリスクが高いのはDeployとRunです。

定着。ツールは、プロジェクトチーム全体が一貫して使えるほどシンプルか。強力なツールでもチームの半分が無視するなら、全員が使うよりシンプルなツールより悪い状況を生みます。なぜなら、その強力なツールは「すべて揃っている」という誤った絵を作るからです。

接続コスト。SAP統合をセットアップする実際のコストはいくらか。ツールのライセンス費用は、しばしば最も小さい数字です。本当の投資は、接続を構成するための統合コンサルティングとBasis工数にあります。コミットする前に、その数字を把握してください。

</details>

<details>
<summary>同じプログラムで複数のSAPトラッキングツールを使えますか。</summary>

使えます。ですが、たいてい問題を生みます。

具体的な問題は、同じワークストリームについて2つのツールが異なるステータスを示すことです。SteerCoはCloud ALMのデータを見ます。業務側のプログラムマネージャーはJiraのデータを見ます。両者は一致しません。どちらが正しいのか誰にも分からなくなります。エスカレーションは遅くなります。最初の会話が、いつも「どちらのシステムを信じるべきか」になるからです。

並行トラッキングツールが最もよく起きるのは、顧客の社内チームがJiraやMicrosoft Projectに投資しており、SIがCloud ALMまたはSolution Managerを持ち込む場合です。結果として、完全には整合しない2つのプロジェクトビューが生まれます。

ガバナンス上の対処は、情報カテゴリごとに単一の正本を定めることです。SAPシステム状態（トランスポート、テスト実行）はCloud ALMまたはSolution Managerに置きます。プログラムスケジュールや業務ワークストリームは、それが顧客標準であればJiraやProjectに置いて構いません。2つのビューは定義された間隔で同期します。どちらのツールも、それ単体で完全な全体像だとは扱いません。

これは美しいやり方ではありません。ですが、既存ツールを捨てて、すべての社内PMOにプロジェクト途中でSAPネイティブツールへ乗り換えさせるよりは、まだ管理しやすいです。

</details>

2026年における最良のSAPプロジェクトトラッキングツールは、機能一覧が最も長いものでも、最新のAIレイヤーを持つものでもありません。SAPランドスケープ統合によってシステムの実際の状態を示し、プロジェクト開始時から定着の規律が徹底され、レッドシグナルが出たときにステアリングコミッティが実際にそのデータに基づいて行動するツールです。AIは報告作業を加速します。そこには意味があります。ただし、より重要なのは統合レイヤーと対応の規律です。まず統合を作ってください。AIツールは後から足すのが簡単です。

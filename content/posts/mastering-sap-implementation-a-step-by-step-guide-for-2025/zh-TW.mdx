SAP 導入是把企業的財務、採購、供應鏈、銷售和人資移到同一套 SAP 系統上的專案，如今這套系統通常是 SAP S/4HANA。它會經過 SAP Activate 的六個階段（Discover、Prepare、Explore、Realize、Deploy 和 Run），成敗取決於在任何人動手設定之前，流程、資料和人員方面的工作做得如何。

簡單的回答：SAP 導入專案是用一套系統、一個資料模型取代各自為政的舊系統。整個流程分成六個步驟：確認商業論證、組成團隊、依照 SAP 標準設計、建置與測試、上線，然後穩定運作並移交。依我的經驗，GROW with SAP 需要 6 到 9 個月，RISE with SAP 需要 9 到 18 個月，我的 [SAP 導入時程指南](/zh-TW/2024-sap-timeline-planning-implementation-guide-essentials/)逐一拆解了各階段。

在我帶領過、救回來過或眼看著走偏的 21 個 SAP 專案中，模式都一樣。把 SAP 當成軟體安裝的企業會很辛苦。先再造流程、後做設定的企業，能兌現對董事會的承諾。

這份指南是寫給即將啟動 SAP 導入的高階主管和專案負責人。如果只讀一節，請讀「設定開始之前的規劃」。

## SAP 導入涵蓋哪些內容

S/4HANA 是 SAP 目前的 ERP，執行在 SAP HANA 記憶體內資料庫上。許多企業仍在使用較舊的 SAP ECC，但 [ECC 的主流維護將於 2027 年 12 月 31 日結束](https://news.sap.com/2020/02/sap-s4hana-maintenance-2040-clarity-choice-sap-business-suite-7/)，企業可以支付較高的費用，選擇延長維護到 2030 年底。

大多數導入專案最先處理的核心模組如下：

| 模組 | 管理內容 |
|---|---|
| FI（財務會計） | 總帳、應付帳款、應收帳款、資產會計 |
| CO（管理會計） | 成本中心、利潤中心、內部訂單、管理報表 |
| MM（物料管理） | 採購、庫存、貨物異動、供應商管理 |
| SD（銷售與配銷） | 訂單到收款、定價、出貨、開立發票 |
| PP（生產規劃） | 生產工單、產能規劃、MRP |
| HCM（人力資本管理） | 人事主檔資料、薪資、出勤管理 |

大多數企業從 FI/CO 加上一兩個營運模組開始，其餘的在後續版本中陸續建置。

導入和移轉不是同一件事。如果您已經在使用 SAP ECC，那是要轉換或重建一套 SAP 系統，我的 [ECC 到 S/4HANA 移轉指南](/zh-TW/ecc-to-s4hana-migration/)說明了綠地、棕地和選擇性三種路徑。

## SAP 導入步驟：SAP Activate 的六個階段

SAP Activate 是 SAP 的導入方法論。它取代了較舊的 ASAP 方法，共有六個階段，每個階段都有一道關卡，通過後才能繼續。

<stepper title="SAP Activate 的六個階段" steps="Discover|Prepare|Explore|Realize|Deploy|Run" bodies="確認商業論證，並在試用或展示系統上驗證優先流程。|啟動：團隊、治理、範圍文件、計畫與系統存取權限。|與流程負責人進行 Fit-to-Standard 工作坊，建立設定、介面與擴充的待辦清單。|設定、擴充、資料移轉與測試。這是最長的階段，結束時需要一輪乾淨的回歸測試。|用真實流程訓練使用者，演練切換，在作戰室就位的情況下上線。|上線後支援、優化，並移交給 Centre of Excellence。"></stepper>

這張表是我貼在專案辦公室牆上的版本。它列出每個階段必須產出什麼、由誰負責，以及進入下一階段之前必須達成什麼條件。

| 階段 | 必須產出 | 負責人 | 進入下一階段的關卡 |
|---|---|---|---|
| Discover | 商業論證、目標範圍、部署方式選擇 | 發起人與 CFO | 預算核准 |
| Prepare | 範圍文件、計畫、治理、團隊到位 | 專案總監 | 發起人簽署範圍 |
| Explore | Fit-to-Standard 結果、待辦清單、擴充決策 | 解決方案架構師與流程負責人 | 沒有未解決的差異 |
| Realize | 已設定並測試的系統、已移轉的測試資料 | 功能負責人與技術負責人 | 回歸測試乾淨；資料核對一致 |
| Deploy | 完成訓練的使用者、演練過的切換、上線決策資料 | 切換經理 | 通過三天月結演練 |
| Run | 上線後支援紀錄、CoE 移交、第二階段待辦清單 | 服務交付負責人 | 沒有未結的 P1/P2；CoE 接手 |

每個階段背後的範本都在我的 [SAP Activate 範本指南](/zh-TW/best-sap-implementation-templates-activate-2024/)裡。

### 五個階段還是六個？

大家會搜尋「SAP 導入五個階段」，是因為 SAP 較舊的 ASAP 方法有五個階段：專案準備、業務藍圖、實現、最終準備、上線與支援。

SAP Activate 沿用了相同的邏輯，在最前面加上 Discover，在最後加上 Run。Prepare 到 Deploy 通常被視為核心交付階段。還在講「藍圖」的團隊，通常指的是 Explore。

### 三天月結演練這道關卡

Realize 和 Deploy 之間的關卡，是團隊在時程壓力下最常跳過的一道。我在每個專案都把為期三天的月結演練當作就緒關卡。如果財務無法在新系統上關帳，不管 IT 怎麼說，您的資料移轉都還沒準備好。

跳過這道關卡的代價，比它原本會造成的延誤還高。

## 設定開始之前的規劃

順序很重要。在做出任何一項設定決策之前，有四件事要先完成。

<explainer-flow title="第一個設定決策之前的四件事" caption="系統是最後一步。流程、資料和人員的工作要先做。" steps="盤點現行流程|決定採用標準還是擴充|稽核資料品質|先找齊團隊，再確定範圍" notes="依實際運作的樣子，包括各種變通做法|標準幾乎總是比較快|在資料移轉開始之前|有哪些人可用，決定了能交付什麼" result="到這時才開始設定"></explainer-flow>

我看過最大的錯誤，是一開始沒有好好規劃。預算在 Explore 階段超支：工作流程、報表、介面、資料轉換、強化功能與表單（WRICEF）清單不斷膨脹，掌控範圍的變成供應商，而不是客戶。我的 [SAP 導入成本拆解](/zh-TW/sap-implementation-cost-breakdown-why-budgets-explode-50/)說明了這對預算會造成什麼影響。

### 依實際運作的樣子盤點現行流程

不是流程應該長什麼樣子，而是它實際上長什麼樣子，包括各種變通做法。

2023 年在歐洲的一個金融服務專案上，我參加了一場藍圖會議，當時財務部門還在用試算表核對公司間交易。沒有人寫下來的需求，就藏在這些變通做法裡。

### 逐一決定每個流程採用標準還是擴充

找出哪些流程 SAP 的標準功能可以涵蓋，哪些需要擴充。標準幾乎總是比較快，因為每多一個擴充，就會多出測試輪次、升級風險和維護工作。

依照 SAP 的 Clean Core 指引，每個擴充還必須刻意決定放在哪裡。這讓這項決策的分量更重，而不是更輕。

### 在資料移轉開始之前稽核資料品質

資料是最常被低估的工作流。依我的經驗，資料移轉占導入工作量的 30% 到 40%。

有一位客戶的重複客戶資料超過 18,000 筆。上線後才修正，讓開立發票的作業亂了好幾週。請及早做資料剖析，並在來源系統中清理；做法可以參考我的 [SAP 資料移轉為什麼會失敗](/zh-TW/why-sap-data-migration-fails-and-how-to-fix-it/)指南。

### 先組成團隊，再確定範圍

您能交付的範圍，取決於每個工作流有誰能設定、測試和負責。先定範圍、後找人的團隊，會花好幾個月重做當初承諾過頭的部分。

## SAP 導入專案需要哪些人

SAP 導入專案需要為以下角色指定具體的人選，其中大多數應該來自您這一方，而不是合作夥伴：

1. **執行發起人。** 對商業論證負責，在意見僵持時拍板。通常是 CFO 或 COO。
2. **專案總監。** 管理計畫、預算和指導委員會。應該是您的員工，或是獨立於合作夥伴的人。
3. **流程負責人。** 每個領域（財務、採購、銷售、生產）一位。他們簽核設計，並對上線後的結果負責。
4. **解決方案架構師。** 掌握整體設計，決定每個擴充要放在哪裡。
5. **功能負責人與技術負責人。** 負責設定、建置和測試。通常是合作夥伴的團隊。
6. **資料移轉負責人。** 在 Prepare 階段任命，而不是 Realize。
7. **變革與訓練負責人。** 從 Explore 階段就開始和終端使用者溝通。
8. **切換經理。** 負責上線作業手冊和上線決策資料。

有一條規則比這份名單更重要：將來負責執行的合作夥伴，不應該幫您寫商業論證。

他們的動機是開工。您的動機是完工。

## 常見挑戰與因應方式

以下是我幾乎在每個專案都會遇到的挑戰，以及各自的對策：

| 挑戰 | 樣貌 | 因應方式 |
|---|---|---|
| 範圍蔓延 | 「既然都在改了，順便加上……」這類需求越堆越多 | 從第一天起就實施正式的變更控管；每項需求都要做影響評估 |
| 資料品質 | 移轉時才發現沒人知道的不一致 | 及早做資料剖析；在來源系統中清理 |
| 使用者抗拒 | 上線後兩週內使用者又回到 Excel | 從 Explore 階段起就讓終端使用者參與設計 |
| 整合失敗 | 第三方連線在 UAT 時出問題 | 在 Explore 階段盤點介面；及早用貼近真實的資料量測試 |
| 測試週期被砍 | 為了趕日期縮短回歸測試 | 保護測試階段；建置延誤不能壓縮測試 |
| 團隊疲乏 | 最後衝刺時士氣下滑、缺陷率上升 | 用簡單的每週情緒指數追蹤 |

關於團隊疲乏，我會追蹤一個簡單的每週情緒指數。當超過 25% 的團隊成員表示快撐不住時，測試缺陷率就會飆升。

2024 年在波灣地區的一個製造業專案上，團隊為了追回三週的時程而跳過回歸測試。結果財務無法核對關鍵報表，之後是好幾個月的善後清理。這不是系統缺陷，而是一個本來可以避免的決定。

### 上線前、上線中與上線後

上線前，要做月結演練，用對帳報表驗證移轉後的資料，並用真實流程而不是展示情境來訓練。也要測試回復計畫。和指導委員會逐條確認上線決策標準，取得明確的簽核，而不是心照不宣的點頭。

上線期間，要加強監控，並在最初 72 小時讓切換團隊全天候待命。這幾個小時做出的決定，決定了上線後支援期是帶著信心開始，還是帶著一長串問題開始。

上線後，至少進行四週的上線後支援，並依類別追蹤支援工單。這些工單會告訴您訓練在哪裡沒做到位，設定在哪裡需要調整。

## 兩個成功的專案

2024 年在歐洲的一個製造業專案上，客戶的原物料一直斷料。採購部門怪計畫人員，計畫人員怪沒有人信得過的試算表。我們用 S/4HANA 取代了這套做法，並大量倚重 MRP 設定得當的 SAP PP。

庫存水準從靠猜測變成即時資料，採購單依需求觸發。前六個月，原物料短缺減少了 50% 以上。這個成果來自設定之前的流程再造，因為沒有流程方面的工作，PP 只會更快地給出錯誤的答案。

2024 年在英國的一個專業服務專案上，問題出在財務。月結要花兩週以上，報表靠人工重做。我們在一個高度投入的指導委員會帶領下，分階段推出 SAP Finance。

月結縮短到一週多一點。CFO 告訴我，這些數字「讓人覺得可信」。

## 對現在啟動的專案而言，有什麼改變

一份為 2022 年寫的指南，放到 2026 年的買方面前已經站不住腳。有三項改變需要從專案啟動時就納入設計。

### 雲端版本已成為預設選擇

SAP 目前銷售兩個雲端 ERP 版本：SAP Cloud ERP（公有版，前身是 S/4HANA Cloud Public Edition）和 SAP Cloud ERP Private（私有版）。[RISE with SAP](https://news.sap.com/2025/04/sap-cloud-erp-private-package-accelerate-transformation/) 把私有版、由 SAP 負責的維運，以及包含 SAP Signavio、SAP LeanIX 和 SAP Cloud ALM 的工具組合包裝在一起。GROW with SAP 則是給使用公有版的中型企業的方案。

如今版本決策的層級高於過去關於導入方式的爭論。大爆炸式還是分階段，綠地、棕地還是選擇性，都是在選定的版本內做的選擇，而不是用來取代版本選擇。

### Clean Core 是分級的，不是二選一

2025 年 8 月，SAP 推出了 [A 到 D 四個 Clean Core 等級](https://news.sap.com/2025/08/extend-sap-s4hana-cloud-right-way-clean-clear/)。A 級只使用已發布的穩定 API，不論是在 SAP BTP 上做並行擴充，還是用 ABAP Cloud 在系統內擴充。B 級允許仍被視為乾淨的傳統 API，C 級需要採取特別措施，D 級則不算乾淨。

公有版只允許 A 級擴充。私有版和地端部署允許傳統擴充，所以那裡的紀律來自治理，而不是平台擋住您。在 Explore 階段決定每個擴充的等級和位置，並指定一位能說「不」的人。

### 交付團隊裡的 AI

Joule 現在已內建於 SAP Activate Roadmap Viewer 和 SAP Cloud ALM，能回答工作相關的問題，並依照方法論草擬內容。SAP Build Code 自 2024 年起正式推出，透過 Joule 為 SAP BTP 上的 Java 和 JavaScript 擴充產生應用程式邏輯、資料模型和測試。SAP 也為 ABAP 開發人員加入了類似的生成式 AI 輔助。

我的看法是：AI 在 SAP 專案中是真的，但價值取決於資料品質。乾淨的流程文件和乾淨的主檔資料能產出有用的結果，髒資料只會產出自信滿滿的雜訊。這些都無法取代為每項決策負責的人。

階段依然適用，工作順序依然重要。在專案啟動時就納入版本決策、擴充紀律和新工具的專案，會把它們當成設計限制來處理。忽略它們的專案，會把前三個月花在搞清楚到底改了什麼，而且通常是從合作夥伴的變更請求中得知。

本指南是我的[SAP 導入指南](/sap-implementation/)的一部分，該指南彙整了從商業論證到上線的所有主題。

## 常見問題

<details>
<summary>簡單來說，什麼是 SAP 導入？</summary>

就是建置 SAP 軟體，讓企業的財務、採購、銷售和人資等核心流程在同一套系統、同一個資料模型上運作的專案。它涵蓋流程設計、設定、資料移轉、測試、訓練和上線，通常依循 SAP 的 Activate 方法論。

</details>

<details>
<summary>SAP 導入的五個階段是什麼？</summary>

這五個階段來自 SAP 較舊的 ASAP 方法：專案準備、業務藍圖、實現、最終準備、上線與支援。SAP Activate 取代了 ASAP，使用六個階段，在開頭加上 Discover，在結尾加上 Run。

</details>

<details>
<summary>SAP Activate 的六個階段是什麼？</summary>

Discover（商業論證與適配度）、Prepare（團隊、治理、計畫）、Explore（Fit-to-Standard 工作坊與待辦清單）、Realize（設定、擴充、移轉、測試）、Deploy（訓練、切換演練、上線）和 Run（上線後支援，並移交給 Centre of Excellence）。

</details>

<details>
<summary>SAP 導入和 SAP 移轉有什麼不同？</summary>

導入是把 SAP 建置起來，通常是取代非 SAP 系統或舊系統。移轉是把既有的 SAP ECC 系統移到 S/4HANA，方式有系統轉換（棕地）、重新建置（綠地）或選擇性資料移轉。兩者都依循 SAP Activate 的各個階段。

</details>

<details>
<summary>SAP 導入團隊應該有哪些人？</summary>

執行發起人、專案總監、各領域的流程負責人、解決方案架構師、功能負責人與技術負責人、資料移轉負責人、變革與訓練負責人，以及切換經理。發起人、流程負責人和資料負責人應該來自您這一方，而不是合作夥伴。

</details>

<details>
<summary>SAP 導入失敗最常見的原因是什麼？</summary>

幾乎每個陷入困境的專案都有三個根本原因：跳過流程工作、資料品質被忽略到切換時，以及變革管理被當成訓練。

還有一個較新的原因：合作夥伴在沒有 Clean Core 規劃的情況下開發擴充。這會留下技術債，在第一次大版本升級時浮上檯面。

</details>

<details>
<summary>如何挑選合適的 SAP 導入合作夥伴？</summary>

找在與您規模相當的企業中有產業經驗、而且能提供您真的可以打電話查證的參考客戶的夥伴。在提案簡報中出現的人，應該就是帶領專案的人。問他們開發過多少個 SAP BTP 和 ABAP Cloud 擴充，並要求實際看看。

</details>

<details>
<summary>什麼是 RISE with SAP，適合我的組織嗎？</summary>

RISE with SAP 是 SAP 為 SAP Cloud ERP Private 提供的訂閱方案：包括軟體、由 SAP 管理的基礎架構與維運，以及用於流程分析、架構和生命週期管理的工具組合。導入工作仍由您的合作夥伴交付。

它適合正要離開 ECC、希望平台與維運只和 SAP 簽一份合約的大型組織。能夠貼近標準運作的中型企業，應該考慮公有版的 GROW with SAP。

</details>

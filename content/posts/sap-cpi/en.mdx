# SAP CPI: what it is, how it works, and where it fits in your architecture

I've seen teams spend months building brittle custom scripts to connect SAP and non-SAP systems. Something works at first. Then a system update changes a field name, or a new API version rolls out, or traffic volume doubles. The script breaks quietly. Nobody knows until a report pulls stale data or an order sits unprocessed for three days.

SAP CPI replaces that with structured, reusable integration flows, not because it's simpler (it isn't always), but because the architecture is built to scale and maintain. Small decisions made early in CPI design compound into technical debt faster than most teams expect. Getting those decisions right is where the real value sits.

## What SAP CPI is (and what it isn't)

SAP CPI stands for Cloud Platform Integration. It's SAP's cloud-based middleware: the layer that connects systems, transforms data, and routes messages between applications. It lives inside SAP BTP (Business Technology Platform).

Officially, SAP CPI is now part of the broader **SAP Integration Suite**, which also includes API Management, Open Connectors, Trading Partner Management, and other services. Most consultants and developers still call it CPI informally. That terminology is still current.

**What CPI does:** moves data between systems, transforms message formats, routes to the right target, handles errors and retries. It works with SAP systems (S/4HANA, SuccessFactors, Ariba) and non-SAP platforms (Salesforce, Workday, ServiceNow) via standard adapters.

**What it doesn't do:** store data long-term, replace an ERP, function as an ETL tool for large batch data migrations. CPI is designed for real-time or near-real-time message processing. Treating it as a data warehouse or a bulk migration tool leads to architecture problems later.

**CPI vs SAP BTP:** BTP is the whole platform. CPI handles integration specifically. The distinction matters when scoping work. BTP skills include app development, database, AI, analytics, and integration. CPI expertise is specifically the integration domain.

## How CPI compares to SAP PI/PO

| Factor | SAP PI/PO | SAP CPI |
|---|---|---|
| Deployment | On-premise, requires server infrastructure | Cloud-native, runs on SAP BTP |
| Maintenance overhead | High: patching, upgrades, server management | Lower: SAP manages the platform |
| Extensibility | Deep customisation possible; harder to upgrade | Modular; updates happen faster; less flexibility for deep control |
| Licensing | Static, often capacity-based | Consumption-based (message volume or throughput) |
| SAP investment direction | Maintenance mode; no new feature development | Active development; where SAP's integration roadmap is |
| Migration | Still supported; no forced cutover | Migration encouraged; tools available from SAP |

SAP PI/PO isn't dead, but SAP has been clear about the direction. Future feature development, certifications, and integration with SAP's cloud ecosystem are focused on CPI and Integration Suite. Companies still running PI/PO can continue doing so, but compatibility gaps grow with each SAP release.

The licensing shift is worth understanding. CPI's consumption-based model ties cost to message volume. Some companies save compared to PI/PO's static model. Others discover their actual integration traffic is higher than expected and need to optimise flows early. Modelling this before migration avoids surprises.

## Key features and adapters

The integration building block in CPI is the **iFlow**: an integration flow, each iFlow defines how a message moves from source to target: what transformation happens, which routing rules apply, what error handling fires when something fails.

| Feature | What it does |
|---|---|
| Prebuilt integration content | Library of pre-configured iFlows and adapters for SAP and common third-party platforms |
| Graphical flow designer | Web-based drag-and-drop interface for building iFlows |
| API management | Full lifecycle API design, deployment, monitoring, and security |
| Security | OAuth2.0, SAML, TLS, certificate management |
| Monitoring and logging | Real-time dashboards, message logs, error stacks, retry history |

**Standard adapters:** SOAP, REST, OData, IDoc, JDBC, SFTP, JMS, AS2, and more. For platforms not covered by standard adapters, Open Connectors inside Integration Suite extends connectivity to over 160 third-party SaaS applications.

**Scripting:** Complex message transformations require Groovy or JavaScript scripts inside iFlows. CPI is not zero-code for anything beyond standard flows. If your team can't write basic script logic, complex mappings become a bottleneck.

## Neo vs Cloud Foundry

SAP BTP offers two environments: **Neo** and **Cloud Foundry**. The choice affects long-term extensibility.

**Neo** is SAP-managed, more constrained, used in earlier CPI projects. It integrates cleanly with classic SAP services, but extensibility is limited, runtime flexibility is minimal, and SAP's development investment is increasingly Cloud Foundry-focused.

**Cloud Foundry** supports multiple programming languages, decoupled runtime, microservices alongside CPI components. More flexibility as architecture grows.

The practical guidance: unless tied to Neo by existing contracts or regional compliance requirements, new CPI implementations go to Cloud Foundry. It gives more room to scale and adapt.

## PI/PO migration: what the process actually involves

Migration from PI/PO to CPI is not an automated conversion. PI interfaces need careful review before moving them.

Adapter behaviour differs between PI and CPI. Error handling logic that worked in PI may behave differently in CPI. Some flows need to be rebuilt entirely. Others can be adapted with small changes.

**Migration approach:**
1. Inventory all PI interfaces: document frequency, volume, business criticality, adapter type
2. Categorise each: rebuild entirely, adapt with changes, or retire
3. Estimate effort and risk by adapter type and scripting complexity
4. Plan regression testing: especially for B2B partners and non-SAP targets
5. Roll out in waves, with fallback paths to the existing PI system

The tools SAP provides (migration toolkits, prebuilt iFlow packages, API Hub content) reduce the mechanical work. They don't replace the judgment calls about what to rebuild and what to retire. That's where experienced architecture input makes the real difference.

## Common integration patterns

The most frequent scenarios I've worked with:

**S/4HANA to SuccessFactors:** Syncing organisational data, headcount updates, compensation plan changes. The native integration content from SAP covers the standard scenarios; custom flows handle deviations.

**SRM or legacy procurement to Ariba:** Linking internal procurement workflows with Ariba's supplier-facing processes. Integration is often two-directional: purchase orders out, confirmations and invoices in.

**Legacy finance to SAP Analytics Cloud:** Transforming and routing financial data from ECC or non-SAP systems into Analytics Cloud's import layers.

**Salesforce to SAP:** Automating lead-to-cash or service-to-invoice pipelines. Sales closed in Salesforce flow into SAP for fulfilment, invoicing, and inventory updates. Without CPI, this typically relies on spreadsheet exports or fragile custom scripts.

<details>
<summary>How is SAP CPI different from SAP PI/PO?</summary>

SAP PI (Process Integration) and PO (Process Orchestration) are on-premise middleware products. They were built for an era when SAP systems lived on company servers and integration happened inside the data centre. They offer deep customisation and full infrastructure control.

SAP CPI is cloud-native, runs on SAP BTP, and requires significantly less infrastructure overhead. SAP manages the platform; integration teams manage the iFlows. Updates happen faster, new adapters and content arrive through the central hub, and licensing is consumption-based rather than static.

SAP's direction is clear: new integration feature development happens in CPI and Integration Suite. PI/PO receive maintenance but not innovation. Companies staying on PI/PO don't face a forced cutover, but compatibility gaps grow with each SAP release cycle.

</details>

<details>
<summary>Is SAP CPI the same as SAP BTP?</summary>

No. SAP BTP is the full Business Technology Platform: it covers app development, database services, analytics, AI capabilities, integration, and more. CPI (or Integration Suite) is specifically the integration service within BTP.

Think of BTP as the platform and CPI as one of the services it hosts. A BTP architect designs across multiple services. A CPI consultant focuses specifically on integration flows, adapters, message transformation, and connectivity.

When scoping integration work, the distinction matters for budget and skill requirements. CPI expertise is the integration domain specifically. BTP skills cover a much broader surface.

</details>

<details>
<summary>How difficult is SAP CPI to learn and work with?</summary>

Manageable, but not simple. The graphical iFlow designer makes standard integrations accessible to people with functional architecture knowledge. Standard adapter configurations follow documented patterns.

The complexity comes from three areas: understanding the underlying business process well enough to design the flow correctly, handling edge cases in error processing and message retry logic, and writing Groovy or JavaScript for complex data transformations. That scripting requirement is where people who aren't comfortable with code get stuck.

The learning curve is steeper when teams try to learn CPI while simultaneously learning SAP backend processes. Learning them sequentially (understand the process, then implement the integration) produces better outcomes.

</details>

<details>
<summary>What should I consider when migrating from SAP PI/PO to CPI?</summary>

Migration is not a direct port. PI interfaces need review because adapter behaviour and error handling differ between the two systems. What worked in PI may not work the same way in CPI.

The practical process: first, inventory every PI interface with its volume, frequency, adapter type, and business criticality. Then categorise: rebuild entirely, adapt with small changes, or retire. Model the consumption-based CPI licensing against your actual message volumes: some companies save, others discover unexpected costs.

Roll out in waves with fallback paths. Don't switch off PI until each wave has been tested and confirmed stable in CPI. Regression testing with B2B partners and non-SAP targets needs to be planned early: these are the integrations that break quietly and cause the most downstream damage.

</details>

<details>
<summary>What is the difference between Neo and Cloud Foundry environments for SAP CPI?</summary>

Both are SAP BTP environments where CPI can be deployed. Neo is the older, SAP-managed environment. It works well for SAP-heavy landscapes with limited change requirements and some regulated environments where tight platform control matters.

Cloud Foundry is the more open environment. It supports multiple programming languages, decoupled runtime, and microservices alongside CPI. New SAP features and investment are primarily targeting Cloud Foundry.

For any new CPI implementation without a specific constraint requiring Neo, Cloud Foundry is the right choice. It has more extensibility, better alignment with SAP's roadmap, and more flexibility as architecture scales.

</details>

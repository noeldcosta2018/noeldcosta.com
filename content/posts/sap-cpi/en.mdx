SAP CPI (Cloud Platform Integration) is SAP's cloud middleware. It now lives as the Cloud Integration capability inside SAP Integration Suite on SAP BTP, and it is SAP's answer for connecting S/4HANA to other SAP and non-SAP systems. If you still run SAP PI/PO, the clock matters: PI/PO 7.5 leaves mainstream maintenance at the end of 2027.

This guide is for integration leads and CIOs deciding how to move off PI/PO or design integration for a new S/4HANA programme. It covers what CPI does and doesn't do, how it compares with PI/PO, and a wave plan for migrating interfaces.

I have seen teams spend months building brittle custom scripts to connect SAP and non-SAP systems. Something works at first. Then a system update changes a field name, or a new API version rolls out, or traffic doubles. The script breaks quietly. Nobody knows until a report pulls stale data or an order sits unprocessed for three days.

CPI replaces that with managed, reusable integration flows. Not because it is simpler (it often isn't), but because the architecture is built to be monitored and maintained. Small decisions made early in CPI design compound into technical debt faster than most teams expect.

## What SAP CPI is, and what it isn't

CPI is the layer that connects systems, transforms data and routes messages between applications. SAP Integration Suite bundles it with API Management, Event Mesh, Integration Advisor and trading partner management. Most consultants still say "CPI" when they mean the integration flow part, and that is fine.

**What CPI does:** moves data between systems, transforms message formats, routes to the right target, and handles errors and retries. It connects SAP systems (S/4HANA, SuccessFactors, Ariba) and non-SAP platforms (Salesforce, Workday, ServiceNow) through standard adapters.

**What it doesn't do:** store data long-term, replace an ERP, or act as an ETL tool for bulk data migration. It is built for real-time or near-real-time messages. Using it as a data warehouse or a migration tool causes architecture problems later.

**CPI versus SAP BTP:** BTP is the whole platform: application development, data, AI, analytics and integration. CPI is one service on it. The distinction matters when you scope skills and budget. A BTP architect designs across services. A CPI specialist owns flows, adapters, mappings and connectivity.

## What has changed for 2026

Four dates and decisions shape any integration plan now.

1. **PI/PO is running out of road.** [SAP NetWeaver 7.5, which includes PI/PO, follows the Business Suite maintenance timeline](https://sapinsider.org/blogs/sap-extends-maintenance-for-sap-netweaver-7-5-and-sap-bw-4hana/): mainstream maintenance to the end of 2027, extended maintenance to the end of 2030. No new features are coming. A planned, wave-based move costs far less than a forced cutover in 2027 or 2030.
2. **Hybrid has an answer.** Edge Integration Cell, generally available since late 2023, runs Integration Suite flows inside your own network for interfaces that must stay on-premise. That removes the most common reason teams gave for staying on PI/PO.
3. **Neo is closing.** SAP [announced in 2023](https://sapinsider.org/blogs/sap-announces-sunset-of-neo-cloud-environment/) that the SAP BTP Neo environment shuts down on 31 December 2028. Earlier CPI tenants on Neo need to move to the multi-cloud (Cloud Foundry) environment, and that migration is its own small project.
4. **Joule is in the tooling.** SAP has added Joule to Integration Suite so developers can describe a flow in plain language and get a first draft. It speeds up standard scenarios. Complex orchestration with real business logic still needs a senior integration architect.

On commercials: if you are on RISE with SAP, check what SAP BTP entitlement your contract already includes before you buy Integration Suite capacity separately.

## How CPI compares to SAP PI/PO

| Factor | SAP PI/PO | SAP CPI (Integration Suite) |
|---|---|---|
| Deployment | On-premise, your servers | Cloud on SAP BTP; Edge Integration Cell for on-premise runtime |
| Maintenance overhead | High: patching, upgrades, server management | Lower: SAP runs the platform |
| Extensibility | Deep customisation; harder to upgrade | Modular; faster updates; less low-level control |
| Licensing | Static, usually capacity-based | Subscription with message-based metrics |
| Investment direction | Maintenance only, no new features | Active development |
| End of mainstream maintenance | End of 2027 (extended to end of 2030) | Not applicable (cloud service) |

The licensing shift is worth modelling. CPI cost ties to message volume. Some companies save compared with PI/PO. Others find their real integration traffic is higher than they thought and have to optimise flows early. Model it before you migrate.

## Key features and adapters

The building block is the **iFlow** (integration flow). Each iFlow defines how a message moves from source to target: the transformation, the routing rules, and what error handling fires when something fails.

| Feature | What it does |
|---|---|
| Prebuilt integration content | Packages of ready-made iFlows for SAP and common third-party scenarios on the SAP Business Accelerator Hub |
| Graphical flow designer | Web-based designer for building iFlows |
| API Management | API design, publishing, security and monitoring |
| Security | OAuth 2.0, SAML, TLS, certificate management |
| Monitoring | Message logs, error details, retry history, alerting |

**Standard adapters** include SOAP, REST, OData, IDoc, JDBC, SFTP, JMS and AS2, with more for specific SaaS products.

**Scripting.** Complex transformations need Groovy or JavaScript inside the iFlow. CPI is not zero-code beyond standard flows. If nobody on your team can write basic script logic, complex mappings become the bottleneck.

## PI/PO migration: what it actually involves

Migration is not an automatic conversion. Adapter behaviour differs between PI and CPI, and error handling that worked in PI can behave differently in CPI. Some flows need rebuilding. Others move with small changes. SAP's migration tooling and prebuilt content reduce the mechanical work. They do not make the judgement calls about what to rebuild and what to retire.

Here is the wave plan I use as a starting point. Adjust the waves to your own inventory.

| Wave | What moves | Why this order | Owner | Exit criteria |
|---|---|---|---|---|
| 0. Inventory | Every PI interface: frequency, volume, adapter, criticality, owner | You cannot plan what you have not counted | Integration lead | Inventory signed off by business owners |
| 1. Low risk | SAP-to-SAP flows with standard content | Proves the operating model and monitoring | Integration lead | Two weeks stable in production, PI path retired |
| 2. Partners | B2B and EDI flows with key trading partners | Needs partner testing windows and coordinated cutover | Integration lead with procurement and sales | Each partner confirms in writing |
| 3. High risk | High-volume, regulated or revenue-critical flows | Moves last, with the most rehearsal | Integration architect | Volume test passed; fallback to PI rehearsed |
| 4. Retire | PI/PO shut down | Stops paying for two platforms | CIO | All flows migrated or retired; licences ended |

Keep a fallback path to PI for each wave until the new flow has run clean in production. The order matters: prove the operating model on low-risk flows before you touch the interfaces that carry revenue.



## Common integration patterns

The scenarios I see most often:

1. **S/4HANA to SuccessFactors.** Organisational data, headcount and compensation changes. SAP's standard integration content covers the common scenarios; custom flows handle the deviations.
2. **Legacy procurement to SAP Ariba.** Purchase orders out, confirmations and invoices back in. Usually two-directional.
3. **Finance data to SAP Analytics Cloud.** Moving data from ECC or non-SAP systems into SAC.
4. **Salesforce to SAP.** Closed deals flowing into SAP for fulfilment, invoicing and stock updates. Without managed integration this usually runs on spreadsheet exports or fragile scripts. ## Frequently asked questions

<details>
<summary>What is SAP CPI and what is it called now?</summary>

SAP CPI stands for Cloud Platform Integration. It is now the Cloud Integration capability of SAP Integration Suite on SAP BTP, alongside API Management, Event Mesh and partner integration tools. "CPI" is still the everyday name for building integration flows.

</details>

<details>
<summary>How is SAP CPI different from SAP PI/PO?</summary>

PI (Process Integration) and PO (Process Orchestration) are on-premise middleware with deep customisation and full infrastructure control. CPI is a cloud service on SAP BTP that SAP runs for you, with new adapters and content arriving centrally.

PI/PO 7.5 receives maintenance only. Mainstream maintenance ends at the end of 2027 and extended maintenance at the end of 2030, so every PI/PO landscape needs a migration plan.

</details>

<details>
<summary>Is SAP CPI the same as SAP BTP?</summary>

No. SAP BTP is the platform: app development, data, analytics, AI and integration. CPI is the integration service on it. When scoping work, budget and skills differ: a BTP architect works across services, a CPI specialist owns flows, adapters and mappings.

</details>

<details>
<summary>How difficult is SAP CPI to learn?</summary>

Manageable, not simple. Standard flows follow documented patterns and the graphical designer helps. The hard parts are understanding the business process well enough to design the flow, handling errors and retries properly, and writing Groovy or JavaScript for complex mappings. Learn the business process first, then the integration.

</details>

<details>
<summary>What should I consider when migrating from SAP PI/PO to CPI?</summary>

Inventory every interface with volume, frequency, adapter and criticality. Decide for each: rebuild, adapt or retire. Model message-based costs against your real volumes. Move in waves with a fallback path, and plan regression testing with B2B partners and non-SAP targets early, because those break quietly. Use Edge Integration Cell for flows that must stay on-premise.

</details>

<details>
<summary>What is the difference between Neo and Cloud Foundry for SAP CPI?</summary>

Both are SAP BTP environments. Neo is the older, SAP-proprietary environment and shuts down on 31 December 2028. The multi-cloud environment based on Cloud Foundry is where SAP's development goes. Any CPI tenant still on Neo needs a migration plan now; new tenants should not start there.

</details>

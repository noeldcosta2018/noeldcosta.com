SAP CPI（Cloud Platform Integration）是SAP用于连接SAP系统和非SAP系统的云中间件。如今它叫Cloud Integration，是SAP业务技术平台（SAP BTP）上SAP Integration Suite的核心能力。

它在应用之间传输消息，转换消息格式，并把消息路由到正确的目标。如果您还在运行SAP PI/PO，时间就很关键：包含PI/PO的SAP NetWeaver 7.5的主流维护将在2027年底结束。

本指南讲解CPI做什么、它的架构如何运作、它与PI/PO相比如何，以及如何规划迁移。它写给集成负责人和CIO，而不只是开发人员。

## 根据我的经验，CPI为什么重要

我见过团队花几个月时间编写脆弱的自定义脚本来连接SAP和非SAP系统。一开始能用。然后某次系统更新改了一个字段名，或者推出了新的API版本，或者流量翻了一倍。

脚本悄无声息地坏掉。没有人知道，直到某份报表拉取了过时的数据，或者一张订单三天都没被处理。

CPI用受管理、可复用的集成流取代了这种做法。不是因为它更简单（它往往并不简单），而是因为它的架构就是为监控和维护而设计的。CPI设计早期做出的小决定，累积成技术债的速度比大多数团队预想的要快。

我对任何仍在使用SAP PI/PO的公司的建议，是迁移到SAP Integration Suite。我看到的最常见的集成失败，是在集成上花的时间不够。

## SAP CPI是什么，不是什么

[SAP自己的迁移指南](https://help.sap.com/docs/migration-guide-po/migration-guide-for-sap-process-orchestration/introduction-sap-integration-suite)把Cloud Integration描述为在云端、本地和混合环境中设计和运行集成流的能力。它覆盖应用到应用（A2A）、企业到企业（B2B）和企业到政府（B2G）的场景。大多数顾问仍然把它叫作“CPI”或“SAP CI”，这没有问题。

SAP Integration Suite把Cloud Integration与其他能力打包在一起。主要的有API Management、Event Mesh、Integration Advisor、Trading Partner Management、Open Connectors和Migration Assessment。

**CPI做什么：**在系统之间传输数据，转换消息格式，路由到正确的目标，并处理错误和重试。它通过标准适配器连接SAP系统（S/4HANA、SuccessFactors、Ariba）和非SAP平台（Salesforce、Workday、ServiceNow）。

**它不做什么：**长期存储数据、取代ERP，或者充当批量数据迁移的ETL工具。它是为实时或近实时消息而构建的。把它当作数据仓库或迁移工具使用，日后会带来架构问题。

**CPI与SAP BTP：**BTP是整个平台：应用开发、数据、AI、分析和集成。CPI是其中的一项服务。BTP架构师跨服务进行设计；CPI专家负责集成流、适配器、映射和连接。

## SAP CPI架构详解：它在实践中如何运作

下图展示了CPI所面向的集成场景。云到云、本地到云、企业到企业（B2B）、企业到政府（B2G），以及与用户和设备的连接。

![SAP CPI架构图，展示围绕SAP S/4HANA和非SAP应用的云到云、本地到云、B2B和B2G集成](/images/wp/elementor/thumbs/SAP-CPI-r6e607fx79xud4tbbufp2yww164i041nvu8xtwedj4.webp "SAP CPI架构")

理解CPI架构不只是开发人员的事。根据我的经验，在结构层面理解CPI如何处理集成的团队，往往能在一开始就做出更好的设计选择。

CPI作为多租户云服务运行在SAP BTP上。平台由SAP运营，所以您不用维护自己的集成服务器。如果某个流必须在您自己的网络内运行，[Edge Integration Cell](https://help.sap.com/docs/integration-suite/sap-integration-suite/what-is-sap-integration-suite-edge-integration-cell)是一个可选的混合运行时：您在云端设计和监控，在自己的网络中运行流。

### 实践中的消息流

核心是iFlow（集成流）。CPI中的每个集成都建模为一个iFlow，每个iFlow分三个阶段把消息从源传到目标：

1. **发送方适配器。**通过SOAP、REST、OData、IDoc、SFTP、JMS、AS2或其他协议从源系统接收消息。
2. **处理步骤。**映射、格式转换（例如JSON转XML）、基于内容的路由、调用其他系统、加密和错误处理。
3. **接收方适配器。**把处理后的消息发送到目标。

流可以同步或异步运行，取决于用例。选哪一种并不总是一目了然，所以请用真实的数据量把两种都测试一下。

监控的作用很大。您有消息处理日志、跟踪和持久化消息，各有各的用途。在测试或调试时，我通常会根据需要深入的程度，在跟踪和持久化之间切换。

### SAP CPI架构的组件

下表把每个组件对应到它在架构中的职责。

| 组件 | 做什么 | 在架构中的角色 |
|---|---|---|
| 集成流运行时 | 执行iFlow | 在运行时处理路由、映射、转换和安全 |
| 基于Web的设计器 | 用于构建、配置和部署iFlow的图形化编辑器 | 开发人员在这里建模集成流；复杂逻辑仍需要Groovy或JavaScript |
| 适配器 | SOAP、REST、OData、IDoc、JDBC、SFTP、JMS、AS2以及针对特定SaaS的适配器 | 连接云端和本地系统 |
| 安全 | OAuth 2.0、SAML、TLS、证书和密钥管理 | 保护传输中的凭据和消息 |
| 监控和运维 | 消息日志、错误详情、重试、告警 | 让支持团队发现并修复故障 |
| 预置内容 | SAP Business Accelerator Hub上由SAP交付的集成包 | 用经过测试的内容加快标准场景的实施 |
| SAP Cloud Connector | 从您的网络到SAP BTP的安全隧道 | 访问本地系统而不把它们暴露到互联网 |
| Edge Integration Cell | 部署在您自己的数据中心或私有云中的可选运行时 | 用于必须留在本地的集成流 |

Groovy脚本处理图形化步骤无法处理的逻辑。我常常建议尽量少用脚本，因为脚本太多会在以后带来维护问题。集成包有版本管理，所以任何变更都只能通过已部署的集成包进入生产环境。

## 决定集成计划的几个日期

当下几乎每一个集成计划都由三个日期驱动。

<explainer-timeline title="集成计划背后的日期" caption="围绕2027年做计划。在那之前分批迁移，成本远低于被迫切换。" items="2027 => PI/PO主流维护结束|2028 => Neo上的Cloud Integration停止服务|2030 => PI/PO延长维护结束" notes="年底，针对SAP NetWeaver 7.5|12月31日。Neo租户迁移到Cloud Foundry|年底。任何PI/PO系统的最后一站" highlight="1" source="SAP Note 1648480和SAP知识库文章3355661"></explainer-timeline>

1. **PI/PO快走到尽头了。**[SAP Note 1648480](https://me.sap.com/notes/1648480)把包含PI/PO的SAP NetWeaver 7.5的主流维护定到2027年底，延长维护到2030年底。系统不会在2028年1月1日停止运行，但此后每多保留一年，成本都会更高。
2. **Neo即将关闭。**[SAP知识库文章3355661](https://me.sap.com/notes/3355661)确认，SAP BTP Neo环境上的Cloud Integration将于2028年12月31日停止服务。早期部署在Neo上的CPI租户需要迁移到多云（Cloud Foundry）环境，而这次迁移本身就是一个小项目。
3. **混合场景有了答案。**Edge Integration Cell在您自己的网络内运行Integration Suite集成流。这消除了团队留在PI/PO上最常见的理由。

关于商务：如果您使用的是RISE with SAP，在单独购买Integration Suite容量之前，请先确认您的合同已经包含哪些SAP BTP授权。

## CPI与SAP PI/PO相比如何

PI（Process Integration）和PO（Process Orchestration）是SAP的本地中间件。下面是它们与CPI的对比。

| 因素 | SAP PI/PO | SAP CPI（Integration Suite） |
|---|---|---|
| 部署 | 本地，在您的服务器上 | SAP BTP上的云端；Edge Integration Cell提供本地运行时 |
| 维护负担 | 高：打补丁、升级、服务器管理 | 较低：平台由SAP运营 |
| 可扩展性 | 深度定制；升级更难 | 模块化；更新更快；底层控制较少 |
| 许可 | 许可加上您自己的基础设施 | SAP BTP上的订阅，按版本 |
| 投资方向 | 仅维护，没有新功能 | 持续开发 |
| 主流维护结束 | 2027年底（延长至2030年底） | 不适用（云服务） |

SAP的迁移指南把Cloud Integration视为主要的替代方案，因为它覆盖了PI/PO的大部分功能。请向SAP询问您的版本如何计量，然后在迁移之前用您真实的消息量建模。有些公司发现自己的集成流量比想象的要高。

## PI/PO迁移：实际涉及什么

迁移不是自动转换。PI和CPI之间的适配器行为不同，在PI中有效的错误处理在CPI中的表现可能不同。有些集成流需要重建；另一些只需少量修改就能迁移。

SAP提供两个官方工具：

1. **Migration Assessment。**Integration Suite的一项能力，连接到您的PO系统，提取集成场景并估算迁移工作量。[SAP的教程](https://developers.sap.com/tutorials/migration-assessment.html)介绍了设置方法。
2. **Migration Tooling。**Cloud Integration的一项功能，可以[半自动化地把](https://developers.sap.com/tutorials/migration-tool.html)PO中的集成配置对象（ICO）迁移为iFlow。只有被评估为“Ready to migrate”或“Adjustment required”的场景才能用它迁移。

[SAP Learning](https://learning.sap.com/courses/sap-process-orchestration-to-sap-integration-suite-migration/developing-a-migration-approach)明确指出，没有一条迁移路径适合所有客户，许多客户在迁移期间并行运行PI/PO和Integration Suite。这些工具减少了机械性工作。它们不会替您判断哪些该重建、哪些该淘汰。

下面是我作为起点使用的分批计划。请根据您自己的接口清单调整批次。

| 批次 | 迁移什么 | 为什么是这个顺序 | 负责人 | 退出标准 |
|---|---|---|---|---|
| 0. 清单 | 每个PI接口：频率、数据量、适配器、关键程度、负责人 | 没有清点过的东西无法规划 | 集成负责人 | 清单由业务负责人签字确认 |
| 1. 低风险 | 使用标准内容的SAP到SAP集成流 | 验证运营模式和监控 | 集成负责人 | 在生产环境稳定运行两周，PI路径已停用 |
| 2. 合作伙伴 | 与关键贸易伙伴之间的B2B和EDI集成流 | 需要合作伙伴的测试窗口和协调一致的切换 | 集成负责人，会同采购和销售 | 每个合作伙伴书面确认 |
| 3. 高风险 | 大数据量、受监管或关系收入的集成流 | 最后迁移，演练最多 | 集成架构师 | 通过数据量测试；回退到PI已演练 |
| 4. 停用 | 关闭PI/PO | 不再为两个平台付费 | CIO | 所有集成流已迁移或停用；许可已终止 |

在新集成流在生产环境中干净运行之前，每个批次都要保留回退到PI的路径。顺序很重要：在动那些承载收入的接口之前，先在低风险集成流上验证运营模式。

集成测试是时间消失的地方。请尽早规划与B2B合作伙伴和非SAP目标系统的回归测试，因为它们会悄无声息地出问题。我的[SAP测试指南](/zh-CN/sap-testing-explained/)讲解了如何组织集成测试和回归测试周期。

如果PI/PO迁移是某个S/4HANA项目的一部分，请让两个计划保持一致。我的[ECC到S/4HANA迁移指南](/zh-CN/ecc-to-s4hana-migration/)讲解了ERP一侧的路径和截止日期。

## 常见的集成模式

我最常见到的场景：

1. **S/4HANA到SuccessFactors。**组织数据、编制人数和薪酬变动。SAP的标准集成内容覆盖了常见场景；自定义集成流处理偏差情况。
2. **旧采购系统到SAP Ariba。**采购订单发出，确认和发票传回。通常是双向的。
3. **财务数据到SAP Analytics Cloud。**把数据从ECC或非SAP系统传入SAC。
4. **Salesforce到SAP。**已成交的交易流入SAP，用于履约、开票和库存更新。我的[为什么Salesforce与ERP的集成会失败](/zh-CN/why-erp-integration-with-salesforce-fails-and-how-to-fix-it/)一文讲解了其中的设计错误。

如果您项目中的集成工作已经在拖延，[SAP Integration Suite交付延误](/zh-CN/sap-integration-suite-delivery-delays/)讲解了常见原因。[SAP集成平台](/zh-CN/sap-implementation/sap-integration-platforms/)概览则把各个选项并排做了比较。

## 常见问题

<details>
<summary>SAP CPI是什么，现在叫什么？</summary>

SAP CPI是Cloud Platform Integration的缩写。它现在是SAP BTP上SAP Integration Suite中的Cloud Integration能力，与API Management、Event Mesh和合作伙伴集成工具并列。“CPI”仍然是构建集成流时的日常叫法。

</details>

<details>
<summary>SAP CI是什么？</summary>

SAP CI是SAP Cloud Integration的简称，也就是以前SAP CPI的现用名称。两个术语指的是SAP Integration Suite中的同一项能力。

</details>

<details>
<summary>SAP CPI是中间件吗？</summary>

是的。CPI是云中间件：它位于系统之间，转换和路由消息，并处理错误和重试。它取代SAP PI/PO这样的本地中间件，并且不长期存储业务数据。

</details>

<details>
<summary>SAP CPI与SAP PI/PO有什么不同？</summary>

PI/PO是您自己安装、打补丁和运行的本地中间件。CPI是SAP替您运营的SAP BTP云服务，新的适配器和内容集中发布。Edge Integration Cell覆盖必须留在本地的集成流。

</details>

<details>
<summary>SAP PI/PO的支持何时结束？</summary>

包含PI/PO的SAP NetWeaver 7.5的主流维护在2027年底结束。延长维护可以持续到2030年底。SAP提供Migration Assessment和Migration Tooling，帮助把场景迁移到Integration Suite。

</details>

<details>
<summary>SAP CPI和SAP BTP是一回事吗？</summary>

不是。SAP BTP是平台：应用开发、数据、分析、AI和集成。CPI是平台上的集成服务。

在确定工作范围时，预算和技能是不同的：BTP架构师跨服务工作，CPI专家负责集成流、适配器和映射。

</details>

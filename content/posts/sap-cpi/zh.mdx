SAP CPI（Cloud Platform Integration）是SAP的云中间件。如今它是SAP BTP上SAP Integration Suite里的Cloud Integration功能，也是SAP给出的答案，用来把S/4HANA与其他SAP及非SAP系统连接起来。如果您仍在运行SAP PI/PO，时间就很关键：PI/PO 7.5将在2027年底结束主流维护。

这份指南写给正在决定如何从PI/PO迁出、或为新的S/4HANA项目设计集成方案的集成负责人和CIO。内容包括CPI能做什么、不能做什么，它与PI/PO如何对比，以及迁移接口的分波次计划。

我见过团队花上几个月，写出脆弱的自定义脚本来连接SAP和非SAP系统。起初能跑。后来，一次系统更新改了字段名，或者新的API版本上线，或者流量翻了一倍。脚本悄无声息地坏了。直到某份报表拉到了过期数据，或者某个订单三天都没人处理，才有人发现。

CPI用受管理、可复用的集成流取代这种做法。并不是因为它更简单（往往并不简单），而是因为它的架构本来就是为了便于监控和维护。CPI设计早期做出的小决定，累积成技术债的速度比大多数团队预想的要快。

## SAP CPI是什么，不是什么

CPI是连接系统、转换数据并在应用之间路由消息的那一层。SAP Integration Suite把它与API Management、Event Mesh、Integration Advisor和贸易伙伴管理捆绑在一起。大多数顾问说“CPI”时指的仍是集成流这一部分，这样说没问题。

**CPI能做什么：** 在系统之间传输数据，转换消息格式，路由到正确的目标，并处理错误和重试。它通过标准适配器连接SAP系统（S/4HANA、SuccessFactors、Ariba）和非SAP平台（Salesforce、Workday、ServiceNow）。

**它不能做什么：** 长期存储数据、取代ERP，或者充当批量数据迁移的ETL工具。它是为实时或近实时消息设计的。把它当数据仓库或迁移工具用，后面会出架构问题。

**CPI与SAP BTP的区别：** BTP是整个平台：应用开发、数据、AI、分析和集成。CPI是其中的一项服务。界定技能和预算时，这个区别很重要。BTP架构师跨服务做设计。CPI专家负责流程、适配器、映射和连通性。

## 2026年发生了什么变化

如今任何集成规划都离不开四个时间点和决策。

<explainer-timeline title="集成规划背后的时间节点" caption="以2027年为节点来规划。在此之前分波次迁移，成本远低于被迫一次性切换。" items="2023年 => Edge Integration Cell正式发布|2027年 => PI/PO主流维护结束|2028年 => SAP BTP Neo环境关闭|2030年 => PI/PO延长维护结束" notes="2023年底，在您自己的网络内运行Integration Suite流程|年底，针对SAP NetWeaver 7.5|12月31日，Neo上的CPI租户迁往Cloud Foundry|年底，所有PI/PO系统环境的最后一站" highlight="2" source="SAP NetWeaver 7.5维护与Neo停用公告，来自SAPinsider报道"></explainer-timeline>

1. **PI/PO的路快走到头了。** [SAP NetWeaver 7.5（包含PI/PO）沿用Business Suite的维护时间表](https://sapinsider.org/blogs/sap-extends-maintenance-for-sap-netweaver-7-5-and-sap-bw-4hana/)：主流维护到2027年底，延长维护到2030年底。不会再有新功能。有计划、分波次的迁移，成本远低于在2027年或2030年被迫一次性切换。
2. **混合部署有了答案。** Edge Integration Cell自2023年底起正式发布，可以在您自己的网络内运行Integration Suite流程，适用于必须留在本地的接口。这就去掉了团队选择继续留在PI/PO上最常见的理由。
3. **Neo即将关闭。** SAP在[2023年宣布](https://sapinsider.org/blogs/sap-announces-sunset-of-neo-cloud-environment/)，SAP BTP Neo环境将于2028年12月31日关闭。早期部署在Neo上的CPI租户需要迁移到多云（Cloud Foundry）环境，这次迁移本身就是一个小项目。
4. **Joule已进入开发工具。** SAP已把Joule加入Integration Suite，开发人员可以用自然语言描述一个流程，并得到初稿。它能加快标准场景的开发。带有真实业务逻辑的复杂编排，仍然需要资深的集成架构师。

商务方面：如果您使用的是RISE with SAP，在单独购买Integration Suite容量之前，请先查清您的合同已经包含哪些SAP BTP使用权限。

## CPI与SAP PI/PO的对比

| 对比项 | SAP PI/PO | SAP CPI（Integration Suite） |
|---|---|---|
| 部署方式 | 本地部署，运行在您自己的服务器上 | SAP BTP上的云服务；本地运行时用Edge Integration Cell |
| 维护负担 | 高：打补丁、升级、服务器管理 | 较低：由SAP运营平台 |
| 可扩展性 | 可深度定制，但升级更难 | 模块化，更新更快，底层控制较少 |
| 许可 | 固定，通常按容量计 | 订阅制，按消息量计量 |
| 投入方向 | 仅维护，无新功能 | 持续开发 |
| 主流维护结束时间 | 2027年底（延长维护至2030年底） | 不适用（云服务） |

许可模式的转变值得建模测算。CPI的费用与消息量挂钩。有些企业相比PI/PO能省钱。也有企业发现自己的实际集成流量比想象的高，不得不提早优化流程。迁移之前先测算一下。

## 主要功能与适配器

基本构件是**iFlow**（集成流）。每个iFlow定义一条消息如何从源端传到目标端：转换方式、路由规则，以及出错时触发什么样的错误处理。

| 功能 | 作用 |
|---|---|
| 预置集成内容 | SAP Business Accelerator Hub上针对SAP及常见第三方场景的现成iFlow包 |
| 图形化流程设计器 | 基于Web的iFlow设计器 |
| API Management | API的设计、发布、安全与监控 |
| 安全 | OAuth 2.0、SAML、TLS、证书管理 |
| 监控 | 消息日志、错误详情、重试记录、告警 |

**标准适配器**包括SOAP、REST、OData、IDoc、JDBC、SFTP、JMS和AS2，另有针对特定SaaS产品的更多适配器。

**脚本。** 复杂的转换需要在iFlow中使用Groovy或JavaScript。超出标准流程的部分，CPI并不是零代码。如果您的团队里没有人能写基本的脚本逻辑，复杂映射就会成为瓶颈。

## PI/PO迁移：实际涉及什么

迁移不是自动转换。适配器在PI和CPI中的行为有差异，在PI里运行良好的错误处理，到了CPI中可能表现不同。有些流程需要重建，另一些只需小改即可迁移。SAP的迁移工具和预置内容可以减少机械性的工作，但哪些该重建、哪些该淘汰，这类判断它们替您做不了。

下面是我作为起点使用的分波次计划。请按您自己的接口清单调整各个波次。

| 波次 | 迁移内容 | 为什么按这个顺序 | 负责人 | 退出标准 |
|---|---|---|---|---|
| 0. 盘点 | 每一个PI接口：频率、消息量、适配器、关键程度、负责人 | 没数清楚的东西，就没法规划 | 集成负责人 | 清单经业务负责人签字确认 |
| 1. 低风险 | 使用标准内容的SAP到SAP流程 | 验证运营模式和监控 | 集成负责人 | 生产环境稳定运行两周，下线PI路径 |
| 2. 合作伙伴 | 与主要贸易伙伴之间的B2B和EDI流程 | 需要合作伙伴的测试窗口和协调一致的切换 | 集成负责人，会同采购和销售 | 每个合作伙伴书面确认 |
| 3. 高风险 | 高流量、受监管或关乎营收的流程 | 最后迁移，演练最充分 | 集成架构师 | 通过大流量测试；已演练回退到PI |
| 4. 退役 | 关闭PI/PO | 不再为两个平台同时付费 | CIO | 所有流程均已迁移或淘汰，许可已终止 |

每个波次都要保留回退到PI的路径，直到新流程在生产环境中运行无误。顺序很重要：先在低风险流程上验证运营模式，再去碰承载营收的接口。

## 常见的集成模式

我最常见到的场景：

1. **S/4HANA到SuccessFactors。** 组织数据、编制人数和薪酬变动。SAP的标准集成内容覆盖了常见场景，偏离标准的部分由自定义流程处理。
2. **遗留采购系统到SAP Ariba。** 采购订单送出，确认和发票传回。通常是双向的。
3. **财务数据到SAP Analytics Cloud。** 把ECC或非SAP系统中的数据送入SAC。
4. **Salesforce到SAP。** 成交的订单流入SAP，用于履约、开票和库存更新。没有受管理的集成时，这通常靠导出表格或脆弱的脚本来运行。我写的[Salesforce与ERP集成为什么会失败](/zh-CN/why-erp-integration-with-salesforce-fails-and-how-to-fix-it/)一文讲了其中的设计错误。

如果您项目中的集成工作已经开始延期，[SAP Integration Suite交付延误](/zh-CN/sap-integration-suite-delivery-delays/)一文讲了常见原因。[SAP集成平台](/zh-CN/sap-implementation/sap-integration-platforms/)的平台概览则把各个选项并排做了比较。

## 常见问题

<details>
<summary>SAP CPI是什么，现在叫什么？</summary>

SAP CPI是Cloud Platform Integration的缩写。它现在是SAP BTP上SAP Integration Suite的Cloud Integration功能，与API Management、Event Mesh和合作伙伴集成工具并列。构建集成流时，人们日常仍然叫它“CPI”。

</details>

<details>
<summary>SAP CPI与SAP PI/PO有什么不同？</summary>

PI（Process Integration）和PO（Process Orchestration）是本地部署的中间件，可深度定制，基础设施完全由您掌控。CPI是SAP BTP上的云服务，由SAP替您运营，新的适配器和内容由SAP统一推送。

PI/PO 7.5只提供维护。主流维护在2027年底结束，延长维护在2030年底结束，因此每一套PI/PO系统环境都需要一份迁移计划。

</details>

<details>
<summary>SAP CPI等同于SAP BTP吗？</summary>

不是。SAP BTP是平台：应用开发、数据、分析、AI和集成。CPI是其上的集成服务。界定工作范围时，预算和技能要求都不同：BTP架构师跨服务工作，CPI专家负责流程、适配器和映射。

</details>

<details>
<summary>SAP CPI学起来难吗？</summary>

能学会，但不简单。标准流程有文档化的模式可循，图形化设计器也有帮助。难点在于：把业务流程理解到足以设计流程的程度，妥善处理错误和重试，以及为复杂映射编写Groovy或JavaScript。先学业务流程，再学集成。

</details>

<details>
<summary>从SAP PI/PO迁移到CPI时需要考虑什么？</summary>

把每个接口的消息量、频率、适配器和关键程度都盘点清楚。对每一个接口做出决定：重建、调整还是淘汰。按真实消息量测算按消息计费的成本。分波次迁移并保留回退路径，同时尽早规划与B2B合作伙伴及非SAP目标系统的回归测试，因为这些地方出问题往往悄无声息。必须留在本地的流程，用Edge Integration Cell。

</details>

<details>
<summary>对SAP CPI而言，Neo与Cloud Foundry有什么区别？</summary>

两者都是SAP BTP的环境。Neo是较早的、SAP专有的环境，将于2028年12月31日关闭。基于Cloud Foundry的多云环境，才是SAP未来的发展方向。仍在Neo上的CPI租户现在就需要一份迁移计划，新租户不应再从那里起步。

</details>

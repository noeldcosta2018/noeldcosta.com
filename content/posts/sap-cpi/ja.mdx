SAP CPI（Cloud Platform Integration）は、SAPのクラウドミドルウェアです。現在はSAP BTP上のSAP Integration Suiteの中で、Cloud Integration機能として提供されており、S/4HANAをほかのSAPシステムや非SAPシステムにつなぐためのSAPの答えです。まだSAP PI/POを使っているなら、時間の制約が重要になります。PI/PO 7.5のメインストリームメンテナンスは、2027年末に終了します。

本ガイドは、PI/POからの移行を検討している、あるいは新しいS/4HANAプログラムの連携を設計するインテグレーションリードやCIO向けです。CPIにできること、できないこと、PI/POとの比較、そしてインタフェースを移行するためのウェーブ計画を取り上げます。

私は、SAPと非SAPのシステムをつなぐために、壊れやすいカスタムスクリプトを作り込むのに何か月も費やすチームを見てきました。最初はうまく動きます。そのうちシステムの更新でフィールド名が変わったり、新しいAPIバージョンがリリースされたり、トラフィックが倍になったりします。スクリプトは音もなく壊れます。レポートが古いデータを引いてくる、あるいは受注が3日間処理されないまま放置される、そこまで誰も気づきません。

CPIはそれを、管理された再利用可能なインテグレーションフローに置き換えます。単純になるからではありません（むしろ単純でないことが多いです）。監視と保守を前提にアーキテクチャが作られているからです。CPIの設計の初期に下した小さな判断は、多くのチームが予想するより早く技術的負債になります。

## SAP CPIとは何か、何ではないか

CPIは、システムをつなぎ、データを変換し、アプリケーション間でメッセージをルーティングする層です。SAP Integration Suiteは、これにAPI Management、Event Mesh、Integration Advisor、取引パートナー管理を加えたものです。ほとんどのコンサルタントは、今もインテグレーションフローの部分を指して「CPI」と呼びますが、それで問題ありません。

**CPIにできること：** システム間のデータ移動、メッセージ形式の変換、適切な宛先へのルーティング、エラー処理とリトライ。標準アダプタを通じて、SAPシステム（S/4HANA、SuccessFactors、Ariba）や非SAPのプラットフォーム（Salesforce、Workday、ServiceNow）に接続します。

**できないこと：** データの長期保存、ERPの代替、大量データ移行のためのETLツールとしての利用。リアルタイムまたはそれに近いメッセージ向けに作られています。データウェアハウスや移行ツールとして使うと、あとでアーキテクチャ上の問題が起きます。

**CPIとSAP BTPの違い：** BTPはプラットフォーム全体で、アプリケーション開発、データ、AI、分析、連携を含みます。CPIはその上の一つのサービスです。スキルと予算の範囲を決めるとき、この違いが重要です。BTPアーキテクトはサービス全体にわたって設計します。CPIスペシャリストは、フロー、アダプタ、マッピング、接続を担当します。

## 2026年時点で変わったこと

現在の連携計画を形づくるのは、4つの日付と判断です。

<explainer-timeline title="連携計画の背景にある日付" caption="2027年を軸に計画してください。それまでにウェーブ方式で移行するほうが、強制的な切替よりはるかに低コストです。" items="2023 => Edge Integration Cell一般提供開始|2027 => PI/POのメインストリームメンテナンス終了|2028 => SAP BTP Neo環境の終了|2030 => PI/POの延長メンテナンス終了" notes="2023年後半。自社ネットワーク内でIntegration Suiteのフローを実行|年末、SAP NetWeaver 7.5の場合|12月31日。NeoのCPIテナントはCloud Foundryへ移行|年末。PI/POランドスケープの最後の期限" highlight="2" source="SAP NetWeaver 7.5のメンテナンスとNeoのサンセットに関する発表、SAPinsider報道"></explainer-timeline>

1. **PI/POは先が見えてきました。** [PI/POを含むSAP NetWeaver 7.5は、Business Suiteのメンテナンス予定に沿っています](https://sapinsider.org/blogs/sap-extends-maintenance-for-sap-netweaver-7-5-and-sap-bw-4hana/)。メインストリームメンテナンスは2027年末まで、延長メンテナンスは2030年末までです。新機能は追加されません。計画的なウェーブ方式の移行は、2027年や2030年に迫られる強制的な切替よりはるかに低コストです。
2. **ハイブリッドにも答えがあります。** 2023年後半から一般提供されているEdge Integration Cellは、Integration Suiteのフローを自社ネットワーク内で実行します。オンプレミスに残す必要があるインタフェース向けです。これで、PI/POに残る理由として多くのチームが挙げてきた最大の理由がなくなります。
3. **Neoは終了します。** SAPは[2023年に発表しました](https://sapinsider.org/blogs/sap-announces-sunset-of-neo-cloud-environment/)。SAP BTP Neo環境は2028年12月31日に終了します。Neo上にある以前のCPIテナントは、マルチクラウド（Cloud Foundry）環境へ移行する必要があり、その移行は小さなプロジェクトになります。
4. **Jouleがツールに組み込まれています。** SAPはIntegration SuiteにJouleを追加し、開発者がフローを平易な言葉で説明すると、最初のドラフトが得られるようになりました。標準的なシナリオは速くなります。業務ロジックを伴う複雑なオーケストレーションには、引き続き経験豊富なインテグレーションアーキテクトが必要です。

契約面では、RISE with SAPをご利用なら、Integration Suiteの容量を別途購入する前に、契約にすでにどのSAP BTPのエンタイトルメントが含まれているかを確認してください。

## CPIとSAP PI/POの比較

| 要素 | SAP PI/PO | SAP CPI（Integration Suite） |
|---|---|---|
| デプロイ | オンプレミス、自社サーバー | SAP BTP上のクラウド。オンプレミスで実行する場合はEdge Integration Cell |
| 保守の負担 | 大きい：パッチ適用、アップグレード、サーバー管理 | 小さい：プラットフォームはSAPが運用 |
| 拡張性 | 深いカスタマイズが可能。アップグレードは難しい | モジュール式。更新は速い。低レベルの制御は少ない |
| ライセンス | 固定的。通常は容量ベース | サブスクリプション。メッセージ数ベースの指標 |
| 投資の方向性 | 保守のみ、新機能なし | 活発に開発中 |
| メインストリームメンテナンスの終了 | 2027年末（延長は2030年末まで） | 該当なし（クラウドサービス） |

ライセンスの変化は、モデル化しておく価値があります。CPIのコストはメッセージ量に連動します。PI/POより安くなる企業もあります。一方で、実際の連携トラフィックが想定より多いと分かり、早めにフローを最適化しなければならなくなる企業もあります。移行する前に試算してください。

## 主な機能とアダプタ

基本単位は**iFlow**（インテグレーションフロー）です。各iFlowは、メッセージがソースからターゲットへどう流れるかを定義します。変換、ルーティングのルール、障害時に起動するエラー処理です。

| 機能 | 内容 |
|---|---|
| 構築済みの連携コンテンツ | SAP Business Accelerator Hubにある、SAPや一般的なサードパーティのシナリオ向けの、すぐ使えるiFlowのパッケージ |
| グラフィカルなフローデザイナー | iFlowを構築するWebベースのデザイナー |
| API Management | APIの設計、公開、セキュリティ、監視 |
| セキュリティ | OAuth 2.0、SAML、TLS、証明書管理 |
| モニタリング | メッセージログ、エラーの詳細、リトライ履歴、アラート |

**標準アダプタ**には、SOAP、REST、OData、IDoc、JDBC、SFTP、JMS、AS2があり、特定のSaaS製品向けにはさらに用意されています。

**スクリプト。** 複雑な変換には、iFlowの中でGroovyまたはJavaScriptが必要です。標準フローを超える範囲では、CPIはノーコードではありません。チームに基本的なスクリプトを書ける人がいなければ、複雑なマッピングがボトルネックになります。

## PI/POの移行：実際に何が必要か

移行は、自動変換ではありません。PIとCPIではアダプタの挙動が異なり、PIで動いていたエラー処理がCPIでは違う動きをすることがあります。作り直しが必要なフローもあれば、小さな変更で移せるものもあります。SAPの移行ツールと構築済みコンテンツは、機械的な作業を減らします。ただし、何を作り直し、何を廃止するかという判断までは代わってくれません。

私が出発点として使うウェーブ計画は次のとおりです。ウェーブは、自社のインベントリに合わせて調整してください。

| ウェーブ | 移行するもの | この順序にする理由 | 担当 | 完了基準 |
|---|---|---|---|---|
| 0. 棚卸し | PIのすべてのインタフェース：頻度、量、アダプタ、重要度、オーナー | 数えていないものは計画できない | インテグレーションリード | 業務オーナーが棚卸しを承認 |
| 1. 低リスク | 標準コンテンツを使うSAPからSAPへのフロー | 運用モデルとモニタリングを実証する | インテグレーションリード | 本番で2週間安定稼働、PI側の経路を廃止 |
| 2. パートナー | 主要な取引パートナーとのB2BおよびEDIのフロー | パートナーのテスト期間と調整したカットオーバーが必要 | インテグレーションリードと、調達および営業 | 各パートナーが書面で確認 |
| 3. 高リスク | 大量、規制対象、または収益に直結するフロー | 最後に移行し、リハーサルを最も重ねる | インテグレーションアーキテクト | ボリュームテストに合格、PIへのフォールバックをリハーサル済み |
| 4. 廃止 | PI/POを停止 | 2つのプラットフォームへの支払いを止める | CIO | すべてのフローを移行または廃止、ライセンスを終了 |

各ウェーブについて、新しいフローが本番で問題なく動くまでは、PIへのフォールバック経路を残しておいてください。順序が重要です。収益を担うインタフェースに手を付ける前に、低リスクのフローで運用モデルを実証してください。

## よくある連携パターン

私がもっともよく目にするシナリオです。

1. **S/4HANAからSuccessFactorsへ。** 組織データ、人員数、報酬の変更。SAP標準の連携コンテンツで一般的なシナリオはカバーされ、例外はカスタムフローで対応します。
2. **従来の調達システムからSAP Aribaへ。** 発注を送り出し、確認と請求書を受け取ります。通常は双方向です。
3. **財務データからSAP Analytics Cloudへ。** ECCまたは非SAPシステムのデータをSACへ移します。
4. **SalesforceからSAPへ。** 成約した案件が、出荷、請求、在庫更新のためにSAPへ流れます。管理された連携がなければ、これは通常、スプレッドシートのエクスポートや壊れやすいスクリプトで動いています。設計上のミスについては、私の記事[SalesforceとERPの連携が失敗する理由](/ja/why-erp-integration-with-salesforce-fails-and-how-to-fix-it/)で取り上げています。

プログラムで連携作業がすでに遅れている場合は、[SAP Integration Suiteのデリバリー遅延](/ja/sap-integration-suite-delivery-delays/)で、よくある原因を取り上げています。[SAP連携プラットフォーム](/ja/sap-implementation/sap-integration-platforms/)の概要ページでは、選択肢を並べて比較しています。

## よくある質問

<details>
<summary>SAP CPIとは何ですか。現在の正式名称は何ですか？</summary>

SAP CPIはCloud Platform Integrationの略です。現在は、SAP BTP上のSAP Integration SuiteのCloud Integration機能で、API Management、Event Mesh、パートナー連携ツールと並ぶ位置づけです。インテグレーションフローを構築する作業については、今も「CPI」が日常的な呼び名です。

</details>

<details>
<summary>SAP CPIとSAP PI/POはどう違いますか？</summary>

PI（Process Integration）とPO（Process Orchestration）は、深いカスタマイズが可能で、インフラを完全に制御できるオンプレミスのミドルウェアです。CPIはSAP BTP上のクラウドサービスで、SAPが運用し、新しいアダプタやコンテンツは中央から提供されます。

PI/PO 7.5は保守のみが提供されます。メインストリームメンテナンスは2027年末、延長メンテナンスは2030年末に終了するため、すべてのPI/POランドスケープに移行計画が必要です。

</details>

<details>
<summary>SAP CPIとSAP BTPは同じものですか？</summary>

いいえ。SAP BTPはプラットフォームで、アプリケーション開発、データ、分析、AI、連携を含みます。CPIはその上の連携サービスです。作業を見積もるとき、予算とスキルは異なります。BTPアーキテクトはサービス全体にわたって働き、CPIスペシャリストはフロー、アダプタ、マッピングを担当します。

</details>

<details>
<summary>SAP CPIの習得はどのくらい難しいですか？</summary>

手に負えないわけではありませんが、簡単でもありません。標準フローは文書化されたパターンに沿っており、グラフィカルなデザイナーが助けになります。難しいのは、フローを設計できるほど業務プロセスを理解すること、エラー処理とリトライを適切に扱うこと、複雑なマッピングのためにGroovyやJavaScriptを書くことです。先に業務プロセスを学び、それから連携を学んでください。

</details>

<details>
<summary>SAP PI/POからCPIへ移行するとき、何を考慮すべきですか？</summary>

すべてのインタフェースを、量、頻度、アダプタ、重要度とともに棚卸しします。それぞれについて、作り直す、調整する、廃止するのいずれかを決めます。メッセージ数ベースのコストを、実際の量に対して試算します。フォールバック経路を確保してウェーブで移行し、B2Bパートナーと非SAPのターゲットのリグレッションテストは早めに計画してください。そこは音もなく壊れるからです。オンプレミスに残す必要があるフローには、Edge Integration Cellを使います。

</details>

<details>
<summary>SAP CPIにおけるNeoとCloud Foundryの違いは何ですか？</summary>

どちらもSAP BTPの環境です。NeoはSAP独自の古い環境で、2028年12月31日に終了します。Cloud Foundryをベースにしたマルチクラウド環境が、SAPの開発の中心です。いまもNeoにあるCPIテナントは、今すぐ移行計画が必要です。新しいテナントをNeoで始めてはいけません。

</details>

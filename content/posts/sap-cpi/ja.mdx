SAP CPI（Cloud Platform Integration）は、SAPシステムとSAP以外のシステムを接続するための、SAPのクラウドミドルウェアです。現在はCloud Integrationと呼ばれ、SAP Business Technology Platform（SAP BTP）上のSAP Integration Suiteの中核機能になっています。

アプリケーション間でメッセージを移動し、形式を変換し、適切なターゲットへルーティングします。まだSAP PI/POを使っているなら、時間が重要です。PI/POを含むSAP NetWeaver 7.5のメインストリームメンテナンスは、2027年末に終了します。

このガイドでは、CPIの機能、アーキテクチャの仕組み、PI/POとの比較、そして移行の計画方法を取り上げます。開発者だけでなく、連携のリーダーやCIOに向けて書いています。

## 私の経験から見た、CPIが重要な理由

SAPシステムとSAP以外のシステムを接続するために、壊れやすい独自スクリプトの構築に何か月も費やすチームを見てきました。最初は動きます。そのうち、システムの更新で項目名が変わったり、新しいAPIバージョンが公開されたり、トラフィックが倍増したりします。

スクリプトは静かに壊れます。レポートが古いデータを取り込んだり、受注が3日間処理されずに残ったりするまで、誰も気づきません。

CPIは、それを管理された再利用可能なインテグレーションフローに置き換えます。シンプルだからではありません（たいていシンプルではありません）。アーキテクチャが、監視と保守を前提に作られているからです。CPIの設計の初期に下した小さな判断は、多くのチームが予想するよりも速く技術的負債として積み上がります。

まだSAP PI/POを使っている企業への私の助言は、SAP Integration Suiteへ移行することです。私が最もよく目にする連携の失敗は、連携に十分な時間をかけないことです。

## SAP CPIとは何か、何ではないか

[SAP自身の移行ガイド](https://help.sap.com/docs/migration-guide-po/migration-guide-for-sap-process-orchestration/introduction-sap-integration-suite)は、Cloud Integrationを、クラウド、オンプレミス、ハイブリッドの構成にわたってインテグレーションフローを設計・実行するための機能と説明しています。アプリケーション間（A2A）、企業間（B2B）、企業と政府機関の間（B2G）のシナリオをカバーします。今でもほとんどのコンサルタントは「CPI」や「SAP CI」と呼んでおり、それで問題ありません。

SAP Integration Suiteは、Cloud Integrationをほかの機能とまとめたものです。主なものは、API Management、Event Mesh、Integration Advisor、Trading Partner Management、Open Connectors、Migration Assessmentです。

**CPIがすること：** システム間でデータを移動し、メッセージ形式を変換し、適切なターゲットへルーティングし、エラーと再試行を処理します。標準アダプタを通じて、SAPシステム（S/4HANA、SuccessFactors、Ariba）とSAP以外のプラットフォーム（Salesforce、Workday、ServiceNow）を接続します。

**CPIがしないこと：** データの長期保存、ERPの代替、大量データ移行のためのETLツールとしての役割です。リアルタイムまたはほぼリアルタイムのメッセージのために作られています。データウェアハウスや移行ツールとして使うと、後でアーキテクチャの問題を引き起こします。

**CPIとSAP BTPの違い：** BTPはプラットフォーム全体です。アプリケーション開発、データ、AI、アナリティクス、連携を含みます。CPIはその上の1つのサービスです。BTPアーキテクトはサービス全体にわたって設計し、CPIのスペシャリストはフロー、アダプタ、マッピング、接続を担当します。

下の図は、CPIが想定している連携シナリオを示しています。クラウド間、オンプレミスとクラウド間、企業間（B2B）、企業と政府機関の間（B2G）、そしてユーザーやデバイスとの接続です。

![SAP S/4HANAとSAP以外のアプリケーションを中心に、クラウド間、オンプレミスとクラウド間、B2B、B2Gの連携を示すSAP CPIのアーキテクチャ構成図](/images/wp/elementor/thumbs/SAP-CPI-r6e607fx79xud4tbbufp2yww164i041nvu8xtwedj4.webp "SAP CPIのアーキテクチャ")

CPIのアーキテクチャを理解することは、開発者だけの仕事ではありません。私の経験では、CPIが構造のレベルで連携をどう扱うかを把握しているチームほど、最初の段階でよい設計判断を下します。

CPIは、SAP BTP上でマルチテナントのクラウドサービスとして動きます。SAPがプラットフォームを運用するため、自社で連携サーバーを保守する必要はありません。フローを自社のネットワーク内で実行しなければならない場合は、オプションのハイブリッドランタイムである[Edge Integration Cell](https://help.sap.com/docs/integration-suite/sap-integration-suite/what-is-sap-integration-suite-edge-integration-cell)があります。設計と監視はクラウドで行い、フローは自社のネットワークで実行します。

### 実際のメッセージの流れ

中心にあるのはiFlow（インテグレーションフロー）です。CPIのすべての連携はiFlowとしてモデル化され、各iFlowは3つの段階でメッセージをソースからターゲットへ移動します。

1. **送信側アダプタ。** SOAP、REST、OData、IDoc、SFTP、JMS、AS2などのプロトコルで、ソースシステムからメッセージを受け取ります。
2. **処理ステップ。** マッピング、形式変換（たとえばJSONからXMLへ）、コンテンツベースのルーティング、ほかのシステムの呼び出し、暗号化、エラー処理です。
3. **受信側アダプタ。** 処理済みのメッセージをターゲットへ送ります。

フローは、ユースケースに応じて同期でも非同期でも実行されます。どちらを選ぶべきかは必ずしも明らかではないため、実際のボリュームで両方をテストしてください。

監視が大きな役割を果たします。メッセージ処理ログ、トレース、永続化されたメッセージがあり、それぞれ目的が異なります。テストやデバッグの間、私はどこまで深く調べる必要があるかに応じて、トレースと永続化を切り替えることが多いです。

### SAP CPIアーキテクチャの構成要素

各構成要素を、アーキテクチャにおける役割に対応させた表です。

| 構成要素 | 何をするか | アーキテクチャにおける役割 |
|---|---|---|
| インテグレーションフローのランタイム | iFlowを実行する | 実行時にルーティング、マッピング、変換、セキュリティを処理する |
| Webベースのデザイナー | iFlowを構築、設定、デプロイするグラフィカルエディター | 開発者がフローをモデル化する場所。複雑なロジックには依然としてGroovyかJavaScriptが必要 |
| アダプタ | SOAP、REST、OData、IDoc、JDBC、SFTP、JMS、AS2、SaaS固有のアダプタ | クラウドとオンプレミスのシステムを接続する |
| セキュリティ | OAuth 2.0、SAML、TLS、証明書と鍵の管理 | 認証情報と転送中のメッセージを保護する |
| 監視と運用 | メッセージログ、エラーの詳細、再試行、アラート | サポートチームが障害を見つけて修正できるようにする |
| 事前パッケージ化されたコンテンツ | SAP Business Accelerator HubでSAPが提供する連携パッケージ | テスト済みのコンテンツで標準シナリオを迅速化する |
| SAP Cloud Connector | 自社ネットワークからSAP BTPへの安全なトンネル | オンプレミスのシステムをインターネットに公開せずに接続する |
| Edge Integration Cell | 自社のデータセンターやプライベートクラウドで動くオプションのランタイム | オンプレミスに留める必要があるフロー向け |

グラフィカルなステップでは扱えないロジックは、Groovyスクリプトが処理します。スクリプトが多すぎると後で保守の問題につながるため、私はこれを最小限に抑えるよう勧めることがよくあります。パッケージはバージョン管理されているため、デプロイされたパッケージ以外から本番に変更が入ることはありません。

## 連携計画を左右する日付

現在、ほぼすべての連携計画を3つの日付が左右しています。

<explainer-timeline title="連携計画の背景にある日付" caption="2027年を軸に計画してください。それまでにウェーブ方式で移行すれば、強制的な切替よりはるかに安く済みます。" items="2027年 => PI/POのメインストリームメンテナンス終了|2028年 => Neo上のCloud Integration終了|2030年 => PI/POの延長メンテナンス終了" notes="SAP NetWeaver 7.5について、年末|12月31日。NeoのテナントはCloud Foundryへ移行|年末。すべてのPI/POシステムにとって最後の期限" highlight="1" source="SAP Note 1648480およびSAPナレッジベース記事3355661"></explainer-timeline>

1. **PI/POに残された時間は少なくなっています。** [SAP Note 1648480](https://me.sap.com/notes/1648480)は、PI/POを含むSAP NetWeaver 7.5のメインストリームメンテナンスを2027年末まで、延長メンテナンスを2030年末までと定めています。2028年1月1日にシステムが止まるわけではありませんが、それ以降は年を追うごとに維持コストが上がります。
2. **Neoは終了します。** [SAPナレッジベース記事3355661](https://me.sap.com/notes/3355661)は、SAP BTP Neo環境上のCloud Integrationが2028年12月31日に終了することを確認しています。Neo上の初期のCPIテナントはマルチクラウド（Cloud Foundry）環境へ移る必要があり、その移行自体が小さなプロジェクトになります。
3. **ハイブリッドには答えがあります。** Edge Integration Cellは、Integration Suiteのフローを自社のネットワーク内で実行します。これで、チームがPI/POに留まる理由として最もよく挙げていたものがなくなります。

契約面について：RISE with SAPを利用しているなら、Integration Suiteの容量を別途購入する前に、契約にすでにどのSAP BTPの利用権が含まれているかを確認してください。

## CPIとSAP PI/POの比較

PI（Process Integration）とPO（Process Orchestration）は、SAPのオンプレミスのミドルウェアです。CPIとの比較は次のとおりです。

| 要素 | SAP PI/PO | SAP CPI（Integration Suite） |
|---|---|---|
| 導入形態 | オンプレミス、自社のサーバー | SAP BTP上のクラウド。オンプレミスのランタイムにはEdge Integration Cell |
| 保守の負担 | 高い：パッチ適用、アップグレード、サーバー管理 | 低い：SAPがプラットフォームを運用 |
| 拡張性 | 深いカスタマイズが可能。アップグレードは難しくなる | モジュール型。更新が速い。低レベルの制御は少ない |
| ライセンス | ライセンスに加えて自社のインフラ | SAP BTP上のサブスクリプション、エディション別 |
| 投資の方向性 | 保守のみ、新機能なし | 積極的に開発中 |
| メインストリームメンテナンスの終了 | 2027年末（延長は2030年末まで） | 該当なし（クラウドサービス） |

SAPの移行ガイドは、PI/POの機能の大半をカバーすることから、Cloud Integrationを主な後継として扱っています。ご自身のエディションがどのように計量されるかをSAPに確認し、移行の前に実際のメッセージ量に照らしてモデル化してください。連携のトラフィックが想定より多いことに気づく企業もあります。

## PI/POの移行：実際に何が必要か

移行は自動変換ではありません。アダプタの動作はPIとCPIで異なり、PIで機能していたエラー処理がCPIでは違う動きをすることがあります。作り直しが必要なフローもあれば、小さな変更で移せるフローもあります。

SAPは公式ツールを2つ提供しています。

1. **Migration Assessment。** Integration Suiteの機能で、POシステムに接続して連携シナリオを抽出し、移行の工数を見積もります。セットアップは[SAPのチュートリアル](https://developers.sap.com/tutorials/migration-assessment.html)で説明されています。
2. **Migration Tooling。** Cloud Integrationの機能で、POの統合設定オブジェクト（ICO）からiFlowへの[移行を半自動化します](https://developers.sap.com/tutorials/migration-tool.html)。このツールで移行できるのは、「Ready to migrate」または「Adjustment required」と評価されたシナリオだけです。

[SAP Learning](https://learning.sap.com/courses/sap-process-orchestration-to-sap-integration-suite-migration/developing-a-migration-approach)は、すべてのお客様に合う単一の移行パスはないと明言しており、多くのお客様は移行期間中にPI/POとIntegration Suiteを並行稼働させています。ツールは機械的な作業を減らします。何を作り直し、何を廃止するかという判断まではしてくれません。

私が出発点として使っているウェーブ計画は次のとおりです。ウェーブは、ご自身のインタフェース一覧に合わせて調整してください。

| ウェーブ | 移行するもの | この順序の理由 | 担当者 | 完了条件 |
|---|---|---|---|---|
| 0. 棚卸し | すべてのPIインタフェース：頻度、ボリューム、アダプタ、重要度、オーナー | 数えていないものは計画できない | 連携リーダー | 業務オーナーがインタフェース一覧を承認 |
| 1. 低リスク | 標準コンテンツを使うSAP間のフロー | 運用モデルと監視を実証する | 連携リーダー | 本番で2週間安定稼働し、PIの経路を廃止 |
| 2. パートナー | 主要な取引先とのB2BおよびEDIのフロー | パートナーのテスト期間と調整された切替が必要 | 連携リーダーと購買部門・営業部門 | 各パートナーが書面で確認 |
| 3. 高リスク | 大量、規制対象、または収益に直結するフロー | 最後に、最も多くのリハーサルを経て移行する | 連携アーキテクト | ボリュームテストに合格し、PIへのフォールバックをリハーサル済み |
| 4. 廃止 | PI/POの停止 | 2つのプラットフォームへの支払いを止める | CIO | すべてのフローを移行または廃止し、ライセンスを終了 |

新しいフローが本番で問題なく稼働するまで、ウェーブごとにPIへのフォールバックの経路を残しておいてください。順序が重要です。収益を担うインタフェースに手を付ける前に、低リスクのフローで運用モデルを実証してください。

連携テストは、時間が消えていく場所です。B2BパートナーやSAP以外のターゲットとの回帰テストは、静かに壊れるため、早めに計画してください。連携テストと回帰テストのサイクルの組み立て方は、私の「[SAPテストガイド](/ja/sap-testing-explained/)」で取り上げています。

PI/POの移行がS/4HANAプログラムの中にあるなら、2つの計画をそろえてください。ERP側の移行パスと期限については、私の「[ECCからS/4HANAへの移行ガイド](/ja/ecc-to-s4hana-migration/)」で取り上げています。

## よくある連携パターン

私が最もよく目にするシナリオは次のとおりです。

1. **S/4HANAからSuccessFactorsへ。** 組織データ、人員数、報酬の変更です。一般的なシナリオはSAPの標準連携コンテンツでカバーでき、例外は独自のフローで処理します。
2. **従来の購買システムからSAP Aribaへ。** 購買発注を送り、確認と請求書を受け取ります。通常は双方向です。
3. **財務データをSAP Analytics Cloudへ。** ECCやSAP以外のシステムからSACへデータを移動します。
4. **SalesforceからSAPへ。** 成約した案件を、出荷、請求、在庫更新のためにSAPへ流します。設計上の誤りについては、私の記事「[SalesforceとERPの連携が失敗する理由](/ja/why-erp-integration-with-salesforce-fails-and-how-to-fix-it/)」で取り上げています。

プログラムで連携作業がすでに遅れているなら、「[SAP Integration Suiteの導入遅延](/ja/sap-integration-suite-delivery-delays/)」でよくある原因を取り上げています。「[SAPの連携プラットフォーム](/ja/sap-implementation/sap-integration-platforms/)」の概要では、選択肢を並べて比較しています。

## よくある質問

<details>
<summary>SAP CPIとは何ですか？現在は何と呼ばれていますか？</summary>

SAP CPIはCloud Platform Integrationの略です。現在は、API Management、Event Mesh、パートナー連携ツールと並ぶ、SAP BTP上のSAP Integration SuiteのCloud Integration機能です。インテグレーションフローを構築する日常の場面では、今も「CPI」という呼び名が使われています。

</details>

<details>
<summary>SAP CIとは何ですか？</summary>

SAP CIはSAP Cloud Integrationの略で、かつてSAP CPIと呼ばれていたものの現在の名称です。どちらも、SAP Integration Suiteの中の同じ機能を指します。

</details>

<details>
<summary>SAP CPIはミドルウェアですか？</summary>

はい。CPIはクラウドミドルウェアです。システムの間に位置し、メッセージを変換・ルーティングし、エラーと再試行を処理します。SAP PI/POのようなオンプレミスのミドルウェアを置き換えるもので、業務データを長期保存することはありません。

</details>

<details>
<summary>SAP CPIはSAP PI/POとどう違いますか？</summary>

PI/POは、自社でインストール、パッチ適用、運用を行うオンプレミスのミドルウェアです。CPIはSAPが運用するSAP BTP上のクラウドサービスで、新しいアダプタやコンテンツは一元的に提供されます。オンプレミスに留める必要があるフローは、Edge Integration Cellでカバーします。

</details>

<details>
<summary>SAP PI/POのサポートはいつ終了しますか？</summary>

PI/POを含むSAP NetWeaver 7.5のメインストリームメンテナンスは、2027年末に終了します。延長メンテナンスは2030年末まで利用できます。SAPは、シナリオをIntegration Suiteへ移行するための支援として、Migration AssessmentとMigration Toolingを提供しています。

</details>

<details>
<summary>SAP CPIはSAP BTPと同じものですか？</summary>

いいえ。SAP BTPはプラットフォームです。アプリケーション開発、データ、アナリティクス、AI、連携を含みます。CPIはその上の連携サービスです。

作業のスコープを決めるときは、予算とスキルが異なります。BTPアーキテクトはサービス全体にわたって仕事をし、CPIのスペシャリストはフロー、アダプタ、マッピングを担当します。

</details>

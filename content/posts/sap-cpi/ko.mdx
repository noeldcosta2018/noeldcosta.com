SAP CPI(Cloud Platform Integration)는 SAP의 클라우드 미들웨어입니다. 지금은 SAP BTP의 SAP Integration Suite 안에 Cloud Integration 기능으로 들어가 있으며, S/4HANA를 다른 SAP 시스템과 비SAP 시스템에 연결하는 SAP의 답입니다. 아직 SAP PI/PO를 운영 중이라면 시간표가 중요합니다. PI/PO 7.5는 2027년 말에 표준 유지보수가 끝납니다.

이 가이드는 PI/PO에서 벗어나는 방법이나 새 S/4HANA 프로그램의 통합 설계를 고민하는 통합 리드와 CIO를 위한 것입니다. CPI가 하는 일과 하지 않는 일, PI/PO와의 비교, 인터페이스 이전을 위한 웨이브 계획을 다룹니다.

SAP와 비SAP 시스템을 연결하려고 취약한 커스텀 스크립트를 만드는 데 몇 달을 쓰는 팀을 보았습니다. 처음에는 잘 돌아갑니다. 그러다 시스템 업데이트로 필드 이름이 바뀌거나, 새 API 버전이 나오거나, 트래픽이 두 배가 됩니다. 스크립트는 조용히 깨집니다. 리포트가 오래된 데이터를 가져오거나 주문이 사흘째 처리되지 않은 채 쌓여 있어야 비로소 알게 됩니다.

CPI는 이를 관리되는 재사용 가능한 통합 플로로 대체합니다. 더 단순해서가 아닙니다(오히려 아닌 경우가 많습니다). 모니터링하고 유지보수할 수 있도록 설계된 아키텍처이기 때문입니다. CPI 설계 초기에 내린 작은 결정은 대부분의 팀이 예상하는 것보다 빠르게 기술 부채로 쌓입니다.

## SAP CPI가 무엇이고 무엇이 아닌가

CPI는 시스템을 연결하고, 데이터를 변환하고, 애플리케이션 사이에서 메시지를 라우팅하는 계층입니다. SAP Integration Suite는 여기에 API Management, Event Mesh, Integration Advisor, 거래 파트너 관리를 묶어 제공합니다. 컨설턴트 대부분은 통합 플로 부분을 가리킬 때 여전히 “CPI”라고 하며, 그래도 괜찮습니다.

**CPI가 하는 일:** 시스템 사이에서 데이터를 옮기고, 메시지 형식을 변환하고, 올바른 대상으로 라우팅하며, 오류와 재시도를 처리합니다. 표준 어댑터를 통해 SAP 시스템(S/4HANA, SuccessFactors, Ariba)과 비SAP 플랫폼(Salesforce, Workday, ServiceNow)을 연결합니다.

**하지 않는 일:** 데이터를 장기 저장하거나, ERP를 대체하거나, 대량 데이터 마이그레이션용 ETL 도구 역할을 하지 않습니다. 실시간 또는 준실시간 메시지를 위해 만들어졌습니다. 데이터 웨어하우스나 마이그레이션 도구로 쓰면 나중에 아키텍처 문제가 생깁니다.

**CPI와 SAP BTP:** BTP는 애플리케이션 개발, 데이터, AI, 분석, 통합을 아우르는 전체 플랫폼입니다. CPI는 그 위의 서비스 하나입니다. 이 구분은 역량과 예산 범위를 정할 때 중요합니다. BTP 아키텍트는 여러 서비스에 걸쳐 설계합니다. CPI 전문가는 플로, 어댑터, 매핑, 연결을 맡습니다.

## 2026년에 달라진 것

지금 모든 통합 계획을 좌우하는 날짜와 결정이 네 가지 있습니다.

1. **PI/PO는 길의 끝에 와 있습니다.** [SAP NetWeaver 7.5는 PI/PO를 포함하며 Business Suite 유지보수 일정을 따릅니다](https://sapinsider.org/blogs/sap-extends-maintenance-for-sap-netweaver-7-5-and-sap-bw-4hana/). 표준 유지보수는 2027년 말, 연장 유지보수는 2030년 말까지입니다. 새 기능은 나오지 않습니다. 계획에 따른 웨이브 방식의 이전은 2027년이나 2030년의 강제 컷오버보다 훨씬 저렴합니다.
2. **하이브리드에도 답이 있습니다.** 2023년 후반부터 정식 출시된 Edge Integration Cell은 온프레미스에 남아야 하는 인터페이스를 위해 Integration Suite 플로를 자사 네트워크 안에서 실행합니다. 팀들이 PI/PO에 남는 이유로 가장 흔히 들던 것이 이로써 사라집니다.
3. **Neo가 닫힙니다.** SAP는 SAP BTP Neo 환경이 2028년 12월 31일에 종료된다고 [2023년에 발표했습니다](https://sapinsider.org/blogs/sap-announces-sunset-of-neo-cloud-environment/). Neo에 있는 초기 CPI 테넌트는 멀티클라우드(Cloud Foundry) 환경으로 옮겨야 하며, 그 이전은 그 자체로 작은 프로젝트입니다.
4. **Joule이 도구 안에 들어왔습니다.** SAP는 Integration Suite에 Joule을 넣어, 개발자가 플로를 일상 언어로 설명하면 초안을 받을 수 있게 했습니다. 표준 시나리오에서는 속도가 빨라집니다. 실제 비즈니스 로직이 있는 복잡한 오케스트레이션에는 여전히 시니어 통합 아키텍트가 필요합니다.

상업 조건을 말씀드리면, RISE with SAP을 쓰고 있다면 Integration Suite 용량을 따로 사기 전에 계약에 이미 어떤 SAP BTP 엔타이틀먼트가 포함되어 있는지 확인하십시오.

## CPI와 SAP PI/PO 비교

| 항목 | SAP PI/PO | SAP CPI (Integration Suite) |
|---|---|---|
| 배포 | 온프레미스, 자사 서버 | SAP BTP 클라우드, 온프레미스 런타임은 Edge Integration Cell |
| 유지보수 부담 | 높음: 패치, 업그레이드, 서버 관리 | 낮음: 플랫폼은 SAP가 운영 |
| 확장성 | 깊은 커스터마이징, 업그레이드가 더 어려움 | 모듈식, 더 빠른 업데이트, 저수준 제어는 적음 |
| 라이선스 | 고정형, 보통 용량 기준 | 메시지 기준 지표의 구독 |
| 투자 방향 | 유지보수만, 새 기능 없음 | 활발한 개발 |
| 표준 유지보수 종료 | 2027년 말(연장은 2030년 말) | 해당 없음(클라우드 서비스) |

라이선스 방식의 변화는 모델링해 볼 가치가 있습니다. CPI 비용은 메시지 볼륨에 연동됩니다. PI/PO보다 절약하는 회사도 있습니다. 실제 통합 트래픽이 생각보다 많아서 플로를 일찍 최적화해야 하는 회사도 있습니다. 이전하기 전에 모델링하십시오.

## 주요 기능과 어댑터

기본 구성 요소는 **iFlow**(통합 플로)입니다. 각 iFlow는 메시지가 소스에서 타깃으로 이동하는 방식을 정의합니다. 변환, 라우팅 규칙, 그리고 무언가 실패했을 때 작동하는 오류 처리입니다.

| 기능 | 하는 일 |
|---|---|
| 사전 구축 통합 콘텐츠 | SAP Business Accelerator Hub에서 제공하는, SAP 및 흔한 서드파티 시나리오용 iFlow 패키지 |
| 그래픽 플로 디자이너 | iFlow를 만드는 웹 기반 디자이너 |
| API Management | API 설계, 게시, 보안, 모니터링 |
| 보안 | OAuth 2.0, SAML, TLS, 인증서 관리 |
| 모니터링 | 메시지 로그, 오류 상세, 재시도 이력, 알림 |

**표준 어댑터**에는 SOAP, REST, OData, IDoc, JDBC, SFTP, JMS, AS2가 있으며, 특정 SaaS 제품용 어댑터가 더 있습니다.

**스크립팅.** 복잡한 변환에는 iFlow 안에서 Groovy나 JavaScript가 필요합니다. 표준 플로를 넘어서면 CPI는 제로 코드가 아닙니다. 팀에 기본적인 스크립트 로직을 쓸 수 있는 사람이 없다면 복잡한 매핑이 병목이 됩니다.

## PI/PO 마이그레이션: 실제로 무엇이 필요한가

마이그레이션은 자동 변환이 아닙니다. 어댑터의 동작이 PI와 CPI에서 다르고, PI에서 잘 되던 오류 처리가 CPI에서는 다르게 동작할 수 있습니다. 일부 플로는 다시 만들어야 합니다. 일부는 작은 변경으로 옮겨집니다. SAP의 마이그레이션 도구와 사전 구축 콘텐츠가 기계적인 작업을 줄여 줍니다. 무엇을 다시 만들고 무엇을 폐기할지에 대한 판단까지 대신해 주지는 않습니다.

제가 출발점으로 쓰는 웨이브 계획은 다음과 같습니다. 웨이브는 자사 인벤토리에 맞게 조정하십시오.

| 웨이브 | 이전 대상 | 이 순서인 이유 | 담당 | 완료 기준 |
|---|---|---|---|---|
| 0. 인벤토리 | 모든 PI 인터페이스: 빈도, 볼륨, 어댑터, 중요도, 오너 | 세어 보지 않은 것은 계획할 수 없습니다 | 통합 리드 | 비즈니스 오너가 인벤토리를 승인 |
| 1. 저위험 | 표준 콘텐츠를 쓰는 SAP 대 SAP 플로 | 운영 모델과 모니터링을 검증 | 통합 리드 | 운영에서 2주간 안정, PI 경로 폐기 |
| 2. 파트너 | 주요 거래 파트너와의 B2B, EDI 플로 | 파트너 테스트 기간과 조율된 컷오버가 필요 | 통합 리드, 구매 및 영업 부서 | 각 파트너가 서면으로 확인 |
| 3. 고위험 | 대용량, 규제 대상 또는 매출에 직결되는 플로 | 가장 마지막에, 가장 많은 리허설을 거쳐 이전 | 통합 아키텍트 | 볼륨 테스트 통과, PI로의 폴백 리허설 완료 |
| 4. 폐기 | PI/PO 종료 | 두 플랫폼에 비용을 내는 일을 멈춤 | CIO | 모든 플로를 이전 또는 폐기, 라이선스 종료 |

웨이브마다 새 플로가 운영에서 문제 없이 돌아갈 때까지 PI로 돌아가는 폴백 경로를 유지하십시오. 순서가 중요합니다. 매출을 나르는 인터페이스를 건드리기 전에 저위험 플로에서 운영 모델을 검증하십시오.

## 흔한 통합 패턴

가장 자주 보는 시나리오입니다.

1. **S/4HANA에서 SuccessFactors로.** 조직 데이터, 인원 수, 보상 변경입니다. SAP의 표준 통합 콘텐츠가 흔한 시나리오를 다루고, 예외는 커스텀 플로가 처리합니다.
2. **레거시 구매 시스템에서 SAP Ariba로.** 구매 오더는 내보내고, 확인과 송장은 들여옵니다. 보통 양방향입니다.
3. **재무 데이터에서 SAP Analytics Cloud로.** ECC나 비SAP 시스템의 데이터를 SAC로 옮깁니다.
4. **Salesforce에서 SAP로.** 체결된 계약이 SAP로 흘러 들어가 주문 이행, 청구, 재고 업데이트로 이어집니다. 관리되는 통합이 없으면 보통 스프레드시트 내보내기나 취약한 스크립트로 돌아갑니다. 설계상의 실수는 [Salesforce와 ERP 통합이 실패하는 이유](/ko/why-erp-integration-with-salesforce-fails-and-how-to-fix-it/)를 다룬 제 글에서 살펴봅니다.

프로그램에서 통합 작업이 이미 밀리고 있다면 [SAP Integration Suite 납기 지연](/ko/sap-integration-suite-delivery-delays/)에서 흔한 원인을 다룹니다. [SAP 통합 플랫폼](/ko/sap-implementation/sap-integration-platforms/) 개요는 선택지를 나란히 비교합니다.

## 자주 묻는 질문

<details>
<summary>SAP CPI란 무엇이며 지금은 무엇이라고 부릅니까?</summary>

SAP CPI는 Cloud Platform Integration의 약자입니다. 지금은 SAP BTP의 SAP Integration Suite에서 API Management, Event Mesh, 파트너 통합 도구와 함께 제공되는 Cloud Integration 기능입니다. 통합 플로를 만드는 작업을 가리키는 일상적인 이름은 여전히 “CPI”입니다.

</details>

<details>
<summary>SAP CPI는 SAP PI/PO와 어떻게 다릅니까?</summary>

PI(Process Integration)와 PO(Process Orchestration)는 깊은 커스터마이징과 인프라 전체 제어를 제공하는 온프레미스 미들웨어입니다. CPI는 SAP BTP의 클라우드 서비스로, SAP가 운영을 대신하며 새 어댑터와 콘텐츠가 중앙에서 제공됩니다.

PI/PO 7.5는 유지보수만 받습니다. 표준 유지보수는 2027년 말, 연장 유지보수는 2030년 말에 끝나므로 모든 PI/PO 환경에 마이그레이션 계획이 필요합니다.

</details>

<details>
<summary>SAP CPI와 SAP BTP는 같은 것입니까?</summary>

아닙니다. SAP BTP는 앱 개발, 데이터, 분석, AI, 통합을 아우르는 플랫폼입니다. CPI는 그 위의 통합 서비스입니다. 업무 범위를 정할 때 예산과 역량이 달라집니다. BTP 아키텍트는 여러 서비스에 걸쳐 일하고, CPI 전문가는 플로, 어댑터, 매핑을 맡습니다.

</details>

<details>
<summary>SAP CPI는 배우기가 얼마나 어렵습니까?</summary>

다룰 만하지만 단순하지는 않습니다. 표준 플로는 문서화된 패턴을 따르고 그래픽 디자이너가 도와줍니다. 어려운 부분은 플로를 설계할 만큼 비즈니스 프로세스를 이해하는 것, 오류와 재시도를 제대로 처리하는 것, 복잡한 매핑을 위해 Groovy나 JavaScript를 쓰는 것입니다. 비즈니스 프로세스를 먼저 배우고, 그다음에 통합을 배우십시오.

</details>

<details>
<summary>SAP PI/PO에서 CPI로 마이그레이션할 때 무엇을 고려해야 합니까?</summary>

모든 인터페이스를 볼륨, 빈도, 어댑터, 중요도와 함께 목록화하십시오. 각각에 대해 다시 만들지, 조정할지, 폐기할지 정하십시오. 메시지 기준 비용을 실제 볼륨에 대입해 모델링하십시오. 폴백 경로를 두고 웨이브로 옮기며, B2B 파트너와 비SAP 타깃에 대한 회귀 테스트는 일찍 계획하십시오. 이쪽은 조용히 깨지기 때문입니다. 온프레미스에 남아야 하는 플로에는 Edge Integration Cell을 쓰십시오.

</details>

<details>
<summary>SAP CPI에서 Neo와 Cloud Foundry의 차이는 무엇입니까?</summary>

둘 다 SAP BTP 환경입니다. Neo는 SAP 독자 방식의 오래된 환경이며 2028년 12월 31일에 종료됩니다. Cloud Foundry 기반의 멀티클라우드 환경이 SAP 개발이 향하는 곳입니다. 아직 Neo에 있는 CPI 테넌트는 지금 마이그레이션 계획이 필요하며, 새 테넌트는 거기서 시작해서는 안 됩니다.

</details>

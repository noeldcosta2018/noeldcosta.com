SAP CPI(Cloud Platform Integration)는 SAP 시스템과 비 SAP 시스템을 연결하는 SAP의 클라우드 미들웨어입니다. 현재 이름은 Cloud Integration이며, SAP Business Technology Platform(SAP BTP) 위의 SAP Integration Suite가 제공하는 핵심 기능입니다.

애플리케이션 간에 메시지를 옮기고, 형식을 변환하고, 올바른 대상으로 라우팅합니다. 아직 SAP PI/PO를 운영하고 계신다면 시간이 중요합니다. PI/PO를 포함하는 SAP NetWeaver 7.5의 메인스트림 유지보수가 2027년 말에 끝납니다.

이 가이드는 CPI가 하는 일, 아키텍처의 작동 방식, PI/PO와의 비교, 그리고 전환 계획 방법을 다룹니다. 개발자만이 아니라 통합 리더와 CIO를 위해 쓴 글입니다.

## 제 경험에서 본 CPI가 중요한 이유

저는 SAP 시스템과 비 SAP 시스템을 연결하려고 몇 달 동안 깨지기 쉬운 커스텀 스크립트를 만드는 팀을 봤습니다. 처음에는 무언가가 작동합니다. 그러다 시스템 업데이트로 필드 이름이 바뀌거나, 새 API 버전이 배포되거나, 트래픽이 두 배가 됩니다.

스크립트는 조용히 깨집니다. 보고서가 오래된 데이터를 가져오거나 주문이 사흘 동안 처리되지 않은 채 남아 있을 때까지 아무도 모릅니다.

CPI는 그것을 관리되고 재사용 가능한 통합 흐름으로 대체합니다. 더 단순해서가 아니라(대개 단순하지 않습니다), 아키텍처가 모니터링과 유지 관리를 전제로 만들어졌기 때문입니다. CPI 설계 초기에 내린 작은 결정은 대부분의 팀이 예상하는 것보다 빠르게 기술 부채로 쌓입니다.

아직 SAP PI/PO를 쓰는 모든 회사에 대한 제 조언은 SAP Integration Suite로 옮기라는 것입니다. 제가 보는 가장 흔한 통합 실패는 통합에 충분한 시간을 들이지 않는 것입니다.

## SAP CPI인 것과 아닌 것

[SAP의 마이그레이션 가이드](https://help.sap.com/docs/migration-guide-po/migration-guide-for-sap-process-orchestration/introduction-sap-integration-suite)는 Cloud Integration을 클라우드, 온프레미스, 하이브리드 환경 전반에서 통합 흐름을 설계하고 실행하는 기능으로 설명합니다. 애플리케이션 간(A2A), 기업 간(B2B), 기업과 정부 간(B2G) 시나리오를 다룹니다. 대부분의 컨설턴트는 아직도 이를 "CPI" 또는 "SAP CI"라고 부르며, 그래도 괜찮습니다.

SAP Integration Suite는 Cloud Integration을 다른 기능들과 묶어 제공합니다. 주요 기능은 API Management, Event Mesh, Integration Advisor, Trading Partner Management, Open Connectors, Migration Assessment입니다.

**CPI가 하는 일:** 시스템 간 데이터 이동, 메시지 형식 변환, 올바른 대상으로의 라우팅, 오류 처리와 재시도. 표준 어댑터를 통해 SAP 시스템(S/4HANA, SuccessFactors, Ariba)과 비 SAP 플랫폼(Salesforce, Workday, ServiceNow)을 연결합니다.

**하지 않는 일:** 데이터 장기 저장, ERP 대체, 대량 데이터 마이그레이션을 위한 ETL 도구 역할. CPI는 실시간 또는 준실시간 메시지를 위해 만들어졌습니다. 데이터 웨어하우스나 마이그레이션 도구로 쓰면 나중에 아키텍처 문제가 생깁니다.

**CPI와 SAP BTP의 차이:** BTP는 애플리케이션 개발, 데이터, AI, 분석, 통합을 아우르는 플랫폼 전체입니다. CPI는 그 위의 서비스 하나입니다. BTP 아키텍트는 여러 서비스에 걸쳐 설계하고, CPI 전문가는 흐름, 어댑터, 매핑, 연결을 책임집니다.

## SAP CPI 아키텍처 해설: 실제 작동 방식

아래 다이어그램은 CPI가 대상으로 하는 통합 시나리오를 보여 줍니다. 클라우드 간, 온프레미스와 클라우드 간, 기업 간(B2B), 기업과 정부 간(B2G), 그리고 사용자 및 디바이스와의 연결입니다.

![SAP S/4HANA와 비 SAP 앱을 중심으로 클라우드 간, 온프레미스와 클라우드 간, B2B, B2G 통합을 보여 주는 SAP CPI 아키텍처 다이어그램](/images/wp/elementor/thumbs/SAP-CPI-r6e607fx79xud4tbbufp2yww164i041nvu8xtwedj4.webp "SAP CPI 아키텍처")

CPI 아키텍처를 이해하는 일은 개발자만의 몫이 아닙니다. 제 경험으로는 CPI가 구조적 수준에서 통합을 어떻게 처리하는지 파악한 팀이 초기에 더 나은 설계 결정을 내리는 경향이 있습니다.

CPI는 SAP BTP 위에서 멀티 테넌트 클라우드 서비스로 실행됩니다. SAP가 플랫폼을 운영하므로 자체 통합 서버를 유지 관리할 필요가 없습니다. 흐름이 반드시 귀사의 네트워크 안에서 실행되어야 하는 경우, [Edge Integration Cell](https://help.sap.com/docs/integration-suite/sap-integration-suite/what-is-sap-integration-suite-edge-integration-cell)이 선택 가능한 하이브리드 런타임입니다. 설계와 모니터링은 클라우드에서 하고, 흐름은 귀사의 네트워크에서 실행합니다.

### 실제 메시지 흐름

핵심에는 iFlow(통합 흐름)가 있습니다. CPI의 모든 통합은 iFlow로 모델링되며, 각 iFlow는 세 단계로 메시지를 소스에서 대상으로 옮깁니다.

1. **송신 어댑터.** SOAP, REST, OData, IDoc, SFTP, JMS, AS2 또는 다른 프로토콜로 소스 시스템에서 메시지를 받습니다.
2. **처리 단계.** 매핑, 형식 변환(예: JSON에서 XML로), 콘텐츠 기반 라우팅, 다른 시스템 호출, 암호화, 오류 처리입니다.
3. **수신 어댑터.** 처리된 메시지를 대상으로 보냅니다.

흐름은 사용 사례에 따라 동기 또는 비동기로 실행됩니다. 어느 쪽을 택할지가 늘 분명하지는 않으므로, 실제 물량으로 둘 다 테스트하십시오.

모니터링이 큰 역할을 합니다. 메시지 처리 로그, 트레이스, 지속 저장된 메시지가 있으며, 각각 목적이 다릅니다. 테스트나 디버깅 중에 저는 얼마나 깊이 들어가야 하는지에 따라 트레이스와 지속 저장을 오가는 편입니다.

### SAP CPI 아키텍처의 구성 요소

아래 표는 각 구성 요소를 아키텍처 안에서의 역할과 연결합니다.

| 구성 요소 | 하는 일 | 아키텍처에서의 역할 |
|---|---|---|
| 통합 흐름 런타임 | iFlow 실행 | 런타임에 라우팅, 매핑, 변환, 보안 처리 |
| 웹 기반 디자이너 | iFlow를 만들고, 구성하고, 배포하는 그래픽 편집기 | 개발자가 흐름을 모델링하는 곳, 복잡한 로직에는 여전히 Groovy나 JavaScript 필요 |
| 어댑터 | SOAP, REST, OData, IDoc, JDBC, SFTP, JMS, AS2 및 SaaS 전용 어댑터 | 클라우드와 온프레미스 시스템 연결 |
| 보안 | OAuth 2.0, SAML, TLS, 인증서 및 키 관리 | 전송 중인 자격 증명과 메시지 보호 |
| 모니터링 및 운영 | 메시지 로그, 오류 세부 정보, 재시도, 경보 | 지원 팀이 실패를 찾아 수정할 수 있게 함 |
| 사전 패키지 콘텐츠 | SAP Business Accelerator Hub에서 SAP가 제공하는 통합 패키지 | 검증된 콘텐츠로 표준 시나리오 속도 향상 |
| SAP Cloud Connector | 귀사의 네트워크에서 SAP BTP로 가는 보안 터널 | 온프레미스 시스템을 인터넷에 노출하지 않고 접근 |
| Edge Integration Cell | 자체 데이터 센터나 프라이빗 클라우드의 선택형 런타임 | 온프레미스에 남아야 하는 흐름용 |

Groovy 스크립트는 그래픽 단계로 처리할 수 없는 로직을 다룹니다. 저는 이를 가볍게 유지하라고 자주 권합니다. 스크립트가 너무 많으면 나중에 유지 관리 문제가 생기기 때문입니다. 패키지는 버전 관리되므로, 배포된 패키지 밖에서 운영 환경에 들어가는 변경은 없습니다.

## 통합 계획을 좌우하는 날짜

지금 거의 모든 통합 계획은 세 가지 날짜가 이끕니다.

1. **PI/PO에 남은 길이 줄어들고 있습니다.** [SAP Note 1648480](https://me.sap.com/notes/1648480)은 PI/PO를 포함하는 SAP NetWeaver 7.5의 메인스트림 유지보수를 2027년 말까지, 연장 유지보수를 2030년 말까지로 정합니다. 2028년 1월 1일에 시스템이 멈추지는 않지만, 그 이후 매년 유지 비용이 더 듭니다.
2. **Neo가 문을 닫습니다.** [SAP Knowledge Base Article 3355661](https://me.sap.com/notes/3355661)은 SAP BTP Neo 환경의 Cloud Integration이 2028년 12월 31일에 종료된다고 확인합니다. Neo에 있는 초기 CPI 테넌트는 멀티 클라우드(Cloud Foundry) 환경으로 옮겨야 하며, 그 이전 자체가 작은 프로젝트입니다.
3. **하이브리드에도 답이 있습니다.** Edge Integration Cell은 Integration Suite 흐름을 귀사의 네트워크 안에서 실행합니다. 이것으로 팀들이 PI/PO에 남겠다며 가장 흔히 들던 이유가 사라집니다.

계약 측면에서는, RISE with SAP를 쓰고 계신다면 Integration Suite 용량을 따로 사기 전에 계약에 이미 어떤 SAP BTP 사용 권한이 포함되어 있는지 확인하십시오.

## CPI와 SAP PI/PO 비교

PI(Process Integration)와 PO(Process Orchestration)는 SAP의 온프레미스 미들웨어입니다. CPI와의 비교는 다음과 같습니다.

| 요소 | SAP PI/PO | SAP CPI(Integration Suite) |
|---|---|---|
| 배포 | 온프레미스, 귀사의 서버 | SAP BTP 위의 클라우드, 온프레미스 런타임은 Edge Integration Cell |
| 유지 관리 부담 | 높음: 패치, 업그레이드, 서버 관리 | 낮음: SAP가 플랫폼 운영 |
| 확장성 | 깊은 커스터마이징, 업그레이드가 더 어려움 | 모듈식, 더 빠른 업데이트, 저수준 제어는 적음 |
| 라이선스 | 라이선스와 자체 인프라 | SAP BTP 구독, 에디션별 |
| 투자 방향 | 유지보수만, 신규 기능 없음 | 활발한 개발 |
| 메인스트림 유지보수 종료 | 2027년 말(연장 시 2030년 말) | 해당 없음(클라우드 서비스) |

SAP의 마이그레이션 가이드는 Cloud Integration이 PI/PO가 하는 일 대부분을 다루기 때문에 이를 주된 대체 수단으로 봅니다. 마이그레이션 전에 귀사의 에디션이 어떻게 계량되는지 SAP에 물어보고, 실제 메시지 물량으로 모델링하십시오. 통합 트래픽이 생각보다 많다는 것을 알게 되는 회사도 있습니다.

## PI/PO 마이그레이션: 실제로 수반되는 것

마이그레이션은 자동 변환이 아닙니다. 어댑터 동작은 PI와 CPI가 서로 다르고, PI에서 작동하던 오류 처리가 CPI에서는 다르게 동작할 수 있습니다. 다시 만들어야 하는 흐름도 있고, 작은 변경만으로 옮겨지는 흐름도 있습니다.

SAP는 두 가지 공식 도구를 제공합니다.

1. **Migration Assessment.** PO 시스템에 연결해 통합 시나리오를 추출하고 이전 공수를 추정하는 Integration Suite의 기능입니다. [SAP의 튜토리얼](https://developers.sap.com/tutorials/migration-assessment.html)이 설정 방법을 다룹니다.
2. **Migration Tooling.** PO의 통합 구성 오브젝트(ICO)를 iFlow로 [반자동 마이그레이션](https://developers.sap.com/tutorials/migration-tool.html)하는 Cloud Integration의 기능입니다. "Ready to migrate" 또는 "Adjustment required"로 평가된 시나리오만 이 도구로 마이그레이션할 수 있습니다.

[SAP Learning](https://learning.sap.com/courses/sap-process-orchestration-to-sap-integration-suite-migration/developing-a-migration-approach)은 모든 고객에게 맞는 단일 마이그레이션 경로는 없다고 분명히 말하며, 많은 고객이 전환 기간에 PI/PO와 Integration Suite를 병행 운영합니다. 도구는 기계적인 작업을 줄여 줍니다. 무엇을 다시 만들고 무엇을 폐기할지에 대한 판단은 해 주지 않습니다.

제가 출발점으로 쓰는 웨이브 계획은 다음과 같습니다. 웨이브는 귀사의 인벤토리에 맞게 조정하십시오.

| 웨이브 | 옮기는 대상 | 이 순서인 이유 | 책임자 | 종료 기준 |
|---|---|---|---|---|
| 0. 인벤토리 | 모든 PI 인터페이스: 빈도, 물량, 어댑터, 중요도, 책임자 | 세지 않은 것은 계획할 수 없음 | 통합 리더 | 현업 책임자가 인벤토리 승인 |
| 1. 저위험 | 표준 콘텐츠가 있는 SAP 간 흐름 | 운영 모델과 모니터링을 검증 | 통합 리더 | 운영 환경에서 2주간 안정, PI 경로 폐기 |
| 2. 파트너 | 주요 거래 파트너와의 B2B 및 EDI 흐름 | 파트너 테스트 기간과 조율된 전환이 필요 | 구매 및 영업과 함께 통합 리더 | 각 파트너가 서면으로 확인 |
| 3. 고위험 | 대량, 규제 대상 또는 매출에 결정적인 흐름 | 가장 많은 리허설을 거쳐 마지막에 이동 | 통합 아키텍트 | 물량 테스트 통과, PI로의 폴백 리허설 완료 |
| 4. 폐기 | PI/PO 종료 | 두 플랫폼에 대한 비용 지출 중단 | CIO | 모든 흐름 마이그레이션 또는 폐기, 라이선스 종료 |

새 흐름이 운영 환경에서 깨끗하게 돌아갈 때까지 각 웨이브마다 PI로 돌아갈 폴백 경로를 유지하십시오. 순서가 중요합니다. 매출을 실어 나르는 인터페이스를 건드리기 전에 저위험 흐름으로 운영 모델을 검증하십시오.

통합 테스트는 시간이 사라지는 곳입니다. B2B 파트너와 비 SAP 대상의 회귀 테스트는 조용히 깨지므로 일찍 계획하십시오. 제 [SAP 테스트 가이드](/ko/sap-testing-explained/)가 통합 및 회귀 사이클을 구성하는 방법을 다룹니다.

PI/PO 전환이 S/4HANA 프로그램 안에 있다면 두 계획을 맞추십시오. 제 [ECC에서 S/4HANA로의 마이그레이션 가이드](/ko/ecc-to-s4hana-migration/)가 ERP 쪽의 경로와 기한을 다룹니다.

## 흔한 통합 패턴

제가 가장 자주 보는 시나리오입니다.

1. **S/4HANA에서 SuccessFactors로.** 조직 데이터, 인원, 보상 변경. SAP의 표준 통합 콘텐츠가 일반적인 시나리오를 다루고, 커스텀 흐름이 예외를 처리합니다.
2. **레거시 구매 시스템에서 SAP Ariba로.** 구매 오더는 나가고, 확인과 송장은 돌아옵니다. 대개 양방향입니다.
3. **재무 데이터를 SAP Analytics Cloud로.** ECC나 비 SAP 시스템의 데이터를 SAC로 옮깁니다.
4. **Salesforce에서 SAP로.** 성사된 거래가 이행, 송장 발행, 재고 업데이트를 위해 SAP로 흘러갑니다. 설계 실수는 제 [Salesforce와 ERP 통합이 실패하는 이유](/ko/why-erp-integration-with-salesforce-fails-and-how-to-fix-it/) 글에서 다룹니다.

귀사 프로그램의 통합 작업이 이미 지연되고 있다면 [SAP Integration Suite 구축 지연](/ko/sap-integration-suite-delivery-delays/)에서 흔한 원인을 다룹니다. [SAP 통합 플랫폼](/ko/sap-implementation/sap-integration-platforms/) 개요는 선택지를 나란히 비교합니다.

## 자주 묻는 질문

<details>
<summary>SAP CPI란 무엇이며 지금은 무엇이라고 부릅니까?</summary>

SAP CPI는 Cloud Platform Integration의 약자입니다. 지금은 SAP BTP 위의 SAP Integration Suite가 제공하는 Cloud Integration 기능이며, API Management, Event Mesh, 파트너 통합 도구와 함께 제공됩니다. 통합 흐름을 만드는 일을 가리킬 때는 여전히 "CPI"가 일상적인 이름입니다.

</details>

<details>
<summary>SAP CI란 무엇입니까?</summary>

SAP CI는 SAP Cloud Integration의 약자로, 예전에 SAP CPI라고 부르던 것의 현재 이름입니다. 두 용어 모두 SAP Integration Suite 안의 같은 기능을 가리킵니다.

</details>

<details>
<summary>SAP CPI는 미들웨어입니까?</summary>

그렇습니다. CPI는 클라우드 미들웨어입니다. 시스템 사이에 위치해 메시지를 변환하고 라우팅하며, 오류와 재시도를 처리합니다. SAP PI/PO 같은 온프레미스 미들웨어를 대체하며, 비즈니스 데이터를 장기 저장하지 않습니다.

</details>

<details>
<summary>SAP CPI는 SAP PI/PO와 어떻게 다릅니까?</summary>

PI/PO는 직접 설치하고, 패치하고, 운영하는 온프레미스 미들웨어입니다. CPI는 SAP가 대신 운영하는 SAP BTP 위의 클라우드 서비스이며, 새로운 어댑터와 콘텐츠가 중앙에서 제공됩니다. 온프레미스에 남아야 하는 흐름은 Edge Integration Cell이 다룹니다.

</details>

<details>
<summary>SAP PI/PO 지원은 언제 끝납니까?</summary>

PI/PO를 포함하는 SAP NetWeaver 7.5의 메인스트림 유지보수는 2027년 말에 끝납니다. 연장 유지보수는 2030년 말까지 받을 수 있습니다. SAP는 시나리오를 Integration Suite로 옮기는 데 도움이 되도록 Migration Assessment와 Migration Tooling을 제공합니다.

</details>

<details>
<summary>SAP CPI와 SAP BTP는 같은 것입니까?</summary>

아닙니다. SAP BTP는 앱 개발, 데이터, 분석, AI, 통합을 아우르는 플랫폼입니다. CPI는 그 위의 통합 서비스입니다.

작업 범위를 정할 때 예산과 역량은 다릅니다. BTP 아키텍트는 여러 서비스에 걸쳐 일하고, CPI 전문가는 흐름, 어댑터, 매핑을 책임집니다.

</details>

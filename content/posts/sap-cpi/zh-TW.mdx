SAP CPI（Cloud Platform Integration）是 SAP 用來連接 SAP 與非 SAP 系統的雲端中介軟體。現在它稱為 Cloud Integration，是 SAP Business Technology Platform（SAP BTP）上 SAP Integration Suite 的核心功能。

它在應用程式之間傳送訊息、轉換訊息格式，並把訊息路由到正確的目標。如果您仍在使用 SAP PI/PO，時間就很關鍵：包含 PI/PO 在內的 SAP NetWeaver 7.5，主流維護將於 2027 年底結束。

本指南說明 CPI 做什麼、架構如何運作、與 PI/PO 相比如何，以及如何規劃移轉。它是寫給整合負責人和資訊長看的，不只是給開發人員。

## 依我的經驗，CPI 為什麼重要

我看過團隊花好幾個月建構脆弱的自訂腳本，來連接 SAP 與非 SAP 系統。一開始可以運作。接著某次系統更新改了欄位名稱，或推出了新版 API，或流量加倍。

腳本悄悄地壞掉。直到某份報表抓到過時的資料，或某張訂單擱置三天沒有處理，才有人發現。

CPI 以受管理、可重複使用的整合流程取代這種做法。不是因為它比較簡單（它往往並不簡單），而是因為它的架構本來就是為了監控和維護而設計的。CPI 設計初期做的小決定，累積成技術債的速度比多數團隊預期的還快。

我給仍在使用 SAP PI/PO 的任何公司的建議，就是移轉到 SAP Integration Suite。我看到最常見的整合失敗，就是在整合上投入的時間不夠。

## SAP CPI 是什麼，又不是什麼

[SAP 自己的移轉指南](https://help.sap.com/docs/migration-guide-po/migration-guide-for-sap-process-orchestration/introduction-sap-integration-suite)把 Cloud Integration 描述為在雲端、地端和混合環境中設計並執行整合流程的功能。它涵蓋應用程式對應用程式（A2A）、企業對企業（B2B）和企業對政府（B2G）的情境。多數顧問仍稱它為「CPI」或「SAP CI」，這也無妨。

SAP Integration Suite 把 Cloud Integration 與其他功能整合在一起。主要包括 API Management、Event Mesh、Integration Advisor、Trading Partner Management、Open Connectors 和 Migration Assessment。

**CPI 做什麼：**在系統之間傳送資料、轉換訊息格式、路由到正確的目標，並處理錯誤與重試。它透過標準配接器連接 SAP 系統（S/4HANA、SuccessFactors、Ariba）和非 SAP 平台（Salesforce、Workday、ServiceNow）。

**它不做什麼：**長期儲存資料、取代 ERP，或充當大量資料移轉的 ETL 工具。它是為即時或近即時訊息而建構的。把它當成資料倉儲或移轉工具，日後會造成架構問題。

**CPI 與 SAP BTP 的差別：**BTP 是整個平台：應用程式開發、資料、AI、分析和整合。CPI 是平台上的一項服務。BTP 架構師跨服務進行設計；CPI 專家則負責流程、配接器、對應和連線。

## SAP CPI 架構解析：實務上如何運作

下圖顯示 CPI 所支援的整合情境。雲端對雲端、地端對雲端、企業對企業（B2B）、企業對政府（B2G），以及與使用者和裝置的連接。

![SAP CPI 架構圖，顯示圍繞 SAP S/4HANA 與非 SAP 應用程式的雲端對雲端、地端對雲端、B2B 和 B2G 整合](/images/wp/elementor/thumbs/SAP-CPI-r6e607fx79xud4tbbufp2yww164i041nvu8xtwedj4.webp "SAP CPI Architecture")

了解 CPI 架構不只是開發人員的事。依我的經驗，能在結構層面掌握 CPI 如何處理整合的團隊，往往一開始就能做出更好的設計選擇。

CPI 以多租用戶雲端服務的形式在 SAP BTP 上運行。平台由 SAP 營運，所以您不需要維護自己的整合伺服器。若某條流程必須在您自己的網路內執行，[Edge Integration Cell](https://help.sap.com/docs/integration-suite/sap-integration-suite/what-is-sap-integration-suite-edge-integration-cell) 是可選用的混合式執行環境：您在雲端設計和監控，並在自己的網路中執行流程。

### 實務上的訊息流程

核心是 iFlow（整合流程）。CPI 中的每個整合都以 iFlow 建模，每個 iFlow 都分三個階段把訊息從來源送到目標：

1. **傳送端配接器。**透過 SOAP、REST、OData、IDoc、SFTP、JMS、AS2 或其他協定，從來源系統接收訊息。
2. **處理步驟。**對應、格式轉換（例如 JSON 轉 XML）、依內容路由、呼叫其他系統、加密和錯誤處理。
3. **接收端配接器。**把處理後的訊息送到目標。

流程可以同步或非同步執行，取決於使用情境。該選哪一種並不總是顯而易見，所以請用實際的流量測試兩者。

監控扮演重要角色。您有訊息處理記錄、追蹤和持久化訊息，各有不同用途。在測試或除錯時，我通常會依需要深入的程度，在追蹤和持久化之間切換。

### SAP CPI 架構的元件

下表列出每個元件在架構中的工作。

| 元件 | 功能 | 在架構中的角色 |
|---|---|---|
| 整合流程執行環境 | 執行 iFlow | 在執行時處理路由、對應、轉換和安全 |
| 網頁式設計工具 | 用於建置、設定和部署 iFlow 的圖形化編輯器 | 開發人員在此建模流程；複雜邏輯仍需要 Groovy 或 JavaScript |
| 配接器 | SOAP、REST、OData、IDoc、JDBC、SFTP、JMS、AS2，以及特定 SaaS 的配接器 | 連接雲端與地端系統 |
| 安全 | OAuth 2.0、SAML、TLS、憑證與金鑰管理 | 保護傳輸中的憑證資訊與訊息 |
| 監控與維運 | 訊息記錄、錯誤細節、重試、警示 | 讓支援團隊找出並修正失敗 |
| 預先封裝的內容 | SAP Business Accelerator Hub 上由 SAP 提供的整合套件 | 以經過測試的內容加快標準情境 |
| SAP Cloud Connector | 從您的網路到 SAP BTP 的安全通道 | 連到地端系統而不必把它們暴露在網際網路上 |
| Edge Integration Cell | 在您自己的資料中心或私有雲中可選用的執行環境 | 用於必須留在地端的流程 |

Groovy 腳本處理圖形化步驟無法處理的邏輯。我常建議盡量少用，因為腳本太多日後會造成維護問題。套件有版本控管，所以任何變更都不會在已部署的套件之外進入正式環境。

## 決定整合計畫的關鍵日期

目前幾乎每份整合計畫都受到三個日期影響。

<explainer-timeline title="整合計畫背後的日期" caption="請以 2027 年為核心規劃。在那之前分波段移轉，成本遠低於被迫的一次切換。" items="2027 => PI/PO 主流維護結束|2028 => Neo 上的 Cloud Integration 停止服務|2030 => PI/PO 延長維護結束" notes="年底，適用於 SAP NetWeaver 7.5|12 月 31 日。Neo 租用戶移轉到 Cloud Foundry|年底。任何 PI/PO 系統的最後一站" highlight="1" source="SAP Note 1648480 與 SAP 知識庫文章 3355661"></explainer-timeline>

1. **PI/PO 的路快走到盡頭了。**[SAP Note 1648480](https://me.sap.com/notes/1648480) 將包含 PI/PO 在內的 SAP NetWeaver 7.5 主流維護訂至 2027 年底，延長維護至 2030 年底。系統不會在 2028 年 1 月 1 日停止運作，但之後每多維持一年，成本就更高。
2. **Neo 即將關閉。**[SAP 知識庫文章 3355661](https://me.sap.com/notes/3355661) 確認 SAP BTP Neo 環境上的 Cloud Integration 將於 2028 年 12 月 31 日停止服務。較早期在 Neo 上的 CPI 租用戶需要移轉到多雲（Cloud Foundry）環境，而這項移轉本身就是一個小專案。
3. **混合架構有了解答。**Edge Integration Cell 在您自己的網路內執行 Integration Suite 流程。這消除了團隊過去留在 PI/PO 最常見的理由。

商務面：如果您使用的是 RISE with SAP，在另外購買 Integration Suite 容量之前，請先確認您的合約已包含哪些 SAP BTP 使用權。

## CPI 與 SAP PI/PO 的比較

PI（Process Integration）和 PO（Process Orchestration）是 SAP 的地端中介軟體。以下是它們與 CPI 的比較。

| 因素 | SAP PI/PO | SAP CPI（Integration Suite） |
|---|---|---|
| 部署 | 地端，您自己的伺服器 | SAP BTP 上的雲端；地端執行環境可用 Edge Integration Cell |
| 維護負擔 | 高：修補程式、升級、伺服器管理 | 較低：平台由 SAP 營運 |
| 擴充性 | 可深度客製化；較難升級 | 模組化；更新較快；底層控制較少 |
| 授權 | 授權費加上您自己的基礎架構 | SAP BTP 上依版本計價的訂閱 |
| 投資方向 | 僅維護，沒有新功能 | 持續開發中 |
| 主流維護結束 | 2027 年底（延長至 2030 年底） | 不適用（雲端服務） |

SAP 的移轉指南把 Cloud Integration 視為主要的替代方案，因為它涵蓋了 PI/PO 大部分的功能。請向 SAP 詢問您的版本如何計量，再在移轉前依您實際的訊息量建立模型。有些公司會發現自己的整合流量比想像中高。

## PI/PO 移轉：實際上包含什麼

移轉不是自動轉換。PI 和 CPI 的配接器行為不同，在 PI 中可行的錯誤處理，在 CPI 中可能表現不同。有些流程需要重建；有些只需小幅修改就能移過去。

SAP 提供兩個官方工具：

1. **Migration Assessment。**Integration Suite 的一項功能，連接到您的 PO 系統，擷取整合情境並估算移轉所需的工作量。[SAP 的教學](https://developers.sap.com/tutorials/migration-assessment.html)說明了設定方式。
2. **Migration Tooling。**Cloud Integration 的一項功能，可[半自動化地把](https://developers.sap.com/tutorials/migration-tool.html) PO 中的整合設定物件（ICO）移轉為 iFlow。只有評估結果為「Ready to migrate」或「Adjustment required」的情境，才能用它移轉。

[SAP Learning](https://learning.sap.com/courses/sap-process-orchestration-to-sap-integration-suite-migration/developing-a-migration-approach) 明確指出，沒有一條移轉路徑適合所有客戶，許多客戶在移轉期間會讓 PI/PO 和 Integration Suite 並行運作。這些工具減少了機械性的工作。但要重建什麼、要淘汰什麼，它們不會替您判斷。

以下是我作為起點的波段計畫。請依您自己的介面清單調整波段。

| 波段 | 移轉內容 | 為何是這個順序 | 負責人 | 完成條件 |
|---|---|---|---|---|
| 0. 盤點 | 每個 PI 介面：頻率、流量、配接器、重要性、負責人 | 沒有清點過的東西無法規劃 | 整合負責人 | 介面清單經業務負責人簽核 |
| 1. 低風險 | 使用標準內容的 SAP 對 SAP 流程 | 驗證營運模式和監控 | 整合負責人 | 在正式環境穩定運行兩週，PI 路徑已停用 |
| 2. 合作夥伴 | 與主要交易夥伴之間的 B2B 和 EDI 流程 | 需要合作夥伴的測試時段和協調的切換 | 整合負責人，會同採購與業務 | 每個合作夥伴以書面確認 |
| 3. 高風險 | 大流量、受法規管制或攸關營收的流程 | 最後移轉，演練最多次 | 整合架構師 | 通過流量測試；已演練退回 PI 的程序 |
| 4. 淘汰 | 關閉 PI/PO | 不再為兩個平台付費 | 資訊長 | 所有流程已移轉或淘汰；授權已終止 |

在新流程於正式環境中乾淨運行之前，每個波段都要保留一條退回 PI 的路徑。順序很重要：先在低風險流程上驗證營運模式，再去動那些承載營收的介面。

整合測試是時間消失的地方。請及早規劃與 B2B 合作夥伴和非 SAP 目標的迴歸測試，因為這些地方會悄悄出問題。我的 [SAP 測試指南](/zh-TW/sap-testing-explained/)說明了如何安排整合與迴歸測試週期。

如果 PI/PO 移轉是 S/4HANA 專案的一部分，請讓兩份計畫保持一致。我的 [ECC 移轉至 S/4HANA 指南](/zh-TW/ecc-to-s4hana-migration/)說明了 ERP 這一側的路徑和期限。

## 常見的整合模式

我最常看到的情境：

1. **S/4HANA 到 SuccessFactors。**組織資料、人數和薪酬異動。SAP 的標準整合內容涵蓋常見情境；自訂流程處理例外情況。
2. **舊有採購系統到 SAP Ariba。**採購單送出，確認和發票回傳。通常是雙向的。
3. **財務資料到 SAP Analytics Cloud。**把資料從 ECC 或非 SAP 系統移入 SAC。
4. **Salesforce 到 SAP。**成交的訂單流入 SAP，進行出貨、開立發票和庫存更新。我在[Salesforce 與 ERP 整合為何失敗](/zh-TW/why-erp-integration-with-salesforce-fails-and-how-to-fix-it/)一文中說明了設計上的錯誤。

如果您專案的整合工作已經開始延誤，[SAP Integration Suite 交付延誤](/zh-TW/sap-integration-suite-delivery-delays/)一文說明了常見原因。[SAP 整合平台](/zh-TW/sap-implementation/sap-integration-platforms/)概覽則並列比較了各種選項。

## 常見問題

<details>
<summary>SAP CPI 是什麼？現在叫什麼名稱？</summary>

SAP CPI 全名是 Cloud Platform Integration。它現在是 SAP BTP 上 SAP Integration Suite 的 Cloud Integration 功能，與 API Management、Event Mesh 和合作夥伴整合工具並列。「CPI」仍是建置整合流程時的日常稱呼。

</details>

<details>
<summary>SAP CI 是什麼？</summary>

SAP CI 是 SAP Cloud Integration 的簡稱，也就是過去 SAP CPI 的現行名稱。兩個名詞指的都是 SAP Integration Suite 中的同一項功能。

</details>

<details>
<summary>SAP CPI 是中介軟體嗎？</summary>

是的。CPI 是雲端中介軟體：它位於系統之間，負責轉換和路由訊息，並處理錯誤與重試。它取代 SAP PI/PO 等地端中介軟體，而且不會長期儲存業務資料。

</details>

<details>
<summary>SAP CPI 和 SAP PI/PO 有什麼不同？</summary>

PI/PO 是您自己安裝、修補和運行的地端中介軟體。CPI 是 SAP 在 SAP BTP 上為您營運的雲端服務，新的配接器和內容會集中推出。必須留在地端的流程，則由 Edge Integration Cell 處理。

</details>

<details>
<summary>SAP PI/PO 的支援何時結束？</summary>

包含 PI/PO 在內的 SAP NetWeaver 7.5，主流維護於 2027 年底結束。延長維護可至 2030 年底。SAP 提供 Migration Assessment 和 Migration Tooling，協助把情境移轉到 Integration Suite。

</details>

<details>
<summary>SAP CPI 和 SAP BTP 是同一個東西嗎？</summary>

不是。SAP BTP 是平台：應用程式開發、資料、分析、AI 和整合。CPI 是平台上的整合服務。

在界定工作範圍時，預算和技能需求並不相同：BTP 架構師跨服務工作，CPI 專家則負責流程、配接器和對應。

</details>

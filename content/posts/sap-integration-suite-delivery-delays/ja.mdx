SAP Integration Suiteは、SAP Cloud Platform Integrationの単なる名称変更のように聞こえるかもしれません。ですが、そうではありません。対象範囲がより広いのです。SAPはこれを、クラウドおよびハイブリッド環境におけるあらゆるシステム間通信の基盤として位置づけています。つまり、従来以上に中核的な存在になっています。特に、レガシーシステム、サードパーティ製プラットフォーム、複雑なデータフローと並行してS/4HANAを管理するプログラムでは重要です。

## 2026年において、RISEのバンドル、PI/POのサポート終了、JouleがIntegration Suiteの位置づけをどう変えるか

2022年時点の前提から変わった3つのポイントが、現在進行中のどのプログラムにも影響します。

**Integration Suiteは、RISE with SAPおよびGROW with SAPのサブスクリプションにバンドルされています。** 基本容量は含まれていますが、バンドルされた階層を超える大量利用には追加費用が発生します。クラウドエディションを利用する組織では、統合プラットフォームの選定はもはや単独の判断ではありません。Integration SuiteをMuleSoftやBoomiと比較評価するプログラムでは、RISEに含まれるバンドルの経済性を織り込む必要があります。単純な機能対機能の比較ではありません。

**PI/POのメインストリームサポートは2027年に終了します。** まだPI/POを使っているプログラムには、移行ロードマップが必要です。段階的なウェーブ移行のパターン（最初に低リスクのSAP間連携、次にB2B EDI、最後に大量の受注管理）は、複数インターフェースを持つ環境でも通常6か月で収まり、計画予算内に収まることが多いです。一方、2027年の期限に追われて強制的にカットオーバーすると、9か月かかり、通常は6桁ドル規模のリカバリー費用が発生します。

**Joule on Integration Suiteは2024年から2025年にかけて一般提供に到達しました。** 自然言語によるiFlowドラフト作成、失敗メッセージに対するAI支援のエラートリアージ、統合ボリュームパターンの異常検知。標準iFlowでは、確かにスピードアップします。ただし、深い業務ロジックを含む複雑なオーケストレーションには、依然としてシニアアーキテクトが必要です。2026年版のJoule for SAP Activateは、標準スコープにおける統合設計成果物のドラフト作成を30～50%高速化します。

ここでチームが誤る技術判断は、たいてい技術そのものの問題ではありません。オーナーシップの空白、レガシーシステムに対する未検証の前提、本番で必ず起きる障害を見つけるのではなく、ただテストを通すために設計された統合テスト戦略が原因です。

これは、何かが壊れるまでチームが通常は話題にしない意思決定と盲点の一覧です。

## 構成要素と、それぞれが実際に何をするのか

SAP Integration Suiteは単一のツールではありません。複数サービスのバンドルです。どの要素を、いつ、なぜ使うのかを理解しているかどうかで、統合基盤が長期的にどれだけ持ちこたえるかが決まります。

| Component | Role | 誤用したときに何が起きるか |
|---|---|---|
| Cloud Integration (CPI) | メッセージフロー、ルーティング、変換。大半のiFlowでの標準選択肢です | APIやイベントまで含めて何でもCPIに詰め込むと、インターフェースの保守とテストが難しくなります |
| API Management | 外部API公開の統制。レート制限、セキュリティ、分析を担います | これを省くとポイントツーポイント呼び出しが増殖し、後からガバナンスを入れることがほぼ不可能になります |
| Event Mesh | 疎結合な下流トリガー向けの非同期メッセージング | 適切に追跡しないと、メッセージキューが誰にも気づかれないまま増え続けます |
| Integration Advisor | EDIやIDocのような構造化フォーマット向けのマッピング提案 | チームは80%カバーできると思いがちですが、実際は40～60%程度で、残りは手作業が必要になることが多いです |
| Open Connectors | SalesforceやShopifyのようなサードパーティAPIをラップします | 外部プラットフォームの更新でコネクタが静かに壊れます。誰かがエンドポイントを能動的に監視する必要があります |

Integration Suiteを「アドオン付きのCPI」として扱うチームは、API ManagementとEvent Meshを完全に無視しがちです。複雑さが追いつくまでは、それでも動きます。

## 標準コンテンツとカスタム開発

事前パッケージ化されたSAPの統合コンテンツは、適切な文脈では本当に有用です。SAP S/4HANAをSAP AribaやSAP SuccessFactorsと標準プロセスで接続する場合、適合性は高いことが多いです。ですが、実際の業務プロセスがSAPのリファレンスラインの中に収まり続けることはほとんどありません。

| Criteria | 標準コンテンツ | カスタム開発 |
|---|---|---|
| プロセス適合性 | 標準的なSAP間シナリオに最適 | 業務ロジックがSAPのリファレンスから外れている場合 |
| 導入までの時間 | 調整が最小限なら初期セットアップは速いです | 初期工数は増えますが、標準フローが硬直的すぎる場合の手戻りを避けられます |
| 変更容易性 | 深くカスタマイズするとSAPサポートとの整合性を崩しやすいです | 実際の業務プロセスに合わせて設計でき、変更要求も実装しやすいです |
| 長期保守 | 想定以上に改変すると技術的負債のリスクがあります | 明確なアーキテクチャで構築すれば長期保守に向いています |
| インターフェースの複雑性 | 単純な一方向フローに最適 | 条件分岐ルーティング、多段ロジック、レガシー特有の癖がある場合に必要です |

この判断は先送りできません。判断が遅れると、プロジェクトの途中で「標準」iFlowがあまりに大きく改変されてSAPサポートとの整合性を失っていたことが分かり、本番稼働直前のプレッシャーの中で作り直すことになります。

私は、標準コンテンツならカスタムのマスタデータ構造、社内開発で追加された項目、レガシー認証モデルを同時に吸収できるとチームが思い込んだために、数週間を失ったプロジェクトを見てきました。実際にはできませんでした。本来は設計段階で行うべき分析が、UAT中に行われていたのです。

ブループリント段階で問うべきなのは、これは本当にSAPのベストプラクティスに近いプロセスなのか、それとも長年の社内判断によって別物になっているのか、という点です。後者なら、カスタム開発のほうがコードもきれいで、オーナーシップも明確になります。

## 複雑なプログラムにおける統合

大規模なSAPプログラムでは、統合はしばしばワークストリームの狭間に落ちます。各チームにはそれぞれの優先順位とタイムラインがあります。インターフェースはその境界をまたぎますが、調整の責任を持つ人がいません。

私は、2つのプロジェクトチームが同じビジネスパートナー向けの統合を別々に構築し、どちらも同じエンドポイントを向いていたケースを見たことがあります。お互いの存在を認識していませんでした。どちらのチームも、UATになるまでそれに気づきませんでした。こうした失敗は技術的なものではなく、構造的なものです。

中央集権的な統合ガバナンスは早い段階で確立する必要があります。具体的には次のとおりです。

1. すべてのワークストリームから見える共有の統合バックログ
2. デリバリー全体を通じて追跡される、指名されたインターフェースオーナー
3. 各主要デプロイ前のワークストリーム横断の調整チェックポイント
4. 本番稼働コミット前のインターフェース依存関係レビュー

| Challenge area | 何が問題になるか | 対応方法 |
|---|---|---|
| ワークストリーム間の調整 | 各ストリームが孤立してインターフェースを構築し、依存関係が重複します | ワークストリーム横断の設計チェックポイントを持つ共有統合バックログ |
| ミドルウェア再利用 | 複数プログラムが無関係なロジックをCPIに詰め込みます | バージョン管理された共有サービスと、各フローごとの文書化されたオーナーシップ |
| オーナーシップの空白 | 障害が起きても、誰が解決するのか分かりません | 各iFlowまたはAPIに対する指名オーナーを設定し、業務部門とITサポートの双方から見えるようにします |
| 並行デプロイ | 2つの本番稼働が同じエンドポイントやキューを共有し、一方が他方を壊します | 依存関係のあるリリース順序を定義し、カットオーバープランに統合依存関係を入れます |
| 環境不一致 | 開発、テスト、本番が互いを反映しておらず、認証情報も異なります | 自動デプロイスクリプトと、各環境ごとの文書化された認証情報 |
| 業務ルールの後期変更 | UATでの変更により、複数の統合に対して土壇場の修正が必要になります | 各反復に機能オーナーを関与させ、マッピング前提を早期に見直します |

## レガシーシステムとサードパーティ統合

最大の統合課題は、たいてい最新プラットフォームではありません。重要な業務プロセスの真ん中に居座っている古いシステムです。

レガシーERPは、負荷がかかった状態で並行する同期呼び出しを処理できないことがよくあります。API呼び出しを5本並列に流すと、サーバーが遅くなる、固まる、あるいはデータを黙って落とします。非同期統合が有効な場合もありますが、それは受信側システムがキューを処理できる場合に限ります。多くのレガシーシステムにはそれができません。

プロトコルの不一致もよくあり、しかも発見が遅れます。OAuth2とRESTでフローを設計したのに、レガシー側はSOAPしか話せず、しかも30秒固定タイムアウトだった、ということがあります。古いシステムは、トークン更新ロジックを正しくサポートしていないこともあります。

2023年の欧州小売プログラムでは、サードパーティの給与システムが発行するOAuthトークンの有効期限が毎週切れるため、ミドルウェアフローが毎週金曜日に失敗していました。誰も気づかず、2回目のUATサイクルで初めて判明しました。設計段階で見つけていれば1時間で済んだギャップが、1週間の遅延になったのです。

| Risk area | よくある課題 | 計画時の対応 |
|---|---|---|
| 同期処理の限界 | レガシーシステムが並列呼び出しでロックします | 非同期メッセージングを使い、Event MeshまたはCPIで呼び出しを分散させます |
| プロトコル不一致 | レガシーがRESTやOAuthを受け付けず、SOAPでタイムアウトします | 設計開始前にプロトコル互換性を確認します |
| APIレート制限 | バッチジョブが外部APIのスロットリング上限を超えます | API Managementで呼び出しを制御し、CPIに待機ロジックを入れます |
| トークン期限切れ | オフピーク時間帯にフローが静かに失敗します | トークン更新サイクルをスケジュールし、期限切れを先回りで監視します |
| データ形式の硬直性 | レガシーは厳格な形式を要求し、動的ペイロードで解析が壊れます | 設計凍結前に本番相当のサンプルデータで検証します |
| 障害時のフォールバックなし | ファイル転送がリトライなしで失敗し、データが滞留します | ミドルウェアでバッファし、iFlowにリトライとアラートのロジックを組み込みます |

## インターフェースのテスト戦略

統合は、機能テストが確認するような壊れ方はしません。時間的な圧力がかかったとき、バックグラウンドジョブが重なったとき、入力が1件ずつではなく大量に到着したときに壊れます。

機能テストで分かるのは、トランザクションが記帳され、ログにメッセージが出たということです。最初の給与計算実行時に200,000件のIDocレコードが流れ込んだら何が起きるかまではテストしません。あるプロジェクトでは、SITでは問題なく見えたIDocが、実際の給与データ量が流れた途端にキューを停止させました。単体テストでは見つかりませんでした。負荷テストが必要だったのです。

統合テストでカバーすべきで、機能テストでは見落とされるものは次のとおりです。

1. 並行ユーザーを含む現実的なデータ負荷
2. サービス中断と復旧時の挙動
3. ミドルウェアとバックエンドをまたぐタイムアウトとリトライ
4. リアルタイム呼び出しと並行して動くバックグラウンドバッチジョブ
5. 月末やピーク時の負荷シナリオ

環境も重要です。開発環境はきれいです。実負荷もなく、スケジュールの重なりもありません。UATや本番前環境になると、他システムが動き、バッチジョブが走り、夜間ウィンドウも有効になります。デッドロック、競合状態、APIスロットル制限が現れるのはここであって、単体テストではありません。

テストのオーナーシップは、テスト範囲と同じくらい重要です。機能チームはエンドツーエンド結果を検証します。統合チームはログ、リトライ、例外フローを扱います。プロジェクトリードは、環境と負荷条件をまたいだカバレッジを確認します。

## Integration Advisorの限界

Integration Advisorは、EDIFACT、ANSI X12、IDocベースのEDIのような構造化フォーマットに対してマッピング候補を提示します。厳格な規約に従うB2Bフォーマットでは、セットアップ時間を短縮できます。ですが、レガシーシステム、カスタム項目、条件付きロジック、文書化されていない業務ルールを含む企業統合では、あくまで出発点にすぎません。

私が関わったあるチームは、Advisorで80%のマッピングをカバーできると見込んでいました。実際は40%程度でした。残りはカスタムマッピング、業務検証、手動テストが必要でした。プロジェクト予算にこれが織り込まれていないと、後始末は本番稼働直前のプレッシャーの中で行うことになります。

Integration Advisorでは解決できない具体的なギャップは次のとおりです。

1. 長年にわたり非公式に積み上がった業務ロジック（支払条件、価格カテゴリ、数量単位の慣行など）
2. 業務コンテキストに基づく条件付き変換ルール
3. 標準フォーマットに収まらない例外ケースのハンドリング

これらを埋めるには機能チームの入力が必要です。その入力なしのIntegration Advisorでは、技術的にはマッピングされていても、特定シナリオでは業務的に誤ったインターフェースができあがります。

## ドキュメントと本番稼働後のガバナンス

統合は本番稼働で終わりません。ドキュメントが実態からずれ、オーナーシップが正式化されず、ハイパーケア後のサポートが構造化されていないと、時間とともに劣化します。

有用な統合ドキュメントに必要な内容は次のとおりです。

1. 項目マッピングと変換ロジック
2. 認証の詳細（エンドポイント、トークン更新サイクル、認証情報ローテーションのスケジュール）
3. エラーハンドリング経路とフォールバックルール
4. 想定ボリュームと重要な時間帯（月末、給与計算、夜間バッチ）

来週サポートチームに新しい担当者が入ったとして、その人は文書だけを使って失敗中のインターフェースを切り分けられるでしょうか。答えがノーなら、そのドキュメントは本番運用に十分ではありません。

指名されたインターフェースオーナーは必須です。各インターフェースは、たとえ低ボリュームでも、監視、エスカレーション、ライフサイクル更新に責任を持つ個人またはチームが必要です。これがないと、障害はBasis、ミドルウェア、機能チームの間をたらい回しになり、その間ビジネス側は待たされます。

ハイパーケア後についても同じです。初期の集中的なサポート期間が終わると、統合監視は薄れがちです。定期的なエラーログレビュー、プロジェクトチームからサポートチームへのオーナーシップ移管、業務部門とITのSLA整合を含むサポートモデルを作ってください。見えなくなった統合は放置されます。放置された統合は、本番稼働の数週間後に表面化する記帳遅延、請求書欠落、財務レポート不整合の根本原因であることが多いです。

## よくある質問

<details>
<summary>SAP Integration Suiteとは何ですか。CPIとはどう違いますか。</summary>

SAP Integration SuiteはSAP Cloud Platform Integration（CPI）の発展形ですが、対象範囲はより広いです。CPIはIntegration Suiteの1コンポーネント（Cloud Integration）であり、メッセージフロー、ルーティング、変換を担います。

Integration Suiteには、さらに4つのサービスが加わります。API Managementは、レート制限、セキュリティ、分析を通じて外部API公開を統制します。Event Meshは、疎結合な下流トリガー向けの非同期メッセージングを可能にします。Integration Advisorは、EDIやIDocのような構造化データ形式に対するマッピング候補を提示します。Open Connectorsは、SalesforceやShopifyのようなサードパーティAPIをラップします。

Integration Suiteを「名前が変わっただけのCPI」と見なすチームは、API ManagementとEvent Meshを完全に飛ばしがちです。単純な環境ならそれでも動きます。ですが、複雑なクロスシステム環境では、その省略がガバナンスの空白を生み、本番負荷の下で表面化します。

</details>

<details>
<summary>SAP統合で、標準コンテンツとカスタム開発はどう使い分けるべきですか。</summary>

標準コンテンツが適しているのは、プロセスがSAPのベストプラクティスモデルに近く、インターフェースがSAP間（たとえばS/4HANAからAriba、またはSuccessFactors）であり、データロジックが比較的単純な場合です。

カスタム開発のほうがよいのは、長年の社内判断によって業務プロセスがSAPのリファレンスから外れている場合、レガシーシステム特有の癖に個別対応が必要な場合、あるいは条件分岐ルーティングや多段ロジックによって標準フローの保守が難しくなる場合です。

この判断は、設定開始後ではなくブループリント段階で行うべきです。先送りのリスクは明確です。チームが標準コンテンツを大きく改変しすぎてSAPサポートとの整合性を失い、その後、本番稼働直前のプレッシャーの中で作り直すことになります。その作り直しは、最初からきれいにカスタム構築していた場合より高くつきます。

</details>

<details>
<summary>複雑なプログラムでSAP統合が失敗する原因は何ですか。</summary>

私が見てきた中で最も多い原因は、技術的というより構造的なものです。

オーナーシップの空白です。特定のインターフェースについて、監視、リトライ、エラー解決に責任を持つ指名担当者がいません。何か失敗すると、チーム間をたらい回しになります。

並行デプロイの衝突です。2つのプロジェクトワークストリームが、同じエンドポイントやメッセージキューを共有する統合を、それぞれ独立に構築してしまいます。互いの存在を認識していません。これが発覚するのはUATになってからです。

発見が遅れたレガシー制約です。レガシーERPは、負荷下で並行する同期呼び出しを処理できません。負荷テストを実施していれば負荷テストで見つかります。実施していなければ本番稼働で見つかります。

何も見つけないテストです。機能テストは単独ではきれいに通りますが、バッチジョブの重なり、ピーク時のボリューム、並行するバックグラウンド処理間のタイミング競合を再現しません。こうした問題は本番で見つかります。

</details>

<details>
<summary>SAP Integration Suiteの統合テストはどのように構成すべきですか。</summary>

統合テストでは、機能テストが扱わないシナリオをカバーする必要があります。現実的なデータ量、並行ユーザー、バッチジョブの重なり、ピーク時の負荷条件です。

含めるべき具体的なシナリオは次のとおりです。

- 大量データ負荷: 個別トランザクションだけでなく、最初の月末処理や給与計算実行に相当するボリュームでテストします
- 並行するバックグラウンドジョブ: 夜間バッチのスケジュール実行とリアルタイムインターフェースを同時に動かしてテストします
- サービス中断と復旧: 下流システムが一時的に利用不可になった場合に何が起きるかをテストし、リトライロジックとアラートを確認します
- APIスロットル制限: 一括ジョブ中に外部APIのレート制限に達した場合に何が起きるかをテストします

環境は重要です。開発環境はきれいで、負荷も軽いです。UATや本番前環境では、他システムが動き、バッチジョブも走っています。負荷テストと性能検証は、本番条件を反映した環境で実施する必要があります。

</details>

<details>
<summary>SAPにおけるレガシーシステム統合で最も多い問題は何ですか。</summary>

発見が遅れる問題の大半は、3つのパターンで説明できます。

同期負荷の限界です。レガシーERPは複数の並列API呼び出しを処理できないことがよくあります。システムが遅くなるか、データを黙って落とします。非同期メッセージングが有効な場合もありますが、それはレガシーシステム側がキュー処理前提で作られている場合に限ります。実際には、そうでないことが多いです。

プロトコル不一致です。最新のSAPフローはOAuth2とRESTを使います。レガシーシステムは、固定タイムアウト付きのSOAPしか話せないことがあります。こうした不一致は、テスト中に見つけるのではなく、設計中に確認すべきです。

認証トークンの期限切れです。サードパーティシステムが発行するOAuthトークンは、インターフェース実行ウィンドウと合わないスケジュールで失効することがあります。あるプロジェクトでは、この理由で給与連携が毎週金曜日に失敗していました。発見されたのは2回目のUATサイクルです。設計段階でトークン更新サイクルを確認していれば1時間で済みました。UATで見つけた結果、1週間かかりました。

</details>

<details>
<summary>本番稼働後、SAP統合はどのようにガバナンスすべきですか。</summary>

本番稼働後の統合ガバナンスには、3つの要素があります。

指名されたオーナーシップです。各インターフェースには、監視、エラーエスカレーション、ライフサイクル更新に責任を持つ個人またはチームが必要です。これがないと、障害はチーム間をたらい回しになり、解決時間が不必要に長引きます。

生きたドキュメントです。統合ドキュメントには、項目マッピング、認証情報ローテーションスケジュールを含む認証詳細、エラーハンドリング経路、想定ボリュームを含めるべきです。変更時にドキュメントが更新されなければ、役に立たないどころか誤解を招きます。

構造化されたハイパーケア後サポートです。ハイパーケア中の集中的な監視は、やがて薄れます。定期的なエラーログレビュー、プロジェクトからサポートチームへの正式なオーナーシップ移管、業務部門とITのSLA整合を含む長期モデルを作ってください。見えなくなった統合は放置されます。そして、放置された統合は、財務記帳の遅延や消込差異のよくある原因です。

</details>

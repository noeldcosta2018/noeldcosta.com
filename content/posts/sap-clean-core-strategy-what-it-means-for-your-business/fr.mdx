Le clean-core n’est pas un concept marketing de SAP. C’est la différence entre une montée de version qui prend six semaines et une autre qui prend six mois. Avec RISE with SAP et GROW with SAP en 2026, c’est aussi une exigence contractuelle plutôt qu’une simple préférence de conception.

Sur 21 programmes SAP S/4HANA, j’ai vu des entreprises réduire leurs délais de montée de version de 40 % en appliquant les principes du clean-core avant même le démarrage de leurs programmes S/4HANA. En 2024, une entreprise européenne de biens de consommation a remplacé une logique de tarification héritée par une application Fiori modulaire construite hors du core sur SAP BTP, et a totalement éliminé les tests de régression de son cycle de montée de version. Ce n’est pas de la théorie. Voilà à quoi cela ressemble quand l’approche est appliquée tôt.

Les équipes qui ignorent le clean-core n’évitent pas le travail. Elles le repoussent. Et ce travail repoussé réapparaît sous forme de montées de version bloquées, de marathons de tests de régression, de code custom que plus personne ne comprend, et de blocages d’intégration avec Joule lorsque SAP publie des fonctions d’IA qui recouvrent ce que vous avez développé sur mesure.

## Ce que le clean-core veut vraiment dire

Une stratégie clean-core SAP consiste à garder le core digital S/4HANA léger. Pas de code custom enfoui partout. Pas d’intégrations câblées en dur qui cassent quand SAP met à jour un objet standard. Pas de programmes Z qui colmatent des écarts que le processus standard pourrait gérer si le métier acceptait de s’adapter.

À la place, les personnalisations et extensions sont construites en parallèle sur SAP BTP (la Business Technology Platform). La logique qui vivait autrefois dans le core est déplacée à l’extérieur. Le système ERP reste aligné sur la trajectoire standard de montée de version de SAP.

La raison pratique pour laquelle c’est important : le cycle de release de SAP avec RISE with SAP est plus rapide qu’à l’époque de ECC. Des mises à jour trimestrielles, des innovations continues, de nouvelles fonctionnalités tout au long de l’année. Un système core fortement modifié signifie que chaque mise à jour devient un risque de régression. Un clean-core signifie que les mises à jour passent sans casser la logique custom, parce que cette logique est découplée.

**Clean-core vs dirty core :**

- **Dirty core :** du code custom ABAP qui modifie des objets standard SAP, des intégrations câblées en dur qui contournent les API, une logique métier embarquée dans le core qui casse quand SAP modifie la fonctionnalité sous-jacente.
- **Clean-core :** des extensions construites via des méthodes approuvées par SAP (BTP, ABAP Cloud, outils d’extensibilité in-app). Le comportement standard de SAP est préservé. Les montées de version sont prévisibles.

Clean ne veut pas dire sans personnalisation. Cela veut dire que les personnalisations sont construites d’une manière qui ne casse pas quand SAP publie une nouvelle version.

## Les cinq dimensions du clean-core SAP

 organise l’approche clean-core autour de cinq dimensions. Chacune est un levier pour réduire le couplage entre la logique custom et le core ERP.

| Dimension | Ce que cela signifie en pratique |
|---|---|
| Extensibilité | Construire des fonctionnalités sur mesure sans modifier le code du core : utiliser BTP ou les outils in-app au lieu de modifier les objets standard SAP |
| Intégration | Connecter les systèmes via des API standard, et non via des intégrations point à point câblées en dur dans le core |
| Configuration | Utiliser les paramètres in-app de SAP et le customizing client pour répondre aux besoins métier avant de recourir au code |
| Infrastructure & Operations | Garder des environnements stables et cohérents ; gouverner qui peut appliquer des modifications et par quel mécanisme |
| Modifications | Réduire au minimum ou éliminer les changements directs sur les objets core SAP ; là où des modifications existent, les suivre et les gérer explicitement |

Ces cinq dimensions décrivent où se situe votre implémentation actuelle par rapport à un état clean-core. Ce sont aussi les cinq domaines qu’une évaluation clean-core doit examiner.

## SAP BTP comme couche d’extensibilité

SAP BTP est l’endroit où vivent les extensions clean-core. Au lieu d’écrire du code custom ABAP dans S/4HANA, vous construisez des applications et des services sur BTP qui interagissent avec S/4HANA via des API standard.

ABAP Cloud est la version cloud-ready de ABAP chez SAP : elle impose le clean-core par conception. Elle limite ce que vous pouvez toucher et exige l’usage d’API approuvées. Voyez-le comme un ABAP avec des garde-fous. Il s’exécute dans l’environnement SAP BTP ABAP Environment et sur S/4HANA Cloud, et c’est ainsi que la logique custom ABAP doit être écrite dans un contexte clean-core.

Les deux types d’extensibilité :
- **Extensibilité in-app :** champs personnalisés, formulaires ou changements de workflow réalisés via les outils fournis par SAP dans S/4HANA. Aucune modification du core.
- **Extensibilité side-by-side :** applications ou services complets construits sur BTP et connectés à S/4HANA via des API. La logique vit entièrement hors du core.

Les deux sont conformes au clean-core. La distinction compte pour la complexité et la gouvernance, pas pour le principe.

## Erreurs courantes dans les projets clean-core

### Trop de code Z et aucune visibilité

Une base de code custom lourde reste le principal frein. Chaque enhancement exit, chaque rapport Z, chaque modification d’un objet standard porte un risque pour les montées de version. La plupart des équipes ne savent pas ce qui est encore réellement utilisé.

Sur un projet, des outils automatisés d’analyse de code ont fait passer le nombre d’objets de 18 000 à 3 200. L’équipe n’a pas eu besoin de revoir manuellement chaque objet. Les outils ont identifié le code inutilisé et séparé la logique métier critique du bruit. Commencer par le code qui s’exécute tous les jours est la bonne séquence ; ne gaspillez pas d’énergie à nettoyer un rapport utilisé deux fois par an par une seule équipe régionale.

### Aucune implication du métier

Le clean-core n’est pas seulement un exercice technique. Sans contribution du métier, vous nettoyez le code pour découvrir ensuite que le processus derrière n’a plus de sens.

Un responsable finance avec qui j’ai travaillé n’a vraiment compris sa nouvelle application Fiori qu’après une session de walkthrough de 45 minutes. Cette session a évité deux semaines d’allers-retours de changements pendant l’UAT. Attendre la phase de test pour impliquer les utilisateurs métier, c’est là que les reprises commencent.

### Aucune gouvernance

Sans règles sur ce qui peut ou non entrer dans le core, la dette technique revient progressivement. Les équipes retombent dans leurs habitudes. Un an après un projet clean-core, le système ressemble à l’environnement ECC d’origine, simplement sur une infrastructure plus récente.

Dès le premier jour, une autorité de conception doit examiner chaque extension, enhancement ou contournement. La question par défaut doit être : pourquoi cela ne peut-il pas vivre dans BTP ?

### Résistance à la standardisation des processus

C’est la partie la plus difficile de tout projet clean-core. L’objection est presque toujours une variante de « notre processus est différent » ou « le standard SAP ne fonctionnera pas pour nous ».

Dans un atelier avec une équipe commerciale, le processus « unique » s’est révélé être à 80 % de l’administratif hérité redondant : des étapes manuelles et des formulaires accumulés au fil des années. Le standard SAP a en réalité amélioré l’expérience client quand l’équipe a abandonné les contournements. Une entreprise mondiale a constaté que 80 % de son traitement des commandes pouvait être standardisé. Les 20 % restants ont été étendus proprement dans BTP.

La question à poser à chaque fois : est-ce vraiment un différenciateur métier, ou est-ce simplement familier ?

### Complexité de la migration des données

Des champs personnalisés, des structures de données héritées, des formats incohérents issus de décennies d’exploitation de ECC. Un client du retail avait plus de 15 000 champs personnalisés à traiter.

La migration des données consomme généralement 30–40 % du délai total d’implémentation. La plupart des équipes la sous-estiment. Le travail consiste à décider quelles données conserver, à nettoyer les doublons, à valider la logique métier liée aux champs personnalisés, et à tout mapper vers le modèle simplifié que le clean-core permet.

Commencez tôt. Impliquez les équipes fonctionnelles et techniques dès le premier sprint.

### Lacunes de compétences

ABAP ne suffit pas. L’extensibilité clean-core exige une vraie maîtrise de BTP, de la conception d’API, d’une pensée modulaire et de l’architecture side-by-side. Une équipe forte en ABAP mais sans expérience sur BTP créera des goulots d’étranglement, non pas parce qu’elle ne peut pas apprendre, mais parce que l’apprentissage prend du temps.

Un industriel a lancé un programme interne de formation BTP de trois mois avant le démarrage de son projet S/4HANA. Cela a payé avec un déploiement plus fluide et moins de surprises d’intégration.

Le clean-core SAP consiste à garder votre système S/4HANA exempt de modifications des objets standard SAP. Les personnalisations sont construites en side-by-side sur SAP BTP à l’aide d’API standard, plutôt que d’être embarquées dans le core ERP.

C’est important parce que la fréquence des montées de version de SAP a fortement augmenté avec RISE with SAP. Quand le code custom est embarqué dans le core, chaque montée de version risque de casser une logique métier critique. Quand les extensions vivent hors du core sur BTP, les montées de version peuvent être appliquées sans tests de régression sur le code custom.

Le support de ECC prend fin en 2033. La plupart des organisations qui utilisent ECC planifient maintenant leur migration vers S/4HANA. Celles qui appliquent les principes du clean-core avant de migrer réalisent la transition plus vite et avec moins de surprises. Celles qui transportent les schémas de personnalisation de ECC dans S/4HANA recréent le même problème sur une infrastructure plus récente.

<details>
<summary>Quelles sont les cinq dimensions du clean-core SAP ?</summary>

SAP organise le clean-core autour de cinq dimensions : Extensibilité, Intégration, Configuration, Infrastructure and Operations, et Modifications.

L’Extensibilité couvre la manière dont les fonctionnalités sur mesure sont construites : idéalement via BTP ou des outils in-app, et non par des modifications directes du core. L’Intégration couvre la manière dont les systèmes se connectent : via des API standard, et non via des intégrations câblées en dur dans le core. La Configuration couvre l’utilisation des paramètres in-app de SAP pour répondre aux besoins métier avant de recourir au code. Infrastructure and Operations couvre la stabilité des environnements et la gouvernance des modifications. Les Modifications couvrent la gestion et la réduction des changements directs sur les objets core SAP.

Une évaluation clean-core examine les cinq. Le résultat identifie où se situe le système aujourd’hui et ce qui doit changer avant une migration ou une montée de version S/4HANA.

</details>

<details>
<summary>Quel est le rôle de SAP BTP dans une stratégie clean-core ?</summary>

SAP BTP est la couche d’extensibilité où vit la logique custom clean-core. Au lieu de modifier S/4HANA, vous construisez des applications et des services sur BTP qui interagissent avec l’ERP via des API standard. Le core reste intact. Les montées de version passent sans casser la logique custom.

L’extensibilité in-app (champs personnalisés, modifications de workflow via les outils fournis par SAP) garde le core propre tout en permettant des changements dans S/4HANA. L’extensibilité side-by-side (applications ou services sur BTP connectés via des API) déplace entièrement la logique hors du core pour les scénarios plus complexes.

ABAP Cloud est la version de ABAP conforme au clean-core pour les environnements cloud. Elle impose les standards clean-core en limitant ce qui peut être modifié et en exigeant l’usage d’API approuvées.

</details>

<details>
<summary>Comment évaluer le niveau de préparation clean-core de mon système SAP actuel ?</summary>

Une évaluation clean-core couvre quatre domaines principaux : le code custom (où il existe, quels objets il touche, s’il est encore activement utilisé), les modifications du système (tout changement apporté aux objets standard SAP), les intégrations (les connexions point à point qui devraient être basées sur des API), et l’approche d’extensibilité (la manière dont la logique custom actuelle est structurée par rapport aux standards clean-core).

Le résultat prend généralement la forme d’une feuille de route : quel code custom conserver et déplacer vers BTP, lequel retirer, quelles intégrations reconstruire à l’aide d’API standard, et quelles structures de gouvernance doivent être en place avant le démarrage du projet.

Les outils automatisés de scan de code réduisent fortement l’effort manuel. Sur un projet, un scan de code a identifié 18 000 objets, dont la plupart n’étaient pas utilisés. Une remédiation active a ramené ce nombre à 3 200 avant le démarrage du programme S/4HANA.

</details>

<details>
<summary>Qu’est-ce qu’un "dirty core" et comment cela crée-t-il des problèmes ?</summary>

Un dirty core est un système SAP avec du code custom qui modifie des objets standard, des intégrations câblées en dur qui contournent les API standard, et une logique métier embarquée dans l’ERP qui entre en conflit avec la trajectoire standard de montée de version de SAP.

Les problèmes s’accumulent avec le temps. Chaque montée de version exige des tests sur tous les objets modifiés. Quand SAP modifie une fonction standard, le code custom construit par-dessus casse. Le périmètre des tests de régression grandit à chaque release. Les équipes cessent de faire les montées de version parce que le coût devient trop élevé, ce qui signifie qu’elles prennent du retard sur les correctifs de sécurité, les nouvelles fonctionnalités et les fonctions supportées.

Le dirty core n’est pas le résultat de mauvaises décisions ; c’est le résultat de pratiques de développement héritées de l’ère ECC, appliquées à un système qui fonctionne désormais sur un cycle de montée de version plus rapide. Le clean-core est la réponse architecturale à ce changement.

</details>

<details>
<summary>Quelles sont les erreurs les plus courantes dans une implémentation clean-core ?</summary>

Six reviennent systématiquement.

Premièrement : faire entrer du code Z dans le projet sans savoir ce qui est encore utilisé. La plupart des équipes supposent qu’une plus grande part de leurs personnalisations est critique pour le métier qu’elle ne l’est réellement. Les scans de code automatisés révèlent généralement des volumes importants d’objets inutilisés.

Deuxièmement : traiter le clean-core comme un projet purement technique. Sans implication du métier dès le départ, vous nettoyez du code qui soutient des processus qui ne servent plus l’entreprise. Un walkthrough de processus de 45 minutes avant l’UAT peut éviter deux semaines de reprises.

Troisièmement : aucun modèle de gouvernance. Sans autorité de conception pour examiner chaque extension et chaque enhancement, la dette technique revient progressivement. Le projet clean-core recrée le désordre de ECC sur une infrastructure plus récente.

Quatrièmement : accepter « notre processus est différent » comme raison de personnaliser ; en pratique, la plupart du temps, le processus est surtout familier plutôt que réellement différenciant. Le flux « unique » d’une équipe commerciale s’est révélé être à 80 % de l’administratif hérité redondant.

Cinquièmement : sous-estimer la migration des données. Les champs personnalisés, les structures héritées et les formats incohérents consomment généralement 30–40 % du temps total d’implémentation.

Sixièmement : ne pas développer les compétences BTP avant le démarrage du projet. Une équipe forte en ABAP mais sans maîtrise de BTP crée des goulots d’étranglement en cours de projet, coûteux à résoudre.

</details>

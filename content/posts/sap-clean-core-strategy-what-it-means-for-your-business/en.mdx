Clean core decides whether an S/4HANA upgrade takes six weeks or six months. If your system is full of modifications to SAP standard objects, every release becomes a regression project. If your custom logic sits behind released interfaces, upgrades become routine maintenance.

I have seen firms cut upgrade timelines by 40% by applying clean core principles before their S/4HANA programme started. One consumer goods company replaced legacy pricing logic with a modular Fiori app built outside the core, and its upgrades stopped breaking that logic.

A lot has changed since I first wrote this in April 2025. SAP now describes clean core through five guiding principles and, since August 2025, classifies every extension into one of four levels. The ECC deadlines are also clearer. This version reflects that.

## What clean core means in practice

Clean core means keeping your S/4HANA system as close to SAP standard as your business allows, and building anything extra in a way that survives upgrades.

You can still customise. The customisation has to use interfaces SAP has released and promised to keep stable. SAP offers two ways to do that:

- **On-stack, with ABAP Cloud.** Extensions run inside S/4HANA but only use released APIs and extension points.
- **Side-by-side, on SAP BTP.** Extensions run as separate applications and talk to S/4HANA through APIs or events.

SAP's own guidance is to choose per use case, with BTP first. In my experience, where the code runs matters less than whether the requirement needs code at all.

A dirty core looks familiar to anyone who ran ECC: modified standard programs, Z-tables written to directly, interfaces that read SAP internals, implicit enhancements nobody documented. None of it was wrong when it was built. It just was not built for a system that upgrades every year or two.

## SAP's five clean core principles

SAP organises clean core around five guiding principles. The earlier version of this article listed different headings. These are the ones SAP uses, with what I look at first in each:

| Principle | What SAP means | What I check first |
|---|---|---|
| Processes | Stay as close as possible to the SAP standard process | Which process variants exist only because "we always did it this way" |
| Extensibility | Extensions decoupled from the core through released APIs, with governance over which option is used | How much custom code exists, how much is used, and which level it sits at |
| Data | Clean, compliant data with an established governance model | Duplicate and incomplete master data, custom fields nobody can explain |
| Integrations | Standardised, secure connections built on supported technologies | Point-to-point interfaces that read tables directly |
| Operations | Governance, people, processes and tools that keep the other four in place | Who approves an extension, and what stops the next modification |

Most teams start and finish with extensibility because it is the easiest to measure. In my experience processes and data cause more delay. Custom code is usually the symptom. The process behind it is the cause.

## Levels A to D: where your custom code sits

In August 2025 SAP replaced its earlier three-tier extensibility model with the [clean core level concept](https://news.sap.com/2025/08/extend-sap-s4hana-cloud-right-way-clean-clear/). Each extension is assessed on how it is built, how decoupled it is from the core and how easily it can be upgraded.

| Level | SAP's description | What it means for your upgrade |
|---|---|---|
| A | Extend with SAP Build. Only publicly released, stable interfaces, on-stack with ABAP Cloud or side-by-side on BTP | Lowest risk. SAP backs these interfaces with stability contracts |
| B | Also uses SAP's classic APIs and technologies | Generally upgrade-stable, but outside the cloud development model |
| C | Accesses SAP internal objects | Partially compliant. Each upgrade needs checking; SAP plans a changelog for internal objects |
| D | Not recommended: modifications, writes to SAP tables, implicit enhancements, explicitly non-recommended objects | The technical debt to remove first |

This is more useful than the old "clean or not clean" debate. It lets you set a target per object. Not everything has to reach level A. Moving your level D objects to B or C before an upgrade is already a real reduction in risk.

## Where I would start

If you asked me to assess your system next month, this is the order I would follow.

1. **Find out what is used.** Run the SAP Readiness Check, which comes with your maintenance agreement, and collect usage data on your custom code. On one programme, analysis with smartShift took us from 18,000 custom objects to 3,200. Most of the rest was simply not used.
2. **Classify what remains into levels A to D.** The ABAP test cockpit is SAP's tool for code-level checks. Under RISE, the RISE with SAP Methodology dashboard reports clean core adoption.
3. **Decide object by object.** Retire it, move it to a released interface, rebuild it on BTP or keep it with a documented reason. Start with code that runs every day. A report used twice a year by one regional team can wait.
4. **Put the business in the room.** A finance lead I worked with only understood their new Fiori app after a 45-minute walkthrough. That session saved two weeks of back-and-forth in UAT.
5. **Challenge "our process is different".** In one sales team workshop, the "unique" process turned out to be 80% redundant legacy admin. Standard SAP improved their customer experience once the workarounds went.
6. **Start data work early.** One retail client had over 15,000 custom fields to sort through. In my experience data migration takes 30 to 40% of the implementation effort, and it is the part most plans underestimate. I cover why in [why SAP data migration fails](/why-sap-data-migration-fails-and-how-to-fix-it/).
7. **Set the governance before go-live.** A design authority should review every new extension. The default question used to be "why can't this live on BTP?" Today I would ask "why can't this be level A, and if it can't, what level are we accepting and why?"

Skills matter as much as tools. An ABAP team that has not worked with ABAP Cloud or BTP will slow the programme down while it learns. One manufacturer I worked with ran a three-month internal BTP programme before its S/4HANA project started, and it paid off in fewer surprises during build.

## Clean core, RISE and AI: what is required and what is not

Three questions come up in almost every conversation I have about this.

**Is clean core mandatory under RISE with SAP?** Not as a blanket rule. In S/4HANA Cloud Public Edition you can only extend through released interfaces, so the system enforces it. In Private Edition and on-premise you can still modify the core. Clean core there is a governance choice, and SAP tracks it through the RISE methodology dashboard. If an SI tells you it is contractual, ask them to show you the clause.

**How long do I have on ECC?** For SAP ERP 6.0 on enhancement packages 6 to 8, [mainstream maintenance ends on 31 December 2027](https://news.sap.com/2020/02/sap-s4hana-maintenance-2040-clarity-choice-sap-business-suite-7/). Optional extended maintenance runs to 31 December 2030 at extra cost, and SAP asks customers to order it by Q3 2027. Earlier enhancement packages left mainstream maintenance at the end of 2025. After 2030, the [SAP ERP, private edition, transition option](https://news.sap.com/2025/08/rise-with-sap-journey-sap-erp-private-edition-transition-option-updates/) covers 2031 to 2033. It applies only to large systems already moved to SAP ERP, private edition on SAP HANA before the end of 2030, and only with SAP's max success plan. Treat 2033 as an exception route, not a planning date. My [ECC to S/4HANA migration guide](/ecc-to-s4hana-migration/) covers the route choices.

**Does clean core matter for AI?** SAP builds its AI features, including Joule, on top of its standard processes and data model. Joule for developers generates ABAP Cloud code against released APIs. My working view is simple: the closer your processes and data are to standard, the less adaptation you need before those features are useful to you. Heavily modified processes are where AI features are hardest to adopt.

The teams that skip clean core do not avoid the work. They defer it, and it comes back as blocked upgrades, regression testing marathons and custom code nobody understands.

If you are about to sign an S/4HANA or RISE contract, ask your SI for a level A to D classification of your current custom code before you agree the scope. If they cannot produce one, that tells you something about the estimate. ## Frequently asked questions

<details>
<summary>What is SAP clean core?</summary>

Clean core means keeping S/4HANA close to SAP standard and building extensions only through interfaces SAP has released and committed to keep stable. Extensions run either on-stack with ABAP Cloud or side-by-side on SAP BTP. The goal is that upgrades do not break your custom logic.

</details>

<details>
<summary>What are the five dimensions of SAP clean core?</summary>

SAP calls them the five guiding principles of clean core: processes, extensibility, data, integrations and operations. Processes stay close to standard. Extensions use released APIs. Data is kept clean under a governance model. Integrations use standardised, supported technologies. Operations covers the governance, people and tools that keep the other four in place.

</details>

<details>
<summary>What are the SAP clean core levels A, B, C and D?</summary>

Since August 2025 SAP classifies extensions into four levels. Level A uses only publicly released, stable interfaces. Level B also uses classic SAP APIs. Level C accesses SAP internal objects and needs checking at each upgrade. Level D covers modifications, writes to SAP tables, implicit enhancements and other non-recommended techniques, and represents the highest risk.

</details>

<details>
<summary>Is clean core mandatory with RISE with SAP?</summary>

Not as a blanket rule. S/4HANA Cloud Public Edition only allows extensions through released interfaces, so it enforces clean core technically. In Private Edition you can still modify the core, so clean core is a governance decision. SAP reports clean core adoption through the RISE with SAP Methodology dashboard.

</details>

<details>
<summary>When does SAP ECC support end?</summary>

For SAP ERP 6.0 on enhancement packages 6 to 8, mainstream maintenance ends on 31 December 2027, with optional extended maintenance to 31 December 2030 at extra cost. Earlier enhancement packages left mainstream maintenance at the end of 2025. The SAP ERP, private edition, transition option extends to 2033 only for eligible large systems moved to SAP ERP, private edition on SAP HANA before the end of 2030.

</details>

<details>
<summary>How do I assess my SAP system's clean core readiness?</summary>

Start with the SAP Readiness Check and usage data for your custom code. Classify what is still used into levels A to D, using the ABAP test cockpit for code-level checks. Then decide per object whether to retire it, move it to a released interface, rebuild it on SAP BTP or keep it with a documented reason. Review processes and data at the same time, because they usually explain why the code exists.

</details>

<details>
<summary>What is the role of SAP BTP in a clean core strategy?</summary>

SAP BTP is where side-by-side extensions run. Applications on BTP connect to S/4HANA through APIs and events, so the core stays untouched. SAP recommends a BTP-first approach, with on-stack ABAP Cloud extensions where the logic needs to sit close to the data or the transaction.

</details>

SAP clean core means keeping your S/4HANA system as close to SAP standard as your business allows. Anything you add is built through interfaces SAP has released and promised to keep stable, so upgrades do not break it.

Short answer: clean core is a discipline for how you extend and govern SAP. Custom logic goes on-stack with ABAP Cloud or side-by-side on SAP BTP, and SAP grades every extension from level A (cleanest) to level D (modifications to remove). The payoff is faster upgrades: I have seen firms cut upgrade timelines by 40% this way.

If your system is full of modifications to SAP standard objects, every release becomes a regression project. If your custom logic sits behind released interfaces, upgrades become routine maintenance.

I have seen firms cut upgrade timelines by 40% by applying clean core principles. They did it by keeping customisations to the minimum and governing the ones they kept.

In 2024 a European consumer goods company replaced its legacy pricing logic with a modular Fiori app built outside the core on SAP BTP. That eliminated regression testing for that logic entirely.

## What clean core means for your ERP

You can still customise a clean core ERP. The customisation has to use interfaces SAP has released and committed to keep stable. SAP offers two ways to do that:

- **On-stack, with ABAP Cloud.** Extensions run inside S/4HANA but only use released APIs and extension points.
- **Side-by-side, on SAP BTP.** Extensions run as separate applications and talk to S/4HANA through APIs or events.

SAP describes its approach as BTP-first, choosing per use case. In my experience, where the code runs matters less than whether the requirement needs code at all.

A dirty core looks familiar to anyone who ran ECC: modified standard programs, Z-tables written to directly, interfaces that read SAP internals, implicit enhancements nobody documented. None of it was wrong when it was built. It just was not built for a system that upgrades every year or two.

## SAP's five clean core principles

SAP organises clean core around five guiding principles. This is how SAP frames each one, and what I look at first:

| Principle | What SAP means | What I check first |
|---|---|---|
| Processes | Stay as close as possible to the SAP standard process | Which process variants exist only because "we always did it this way" |
| Extensibility | Extensions decoupled from the core through released APIs, with governance over which option is used | How much custom code exists, how much is used, and which level it sits at |
| Data | Clean, compliant data with an established governance model | Duplicate and incomplete master data, custom fields nobody can explain |
| Integrations | Standardised, secure connections built on supported technologies | Point-to-point interfaces that read tables directly |
| Operations | Governance, people, processes and tools that keep the other four in place | Who approves an extension, and what stops the next modification |

Most teams start and finish with extensibility because it is the easiest to measure. In my experience processes and data cause more delay. Custom code is usually the symptom, and the process behind it is the cause.

## Clean core levels A to D

In August 2025 SAP replaced its earlier three-tier extensibility model with the [clean core level concept](https://news.sap.com/2025/08/extend-sap-s4hana-cloud-right-way-clean-clear/). Each extension is rated on how it is built, how decoupled it is from the core and how safely it survives an upgrade. If you read older SAP material that talks about tiers, this is what superseded it.

<explainer-compare title="Clean core levels A to D" caption="Upgrade risk rises from A to D. Not everything has to reach A, but D is the debt to clear first." options="Level A|Level B|Level C|Level D" criteria="What it uses => Publicly released, stable interfaces only ; Also SAP's classic APIs ; SAP internal objects ; Modifications, writes to SAP tables, implicit enhancements|Upgrade risk => [0] Lowest, backed by stability contracts ; [1] Generally upgrade-stable ; [2] Needs checking at each upgrade ; [3] Highest|What to decide => The default for anything new ; Accept, with the reason recorded ; Accept with a reason, recheck each upgrade ; Remove first, or move it to B or C" highlight="4" source="SAP clean core level concept, SAP News, August 2025"></explainer-compare>

Level A uses only publicly released interfaces with stability contracts, built with SAP Build, ABAP Cloud or BTP. Level B adds SAP's classic APIs. Level C touches SAP internal objects, and SAP plans a changelog for those to help with upgrade planning.

Level D is modifications, writes to SAP tables, implicit enhancements and other techniques SAP does not recommend. This is more useful than the old "clean or not clean" debate, because it lets you set a target per object. Moving your level D objects to B or C before an upgrade is already a real reduction in risk.

## ABAP Cloud and BTP extensibility for S/4HANA Cloud

ABAP Cloud is SAP's cloud-ready ABAP development model. Developers use the "ABAP for Cloud Development" language version and can only build on released objects, public APIs and extension points. It started in the SAP BTP ABAP environment and is now available in every S/4HANA edition ([SAP ABAP Cloud FAQ](https://pages.community.sap.com/topics/abap/abap-cloud-faq)).

S/4HANA Cloud gives you three extension routes. Key user extensibility covers simple field, logic and UI changes without touching SAP code. Developer extensibility with ABAP Cloud handles tightly coupled logic, and side-by-side extensions on SAP BTP handle anything that should stay decoupled.

The edition decides how much choice you have:

| | S/4HANA Cloud Public Edition | S/4HANA Cloud Private Edition and on-premise |
|---|---|---|
| ABAP development | ABAP Cloud only, mandatory for new customers since release 2208 | ABAP Cloud recommended since 2022; classic ABAP still permitted |
| Changes to SAP code | Not possible | Possible, but they are level D |
| Key user and BTP side-by-side extensions | Available | Available |
| Who enforces clean core | The system | Your governance |

My rule for Private Edition customers: treat it as if it were Public Edition for anything new. Classic ABAP is allowed, but every classic object you add today is a decision someone has to defend at the next upgrade.

## Clean core governance: who owns the decisions

Clean core decisions should be owned by a design authority made up of business and IT. IT alone will approve anything that is technically possible. The business alone will ask for its old process back.

This is how I would set it up:

1. **Name the members.** Business process owners for each major area, plus the solution architect and the lead developer. The business owners decide whether a requirement is real, and IT decides how it gets built.
2. **Agree the order of preference before build starts.** Standard process first, then key user extensibility, then level A on ABAP Cloud or BTP. Level B or C needs a written reason, and level D needs an exit plan.
3. **Make every extension request carry an owner and a business reason.** No owner, no build. The decision and the level accepted go into one register.
4. **Put a technical gate in front of transports.** Run the ABAP test cockpit's clean core checks on a schedule, and stop new level D code before it reaches production.
5. **Review the register before every upgrade.** Retire what nobody uses any more and move anything that can now reach a higher level.

The question at that table used to be "why can't this live on BTP?" Today I would ask "why can't this be level A?" If it can't, the next question is which level you are accepting and why.

The biggest clean core mistake I see is trying to make SAP work like Oracle. Adopt SAP's standard processes rather than rebuilding another system's logic in custom code. ## Clean core and change management

Clean core is a change management problem before it is a technical one. Every custom object exists because somebody asked for it. Removing it means persuading that person the standard process is good enough.

That conversation goes better when the business sees the new process working, not a slide about it. It also goes better when you test the claim that a process is unique, because it often is not (see steps 4 and 5 below).

Skills matter as much as tools. An ABAP team that has not worked with ABAP Cloud or BTP will slow the programme down while it learns. One manufacturer I worked with ran a three-month internal BTP programme before its S/4HANA project started, and it paid off in fewer surprises during build.

## Clean core compliance: how to measure it

Clean core compliance is how much of your system meets SAP's criteria across the five principles. You cannot manage it without numbers, and SAP gives you three places to get them.

1. **The ABAP test cockpit.** SAP's tool for code-level checks. It shows which custom objects use unreleased objects, modifications or direct table access.
2. **The SAP Readiness Check.** It comes with your maintenance agreement and shows what an S/4HANA move will touch before you commit.
3. **The RISE with SAP Methodology dashboard, also known as the clean core dashboard.** It runs in [SAP Cloud ALM](https://support.sap.com/en/alm/sap-cloud-alm/sap-cloud-alm-clean-core-adoption.html). Its system view checks your S/4HANA version, confirms data collection tools are active and reviews extensions ahead of an upgrade, and its operations view tracks operational KPIs.

The numbers I would put in front of the design authority every month are simple. How many custom objects sit at each level, and is level D falling? How many exceptions are open, and does each have an owner?

## Where I would start

If you asked me to assess your system next month, this is the order I would follow.

1. **Find out what is used.** Run the SAP Readiness Check and collect usage data on your custom code. On one programme, analysis with smartShift took us from 18,000 custom objects to 3,200, because most of the rest was simply not used.
2. **Classify what remains into levels A to D.** Use the ABAP test cockpit for the code. If you are on RISE, the clean core dashboard tracks it from there.
3. **Decide object by object.** Retire it, move it to a released interface, rebuild it on BTP or keep it with a documented reason. Start with code that runs every day, because a report used twice a year by one regional team can wait.
4. **Put the business in the room.** A finance lead I worked with only understood their new Fiori app after a 45-minute walkthrough. That session saved two weeks of back-and-forth in UAT.
5. **Challenge "our process is different".** In a sales team workshop at a European industrial company in 2023, the "unique" process turned out to be 80% redundant legacy admin. Standard SAP improved their customer experience once the workarounds went.
6. **Start data work early.** A GCC retail client I worked with in 2024 had over 15,000 custom fields to sort through. In my experience data migration takes 30 to 40% of the implementation effort, and my [SAP implementation cost guide](/sap-implementation-cost-and-budget-breakdown/) shows where that lands in the budget.
7. **Set the governance before go-live.** Stand up the design authority described above and make it the only route for a new extension.

## Clean core, RISE and AI: what is required and what is not

Three questions come up in almost every conversation I have about this.

### Is clean core mandatory under RISE with SAP?

Not as a blanket rule. In Public Edition the system enforces it, while in Private Edition and on-premise you can still modify the core.

There, clean core is a governance choice that SAP tracks through the RISE methodology dashboard. If an SI tells you it is contractual, ask them to show you the clause.

### How long do I have on ECC?

For SAP ERP 6.0 on enhancement packages 6 to 8, [mainstream maintenance ends on 31 December 2027](https://news.sap.com/2020/02/sap-s4hana-maintenance-2040-clarity-choice-sap-business-suite-7/). Optional extended maintenance runs to 31 December 2030 at extra cost.

After that, the [SAP ERP, private edition, transition option](https://news.sap.com/2025/08/rise-with-sap-journey-sap-erp-private-edition-transition-option-updates/) covers 2031 to 2033. It applies only to large systems already moved to SAP ERP, private edition on SAP HANA before the end of 2030.

Treat 2033 as an exception route, not a planning date. My [ECC to S/4HANA migration guide](/ecc-to-s4hana-migration/) covers the route choices.

### Does clean core matter for AI?

Yes. Keeping SAP standard helps AI and Joule work better, and heavily modified processes are where they are hardest to adopt.

SAP builds its AI features, including Joule, on its standard processes and data model. Joule for developers generates ABAP Cloud code against released APIs. I cover how cloud, AI and clean core fit together in [ERP modernisation](/erp-modernization-2025-cloud-ai-clean-core/).

The teams that skip clean core do not avoid the work. They defer it, and it comes back as blocked upgrades, regression testing marathons and custom code nobody understands.

SAP clean core σημαίνει ότι κρατάτε το σύστημα S/4HANA όσο πιο κοντά στο standard της SAP επιτρέπει η επιχείρησή σας. Ό,τι προσθέτετε χτίζεται μέσω διεπαφών που η SAP έχει κάνει released και έχει δεσμευτεί να κρατά σταθερές, ώστε οι αναβαθμίσεις να μην το σπάνε.

Σύντομη απάντηση: το clean core είναι μια πειθαρχία για το πώς επεκτείνετε και διακυβερνάτε το SAP. Η custom λογική μπαίνει on-stack με ABAP Cloud ή side-by-side στο SAP BTP, και η SAP βαθμολογεί κάθε επέκταση από το επίπεδο A (το πιο καθαρό) έως το επίπεδο D (τροποποιήσεις προς αφαίρεση). Το όφελος είναι ταχύτερες αναβαθμίσεις: έχω δει εταιρείες να μειώνουν τον χρόνο αναβάθμισης κατά 40% με αυτόν τον τρόπο.

Αν το σύστημά σας είναι γεμάτο τροποποιήσεις σε standard αντικείμενα της SAP, κάθε release γίνεται έργο regression. Αν η custom λογική σας βρίσκεται πίσω από released διεπαφές, οι αναβαθμίσεις γίνονται ρουτίνα συντήρησης.

Έχω δει εταιρείες να μειώνουν τον χρόνο αναβάθμισης κατά 40% εφαρμόζοντας τις αρχές του clean core. Το πέτυχαν κρατώντας τις προσαρμογές στο ελάχιστο και διακυβερνώντας όσες κράτησαν.

Το 2024 μια ευρωπαϊκή εταιρεία καταναλωτικών αγαθών αντικατέστησε την παλιά λογική τιμολόγησης με μια modular εφαρμογή Fiori, χτισμένη εκτός πυρήνα στο SAP BTP. Αυτό εξάλειψε εντελώς το regression testing για αυτή τη λογική.

## Τι σημαίνει το clean core για το ERP σας

Μπορείτε ακόμη να προσαρμόσετε ένα ERP με clean core. Η προσαρμογή πρέπει να χρησιμοποιεί διεπαφές που η SAP έχει κάνει released και έχει δεσμευτεί να κρατά σταθερές. Η SAP προσφέρει δύο τρόπους:

- **On-stack, με ABAP Cloud.** Οι επεκτάσεις τρέχουν μέσα στο S/4HANA, αλλά χρησιμοποιούν μόνο released API και σημεία επέκτασης.
- **Side-by-side, στο SAP BTP.** Οι επεκτάσεις τρέχουν ως ξεχωριστές εφαρμογές και επικοινωνούν με το S/4HANA μέσω API ή events.

Η SAP περιγράφει την προσέγγισή της ως BTP-first, με επιλογή ανά περίπτωση χρήσης. Από την εμπειρία μου, το πού τρέχει ο κώδικας μετράει λιγότερο από το αν η απαίτηση χρειάζεται κώδικα καθόλου.

Ένας «βρόμικος» πυρήνας είναι γνώριμος σε όποιον έτρεξε ECC: τροποποιημένα standard προγράμματα, Z-πίνακες στους οποίους γράφει κανείς απευθείας, διεπαφές που διαβάζουν τα εσωτερικά της SAP, implicit enhancements που δεν τεκμηρίωσε κανείς. Τίποτα από αυτά δεν ήταν λάθος όταν χτίστηκε. Απλώς δεν χτίστηκε για ένα σύστημα που αναβαθμίζεται κάθε ένα ή δύο χρόνια.

## Οι πέντε αρχές clean core της SAP

Η SAP οργανώνει το clean core γύρω από πέντε κατευθυντήριες αρχές. Έτσι περιγράφει η SAP την καθεμία, και αυτό εξετάζω εγώ πρώτα:

| Αρχή | Τι εννοεί η SAP | Τι ελέγχω πρώτα |
|---|---|---|
| Διαδικασίες | Όσο πιο κοντά γίνεται στη standard διαδικασία της SAP | Ποιες παραλλαγές διαδικασιών υπάρχουν μόνο επειδή «πάντα έτσι το κάναμε» |
| Επεκτασιμότητα | Επεκτάσεις αποσυνδεδεμένες από τον πυρήνα μέσω released API, με διακυβέρνηση για το ποια επιλογή χρησιμοποιείται | Πόσος custom κώδικας υπάρχει, πόσος χρησιμοποιείται και σε ποιο επίπεδο βρίσκεται |
| Δεδομένα | Καθαρά, συμμορφωμένα δεδομένα με καθιερωμένο μοντέλο διακυβέρνησης | Διπλά και ελλιπή κύρια δεδομένα, custom πεδία που κανείς δεν μπορεί να εξηγήσει |
| Ενοποιήσεις | Τυποποιημένες, ασφαλείς συνδέσεις σε υποστηριζόμενες τεχνολογίες | Point-to-point διεπαφές που διαβάζουν πίνακες απευθείας |
| Λειτουργία | Διακυβέρνηση, άνθρωποι, διαδικασίες και εργαλεία που κρατούν τις άλλες τέσσερις στη θέση τους | Ποιος εγκρίνει μια επέκταση και τι σταματά την επόμενη τροποποίηση |

Οι περισσότερες ομάδες ξεκινούν και τελειώνουν με την επεκτασιμότητα, επειδή μετριέται πιο εύκολα. Από την εμπειρία μου, οι διαδικασίες και τα δεδομένα προκαλούν περισσότερη καθυστέρηση. Ο custom κώδικας είναι συνήθως το σύμπτωμα και η διαδικασία πίσω του η αιτία.

## Επίπεδα clean core A έως D

Τον Αύγουστο του 2025 η SAP αντικατέστησε το προηγούμενο μοντέλο επεκτασιμότητας τριών βαθμίδων με το [clean core level concept](https://news.sap.com/2025/08/extend-sap-s4hana-cloud-right-way-clean-clear/). Κάθε επέκταση αξιολογείται με βάση το πώς χτίστηκε, πόσο αποσυνδεδεμένη είναι από τον πυρήνα και πόσο ασφαλώς επιβιώνει μιας αναβάθμισης. Αν διαβάσετε παλαιότερο υλικό της SAP που μιλά για βαθμίδες, αυτό είναι που το αντικατέστησε.

Το επίπεδο A χρησιμοποιεί μόνο δημόσια released διεπαφές με συμβόλαια σταθερότητας, χτισμένες με SAP Build, ABAP Cloud ή BTP. Το επίπεδο B προσθέτει τα κλασικά API της SAP. Το επίπεδο C αγγίζει εσωτερικά αντικείμενα της SAP, και η SAP σχεδιάζει ένα changelog για αυτά ώστε να βοηθά στον σχεδιασμό αναβαθμίσεων.

Το επίπεδο D είναι οι τροποποιήσεις, οι εγγραφές σε πίνακες της SAP, τα implicit enhancements και άλλες τεχνικές που η SAP δεν συνιστά. Αυτό είναι πιο χρήσιμο από την παλιά συζήτηση «καθαρό ή όχι», γιατί σας επιτρέπει να ορίσετε στόχο ανά αντικείμενο. Αν μεταφέρετε τα αντικείμενα επιπέδου D σε B ή C πριν από μια αναβάθμιση, έχετε ήδη πραγματική μείωση κινδύνου.

## ABAP Cloud και επεκτασιμότητα BTP για το S/4HANA Cloud

Το ABAP Cloud είναι το cloud-ready μοντέλο ανάπτυξης ABAP της SAP. Οι developers χρησιμοποιούν την έκδοση γλώσσας «ABAP for Cloud Development» και μπορούν να χτίζουν μόνο πάνω σε released αντικείμενα, δημόσια API και σημεία επέκτασης. Ξεκίνησε στο SAP BTP ABAP environment και σήμερα είναι διαθέσιμο σε κάθε έκδοση του S/4HANA ([SAP ABAP Cloud FAQ](https://pages.community.sap.com/topics/abap/abap-cloud-faq)).

Το S/4HANA Cloud σας δίνει τρεις δρόμους επέκτασης. Το key user extensibility καλύπτει απλές αλλαγές σε πεδία, λογική και UI χωρίς να αγγίζει κώδικα της SAP. Το developer extensibility με ABAP Cloud χειρίζεται στενά συνδεδεμένη λογική, και οι side-by-side επεκτάσεις στο SAP BTP χειρίζονται ό,τι πρέπει να μείνει αποσυνδεδεμένο.

Η έκδοση καθορίζει πόση επιλογή έχετε:

| | S/4HANA Cloud Public Edition | S/4HANA Cloud Private Edition και on-premise |
|---|---|---|
| Ανάπτυξη ABAP | Μόνο ABAP Cloud, υποχρεωτικό για νέους πελάτες από το release 2208 | Το ABAP Cloud συνιστάται από το 2022· το κλασικό ABAP επιτρέπεται ακόμη |
| Αλλαγές στον κώδικα της SAP | Δεν είναι δυνατές | Δυνατές, αλλά είναι επιπέδου D |
| Επεκτάσεις key user και side-by-side στο BTP | Διαθέσιμες | Διαθέσιμες |
| Ποιος επιβάλλει το clean core | Το σύστημα | Η δική σας διακυβέρνηση |

Ο κανόνας μου για πελάτες Private Edition: για οτιδήποτε νέο, φερθείτε σαν να ήταν Public Edition. Το κλασικό ABAP επιτρέπεται, αλλά κάθε κλασικό αντικείμενο που προσθέτετε σήμερα είναι μια απόφαση που κάποιος θα πρέπει να υπερασπιστεί στην επόμενη αναβάθμιση.

## Διακυβέρνηση clean core: ποιος παίρνει τις αποφάσεις

Οι αποφάσεις clean core πρέπει να ανήκουν σε μια design authority με εκπροσώπους της επιχείρησης και του IT. Το IT μόνο του θα εγκρίνει ό,τι είναι τεχνικά εφικτό. Η επιχείρηση μόνη της θα ζητήσει πίσω την παλιά της διαδικασία.

Έτσι θα το έστηνα εγώ:

1. **Ορίστε τα μέλη.** Τους business process owners για κάθε βασική περιοχή, μαζί με τον solution architect και τον lead developer. Οι business owners αποφασίζουν αν μια απαίτηση είναι πραγματική και το IT αποφασίζει πώς θα χτιστεί.
2. **Συμφωνήστε τη σειρά προτίμησης πριν ξεκινήσει το build.** Πρώτα η standard διαδικασία, μετά το key user extensibility, μετά το επίπεδο A σε ABAP Cloud ή BTP. Το επίπεδο B ή C χρειάζεται γραπτή αιτιολόγηση και το επίπεδο D χρειάζεται σχέδιο εξόδου.
3. **Κάθε αίτημα επέκτασης να έχει owner και επιχειρηματικό λόγο.** Χωρίς owner δεν χτίζεται τίποτα. Η απόφαση και το επίπεδο που έγινε αποδεκτό καταγράφονται σε ένα ενιαίο μητρώο.
4. **Βάλτε τεχνικό φίλτρο πριν από τα transports.** Τρέχετε τους ελέγχους clean core του ABAP test cockpit σε πρόγραμμα και σταματάτε κάθε νέο κώδικα επιπέδου D πριν φτάσει στην παραγωγή.
5. **Ελέγχετε το μητρώο πριν από κάθε αναβάθμιση.** Αποσύρετε ό,τι δεν χρησιμοποιεί πια κανείς και μεταφέρετε ό,τι μπορεί πλέον να φτάσει σε υψηλότερο επίπεδο.

Η ερώτηση σε εκείνο το τραπέζι ήταν παλιά «γιατί αυτό δεν μπορεί να ζει στο BTP;». Σήμερα θα ρωτούσα «γιατί αυτό δεν μπορεί να είναι επιπέδου A;». Αν δεν μπορεί, η επόμενη ερώτηση είναι ποιο επίπεδο αποδέχεστε και γιατί.

Το μεγαλύτερο λάθος clean core που βλέπω είναι η προσπάθεια να κάνετε το SAP να λειτουργεί σαν Oracle. Υιοθετήστε τις standard διαδικασίες της SAP αντί να ξαναχτίζετε σε custom κώδικα τη λογική ενός άλλου συστήματος. Αν ακόμη διαλέγετε ανάμεσα στα δύο, τα συγκρίνω στο [SAP vs Oracle](/el/sap-vs-oracle-which-erp-is-better-for-your-business/).

## Clean core και διαχείριση αλλαγών

Το clean core είναι πρόβλημα διαχείρισης αλλαγών πριν γίνει τεχνικό. Κάθε custom αντικείμενο υπάρχει επειδή κάποιος το ζήτησε. Για να το αφαιρέσετε, πρέπει να πείσετε αυτόν τον άνθρωπο ότι η standard διαδικασία είναι αρκετά καλή.

Αυτή η συζήτηση πάει καλύτερα όταν η επιχείρηση βλέπει τη νέα διαδικασία να λειτουργεί, όχι μια διαφάνεια γι' αυτήν. Πάει επίσης καλύτερα όταν ελέγχετε τον ισχυρισμό ότι μια διαδικασία είναι μοναδική, γιατί συχνά δεν είναι (δείτε τα βήματα 4 και 5 παρακάτω).

Οι δεξιότητες μετρούν όσο και τα εργαλεία. Μια ομάδα ABAP που δεν έχει δουλέψει με ABAP Cloud ή BTP θα καθυστερήσει το πρόγραμμα όσο μαθαίνει. Ένας κατασκευαστής με τον οποίο συνεργάστηκα έτρεξε ένα εσωτερικό πρόγραμμα BTP τριών μηνών πριν ξεκινήσει το έργο S/4HANA, και αυτό απέδωσε με λιγότερες εκπλήξεις στη φάση του build.

## Συμμόρφωση με το clean core: πώς τη μετράτε

Η συμμόρφωση με το clean core είναι το πόσο μέρος του συστήματός σας πληροί τα κριτήρια της SAP στις πέντε αρχές. Δεν μπορείτε να τη διαχειριστείτε χωρίς αριθμούς, και η SAP σας δίνει τρία σημεία για να τους πάρετε.

1. **Το ABAP test cockpit.** Το εργαλείο της SAP για ελέγχους σε επίπεδο κώδικα. Δείχνει ποια custom αντικείμενα χρησιμοποιούν μη released αντικείμενα, τροποποιήσεις ή άμεση πρόσβαση σε πίνακες.
2. **Το SAP Readiness Check.** Περιλαμβάνεται στη σύμβαση συντήρησης και δείχνει τι θα επηρεάσει μια μετάβαση σε S/4HANA πριν δεσμευτείτε.
3. **Το RISE with SAP Methodology dashboard, γνωστό και ως clean core dashboard.** Τρέχει στο [SAP Cloud ALM](https://support.sap.com/en/alm/sap-cloud-alm/sap-cloud-alm-clean-core-adoption.html). Η προβολή συστήματος ελέγχει την έκδοση του S/4HANA, επιβεβαιώνει ότι τα εργαλεία συλλογής δεδομένων είναι ενεργά και εξετάζει τις επεκτάσεις πριν από μια αναβάθμιση, ενώ η προβολή λειτουργίας παρακολουθεί λειτουργικά KPI.

Οι αριθμοί που θα έβαζα μπροστά στη design authority κάθε μήνα είναι απλοί. Πόσα custom αντικείμενα βρίσκονται σε κάθε επίπεδο, και πέφτει το επίπεδο D; Πόσες εξαιρέσεις είναι ανοιχτές, και έχει η καθεμία owner;

## Από πού θα ξεκινούσα

Αν μου ζητούσατε να αξιολογήσω το σύστημά σας τον επόμενο μήνα, αυτή είναι η σειρά που θα ακολουθούσα.

1. **Βρείτε τι χρησιμοποιείται.** Τρέξτε το SAP Readiness Check και συλλέξτε δεδομένα χρήσης για τον custom κώδικα. Σε ένα πρόγραμμα, η ανάλυση με το smartShift μάς πήγε από 18.000 custom αντικείμενα σε 3.200, γιατί τα περισσότερα από τα υπόλοιπα απλώς δεν χρησιμοποιούνταν.
2. **Κατατάξτε όσα μένουν στα επίπεδα A έως D.** Χρησιμοποιήστε το ABAP test cockpit για τον κώδικα. Αν είστε σε RISE, το clean core dashboard το παρακολουθεί από εκεί και πέρα.
3. **Αποφασίστε αντικείμενο προς αντικείμενο.** Αποσύρετέ το, μεταφέρετέ το σε released διεπαφή, ξαναχτίστε το στο BTP ή κρατήστε το με τεκμηριωμένο λόγο. Ξεκινήστε από τον κώδικα που τρέχει κάθε μέρα, γιατί μια αναφορά που χρησιμοποιεί δύο φορές τον χρόνο μια περιφερειακή ομάδα μπορεί να περιμένει.
4. **Φέρτε την επιχείρηση στο τραπέζι.** Ένας υπεύθυνος οικονομικών με τον οποίο συνεργάστηκα κατάλαβε τη νέα του εφαρμογή Fiori μόνο μετά από μια παρουσίαση 45 λεπτών. Εκείνη η συνάντηση γλίτωσε δύο εβδομάδες πήγαινε-έλα στο UAT.
5. **Αμφισβητήστε το «η δική μας διαδικασία είναι διαφορετική».** Σε ένα εργαστήριο με την ομάδα πωλήσεων μιας ευρωπαϊκής βιομηχανικής εταιρείας το 2023, η «μοναδική» διαδικασία αποδείχθηκε κατά 80% περιττή, παλιά διοικητική δουλειά. Το standard SAP βελτίωσε την εμπειρία των πελατών τους μόλις έφυγαν οι παρακαμπτήριες λύσεις.
6. **Ξεκινήστε νωρίς τη δουλειά στα δεδομένα.** Ένας πελάτης λιανικής στο GCC με τον οποίο συνεργάστηκα το 2024 είχε πάνω από 15.000 custom πεδία να ξεκαθαρίσει. Από την εμπειρία μου, η μετάπτωση δεδομένων παίρνει το 30 έως 40% της προσπάθειας υλοποίησης, και ο [οδηγός μου για το κόστος υλοποίησης SAP](/el/sap-implementation-cost-and-budget-breakdown/) δείχνει πού πέφτει αυτό στον προϋπολογισμό.
7. **Ορίστε τη διακυβέρνηση πριν από το go-live.** Στήστε τη design authority που περιέγραψα παραπάνω και κάντε τη τον μόνο δρόμο για κάθε νέα επέκταση.

## Clean core, RISE και AI: τι απαιτείται και τι όχι

Τρεις ερωτήσεις έρχονται σχεδόν σε κάθε συζήτηση που κάνω για το θέμα.

### Είναι το clean core υποχρεωτικό στο RISE with SAP;

Όχι ως γενικός κανόνας. Στην Public Edition το επιβάλλει το σύστημα, ενώ στην Private Edition και on-premise μπορείτε ακόμη να τροποποιήσετε τον πυρήνα.

Εκεί, το clean core είναι επιλογή διακυβέρνησης που η SAP παρακολουθεί μέσω του RISE methodology dashboard. Αν ένας SI σας πει ότι είναι συμβατική υποχρέωση, ζητήστε του να σας δείξει τον όρο.

### Πόσο χρόνο έχω ακόμη στο ECC;

Για το SAP ERP 6.0 με enhancement packages 6 έως 8, [το mainstream maintenance λήγει στις 31 Δεκεμβρίου 2027](https://news.sap.com/2020/02/sap-s4hana-maintenance-2040-clarity-choice-sap-business-suite-7/). Το προαιρετικό extended maintenance διαρκεί έως τις 31 Δεκεμβρίου 2030 με επιπλέον κόστος.

Μετά από αυτό, το [SAP ERP, private edition, transition option](https://news.sap.com/2025/08/rise-with-sap-journey-sap-erp-private-edition-transition-option-updates/) καλύπτει τα έτη 2031 έως 2033. Ισχύει μόνο για μεγάλα συστήματα που έχουν ήδη μεταφερθεί στο SAP ERP, private edition σε SAP HANA πριν από το τέλος του 2030.

Δείτε το 2033 ως δρόμο εξαίρεσης, όχι ως ημερομηνία σχεδιασμού. Ο [οδηγός μου για τη μετάβαση από ECC σε S/4HANA](/el/ecc-to-s4hana-migration/) καλύπτει τις επιλογές διαδρομής.

### Έχει σημασία το clean core για την AI;

Ναι. Όταν μένετε κοντά στο standard της SAP, η AI και το Joule λειτουργούν καλύτερα, και οι βαριά τροποποιημένες διαδικασίες είναι εκεί όπου υιοθετούνται πιο δύσκολα.

Η SAP χτίζει τις λειτουργίες AI της, μαζί και το Joule, πάνω στις standard διαδικασίες και στο μοντέλο δεδομένων της. Το Joule for developers παράγει κώδικα ABAP Cloud πάνω σε released API. Εξηγώ πώς δένουν cloud, AI και clean core στο [ERP modernisation](/el/erp-modernization-2025-cloud-ai-clean-core/).

Οι ομάδες που παρακάμπτουν το clean core δεν γλιτώνουν τη δουλειά. Την αναβάλλουν, και επιστρέφει ως μπλοκαρισμένες αναβαθμίσεις, μαραθώνιοι regression testing και custom κώδικας που κανείς δεν καταλαβαίνει.

Πριν υπογράψετε σύμβαση S/4HANA ή RISE, ζητήστε από τον SI σας να κατατάξει τον τρέχοντα custom κώδικα στα επίπεδα A έως D. Αν δεν μπορεί να το κάνει, αυτό κάτι σας λέει για την εκτίμησή του. [Κλείστε μια συνάντηση](/el/contact-noel-erp-support/) και μπορούμε να δούμε τη δική σας περίπτωση.

## Συχνές ερωτήσεις

<details>
<summary>Τι είναι το clean core στο SAP;</summary>

Clean core σημαίνει ότι κρατάτε το S/4HANA κοντά στο standard της SAP και χτίζετε επεκτάσεις μόνο μέσω διεπαφών που η SAP έχει κάνει released και έχει δεσμευτεί να κρατά σταθερές. Οι επεκτάσεις τρέχουν είτε on-stack με ABAP Cloud είτε side-by-side στο SAP BTP. Ο στόχος είναι οι αναβαθμίσεις να μη σπάνε την custom λογική σας.

</details>

<details>
<summary>Ποιες είναι οι πέντε αρχές του SAP clean core;</summary>

Οι πέντε κατευθυντήριες αρχές clean core της SAP είναι οι διαδικασίες, η επεκτασιμότητα, τα δεδομένα, οι ενοποιήσεις και η λειτουργία. Οι διαδικασίες μένουν κοντά στο standard, οι επεκτάσεις χρησιμοποιούν released API και τα δεδομένα μένουν καθαρά μέσα σε ένα μοντέλο διακυβέρνησης. Οι ενοποιήσεις χρησιμοποιούν υποστηριζόμενες τεχνολογίες, και η λειτουργία καλύπτει τη διακυβέρνηση, τους ανθρώπους και τα εργαλεία που κρατούν τις άλλες τέσσερις στη θέση τους.

</details>

<details>
<summary>Τι είναι τα επίπεδα clean core A, B, C και D της SAP;</summary>

Από τον Αύγουστο του 2025 η SAP κατατάσσει τις επεκτάσεις σε τέσσερα επίπεδα. Το επίπεδο A χρησιμοποιεί μόνο δημόσια released, σταθερές διεπαφές, το επίπεδο B χρησιμοποιεί επίσης κλασικά API της SAP και το επίπεδο C έχει πρόσβαση σε εσωτερικά αντικείμενα της SAP. Το επίπεδο D καλύπτει τροποποιήσεις, εγγραφές σε πίνακες της SAP και implicit enhancements, και έχει τον υψηλότερο κίνδυνο στις αναβαθμίσεις.

</details>

<details>
<summary>Είναι το clean core υποχρεωτικό για το RISE with SAP;</summary>

Όχι ως γενικός κανόνας. Το S/4HANA Cloud Public Edition επιτρέπει μόνο ABAP Cloud και released διεπαφές, άρα επιβάλλει τεχνικά το clean core. Στην Private Edition μπορείτε ακόμη να τροποποιήσετε τον πυρήνα, οπότε το clean core είναι απόφαση διακυβέρνησης που η SAP παρακολουθεί μέσω του RISE with SAP Methodology dashboard.

</details>

<details>
<summary>Τι είναι το ABAP Cloud;</summary>

Το ABAP Cloud είναι το cloud-ready μοντέλο ανάπτυξης ABAP της SAP. Επιτρέπει μόνο released αντικείμενα, δημόσια API και σημεία επέκτασης, κάτι που κρατά τον custom κώδικα σταθερό στις αναβαθμίσεις. Είναι υποχρεωτικό στο S/4HANA Cloud Public Edition για νέους πελάτες από το release 2208 και συνιστάται στην Private Edition και on-premise από το 2022.

</details>

<details>
<summary>Πώς μετράτε το clean core;</summary>

Χρησιμοποιήστε το ABAP test cockpit για ελέγχους σε επίπεδο κώδικα και κατατάξτε τα custom αντικείμενα στα επίπεδα A έως D. Οι πελάτες RISE μπορούν να παρακολουθούν την υιοθέτηση στο RISE with SAP Methodology dashboard, που λέγεται και clean core dashboard, στο SAP Cloud ALM. Εγώ παρακολουθώ τον αριθμό αντικειμένων σε κάθε επίπεδο, την τάση του επιπέδου D και τον αριθμό των ανοιχτών εξαιρέσεων με owner.

</details>

<details>
<summary>Ποιος πρέπει να έχει τη διακυβέρνηση του SAP clean core;</summary>

Κάθε απόφαση clean core πρέπει να ανήκει σε μια design authority με εκπροσώπους της επιχείρησης και του IT. Οι business process owners αποφασίζουν αν μια απαίτηση είναι πραγματική, και το IT αποφασίζει πώς θα χτιστεί και σε ποιο επίπεδο. Κάθε εξαίρεση καταγράφεται με owner και επανεξετάζεται πριν από κάθε αναβάθμιση.

</details>

<details>
<summary>Πότε λήγει η υποστήριξη του SAP ECC;</summary>

Για το SAP ERP 6.0 με enhancement packages 6 έως 8, το mainstream maintenance λήγει στις 31 Δεκεμβρίου 2027, με προαιρετικό extended maintenance έως τις 31 Δεκεμβρίου 2030 με επιπλέον κόστος. Το SAP ERP, private edition, transition option διαρκεί έως το 2033 μόνο για επιλέξιμα μεγάλα συστήματα που έχουν μεταφερθεί στο SAP ERP, private edition σε SAP HANA πριν από το τέλος του 2030.

</details>

Το clean-core δεν είναι μια έννοια marketing της SAP. Είναι η διαφορά ανάμεσα σε ένα upgrade που παίρνει έξι εβδομάδες και σε ένα που παίρνει έξι μήνες. Στο πλαίσιο του RISE with SAP και του GROW with SAP το 2026, είναι επίσης συμβατική υποχρέωση και όχι απλώς σχεδιαστική προτίμηση.

Σε 21 προγράμματα SAP S/4HANA έχω δει εταιρείες να μειώνουν τα χρονοδιαγράμματα upgrade κατά 40% εφαρμόζοντας αρχές clean-core πριν καν ξεκινήσουν τα προγράμματα S/4HANA. Μια ευρωπαϊκή εταιρεία καταναλωτικών αγαθών το 2024 αντικατέστησε legacy λογική τιμολόγησης με ένα modular app Fiori χτισμένο εκτός core στο SAP BTP και εξάλειψε πλήρως το regression testing από τον κύκλο upgrade της. Αυτό δεν είναι θεωρία. Έτσι μοιάζει όταν η προσέγγιση εφαρμόζεται νωρίς.

Οι ομάδες που παραλείπουν το clean-core δεν αποφεύγουν τη δουλειά. Την αναβάλλουν. Η αναβλημένη δουλειά clean-core εμφανίζεται ως μπλοκαρισμένα upgrades, μαραθώνιοι regression testing, custom code που κανείς δεν καταλαβαίνει πια και εμπόδια στην ενσωμάτωση του Joule όταν η SAP κυκλοφορεί λειτουργίες AI που επικαλύπτουν το δικό σας custom build.

## Τι σημαίνει στην πράξη το clean-core

Μια στρατηγική clean-core στην SAP αφορά τη διατήρηση του digital core του S/4HANA λιτού. Χωρίς θαμμένο custom code. Χωρίς hardwired integrations που σπάνε όταν η SAP ενημερώνει ένα standard object. Χωρίς Z-programs που μπαλώνουν κενά τα οποία η standard διαδικασία θα κάλυπτε, αν η επιχείρηση ήταν διατεθειμένη να προσαρμοστεί.

Αντί γι' αυτό, τα customisations και τα extensions υλοποιούνται side-by-side στο SAP BTP (το Business Technology Platform). Η λογική που παλιότερα βρισκόταν μέσα στο core μεταφέρεται έξω από αυτό. Το σύστημα ERP παραμένει ευθυγραμμισμένο με το standard upgrade path της SAP.

Ο πρακτικός λόγος που αυτό έχει σημασία: ο κύκλος releases της SAP στο πλαίσιο του RISE with SAP είναι ταχύτερος απ' ό,τι ήταν στο ECC. Τριμηνιαία updates, συνεχείς καινοτομίες, νέα features καθ' όλη τη διάρκεια του έτους. Ένα heavily modified core system σημαίνει ότι κάθε update είναι ρίσκο regression. Ένα clean-core σημαίνει ότι τα updates περνούν χωρίς να σπάνε την custom logic, επειδή η custom logic είναι αποσυνδεδεμένη.

**Clean-core vs dirty core:**

- **Dirty core:** Custom ABAP που τροποποιεί standard objects της SAP, hardwired integrations που παρακάμπτουν APIs, business logic ενσωματωμένη μέσα στο core που σπάει όταν η SAP αλλάζει την υποκείμενη λειτουργικότητα.
- **Clean-core:** Extensions υλοποιημένα με μεθόδους εγκεκριμένες από τη SAP (BTP, ABAP Cloud, in-app extensibility tools). Η standard συμπεριφορά της SAP διατηρείται. Τα upgrades είναι προβλέψιμα.

Clean δεν σημαίνει χωρίς customisations. Σημαίνει ότι τα customisations υλοποιούνται με τρόπο που δεν σπάει όταν η SAP κυκλοφορεί νέα έκδοση.

## Οι πέντε διαστάσεις του clean-core στην SAP

Η SAP οργανώνει την προσέγγιση clean-core γύρω από πέντε διαστάσεις, και καθεμία είναι ένας μοχλός για τη μείωση της σύζευξης ανάμεσα στην custom logic και το ERP core.

| Διάσταση | Τι σημαίνει στην πράξη |
|---|---|
| Extensibility | Υλοποίηση custom features χωρίς αλλαγή του core code: χρήση BTP ή in-app tools αντί για τροποποίηση standard objects της SAP |
| Integration | Σύνδεση συστημάτων μέσω standard APIs, όχι hardwired point-to-point integrations χτισμένων μέσα στο core |
| Configuration | Χρήση των in-app ρυθμίσεων της SAP και του customising client για την κάλυψη επιχειρησιακών απαιτήσεων πριν καταφύγετε σε code |
| Infrastructure & Operations | Διατήρηση των environments σταθερών και συνεπών· διακυβέρνηση του ποιος μπορεί να εφαρμόζει τροποποιήσεις και με ποιον μηχανισμό |
| Modifications | Ελαχιστοποίηση ή εξάλειψη άμεσων αλλαγών σε core objects της SAP· όπου υπάρχουν modifications, ρητή παρακολούθηση και διαχείρισή τους |

Αυτές οι πέντε διαστάσεις περιγράφουν πού βρίσκεται η τρέχουσα υλοποίησή σας σε σχέση με μια κατάσταση clean-core. Είναι επίσης οι πέντε περιοχές που πρέπει να εξετάζει ένα clean-core assessment.

## Το SAP BTP ως layer extensibility

Το SAP BTP είναι το σημείο όπου ζουν τα clean-core extensions. Αντί να γράφετε custom ABAP μέσα στο S/4HANA, χτίζετε apps και services στο BTP που αλληλεπιδρούν με το S/4HANA μέσω standard APIs.

Το ABAP Cloud είναι η cloud-ready εκδοχή της ABAP από τη SAP: επιβάλλει clean-core by design. Περιορίζει τι μπορείτε να αγγίξετε και απαιτεί τη χρήση εγκεκριμένων APIs. Σκεφτείτε το ως ABAP με προστατευτικά όρια. Τρέχει στο SAP BTP ABAP Environment και στο S/4HANA Cloud, και έτσι πρέπει να γράφεται η custom ABAP logic σε ένα clean-core πλαίσιο.

Οι δύο τύποι extensibility:
- **In-app extensibility:** Custom fields, forms ή αλλαγές σε workflow που γίνονται μέσω εργαλείων που παρέχει η SAP μέσα στο S/4HANA. Χωρίς τροποποίηση του core.
- **Side-by-side extensibility:** Πλήρη apps ή services χτισμένα στο BTP που συνδέονται με το S/4HANA μέσω APIs. Η λογική ζει εξ ολοκλήρου έξω από το core.

Και οι δύο είναι συμβατοί με clean-core. Η διάκριση έχει σημασία για την πολυπλοκότητα και τη διακυβέρνηση, όχι για την αρχή.

## Συνηθισμένα λάθη σε έργα clean-core

### Υπερβολικός Z-code και μηδενική ορατότητα

Μια βαριά βάση custom code παραμένει το μεγαλύτερο εμπόδιο. Κάθε enhancement exit, κάθε Z-report, κάθε modification σε standard object κουβαλά ρίσκο upgrade. Οι περισσότερες ομάδες δεν ξέρουν τι χρησιμοποιείται πραγματικά.

Σε ένα έργο, εργαλεία αυτοματοποιημένης ανάλυσης κώδικα μείωσαν τον αριθμό αντικειμένων από 18,000 σε 3,200. Η ομάδα δεν χρειάστηκε να ελέγξει χειροκίνητα κάθε object. Τα εργαλεία εντόπισαν αχρησιμοποίητο code και διαχώρισαν την business-critical logic από τον θόρυβο. Το σωστό sequence είναι να ξεκινήσετε από τον κώδικα που τρέχει κάθε μέρα· μην ξοδεύετε κύκλους καθαρίζοντας ένα report που χρησιμοποιείται δύο φορές τον χρόνο από μία περιφερειακή ομάδα.

### Καμία συμμετοχή της επιχείρησης

Το clean-core δεν είναι μόνο τεχνική άσκηση. Χωρίς input από την επιχείρηση, καθαρίζετε κώδικα μόνο και μόνο για να ανακαλύψετε ότι η διαδικασία πίσω από αυτόν δεν βγάζει πλέον νόημα.

Ένας επικεφαλής finance με τον οποίο συνεργάστηκα κατάλαβε το νέο του app Fiori μόνο μετά από ένα walkthrough session 45 λεπτών. Αυτή η συνεδρία απέτρεψε δύο εβδομάδες από μπρος-πίσω αλλαγές κατά το UAT. Όταν περιμένετε μέχρι το testing για να εμπλέξετε business users, εκεί αρχίζει το rework.

### Καμία διακυβέρνηση

Χωρίς κανόνες για το τι μπορεί και τι δεν μπορεί να μπει μέσα στο core, το technical debt επιστρέφει σταδιακά. Οι ομάδες πέφτουν σε γνώριμες συνήθειες. Έναν χρόνο μετά από ένα έργο clean-core, το σύστημα μοιάζει με το αρχικό περιβάλλον ECC: απλώς πάνω σε νεότερη υποδομή.

Από την πρώτη μέρα, μια design authority πρέπει να εξετάζει κάθε extension, enhancement ή workaround. Η προεπιλεγμένη ερώτηση πρέπει να είναι: γιατί αυτό δεν μπορεί να ζήσει στο BTP;

### Αντίσταση στην τυποποίηση διαδικασιών

Αυτό είναι το πιο δύσκολο κομμάτι σε κάθε έργο clean-core. Η ένσταση είναι σχεδόν πάντα κάποια εκδοχή του "η διαδικασία μας είναι διαφορετική" ή "το standard SAP δεν θα δουλέψει για εμάς".

Σε ένα workshop με ομάδα πωλήσεων, η "μοναδική" διαδικασία αποδείχθηκε ότι ήταν κατά 80% περιττό legacy admin: χειροκίνητα βήματα και φόρμες που είχαν συσσωρευτεί με τα χρόνια. Το standard SAP στην πραγματικότητα βελτίωσε την εμπειρία πελάτη όταν η ομάδα άφησε τα workarounds. Μια global εταιρεία διαπίστωσε ότι το 80% της επεξεργασίας παραγγελιών της μπορούσε να τυποποιηθεί. Το υπόλοιπο 20% επεκτάθηκε καθαρά στο BTP.

Η ερώτηση που αξίζει να τίθεται κάθε φορά: είναι αυτό πραγματικά επιχειρησιακός διαφοροποιητής ή απλώς κάτι οικείο;

### Πολυπλοκότητα data migration

Custom fields, legacy δομές δεδομένων, ασυνεπή formats από δεκαετίες λειτουργίας του ECC. Ένας πελάτης λιανικής είχε πάνω από 15,000 custom fields να επιλύσει.

Το data migration συνήθως καταναλώνει το 30–40% του συνολικού χρονοδιαγράμματος υλοποίησης. Οι περισσότερες ομάδες το υποτιμούν. Η δουλειά περιλαμβάνει αποφάσεις για το ποια δεδομένα θα κρατήσετε, καθαρισμό διπλοεγγραφών, επικύρωση business logic που συνδέεται με custom fields και χαρτογράφηση των πάντων στο απλοποιημένο μοντέλο που επιτρέπει το clean-core.

Ξεκινήστε νωρίς. Εμπλέξτε functional και technical ομάδες από το πρώτο sprint.

### Κενά γνώσης

Η ABAP δεν αρκεί. Το clean-core extensibility απαιτεί ευχέρεια στο BTP, σχεδιασμό API, modular τρόπο σκέψης και κατανόηση της side-by-side αρχιτεκτονικής. Μια ομάδα δυνατή στην ABAP που δεν έχει δουλέψει με BTP θα δημιουργήσει bottlenecks, όχι επειδή δεν μπορεί να μάθει, αλλά επειδή η μάθηση θέλει χρόνο.

Ένας κατασκευαστής έτρεξε ένα εσωτερικό πρόγραμμα εκπαίδευσης BTP διάρκειας τριών μηνών πριν ξεκινήσει το έργο S/4HANA. Απέδωσε με πιο ομαλό deployment και λιγότερες εκπλήξεις στις integrations.

<summary>Ποιες είναι οι πέντε διαστάσεις του clean-core της SAP;</summary>

Η SAP οργανώνει το clean-core γύρω από πέντε διαστάσεις: Extensibility, Integration, Configuration, Infrastructure and Operations και Modifications.

Το Extensibility καλύπτει το πώς υλοποιούνται τα custom features: ιδανικά μέσω BTP ή in-app tools, όχι με άμεσες modifications στο core. Το Integration καλύπτει το πώς συνδέονται τα συστήματα: μέσω standard APIs, όχι μέσω hardwired integrations μέσα στο core. Το Configuration καλύπτει τη χρήση των in-app ρυθμίσεων της SAP για την κάλυψη επιχειρησιακών απαιτήσεων πριν καταφύγετε σε code. Το Infrastructure and Operations καλύπτει τη σταθερότητα του environment και τη διακυβέρνηση των modifications. Το Modifications καλύπτει τη διαχείριση και τη μείωση των άμεσων αλλαγών σε core objects της SAP.

Ένα clean-core assessment εξετάζει και τις πέντε. Το αποτέλεσμα δείχνει πού βρίσκεται σήμερα το σύστημα και τι πρέπει να αλλάξει πριν από ένα migration ή upgrade σε S/4HANA.

</details>

<details>
<summary>Ποιος είναι ο ρόλος του SAP BTP σε μια στρατηγική clean-core;</summary>

Το SAP BTP είναι το layer extensibility όπου ζει η custom logic του clean-core. Αντί να τροποποιείτε το S/4HANA, χτίζετε apps και services στο BTP που αλληλεπιδρούν με το ERP μέσω standard APIs. Το core παραμένει ανέγγιχτο. Τα upgrades περνούν χωρίς να σπάνε την custom logic.

Το in-app extensibility (custom fields, modifications σε workflow μέσω εργαλείων που παρέχει η SAP) κρατά το core καθαρό ενώ επιτρέπει αλλαγές μέσα στο S/4HANA. Το side-by-side extensibility (apps ή services στο BTP που συνδέονται μέσω APIs) μεταφέρει τη λογική εξ ολοκλήρου έξω από το core για πιο σύνθετα σενάρια.

Το ABAP Cloud είναι η συμβατή με clean-core εκδοχή της ABAP για cloud environments. Επιβάλλει τα πρότυπα clean-core περιορίζοντας το τι μπορεί να αλλάξει και απαιτώντας τη χρήση εγκεκριμένων APIs.

</details>

<details>
<summary>Πώς αξιολογώ την ετοιμότητα του τρέχοντος συστήματός μου SAP για clean-core;</summary>

Ένα clean-core assessment καλύπτει τέσσερις βασικές περιοχές: custom code (πού υπάρχει, ποια objects αγγίζει, αν εξακολουθεί να χρησιμοποιείται ενεργά), system modifications (οποιεσδήποτε αλλαγές σε standard objects της SAP), integrations (point-to-point συνδέσεις που θα έπρεπε να βασίζονται σε APIs) και προσέγγιση extensibility (πώς είναι δομημένη η τρέχουσα custom logic σε σχέση με τα πρότυπα clean-core).

Το αποτέλεσμα είναι συνήθως ένα roadmap: ποιο custom code να διατηρηθεί και να μεταφερθεί στο BTP, ποιο να αποσυρθεί, ποιες integrations να ξαναχτιστούν με standard APIs και ποιες δομές διακυβέρνησης πρέπει να υπάρχουν πριν ξεκινήσει το έργο.

Τα αυτοματοποιημένα εργαλεία για code scanning μειώνουν σημαντικά τη χειροκίνητη προσπάθεια. Σε ένα έργο, ένα code scan εντόπισε 18,000 objects, τα περισσότερα από τα οποία ήταν αχρησιμοποίητα. Η ενεργή αποκατάσταση μείωσε τον αριθμό σε 3,200 πριν ξεκινήσει το πρόγραμμα S/4HANA.

</details>

<details>
<summary>Τι είναι το "dirty core" και πώς δημιουργεί προβλήματα;</summary>

Ένα dirty core είναι ένα σύστημα SAP με custom code που τροποποιεί standard objects, hardwired integrations που παρακάμπτουν standard APIs και business logic ενσωματωμένη μέσα στο ERP που συγκρούεται με το standard upgrade path της SAP.

Τα προβλήματα συσσωρεύονται με τον χρόνο. Κάθε upgrade απαιτεί testing σε όλα τα modified objects. Όταν η SAP αλλάζει μια standard λειτουργία, το custom code που έχει χτιστεί πάνω της σπάει. Το εύρος του regression testing μεγαλώνει με κάθε release. Οι ομάδες σταματούν να κάνουν upgrades επειδή το κόστος είναι πολύ υψηλό, πράγμα που σημαίνει ότι μένουν πίσω σε security patches, νέα features και υποστηριζόμενη λειτουργικότητα.

Το dirty core δεν είναι αποτέλεσμα κακών αποφάσεων· είναι αποτέλεσμα πρακτικών ανάπτυξης της εποχής ECC που εφαρμόζονται σε ένα σύστημα το οποίο πλέον τρέχει σε ταχύτερο κύκλο upgrades. Το clean-core είναι η αρχιτεκτονική απάντηση σε αυτή τη μετατόπιση.

</details>

<details>
<summary>Ποια είναι τα πιο συνηθισμένα λάθη υλοποίησης clean-core;</summary>

Έξι εμφανίζονται σταθερά.

Πρώτο: μεταφορά Z-code στο έργο χωρίς να ξέρετε τι εξακολουθεί να χρησιμοποιείται. Οι περισσότερες ομάδες υποθέτουν ότι περισσότερα από τα customisations τους είναι business-critical απ' ό,τι πραγματικά είναι. Το αυτοματοποιημένο code scanning συνήθως αποκαλύπτει σημαντικό όγκο αχρησιμοποίητων objects.

Δεύτερο: αντιμετώπιση του clean-core ως καθαρά τεχνικού έργου. Χωρίς συμμετοχή της επιχείρησης από την αρχή, καθαρίζετε κώδικα που στηρίζει διαδικασίες οι οποίες δεν εξυπηρετούν πλέον την επιχείρηση. Ένα process walkthrough 45 λεπτών πριν από το UAT μπορεί να γλιτώσει δύο εβδομάδες rework.

Τρίτο: απουσία μοντέλου διακυβέρνησης. Χωρίς design authority που να εξετάζει κάθε extension και enhancement, το technical debt επιστρέφει σταδιακά. Το έργο clean-core αναπαράγει την ακαταστασία του ECC πάνω σε νεότερη υποδομή.

Τέταρτο: αποδοχή του "η διαδικασία μας είναι διαφορετική" ως λόγου για customisation, ενώ στην πράξη τις περισσότερες φορές η διαδικασία είναι οικεία και όχι πραγματικά διαφοροποιημένη. Η "μοναδική" ροή μιας ομάδας πωλήσεων αποδείχθηκε ότι ήταν κατά 80% περιττό legacy admin.

Πέμπτο: υποτίμηση του data migration. Custom fields, legacy δομές και ασυνεπή formats καταναλώνουν συνήθως το 30–40% του συνολικού χρόνου υλοποίησης.

Έκτο: μη ανάπτυξη δεξιοτήτων BTP πριν ξεκινήσει το έργο. Μια ομάδα δυνατή στην ABAP αλλά χωρίς ευχέρεια στο BTP δημιουργεί bottlenecks στη μέση του έργου που κοστίζουν ακριβά για να λυθούν.

</details>

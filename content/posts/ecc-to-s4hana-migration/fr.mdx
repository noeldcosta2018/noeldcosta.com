SAP ECC sort du support standard en décembre 2027, soit dans un an. Le support étendu standard court jusqu’en 2030, avec des options payantes supplémentaires jusqu’en 2033, mais à un coût plus élevé et avec des limites en matière d’innovation. La plupart des migrations complexes, une fois les vrais tests lancés, durent 18 à 24 mois. RISE with SAP est le choix par défaut le plus pragmatique pour de nouveaux engagements.

Voilà la pression réelle. Beaucoup d’équipes attendent encore un signal plus clair pour démarrer. Le voici.

La partie la plus difficile, c’est que le passage de ECC à S/4HANA n’est pas une simple montée de version. Cela change la façon dont les données sont structurées, dont le système traite les transactions, et dont les utilisateurs interagissent avec l’ensemble. Les équipes qui le traitent comme un simple rafraîchissement technique reconstruisent souvent leurs anciens processus sur une plateforme conçue pour faire mieux.

Sur un projet, une équipe a passé des mois à reconstruire des dizaines de rapports spécifiques exactement tels qu’ils existaient dans ECC. Sans jamais se demander s’ils étaient encore nécessaires. Plus tard, la moitié n’a jamais été utilisée. La migration était propre sur le plan technique. La valeur, non.

## Ce qui change réellement entre ECC et S/4HANA

| Domaine | SAP ECC | SAP S/4HANA |
|---|---|---|
| Base de données | Toute base (Oracle, DB2, SQL Server, etc.) | SAP HANA uniquement |
| Modèle de données | Plusieurs tables d’agrégats par transaction | Universal Journal (ACDOCA) : source unique, sans agrégats |
| Interface utilisateur | SAP GUI | SAP Fiori (basé sur les rôles, compatible mobile) |
| Déploiement | Standard on-premise | On-premise, cloud privé ou RISE with SAP (cloud public) |
| Performance | Reporting fortement basé sur des traitements batch | Analytique en temps réel intégrée aux transactions |
| Personnalisation | Programmes Z attendus | Clean core : les extensions passent par BTP, pas par le core |
| Calendrier de support | Support standard jusqu’en 2027, étendu jusqu’en 2033 | Feuille de route long terme, innovation continue |

Un client industriel européen a constaté en 2023 que ses traitements batch spécifiques ne fonctionnaient plus après la conversion. Toute la logique reposait sur l’ancienne structure de tables de ECC : des tables qui n’existent plus dans S/4HANA. La migration était techniquement terminée. Personne ne s’était demandé si ces traitements avaient encore du sens dans le nouveau modèle.

C’est la distinction importante : la migration déplace les données. La vraie question stratégique, c’est ce que vous faites des choix de conception dont vous héritez.

## Trois trajectoires de migration

<decision-tree question="Quel parcours de migration correspond à votre situation ?" options="Le legacy est fragmenté et vous voulez repenser les processus => Greenfield|Les processus sont solides, ECC est stable, l’historique doit être conservé => Brownfield|Environnement multi-entités, réutilisation partielle souhaitée et données sélectionnées => Bluefield"></decision-tree>

### Greenfield : repartir de zéro

Construire à partir de zéro sur S/4HANA. Aucune configuration historique n’est reprise. Les processus sont redessinés selon les bonnes pratiques SAP.

**À utiliser quand :** les systèmes historiques sont trop fragmentés pour être convertis proprement, ou quand l’entreprise veut repenser ses processus au lieu de les répliquer.

**Point de vigilance :** davantage de gestion du changement est nécessaire. Les utilisateurs perdent leurs workflows familiers. Si la planification de l’adoption commence au moment de la formation, il est déjà trop tard.

### Brownfield : conversion du système

Convertir votre environnement ECC existant vers S/4HANA. La configuration, le code spécifique et les données historiques vous suivent.

**À utiliser quand :** les processus sont matures et bien documentés, la conservation de l’historique transactionnel compte pour la conformité, et qu’aucune restructuration majeure n’est en cours.

**Point de vigilance :** vous emportez votre dette technique avec vous. La complexité historique se déplace aussi, sauf si vous la réduisez délibérément pendant la conversion.

### Transition sélective des données (Bluefield)

Migrer des codes société, des business units ou des plages de données spécifiques, pas l’ensemble. Utile quand l’entreprise est le produit de fusions ou de carve-out, ou quand des années de données historiques n’ont plus de pertinence pour les opérations actuelles.

**À utiliser quand :** vous voulez la flexibilité processus d’un Greenfield, mais la continuité des données d’un Brownfield pour les périmètres qui comptent.

| Critères | Greenfield | Brownfield | Sélectif |
|---|---|---|---|
| Refonte des processus | Refonte complète selon le standard SAP | Largement préservés | Sélectionnable par entité |
| Données historiques | Non reprises | Entièrement reprises | Reprise sélective |
| Délai jusqu’au go-live | Plus long | Plus court | Variable selon le périmètre |
| Dette technique | Éliminée | Reprise | Réduite sur le périmètre migré |
| Impact du changement | Élevé | Plus faible | Modéré |
| Idéal pour | Legacy fragmenté, transformation majeure | ECC stable et bien maintenu | Post-fusion, carve-out, déploiement par phases |

## Cinq étapes qui définissent le vrai travail

### 1. Évaluation et préparation

Commencez ici. Toujours. Exécutez le SAP Readiness Check : il analyse votre système ECC et produit un état des lieux des volumes de code spécifique, des dépendances aux add-ons, de la conformité Unicode, du dimensionnement des données et des simplification items.

Les surprises viennent généralement des add-ons. Les équipes découvrent des dépendances à des composants qui ne sont pas supportés dans S/4HANA, ou des volumes de code spécifique trois fois supérieurs à ce qu’elles avaient estimé. Mieux vaut le découvrir en semaine deux qu’au mois douze.

En parallèle du Readiness Check : faites l’inventaire de vos développements spécifiques, interfaces et connexions tierces. Identifiez ce qui apporte de la valeur, ce qui est obsolète, et ce que plus personne ne sait expliquer.

### 2. Analyse et classification des données

Évaluez votre volume de données avant de le déplacer. Segmentez-le :

1. **Hot.** Utilisé fréquemment, nécessaire au traitement en production.
2. **Warm.** Accès occasionnel, pertinent mais pas au quotidien.
3. **Cold.** Historique ou inutilisé, conservé uniquement pour l’audit ou la sauvegarde.

Les données cold n’ont pas besoin d’aller dans S/4HANA. Les équipes qui sautent cette étape apportent du désordre dans le nouveau système, ce qui affecte les performances et les délais de migration.

### 3. Nettoyage et archivage des données

Cette étape prend plus de temps que tous les plans ne le prévoient. Doublons dans les fiches fournisseurs. Unités de mesure incohérentes. Données de base clients incomplètes. Ces problèmes existent dans tous les systèmes ECC et se transfèrent très bien vers S/4HANA si vous ne les traitez pas d’abord.

SAP MDG et Information Steward prennent en charge cette phase. Archivez les données cold. Nettoyez le reste avant la migration, pas après.

Les équipes qui sautent le nettoyage découvrent les problèmes pendant le cutover, quand il n’y a plus le temps de les corriger correctement.

### 4. Adaptation du code spécifique

Exécutez ATC (ABAP Test Cockpit) pour détecter les incompatibilités. Croisez ensuite avec le Simplification Item Catalog de SAP. Le résultat vous indique ce qui nécessite des corrections de syntaxe, ce qui demande un remplacement fonctionnel, et ce qui doit être retiré.

Cette phase est itérative. Revue, test, affinage. L’objectif est de réduire le code Z, pas seulement de le corriger. Reprendre du code spécifique dans S/4HANA prolonge les coûts de maintenance et complique chaque future montée de version.

### 5. Tests, formation et cutover

Les tests doivent se dérouler en plusieurs cycles : tests unitaires, tests d’intégration, UAT, et au moins une répétition complète du cutover. Incluez à la fois les utilisateurs experts et les utilisateurs occasionnels dans l’UAT. Ils trouvent des problèmes différents.

La répétition du cutover n’est pas optionnelle. Elle révèle des écarts de timing, des validations manquantes et des échecs d’intégration qui n’apparaissent que lorsque la séquence complète s’exécute de bout en bout. Les équipes qui la sautent découvrent ces problèmes le week-end du go-live.

## Outils utiles

| Outil | Ce qu’il fait | Quand l’utiliser |
|---|---|---|
| SAP Readiness Check | Analyse ECC pour la compatibilité, les add-ons, le code spécifique, le dimensionnement | Avant de choisir l’approche de migration |
| SAP Transformation Navigator | Fait la correspondance entre les composants historiques et leurs équivalents S/4HANA ; suggère des extensions cloud | Phase de stratégie et de cadrage |
| ABAP Test Cockpit (ATC) + Simplification Item Check | Identifie le code spécifique incompatible | Phase d’adaptation du code spécifique |
| SAP Signavio | Cartographie des processus : comment les choses fonctionnent réellement, pas comment elles ont été documentées | Avant le gel du design |
| LeanIX | Cartographie du paysage applicatif : quels systèmes sont connectés à quoi | Phase de conception des intégrations |
| SAP Migration Cockpit | Déplace les données de base et transactionnelles vers S/4HANA | Phase de migration des données |

Le Readiness Check est le point de départ de la plupart des équipes. Tout le reste dépend de ce qu’il met en évidence.

## Calendriers et échéance 2027

La maintenance standard de SAP ECC prend fin le 31 décembre 2027. Le support étendu est disponible jusqu’en 2033, mais avec une prime tarifaire et un accès limité aux nouvelles capacités.

Les migrations complexes en entreprise (multi-entités, globales, avec beaucoup de code spécifique) prennent généralement 18–24 mois entre l’évaluation et le go-live. Les conversions brownfield mid-market peuvent durer 12–18 mois. Les implémentations greenfield à grande échelle peuvent prendre 24–36 mois.

Si vous démarrez une évaluation maintenant, un go-live en 2027 pour un système complexe est déjà tendu. Un démarrage d’évaluation en 2025 vous donne une trajectoire plus confortable vers un go-live en 2027–2028, avec du temps pour la stabilisation.

## Questions fréquentes

<details>
<summary>Quelle est la différence entre une migration greenfield et brownfield de ECC vers S/4HANA ?</summary>

Le greenfield repart de zéro : aucune configuration historique, donnée ou code spécifique n’est repris. Vous concevez les processus selon le standard SAP et ne migrez que les données dont vous avez besoin. Cela produit un système plus propre, mais demande davantage de gestion du changement et prend plus de temps.

Le brownfield convertit votre environnement ECC existant vers S/4HANA. La configuration, le code spécifique et les données historiques vous suivent. C’est plus rapide et moins perturbant pour les utilisateurs, mais la dette technique est reprise sauf si vous la traitez pendant la conversion.

La transition sélective des données (également appelée Bluefield) est la voie intermédiaire : migrer des codes société ou des plages de données spécifiques tout en redessinant les processus pour les entités que vous migrez.

</details>

<details>
<summary>Quelle est la date limite de migration de SAP ECC vers S/4HANA ?</summary>

La maintenance standard de SAP pour ECC prend fin le 31 décembre 2027. Le support étendu est disponible jusqu’en 2033, mais à un coût plus élevé et avec des contraintes : généralement 2-4% des frais de licence logicielle par an, et un accès limité aux nouvelles innovations.

La plupart des équipes qui n’ont pas commencé à planifier d’ici mi-2026 seront juste pour un go-live en 2027. Les migrations complexes ont besoin, de façon réaliste, de 18 à 24 mois entre l’évaluation et le go-live.

</details>

<details>
<summary>Que vous indique le SAP Readiness Check ?</summary>

Le Readiness Check analyse votre système ECC et produit un rapport couvrant plusieurs domaines. Les volumes de code spécifique et les programmes Z incompatibles avec S/4HANA. Les add-ons installés et leur niveau de support dans la nouvelle version. Le statut de conformité Unicode, les exigences de dimensionnement système pour HANA, et les simplification items : les changements fonctionnels dans S/4HANA qui affectent votre configuration actuelle.

L’exécuter tôt change la discussion sur le périmètre de migration. Les équipes découvrent régulièrement des dépendances à des add-ons dont elles n’avaient pas connaissance, ou des volumes de code spécifique deux fois supérieurs à leurs estimations. Joule for SAP Activate accélère le fit-gap et la rédaction de configuration de 30 à 50 percent sur les programmes qui l’adoptent de bout en bout jusqu’en 2026.

</details>

<details>
<summary>Combien de temps prend une migration de ECC vers S/4HANA ?</summary>

Une conversion brownfield pour une entreprise mid-market avec peu de code spécifique peut durer 12–18 mois. Une implémentation greenfield pour une entreprise avec plusieurs entités, des intégrations complexes et beaucoup de code spécifique dure généralement 24–36 mois.

Le nettoyage des données est la cause la plus fréquente des dépassements. Les équipes qui sous-estiment le temps nécessaire pour nettoyer les données de base avant la migration voient systématiquement leur planning glisser pendant la phase de réalisation.

</details>

<details>
<summary>Qu’est-ce que l’Universal Journal (ACDOCA) et pourquoi est-ce important pour la migration ?</summary>

L’Universal Journal remplace les tables séparées FI, CO et de rentabilité dans ECC par une table unique ACDOCA. Il élimine le stockage redondant des données et permet un reporting en temps réel sans agrégats.

Pour la migration, cela signifie que tout code spécifique ou rapport construit sur l’ancienne structure de tables ECC (BSEG, COEP, tables CE) doit être revu. Certains fonctionneront avec de simples ajustements. D’autres doivent être repensés parce que la table sous-jacente n’existe plus.

</details>

<details>
<summary>Quelles sont les exigences techniques minimales avant de convertir ECC vers S/4HANA ?</summary>

Le système ECC doit être en version 6.0 EhP 6 ou supérieure. La conformité Unicode est obligatoire : les systèmes non-Unicode doivent être convertis avant que la migration puisse commencer. Le SAP Readiness Check doit être terminé et tous les constats critiques traités. Le code spécifique doit être évalué par rapport au Simplification Item Catalog.

Au-delà des exigences techniques, la préparation métier est souvent la contrainte la plus forte. Les équipes de test doivent être disponibles pour l’UAT, avec un plan de gestion du changement en place. Un processus de gouvernance go/no-go clair doit être défini avant la fenêtre de cutover.

</details>

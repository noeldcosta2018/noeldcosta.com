SAP ECC のメインストリームサポートは、今から1年後の2027年12月に終了します。標準の延長サポートは2030年までで、追加料金ベースのオプションを使えば2033年まで延ばせますが、どちらもコストは高くなり、イノベーション面でも制約があります。複雑な移行は、実際のテストが始まると、たいてい18〜24か月かかります。新たなコミットメントでは、RISE with SAP が実務上の標準的な選択肢です。

これが現実的なプレッシャーです。まだ、着手するためのより明確なシグナルを待っているチームも少なくありません。今がそのタイミングです。

より難しいのは、ECC から S/4HANA への移行は、単純なアップグレードではないという点です。データ構造、システムのトランザクション処理の仕組み、そしてユーザーがあらゆるものとどう関わるかまで変わります。これを単なる技術刷新として扱うチームは、本来もっと良いもののために設計されたプラットフォーム上で、古い業務プロセスをそのまま作り直してしまいがちです。

あるプロジェクトでは、チームが ECC にあった数十本のカスタムレポートを、必要性を一切問い直さず、そのまま再構築するのに何か月も費やしました。後になって、その半分は一度も使われませんでした。移行自体は技術的にはきれいに完了していました。ですが、価値は生まれていませんでした。

## ECC と S/4HANA の間で実際に何が変わるのか

| 項目 | SAP ECC | SAP S/4HANA |
|---|---|---|
| データベース | 任意（Oracle、DB2、SQL Server など） | SAP HANA のみ |
| データモデル | トランザクションごとに複数の集計テーブル | Universal Journal (ACDOCA): 単一ソース、集計テーブルなし |
| ユーザーインターフェース | SAP GUI | SAP Fiori（ロールベース、モバイル対応） |
| 導入形態 | オンプレミスが標準 | オンプレミス、プライベートクラウド、または RISE with SAP（パブリッククラウド） |
| パフォーマンス | バッチ中心のレポーティング | トランザクションに組み込まれたリアルタイム分析 |
| カスタマイズ | Zプログラムが前提 | クリーンコア: 拡張はコアではなく BTP 経由 |
| サポート期間 | メインストリームは2027年終了、延長は2033年まで | 長期ロードマップ、継続的なイノベーション |

2023年、ある欧州の製造業クライアントでは、コンバージョン後にカスタムのバッチジョブが動かなくなりました。ロジック全体が、ECC の古いテーブル構造、つまり S/4HANA にはもう存在しないテーブルに依存していたからです。移行は技術的には完了していました。ですが、そのジョブが新しいモデルでも本当に意味を持つのかを、誰も問いませんでした。

ここで区別すべき点があります。移行はデータを動かします。戦略上の問いは、引き継ぐ設計判断をどう扱うかです。

## 3つの移行パス

<decision-tree question="どの移行パスが貴社の状況に適していますか？" options="レガシーが分断されており、プロセスを再設計したい => Greenfield|プロセスは適切で、ECCは安定しており、履歴を維持する必要がある => Brownfield|複数法人があり、一部を再利用しつつデータを選択的に移行したい => Bluefield"></decision-tree>

### Greenfield: ゼロから始める

S/4HANA 上でゼロから構築します。既存の設定は引き継ぎません。業務プロセスは SAP のベストプラクティスに沿って再設計します。

**使うべき場面:** 既存システムが断片化しすぎていてきれいに変換できない場合、または業務側が単なる踏襲ではなくプロセスそのものを見直したい場合です。

**注意点:** より多くのチェンジマネジメントが必要です。ユーザーは慣れた業務フローを失います。定着化の計画がトレーニング段階から始まるなら、すでに遅いです。

### Brownfield: システムコンバージョン

既存の ECC 環境を S/4HANA に変換します。設定、カスタムコード、過去データはそのまま持っていきます。

**使うべき場面:** 業務プロセスが成熟していて文書化もされており、コンプライアンス上トランザクション履歴の保持が重要で、大規模な組織再編も進行していない場合です。

**注意点:** 技術的負債も一緒に持ち込みます。変換の中で意図的に整理しない限り、レガシーの複雑さはそのまま残ります。

### Selective data transition (Bluefield)

すべてではなく、特定の会社コード、事業部門、またはデータ範囲だけを移行します。企業が合併やカーブアウトの結果として成り立っている場合や、何年分もの履歴データが現在の業務に関係しない場合に有効です。

**使うべき場面:** Greenfield型のプロセス柔軟性は欲しいが、重要な領域についてはBrownfield型のデータ継続性も確保したい場合です。

| Criteria | Greenfield | Brownfield | Selective |
|---|---|---|---|
| プロセス再設計 | SAP 標準に合わせて全面再設計 | おおむね維持 | 単位ごとに選択可能 |
| 履歴データ | 引き継がない | 全面引き継ぎ | 選択的に引き継ぎ |
| 本番稼働までの期間 | 長い | 短い | スコープ次第 |
| 技術的負債 | 解消される | 引き継がれる | 移行対象範囲では削減 |
| 変更影響 | 高い | 低い | 中程度 |
| 最適なケース | 断片化したレガシー、大規模変革 | 安定運用され、適切に保守された ECC | 合併後、カーブアウト、段階展開 |

## 実際の作業を決める5つのステップ

<stepper title="移行の進め方" steps="評価|データを分類|データをクレンジング|コードを適応|テストとカットオーバー" bodies="SAP Readiness Checkを実行します。カスタムコード、アドオン、インターフェースを棚卸しします。|データをhot、warm、coldに分類します。coldデータは移行しなくても構いません。|重複、不整合、欠損項目を解消します。常に想定より長くかかります。|ABAP Test Cockpitを実行します。Zコードを減らし、単に移植するだけにしません。|複数回のテストに加え、少なくとも1回は本番同等のカットオーバーリハーサルを行います。"></stepper>

### 1. アセスメントと準備状況の確認

ここから始めてください。必ずです。SAP Readiness Check を実行します。これは ECC システムをスキャンし、カスタムコード量、アドオン依存関係、Unicode準拠状況、データサイズ、簡素化項目のスナップショットを出します。

ここで驚きになりやすいのは、たいていアドオンです。チームは、S/4HANA ではサポートされないコンポーネントへの依存や、見積もりの3倍あるカスタムコード量を見つけます。12か月目に見つけるより、2週目に見つけるほうがはるかにましです。

Readiness Check と並行して、カスタム開発、インターフェース、サードパーティ接続を棚卸ししてください。価値を生むもの、古くなっているもの、誰も説明できないものを切り分けます。

### 2. データ分析と分類

移行前にデータ量を評価します。次のように分けてください。

1. **Hot.** 頻繁に使われ、ライブ処理に必要なもの。
2. **Warm.** ときどき参照され、関連性はあるが日常的ではないもの。
3. **Cold.** 履歴用または未使用で、監査やバックアップのためだけに保持しているもの。

Coldデータを S/4HANA に入れる必要はありません。このステップを飛ばすチームは、新システムに不要なものまで持ち込み、パフォーマンスや移行スケジュールに影響を与えます。

### 3. データクレンジングとアーカイブ

このステップは、どの計画でも見込んでいるより長くかかります。重複した仕入先レコード。不整合な数量単位。不完全な顧客マスタデータ。こうした問題はどの ECC システムにもあり、先に対処しなければ、そのままきれいに S/4HANA に移ってしまいます。

SAP MDG と Information Steward はこのフェーズを支援します。Coldデータはアーカイブし、それ以外は移行後ではなく移行前にクレンジングしてください。

クレンジングを飛ばしたチームは、切替時に問題を見つけます。その時点では、もう適切に直す時間はありません。

### 4. カスタムコード適応

ATC（ABAP Test Cockpit）を実行して非互換をスキャンします。SAP の Simplification Item Catalog と照合してください。出力結果から、構文修正が必要なもの、機能置換が必要なもの、廃止すべきものが分かります。

このフェーズは反復型です。レビューし、テストし、絞り込みます。目標はZコードを単に直すことではなく、減らすことです。カスタムコードを S/4HANA に持ち込むと、保守コストが延び、今後のアップグレードがすべて複雑になります。

### 5. テスト、トレーニング、切替

テストは複数ラウンドで進めるべきです。単体テスト、結合テスト、UAT、そして少なくとも1回のフル切替リハーサルです。UATには、ヘビーユーザーだけでなくライトユーザーも含めてください。見つける問題が違います。

切替リハーサルは任意ではありません。タイミングの抜け、欠けている検証、全体シーケンスをエンドツーエンドで流したときにしか表面化しない連携障害が見つかります。これを飛ばすチームは、本番稼働の週末にそれらを発見します。

## 役立つツール

| Tool | 何をするか | 使うタイミング |
|---|---|---|
| SAP Readiness Check | ECC の互換性、アドオン、カスタムコード、サイズをスキャン | 移行アプローチを選ぶ前 |
| SAP Transformation Navigator | レガシーコンポーネントを S/4HANA の相当機能にマッピングし、クラウド拡張を提案 | 戦略・スコーピングフェーズ |
| ABAP Test Cockpit (ATC) + Simplification Item Check | 非互換のカスタムコードを特定 | カスタムコード適応フェーズ |
| SAP Signavio | プロセスマッピング: 文書上の姿ではなく、実際の動き方を可視化 | 設計凍結前 |
| LeanIX | アプリケーションランドスケープの可視化: どのシステムが何とつながっているかを把握 | 連携設計フェーズ |

ほとんどのチームは、まず Readiness Check から始めるべきです。それ以外はすべて、そこで何が見つかるかに左右されます。

## スケジュールと2027年の期限

SAP ECC のメインストリーム保守は2027年12月31日に終了します。延長サポートは2033年まで利用できますが、割増費用がかかり、新機能へのアクセスも制限されます。

複雑なエンタープライズ移行（複数法人、グローバル展開、大量のカスタムコードあり）は、通常、アセスメントから本番稼働まで18〜24か月かかります。中堅企業のBrownfieldコンバージョンなら12〜18か月で進むこともあります。大規模なGreenfield導入は24〜36か月かかることがあります。

今アセスメントを始めるなら、複雑なシステムで2027年本番稼働はすでにかなりタイトです。2025年にアセスメントを開始できれば、安定化期間も含めて2027〜2028年本番稼働に向けて、より余裕のある進め方ができます。

## よくある質問

<details>
<summary>greenfield と brownfield の ECC から S/4HANA への移行の違いは何ですか？</summary>

Greenfield はゼロから始めます。既存の設定、データ、カスタムコードは引き継ぎません。業務プロセスは SAP 標準に合わせて設計し、必要なデータだけを移行します。よりクリーンなシステムになりますが、より多くのチェンジマネジメントが必要で、時間もかかります。

Brownfield は既存の ECC 環境を S/4HANA に変換します。設定、カスタムコード、履歴データはすべて一緒に持っていきます。より速く、ユーザーへの混乱も少ないですが、変換の中で整理しない限り、技術的負債も引き継がれます。

Selective data transition（Bluefield とも呼ばれます）はその中間です。移行対象の部門ではプロセスを再設計しつつ、特定の会社コードやデータ範囲だけを移行します。

</details>

<details>
<summary>SAP ECC から S/4HANA への移行期限はいつですか？</summary>

SAP の ECC に対するメインストリーム保守は2027年12月31日に終了します。延長サポートは2033年まで利用できますが、コストは高く、制約もあります。通常、年間でソフトウェアライセンス料の2〜4%が追加でかかり、新しいイノベーションへのアクセスも限定されます。

2026年半ばまでに計画を始めていないチームの多くは、2027年本番稼働にかなり近い日程になります。複雑な移行では、アセスメントから本番稼働まで現実的に18〜24か月必要です。

</details>

<details>
<summary>SAP Readiness Check で何が分かりますか？</summary>

Readiness Check は ECC システムをスキャンし、複数の領域をカバーするレポートを出します。カスタムコード量と、どのZプログラムが S/4HANA と非互換か。導入済みアドオンと、それらが新バージョンでサポートされるか。Unicode準拠状況、HANA 向けのシステムサイジング要件、そして simplification items、つまり現在の設定に影響する S/4HANA 上の機能変更です。

これを早い段階で実行すると、移行スコープの議論そのものが変わります。チームは、自分たちが把握していなかったアドオン依存や、見積もりの2倍あるカスタムコード量を定期的に見つけています。Joule for SAP Activate は、2026年までにエンドツーエンドで採用するプログラムにおいて、fit-gap と設定ドラフト作成を30〜50%高速化します。

</details>

<details>
<summary>ECC から S/4HANA への移行にはどれくらいかかりますか？</summary>

カスタムコードが少ない中堅企業のBrownfieldコンバージョンなら、12〜18か月で進むことがあります。複数法人、複雑な連携、大量のカスタムコードを抱える企業のGreenfield導入では、通常24〜36か月かかります。

超過の最も一般的な原因はデータクレンジングです。移行前のマスタデータ整備に必要な時間を過小評価したチームは、realisation フェーズで一貫してスケジュール遅延を起こしています。

</details>

<details>
<summary>Universal Journal (ACDOCA) とは何ですか？ また、なぜ移行で重要なのですか？</summary>

Universal Journal は、ECC で分かれていた FI、CO、収益性分析の各テーブルを、単一の ACDOCA テーブルに置き換えます。これにより重複したデータ保存がなくなり、集計テーブルなしでリアルタイムレポーティングが可能になります。

移行の観点では、古い ECC のテーブル構造（BSEG、COEP、CE テーブル）を前提に作られたカスタムコードやレポートは見直しが必要だということです。簡単な調整で動くものもあります。ですが、基盤となるテーブル自体がもう存在しないため、再設計が必要なものもあります。

</details>

<details>
<summary>ECC を S/4HANA に変換する前の最低限の技術要件は何ですか？</summary>

ECC システムはリリース 6.0 EhP 6 以上であるべきです。Unicode準拠は必須です。非Unicodeシステムは、移行開始前に変換を完了しなければなりません。SAP Readiness Check を完了し、重大な指摘事項にはすべて対処しておく必要があります。カスタムコードは Simplification Item Catalog に照らして評価する必要があります。

技術要件以上に、制約になりやすいのは業務側の準備状況です。UATに対応できるテストチームを確保し、チェンジマネジメント計画も整っている必要があります。切替ウィンドウに入る前に、明確な go/no-go のガバナンスプロセスを合意しておくべきです。

</details>

SAP ECC deixa de ter suporte mainstream em dezembro de 2027, daqui a um ano. O suporte estendido padrão vai até 2030, com opções adicionais pagas até 2033, ambas com custo mais alto e restrições à inovação. A maioria das migrações complexas, quando os testes reais começam, leva de 18 a 24 meses. RISE with SAP é a opção prática por defeito para novos compromissos.

Essa é a pressão prática. Muitas equipas ainda estão à espera de um sinal mais claro para começar. É este.

A parte mais difícil é que a passagem de ECC para S/4HANA não é um upgrade direto. Muda a forma como os dados são estruturados, como o sistema trata as transações e como os utilizadores interagem com tudo. As equipas que tratam isto como uma simples renovação técnica acabam muitas vezes por reconstruir os processos antigos numa plataforma desenhada para algo melhor.

Num projeto, uma equipa passou meses a reconstruir dezenas de relatórios customizados exatamente como eram no ECC. Sem questionar se ainda eram necessários. Mais tarde, metade deles nunca foi usada. A migração estava tecnicamente limpa. O valor, não.

## O que realmente muda entre ECC e S/4HANA

| Área | SAP ECC | SAP S/4HANA |
|---|---|---|
| Base de dados | Qualquer uma (Oracle, DB2, SQL Server, etc.) | Apenas SAP HANA |
| Modelo de dados | Múltiplas tabelas agregadas por transação | Universal Journal (ACDOCA): fonte única, sem agregados |
| Interface do utilizador | SAP GUI | SAP Fiori (baseado em funções, preparado para mobile) |
| Implementação | Standard on-premise | On-premise, cloud privada ou RISE with SAP (cloud pública) |
| Desempenho | Reporting fortemente dependente de batch | Analytics em tempo real embebidos nas transações |
| Customização | Programas Z esperados | Clean core: as extensões passam por BTP, não pelo core |
| Calendário de suporte | Mainstream termina em 2027, estendido até 2033 | Roadmap de longo prazo, inovação contínua |

Um cliente industrial europeu, em 2023, descobriu que os seus jobs batch customizados deixaram de funcionar após a conversão. Toda a lógica dependia da estrutura de tabelas mais antiga do ECC: tabelas que já não existem no S/4HANA. A migração estava tecnicamente concluída. Ninguém tinha perguntado se esses jobs ainda faziam sentido no novo modelo.

Essa é a distinção que vale a pena fazer: a migração move os dados. A questão estratégica é o que fazer com as decisões de desenho que se herdam.

## Três caminhos de migração

<decision-tree question="Qual caminho de migração se adequa à sua situação?" options="O legado é fragmentado e você quer redesenhar processos => Greenfield|Os processos são sólidos, o ECC é estável, o histórico precisa ser mantido => Brownfield|Múltiplas entidades, com reutilização parcial e dados seletivos => Bluefield"></decision-tree>

### Greenfield: começar de novo

Construir de raiz em S/4HANA. Nenhuma configuração legacy é transportada. Os processos são redesenhados com base nas melhores práticas da SAP.

**Usar quando:** os sistemas legacy estão demasiado fragmentados para uma conversão limpa, ou quando a empresa quer repensar processos em vez de os replicar.

**Atenção a:** é necessária mais gestão da mudança. Os utilizadores perdem fluxos de trabalho familiares. Se o planeamento da adoção começa na formação, já vai tarde.

### Brownfield: conversão do sistema

Converter o ambiente atual de ECC para S/4HANA. Configuração, código customizado e dados históricos vêm consigo.

**Usar quando:** os processos são maduros e bem documentados, preservar o histórico transacional é importante para compliance, e não há nenhuma grande reestruturação em curso.

**Atenção a:** a dívida técnica vem consigo. A complexidade legacy também, a menos que seja eliminada deliberadamente durante a conversão.

### Transição seletiva de dados (Bluefield)

Migrar códigos de empresa, unidades de negócio ou intervalos de dados específicos, não tudo. Útil quando a empresa resulta de fusões ou carve-outs, ou quando anos de dados históricos são irrelevantes para a operação atual.

**Usar quando:** se quer a flexibilidade de processos de um Greenfield, mas com a continuidade de dados de um Brownfield nas partes que realmente importam.

| Critérios | Greenfield | Brownfield | Seletivo |
|---|---|---|---|
| Redesenho de processos | Redesenho completo com base no standard SAP | Em grande parte preservado | Selecionável por unidade |
| Dados históricos | Não são transportados | Totalmente transportados | Transporte seletivo |
| Tempo até go-live | Mais longo | Mais curto | Varia consoante o âmbito |
| Dívida técnica | Eliminada | Transportada | Reduzida no âmbito migrado |
| Impacto da mudança | Alto | Mais baixo | Moderado |
| Melhor para | Legacy fragmentado, grande transformação | ECC estável e bem mantido | Pós-fusão, carve-out, rollout faseado |

## Cinco passos que definem o trabalho real

<stepper title="A sequência da migração" steps="Avaliar|Classificar dados|Sanear|Adaptar código|Testar e executar o cutover" bodies="Execute o SAP Readiness Check. ### 1. Avaliação e preparação

Comece aqui. Sempre. Execute o SAP Readiness Check: faz uma análise ao sistema ECC e produz uma fotografia dos volumes de código customizado, dependências de add-ons, conformidade Unicode, dimensionamento de dados e simplification items.

As surpresas aqui costumam ser os add-ons. As equipas descobrem dependências de componentes que não são suportados no S/4HANA, ou volumes de código customizado três vezes superiores ao que estimavam. É melhor descobrir isso na segunda semana do que no décimo segundo mês.

Em paralelo com o Readiness Check: faça o inventário dos desenvolvimentos customizados, interfaces e ligações a terceiros. Assinale o que acrescenta valor, o que está desatualizado e o que ninguém consegue explicar.

### 2. Análise e classificação de dados

Avalie o volume de dados antes de o mover. Segmente-o:

1. **Hot.** Usado com frequência, necessário para processamento em produção.
2. **Warm.** Acesso ocasional, relevante mas não diário.
3. **Cold.** Histórico ou sem uso, mantido apenas para auditoria ou backup.

Os dados cold não precisam de ir para o S/4HANA. As equipas que saltam este passo levam desordem para o novo sistema, o que afeta o desempenho e os prazos da migração.

### 3. Limpeza e arquivamento de dados

Este passo demora mais do que qualquer plano prevê. Registos duplicados de fornecedores. Unidades de medida inconsistentes. Dados mestre de clientes incompletos. Estes problemas existem em todos os sistemas ECC e passam de forma limpa para o S/4HANA se não forem tratados primeiro.

SAP MDG e Information Steward apoiam esta fase. Arquive os dados cold. Limpe o resto antes da migração, não depois.

As equipas que saltam a limpeza descobrem os problemas durante o cutover, quando já não há tempo para os corrigir como deve ser.

### 4. Adaptação do código customizado

Execute o ATC (ABAP Test Cockpit) para detetar incompatibilidades. Cruze isso com o Simplification Item Catalog da SAP. O resultado mostra o que precisa de correções de sintaxe, o que precisa de substituição funcional e o que deve ser retirado.

Esta fase é iterativa. Rever, testar, refinar. O objetivo é reduzir o código Z, não apenas corrigi-lo. Levar código customizado para S/4HANA prolonga o custo de manutenção e complica todos os upgrades futuros.

### 5. Testes, formação e cutover

Os testes devem decorrer em várias rondas: testes unitários, testes de integração, UAT e pelo menos um ensaio completo de cutover. Inclua no UAT tanto power users como utilizadores ocasionais. Encontram problemas diferentes.

O ensaio de cutover não é opcional. Revela falhas de timing, validações em falta e falhas de integração que só aparecem quando a sequência completa corre de ponta a ponta. As equipas que o saltam descobrem estes problemas no fim de semana do go-live.

## Ferramentas que ajudam

| Ferramenta | O que faz | Quando usar |
|---|---|---|
| SAP Readiness Check | Analisa o ECC quanto a compatibilidade, add-ons, código customizado e dimensionamento | Antes de escolher a abordagem de migração |
| SAP Transformation Navigator | Mapeia componentes legacy para equivalentes em S/4HANA; sugere extensões cloud | Fase de estratégia e definição de âmbito |
| ABAP Test Cockpit (ATC) + Simplification Item Check | Identifica código customizado incompatível | Fase de adaptação do código customizado |
| SAP Signavio | Mapeamento de processos: como as coisas realmente funcionam, não como foram documentadas | Antes do congelamento do desenho |
| LeanIX | Mapeamento da paisagem aplicacional: que sistemas se ligam a quê | Fase de desenho de integrações |
| SAP Migration Cockpit | Move dados mestre e transacionais para S/4HANA | Fase de migração de dados |

O Readiness Check é onde a maioria das equipas deve começar. Tudo o resto depende do que ele revelar.

## Prazos e o deadline de 2027

A manutenção mainstream do SAP ECC termina em 31 de dezembro de 2027. O suporte estendido está disponível até 2033, mas tem um prémio de custo e limita o acesso a novas capacidades.

As migrações empresariais complexas (multi-entidade, globais, com muito código customizado) demoram tipicamente 18–24 meses desde a avaliação até ao go-live. Conversões brownfield de empresas mid-market podem demorar 12–18 meses. Implementações greenfield em escala podem demorar 24–36 meses.

Se está a começar uma avaliação agora, um go-live em 2027 para um sistema complexo já é apertado. Começar a avaliação em 2025 dá-lhe um caminho mais confortável para um go-live em 2027–2028, com tempo para estabilização.

## Perguntas frequentes

<details>
<summary>Qual é a diferença entre uma migração greenfield e brownfield de ECC para S/4HANA?</summary>

Greenfield começa do zero: nenhuma configuração legacy, dados ou código customizado é transportado. Os processos são desenhados com base no standard SAP e migram-se apenas os dados necessários. Produz um sistema mais limpo, mas exige mais gestão da mudança e demora mais tempo.

Brownfield converte o ambiente atual de ECC para S/4HANA. Configuração, código customizado e dados históricos vêm todos consigo. É mais rápido e menos disruptivo para os utilizadores, mas a dívida técnica também vem, a menos que seja eliminada durante a conversão.

A transição seletiva de dados (também chamada Bluefield) é o caminho intermédio: migrar códigos de empresa ou intervalos de dados específicos enquanto se redesenham processos para as unidades que estão a ser migradas.

</details>

<details>
<summary>Qual é o prazo-limite para a migração de SAP ECC para S/4HANA?</summary>

A manutenção mainstream da SAP para ECC termina em 31 de dezembro de 2027. O suporte estendido está disponível até 2033, mas com custo mais elevado e restrições: tipicamente 2-4% das taxas de licença de software por ano, e acesso limitado a novas inovações.

A maioria das equipas que não tiver começado a planear até meados de 2026 estará muito em cima da hora para um go-live em 2027. Migrações complexas precisam realisticamente de 18 a 24 meses desde a avaliação até ao go-live.

</details>

<details>
<summary>O que lhe diz o SAP Readiness Check?</summary>

O Readiness Check analisa o sistema ECC e produz um relatório que cobre várias áreas. Volumes de código customizado e quais os programas Z incompatíveis com S/4HANA. Add-ons instalados e se são suportados na nova versão. Estado de conformidade Unicode, requisitos de dimensionamento do sistema para HANA e simplification items: alterações funcionais no S/4HANA que afetam a configuração atual.

Executá-lo cedo muda a discussão sobre o âmbito da migração. As equipas descobrem regularmente dependências de add-ons de que não tinham conhecimento, ou volumes de código customizado que são o dobro do que estimavam. Joule for SAP Activate acelera o fit-gap e a elaboração da configuração em 30 a 50 por cento nos programas que o adotam de ponta a ponta até 2026.

</details>

<details>
<summary>Quanto tempo demora uma migração de ECC para S/4HANA?</summary>

Uma conversão brownfield para uma empresa mid-market com pouco código customizado pode demorar 12–18 meses. Uma implementação greenfield para uma empresa com múltiplas entidades, integrações complexas e muito código customizado demora tipicamente 24–36 meses.

A limpeza de dados é a causa mais comum de derrapagens. As equipas que subestimam o tempo necessário para limpar dados mestre antes da migração veem de forma consistente os calendários escorregar na fase de realização.

</details>

<details>
<summary>O que é o Universal Journal (ACDOCA) e porque é importante para a migração?</summary>

O Universal Journal substitui as tabelas separadas de FI, CO e rentabilidade no ECC por uma única tabela ACDOCA. Elimina o armazenamento redundante de dados e permite reporting em tempo real sem agregados.

Para a migração, isto significa que qualquer código customizado ou relatório construído sobre a antiga estrutura de tabelas do ECC (BSEG, COEP, tabelas CE) precisa de ser revisto. Alguns funcionarão com ajustes simples. Outros precisam de ser redesenhados porque a tabela subjacente já não existe.

</details>

<details>
<summary>Quais são os requisitos técnicos mínimos antes de converter ECC para S/4HANA?</summary>

O sistema ECC deve estar na release 6.0 EhP 6 ou superior. A conformidade Unicode é obrigatória: sistemas não Unicode têm de ser convertidos antes de a migração poder começar. O SAP Readiness Check deve estar concluído e todas as conclusões críticas tratadas. O código customizado precisa de ser avaliado face ao Simplification Item Catalog.

Para além dos requisitos técnicos, a preparação do negócio é muitas vezes a maior restrição. As equipas de teste precisam de estar disponíveis para UAT, com um plano de gestão da mudança em vigor. Deve existir um processo claro de governance go/no-go acordado antes da janela de cutover.

</details>

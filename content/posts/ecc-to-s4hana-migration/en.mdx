SAP ECC mainstream support ends December 2027. Extended support runs to 2033, but at higher cost and with constraints on innovation. Most complex migrations, once real testing begins, run 18 to 24 months.

That's the practical pressure. Plenty of teams are still waiting for a clearer signal to start. This is it.

The harder part is that ECC to S/4HANA is not a straight upgrade. It changes how data is structured, how the system handles transactions, and how users interact with everything. Teams that treat it like a technical refresh often rebuild their old processes in a platform designed for something better.

On one project, a team spent months rebuilding dozens of custom reports exactly as they were in ECC. No questions asked about whether they were still needed. Later, half of them were never used. The migration was technically clean. The value was not.

## What actually changes between ECC and S/4HANA

| Area | SAP ECC | SAP S/4HANA |
|---|---|---|
| Database | Any (Oracle, DB2, SQL Server, etc.) | SAP HANA only |
| Data model | Multiple aggregate tables per transaction | Universal Journal (ACDOCA): single source, no aggregates |
| User interface | SAP GUI | SAP Fiori (role-based, mobile-enabled) |
| Deployment | On-premise standard | On-premise, private cloud, or RISE with SAP (public cloud) |
| Performance | Batch-heavy reporting | Real-time analytics embedded in transactions |
| Customisation | Z-programs expected | Clean core: extensions go through BTP, not the core |
| Support timeline | Mainstream ends 2027, extended to 2033 | Long-term roadmap, continuous innovation |

One client's custom batch jobs stopped working after conversion. The entire logic relied on ECC's older table structure: tables that no longer exist in S/4HANA. The migration was technically complete. Nobody had asked whether those jobs still made sense in the new model.

That's the distinction worth making: the migration moves the data. The strategic question is what you do with the design decisions you inherit.

## Three migration paths

<decision-tree question="Which migration path fits your situation?" options="Legacy is fragmented and you want to redesign processes => Greenfield|Processes are sound, ECC is stable, history must stay => Brownfield|Multi-entity, want partial reuse and selective data => Bluefield"></decision-tree>

### Greenfield: start fresh

Build from scratch on S/4HANA. No legacy configuration carried forward. Processes redesigned against SAP best practices.

**Use when:** legacy systems are too fragmented to convert cleanly, or when the business wants to rethink processes rather than replicate them.

**Watch for:** more change management required. Users lose familiar workflows. If adoption planning starts at training, it's already late.

### Brownfield: system conversion

Convert your existing ECC environment to S/4HANA. Configuration, custom code, and historical data come with you.

**Use when:** processes are mature and well-documented, preserving transaction history matters for compliance, and there's no major restructuring underway.

**Watch for:** you carry forward technical debt. Legacy complexity moves with you unless you deliberately clean it up during the conversion.

### Selective data transition (Bluefield)

Migrate specific company codes, business units, or data ranges, not everything. Useful when the business is a product of mergers or carve-outs, or when years of historical data are irrelevant to current operations.

**Use when:** you want Greenfield-style process flexibility but Brownfield-style data continuity for the parts that matter.

| Criteria | Greenfield | Brownfield | Selective |
|---|---|---|---|
| Process redesign | Full redesign against SAP standard | Largely preserved | Selectable by unit |
| Historical data | Not carried forward | Fully carried forward | Selective carryover |
| Time to go-live | Longer | Shorter | Varies by scope |
| Technical debt | Eliminated | Carried forward | Reduced for migrated scope |
| Change impact | High | Lower | Moderate |
| Best for | Fragmented legacy, major transformation | Stable, well-maintained ECC | Post-merger, carve-out, phased rollout |

## Five steps that define the actual work

<stepper title="The migration sequence" steps="Assess|Classify data|Cleanse|Adapt code|Test and cut over" bodies="Run the SAP Readiness Check. ### 1. Assessment and readiness

Start here. Always. Run the SAP Readiness Check: it scans your ECC system and produces a snapshot of custom code volumes, add-on dependencies, Unicode compliance, data sizing, and simplification items.

The surprises here are usually the add-ons. Teams discover dependencies on components that are unsupported in S/4HANA, or custom code volumes that are three times what they estimated. Better to find this in week two than in month twelve.

Alongside the Readiness Check: inventory your custom developments, interfaces, and third-party connections. Flag what adds value, what's outdated, and what no one can explain.

### 2. Data analysis and classification

Evaluate your data volume before you move it. Segment it:

1. **Hot.** Used frequently, needed for live processing.
2. **Warm.** Occasional access, relevant but not daily.
3. **Cold.** Historical or unused, kept for audit or backup only.

Cold data doesn't need to go into S/4HANA. Teams that skip this step bring clutter into the new system that affects performance and migration timelines.

### 3. Data cleansing and archiving

This step takes longer than every plan allows for. Duplicate vendor records. Inconsistent units of measure. Partial customer master data. These problems exist in every ECC system and they transfer cleanly to S/4HANA if you don't address them first.

SAP MDG and Information Steward support this phase. Archive the cold data. Clean the rest before migration, not after.

The teams that skip cleansing discover the problems during cutover, when there's no time to fix them properly.

### 4. Custom code adaptation

Run ATC (ABAP Test Cockpit) to scan for incompatibilities. Cross-reference against SAP's Simplification Item Catalog. The output tells you what needs syntax fixes, what needs functional replacement, and what should be retired.

This phase is iterative. Review, test, refine. The goal is to reduce Z-code, not just fix it. Carrying custom code into S/4HANA extends maintenance cost and complicates every future upgrade.

### 5. Testing, training, and cutover

Testing should run in multiple rounds: unit testing, integration testing, UAT, and at least one full cutover rehearsal. Include both power users and casual users in UAT. They find different problems.

The cutover rehearsal is not optional. It reveals timing gaps, missing validations, and integration failures that only surface when the full sequence runs end-to-end. Teams that skip it discover these problems on go-live weekend.

## Tools that help

| Tool | What it does | When to use it |
|---|---|---|
| SAP Readiness Check | Scans ECC for compatibility, add-ons, custom code, sizing | Before choosing migration approach |
| SAP Transformation Navigator | Maps legacy components to S/4HANA equivalents; suggests cloud extensions | Strategy and scoping phase |
| ABAP Test Cockpit (ATC) + Simplification Item Check | Identifies incompatible custom code | Custom code adaptation phase |
| SAP Signavio | Process mapping: how things actually work, not how they were documented | Before design freeze |
| LeanIX | Application landscape mapping: what systems connect to what | Integration design phase |
| SAP Migration Cockpit | Moves master and transactional data into S/4HANA | Data migration phase |

The Readiness Check is where most teams should start. Everything else depends on what it surfaces.

## Timelines and the 2027 deadline

SAP ECC mainstream maintenance ends December 31, 2027. Extended support is available to 2033 but carries a premium and limits access to new capabilities.

Complex enterprise migrations (multi-entity, global, with significant custom code) typically take 18–24 months from assessment to go-live. Mid-market brownfield conversions can run 12–18 months. Greenfield implementations at scale can take 24–36 months.

If you're starting an assessment now, a 2027 go-live for a complex system is already tight. 2025 assessment starts give you a more comfortable path to 2027–2028 go-live with time for stabilisation.

## Frequently asked questions

<details>
<summary>What is the difference between greenfield and brownfield ECC to S/4HANA migration?</summary>

Greenfield starts from scratch: no legacy configuration, data, or custom code carried forward. You design processes against SAP standard and migrate only the data you need. It produces a cleaner system but requires more change management and takes longer.

Brownfield converts your existing ECC environment to S/4HANA. Configuration, custom code, and historical data all come with you. It's faster and less disruptive to users, but technical debt carries forward unless you clean it up during the conversion.

Selective data transition (also called Bluefield) is the middle path: migrate specific company codes or data ranges while redesigning processes for the units you're migrating.

</details>

<details>
<summary>What is the SAP ECC to S/4HANA migration deadline?</summary>

SAP mainstream maintenance for ECC ends December 31, 2027. Extended support is available until 2033, but at higher cost and with constraints: typically 2-4% of software licence fees per year, and limited access to new innovations.

Most teams that haven't started planning by 2025 will be cutting it close for a 2027 go-live. Complex migrations realistically need 18–24 months from assessment to go-live.

</details>

<details>
<summary>What does the SAP Readiness Check tell you?</summary>

The Readiness Check scans your ECC system and produces a report covering: custom code volumes and which Z-programs are incompatible with S/4HANA, installed add-ons and whether they're supported in the new version, Unicode compliance status, system sizing requirements for HANA, and simplification items: functional changes in S/4HANA that affect your current configuration.

Running it early changes the migration scope discussion. Teams regularly discover add-on dependencies they weren't aware of, or custom code volumes double what they estimated.

</details>

<details>
<summary>How long does an ECC to S/4HANA migration take?</summary>

A brownfield conversion for a mid-market company with limited custom code can run 12–18 months. A greenfield implementation for an enterprise with multiple entities, complex integrations, and significant custom code typically runs 24–36 months.

Data cleansing is the most common cause of overruns. Teams that underestimate the time needed to clean master data before migration consistently see schedules slip in the realisation phase.

</details>

<details>
<summary>What is the Universal Journal (ACDOCA) and why does it matter for migration?</summary>

The Universal Journal replaces the separate FI, CO, and profitability tables in ECC with a single ACDOCA table. It eliminates redundant data storage and enables real-time reporting without aggregates.

For migration, this means any custom code or reports built against the old ECC table structure (BSEG, COEP, CE tables) needs to be reviewed. Some will work with simple adjustments. Others need redesign because the underlying table no longer exists.

</details>

<details>
<summary>What are the minimum technical requirements before converting ECC to S/4HANA?</summary>

The ECC system should be at release 6.0 EhP 6 or higher. Unicode compliance is required: non-Unicode systems must convert before migration can begin. The SAP Readiness Check should be completed and all critical findings addressed. Custom code needs to be evaluated against the Simplification Item Catalog.

Beyond the technical requirements, business readiness is often the bigger constraint: testing teams available for UAT, change management plan in place, and a clear go/no-go governance process agreed before the cutover window.

</details>

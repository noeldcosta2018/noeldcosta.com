主要的SAP测试工具是：测试管理用SAP Cloud ALM和SAP Solution Manager，测试自动化用Tricentis Tosca（SAP以SAP Test Automation by Tricentis之名销售）、Worksoft、Panaya和UiPath，性能测试用OpenText LoadRunner。大多数S/4HANA项目需要每一类各选一款：一款管理和追溯测试，一款自动化回归测试，一款测试负载。

这七款工具我都自己用过，或让我的团队用过。这篇指南比较每款工具用来做什么（已于2026年10月对照厂商文档核实），以及如何在它们之间做选择。关于测试类型本身，请先看[SAP测试详解](/zh-CN/sap-testing-explained/)。

我听过几十场工具演示，演示中一切都完美运行。可一到真实项目里，脚本不断出错，或者集成从来不像厂商演示的那样工作。所以我不靠功能清单来挑选SAP测试工具。

## SAP测试工具组合要完成的三项工作

在我负责的项目中，测试约占工作量的35%。工具决定了这部分工作量中有多少是可以重复的。

它们分为三类。不要指望一类工具去做另一类工具的工作。

1. **测试管理**。存放测试用例、测试计划、执行结果和缺陷，并把它们与需求和变更关联起来。手工测试在这里进行，审计师也在这里查看。SAP Cloud ALM、SAP Solution Manager和Panaya Test Management属于这一类。
2. **功能测试自动化**。录制或建模业务流程测试，并在每次变更后重新运行。Tricentis、Worksoft、Panaya Test Automation和UiPath属于这一类。
3. **性能测试**。同时模拟大量用户，在上线前找出瓶颈。OpenText LoadRunner属于这一类，SAP也转售Tricentis的性能测试产品。

有几家厂商横跨两类，而且边界随着每次版本发布而变化。先决定您是为哪项工作购买，再在那一类中比较工具。

## SAP测试工具对比

下表汇总了这七款工具。每一行都已对照厂商自己的页面或SAP支持门户核实。

| 工具 | 厂商 | 主要用途 | 用来做什么 | 适用场景 |
|---|---|---|---|---|
| SAP Cloud ALM | SAP | 测试管理 | 测试用例、测试计划、手工执行、缺陷，以及到流程和需求的可追溯性 | 新的S/4HANA和RISE项目的默认选择；Enterprise Support包含一个租户 |
| SAP Solution Manager 7.2 | SAP | 测试管理 | Test Suite、Business Process Change Analyzer，与变更控制关联 | 已经在运行它的现有本地部署系统环境；主流维护于2027年结束 |
| Tricentis Tosca / SAP Test Automation by Tricentis | Tricentis，由SAP转售 | 自动化 | 跨SAP和非SAP应用、基于模型的无代码自动化 | 版本发布频繁、系统环境混合的项目 |
| Worksoft Certify | Worksoft | 自动化 | 无代码流程自动化，外加流程捕获和影响分析 | 流程密集、希望由业务用户构建测试的系统环境 |
| Panaya | Panaya | 影响分析、测试管理、自动化 | 变更影响分析、测试管理和AI辅助的自动化 | 升级和变更频繁、需要知道该重新测试什么的项目 |
| UiPath Test Manager（UiPath Test Suite） | UiPath | 自动化和测试管理 | 用UiPath机器人在SAP GUI、Fiori和非SAP系统上编排测试 | 已经在用UiPath做流程自动化的公司 |
| OpenText LoadRunner | OpenText | 性能 | 使用SAP、SAP GUI和SAP Web协议进行负载和并发测试 | 上线前的峰值业务量和并发测试 |

这些工具没有一款是糟糕的选择。它们的区别在于方法、许可方式，以及您的团队已经掌握了什么。

## 测试管理：Cloud ALM与Solution Manager

### SAP Cloud ALM

根据[SAP关于测试的Cloud ALM培训](https://learning.sap.com/courses/implementing-with-sap-cloud-alm/planning-and-executing-testing_ef46a49b-9885-4aaa-841d-5ac9c80a3681)，Cloud ALM涵盖测试准备、测试计划、测试执行和缺陷。测试用例基于解决方案流程活动构建，测试人员逐步记录通过或不通过，缺陷直接从失败的运行中提出。这让您拥有从流程到测试再到缺陷的可追溯性。

在自动化方面，它负责编排而不负责执行。SAP列出了两款集成工具：SAP S/4HANA Cloud Test Automation Tool和Tricentis Test Automation for SAP。Worksoft、Panaya和UiPath都各自发布了自己的Cloud ALM集成。

许可很简单。[SAP的使用权页面](https://support.sap.com/en/alm/usage-rights.html)为拥有SAP Enterprise Support、Enterprise Support cloud editions或Product Support for Large Enterprises的客户提供一个租户。用途仅限于客户自己内部的应用生命周期管理。

### SAP Solution Manager

在许多本地部署系统环境中，Solution Manager 7.2仍在承担测试管理。在Enterprise Support下，它的范围包括Business Process Change Analyzer（把测试范围缩小到变更所涉及的流程）以及SAP的测试自动化功能。

日期比功能更重要。[SAP的Solution Manager页面](https://support.sap.com/en/alm/solution-manager.html)给出的主流维护截止于2027年底。部分功能（包括测试套件）可以选择延长维护至2030年底，SAP建议在2027年底之前迁移到Cloud ALM。

不要在新项目中为了测试而引入Solution Manager。如果它已经在负责您的变更控制，就一直用到系统环境迁移，然后把测试文档作为迁移的一部分一并迁移。

### 手工测试工具

搜索SAP手工测试工具的人，通常需要的是测试管理，而不是一个单独的产品。Cloud ALM、Solution Manager、Panaya Test Management和UiPath Test Manager都能记录带步骤、结果和缺陷的手工测试执行情况。

它们取代的是电子表格。电子表格与传输没有关联，没有审计轨迹，下一个周期一开始，历史记录也就没了。

## 测试自动化工具：Tricentis、Worksoft、Panaya和UiPath

这四款工具都能自动化SAP GUI和Fiori业务流程。区别在于测试如何构建、附带了什么，以及它们如何与您的测试管理工具连接。

### Tricentis与SAP Test Automation by Tricentis

[SAP Test Automation by Tricentis](https://www.sap.com/products/technology-platform/test-automation.html)是SAP转售的、基于云的Tricentis产品。SAP把它描述为跨SAP和第三方应用、基于模型的无代码自动化，并与Cloud ALM集成。SAP还转售SAP Enterprise Continuous Testing by Tricentis，Tricentis称之为Tosca。

购买之前先核对您的授权。SAP的使用权页面为Enterprise Support客户提供一份与Cloud ALM集成的Tricentis Test Automation for SAP定期许可，有效期至2028年12月31日。它的上限是5个指定用户、每月500次测试运行、5个执行代理和12个月的结果保留，所以它是一个起点，而不是项目规模的许可。

另有一份单独的许可，涵盖与Solution Manager集成的Tricentis Test Automation for SAP，有效期至2027年12月31日。请阅读该页面上与您的支持类型对应的两个条目。

### Worksoft

Worksoft Certify是一款无代码自动化产品，用于测试、测试数据准备和数据更正。Worksoft的平台还包括Business Capture（把真实的用户活动录制下来作为测试的基础），以及一款用于变更分析的Impact产品。

Worksoft列出了与SAP Cloud ALM和Solution Manager的集成，并已在SAP Store上架。它适合希望由业务流程专家而不是开发人员来掌管测试库的团队。

### Panaya

Panaya的产品线包括Change Impact Analysis、Test Management、Test Automation和Custom Code Correction。它的出发点是每次升级都会提出的问题：这次变更涉及了什么，我需要重新测试什么？

这让它适合升级、支持包和S/4HANA转换，在这些场景中，自定义代码和影响范围主导着工作。Panaya的Cloud ALM集成目前涵盖其无代码自动化产品中的自动化测试。

### UiPath Test Suite

UiPath Test Manager负责规划、编排和报告测试运行，由UiPath机器人执行。UiPath列出了对S/4HANA、ECC、Fiori、WinGUI、WebGUI和Business Client的支持，以及一项SAP Cloud ALM集成。

UiPath的文档还介绍了一项Solution Manager集成，需要Solution Manager 7.2 SP08或更高版本。选择UiPath的实际理由是复用：如果您的公司已经在用UiPath做流程自动化，您的技能和许可都可以延续。

### 自动化什么时候值得做

我的原则很简单。测试用例数量大、需要大量反复测试时，就做自动化。达不到这个程度，手工测试就可以，而一个建了一半的自动化库，花费会比它省下的更多。

反复测试，说的就是回归测试。我的[SAP测试自动化](/zh-CN/sap-test-automation-guide/)指南讲了从哪里入手，[SAP回归测试](/zh-CN/sap-regression-testing/)讲了升级周期和版本范围。

## 性能测试工具：OpenText LoadRunner

功能自动化告诉您一个流程对一个用户是可用的。它不会告诉您月末数百个用户同时过账时会发生什么。性能测试必须在上线前完成，而并发测试，也就是大量用户同时操作的测试，才是要紧的。

LoadRunner现在是OpenText的产品。[OpenText的LoadRunner Professional页面](https://www.opentext.com/products/loadrunner-professional)现在称它为OpenText Professional Performance Engineering。它的协议列表包括SAP、SAP GUI和SAP Web。

OpenText Enterprise Performance Engineering服务于同时在多个地点运行测试的团队，OpenText Core Performance Engineering则是云端产品。SAP也转售Tricentis的性能测试产品。我的[SAP性能测试](/zh-CN/sap-performance-testing-it-leaders/)指南讲了如何设计这些测试。

## 如何选择SAP测试工具

按这个顺序选择工具：先测试管理，再自动化，最后性能测试。可追溯性和审计都在测试管理中，而且它决定了哪些自动化集成容易实现。

1. **核对您已经拥有什么**。Cloud ALM和有上限的Tricentis许可随Enterprise Support提供。Solution Manager随本地部署维护提供。
2. **选定测试管理平台**。新项目和RISE用Cloud ALM。只有在Solution Manager已经负责变更控制的地方才用它，并在2028年之前制定迁移计划。
3. **数一数您要反复运行的测试用例**。如果回归测试量很小，就在测试管理工具中手工测试，暂时不做自动化。
4. **按契合度筛选自动化工具**。SAP与非SAP混合的系统环境、变更影响分析的需要、已有的UiPath资产，以及由业务用户掌管测试，各自指向上表中不同的工具。
5. **用您自己的流程做试点**。用一个真实的业务流程，配上您自己的数据和界面，而不是厂商的演示系统。
6. **加上一款性能测试工具**。为月结这样的高峰期规划并发测试。

下面这些问题能把真正合适的工具和演示效果好的工具区分开。

| 因素 | 要问的问题 |
|---|---|
| SAP覆盖范围 | 它原生支持驱动哪些SAP GUI、Fiori和API技术？ |
| 集成 | 它与Cloud ALM或Solution Manager的连接方式，是否符合您的测试经理的工作方式？ |
| 变更影响 | 它能否告诉您一次传输或升级会影响哪些测试？ |
| 维护 | 版本发布后由谁来修复出错的测试，需要多长时间？ |
| 掌管权 | 功能顾问和关键用户能否构建和读懂测试？ |
| 第二年成本 | 第一年之后，代理、用户和维护要花多少钱？ |

## 工具不是全部答案

我见得最多的测试失败，不是工具问题，而是系统集成测试和用户验收测试做得不够。如果计划给这些周期的时间太少，工具也无济于事。

有两项做法比买哪款产品更重要。测试数据应该经过脱敏，但要达到生产水平，数据量要接近真实。在项目期间，运行两套独立的环境，一套给项目，一套给日常运营，让线上支持变更和项目变更分开测试。

云版本发布还要多考虑一点。SAP Cloud ERP公有版每年有两次大升级，在2月和8月，客户在升级后的测试系统中运行回归测试。SAP的Test Automation Tool就是为这项工作提供的。

要把测试结果与上线决策联系起来，请看我关于[SAP质量关口](/zh-CN/sap-quality-gates-implementation/)的文章。

## 常见问题

<details>
<summary>主要的SAP测试工具有哪些？</summary>

测试管理方面，有SAP Cloud ALM和SAP Solution Manager。测试自动化方面，有Tricentis Tosca（也以SAP Test Automation by Tricentis之名销售）、Worksoft Certify、Panaya和UiPath。性能测试方面，有OpenText LoadRunner，现以OpenText Professional Performance Engineering和Enterprise Performance Engineering之名销售。

</details>

<details>
<summary>SAP Enterprise Support包含Tricentis吗？</summary>

部分包含：SAP为Enterprise Support客户提供一份与SAP Cloud ALM集成的Tricentis Test Automation for SAP定期许可，有效期至2028年12月31日。它的上限是5个指定用户、每月500次测试运行和5个执行代理。较大的项目通常需要完整的Tricentis产品，SAP也转售这些产品。

</details>

<details>
<summary>测试应该用SAP Cloud ALM还是Solution Manager？</summary>

任何新项目都用Cloud ALM。它涵盖测试准备、测试计划、执行和缺陷，而且Enterprise Support包含一个租户。Solution Manager的主流维护于2027年底结束，所以只在它已经负责变更控制的地方保留它，并规划好迁移。

</details>

<details>
<summary>SAP手工测试最好的工具是什么？</summary>

您的测试管理工具。Cloud ALM、Solution Manager、Panaya和UiPath Test Manager都能记录手工测试的步骤、结果和缺陷。把手工测试从电子表格中搬出来，您就有了审计轨迹以及与变更的关联。

</details>

<details>
<summary>什么时候应该对SAP测试做自动化？</summary>

当测试用例数量大、需要大量反复测试时，例如跨升级和版本发布的回归测试。达不到这个程度，手工测试就可以。把一小套不稳定的测试自动化，维护成本通常比它省下的更多。

</details>

<details>
<summary>SAP性能测试用什么工具？</summary>

OpenText LoadRunner是常见的选择，支持SAP、SAP GUI和SAP Web协议。SAP也转售Tricentis的性能测试产品。无论用哪一款，都要在上线前用大量同时在线的用户运行并发测试。

</details>

主要的 SAP 測試工具包括：用於測試管理的 SAP Cloud ALM 與 SAP Solution Manager；用於測試自動化的 Tricentis Tosca（SAP 以 SAP Test Automation by Tricentis 之名銷售）、Worksoft、Panaya 與 UiPath；以及用於效能測試的 OpenText LoadRunner。大多數 S/4HANA 專案每一類各需要一種工具：一種用來管理與追溯測試，一種用來自動化迴歸測試，一種用來測試負載。

這七種工具我都用過，或讓我的團隊用過。本指南比較每一種的用途（已於 2026 年 10 月對照供應商文件查證），以及如何在它們之間做選擇。關於測試類型本身，請先閱讀 [SAP 測試全解析](/zh-TW/sap-testing-explained/)。

我看過幾十場工具展示，每一樣東西都運作得完美無缺。然後到了真正的專案，腳本不停壞掉，或整合從來不像供應商展示的那樣運作。這就是為什麼我不靠功能檢查清單來挑選 SAP 測試工具。

## SAP 測試工具組要完成的三項工作

在我主導的專案中，測試約占工作量的 35%。工具決定了這些工作中有多少可以重複執行。

這些工具分成三類。不要期待某一類的工具去做另一類的工作。

1. **測試管理。** 保存測試案例、測試計畫、執行結果與缺陷，並把它們連結到需求與變更。這是手動測試進行的地方，也是稽核人員查看的地方。SAP Cloud ALM、SAP Solution Manager 與 Panaya Test Management 屬於這一類。
2. **功能測試自動化。** 錄製或建模業務流程測試，並在每次變更後重新執行。Tricentis、Worksoft、Panaya Test Automation 與 UiPath 屬於這一類。
3. **效能測試。** 模擬大量使用者同時作業，在上線前找出瓶頸。OpenText LoadRunner 屬於這一類，SAP 也轉售 Tricentis 的效能測試產品。

有幾家供應商橫跨兩類，而且界線會隨每次版本更新而移動。先決定您要為哪一項工作採購，再在該類別內比較工具。

## SAP 測試工具比較

下表整理這七種工具。每一列都已對照供應商自己的頁面或 SAP 支援入口網站查證。

| 工具 | 供應商 | 主要工作 | 用途 | 適用情境 |
|---|---|---|---|---|
| SAP Cloud ALM | SAP | 測試管理 | 測試案例、測試計畫、手動執行、缺陷，以及與流程和需求的追溯關係 | 新 S/4HANA 與 RISE 專案的預設選擇；Enterprise Support 包含一個租用戶 |
| SAP Solution Manager 7.2 | SAP | 測試管理 | Test Suite、Business Process Change Analyzer、與變更管控的連結 | 已在使用它的現有地端系統環境；主流維護於 2027 年結束 |
| Tricentis Tosca / SAP Test Automation by Tricentis | Tricentis，由 SAP 轉售 | 自動化 | 跨 SAP 與非 SAP 應用程式的模型式、無程式碼自動化 | 版本更新頻繁、系統環境混合的專案 |
| Worksoft Certify | Worksoft | 自動化 | 無程式碼流程自動化，另有流程擷取與影響分析 | 流程密集、希望由業務使用者建置測試的系統環境 |
| Panaya | Panaya | 影響分析、測試管理、自動化 | 變更影響分析、測試管理與 AI 輔助自動化 | 升級與變更頻繁、需要知道該重新測試什麼的專案 |
| UiPath Test Manager（UiPath Test Suite） | UiPath | 自動化與測試管理 | 以 UiPath 機器人跨 SAP GUI、Fiori 與非 SAP 系統協調測試 | 已在使用 UiPath 做流程自動化的公司 |
| OpenText LoadRunner | OpenText | 效能 | 使用 SAP、SAP GUI 與 SAP Web 協定的負載與並行測試 | 上線前的尖峰資料量與並行測試 |

這些工具沒有一個是糟糕的選擇。它們的差別在於做法、授權方式，以及您的團隊已經熟悉什麼。

## 測試管理：Cloud ALM 與 Solution Manager

### SAP Cloud ALM

Cloud ALM 涵蓋測試準備、測試計畫、測試執行與缺陷。根據 [SAP 的 Cloud ALM 測試訓練課程](https://learning.sap.com/courses/implementing-with-sap-cloud-alm/planning-and-executing-testing_ef46a49b-9885-4aaa-841d-5ac9c80a3681)，測試案例從解決方案流程活動建立，測試人員逐步記錄通過或失敗，缺陷則直接從失敗的執行中提出。這讓您擁有從流程到測試再到缺陷的追溯能力。

在自動化方面，它負責協調而不是執行。SAP 列出兩項已整合的工具：SAP S/4HANA Cloud Test Automation Tool 與 Tricentis Test Automation for SAP。Worksoft、Panaya 與 UiPath 也各自發布了自己的 Cloud ALM 整合。

授權很單純。[SAP 的使用權頁面](https://support.sap.com/en/alm/usage-rights.html) 授予擁有 SAP Enterprise Support、Enterprise Support cloud editions 或 Product Support for Large Enterprises 的客戶一個租用戶。使用範圍僅限於客戶自己內部的應用程式生命週期管理。

### SAP Solution Manager

許多地端系統環境仍以 Solution Manager 7.2 執行測試管理。在 Enterprise Support 下，它的範圍包括 Business Process Change Analyzer（能把測試範圍縮小到變更所觸及的流程），以及 SAP 的測試自動化功能。

日期比功能更重要。[SAP 的 Solution Manager 頁面](https://support.sap.com/en/alm/solution-manager.html) 提供至 2027 年底的主流維護。部分功能（包括測試套件）可選擇延長維護至 2030 年底，而 SAP 建議在 2027 年底之前移轉到 Cloud ALM。

不要在新專案中為了測試而導入 Solution Manager。如果它已經在處理您的變更管控，就沿用到系統環境移轉為止，再把測試文件的移轉納入那次移轉之中。

### 手動測試工具

搜尋 SAP 手動測試工具的人，通常需要的是測試管理，而不是另一套產品。Cloud ALM、Solution Manager、Panaya Test Management 與 UiPath Test Manager 都能記錄手動測試的執行步驟、結果與缺陷。

它們取代的是試算表。試算表與傳輸之間沒有連結、沒有稽核軌跡，下一個週期一開始也就沒有歷史紀錄。

## 測試自動化工具：Tricentis、Worksoft、Panaya 與 UiPath

這四種工具都能自動化 SAP GUI 與 Fiori 業務流程。差別在於測試的建置方式、附帶的功能，以及如何連接到您的測試管理工具。

### Tricentis 與 SAP Test Automation by Tricentis

[SAP Test Automation by Tricentis](https://www.sap.com/products/technology-platform/test-automation.html) 是 SAP 轉售的雲端 Tricentis 產品。SAP 將它描述為跨 SAP 與第三方應用程式的無程式碼、模型式自動化，並與 Cloud ALM 整合。SAP 也轉售 SAP Enterprise Continuous Testing by Tricentis，Tricentis 表示這就是 Tosca。

購買之前先確認您的授權權益。SAP 的使用權頁面授予 Enterprise Support 客戶一份與 Cloud ALM 整合的 Tricentis Test Automation for SAP 定期授權，效期至 2028 年 12 月 31 日。它的上限是 5 位具名使用者、每月 500 次測試執行、5 個執行代理程式與 12 個月的結果保存期，所以它是一個起點，而不是專案規模的授權。

另一份授權涵蓋與 Solution Manager 整合的 Tricentis Test Automation for SAP，效期至 2027 年 12 月 31 日。請依您的支援類型閱讀頁面上的兩個項目。

### Worksoft

Worksoft Certify 是一套用於測試、測試資料準備與資料修正的無程式碼自動化產品。Worksoft 的平台也包含 Business Capture（記錄真實使用者活動作為測試基礎），以及一項用於變更分析的 Impact 產品。

Worksoft 列出與 SAP Cloud ALM 及 Solution Manager 的整合，並在 SAP Store 上架。它適合希望由業務流程專家（而不是開發人員）負責測試庫的團隊。

### Panaya

Panaya 的產品線涵蓋 Change Impact Analysis、Test Management、Test Automation 與 Custom Code Correction。它的出發點是每次升級都會引出的問題：這次變更觸及了什麼，我需要重新測試什麼？

這讓它適合由客製程式碼與影響範圍主導工作的升級、支援套件與 S/4HANA 轉換。Panaya 的 Cloud ALM 整合目前涵蓋其無程式碼自動化產品所產生的自動化測試。

### UiPath Test Suite

UiPath Test Manager 負責規劃、協調與報告測試執行，再由 UiPath 機器人執行。UiPath 列出對 S/4HANA、ECC、Fiori、WinGUI、WebGUI 與 Business Client 的支援，以及一項 SAP Cloud ALM 整合。

UiPath 的文件也說明了一項 Solution Manager 整合，需要 Solution Manager 7.2 SP08 或更新版本。選擇 UiPath 的實際理由是重複利用：如果您的公司已經在用 UiPath 做流程自動化，您的技能與授權都能延續使用。

### 自動化何時能回本

我的原則很簡單。當測試案例數量很多，而且需要大量重複測試時，就自動化。低於這個程度，手動測試就夠了，而一套建到一半的自動化測試庫，成本會高於它省下的錢。

重複測試正是迴歸測試的本質。我的 [SAP 測試自動化](/zh-TW/sap-test-automation-guide/) 指南說明從哪裡開始，[SAP 迴歸測試](/zh-TW/sap-regression-testing/) 則說明升級週期與版本範圍。

## 效能測試工具：OpenText LoadRunner

功能自動化告訴您一個流程對單一使用者可行。它不會告訴您月結時數百位使用者同時過帳會發生什麼事。效能測試必須在上線前完成，而並行測試（大量使用者同時作業）才是重要的那一種。

LoadRunner 現在是 OpenText 的產品。[OpenText 的 LoadRunner Professional 頁面](https://www.opentext.com/products/loadrunner-professional) 現在稱它為 OpenText Professional Performance Engineering。它的協定清單包括 SAP、SAP GUI 與 SAP Web。

OpenText Enterprise Performance Engineering 服務在多個地點同時執行測試的團隊，OpenText Core Performance Engineering 則是雲端版本。SAP 也轉售 Tricentis 的效能測試產品。我的 [SAP 效能測試](/zh-TW/sap-performance-testing-it-leaders/) 指南說明如何設計這些測試。

## 如何選擇 SAP 測試工具

依照這個順序選擇工具：先選測試管理，再選自動化，最後選效能測試。追溯能力與稽核都在測試管理中，而且它決定了哪些自動化整合容易做到。

1. **確認您已經擁有什麼。** Cloud ALM 與有上限的 Tricentis 授權隨 Enterprise Support 提供。Solution Manager 隨地端維護提供。
2. **挑選測試管理平台。** 新專案與 RISE 用 Cloud ALM。只有在 Solution Manager 已經處理變更管控時才用它，並在 2028 年之前訂好移轉計畫。
3. **計算您需要重複執行的測試案例。** 如果迴歸測試量很小，就在測試管理工具中手動測試，暫時跳過自動化。
4. **依契合度列出自動化候選名單。** SAP 與非 SAP 混合的系統環境、變更影響分析需求、既有的 UiPath 部署，以及由業務使用者負責，各自指向上表中不同的工具。
5. **在您自己的流程上進行試點。** 使用一條真實的業務流程，搭配您自己的資料與畫面，而不是供應商的展示系統。
6. **加入效能測試工具。** 為月結等尖峰期間規劃並行測試。

這些問題能區分真正適合的工具與只是展示得好看的工具。

| 因素 | 要問的問題 |
|---|---|
| SAP 支援範圍 | 它能原生驅動哪些 SAP GUI、Fiori 與 API 技術？ |
| 整合 | 它與 Cloud ALM 或 Solution Manager 的連接方式，是否符合您測試經理的工作方式？ |
| 變更影響 | 它能否告訴您一筆傳輸或一次升級影響了哪些測試？ |
| 維護 | 版本更新後由誰修正壞掉的測試，需要多久？ |
| 負責歸屬 | 功能顧問與關鍵使用者能否建置與閱讀測試？ |
| 第二年成本 | 第一年之後，代理程式、使用者與維護的成本是多少？ |

## 工具不是全部的答案

我最常看到的測試失敗不是工具問題。而是系統整合測試與使用者驗收測試的測試量不足。工具無法修正一份給這些週期太少時間的計畫。

有兩項做法比您買哪一套產品更重要。測試資料應該經過遮罩但達到正式環境等級，具備貼近真實的資料量。專案期間，維持兩套獨立的環境，一套給專案，一套給日常維運，讓正式環境維運變更與專案變更分開測試。

雲端版本更新還多了一項考量。SAP Cloud ERP public edition 每年有兩次主要升級，分別在 2 月與 8 月，客戶要在升級後的測試系統中執行迴歸測試。SAP 的 Test Automation Tool 已包含在內，可用於這項工作。

若要把測試結果連結到上線決策，請參閱我關於 [SAP 品質關卡](/zh-TW/sap-quality-gates-implementation/) 的文章。

</details>

</details>

</details>

Las principales herramientas de pruebas SAP son SAP Cloud ALM y SAP Solution Manager para la gestión de pruebas; Tricentis Tosca (que SAP vende como SAP Test Automation by Tricentis), Worksoft, Panaya y UiPath para la automatización de pruebas; y OpenText LoadRunner para las pruebas de rendimiento. La mayoría de los programas S/4HANA necesitan una herramienta de cada grupo: una para gestionar y trazar las pruebas, otra para automatizar la regresión y otra para probar la carga.

He usado, o mis equipos han usado, las siete. Esta guía compara para qué sirve cada una, contrastado con la documentación de los proveedores en octubre de 2026, y cómo elegir entre ellas. Para los tipos de prueba en sí, empiece por las [pruebas SAP explicadas](/es/sap-testing-explained/).

He asistido a decenas de demostraciones de herramientas en las que todo funciona a la perfección. Luego, en el proyecto real, los scripts se rompen una y otra vez, o la integración nunca funciona como la mostró el proveedor. Por eso no elijo las herramientas de pruebas SAP a partir de listas de funcionalidades.

## Los tres trabajos de un conjunto de herramientas de pruebas SAP

En los programas que dirijo, las pruebas consumen cerca del 35 por ciento del esfuerzo. Las herramientas deciden qué parte de ese esfuerzo se puede repetir.

Se dividen en tres grupos. No espere que una herramienta de un grupo haga el trabajo de otro.

1. **Gestión de pruebas.** Guarda los casos de prueba, los planes de prueba, los resultados de ejecución y los defectos, y los vincula con los requisitos y los cambios. Aquí es donde ocurren las pruebas manuales y donde miran los auditores. SAP Cloud ALM, SAP Solution Manager y Panaya Test Management pertenecen a este grupo.
2. **Automatización de pruebas funcionales.** Graba o modela pruebas de procesos de negocio y las vuelve a ejecutar después de cada cambio. Tricentis, Worksoft, Panaya Test Automation y UiPath pertenecen a este grupo.
3. **Pruebas de rendimiento.** Simulan muchos usuarios a la vez para encontrar cuellos de botella antes del go-live. OpenText LoadRunner pertenece a este grupo, y SAP también revende productos de rendimiento de Tricentis.

Varios proveedores abarcan dos grupos, y los límites se mueven con cada versión. Decida primero para qué trabajo compra y después compare las herramientas dentro de ese grupo.

Ninguna de estas herramientas es una mala elección. Se diferencian en el enfoque, en el licenciamiento y en lo que su equipo ya conoce.

## Gestión de pruebas: Cloud ALM y Solution Manager

### SAP Cloud ALM

Cloud ALM cubre la preparación de pruebas, los planes de prueba, la ejecución de pruebas y los defectos. Según la [formación de SAP sobre pruebas en Cloud ALM](https://learning.sap.com/courses/implementing-with-sap-cloud-alm/planning-and-executing-testing_ef46a49b-9885-4aaa-841d-5ac9c80a3681), los casos de prueba se construyen a partir de las actividades de los procesos de la solución, los probadores registran superado o fallido en cada paso y los defectos se abren directamente desde las ejecuciones fallidas. Eso le da trazabilidad del proceso a la prueba y de la prueba al defecto.

En la automatización, orquesta en lugar de ejecutar. SAP nombra dos herramientas integradas: la SAP S/4HANA Cloud Test Automation Tool y Tricentis Test Automation for SAP. Worksoft, Panaya y UiPath publican cada uno sus propias integraciones con Cloud ALM.

El licenciamiento es sencillo. La [página de derechos de uso de SAP](https://support.sap.com/en/alm/usage-rights.html) concede un tenant a los clientes con SAP Enterprise Support, Enterprise Support cloud editions o Product Support for Large Enterprises. El uso se limita a la gestión interna del ciclo de vida de las aplicaciones del propio cliente.

### SAP Solution Manager

Solution Manager 7.2 sigue gestionando las pruebas en muchos entornos on-premise. Con Enterprise Support, su alcance incluye el Business Process Change Analyzer, que reduce el alcance de las pruebas a los procesos que toca un cambio, y las funciones de automatización de pruebas de SAP.

La fecha importa más que las funciones. La [página de Solution Manager de SAP](https://support.sap.com/en/alm/solution-manager.html) fija el mantenimiento estándar hasta finales de 2027. El mantenimiento extendido hasta finales de 2030 es una opción para algunas funciones, entre ellas el test suite, y SAP recomienda pasar a Cloud ALM antes de finales de 2027.

No introduzca Solution Manager para las pruebas en un programa nuevo. Si ya gestiona su control de cambios, consérvelo hasta que el entorno cambie y migre entonces la documentación de pruebas como parte de ese cambio.

### Herramientas de pruebas manuales

Quien busca herramientas de pruebas manuales para SAP suele necesitar gestión de pruebas, no un producto aparte. Cloud ALM, Solution Manager, Panaya Test Management y UiPath Test Manager registran la ejecución de pruebas manuales con pasos, resultados y defectos.

Lo que sustituyen es la hoja de cálculo. Una hoja de cálculo no tiene vínculo con el transporte, ni pista de auditoría, ni historial una vez que empieza el ciclo siguiente.

## Herramientas de automatización de pruebas: Tricentis, Worksoft, Panaya y UiPath

Las cuatro automatizan procesos de negocio en SAP GUI y Fiori. Las diferencias están en cómo se construyen las pruebas, qué incluyen y cómo se conectan con su herramienta de gestión de pruebas.

### Tricentis y SAP Test Automation by Tricentis

[SAP Test Automation by Tricentis](https://www.sap.com/products/technology-platform/test-automation.html) es el producto de Tricentis en la nube que SAP revende. SAP lo describe como automatización sin código y basada en modelos para aplicaciones SAP y de terceros, integrada con Cloud ALM. SAP también revende SAP Enterprise Continuous Testing by Tricentis, que Tricentis identifica como Tosca.

Revise su derecho de uso antes de comprar. La página de derechos de uso de SAP concede a los clientes de Enterprise Support una licencia temporal de Tricentis Test Automation for SAP integrada con Cloud ALM hasta el 31 de diciembre de 2028. Está limitada a 5 usuarios nominales, 500 ejecuciones de prueba al mes, 5 agentes de ejecución y 12 meses de conservación de resultados, así que es un punto de partida y no una licencia a escala de programa.

Una licencia aparte cubre Tricentis Test Automation for SAP integrada con Solution Manager, hasta el 31 de diciembre de 2027. Lea ambas entradas de la página para su tipo de soporte.

### Worksoft

Worksoft Certify es un producto de automatización sin código para pruebas, aprovisionamiento de datos de prueba y correcciones de datos. La plataforma de Worksoft incluye además Business Capture, que graba la actividad real de los usuarios como base para las pruebas, y un producto Impact para el análisis de cambios.

Worksoft incluye integraciones con SAP Cloud ALM y Solution Manager y está disponible en SAP Store. Encaja con equipos que quieren que la biblioteca de pruebas sea responsabilidad de expertos en procesos de negocio, no de desarrolladores.

### Panaya

La oferta de Panaya abarca Change Impact Analysis, Test Management, Test Automation y Custom Code Correction. Su punto de partida es la pregunta que plantea cada actualización: ¿qué ha tocado este cambio y qué tengo que volver a probar?

Eso la hace adecuada para actualizaciones, support packs y conversiones a S/4HANA en las que el código a medida y el alcance del impacto marcan el trabajo. La integración de Panaya con Cloud ALM cubre actualmente las pruebas automatizadas de su producto de automatización sin código.

### UiPath Test Suite

UiPath Test Manager planifica, orquesta e informa sobre las ejecuciones de prueba, y los robots de UiPath las ejecutan. UiPath indica cobertura para S/4HANA, ECC, Fiori, WinGUI, WebGUI y Business Client, además de una integración con SAP Cloud ALM.

La documentación de UiPath describe también una integración con Solution Manager, que requiere Solution Manager 7.2 SP08 o posterior. El argumento práctico a favor de UiPath es la reutilización: si su empresa ya usa UiPath para la automatización de procesos, sus conocimientos y licencias se aprovechan.

### Cuándo compensa la automatización

Mi regla es sencilla. Cuando hay un gran número de casos de prueba que exigen pruebas extensas y repetidas, automatice. Por debajo de eso, las pruebas manuales están bien, y una biblioteca de automatización a medio construir cuesta más de lo que ahorra.

Las pruebas repetidas son precisamente la regresión. Mi guía de [automatización de pruebas SAP](/es/sap-test-automation-guide/) trata por dónde empezar, y la de [pruebas de regresión en SAP](/es/sap-regression-testing/) trata los ciclos de actualización y el alcance de las versiones.

## Herramientas de pruebas de rendimiento: OpenText LoadRunner

La automatización funcional le dice que un proceso funciona para un usuario. No le dice qué ocurre cuando cientos de usuarios contabilizan en el cierre mensual. Las pruebas de rendimiento tienen que hacerse antes del go-live, y las de concurrencia, con muchos usuarios a la vez, son las que importan.

LoadRunner es ahora un producto de OpenText. La [página de OpenText sobre LoadRunner Professional](https://www.opentext.com/products/loadrunner-professional) lo denomina ahora OpenText Professional Performance Engineering. Su lista de protocolos incluye SAP, SAP GUI y SAP Web.

OpenText Enterprise Performance Engineering está pensado para equipos que ejecutan pruebas en varias ubicaciones a la vez, y OpenText Core Performance Engineering es la oferta en la nube. SAP también revende productos de pruebas de rendimiento de Tricentis. Mi guía de [pruebas de rendimiento en SAP](/es/sap-performance-testing-it-leaders/) explica cómo diseñar esas pruebas.

## Cómo elegir herramientas de pruebas SAP

Elija las herramientas en este orden: primero la gestión de pruebas, después la automatización y por último el rendimiento. La gestión de pruebas es donde residen la trazabilidad y la auditoría, y decide qué integraciones de automatización resultan sencillas.

1. **Compruebe lo que ya tiene.** Cloud ALM y la licencia limitada de Tricentis vienen con Enterprise Support. Solution Manager viene con el mantenimiento on-premise.
2. **Elija la plataforma de gestión de pruebas.** Cloud ALM para los programas nuevos y RISE. Solution Manager solo donde ya gestiona el control de cambios, con un plan de migración antes de 2028.
3. **Cuente sus casos de prueba repetidos.** Si el volumen de regresión es pequeño, pruebe manualmente en su herramienta de gestión de pruebas y deje la automatización para más adelante.
4. **Preseleccione la automatización según el encaje.** Los entornos mixtos SAP y no SAP, la necesidad de análisis de impacto, las instalaciones existentes de UiPath y la propiedad por parte de los usuarios de negocio apuntan cada uno a herramientas distintas de la tabla anterior.
5. **Haga un piloto con sus propios procesos.** Use un flujo de proceso de negocio real con sus propios datos y pantallas, no el sistema de demostración del proveedor.
6. **Añada una herramienta de rendimiento.** Planifique pruebas de concurrencia para los periodos pico, como el cierre mensual.

Estas preguntas distinguen un buen encaje de una buena demo.

| Factor | Pregunta que hacer |
|---|---|
| Cobertura de SAP | ¿Qué tecnologías de SAP GUI, Fiori y API maneja de forma nativa? |
| Integración | ¿Se conecta con Cloud ALM o Solution Manager de la forma en que trabaja su gestor de pruebas? |
| Impacto de cambios | ¿Puede decirle qué pruebas afecta un transporte o una actualización? |
| Mantenimiento | ¿Quién corrige las pruebas rotas después de una versión y cuánto tarda? |
| Propiedad | ¿Pueden los consultores funcionales y los usuarios clave construir y leer las pruebas? |
| Costo del segundo año | ¿Cuánto cuestan los agentes, los usuarios y el mantenimiento después del primer año? |

## Las herramientas no son toda la respuesta

El fallo de pruebas más frecuente que veo no es un problema de herramientas. Es probar demasiado poco en las pruebas de integración del sistema y en las pruebas de aceptación del usuario. Ninguna herramienta puede arreglar un plan que da a esos ciclos demasiado poco tiempo.

Dos prácticas importan más que el producto que compre. Los datos de prueba deben estar enmascarados pero a nivel de producción, con volúmenes realistas. Durante un programa, mantenga dos entornos separados, uno para el proyecto y otro para la operación diaria, de modo que los cambios del soporte en vivo y los del proyecto se prueben por separado.

Las versiones en la nube añaden una consideración más. SAP Cloud ERP public edition recibe dos grandes actualizaciones al año, en febrero y agosto, y los clientes ejecutan las pruebas de regresión en el sistema de pruebas actualizado. La Test Automation Tool de SAP está incluida para ese trabajo.

Para vincular los resultados de las pruebas con las decisiones de go-live, lea mi artículo sobre [quality gates en SAP](/es/sap-quality-gates-implementation/).

Coloque las siete herramientas frente a los tres trabajos y marque lo que ya incluye su contrato de soporte de SAP. Después, preseleccione solo para cubrir los huecos y pida demos con sus propios procesos.

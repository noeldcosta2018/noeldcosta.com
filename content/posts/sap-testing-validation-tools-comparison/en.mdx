For most SAP programmes in 2026, the toolset is SAP Cloud ALM for test management and traceability, a Tricentis product for automation, and a separate tool for performance testing. Cloud ALM carries no licence fee for customers with SAP Enterprise Support or a cloud subscription, and Enterprise Support now includes an entry-level Tricentis automation licence. Xray fits when delivery already runs in Jira. Solution Manager only makes sense where it is already configured, because its mainstream maintenance ends in 2027. This guide is for test leads, programme managers and QA owners choosing tools for an S/4HANA programme. Check what your support contract already entitles you to before you buy anything.

I have sat through dozens of tool demos where everything works perfectly. Then in the real project the scripts keep breaking, or the integration never works the way the vendor showed. That is why I do not pick SAP testing tools from feature checklists. I pick them from release cadence, deployment model and audit posture.

## What you are actually testing

SAP testing is a risk control, not a pre-go-live checkbox. It starts in Realize and continues for as long as the system changes. Five layers matter, and none substitutes for another:

1. **Unit testing**: developers confirm individual programs and functions behave as expected
2. **Integration testing**: a sales order moves into delivery and billing, and each handoff posts correctly
3. **Regression testing**: in an integrated system, small changes break unrelated areas
4. **User acceptance testing**: finance and operations confirm the system handles real scenarios
5. **Performance testing**: the system stays responsive at peak volume, which no functional script will tell you

<explainer-layers title="Five layers of SAP testing" caption="None of them substitutes for another. Performance is the layer functional scripts never cover." layers="Performance => Responsive at peak volume, in its own test cycle|User acceptance => Finance and operations confirm real scenarios|Regression => Small changes break unrelated areas, so retest them|Integration => Each handoff in a flow posts correctly|Unit => Programs and functions behave as expected" tones="accent||||"></explainer-layers>

Automation pays off on frequent regression cycles, large data or interface checks, and predictable flows after each transport. It does not replace judgement. A script will not notice that a screen confuses users or that a workflow makes no practical sense.

Test what the business needs to protect. Month-end close, revenue-critical processes and anything rolled out across many sites come first. Full coverage tied to nothing is not protection. My guide to [SAP performance testing](/sap-performance-testing-it-leaders/) covers the fifth layer in depth.

## The four tools

### SAP Cloud ALM

SAP's lifecycle management platform links requirements, test plans, test execution and defects to SAP Activate phases and to changes. Customers with Enterprise Support, Product Support for Large Enterprises, or a cloud subscription that includes the "SAP Enterprise Support, cloud editions" service get one tenant with no licence fee. RISE and GROW contracts qualify.

SAP has also added AI to it. Joule-based assistants can draft requirements and generate test cases from documentation, and SAP positions a test management assistant for ECC to S/4HANA migrations that proposes risk-based test scope. Treat the output as a first draft for your test architect to review.

For any new S/4HANA programme, Cloud ALM is the default backbone for test documentation and traceability.

### Tricentis

[Tricentis Tosca](https://www.tricentis.com/products/automate-continuous-testing-tosca) uses model-based automation: you build reusable test components visually instead of writing scripts, which suits functional teams. It covers SAP GUI, Fiori and non-SAP applications in one test flow, which is its main advantage for testing whole business processes.

SAP and Tricentis have a close partnership. SAP resells Tosca-based products such as SAP Enterprise Continuous Testing by Tricentis, SAP Load Testing by Tricentis and SAP Change Impact Analysis by Tricentis. For budgets, the bigger news is in [SAP's usage rights](https://support.sap.com/en/alm/usage-rights.html). Enterprise Support customers get a term licence for Tricentis Test Automation for SAP integrated with Cloud ALM, currently to 31 December 2027. It is capped at 5 named users, 500 test runs a month and 5 execution agents, so treat it as a starting point rather than a programme-scale tool.

Where it struggles: highly dynamic web front ends raise maintenance effort, test data management at scale usually needs extra tooling, and a large module library needs governance from the start.

### Xray for Jira

[Xray](https://www.getxray.app/) was not built for SAP, but if your delivery runs in Jira it feels like a natural extension. Test cases sit next to user stories and change requests, so coverage becomes part of sprint planning. It supports Cucumber and Gherkin for behaviour-driven tests and plugs into CI pipelines.

Where it struggles: heavy SAP transactional testing such as batch jobs and deep integration chains, very large test repositories, and complex custom reports, which need add-ons or API work.

### SAP Solution Manager

Solution Manager links requirements, test plans, execution and transports in one place, and integrates with Change Request Management (ChaRM). Its Business Process Change Analyzer narrows test scope to the processes a change actually touches. In regulated environments that audit trail is still valuable.

Its weaknesses are a dated user experience, heavy set-up, automation (CBTA) that only covers SAP user interfaces, and a skill set few teams still have. Mainstream maintenance ends at the end of 2027, with extended maintenance to 2030 for selected functions. Do not bring it in for test management if you are not already using it for change control.

Other tools fit niches. Worksoft Certify is strong in validated environments such as pharmaceuticals. Katalon can help on lightweight, web-facing SAP projects. Neither is what I usually recommend for a core SAP test programme.

## How I pick between them

I separate testing into documentation and automation. They solve different problems, and teams that force both into one platform usually struggle.

For documentation and traceability, use Cloud ALM on a new programme. If Solution Manager already runs your change control, extend it until the landscape moves, then migrate. For automation, Tricentis is my usual recommendation for SAP-heavy landscapes with frequent releases. Once the models are stable, execution is consistent and maintenance falls compared with scripted automation. For agile teams building Fiori apps and APIs in Jira, Xray is often enough.

Before choosing, work through these questions with the people who will run the tests.

| Factor | Why it matters | Question to ask |
|---|---|---|
| SAP coverage | Tests must drive SAP GUI, Fiori and the interfaces you actually use | Which SAP UI technologies and APIs does it support natively? |
| Change impact | Knowing what to retest after a transport avoids over-testing and missed risk | Can it link a change to the tests it affects? |
| CI/CD integration | Automated runs need triggers from your pipeline | Does it work with your build and transport tooling? |
| Governance | Large programmes need reusable, versioned components | Can tests be modularised, versioned and reused across waves? |
| Business usability | Functional consultants and key users must review tests | Can non-developers create and read test cases? |
| Entitlements | Your support contract may already cover part of the need | What do Cloud ALM and the Tricentis entitlement already give us? |
| Total cost | Set-up, agents and maintenance outweigh the licence | What does year two cost, including model maintenance? |

## What real programmes taught me

**Global manufacturer: Tosca.** The company ran SAP ECC with a heavily customised warehouse system. Quarterly releases kept slipping on long manual regression cycles and defects leaking into production. The team piloted Tosca in inbound logistics and built a library of reusable steps over four weeks. Automated runs were linked to transport approvals, then extended to outbound logistics and production planning. Regression coverage of high-volume transactions rose from 35% to more than 85%, and post-go-live defects fell 40% within two quarters. I remember the pushback during rollout about automating such a custom environment. It stopped once the teams saw production incidents drop and the same models reused across plants.

**Retail company: Xray.** The company moved to S/4HANA alongside new Fiori apps and cloud integrations, and ran all IT delivery in Jira. Xray tied tests to user stories, let product owners follow progress without switching tools, and supported Gherkin acceptance criteria for the Fiori squads. Test evidence was ready for sprint reviews. It would not have handled heavy transactional or batch testing, but for agile Fiori, API and user-centric work it was enough without adding complexity.

**Financial services institution: Solution Manager.** A heavily customised landscape across finance, treasury and regulatory reporting faced audit pressure for full traceability. Testing lived in spreadsheets with no link to transports. Linking test plans to ChaRM change documents, time-stamping every execution and using the Business Process Change Analyzer to scope retests changed the conversation. The turning point came when auditors stopped asking for Excel files and validated test history directly in the system.

**Moving from Solution Manager to Cloud ALM.** Migrating test documentation is a project of its own. Do it when the landscape is moving anyway, for example as part of a RISE adoption, and not on its own.

## Practices that make testing work

Tools do not deliver quality on their own. These practices do, and they hold across tools.

| Practice | How to apply it |
|---|---|
| Start early | Involve test leads while requirements are written, so outcomes are testable |
| Test the process, not the transaction | Build flows that cross modules and include exceptions |
| Control test data | Use dedicated, resettable test clients; mask any production data |
| Make regression routine | Trigger automated runs with each transport, not only before cutover |
| Prioritise by risk | Critical and frequently changed processes first; aim for smart coverage, not 100% |
| Bring the business in | Key users validate test cases before execution starts |
| Link testing to change approvals | No transport moves without verified tests |
| Stay audit-ready | Record who tested what and when, in exportable form |

Track three numbers: defect leakage into production, the share of test cases reused rather than rewritten, and how long a full regression takes. They tell you where to put effort. My article on [SAP quality gates](/sap-quality-gates-implementation/) shows how to tie test results to go/no-go decisions.

## What changes in 2026

**Cloud ALM is the default.** New RISE and GROW programmes should make it the test backbone. Existing on-premise landscapes on Solution Manager have time, but not much: plan the move before 2028. Hybrid landscapes will run both for a while. Plan for the overlap.

**AI drafts tests.** Joule-based assistants in Cloud ALM generate test cases and requirements from documentation. The savings are in volume work such as regression scripts where variation is mostly data. Edge cases, complex integration logic and performance test design still need senior test architects.

**Clean core moves the target.** On public cloud there is no custom code in the core to regress. On private cloud and on-premise, custom ABAP in the core is the most expensive place to find a regression. You fix it, then revalidate it against the next SAP release. Side-by-side extensions on SAP BTP are versioned separately and need their own regression coverage.

**AI steps need new test patterns.** Deterministic regression scripts do not test non-deterministic AI behaviour. Expect a separate test class for Joule and agent-driven steps.

## Frequently asked questions

<details>
<summary>What is the best SAP testing tool for automation?</summary>

For SAP-heavy landscapes, Tricentis Tosca is the tool I most often recommend. Its model-based approach makes tests easier to build and maintain, and it covers SAP and non-SAP applications in one flow. If your team works in Jira and mainly builds Fiori apps in an agile model, Xray with a test framework may fit better. Context decides, not the demo.

</details>

<details>
<summary>Is Tricentis included with SAP Enterprise Support?</summary>

Partly. SAP grants a term licence for Tricentis Test Automation for SAP integrated with SAP Cloud ALM, currently until 31 December 2027. It covers customers with Enterprise Support (cloud editions or on-premise) or Product Support for Large Enterprises. It is limited to 5 named users, 500 test runs a month and 5 execution agents. Larger programmes usually need a full Tricentis product, which SAP also resells.

</details>

<details>
<summary>Can SAP Solution Manager handle test automation?</summary>

Only partly. Its Component-Based Test Automation (CBTA) covers SAP user interfaces but not non-SAP applications, and it needs significant maintenance as screens change. Solution Manager is mainly a test management and documentation platform. Most teams pair it with Tricentis or another automation tool, and with mainstream maintenance ending in 2027, new programmes should start on Cloud ALM instead.

</details>

<details>
<summary>Should I use SAP Cloud ALM or Solution Manager for testing in 2026?</summary>

Cloud ALM for any new programme, and for RISE and GROW in particular. It ties testing to SAP Activate phases and changes, and carries no licence fee with Enterprise Support. If an existing on-premise landscape already runs Solution Manager well, stay until the landscape moves, but plan the migration before 2028.

</details>

<details>
<summary>Do I need both a test management tool and an automation tool?</summary>

On most enterprise programmes, yes. Test management (Cloud ALM or Solution Manager) gives traceability from requirement to test to change, which auditors need. Automation (Tricentis or similar) runs regression cycles efficiently. One tool rarely does both well. For simpler environments, start with Cloud ALM and the included Tricentis entitlement, then add a full automation product when release volume justifies it.

</details>

<details>
<summary>How does SAP testing change with clean core?</summary>

Testing shifts from custom code inside the core to extensions around it. On public cloud there is no core custom code to regress. On private cloud and on-premise, any remaining core modifications need retesting after every SAP release. SAP BTP extensions have their own release cycle and need their own regression suite, and AI steps need test patterns that allow for non-deterministic output.

</details>

2026년 대부분의 SAP 프로그램에서 도구 구성은 이렇습니다. 테스트 관리와 추적성에는 SAP Cloud ALM, 자동화에는 Tricentis 제품, 성능 테스트에는 별도 도구. Cloud ALM은 SAP Enterprise Support 또는 클라우드 구독을 가진 고객에게 라이선스 비용이 없고, Enterprise Support에는 이제 입문 수준의 Tricentis 자동화 라이선스가 포함됩니다. 이미 Jira에서 구축을 운영한다면 Xray가 맞습니다. Solution Manager는 메인스트림 유지보수가 2027년에 끝나므로 이미 구성되어 있는 경우에만 의미가 있습니다. 이 가이드는 S/4HANA 프로그램의 도구를 고르는 테스트 리드, 프로그램 매니저, QA 책임자를 위한 것입니다. 무언가를 구매하기 전에 지원 계약이 이미 어떤 권한을 주는지 확인하십시오.

모든 것이 완벽하게 작동하는 도구 시연을 수십 번 지켜보았습니다. 그런데 실제 프로젝트에서는 스크립트가 계속 깨지거나, 연계가 벤더가 보여 준 대로 동작하지 않습니다. 그래서 저는 기능 체크리스트로 SAP 테스트 도구를 고르지 않습니다. 릴리스 주기, 배포 모델, 감사 대응 태세로 고릅니다.

## 실제로 무엇을 테스트하는가

SAP 테스트는 Go-Live 전에 체크하고 넘어가는 항목이 아니라 리스크 통제 수단입니다. Realize 단계에서 시작해 시스템이 바뀌는 동안 계속됩니다. 다섯 개 계층이 중요하며, 어느 것도 다른 것을 대신하지 못합니다.

1. **단위 테스트**: 개발자가 개별 프로그램과 기능이 기대대로 동작하는지 확인합니다
2. **통합 테스트**: 판매 오더가 납품과 청구로 넘어가고, 각 인계 단계가 올바르게 전기됩니다
3. **회귀 테스트**: 통합된 시스템에서는 작은 변경이 무관한 영역을 깨뜨립니다
4. **사용자 인수 테스트**: 재무와 운영 부서가 시스템이 실제 시나리오를 처리하는지 확인합니다
5. **성능 테스트**: 피크 물량에서도 시스템이 응답성을 유지하는지 보며, 어떤 기능 스크립트도 이를 알려 주지 못합니다

자동화는 빈번한 회귀 테스트 사이클, 대량 데이터나 인터페이스 점검, 트랜스포트 후마다 반복되는 예측 가능한 흐름에서 효과를 냅니다. 판단력을 대신하지는 못합니다. 스크립트는 화면이 사용자를 혼란스럽게 한다는 점이나 워크플로가 실무에서 말이 되지 않는다는 점을 알아채지 못합니다.

비즈니스가 지켜야 하는 것을 테스트하십시오. 월 마감, 매출에 직결되는 프로세스, 여러 사이트에 걸쳐 롤아웃되는 모든 것이 우선입니다. 아무것과도 연결되지 않은 전면 커버리지는 보호가 아닙니다. 제 [SAP 성능 테스트](/ko/sap-performance-testing-it-leaders/) 가이드에서 다섯 번째 계층을 깊이 다룹니다.

## 네 가지 도구

### SAP Cloud ALM

SAP의 라이프사이클 관리 플랫폼으로, 요구사항, 테스트 계획, 테스트 실행, 결함을 SAP Activate 단계와 변경에 연결합니다. Enterprise Support, Product Support for Large Enterprises, 또는 “SAP Enterprise Support, cloud editions” 서비스가 포함된 클라우드 구독을 가진 고객은 라이선스 비용 없이 테넌트 하나를 받습니다. RISE와 GROW 계약이 해당됩니다.

SAP는 여기에 AI도 추가했습니다. Joule 기반 어시스턴트가 문서에서 요구사항 초안을 작성하고 테스트 케이스를 생성할 수 있으며, SAP는 ECC에서 S/4HANA로의 마이그레이션을 위해 리스크 기반 테스트 범위를 제안하는 테스트 관리 어시스턴트를 내세웁니다. 결과물은 테스트 아키텍트가 검토할 초안으로 취급하십시오.

신규 S/4HANA 프로그램에서는 Cloud ALM이 테스트 문서화와 추적성의 기본 뼈대입니다.

### Tricentis

[Tricentis Tosca](https://www.tricentis.com/products/automate-continuous-testing-tosca)는 모델 기반 자동화를 사용합니다. 스크립트를 작성하는 대신 재사용 가능한 테스트 구성 요소를 시각적으로 구축하므로 기능 팀에 맞습니다. SAP GUI, Fiori, 비SAP 애플리케이션을 하나의 테스트 흐름으로 다루며, 이것이 전체 비즈니스 프로세스를 테스트할 때의 가장 큰 장점입니다.

SAP와 Tricentis는 긴밀한 파트너십을 맺고 있습니다. SAP는 SAP Enterprise Continuous Testing by Tricentis, SAP Load Testing by Tricentis, SAP Change Impact Analysis by Tricentis 같은 Tosca 기반 제품을 재판매합니다. 예산 면에서 더 큰 소식은 [SAP의 사용 권한](https://support.sap.com/en/alm/usage-rights.html)에 있습니다. Enterprise Support 고객은 Cloud ALM과 통합된 Tricentis Test Automation for SAP의 기간 한정 라이선스를 받으며, 현재는 2027년 12월 31일까지입니다. 지명 사용자 5명, 월 테스트 실행 500회, 실행 에이전트 5개로 제한되므로 프로그램 규모의 도구가 아니라 출발점으로 보십시오.

어려운 점: 매우 동적인 웹 프런트 엔드는 유지보수 노력을 늘리고, 대규모 테스트 데이터 관리는 대개 추가 도구가 필요하며, 대규모 모듈 라이브러리는 처음부터 거버넌스가 필요합니다.

### Xray for Jira

[Xray](https://www.getxray.app/)는 SAP용으로 만들어진 도구는 아니지만, 구축이 Jira에서 돌아간다면 자연스러운 확장처럼 느껴집니다. 테스트 케이스가 사용자 스토리와 변경 요청 옆에 놓이므로 커버리지가 스프린트 계획의 일부가 됩니다. 행동 주도 테스트를 위한 Cucumber와 Gherkin을 지원하고 CI 파이프라인에 연결됩니다.

어려운 점: 배치 잡이나 깊은 연계 체인 같은 무거운 SAP 트랜잭션 테스트, 매우 큰 테스트 저장소, 복잡한 커스텀 리포트는 애드온이나 API 작업이 필요합니다.

### SAP Solution Manager

Solution Manager는 요구사항, 테스트 계획, 실행, 트랜스포트를 한곳에서 연결하고 변경 요청 관리(ChaRM)와 통합됩니다. Business Process Change Analyzer는 테스트 범위를 변경이 실제로 건드리는 프로세스로 좁혀 줍니다. 규제 환경에서는 그 감사 추적이 여전히 가치 있습니다.

약점은 낡은 사용자 경험, 무거운 설정, SAP 사용자 인터페이스만 다루는 자동화(CBTA), 그리고 이제는 갖춘 팀이 드문 역량입니다. 메인스트림 유지보수는 2027년 말에 끝나며, 일부 기능은 2030년까지 연장 유지보수가 제공됩니다. 이미 변경 통제에 쓰고 있지 않다면 테스트 관리용으로 새로 들이지 마십시오.

다른 도구들은 틈새에 맞습니다. Worksoft Certify는 제약 같은 검증된 환경에 강합니다. Katalon은 가볍고 웹을 향한 SAP 프로젝트에 도움이 될 수 있습니다. 둘 다 제가 핵심 SAP 테스트 프로그램에 보통 권하는 도구는 아닙니다.

## 나란히 비교

표는 적합성을 가르는 기능을 기준으로 네 가지 도구를 비교합니다.

| 기능 | SAP Cloud ALM | Tricentis | Xray for Jira | SAP Solution Manager |
|---|---|---|---|---|
| 주요 역할 | 테스트 관리와 추적성 | SAP와 비SAP를 아우르는 자동화 | Jira 안의 테스트 관리 | ChaRM과 연결된 테스트 관리 |
| 요구사항 추적성 | 기본 제공, Activate 단계와 연결 | 완전, 자체 테스트 관리를 통해 | Jira 링크를 통해, 규율 필요 | 기본 제공, ChaRM과 함께 가장 강력 |
| 자동화 | 통합된 Tricentis 또는 파트너 도구를 통해 | 핵심 강점, 모델 기반 | 외부 프레임워크를 통해 | CBTA, SAP 인터페이스만 |
| 비SAP 애플리케이션 | 제한적 | 가능, 같은 흐름 안에서 | 가능, 프레임워크를 통해 | 불가 |
| 감사 추적 | 강력 | 강력 | 기본 상태로는 제한적 | 강력, 트랜스포트 포함 |
| 라이선스 | Enterprise Support 포함 시 무료 | Enterprise Support에 입문용 라이선스 포함, 전체 제품은 별도 가격 | Jira에 사용자당 애드온 | 온프레미스 유지보수에 포함 |
| 전망 | SAP의 전략 플랫폼 | 깊어지는 SAP 파트너십 | Jira 전략에 달려 있음 | 메인스트림 유지보수 2027년 종료 |

## 제가 고르는 방법

저는 테스트를 문서화와 자동화로 나눕니다. 둘은 서로 다른 문제를 풀며, 둘 다 하나의 플랫폼에 밀어 넣는 팀은 대개 고전합니다.

문서화와 추적성에는 신규 프로그램에서 Cloud ALM을 쓰십시오. Solution Manager가 이미 변경 통제를 맡고 있다면 환경이 바뀔 때까지 확장해서 쓰고, 그다음에 이전하십시오. 자동화에는 릴리스가 잦은 SAP 비중이 큰 환경에서 제가 보통 권하는 것이 Tricentis입니다. 모델이 안정되면 실행이 일관되고, 스크립트 기반 자동화보다 유지보수가 줄어듭니다. Jira에서 Fiori 앱과 API를 만드는 애자일 팀에는 Xray로 충분한 경우가 많습니다.

선택하기 전에, 테스트를 실제로 수행할 사람들과 함께 다음 질문을 짚어 보십시오.

| 요소 | 왜 중요한가 | 던질 질문 |
|---|---|---|
| SAP 커버리지 | 테스트가 SAP GUI, Fiori, 실제로 쓰는 인터페이스를 구동해야 함 | 어떤 SAP UI 기술과 API를 기본으로 지원합니까? |
| 변경 영향 | 트랜스포트 후 무엇을 다시 테스트할지 알면 과잉 테스트와 리스크 누락을 피함 | 변경을 영향받는 테스트에 연결할 수 있습니까? |
| CI/CD 연계 | 자동화 실행에는 파이프라인의 트리거가 필요 | 빌드 및 트랜스포트 도구와 함께 동작합니까? |
| 거버넌스 | 대규모 프로그램에는 재사용 가능하고 버전 관리되는 구성 요소가 필요 | 테스트를 모듈화하고, 버전 관리하고, 웨이브 간에 재사용할 수 있습니까? |
| 비즈니스 사용성 | 기능 컨설턴트와 핵심 사용자가 테스트를 검토해야 함 | 개발자가 아닌 사람도 테스트 케이스를 만들고 읽을 수 있습니까? |
| 사용 권한 | 지원 계약이 이미 필요의 일부를 포함하고 있을 수 있음 | Cloud ALM과 Tricentis 사용 권한이 이미 무엇을 제공합니까? |
| 총비용 | 설정, 에이전트, 유지보수가 라이선스보다 큼 | 모델 유지보수를 포함해 2년 차에 얼마가 듭니까? |

## 실제 프로그램이 가르쳐 준 것

**글로벌 제조 기업: Tosca.** 이 회사는 크게 커스터마이징된 창고 시스템과 함께 SAP ECC를 운영했습니다. 분기별 릴리스는 긴 수작업 회귀 테스트 사이클 때문에 계속 밀렸고 결함이 운영으로 새어 나갔습니다. 팀은 입고 물류에서 Tosca를 시범 적용해 4주 동안 재사용 가능한 단계 라이브러리를 만들었습니다. 자동화 실행은 트랜스포트 승인과 연결되었고, 이후 출고 물류와 생산 계획으로 확장되었습니다. 대량 트랜잭션의 회귀 테스트 커버리지는 35%에서 85% 이상으로 올랐고, Go-Live 후 결함은 두 분기 안에 40% 줄었습니다. 이렇게 커스터마이징이 많은 환경을 자동화하는 데 대한 롤아웃 중의 반발이 기억납니다. 운영 장애가 줄고 같은 모델이 여러 공장에서 재사용되는 것을 팀들이 본 뒤에 반발은 멈췄습니다.

**유통 기업: Xray.** 이 회사는 새로운 Fiori 앱과 클라우드 연계와 함께 S/4HANA로 이전했고, 모든 IT 구축을 Jira에서 운영했습니다. Xray는 테스트를 사용자 스토리에 묶고, 프로덕트 오너가 도구를 바꾸지 않고도 진행 상황을 따라가게 해 주었으며, Fiori 스쿼드를 위한 Gherkin 인수 기준을 지원했습니다. 테스트 증적은 스프린트 리뷰에 맞춰 준비되었습니다. 무거운 트랜잭션이나 배치 테스트는 감당하지 못했겠지만, 애자일 Fiori, API, 사용자 중심 작업에는 복잡성을 더하지 않고도 충분했습니다.

**금융 서비스 기관: Solution Manager.** 재무, 자금, 규제 보고에 걸쳐 크게 커스터마이징된 환경이 완전한 추적성에 대한 감사 압박을 받고 있었습니다. 테스트는 트랜스포트와 연결되지 않은 스프레드시트에 있었습니다. 테스트 계획을 ChaRM 변경 문서에 연결하고, 모든 실행에 타임스탬프를 남기고, Business Process Change Analyzer로 재테스트 범위를 정하자 대화가 달라졌습니다. 전환점은 감사인이 더 이상 Excel 파일을 요청하지 않고 시스템 안에서 테스트 이력을 직접 검증하기 시작했을 때 왔습니다.

**Solution Manager에서 Cloud ALM으로 이동.** 테스트 문서를 이전하는 일은 그 자체로 하나의 프로젝트입니다. 어차피 환경이 바뀔 때, 예를 들어 RISE 도입의 일부로 하십시오. 단독으로 하지는 마십시오.

## 테스트가 효과를 내게 하는 실천

도구가 스스로 품질을 만들어 주지는 않습니다. 품질을 만드는 것은 이런 실천이며, 도구가 바뀌어도 유효합니다.

| 실천 | 적용 방법 |
|---|---|
| 일찍 시작 | 결과를 테스트할 수 있도록 요구사항을 쓰는 동안 테스트 리드를 참여시킴 |
| 트랜잭션이 아니라 프로세스를 테스트 | 모듈을 가로지르고 예외를 포함하는 흐름을 구성 |
| 테스트 데이터 통제 | 초기화할 수 있는 전용 테스트 클라이언트를 쓰고, 운영 데이터는 마스킹 |
| 회귀 테스트를 일상화 | 컷오버 직전에만이 아니라 트랜스포트마다 자동화 실행을 트리거 |
| 리스크 기준으로 우선순위 설정 | 중요하고 자주 바뀌는 프로세스를 먼저, 100%가 아니라 똑똑한 커버리지를 목표로 |
| 비즈니스를 참여시킴 | 핵심 사용자가 실행 시작 전에 테스트 케이스를 검증 |
| 테스트를 변경 승인에 연결 | 검증된 테스트 없이는 어떤 트랜스포트도 이동하지 않음 |
| 감사 대응 상태 유지 | 누가 언제 무엇을 테스트했는지 내보낼 수 있는 형태로 기록 |

세 가지 숫자를 추적하십시오. 운영으로의 결함 유출, 다시 쓰지 않고 재사용된 테스트 케이스의 비율, 전체 회귀 테스트에 걸리는 시간입니다. 이 숫자들이 노력을 어디에 쏟아야 하는지 알려 줍니다. [SAP 품질 게이트](/ko/sap-quality-gates-implementation/)에 관한 제 글은 테스트 결과를 Go/No-Go 의사결정에 연결하는 방법을 보여 줍니다.

## 2026년에 달라지는 것

**Cloud ALM이 기본값입니다.** 새로운 RISE와 GROW 프로그램은 이를 테스트의 뼈대로 삼아야 합니다. Solution Manager를 쓰는 기존 온프레미스 환경에는 시간이 있지만 많지는 않습니다. 2028년 전에 이전을 계획하십시오. 하이브리드 환경은 한동안 둘 다 운영할 것입니다. 중복 기간을 계획하십시오.

**AI가 테스트 초안을 작성합니다.** Cloud ALM의 Joule 기반 어시스턴트는 문서에서 테스트 케이스와 요구사항을 생성합니다. 절감은 변형이 대부분 데이터인 회귀 스크립트 같은 물량 작업에서 나옵니다. 엣지 케이스, 복잡한 연계 로직, 성능 테스트 설계에는 여전히 숙련된 테스트 아키텍트가 필요합니다.

**Clean Core가 테스트 대상을 옮깁니다.** 퍼블릭 클라우드에서는 코어에 회귀 테스트할 커스텀 코드가 없습니다. 프라이빗 클라우드와 온프레미스에서는 코어의 커스텀 ABAP이 회귀 문제를 발견하기에 가장 비싼 곳입니다. 고친 다음, 다음 SAP 릴리스에 맞춰 다시 검증해야 합니다. SAP BTP의 사이드바이사이드 확장은 별도로 버전 관리되며 자체 회귀 테스트 커버리지가 필요합니다.

**AI 단계에는 새로운 테스트 패턴이 필요합니다.** 결정론적 회귀 스크립트로는 비결정적인 AI 동작을 테스트할 수 없습니다. Joule과 에이전트가 주도하는 단계를 위한 별도의 테스트 유형을 예상하십시오.

## 자주 묻는 질문

<details>
<summary>SAP 자동화에 가장 좋은 테스트 도구는 무엇입니까?</summary>

SAP 비중이 큰 환경에서는 Tricentis Tosca가 제가 가장 자주 권하는 도구입니다. 모델 기반 접근 방식 덕분에 테스트를 만들고 유지하기가 쉽고, SAP와 비SAP 애플리케이션을 하나의 흐름으로 다룹니다. 팀이 Jira에서 일하고 주로 애자일 방식으로 Fiori 앱을 만든다면, 테스트 프레임워크와 함께 쓰는 Xray가 더 맞을 수 있습니다. 결정하는 것은 시연이 아니라 상황입니다.

</details>

<details>
<summary>Tricentis는 SAP Enterprise Support에 포함되어 있습니까?</summary>

일부 포함됩니다. SAP는 SAP Cloud ALM과 통합된 Tricentis Test Automation for SAP의 기간 한정 라이선스를 부여하며, 현재는 2027년 12월 31일까지입니다. Enterprise Support(클라우드 에디션 또는 온프레미스) 또는 Product Support for Large Enterprises를 가진 고객이 대상입니다. 지명 사용자 5명, 월 테스트 실행 500회, 실행 에이전트 5개로 제한됩니다. 더 큰 프로그램에는 대개 전체 Tricentis 제품이 필요하며, SAP도 이를 재판매합니다.

</details>

<details>
<summary>SAP Solution Manager로 테스트 자동화를 처리할 수 있습니까?</summary>

일부만 가능합니다. Component-Based Test Automation(CBTA)은 SAP 사용자 인터페이스는 다루지만 비SAP 애플리케이션은 다루지 못하며, 화면이 바뀔 때마다 상당한 유지보수가 필요합니다. Solution Manager는 주로 테스트 관리와 문서화 플랫폼입니다. 대부분의 팀은 Tricentis나 다른 자동화 도구와 함께 쓰며, 메인스트림 유지보수가 2027년에 끝나므로 신규 프로그램은 대신 Cloud ALM에서 시작해야 합니다.

</details>

<details>
<summary>2026년에 테스트에는 SAP Cloud ALM과 Solution Manager 중 무엇을 써야 합니까?</summary>

신규 프로그램에는 Cloud ALM, 특히 RISE와 GROW에는 Cloud ALM입니다. 테스트를 SAP Activate 단계와 변경에 연결하며 Enterprise Support에서는 라이선스 비용이 없습니다. 기존 온프레미스 환경에서 Solution Manager가 이미 잘 돌아가고 있다면 환경이 바뀔 때까지 유지하되, 2028년 전에 이전을 계획하십시오.

</details>

<details>
<summary>테스트 관리 도구와 자동화 도구가 둘 다 필요합니까?</summary>

대부분의 엔터프라이즈 프로그램에서는 그렇습니다. 테스트 관리(Cloud ALM 또는 Solution Manager)는 감사인이 필요로 하는, 요구사항에서 테스트와 변경까지의 추적성을 제공합니다. 자동화(Tricentis 등)는 회귀 테스트 사이클을 효율적으로 실행합니다. 하나의 도구가 둘 다 잘하는 경우는 드뭅니다. 더 단순한 환경에서는 Cloud ALM과 포함된 Tricentis 사용 권한으로 시작하고, 릴리스 물량이 정당화할 때 전체 자동화 제품을 추가하십시오.

</details>

<details>
<summary>Clean Core에서 SAP 테스트는 어떻게 달라집니까?</summary>

테스트의 초점이 코어 안의 커스텀 코드에서 코어 주변의 확장으로 옮겨 갑니다. 퍼블릭 클라우드에는 회귀 테스트할 코어 커스텀 코드가 없습니다. 프라이빗 클라우드와 온프레미스에서는 남아 있는 코어 수정을 SAP 릴리스마다 다시 테스트해야 합니다. SAP BTP 확장은 자체 릴리스 주기가 있어 자체 회귀 테스트 모음이 필요하고, AI 단계에는 비결정적 출력을 허용하는 테스트 패턴이 필요합니다.

</details>

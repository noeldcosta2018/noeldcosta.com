## 1\. SAP Integration Suiteの概要

[SAP implementationは、単にSAPを設定するだけ](https://noeldcosta.com/sap-implementation/sap-modules/)で終わることはほとんどありません。実際には、[SAPを他のあらゆるものと連携させること](https://noeldcosta.com/sap-implementation/s4hana/)のほうが多いです。レガシーシステム、クラウドアプリ、データベース、そして業務が長年頼ってきた独自ツールも含まれます。 

そこで統合が重要になります。ランドスケープ全体をしっかり支えることもできますし、何か壊れるまで誰も気づかない摩擦を静かに生むこともあります。

実務では、統合は過小評価されがちです。チームは[機能、プロセス設計、テスト](https://noeldcosta.com/sap-implementation/)に集中します。そして終盤になって、誰かがこう気づきます。

-   重要データがリアルタイムで同期していない
    
-   API制限に数週間前から引っかかっていた
    
-   間接利用のせいでライセンス費用が倍になった
    
-   選んだミドルウェアが高負荷時の処理量に耐えられない
    

こうしたことは、最初から明白とは限りません。ですが、最終的にはスケジュール、予算、さらにはコンプライアンスにまで影響します。

このページでは、そうした前提を踏まえて[SAP Integration Suite](https://noeldcosta.com/sap-vs-oracle-which-erp-is-better-for-your-business/)を見ていきます。プロジェクトの現場で実際にどう機能するのか、どんな問題を解決するのか、そしてリスクがどこに潜みやすいのか、という観点です。

## 2\. SAPプロジェクトでよくある統合シナリオ

[SAP projects](https://noeldcosta.com/2024-sap-timeline-planning-implementation-guide-essentials/)は、たいてい白紙の状態から始まりません。既存システムが混在した状態から始まります。きちんと文書化されたものもあれば、ほとんど誰も理解していないものもあります。統合は、そのすべてを整理しなければなりません。しかも、遅延の余地はあまりありません。

多くのランドスケープで繰り返し出てくるパターンがいくつかあります。

-   SAPとnon-SAPの接続。今も使われているレガシーERP、CRM、自社開発アプリ。
-   ハイブリッド構成。クラウドサービスとオンプレミスシステムが混在し、同期を保とうとしている状態。
-   リアルタイムとバッチのフロー。速さは魅力ですが、実際には信頼性が勝つことも多いです。
-   API主導かミドルウェア主導か。状況によっては両方使います。

[ツール](https://noeldcosta.com/simplify-your-business-with-erp-ai-tools/)としてのSAP Integration Suiteは、こうしたパターンの多くに対応できるよう設計されています。特にハイブリッド環境やクラウド比率の高い環境では有効です。ただし、ツール自体は解決策の一部にすぎません。

[SAPを外部プラットフォームとつなぐこと](https://noeldcosta.com/why-erp-integration-with-salesforce-fails-and-how-to-fix-it/)は、聞こえは簡単です。ですが、フォーマット、セキュリティ、タイミングが邪魔をし始めると話が変わります。私は、小さな不一致でチームが何日も止まるのを見てきました。片方はREST、もう片方はフラットファイルに固執する、といった具合です。

ハイブリッド構成は最初は柔軟に見えます。実際には、例外の継ぎはぎで成り立っていることが多いです。あるサービスは即時にデータを送ります。別のサービスは今でも夜間バッチ頼みです。

[リアルタイム統合](https://noeldcosta.com/why-erp-integration-with-salesforce-fails-and-how-to-fix-it/)は、計画段階では誰にでも魅力的に見えます。ですが、両方のシステムがそれに耐えられる場合にしか機能しません。いつもそうとは限りません。

ミドルウェアは構造を与え、APIはスピードを与えます。どちらを選ぶかは好みよりも、すでに何があるか、そしてチームが現実的に何を運用できるかで決まります。

#### 1\. SAPからnon-SAPへの統合

SAPは、[プラットフォームと接続する](https://noeldcosta.com/sap-vs-oracle-which-erp-is-better-for-your-business/)必要がよくあります。たとえばSalesforce、Oracle、あるいは業界特化ツールです。こうした統合は、重要な業務システムとプロセスの継続性を支えます。

-   SAPとサードパーティプラットフォーム間の構造化されたデータ連携を可能にします
-   認証、項目マッピング、変換レイヤーが関わります
-   SAP展開時にも[既存の業務ワークフローを維持する](https://noeldcosta.com/2024-sap-timeline-planning-implementation-guide-essentials/)のに役立ちます

#### 2\. ハイブリッドランドスケープ（オンプレ / クラウド）

多くの[SAP customers operate in hybrid environments](https://noeldcosta.com/sap-implementation/grow-with-sap/)。オンプレミスの[SAP systems coexist with cloud](https://noeldcosta.com/sap-implementation/rise-with-sap/)プラットフォームが共存しており、データ整合性と業務の俊敏性のためにシームレスな統合が不可欠です。

-   [SAP ECC](https://noeldcosta.com/ecc-to-s4hana-migration/)またはS/4HANAを、SuccessFactorsやAribaのようなクラウドソリューションと接続します
-   異なるプロトコルとセキュリティモデルを橋渡しします
-   遅延や同期問題を避けるには強いガバナンスが必要です

#### 3\. リアルタイム統合 vs バッチ統合

[リアルタイム統合とバッチ統合](https://noeldcosta.com/why-erp-integration-with-salesforce-fails-and-how-to-fix-it/)のどちらを選ぶかは、システム能力、データ量、業務要件によります。すべてのプロセスが即時データ同期の恩恵を同じように受けるわけではありません。

-   リアルタイムは、受注作成や在庫更新のようなトランザクションに向いています
-   バッチは、価格、マスタデータ、履歴ロードのような大規模データセットに向いています
-   多くのランドスケープでは、プロセスの重要度に応じて両方を使います

#### 4\. APIベース統合

APIベース統合では、アプリケーション同士が軽量プロトコルを使って[直接通信](https://noeldcosta.com/2025-the-year-sap-generative-ai-redefines-middle-east-careers/)できます。クラウドネイティブなサービスやモダンな開発環境に向いています。

-   SAPをモバイルアプリ、ポータル、マイクロサービスと接続するのに適しています
-   導入は速いですが、厳格なバージョン管理とセキュリティ対応が必要です
-   一般的には[SAP API Management and OData services](https://noeldcosta.com/sap-implementation/sap-modules/)と組み合わせて使われます

#### 5\. ミドルウェアベース統合

ミドルウェアは、SAPを複数システムと統合するための中央制御ポイントを追加します。オーケストレーション、メッセージキューイング、データ変換によって複雑さを管理しやすくします。

-   [複数システムがSAPとやり取りする](https://noeldcosta.com/why-sap-data-migration-fails-and-how-to-fix-it/)ランドスケープで使われます
-   集中監視とエラーハンドリングを提供します
-   例: SAP PI/PO, SAP Integration Suite, MuleSoft, Dell Boomi

#### 6\. 混合型の統合アプローチ

多くの企業は、API戦略とミドルウェア戦略を組み合わせて使っています。このハイブリッドモデルは、システム制約、チームスキル、長期的なサポート要件に合わせやすいです。

-   直接統合と管理型統合の手法を組み合わせます
-   将来の拡張やツール変更に対する柔軟性を確保します
-   [技術面と業務面の両方の優先事項に統合を合わせる](https://noeldcosta.com/sap-implementation/for-retail/)のに役立ちます

## 3\. SAP Integration Suiteの全体像

[SAP integrationを考えるとき、適切な](https://noeldcosta.com/5-best-crm-systems-for-sap-in-2024/)SAP Integration suiteを選ぶことは、多くのチームが思う以上に重要です。単に機能や速度の話ではありません。この判断は、スケジュール、サポートモデル、さらにはライセンスにも影響します。私は、[プロジェクトが止まる](https://noeldcosta.com/why-erp-integration-with-salesforce-fails-and-how-to-fix-it/)場面を見てきました。統合そのものが失敗したのではなく、プラットフォームが業務の進め方に合っていなかったのです。

SAPには[複数の統合](https://noeldcosta.com/sap-implementation/s4hana/)オプションがあります。古いものも、新しいものも、そして人が思う以上に重なっているものもあります。どのツールを使うべきかは、よく議論になります。もちろん、答えは「状況による」です。何をつなぐのか。データをどう動かす必要があるのか。チームが何を理解しているのか。

1つのツールですべてをカバーできるわけではありません。どれにもトレードオフがあります。ただ、それぞれがどこに最も合うかを理解すれば、全体像はかなり見えやすくなります。

以下は、実際のプロジェクトでどう使われているかに基づく、広く使われているSAP統合プラットフォームの簡単な整理です。SAPのマーケティング資料上の位置づけではなく、現場での使われ方ベースです。

SAP統合プラットフォーム

#### 1\. SAP PI / PO (Process Integration / Orchestration)

PI/POは、長年にわたりオンプレミスのSAP統合の標準でした。[メッセージ変換、ワークフロー、さまざまな](https://noeldcosta.com/sap-cpi/)プロトコル変換を処理します。信頼性はありますが、変化の速い環境では少し重く感じます。それでも、複雑なバックエンドロジックを扱うときには仕事をきちんとこなします。

-   [SAP-to-SAP and legacy integrations](https://noeldcosta.com/sap-implementation/s4hana/)に適しています
-   IDoc、BAPI、RFC、SOAPなどをサポートします
-   ECCベースまたはハイブリッド構成でよく使われます

#### 2\. SAP CPI / Integration Suite

SAP CPIはより柔軟で、クラウドファーストおよびハイブリッドランドスケープ向けに設計されています。特にSAPに不慣れなチームでも、[着手しやすい](https://noeldcosta.com/mastering-sap-implementation-a-step-by-step-guide-for-2025/)です。[事前構築済みiFlowsは役立ちますが、本格的なカスタマイズ](https://noeldcosta.com/sap-cpi/)にはやはり時間がかかります。新規のS/4HANAプロジェクトの多くでは、これが通常の第一候補です。

-   クラウドおよびハイブリッド統合をサポートします
-   再利用可能なコンテンツパッケージとアダプタを含みます
-   [SAP Integration](https://noeldcosta.com/what-consultants-actually-do-beyond-using-buzzwords/) Suiteのライセンスモデルの一部です

#### 3\. SAP API Management

実際のデータ移動よりも、ガバナンスに重点があります。API Managementは、誰が何に、どの条件でアクセスできるかを制御するためのものです。配送車というより、正面ゲートに近いと考えるとわかりやすいです。パートナーや社内利用者にAPIを公開する場合に有効です。

-   トラフィック制御、スロットリング、認証に使われます
-   SAP APIを外部アプリに公開する際に有効です
-   CPIや他のバックエンドツールを補完することが多いです

#### 4\. SAP BTP Integration Services

これは、CPI、API Management、イベント処理などを含む、より広い傘のような位置づけです。ツールを一元的に管理する場所を提供しますが、個々のツールは依然としてある程度独立して動きます。価値は、それらが束ねられ、ゆるやかに統合されている点にあります。

-   複数のSAP統合コンポーネントを組み合わせます
-   [SAP BTP cockpit](https://noeldcosta.com/master-the-sap-btp-cockpit-simple-steps/)経由で一元アクセスできます
-   複数ツールを使う統合ランドスケープに向いています

#### 5\. SAP Data Intelligence

Data Intelligenceは、データを構造化されたパイプラインでプラットフォーム間に流す必要がある場合のためのものです。トランザクションというより分析寄りです。SAPをデータレイク、MLツール、あるいは日常業務フローには入ってこない外部ソースと接続します。

-   プラットフォーム横断のデータオーケストレーションに重点を置きます
-   分析基盤や機械学習スタックと統合します
-   高頻度トランザクションではなく、データパイプライン向きです

#### 6\. 適切なツールの選び方

単一の「ベスト」プラットフォームはありません。適切なツールは、何を統合するのか、統合の規模はどれくらいか、どれだけの柔軟性が必要かで決まります。チームがすでに慣れているものを使う、というだけの話になることもあります。それも十分に重要です。

-   ツールではなく、まずユースケースから始めてください
-   ライセンス、スキルの確保しやすさ、サポートモデルを評価してください
-   実際には複数ツールを並行利用することが多いです

## 4\. SAP Integration Suiteで適切なコンポーネントを選ぶ

完璧な統合ツールはありません。あるSAPプロジェクトでうまくいくものが、別のプロジェクトでは不要なオーバーヘッドになることもあります。[SAP Integration Suite](https://noeldcosta.com/sap-integration-suite-delivery-delays/)で適切なコンポーネントを選ぶには、対象ランドスケープと、統合が受けるプレッシャーの種類を見なければなりません。技術面、運用面、時には政治的な要素まで含みます。

まずは、いくつかの基準で候補を絞ってください。

-   **システムランドスケープ** – 何個のシステムが関わりますか。すべてSAPですか。それともクラウドやnon-SAPツールが混在していますか。
    
-   **遅延要件** – データは即時に動く必要がありますか。それとも多少の遅れは許容できますか。
    
-   **拡張性** – 新しいシステムは頻繁に追加されますか。標準化より柔軟性が重要ですか。
    
-   **処理量** – 1時間に数件ですか。それとも1分あたり数万件ですか。
    

ざっくり言うと、各プラットフォームは次のようなニーズに合いやすいです。

-   **SAP-to-SAP -** PI/PO または CPI
-   **Cloud-to-cloud -** CPI, MuleSoft, Boomi
    
-   **API management -** SAP API Management, MuleSoft
    
-   **High-volume ETL -** Informatica, SAP Data Intelligence
    
-   **Complex orchestration -** PI/PO, MuleSoft, BTP Integration Services
    

## 5\. SAP Integration SuiteとOracle、Microsoft、Salesforceの連携

実際のSAPランドスケープでは、SAPが単独で動いていることはまれです。多くの環境には、Oracle、Microsoft、Salesforceのような大規模で業務上重要なプラットフォームが含まれています。それぞれに独自の統合課題があります。技術的なものもあれば、構造的なものもあり、ライセンスのグレーゾーンに入るものもあります。

### 1\. SAP ↔ Oracle (ERP, HR, SCM)

SAPとOracleは、大企業ではよく共存しています。片方が財務を担い、もう片方がサプライチェーンやHRを担う、といった形です。両者で確実にデータ共有させるのは、最初は遅く感じることがあります。特に、データモデルの違いが想像以上に大きい場合です。

-   Oracleのテーブルは、APIやステージングレイヤー経由で公開する必要があることが多いです
    
-   SAPは通常IDocを送るかBAPIを使うため、変換が必要です
    
-   タイミングが重要です。バッチウィンドウが同期遅延の原因になります
    
-   OracleアプリがSAPプロセスを自動起動する場合、間接アクセスのリスクがよく発生します
    

### 2\. SAP ↔ Microsoft (Azure, Power Platform, M365)

MicrosoftとSAPは、多くの人が思う以上に多くの場所で接点があります。Power BIがSAPからデータを引く場合もあれば、TeamsにライブKPIを表示する場合もあります。接続は増えています。ただし、統合には慎重な設計が必要です。スムーズな部分もあります。そうでない部分もあります。

-   Azure Logic AppsはSAP APIを呼び出せますが、認証情報の管理には注意が必要です
    
-   Power Platformにはコネクタがありますが、複雑なフローではカスタム関数が必要になることがあります
    
-   Microsoft 365（たとえばExcel）は、SAPデータをオフラインで編集してから同期し戻す用途でよく使われます。この構成は、追跡していないと静かにライセンス問題を生むことがあります
    

SAPとAzureの接続性は改善していますが、特にオンプレミスシステムが絡む場合、ハイブリッドモデルでは依然として強固な認証が必要です。

### 3\. SAP ↔ Salesforce (顧客データ、受注、サポート)

Salesforceは、ほぼ常に顧客接点側です。SAPはバックエンドを担います。この2つをつなぐ目的は、通常、顧客レコード、受注ステータス、サービス履歴の同期です。

-   こうしたフローでは[SAP CPI](https://noeldcosta.com/sap-cpi/)やMuleSoftの利用が一般的です
    
-   オブジェクトモデルが異なります。Salesforceは柔軟で、SAPはより厳格です
    
-   SalesforceのAPIレート制限が、大量同期を止めることがあります
    
-   ライセンス済みユーザーなしでSalesforceがSAPトランザクションを起動すると、間接ライセンスのリスクがあります
    

こうした接続は、最初は簡単に見えることがあります。ですが、処理量が増えたり、プロジェクト途中でプロセスが変わったりすると、複雑さが表に出てきます。こうした例外を早い段階で見込んでおくのは、たいてい無駄になりません。

## 6\. 間接ライセンスとは何か

間接ライセンスは、SAPの外にあるシステムが裏側でSAPとやり取りするときに発生します。誰もSAPに直接ログインしていなくても、業務プロセスはSAPに依存しています。典型例は、SalesforceがSAP上で販売注文を自動作成するケースです。画面を操作するSAPユーザーが1人もいなくても、これは該当します。

SAPはこれを「indirect access」と呼びます。そして重要です。ユーザーがSAPをまったく見ていなくても、ライセンス対象イベントと見なされるからです。

これに対応するため、SAPは**Digital Access model**を導入し、焦点をユーザー数からドキュメント数へ移しました。

典型的なトリガーには、次のようなものがあります。

-   サードパーティポータルが注文をSAPに送る
    
-   モバイルアプリがAPI経由で在庫レベルを確認する
    
-   ボットがログインせずに顧客データを更新する
    
-   CRMがSAPから価格情報をリアルタイムで取得する
    

どこまでが線引きか、いつも明確とは限りません。ただ、別システムの代わりにSAPが何かを処理しているなら、確認する価値はあります。

## 7\. ライセンスとコンプライアンスの考慮事項（直接 + 間接）

SAPプロジェクトでは、ライセンスの話は後になって表面化しがちです。ときには、統合の判断が終わった後です。ですが重要です。多くの人が思う以上に重要です。特に、サードパーティシステムが記名ユーザーなしでSAPを読み書きし始めるときはなおさらです。

核心はたいてい、**direct accessとindirect accessの違い**です。direct accessは単純です。記名されたSAPユーザーがログインし、プロセスを起動し、その行為にライセンスが紐づきます。ですがindirect accessは、外部システム、たとえばSalesforce、カスタムポータル、あるいはボットが、バックグラウンドでSAPとやり取りする場合です。これもSAPの条件上、利用と見なされることがあります。

これに対応するため、SAPは**Digital Access model**を導入しました。ユーザー単位ではなく、間接アクセス経由で作成される特定のドキュメント種別の数を数えます。販売注文、請求書、在庫移動などが含まれます。紙の上では、以前より明確です。実務では、まだグレーな部分が残ります。

コンプライアンスリスクは、善意の自動化から生まれることがよくあります。たとえば次のようなものです。

-   ユーザーログインなしでSAPから価格を取得するモバイルアプリ
    
-   SAPに顧客レコードを自動作成するCRM
    
-   毎時間在庫レベルを確認するスケジューリングツール
    

どれも便利です。ですが、適切に追跡・報告していなければ、ライセンス上の露出を引き起こす可能性があります。

コストを管理する方法はあります。SAPは、ドキュメントベースライセンスへの移行向けに**Digital Access Adoption Program (DAAP)**のインセンティブを提供しています。また、**usage monitoring tools**を導入する企業もあります。SAP Passportや外部ログソリューションを使って、どこにリスクがあるかを追跡します。

監査はまた別の話です。技術監査の場合もあれば、商務監査の場合もあり、両方のこともあります。予測しやすい監査もあります。そうでないものもあります。いずれにせよ、先回りしておくほうが、不意打ちを受けるより安く済むことが多いです。

#### 1\. SalesforceがSAPで販売注文を作成する

営業担当者がSalesforceに案件を入力し、その後、注文データが自動的にSAPへ送られます。SAPユーザーはログインしませんが、バックエンドのドキュメントは作成されます。

-   **何が問題か:** 販売注文がindirect access経由で生成されており、SAPのデジタルライセンスの対象になります。
-   **対策:** SAPのDigital Access modelを使ってこれらをドキュメントとしてカウントするか、記名SAPユーザーのワークフロー経由で起動するよう再設計します。

#### 2\. カスタムポータルがSAPから価格を読む

公開向けまたはパートナー向けのWebポータルが、API経由でSAPから取得したリアルタイム価格を表示します。SAP認証は使われていません。

-   **何が問題か:** 価格データへのアクセスが記名ユーザーを経由せず、追跡性のない形でSAPバックエンドを公開しています。
-   **対策:** SAP API Management経由にし、適切なユーザー認証またはクォータ制御を適用します。

#### 3\. モバイルアプリが在庫可用性を確認する

倉庫チームが、SAPに直接ログインせずに、ライブのSAP在庫を照会するモバイルアプリを使っています。

-   **何が問題か:** データが間接的にアクセスされており、量や頻度によってはライセンス責任が発生する可能性があります。
-   **対策:** モバイルユーザーにライセンスを付与するか、アクセスがドキュメントベースライセンスの閾値内に収まるようにします。

#### 4\. Eコマースプラットフォームが請求書を作成する

オンライン購入の結果、請求書転記が自動的にSAPへ行われます。完全なシステム間処理で、SAPユーザーは関与しません。

-   **何が問題か:** 請求書作成は、間接的に行われる場合、SAPのDigital Access model上のライセンス対象イベントです。
-   **対策:** デジタルアクセスライセンスのカウントに請求書ドキュメントを含め、処理量の傾向を監視します。

#### 5\. HRシステムが従業員データをSAPへ書き込む

サードパーティのHRソフトウェアが従業員マスタデータを管理し、バッチジョブ経由でSAP HCMを更新します。

-   **何が問題か:** ライセンス済みのSAPユーザーなしでマスタデータを作成することは、データ処理のされ方によっては非準拠になる可能性があります。
-   **対策:** これらがライセンス対象ドキュメントに該当するかをSAPに確認し、利用追跡または記名ユーザー経由のルーティングを実装します。

#### 6\. BIツールが定期的にSAPからレポートを取得する

Power BIやTableauのようなレポーティングプラットフォームが、ODataやJDBC経由でスケジュール実行によりSAPテーブルへ接続し、静かにデータを取得します。

-   **何が問題か:** 頻繁なデータ抽出は、認証されていない場合やユーザーにライセンスがない場合、アクセス方針に違反する可能性があります。
-   **対策:** 認可済みレポーティングユーザー経由でアクセスさせるか、ライセンス追跡を適切に行うSAP認定アナリティクスコネクタを使います。

## 9\. 統合のベストプラクティス

プロジェクト初期の統合は、たいてい「動かすこと」が中心です。あるシステムから別のシステムへデータを移し、いくつかのチェックボックスを埋めて先へ進む。ですが、本当の難しさは後で出てきます。何かが静かに壊れたときや、そもそもインターフェースをどう設定したか誰も覚えていないときです。

ベストプラクティスは、硬直した標準に従うことではありません。避けられるリスクを減らすことです。より強い認証を使うことかもしれませんし、規模が大きくなる前に監視を入れることかもしれません。ときには、その時点では過剰に思えるくらい文書化するだけのこともあります。

長期的に統合を健全に保つうえで、次のようなことが役立ちます。

-   OAuth2、SAML、X.509のような安全なプロトコルを使う
    
-   フローが単純に見えても監視を設定する
    
-   再利用や拡張ができるiFlowsやAPIを作る
    
-   どう動くか、失敗したときに何をするかを文書化する
    

こうした手順は、たいてい緊急ではありません。ですが後になると、何時間も節約します。ときには何日分もです。

#### 1\. すべての統合ポイントを安全にする

セキュリティは後回しになりがちです。たいてい本番稼働直前です。ですが、その時点がいちばん直しにくいです。シナリオに応じてOAuth2、SAML、または証明書を使ってください。静的認証情報を使うなら、きちんと記録し、ローテーションしてください。設定ファイルに置いたまま、誰かが忘れないことを祈るだけ、というのは避けるべきです。

-   外部だけでなく、エンドツーエンドで暗号化してください
-   データリスクに応じて認証プロトコルを選んでください
-   トークンの有効期限切れと更新を早めにテストしてください

#### 2\. 最初から監視する

監視は、インシデントの後に追加されることが多いです。ですが、本当に機能するのは壊れる前から入っているときです。最小限のログでも役立ちます。派手なダッシュボードの話ではありません。何が、いつ、なぜ失敗したのかがわかることです。それがなければ、小さな問題でも追跡に何時間もかかります。

-   障害とタイムアウトのアラートを設定してください
-   応答時間とリトライ回数を記録してください
-   利用可能なら既存のSAP監視機能を使ってください

#### 3\. 目先ではなく再利用を前提に設計する

目の前の問題を、ハードコードした即席の解決策で片づけたくなることはあります。ですが、その場しのぎは後で必ず摩擦になります。再利用可能なiFlows、共通の変換ロジック、パラメータ化された入力は、プロセスが変わったときに時間を節約します。たいてい、実際に変わります。

-   可能なところではテンプレートを使ってください
-   マッピング手順に業務ルールを埋め込まないでください
-   ロジックと転送レイヤーを分離してください

#### 4\. 運用を意識して文書化する

文書化は設計フェーズで止まりがちです。ですが、サポートチームに必要なのは図だけではありません。エンドポイントが落ちたときや、項目が欠けているときに何が起きるのかを知る必要があります。良い文書は、チケットが上がる前にその答えを持っています。

-   リトライロジック、障害時処理、バージョン情報を含めてください
-   上流・下流システムに関する前提を記述してください
-   フロー変更に合わせて文書を更新してください

#### 5\. 明確なオーナーを決める

何カ月も動いている統合で、誰もオーナーではなかったと後で気づくことがあります。障害が起きると、全員が誰か別の人が見ていると思っています。これは避けるべきです。オーナーを決めてください。非公式でも構いません。この1ステップだけで、多くの技術的対策よりダウンタイムを減らせます。

-   各フローまたはインターフェースの責任者を定義してください
-   オーナーがログとツールにアクセスできるようにしてください
-   オンボーディングと引き継ぎ文書にオーナー情報を含めてください

#### 6\. 立ち上げだけでなく変更を前提に作る

インターフェースは固定ではありません。項目は変わります。APIはバージョンアップされます。処理量も増えます。フローが硬直しすぎていると、小さな変更でも壊れます。要件が今は安定して見えても、最初から調整を見込んでください。

-   マッピングと設定にバージョン管理を使ってください
-   既知の制約や限界を明確に文書化してください
-   リリースサイクルの中で統合フローを見直してください

## 10\. 総コストとROIの考慮事項

統合プロジェクトは、たいてい技術目標から始まります。システムをつなぐ、データを同期する、動かす。ですが、その下ではコストが多くの人の想像以上に大きな役割を持っています。初期ライセンスだけではありません。後で出てくる種類のコストです。負荷が増えたとき、要件が変わったとき、回避策が恒久対応になったときに出てきます。

**SAP CPI**のようなクラウドツールは、初期にはコスト効率がよく見えるかもしれません。ハードウェア不要で、立ち上げも速いです。ですが、従量課金なので、処理量とともにコストは上がります。**PI/PO**のようなオンプレミスの選択肢は価格が安定しやすい一方、インフラ負担があります。

さらにサードパーティプラットフォームもあります。それぞれ独自のライセンスモデルがあり、ユーザー課金のものもあれば、トランザクションやコネクタ課金のものもあります。積み上がります。

ですから、ROIの観点で統合を見るなら、「今いくらかかるか」以上の問いが必要です。先を見なければなりません。どうスケールするのか。変更が必要になったとき、そのコストを誰が負担するのか。

#### 1\. クラウド vs オンプレミスのコスト

[Cloud platforms like SAP](https://noeldcosta.com/sap-implementation/grow-with-sap/) CPIは、立ち上げが速くインフラコストも低いですが、価格は利用量に応じて増えることが多いです。PI/POのようなオンプレミスツールは初期投資が大きい一方、特にハードウェアがすでにある場合は、長期的にコスト安定性を得やすいです。

-   クラウド: サブスクリプション型で、メッセージ数や接続数ベースが多いです
-   オンプレミス: CAPEXが重く、継続ライセンス費は比較的低いです
-   価格はシステム処理量とITフットプリントに左右されます

#### 2\. SAP CPIライセンスの影響

SAP CPIは、段階制の従量課金モデルです。メッセージ量とスループットに基づいて課金されます。低～中程度の利用では予測しやすいですが、トラフィックが多い場合や最適化されていないフローでは、コストが急増することがあります。

-   開始ティアは通常€1,000–€2,000/月前後からです
-   大量メッセージや標準外アダプタには追加料金が発生します
-   コストを先回りで管理するため、月次で利用量を追跡してください

#### 3\. サードパーティミドルウェアの価格

MuleSoft、Dell Boomi、Informaticaは、コネクタ単位、ユーザー単位、トランザクション単位など、さまざまな価格モデルを採っています。基本価格は手頃に見えても、スケールすると新たな料金が発生する制限が見えてくることがあります。

-   MuleSoft: ライセンス + API量 + core packs (~$18K+/year)
-   Boomi: 統合プロセス、コネクタ、またはユーザーティアごとの課金
-   Informatica: ETL量とプラットフォームサービスがコストを左右します

#### 4\. 時間とともに増える変更コスト

初期設定コストは全体の一部にすぎません。新しいエンドポイント、更新されたマッピング、業務ルールの変更は、特に硬直した環境では、追加のライセンス費や開発費を生むことがあります。

-   複雑なランドスケープでは、年間15–30%の変更コストを見込んでください
-   よりモジュール化されたプラットフォームは変更時の摩擦を減らしやすいです
-   カスタマイズにはライセンス拡張やコンサルティングが必要になることがあります

#### 5\. サポートと保守コスト

サポートは、コスト見積もりで見落とされがちです。SAP CPIには基本サポートティアが含まれますが、応答時間やSLAはさまざまです。サードパーティツールはより速いサポートを提供することもありますが、有償だったり、追加契約が必要だったりします。

-   SAPサポートは既存のエンタープライズ契約に紐づくことが多いです
-   サードパーティツールは、サポートに年間ライセンスの15–20%を請求することがあります
-   システムが複雑になるほど、社内サポート負荷も増えることがあります

#### 6\. セットアップ以外も含めてROIを評価する

本当のROIには、実装だけでなく、時間を通じた保有コストが含まれます。安いプラットフォームは柔軟性に欠けるかもしれませんし、高いツールが後のダウンタイムや変更工数を減らすこともあります。立ち上げ時点ではなく、ライフサイクル全体で評価してください。

-   総ライセンス + 保守 + サポート + 変更コストを織り込んでください
-   ROIはプロジェクト期間だけでなく、2–3年の視点で見積もってください
-   失敗または遅延した統合のコストも潜在リスクとして含めてください

### 1\. SAP CPIとは何ですか。

SAP CPI、つまりCloud Platform Integrationは、SAP Integration Suiteの一部です。主にクラウドまたはハイブリッド環境で、SAPと[non-SAP systems](https://noeldcosta.com/erp-modernization-sap-servicenow/)を接続するのに役立ちます。ミドルウェアですが、分散型ランドスケープ向けに作られていると考えるとわかりやすいです。

含まれるものは次のとおりです。

-   事前構築済みの統合フロー（iFlowsと呼ばれます）
    
-   HTTPS、SFTP、ODataのようなプロトコルのサポート
    
-   カスタムマッピング、スクリプト、ルーティングのオプション
    

CPIは、オンプレミスからクラウドへ移行するときや、サードパーティアプリが安全にSAPとやり取りする必要があるときに特に有効です。

### 2\. SAPはSalesforceとどう統合しますか。

SAPとSalesforceは、通常、APIまたはSAP CPI、MuleSoft、Dell Boomiのようなミドルウェアを通じてデータをやり取りします。

一般的なユースケースには次のようなものがあります。

-   [customer master data](https://noeldcosta.com/sap-sd-sales-and-distribution/)の同期
    
-   受注情報や請求情報の転送
    
-   サポート案件履歴や価格情報の共有
    

課題は、Salesforce側のデータモデルの違いとAPI制限から来ることが多いです。慎重なマッピングとスロットリングが重要です。

ライセンスも懸念点になりえます。SalesforceがSAPでアクションを起こす場合、indirect accessが該当する可能性があります。

### 3\. SAPのindirect accessとは何ですか。

indirect accessは、外部システムがユーザーの直接ログインなしにSAPとやり取りするときに発生します。たとえば、ポータルやサードパーティアプリがAPI経由でSAPに販売注文を作成するケースです。

SAPはこれを、**Digital Access** modelのもとでライセンス対象と見なします。利用はドキュメント種別（注文、請求書など）で追跡されます。

これはチームにとって不意打ちになりがちです。システムは静かにバックグラウンドで動いていても、ライセンス上の露出を生むドキュメントを生成するからです。

管理するには、次のことが必要です。

-   外部システムがSAPをどう使っているかを評価する
    
-   ドキュメント作成量を監視する
    
-   SAPのドキュメントベースのデジタルライセンス体系を検討する
    

### 4\. どのSAP統合ツールが最適ですか。

それは、何を統合するのか、どれくらい頻繁に変わるのか、そして誰が保守するのかによります。

-   クラウド間またはハイブリッド向け: **SAP Integration Suite (CPI)**
    
-   オンプレミスのSAP-to-SAP向け: **SAP PI/PO**
    
-   APIガバナンス向け: **SAP API Management**
    
-   データパイプラインと分析向け: **SAP Data Intelligence**
    
-   より広いエンタープライズ統合向け: **MuleSoft or Dell Boomi**
    

多くのランドスケープでは組み合わせて使います。「最適」は機能よりも適合性で決まります。

### 5\. SAPはMicrosoftやOracleと統合できますか。

はい。しかもよくあります。

**SAP ↔ Microsoft**

-   Azure Logic Apps、Power Automate、またはPower BI内のSAPコネクタ
    
-   一般的な用途: SAPデータをExcel、Teams、ダッシュボードへ取り込むこと
    

**SAP ↔ Oracle**

-   通常はミドルウェア（CPI、PI、またはサードパーティ）が関わります
    
-   ユースケースには財務、調達、HR統合が含まれます
    

課題には、認証モデルの違い、タイミングのずれ、場合によってはライセンスが含まれます。

### 6\. SAP Integration Suiteとは何ですか。

SAP Integration Suiteは、システム、アプリ、データを接続するためのSAPのクラウドネイティブプラットフォームです。CPI、API Management、Open Connectors、event mesh機能を含みます。

ツールキットのようなものだと考えるとわかりやすいです。事前構築済みの部分もあれば、設定可能な部分もあります。クラウドファーストおよびハイブリッド環境向けに設計されています。

主な利点は次のとおりです。

-   一般的な統合向けの事前構築済みコンテンツ
    
-   リアルタイム処理とバッチ処理
    
-   セキュリティ、監視、ガバナンスのためのツール
    

これは、モダンなランドスケープにおけるSAPの戦略的統合レイヤーとして位置づけられています。

### 7\. SAP CPIはPI/POを置き換えていますか。

クラウド比率の高い、またはハイブリッドなランドスケープでは、はい。**SAP CPIが推奨される方向です**。ただし、PI/POも引き続きサポートされており、特にECCベースのシステムやオンプレミス構成では広く使われています。

SAPは時間をかけてIntegration Suiteへ移行することを勧めていますが、強制切替ではありません。プロジェクト時期、システムロードマップ、コストによります。

両方を使い、段階的にCPIへ移していく企業もあります。

### 8\. SAPはAPIセキュリティをどう扱いますか。

SAPは標準的なセキュリティプロトコルをサポートしています。

-   トークンベース認証の**OAuth2**
    
-   フェデレーションIDの**SAML**
    
-   システム間信頼のための**X.509 certificates**
    

Integration Suiteは、APIスロットリング、クォータ適用、ポリシー管理も提供します。多くのチームは、SAPのセキュリティツールをAzure ADやOktaのような企業向けIDプロバイダーと組み合わせています。

必要なセキュリティはシナリオごとに異なるので、早めに計画してください。

### 9\. SAP統合コストを左右するものは何ですか。

コストに影響する要因はいくつかあります。

-   ツールの種類（クラウドかオンプレか）
    
-   トランザクション数またはメッセージ数
    
-   インターフェース数とシステム数
    
-   ライセンスモデル（たとえばCPIは従量課金）
    

たとえば、SAP CPIのライセンスは最初は安く見えても、処理量とともに急速に増えることがあります。サードパーティミドルウェアは、コネクタ単位またはユーザー単位で課金することがあります。

見積もりには、ライセンス費だけでなく、サポート費と変更コストも必ず含めてください。

### 10\. SAP統合はどう監視すればよいですか。

SAP Integration Suiteには、監視ダッシュボード、ログ、トレースツールが標準で含まれています。次のことができます。

-   メッセージログとエラーをリアルタイムで確認する
    
-   パフォーマンスと遅延を追跡する
    
-   失敗したフローや遅いフローのアラートを設定する
    

PI/POのようなオンプレミスシステムでは、監視はIntegration Engineまたは[SAP Solution Manager](https://noeldcosta.com/creating-an-effective-sap-project-steering-committee/)で行います。

重要なのは、監視を早めに設定することです。何かが壊れてから待つほうが、たいてい事前計画より高くつきます。

SAPとSalesforceは、通常、APIまたはSAP CPI、MuleSoft、Dell Boomiのようなミドルウェアを通じてデータをやり取りします。

一般的なユースケースには次のようなものがあります。

-   [customer master data](https://noeldcosta.com/sap-sd-sales-and-distribution/)の同期
    
-   受注情報や請求情報の転送
    
-   サポート案件履歴や価格情報の共有
    

課題は、Salesforce側のデータモデルの違いとAPI制限から来ることが多いです。慎重なマッピングとスロットリングが重要です。

ライセンスも懸念点になりえます。SalesforceがSAPでアクションを起こす場合、indirect accessが該当する可能性があります。

indirect accessは、外部システムがユーザーの直接ログインなしにSAPとやり取りするときに発生します。たとえば、ポータルやサードパーティアプリがAPI経由でSAPに販売注文を作成するケースです。

SAPはこれを、**Digital Access** modelのもとでライセンス対象と見なします。利用はドキュメント種別（注文、請求書など）で追跡されます。

これはチームにとって不意打ちになりがちです。システムは静かにバックグラウンドで動いていても、ライセンス上の露出を生むドキュメントを生成するからです。

管理するには、次のことが必要です。

-   外部システムがSAPをどう使っているかを評価する
    
-   ドキュメント作成量を監視する
    
-   SAPのドキュメントベースのデジタルライセンス体系を検討する
    

それは、何を統合するのか、どれくらい頻繁に変わるのか、そして誰が保守するのかによります。

-   クラウド間またはハイブリッド向け: **SAP Integration Suite (CPI)**
    
-   オンプレミスのSAP-to-SAP向け: **SAP PI/PO**
    
-   APIガバナンス向け: **SAP API Management**
    
-   データパイプラインと分析向け: **SAP Data Intelligence**
    
-   より広いエンタープライズ統合向け: **MuleSoft or Dell Boomi**
    

多くのランドスケープでは組み合わせて使います。「最適」は機能よりも適合性で決まります。

**SAP ↔ Microsoft**

-   Azure Logic Apps、Power Automate、またはPower BI内のSAPコネクタ
    
-   一般的な用途: SAPデータをExcel、Teams、ダッシュボードへ取り込むこと
    

**SAP ↔ Oracle**

-   通常はミドルウェア（CPI、PI、またはサードパーティ）が関わります
    
-   ユースケースには財務、調達、HR統合が含まれます
    

課題には、認証モデルの違い、タイミングのずれ、場合によってはライセンスが含まれます。

SAP Integration Suiteは、システム、アプリ、データを接続するためのSAPのクラウドネイティブプラットフォームです。CPI、API Management、Open Connectors、event mesh機能を含みます。

ツールキットのようなものだと考えるとわかりやすいです。事前構築済みの部分もあれば、設定可能な部分もあります。クラウドファーストおよびハイブリッド環境向けに設計されています。

主な利点は次のとおりです。

-   一般的な統合向けの事前構築済みコンテンツ
    
-   リアルタイム処理とバッチ処理
    
-   セキュリティ、監視、ガバナンスのためのツール
    

これは、モダンなランドスケープにおけるSAPの戦略的統合レイヤーとして位置づけられています。

クラウド比率の高い、またはハイブリッドなランドスケープでは、はい。**SAP CPIが推奨される方向です**。ただし、PI/POも引き続きサポートされており、特にECCベースのシステムやオンプレミス構成では広く使われています。

SAPは時間をかけてIntegration Suiteへ移行することを勧めていますが、強制切替ではありません。プロジェクト時期、システムロードマップ、コストによります。

両方を使い、段階的にCPIへ移していく企業もあります。

SAPは標準的なセキュリティプロトコルをサポートしています。

-   トークンベース認証の**OAuth2**
    
-   フェデレーションIDの**SAML**
    
-   システム間信頼のための**X.509 certificates**
    

Integration Suiteは、APIスロットリング、クォータ適用、ポリシー管理も提供します。多くのチームは、SAPのセキュリティツールをAzure ADやOktaのような企業向けIDプロバイダーと組み合わせています。

必要なセキュリティはシナリオごとに異なるので、早めに計画してください。

コストに影響する要因はいくつかあります。

-   ツールの種類（クラウドかオンプレか）
    
-   トランザクション数またはメッセージ数
    
-   インターフェース数とシステム数
    
-   ライセンスモデル（たとえばCPIは従量課金）
    

たとえば、SAP CPIのライセンスは最初は安く見えても、処理量とともに急速に増えることがあります。サードパーティミドルウェアは、コネクタ単位またはユーザー単位で課金することがあります。

見積もりには、ライセンス費だけでなく、サポート費と変更コストも必ず含めてください。

SAP Integration Suiteには、監視ダッシュボード、ログ、トレースツールが標準で含まれています。次のことができます。

-   メッセージログとエラーをリアルタイムで確認する
    
-   パフォーマンスと遅延を追跡する
    
-   失敗したフローや遅いフローのアラートを設定する
    

PI/POのようなオンプレミスシステムでは、監視はIntegration Engineまたは[SAP Solution Manager](https://noeldcosta.com/creating-an-effective-sap-project-steering-committee/)で行います。

重要なのは、監視を早めに設定することです。何かが壊れてから待つほうが、たいてい事前計画より高くつきます。

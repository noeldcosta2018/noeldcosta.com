在我主持过的每一个 ERP 项目里，数据迁移始终是最容易被低估的工作流。供应商按三个月的数据工作量来界定范围，实际落在六到九个月。到了切换阶段，一半的团队都在忙着扑灭重复数据的火，指导委员会则在追问为什么没人早点提出来。

我做这个估算器，是想把这场对话提前几个月。它按数据对象、数据量和目标 ERP 来估算工作量，给出人天估算、成本区间和推荐的迁移方式。它不绑定厂商，涵盖 SAP S/4HANA、SAP ECC、Oracle Fusion Cloud、Oracle E-Business Suite，以及 Microsoft Dynamics 365 和 AX。

输出的是一个区间，而不是一个点，因为真实情况就是一个区间。对结果影响最大的变量是数据质量、源系统的数量，以及您决定迁移多少历史数据。

## 如何使用

选择您的目标 ERP。添加范围内的数据对象，以及每个对象预计的记录量。如实设置数据质量标志。估算器会返回按对象划分的工作量、总人天区间、成本区间，以及推荐的方式（Migration Cockpit、LSMW、定制 ETL 或混合方式）。

一切都在您的浏览器中运行。不会向任何地方发送数据，也不会保存任何内容。您可以随时调整输入，用自己的假设对结果做压力测试。

## 为什么数据迁移超支会拖垮时间表

模式总是一样的。调研阶段在研讨会上进行，系统负责人都在场。他们告诉您数据“基本干净”。估算就建立在这句话之上。在这个数字写进商业论证之前，没人跑过哪怕一条数据剖析查询。

有一家制造业客户告诉我，他们的零件号是标准化的。我们把数据拉出来一看，正在使用的格式有 12 种。在另一个项目里，客户备注的记录系统其实是一个没人记录过的自定义字段，映射漏掉了它，三年的历史数据就这样消失了。在一次财务迁移中，唯一懂得遗留会计科目表的人，五年前就已经退休了。

代价高昂的时刻，是在切换演练中才发现这些问题，而不是在规划阶段。在调研第二周发现的数据质量修复，只花几天。同样的修复要是到第三轮模拟切换才发现，项目就要为此多花几周，有时是一个季度。到那时，日期已经对外公布，变革网络已经动员起来，要推迟上线就成了董事会层面的事。

正确的做法，是在估算签字之前先对数据做剖析。对源系统跑真实的查询。数一数重复记录。数一数空值。数一数按目标系统今天的必填字段规则会校验失败的记录。估算器默认您会这么做。当您如实设置数据质量标志时，成本区间会明显变宽。

## 迁移方式对比

合适的方式取决于目标 ERP、数据量，以及需要整合多少个源系统。下面是我通常会选的方式的大致样貌，工作量以最简单的方案为基准。

| 方式 | 最适合 | 工作量系数 | 工具 |
|---|---|---|---|
| SAP Migration Cockpit（LTMC / LTMOM） | Greenfield S/4HANA、标准对象、中等数据量 | 1.0× | LTMC、LTMOM、SAP 提供的模板 |
| LSMW | ECC、遗留系统迁移、仍在较旧版本上的项目 | 1.2× | LSMW、录制的 BDC 会话 |
| 通过 SAP BTP / Integration Suite 的定制 ETL | 数据量大、转换复杂、多源整合 | 2.0× | BTP、CPI、SAP Data Services、Syniti、SNP |
| 混合方式（Cockpit + ETL） | Brownfield S/4HANA 转换和选择性迁移 | 1.5× | 主数据用 Cockpit，事务历史用 ETL |
| Oracle 原生方式 | 以 Oracle Fusion Cloud 和 EBS 为目标 | 1.3× | FBDI、ADFdi、Oracle GoldenGate |
| Dynamics Data Management Framework | 以 Dynamics 365 F&O 和 AX 为目标 | 1.3× | DMF 实体、Azure Data Factory |

定制 ETL 最灵活，也最贵。要不要用它，一个诚实的检验标准是：您的源数据违反目标系统标准规则的方式，是不是没有逐条记录的逻辑就没有任何模板能修复。如果答案是否定的，就用标准交付的工具。

<summary>这个工具给出的数据迁移估算有多准确？</summary>

这些数字反映的是我过去 25 年在 SAP、Oracle 和 Dynamics 项目中看到的规律。它们的用途是为规划讨论提供一个锚点，而不是取代对您实际数据所做的剖析。

影响准确度的最大因素，是您有没有对源系统跑过数据剖析查询。基于如实设置的数据质量标志得出的成本区间站得住脚，基于研讨会上乐观情绪得出的则不然。把估算器的输出当作与系统集成商（SI）沟通时的基准数字。如果对方的估算明显更低，就问问他们做了什么数据质量假设，又是如何验证的。

</details>

<details>
<summary>应该迁移历史财务交易，还是只迁移未清项？</summary>

对大多数项目来说，正确答案是迁移未清项加期初余额，历史数据则通过只读归档或报表层，继续留在遗留系统中供查阅。迁移全部事务历史会成倍增加工作量，拖慢对账，而且很少值回成本。

例外情况有两类：一是受监管行业，法定保存要求历史数据必须放在记录系统中；二是在新系统里做滚动同比对比属于实际运营需求的企业。这两种情况下，估算器针对历史数据的工作量系数会体现出更重的负担。

</details>

<details>
<summary>工具会推荐哪种迁移方式？</summary>

它根据目标 ERP、对象范围和数据量来选定起点。采用标准对象的 Greenfield S/4HANA，通常会落在 Migration Cockpit 上。Brownfield 转换和选择性迁移倾向于混合方式。数据量大、源系统多或转换复杂时，推荐会转向 BTP 上的定制 ETL，或 Oracle、Microsoft 一侧的同类平台。

这个推荐只是起点。真正的决定要在用您的一部分样本数据做完概念验证（PoC）之后才能下，而不是靠一个计算器。把输出当作带进那次验证的工作假设。

</details>

<details>
<summary>它如何处理多区域、多实体的推广？</summary>

估算器针对的是单次迁移事件。多区域推广时，按每一波次各运行一次，再把各波次相加，并对从第一波起复用的模板、映射和工具设一个折减系数。按我的经验，第二波的成本大约是第一波的 60% 到 70%，第三波降到 50% 左右，之后趋于稳定。各地法定的数据对象（税务、薪资、银行）通常是无法干净复用的部分。

</details>

<details>
<summary>这个工具适用于从 ECC 到 S/4HANA 的 Brownfield 转换吗？</summary>

适用。它会针对就地转换的对象与需要重新映射的对象，调整其中较低的工作量。Brownfield 转换的数据工作量，通常是同等规模 Greenfield 迁移的 40% 到 60%，因为客户、供应商、物料和会计科目表结构无需重新抽取就能带过去。更大的工作量通常来自业务伙伴转换，以及新总账对历史过账的影响。

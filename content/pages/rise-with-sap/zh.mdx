RISE with SAP是SAP面向现有SAP客户推出的方案，让他们在一份订阅下把本地ERP迁移到云端。它打包了一套云ERP（通常是SAP Cloud ERP Private，即以前的SAP S/4HANA Cloud Private Edition）、由SAP托管的技术运维、转型工具以及RISE with SAP方法论（RISE with SAP Methodology）。

我在其中三个方面为企业提供帮助：在签约之前审查RISE合同，为迁移提供建议，以及检查系统和团队是否已经就绪。本页说明2026年10月时RISE是什么、哪些由SAP运营、哪些仍归您负责，以及我的详细指南在哪些方面讲得更深入。

## 2026年的RISE with SAP是什么

SAP把RISE with SAP描述为一条借助“经过验证的方法论、专家指导和由智能体主导的工具链”来实现本地ERP现代化的路线（引自[RISE with SAP产品页面](https://www.sap.com/products/erp/rise.html)）。它是一个商务和交付方案包，而不是一个独立的ERP产品。

这些名称在2025年发生了变化，而搜索中仍在使用旧名称。它们目前的情况如下：

1. **SAP Cloud ERP Private**是大多数RISE合同核心的私有云ERP。大多数人仍然用SAP S/4HANA Cloud Private Edition或“rise with sap s/4hana cloud”来搜索它。
2. **SAP Cloud ERP**是SAP云ERP的名称，它的公有版就是人们所说的“rise with sap public cloud”。RISE可以基于任一版本构建。
3. **SAP GROW**（仍被广泛称为GROW with SAP）是面向SAP新客户的方案，基于公有版构建。
4. **SAP RISE**和**RISE with SAP**是同一回事。“SAP RISE”只是更短的搜索词。

版本选择是大多数公司做错的决定，因为他们以为RISE就意味着私有云。我的[RISE with SAP公有云与私有云对比](/zh-CN/rise-with-sap-public-vs-private-cloud/)指南讲解了每个版本在配置、升级、行业和迁移路径方面允许什么。我在那里的原则是：不需要非常特殊配置的标准流程，可以走公有云。

## RISE with SAP托管服务：哪些由SAP运营，哪些仍归您负责

“由SAP运营”是造成预算意外最多的一句话。SAP的[托管云服务页面](https://www.sap.com/products/erp/cloud-erp-private/features/managed-cloud-services.html)说明，这项服务不止于基础设施，还包括对操作系统、SAP HANA数据库和SAP Cloud ERP Private应用的管理。这属于技术运维。

您的业务流程、主数据和月结仍然归您负责。实施本身也是如此。下面是分工的简要版本：

| 领域 | 在RISE下由SAP运营 | 仍由您或您的合作伙伴负责 |
|---|---|---|
| 托管 | 超大规模云服务商或SAP数据中心中的基础设施 | 选择符合您数据驻留规则的提供商和区域 |
| 技术运维 | 操作系统、SAP HANA数据库、应用运维、监控和安全 | 在私有版中决定何时进行升级，并进行测试 |
| 业务流程 | SAP标准内容和最佳实践 | 流程设计、配置决策和功能支持 |
| 数据 | 数据所在的数据库 | 主数据的清洗、映射、迁移和归属 |
| 自定义代码 | 用于扩展的平台 | 修复、淘汰或重建您的自定义对象 |
| 项目 | 入门引导、方法论和质量关卡 | 合作伙伴选择、治理、测试、培训和切换 |

如果您需要详细的条目，SAP Help Portal发布了完整的[公有版、私有版和本地部署版的方案对比](https://help.sap.com/docs/SAP_S4HANA_CLOUD_PE/b89b8b9026e1456bb2a1df7c0d59c937/1485d139460246d2a4b936c0bb0ca272.html)。更高可用性的SLA和灾难恢复等可选附加项是单独的条目。我在[RISE with SAP合同与定价指南](/zh-CN/rise-with-sap-contract-pricing/)中讲解了这些内容。

## RISE with SAP方法论（人们搜索的“采用框架”）

人们常常搜索“RISE with SAP采用框架”。SAP自己的名称是**RISE with SAP方法论**（RISE with SAP Methodology）。它取代了早期RISE客户收到的那些零散的入门材料。

在SAP的[RISE with SAP方法论页面](https://www.sap.com/products/erp/rise/methodology.html)上，这个方法论有三个实际组成部分：

1. **SAP Cloud ALM中的SAP Activate路线图。**项目按熟悉的阶段推进：发现、准备、探索、实现、部署和运行。
2. **质量关卡。**每个阶段结束时的检查点，由您填写一份问卷，让SAP和您的合作伙伴看到相同的状态。
3. **入门引导和准备。**入门引导会议、发现阶段的数字化发现评估工具包，以及一项转型准备服务，SAP称这项服务是SAP Cloud ERP Private方案包中的一项权益。

SAP在2026年对RISE的描述还列出了工具链中的转型工具：[SAP Signavio、SAP LeanIX和WalkMe](https://learning.sap.com/courses/discovering-the-autonomous-enterprise/exploring-the-strategy-updates-for-rise-with-sap-and-sap-grow_ddbdcd8d-bf12-4298-a71e-a2c895a3673c)。SAP现在还把用于迁移和现代化的AI助手描述为这条工具链的一部分。您实际享有哪些权益取决于您的订单表，所以请逐一按名称核对每个工具。

这个方法论是有用的框架。它不会替您做艰难的决定。质量关卡确认的是某个阶段已经完成；它们不会告诉您，您的范围、版本或数据计划从一开始是否正确。

## 我如何在RISE with SAP方面提供帮助

有时我从一开始就主导项目。有时则是在事情出了偏差时被请来稳住局面。在我主导或挽救过的21个SAP项目中，我所做的RISE工作分为三项服务。

每一项都有明确的产出，所以您知道自己在为什么付费。

| 服务 | 最有帮助的时机 | 您得到什么 |
|---|---|---|
| 合同审查 | 在签署第一份RISE订单表之前，或在续约之前 | 对照您的设计逐条审阅订单表，并列出需要谈判的条款 |
| 迁移建议 | 在您选择路径、版本或合作伙伴时 | 关于版本和迁移路径的建议，并以书面形式写明理由 |
| 就绪检查 | 在您承诺时间表或接受合作伙伴报价之前 | 对SAP Readiness Check和您自己系统的解读，以及决定范围的未决问题 |

### 1. RISE合同审查

大多数RISE超支是在第一份订单表中就决定了的，而不是在续约时。我最常看到的三个陷阱是续约条款、FUE规模测算和AI额度。完全使用等价量（Full Use Equivalent，FUE）是SAP为ERP订阅定价所依据的使用量指标。

我总会在RISE交易中谈下两件事：按名称列明包含的模块，以及分阶段定价，这样您按阶段上线付费，而不是从第一天起就为全部范围付费。在一个首次上线前要运行9到18个月的项目中，为那些还不会接触系统的用户付费，是一笔实实在在的钱。

审查为您提供：

1. **范围检查。**把订单表中的每个模块、附加项和云服务与您的设计需要进行对比。
2. **规模检查。**根据人们实际将如何使用系统，而不是他们的职位名称，来检验您的FUE数量。
3. **谈判清单。**续约条款、AI额度条款、包含的模块和分阶段定价，写成采购部门可以拿去与SAP谈的要点。

FUE如何计算、订阅包含和不包含什么，以及要向SAP提出的问题，都在我的[RISE with SAP定价指南](/zh-CN/rise-with-sap-contract-pricing/)中。这是来自项目工作的实用指导，不是法律意见。您的合同律师仍然应该审阅订单表。

### 2. RISE迁移建议

RISE是外包装。在它下面仍然是一次ERP迁移，有三条可能的路径：绿地（新实施）、棕地（系统转换）或选择性数据转换。公有版只能新实施，所以版本选择和路径选择必须一起做出。

我的路径原则是：当您从其他系统迁移过来，或者必须定义新流程时，选绿地。当流程已经定义好并且运行良好时，选棕地。当某些领域的流程需要重新定义时，选选择性数据转换。

迁移建议为您提供：

1. **版本建议。**根据您的流程标准化程度以及您所在的行业，选择公有版还是私有版。
2. **路径建议。**绿地、棕地或选择性数据转换，与您的流程和数据发现相挂钩。
3. **切合实际的时间表。**对于RISE项目，我按9到18个月来计划；基于公有版的GROW项目通常需要6到9个月。
4. **合作伙伴需求说明。**用您自己的话写出的范围，让合作伙伴按照您的设计而不是他们的设计来报价。

完整的分步说明、工具以及SAP ECC的维护截止日期，都在我的[ECC到S/4HANA迁移指南](/zh-CN/ecc-to-s4hana-migration/)中。关于不同路径下预算由什么决定，请阅读我的[S/4HANA迁移成本](/zh-CN/s4hana-migration-cost/)指南。

### 3. RISE就绪检查

SAP Readiness Check告诉您ECC系统中有哪些内容与S/4HANA冲突。它不会告诉您该怎么处理。就绪检查把这些结果转化为您可以拨款执行的决策。

就绪检查为您提供：

1. **对SAP Readiness Check的解读。**简化项、附加组件、自定义代码影响、接口和财务数据质量，向需要做决定的人解释清楚。
2. **自定义代码视图。**哪些对象会出问题，哪些应该淘汰而不是修复。
3. **接口和数据视图。**每个接口的两端，以及您的数据在迁移之前需要在哪里进行清洗。
4. **未决问题。**检查本身无法回答的决策清单，它将成为您迁移评估的范围。

Readiness Check覆盖什么、如何运行以及它的不足之处，都在我的[SAP Readiness Check与S/4HANA迁移评估](/zh-CN/sap-readiness-check-migration-assessment/)指南中。如果您是SAP新客户，而不是从ECC迁移，我的[GROW with SAP页面](/zh-CN/sap-implementation/grow-with-sap/)是更好的起点。

## RISE with SAP适合您吗？

当您是现有SAP客户、您的ECC或本地S/4HANA系统是业务的核心，并且您希望由SAP而不是您自己的团队或托管服务商来运营技术栈时，RISE最合适。当您不愿意采用标准流程，或者企业内部没有人能就范围、数据和自定义代码做出决定时，它就不那么合适。

签约之前，请问自己这些问题：

1. 我们是否已经在公有版和私有版之间做出了决定，还是默认选择了私有版？
2. 我们是否知道哪些自定义对象仍在使用？
3. 我们的FUE数量是基于人们将如何使用系统，还是基于职位名称？
4. 合同价格是否与我们的推广阶段相匹配？
5. 既然SAP只运营技术层，那么上线后的功能支持由谁负责？

如果其中有两个或更多问题没有明确答案，请在签订单表之前，而不是之后，把它们解决掉。

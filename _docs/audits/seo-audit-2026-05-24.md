# SEO audit — 2026-05-24

Audit run against the Next.js codebase at `noeldcosta-web/` per `_docs/audits/_prompts/audit-2-seo.md`. The migration target is zero URL changes from the WordPress origin at noeldcosta.com; GTranslate stays in place externally and serves all `/{lang}/` paths. The Next.js site must serve English at flat URLs only.

This is a report. No code changed in this pass.

## 1. URL preservation table

### How the routing works today

The codebase still nests every route under `src/app/[lang]/`. `src/proxy.ts` is a Next.js 16 middleware (the renamed `middleware.ts`) that rewrites any non-locale-prefixed request to `/en/{path}` invisibly, so the browser address bar shows the flat WP-equivalent URL while the server renders `/en/...`. From an end-user / Googlebot perspective the URLs *appear* flat. From an audit perspective the `[lang]` segment still exists in the source tree, every page generates static params for 14 locales, and the metadata + sitemap + JSON-LD all emit `/{lang}/` variants. The audit-2 prompt is explicit that this counts as a critical issue and that the segment must be removed (see Part 2 for scope).

The catch-all responsible for arbitrary WordPress slugs is `src/app/[lang]/[slug]/page.tsx`. It only handles **single-segment** paths. Anything with a `/` in the middle (`/sap-implementation/for-aviation/`, `/ai-insights-shiftgearx-noeldcosta/erp-implementation-cost-calculator/`) has no matching route at all and will 404 the moment the WordPress origin is taken offline.

### Locale plumbing to remove or stub

- `src/lib/locales.ts` exports `LOCALES` (14 entries), `TIER_1_LOCALES`, `RTL_LOCALES`, and the `Locale` type. Re-exported from `src/lib/content.ts:10-11`. Either delete the file and replace each importer with the literal "en", or shrink `LOCALES` to `["en"]` and let the rest of the code collapse naturally.
- `src/proxy.ts` (the new Next.js 16 middleware) rewrites every flat request to `/en/{path}`. After removing `[lang]`, the proxy has nothing to do — delete it, including the `matcher` config. The header rules in `next.config.ts:58-81` are unaffected (they live in `headers()` not middleware).
- `src/lib/content.ts:11` re-exports `LOCALES`. `getPost(slug, locale)`, `getPage(slug, locale)`, `getAllPosts(locale)`, etc. all take a `locale` parameter that defaults to `"en"`. Callers will need their `locale: Locale` parameter removed or the helper signatures simplified.
- `src/lib/seo.ts:20-39` defines `LOCALE_HREFLANG` and `localePath(locale, slug)`. `buildPostMetadata` and `buildPageMetadata` (lines 64-153) build a per-page `languages` dict for hreflang. `articleJsonLd` uses `localePath` to build URLs. All of this collapses to `/${slug}` and a single `inLanguage: "en"`.
- `next.config.ts` has **no** i18n config — clean.

### Components and pages that take `locale` props

`PostPage`, `CategoryPage`, `MdxPageLayout`, `CaseStudyArticlePage`, `CaseStudyPortfolioPage`, `ArticleHero`, `AuthorBox`, `RelatedArticles`, `PostCard`, `StartHereRow`, `BreadcrumbList` builders. Every one of them computes `const localePrefix = locale === "en" ? "" : "/" + locale` and threads it through `Link href={…}`. Removing locale = strip the prefix and inline the literal slash. Roughly 12 component files.

### One-paragraph estimate

Remove all `[lang]/...` directory shells (13 file groups), delete `src/proxy.ts`, strip the LOCALES traversal from `src/app/sitemap.ts` and the hreflang annotations from `src/lib/seo.ts`. Either delete `src/lib/locales.ts` outright or reduce it to a stub re-exporting `"en"` so existing imports don't break in one sweep. Then a follow-up pass through ~12 components to remove `locale: Locale` props and `localePrefix` computation. Estimated 25-30 file edits and a build verification. None of the MDX content files in `content/` need to change — they're already English-only when `*.mdx` is the canonical (the `*.raw.mdx` siblings can stay for historical reference or be removed in a separate clean-up).
